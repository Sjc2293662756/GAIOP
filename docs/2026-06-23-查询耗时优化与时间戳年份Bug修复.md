日期：2026-06-23

## 背景

用户反馈 NAPM 查询耗时过长（10-19 秒），排查远端日志后发现两个严重问题：
1. LLM 自行计算的时间戳年份错误（2025 vs 2026），导致查询返回空数据
2. OpenClaw Memory 子系统故障，每次查询白白浪费 7 秒

## 问题1：时间戳年份错误

### 根因

LLM 在构造 `resolvedQuery` 时，未调用 `napm-resolve-time-range` 工具，而是自行计算了时间戳。LLM 知道当前是 "2026-06-23 17:50 CST"，但在计算 `start = now - 86400` 时，内部算术出错，产出了 2025 年的时间戳。

NAP API 收到 2025 年时间戳后返回空数据，LLM 误判为"该时段内没有丢包事件"，给用户错误结论。

### 影响

- 查询返回空数据，用户无法获得真实答案
- LLM 基于错误结果作出错误推断和建议
- 浪费 3 秒在无效查询和困惑上

### 修复

**文件**：[`skills/openclaw-napm-query/services/ResolvedQueryTimeRangeService.js`](../skills/openclaw-napm-query/services/ResolvedQueryTimeRangeService.js)

新增三个函数：

```javascript
// 检查时间戳是否在合理范围内（距当前服务器时间 < ~1.1 年）
function isTimestampFresh(timestamp, nowSeconds)

// 批量校验 start/end 时间戳的新鲜度
function validateTimeRangeFreshness(start, end, nowSeconds)

// 自动修正过期时间戳：保留 HH:MM:SS，替换为当前年份
function autoCorrectTimestampIfStale(timestamp, nowSeconds)
```

**文件**：[`skills/openclaw-napm-query/scripts/run_napm_query.js`](../skills/openclaw-napm-query/scripts/run_napm_query.js)

在 `normalizeResolvedQueryTimeRange()` 中接入校验逻辑：

```
if (时间戳不在合理范围内) {
  自动修正年份 → 记录审计日志 napm_skill_time_range_stale_corrected
}
```

### 效果

- LLM 即使传了 2025 年时间戳，skill 在毫秒级自动修正为 2026
- 每次修正都记录审计日志，便于追踪 LLM 的时间计算问题频率
- NAPM API 收到正确年份，返回真实数据

## 问题2：Memory 子系统故障

### 根因

OpenClaw 的 Memory 子系统在每次查询时尝试：
1. 用 SQLite FTS5 做全文搜索检索历史上下文
2. 调用 Embedding API 做语义搜索

但远端服务器上：
- SQLite 编译时未开启 FTS5 支持 → `fts unavailable: no such module: fts5`
- Embedding API 被限流 → 触发指数退避重试（10 次，每次 0.5-2.2s）

两个失败串行发生，累计浪费 **7 秒**（占 19 秒总耗时的 37%）。

### 影响

- 每次 NAPM 查询增加 7 秒固定延迟
- 对于简单查询（如单指标 TopN），延迟占比超过 60%
- 用户感知"系统很慢"，实际是 Memory 子系统空转

### 修复

**远端服务器**：`/home/netinside/.openclaw/config.yaml`

新增配置：
```yaml
memory:
  embeddings:
    enabled: false
  fts:
    enabled: false
```

**操作步骤**：
1. 备份原配置：`config.yaml.bak-20260623`
2. 写入新配置
3. 重启 OpenClaw（kill HUP → 进程自动重启，新 PID 3149135）

### 效果

- 查询不再触发 Memory 检索，节省 7 秒固定延迟
- 用户感知从 19 秒降至 5-8 秒
- 如后续需要 Memory 功能，需先安装带 FTS5 的 SQLite 并解决 Embedding API 限流问题

## 后续建议

1. **LLM 时间计算**：在 `openai.yaml` 的 Metric guardrails 中增加"始终使用 napm-resolve-time-range 工具计算时间戳，禁止自行计算"的规则
2. **Memory 功能恢复**：如果后续需要 Memory 功能，需在远端服务器安装带 FTS5 编译选项的 SQLite，并配置可用的 Embedding API
3. **LLM 推理优化**：精简 `openai.yaml` 的 default_prompt，将低频 guardrail 移至 reference 文件按需加载
4. **Tool call 合并**：将时间解析和查询构造合并为单次 tool call，减少 LLM 往返轮次
