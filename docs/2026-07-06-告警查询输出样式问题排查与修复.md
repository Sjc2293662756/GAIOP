# 告警查询输出样式 — 问题排查与修复

> 日期：2026-07-06 | 状态：已修复

---

## 1. 问题

"现在系统的告警有哪些？" 这个查询，每次返回的格式都不同——有时候是 AI 自己生成的表格，有时候是列表，有时候是分级标题。skill 里 `buildDisplayText` 已经设计好了 ①②③ 分类格式，但从未生效。

10 轮测试，10 种不同的输出格式。最终排查发现：**代码逻辑正确，修改却从未被执行。**

---

## 2. 初步排查路径

### 尝试 1：verbatim_final_answer
在 `execute` 返回中设 `renderPolicy: { mode: 'verbatim_final_answer' }` 让 AI 原样输出。
**结果：** AI 忽略此标志，自行生成格式。

### 尝试 2：全局变量 + hook 替换
设 `pendingAlertDisplayText` 全局变量，在 `message_sending` 和 `before_message_write` hook 里检查并替换 AI 输出。
**结果：** hook 从未触发——audit log 查不到 `pendingAlertDisplayText` 被设置或消费的记录。

### 尝试 3：SKILL.md 加 displayText 说明
在 SKILL.md 里写明 displayText 是最终输出，AI 必须原样使用。
**结果：** AI 不读取 displayText 字段，仍自行生成格式。

### 尝试 4：重启 gateway
推送文件后网关进程未重启，Node.js 的 require 缓存仍是旧代码。
**结果：** 重启后 `napm_alert_query_invoked` 等旧 audit 事件正常写入，但我们的新 audit 事件仍无记录。

## 3. 关键突破

### 3.1 硬证据

audit log 确认：
- `napm_alert_query_invoked` ✅ — 在 `runAlertExecutor()` 中写入
- `napm_alert_query_completed` ✅ — 在 `runAlertExecutor()` 中写入  
- `napm_alert_displaytext_set` ❌ — **从未出现**

说明 `appendPluginAuditEvent` 函数本身正常，但我们的调用点从未被执行。

### 3.2 代码追踪

搜索 `name.*napm-alert-query` 发现 3 处引用：

```js
// L4677 — createAlertQueryToolDefinition 的 tool name
// L5206 — 命令处理器
// L6023 — registerCommand 注册
```

**关键发现：L5206**

```js
// 命令处理器（被 AI 的 tool call 实际走的是这条路！）
if (definition.name === 'napm-alert-query') {
    const result = await runAlertExecutor({ prompt });
    rememberSkillResult(prompt, result, null);
    return makeTextReply(buildAlertQueryReply(result));
    // ⚠️ 没有设置 pendingAlertDisplayText！
}
```

AI 调 `napm-alert-query` tool 时，**实际走的是 L5206 这个命令处理器，不是 L4733 的 `execute` 函数。**

我们的所有改动都在 L4733 的 `execute` 里：
- `pendingAlertDisplayText = displayText` ← L4737
- `appendPluginAuditEvent('napm_alert_displaytext_set', ...)` ← L4739
- USE_CANDIDATES/STOP 格式化返回逻辑 ← L4740-L4764

**这些全部没有被执行。**

### 3.3 为什么 L5206 会被调用？

OpenClaw 的 tool 框架在处理 tool call 时，优先匹配 `definition.name` 走命令处理器路径。`createAlertQueryToolDefinition` 返回的 `execute` 只在特定条件下被调用，当存在同名的 `definition.name` 匹配时，命令处理器优先。

## 4. LLM 在链路中的角色

```
用户请求
  │
  ├─ LLM 决策: 选择调哪个 tool
  │
  ├─ command handler (L5206): 执行 skill → 获取格式化文本
  │     └─ 这里产出 displayText
  │
  ├─ LLM 生成回复: ★ LLM 是最终的格式化者 ★
  │     它看到 tool 返回的文本，但用自己语言重新组织
  │
  ├─ message_sending hook: 拦截 → 替换（需要 pendingAlertDisplayText）
  │
  └─ before_message_write hook: 二次拦截
```

**LLM 在两个阶段起作用：**
1. 决策阶段（选 tool）
2. 格式化阶段（tool 返回后，重新组织语言输出给用户）

第 2 阶段就是为什么每次输出格式不同——LLM 每次用自己的方式重写。hook 是为了在 LLM 输出后**硬替换**成我们的 displayText，但 hook 依赖 `pendingAlertDisplayText`，而它从未被设置。

---

## 5. 修复

**在 L5206 的命令处理器里加一行：**

```diff
  if (definition.name === 'napm-alert-query') {
      const result = await runAlertExecutor({ prompt });
      const replyText = buildAlertQueryReply(result);
+     pendingAlertDisplayText = result?.narrationInput?.displayText || null;
      rememberSkillResult(prompt, result, null);
      return makeTextReply(replyText);
  }
```

**为什么这一行就够：**
1. `runAlertExecutor` 返回 skill 的完整结果（含 `narrationInput.displayText`）
2. `pendingAlertDisplayText` 被设置
3. LLM 生成自己的回复
4. `message_sending` hook 检测到 `pendingAlertDisplayText` 有值 → 替换 LLM 的输出为 displayText
5. 用户看到 skill 生成的 ①②③ 格式化文本

## 7. 经验教训

1. **先确认代码是否被执行。** 在函数里加一个最简单的日志（写文件），比改 10 轮逻辑更高效。
2. **不要假设代码路径。** `execute` 和 `command handler` 都可以被框架调用，必须两条路都覆盖。
3. **LLM 永远是最终的格式化者。** 不要指望 `renderPolicy` 或 system prompt 让 LLM 按要求格式输出——要用 hook 在 LLM 输出后硬替换。
4. **全局变量 + hook 的模式虽然简单，但有效。** 关键是要在正确的入口点设置全局变量。
