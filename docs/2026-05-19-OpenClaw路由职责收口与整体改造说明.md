# 2026-05-19 OpenClaw 路由职责收口与整体改造说明

最后更新：2026-05-19

## 1. 这次到底在解决什么问题

当前线上最核心的问题，不是 OpenClaw “没理解用户问题”，而是：

- 它已经能较稳定识别对象和意图
- 但“理解之后该走哪条查询路径”这件事，没有被一个唯一层统一接管
- 结果就是简单问题也会在多层之间来回试探

这也是为什么像：

- `系统中都有哪些业务？`

这种本该第一时间进入固定元数据查询入口的问题，会出现很多中间尝试，导致：

- reasoning preview 里看起来像在反复排查
- 收敛速度慢
- 同一句话在不同入口下可能走不同路

一句话总结：

**当前真正的问题不是“再多补几个问法”，而是“路由职责分散，缺少单一判路源”。**

## 2. 这次梳理后的整体结论

当前项目应该按下面这条主线理解：

`OpenClaw 主链 -> napm-openclaw-plugin -> openclaw-napm-query skill -> NAPM API`

其中三层职责应该继续收口为：

- `OpenClaw 主链 + napm-openclaw-plugin`
  - 负责问句边界识别
  - 负责 prompt 路由判定
  - 负责把简单问法尽早注入为结构化 `resolvedQuery`
  - 负责阻止模型绕开 skill 乱走其他工具

- `openclaw-napm-query skill`
  - 负责执行结构化查询
  - 负责元数据调用、路径规划、overview 执行、结果 contract 输出
  - 允许保留少量 prompt fallback，但它只能是兜底，不应该再承担主判路职责

- 企业微信插件
  - 继续只做通道和结果承载
  - 不参与新的语义判路改造

这次修改的方向，就是把原来散在多处的“简单问句该走哪条路”继续往一个共享路由层收。

## 3. 这次确认出的结构性根因

之前真正让系统“越补越乱”的点，有三个：

### 3.1 同一类 prompt 的路由归属不唯一

之前至少有三处在做重叠判断：

- `napm-openclaw-plugin.remote.js`
- `skills/openclaw-napm-query/scripts/run_napm_query.js`
- 各自内部局部 fallback / refresh 逻辑

虽然单看每一处都“有道理”，但合起来就会变成：

- 一个入口先认为它是 overview
- 另一个入口又把它当作业务清单
- 回包阶段又可能再触发一次修正

这就是简单问题也会多次试探的根源。

### 3.2 插件两个入口的注入顺序不一致

插件内部此前存在两个关键入口：

- `prepareSkillExecutionArgs()`
- `buildCanonicalSkillToolParams()`

它们对同一句 prompt 的注入顺序并不完全一致。

这会导致：

- 同一句话从 tool execute 入口进来一个结果
- 从 `before_tool_call` 入口进来又是另一个结果

这是很典型的架构层不稳定，不是单个正则或单个 if 能彻底修好的问题。

### 3.3 `before_message_write` 长期承担了过多职责

这个钩子原本更适合做：

- 输出守门
- 同步保护
- 少量明显错误内容替换

但之前它逐步长成了：

- 同步重写最终结果
- 追加 Debug API
- 借 remembered result 做常规回复替换

这会让“展示层”慢慢变成“半个执行层”，后续继续补逻辑就一定越来越乱。

## 4. 这次实际做了什么

### 4.1 共享路由服务从“零散判断函数”提升为“统一判路入口”

修改文件：

- [PromptRoutingService.js](/g:/my_file/项目测试/观枢·智维平台-GAIOP/project_3/NAPM_Semantic_Gateway/skills/openclaw-napm-query/services/PromptRoutingService.js)

这次不再只提供：

- `isOverviewPrompt`
- `isMetricInventoryPrompt`
- `isBusinessObjectInventoryPrompt`
- `isHierarchyCatalogPrompt`

而是新增统一入口：

- `resolvePromptRoute(prompt, options)`

它负责按统一优先级输出最终路由结论。

当前一阶段优先级明确为：

1. 指标清单
2. 业务清单
3. 未知端口流量（按调用方是否接入）
4. 层级目录（按调用方是否接入）
5. overview

这意味着：

- “具体清单型问题”优先
- “总览型问题”最后兜底

这正是 `系统中都有哪些业务？` 这类问题应该有的判路顺序。

### 4.2 插件两个入口改成共用同一套路由注入决策

修改文件：

- [napm-openclaw-plugin.remote.js](/g:/my_file/项目测试/观枢·智维平台-GAIOP/project_3/NAPM_Semantic_Gateway/napm-openclaw-plugin.remote.js)
- [.codex-temp/napm-openclaw-plugin.remote.js](/g:/my_file/项目测试/观枢·智维平台-GAIOP/project_3/NAPM_Semantic_Gateway/.codex-temp/napm-openclaw-plugin.remote.js)

新增：

- `resolvePromptInjectedResolvedQuery()`

然后让下面两个入口都复用它：

- `prepareSkillExecutionArgs()`
- `buildCanonicalSkillToolParams()`

这样收口后：

- 同一句 prompt 不再由两个入口各自维护一套注入顺序
- 指标清单、业务清单、丢包特例、overview 覆盖逻辑都走同一个决策函数

这一步是本次最重要的“防继续缝补”改动之一。

### 4.3 `before_message_write` 回退为同步守门层

这次明确做了两件事：

- 去掉同步钩子里“仅为追加 Debug API 而重写整条消息”的逻辑
- 去掉“只因为 remembered skill result 存在，就常规同步替换指标清单回复”的逻辑

保留的只剩下更合理的同步职责：

- 明显越界回复拦截
- 明显错误内容同步纠偏
- reasoning 保护

而真正的“需要刷新 skill / 重新拿结果 / 异步替换”的工作，继续留在：

- `message_sending`

这说明插件边界现在更清楚了：

- `before_message_write` 是同步保护层
- `message_sending` 是异步纠偏层

## 5. 这次为什么不算“再补一个补丁”

因为这次改动不是单纯给某个问法再加一条 if，而是同时收了三类结构问题：

- 把 prompt 路由优先级抽成共享能力
- 把插件两个入口的注入顺序统一
- 把同步输出钩子从“半个执行层”拉回展示保护边界

也就是说，这次改动的价值不只体现在：

- `系统中都有哪些业务？`

这一个问法上。

更重要的是，它降低了后续继续出现下面这种问题的概率：

- 一个入口识别对了，另一个入口识别错了
- skill 明明能查，插件又把结果改乱
- 同步钩子偷偷承担越来越多执行职责

## 6. 本次修改后，项目整体应该继续怎么改

如果继续按专业程序员视角推进，后面建议按阶段做，而不是继续零碎补问法。

### 阶段 1：继续把 prompt 路由彻底集中

当前已集中了一部分，但还没完全结束。

下一步建议：

- 所有“简单固定问法 -> 结构化 resolvedQuery”的入口，继续统一交给 `PromptRoutingService`
- skill 里的 prompt fallback 也逐步改成优先调用共享路由，而不是在脚本里继续散写优先级
- hierarchy catalog 也可以逐步完全纳入共享路由主出口

目标：

**任何简单问法，只允许一个地方决定它走哪条路。**

### 阶段 2：把插件中的“刷新判断”继续模块化

当前插件里还有一批 refresh 判断函数：

- `shouldRefreshMetricInventory`
- `shouldRefreshBusinessObjectInventory`
- `shouldRefreshHierarchyCatalog`

它们现在已经比之前清晰，但仍然比较散。

下一步建议：

- 提炼成单独的 reply-guard / refresh-policy service
- 把“什么情况需要重新跑 skill”从插件主文件继续拆出去

目标：

**插件主文件只负责编排，不继续膨胀为超大策略脚本。**

### 阶段 3：让 skill 的 prompt fallback 真正退居兜底

当前 skill 仍保留 prompt fallback，是为了兼容和安全。

这没有问题，但长期目标应该是：

- 主链优先产生结构化 `resolvedQuery`
- skill 只在主链偶发漏判时兜底

目标：

**主链负责“先判路”，skill 负责“稳执行”。**

## 8. 对当前问题的直接结论

对于你最关心的现象：

- “系统中都有哪些业务？”这种简单问题为什么还会试很多次

这次的答案已经不是“再补一个业务清单规则”了，而是：

- 继续把 prompt 路由判定收成共享单点
- 保证插件所有入口使用同一套判路优先级
- 让展示层不再偷偷承担执行层职责

这次改动已经把这条主线往正确方向推进了一大步。

它不能保证以后所有 NAPM 语义问题一次性全部消失，但对“简单问题不该来回试探”这个核心现状，是一套更成体系、更不容易继续越补越乱的改法。
