# 2026-05-12 业务指标清单强制走 Skill 与旁路拦截修复说明

## 1. 本次修复的真实问题

企业微信实测里，`业务都可以查哪些指标？` 出现了两类错误链路：

1. 模型把原始问题改写成了 `业务组 BusinessGroup 都可以查哪些指标`
2. 模型没有调用 `napm-skill-query`，而是直接走了 `exec` / 直查工具

这会导致两个后果：

1. `业务` 与 `业务组` 口径混淆
2. 企业微信端可能直接看到英文中间推理与错误的 BusinessGroup 指标整理结果

---

## 2. 本次修复的核心设计

本次不再只修“回答文案”，而是收口“主链路规则”：

1. 只要是 NAPM 自然语言问题，第一跳必须先走 `napm-skill-query`
2. `before_tool_call` 不再只信当前 tool 参数，而是优先回看会话中的原始用户问题
3. 对 `业务都可以查哪些指标？` 这类指标清单问题：
   - 如果模型把 prompt 改写成 `BusinessGroup`
   - 或者想直接调用 `exec`
   - 或者想先走 `napm-topn / napm-average / napm-timeseries`
   都会被回正或拦截

---

## 3. 已修改的插件逻辑

修改文件：

- `.codex-temp/napm-openclaw-plugin.remote.js`
- `napm-openclaw-plugin.remote.js`

关键改动：

1. 新增 `derivePromptGuardState(...)`
   - 基于会话原始 prompt 重建当前判定状态
   - 不再只依赖本轮被模型改写后的参数

2. `before_tool_call` 改为：
   - 使用 `selectActivePromptText(conversationState, guardState, normalizePrompt(toolParams))`
   - 再基于该 prompt 计算真实 guard state

3. 对 `napm-skill-query`：
   - 若发现 prompt 被改写，会强制 canonicalize 回原始问题
   - `业务都可以查哪些指标？` 会重新落到 `WebApplication`

4. 对直接 NAPM 工具：
   - 在当前轮还没先走 skill 时，不允许直接执行
   - 会被强制改写成“先转发给 skill”

5. 对非 skill 工具：
   - 只要当前是 NAPM 自然语言问题，就直接 block
   - 典型如 `exec`

## 4. 指标分类口径补充

根据当前项目文档口径：

### 4.1 业务类对象

业务类对象：

```text
WebApplication / PageFamily / User / ClientBusinessGroup
```

回答指标清单时，固定按以下分类说明：

```text
业务网络 / 业务访问 / 业务性能 / 响应代码
```

项目当前允许业务侧额外带：

```text
页面优化
```

### 4.2 非业务类对象

非业务类对象回答指标清单时，固定按以下 9 类说明：

```text
数据包 / 网络流量 / 传输效率 / 网络性能 / 网络连接 / 应用访问 / 应用性能 / 用户体验 / 安全分析
```

本次也补齐了 `BusinessGroup` 侧缺失的 `安全分析` 分类描述。

## 6. 当前结论

可以确认的是：

1. `业务都可以查哪些指标？` 这类问题，远端插件层已经不会再放行 `exec` 旁路
2. 即使模型把问题改写成 `BusinessGroup`，也会在调用 skill 前被回正为原始业务口径

还需要你做的最后一层验证是：

1. 直接在企业微信端再问一次 `业务都可以查哪些指标？`
2. 观察是否仍有英文中间推理片段被发出
3. 观察最终回答是否回到业务类固定分类口径

如果企业微信端这次仍出现英文中间推理，就说明 OpenClaw 还存在更前置的流式发送钩子未收住；那时需要继续查是否存在更早的 streaming hook 可以拦截。
