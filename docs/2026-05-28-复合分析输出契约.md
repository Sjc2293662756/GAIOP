## 1. 文档目标

本文档定义功能一复杂分析的最终输出形态。

它解决三个问题：

- skill 已经执行出结构化结果后，最终中文回答应该包含哪些固定信息。
- discovery、focused overview、失败态分别怎么表达。
- 哪些话术会制造误导，必须禁止。

本文档只约束输出，不负责重新构造查询，也不允许输出层补查数据。

---

## 2. 输出层职责边界

### 2.1 输出层可以做什么

输出层可以：

- 读取 skill 返回的结构化数据。
- 归纳 discovery 发现对象。
- 归纳 overview 关键指标和异常方向。
- 组织中文结论、证据、建议动作。
- 标注数据时间范围。
- 在数据为空或失败时如实说明。

### 2.2 输出层不能做什么

输出层禁止：

- 补调南向 API。
- 用 curl、Python、临时脚本补结果。
- 编造对象、指标或原因。
- 因为结果为空而换 service。
- 因为结果不理想而修改对象类型。
- 把内部推理、尝试过程、fallback 过程暴露给用户。
- 用历史轮次结果替代本轮 skill 结果，除非用户明确要求沿用。

## 3. 标准输出结构

复杂分析输出至少包含六部分：

```text
1. 结论
2. 发现对象
3. 发现依据
4. 聚焦分析证据
5. 时间范围
6. 建议动作
```

推荐中文结构：

```text
结论：
本次最需要关注的是 <对象>，主要问题是 <异常方向>。

发现对象：
按 <discovery 指标> 排序，<对象> 排名第 1，指标值为 <value>。

关键证据：
- <指标1>：<值>，说明 <含义>
- <指标2>：<值>，说明 <含义>
- <指标3>：<值>，说明 <含义>

分析判断：
综合看更像 <原因方向>，不是 <排除方向>。

建议动作：
建议优先检查 <对象关联方向>。

数据时间：
<displayText>，<startText> 至 <endText>。
```

## 4. 输出字段契约

### 4.1 顶层字段

| 字段 | 必填 | 来源 | 说明 |
|---|---|---|---|
| `summary` | 是 | skill result / narration | 一句话结论 |
| `target` | 视场景 | discovery 或 groups | 聚焦对象 |
| `evidence` | 是 | overview / topValues rows | 关键证据列表 |
| `timeRange` | 是 | resolvedQuery 顶层 | 数据时间 |
| `recommendations` | 否 | narration | 建议动作 |
| `failure` | 失败时必填 | skill error | 失败阶段和原因 |

### 4.2 target 字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `objectType` | 是 | `WebApplication` / `BusinessGroup` / `IPAddress` 等 |
| `argument` | 是 | 可执行对象参数 |
| `label` | 否 | 展示名称 |
| `source` | 是 | `explicit_user_input` / `discovery_result` |

### 4.3 evidence 字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `metric` | 是 | 指标 ID |
| `metricName` | 否 | 中文指标名 |
| `value` | 是 | 指标值 |
| `unit` | 否 | 单位 |
| `direction` | 否 | 入向 / 出向 / 总量 |
| `meaning` | 否 | 用于中文解释 |

## 5. discovery + focused overview 输出

适用于：

```text
找到连接失败最多的地址，然后分析它。
丢包最严重的 IP 是谁，为什么？
哪个业务 HTTP 500 最严重，并分析原因？
```

输出顺序必须是：

```text
先说明 discovery 发现谁。
再说明为什么它被选中。
再说明 focused overview 的综合分析。
最后给建议。
```

示例：

```text
结论：
最近一小时连接失败最需要关注的是 101.254.114.237。

发现依据：
按 RFCI（流入连接失败数）排序，该 IP 排名第 1，RFCI 为 128 次。

关键证据：
- CONI：2,360 次，说明该 IP 流入连接请求量较高。
- RFCI：128 次，说明连接失败集中在入向。
- CSTI：320 ms，说明建连耗时偏高。

分析判断：
该问题更像服务端连接接收或中间网络链路不稳定导致，不只是普通流量升高。

建议动作：
优先检查该 IP 对应服务端端口、连接队列、防火墙策略和关联会话。

数据时间：
最近一小时，2026-05-28 14:07 至 15:07。
```

## 6. focused overview 输出

适用于用户已经明确对象：

```text
可观测239web 为什么慢？
Default-Internet 工作组整体情况怎么样？
回溯238 这个应用是否异常？
```

输出顺序：

```text
先给对象当前状态结论。
再给支撑结论的核心指标。
再指出主要异常方向。
最后给建议。
```

示例：

```text
结论：
可观测239web 最近一小时存在页面响应偏慢，主要体现在慢页面数量和平均页面耗时。

关键证据：
- PGTME：2.8 s，页面平均耗时偏高。
- PGNSLPGE：46 个，慢页面数量较多。
- PGHTTP500：0 次，暂未看到明显服务端 500 错误。

分析判断：
当前更像页面性能或服务端响应耗时问题，不像 HTTP 500 错误主导。

建议动作：
优先查看慢页面 TopN、服务端处理耗时和对应接口。

数据时间：
最近一小时，2026-05-28 14:07 至 15:07。
```

## 7. 普通 TopN 输出

普通 TopN 不要强行给复杂原因分析。

适用于：

```text
最近一小时丢包最高的前 10 个 IP。
今天吞吐量最大的前 10 个 IP。
```

输出结构：

```text
查询结果：
按 <topMetric> 排序，前 <topCount> 个 <objectType> 如下：

| 排名 | 对象 | 指标值 |
|---|---|---|

补充说明：
只解释显著异常，不要编造原因。

数据时间：
...
```

如果用户问“为什么”或“分析原因”，才进入复合分析或 focused overview。

## 8. 元数据清单输出

适用于：

```text
系统中有哪些业务？
系统中有哪些工作组？
系统中有哪些自动识别的应用？
```

输出必须说明查询口径：

```text
系统中目前有 9 个业务系统（WebApplication，applications Type=3）：
...

查询口径：
南向 applications 目录，按 Type=3 识别 WebApplication/业务系统。
这不是按流量活跃度过滤，也不是中文名称过滤。
```

不同对象的口径：

| objectType | 必须说明的口径 |
|---|---|
| `WebApplication` | `applications Type=3` |
| `BusinessGroup` | `businessGroups` |
| `DefinedApp` | `applications Type=2` |
| `CompositeApplication` | `applications Type=4` |

## 9. 失败态输出

### 9.1 discovery 无数据

当 discovery 返回空：

```text
本次未在指定时间范围内发现符合条件的对象，因此没有进入聚焦分析。

查询对象：IPAddress
排序指标：PLI
时间范围：最近一小时，2026-05-28 14:07 至 15:07。
```

禁止：

- 说“系统一定正常”。
- 沿用上轮对象。
- 换一个指标继续查后直接回答。

### 9.2 discovery 执行失败

当 discovery 查询失败：

```text
本次未能完成“先发现对象”的步骤，因此没有进入聚焦分析。

失败阶段：discoveryQuery
查询对象：IPAddress
排序指标：RFCI
失败原因：<error message>
```

### 9.3 focused overview 执行失败

当 discovery 成功但 overview 失败：

```text
已锁定需要分析的对象：101.254.114.237。
发现依据：按 RFCI 排名第 1。

但聚焦分析执行失败，因此不能给出原因判断。
失败阶段：focusedOverview
失败原因：<error message>
```

### 9.4 语义不完整

如果无法确认“严重”指什么：

```text
你想按哪个方向判断“最严重”：连接失败、丢包、HTTP 错误、响应时间，还是流量？
```

## 10. 禁止输出

以下输出必须禁止：

- “我先试试 overview，不行再试 groups。”
- “我用 curl / python 过滤了一下。”
- “端口 8083 不通，所以我直接查后端。”
- “当前问题必须经 NAPM skill 执行后才能回答。”
- “本轮未拿到有效 skill 结果，因此不展示主链推理。”
- “看起来应该是某某问题”，但没有指标证据。
- “因为结果为空，所以该系统正常。”
- “上次查到某对象，这次沿用它分析”，但用户没有要求沿用。
- 把 `Debug API` 默认暴露给最终用户。

## 11. 输出质量验收

| 编号 | 验收点 | 通过标准 |
|---|---|---|
| OC001 | 有结论 | 第一段给出明确结论或明确说明无数据 |
| OC002 | 有对象 | 明确对象类型和对象名称 |
| OC003 | 有依据 | 说明是哪个指标、哪个排序或哪个 overview 证据 |
| OC004 | 有时间 | 展示用户可读时间范围 |
| OC005 | 不泄露内部过程 | 不出现 curl、python、fallback、端口探测、内部尝试 |
| OC006 | 不编造原因 | 每个原因判断都有指标或结果支撑 |
| OC007 | 失败态清楚 | 失败时说明失败阶段，不继续编造 |
| OC008 | 口径清楚 | 元数据清单说明 provider 和 Type 过滤 |
