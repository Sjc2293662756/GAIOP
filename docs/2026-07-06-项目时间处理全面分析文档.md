## 一、概述与核心原则

### 1.1 核心原则

整个项目遵循以下时间处理原则：

| 原则 | 说明 |
|------|------|
| **LLM 只传时间描述，插件计算时间戳** | LLM 传递 `timeRange.key`（如 `last1hour`），插件用 `Date.now()` 计算实际 start/end。LLM 永不算 Unix 数字 |
| **Unix 秒为单位** | 所有内部时间统一使用 Unix 时间戳（**秒**），不是毫秒 |
| **60 秒分钟对齐** | 所有查询时间戳对齐到 60 秒边界（`floorToMinute`） |
| **服务器本地时间** | `Date.now()` 依赖服务器系统时钟（假定已 NTP 同步），无额外时区转换 |
| **防御深度** | 插件层 → 契约校验层 → Skill 进程内校验，三层防护 |
| **Asia/Shanghai 显示** | 所有面向用户的时间展示使用 `Asia/Shanghai`（UTC+8） |

### 1.2 统一的数据流

```
用户输入（自然语言）
    │
    ▼
LLM 解析 → timeRange.key（如 "last1hour"、"today"）
    │
    ▼
Plugin 层（napm-openclaw-plugin.remote.js）
  └─ runSkillExecutor: Date.now() → 计算 start/end → 注入 resolvedQuery
    │
    ▼
契约校验层（validateResolvedQueryTimeContract）
  └─ 检查: 分钟对齐、root-level start/end、时间新鲜度
    │
    ▼
Skill 进程（run_napm_query.js）
  └─ normalizeResolvedQueryTimeRange: 二次校验 + 自动修正
    │
    ▼
NAPM API 调用（start/end 作为查询参数）
```

### 3.2 Layer 1: 时间描述解析层

**文件**: [skills/openclaw-napm-query/services/ResolvedQueryTimeRangeService.js](../skills/openclaw-napm-query/services/ResolvedQueryTimeRangeService.js)

这是专门为 NAPM 查询设计的时间范围解析服务，是整个项目的**时间中枢**。

#### 核心函数

**`resolveTimeRange(input, options)`** — 主入口
```javascript
// 输入: { timeRangeKey: 'last1hour', prompt: '最近1小时流量' }
// 输出: { key, displayText, start, end, source, alignment, boundary }
```

**`inferTimeRangeKeyFromPrompt(prompt)`** — 从自然语言推断时间意图
- 支持中文: 今天、昨天、最近X分钟/小时/天、过去X天
- 支持英文: today, yesterday, last X minutes/hours/days, past
- 兜底: `last1hour`

**`resolveKnownTimeRangeKey(key, nowSeconds)`** — 已知键 → 时间范围
- 支持: `today`, `yesterday`, `last1hour`, `last24hours`, `lastNminutes`, `lastNhours`, `lastNdays`

#### 时间新鲜度校验

**`isTimestampFresh(timestamp, nowSeconds)`**
- 检查年份是否匹配当前年份（第一道防线）
- 检查时间戳距当前时间 < 400 天（~1.1 年容差）
- 年份不匹配 → 直接判定为 `false`

**`validateTimeRangeFreshness(start, end, nowSeconds)`**
- 批量校验 start/end 的新鲜度
- 返回 `{ ok, issues[], nowSeconds }`

**`autoCorrectTimestampIfStale(timestamp, nowSeconds)`**
- 年份不匹配 → 保留月日时分秒，替换年份为当前年
- 距离太远 → 同样修正年份
- 新鲜 → 原值返回

#### 时间范围构建方法

| 方法 | 逻辑 | 边界 |
|------|------|------|
| `buildLast1HourTimeRange()` | now - 3600 → now | minute_floor |
| `buildLast24HoursTimeRange()` | now - 86400 → now | minute_floor |
| `buildTodayTimeRange()` | 今日 00:00 → 23:59 | local_day |
| `buildYesterdayTimeRange()` | 昨日 00:00 → 23:59 | local_day |
| `buildRelativeTimeRange(key, seconds)` | now - seconds → now | minute_floor |
| `buildLocalDayTimeRange(key, dayOffset)` | day±offset 00:00 → 23:59 | local_day |

### 3.3 Layer 2: 插件主防线（时间描述替代时间戳）

**文件**: [napm-openclaw-plugin.remote.js](../napm-openclaw-plugin.remote.js)

位置: `runSkillExecutor` 函数，约 line 2618-2648

这是 **2026-06-29** 实施的核心改动——"时间描述替代时间戳"方案。

#### 实现逻辑

```javascript
// LLM 只传 timeRange.key，插件用 Date.now() 无条件计算 start/end
if (isPlainObject(payload.resolvedQuery)) {
  const rq = payload.resolvedQuery;
  const needsTime = ['topValues','averageValues','timeValues','overview','topValues_multi_protocol'];
  if (needsTime.includes(String(rq.service || '').trim())) {
    const now = Math.floor(Date.now() / 1000);
    const floor = (v) => Math.floor(v / 60) * 60;
    const timeKey = String(rq.timeRange?.key || '').trim() || 'last1hour';

    if (timeKey === 'today') {
      // 今日 00:00:00 ~ now
    } else if (timeKey === 'yesterday') {
      // 昨日 00:00:00 ~ 昨日 23:59:00
    } else {
      const DURATION_MAP = {
        last5minutes: 300,
        last1hour: 3600,
        last24hours: 86400,
        last1day: 86400,
        last7days: 604800,
        last30days: 2592000
      };
      const duration = DURATION_MAP[timeKey] || 3600;
      start = floor(now - duration);
      end = floor(now);
    }

    rq.start = start;  // 无条件覆盖
    rq.end = end;
  }
}
```

#### 关键设计点

| 设计 | 说明 |
|------|------|
| **无条件覆盖** | 不管 LLM 传了什么 start/end，一律用服务器时间重新计算 |
| **默认 last1hour** | 如果 LLM 没传 timeRange.key，默认最近 1 小时 |
| **只对需要时间的 service 生效** | topValues, averageValues, timeValues, overview 等 |
| **内联实现** | 不依赖 Skill 进程的 ResolvedQueryTimeRangeService，避免跨进程依赖 |
| **分钟对齐** | 所有计算结果取整到 60 秒边界 |

### 3.4 Layer 3: 契约校验层

**文件**: [napm-openclaw-plugin.remote.js](../napm-openclaw-plugin.remote.js)

#### `validateResolvedQueryTimeContract(normalizedResolvedQuery, serviceName)`

执行以下校验：

| 校验项 | 规则 | 违规后果 |
|--------|------|---------|
| 时间戳位置 | start/end 必须在 root-level，不能在 timeRange 内 | 阻止执行 |
| 分钟对齐 | start/end 必须对齐 60 秒边界 | 阻止执行 |
| 时间戳存在 | 数据类 service 必须有 start/end | 错误提示 |
| 时间先后 | end > start | 错误提示 |

#### `validateResolvedQueryAgainstSpec(resolvedQuery, options)`

- 检测相对时间范围是否过期（`relative_time_range_stale_or_miscalculated`）
- 对比 LLM 传的时间戳与服务器重新计算的时间戳
- 偏差 > 容差值 → 标记为过期

#### 时间戳工具函数

```javascript
// roundToNearestMinute — 分钟取整
function roundToNearestMinute(ts) {
  return Math.floor(ts / 60) * 60;
}

// buildDefaultResolvedTimeRange — 构建默认时间范围
const end = roundToNearestMinute(Math.floor(Date.now() / 1000));
// 默认: last 24 hours
```

### 3.5 Layer 4: Skill 进程防线

**文件**: [skills/openclaw-napm-query/scripts/run_napm_query.js](../skills/openclaw-napm-query/scripts/run_napm_query.js)

#### `normalizeResolvedQueryTimeRange(resolvedQuery)`

在 Skill 进程内对时间范围做最后的规范化处理：
1. 从 `resolvedQuery.start/end` 或 `timeRange` 中提取时间范围
2. 调用 `validateTimeRangeFreshness()` 校验新鲜度
3. 如果时间戳过期，调用 `autoCorrectTimestampIfStale()` 修正
4. 记录审计日志 `napm_skill_time_range_stale_corrected`

这是**最后防线**——即使插件层的覆盖失败了，Skill 进程仍能修正错误的时间戳。

## 四、时区处理策略

### 4.1 当前策略

整个项目使用 **单一本地时区**，没有显式的时区转换逻辑：

| 层级 | 时区 | 说明 |
|------|------|------|
| 服务器系统时钟 | UTC+8（Asia/Shanghai） | `Date.now()` 和 `new Date()` 直接依赖 |
| NAPM 设备 | UTC+8（Asia/Shanghai） | 数据采集时间戳与服务器一致 |
| 用户展示 | UTC+8（Asia/Shanghai） | `Intl.DateTimeFormat('zh-CN', { timeZone: 'Asia/Shanghai' })` |
| Syslog 时间戳 | ISO 8601 +08:00 | `2025-06-16T10:30:00+08:00` |

### 4.2 时区配置位置

| 文件 | 时区配置 |
|------|---------|
| [InspectionFieldMapperService.js](../skills/openclaw-napm-inspection/services/InspectionFieldMapperService.js) | `this.timezone = options.timezone \|\| 'Asia/Shanghai'` |
| [InspectionTrafficAnalysisService.js](../skills/openclaw-napm-inspection/services/InspectionTrafficAnalysisService.js) | `const timezone = options.timezone \|\| 'Asia/Shanghai'` |
| [InspectionReportDataService.js](../skills/openclaw-napm-inspection/services/InspectionReportDataService.js) | `timezone: input.timezone \|\| 'Asia/Shanghai'` |

### 4.3 当前时区处理的局限

1. **无多时区支持**: 如果 NAPM 设备部署在不同时区，时间戳可能偏移
2. **硬编码 Asia/Shanghai**: 巡检相关服务硬编码了时区
3. **无 DST 处理**: 中国无夏令时，但如果扩展到其他地区需要注意
4. **依赖系统时钟**: `Date.now()` 的结果取决于服务器时钟是否准确（当前假设 NTP 已同步）

### 5.1 综述报告 (openclaw-napm-summary)

**文件**: [SummaryService.js](../skills/openclaw-napm-summary/services/SummaryService.js)

#### 时间范围解析 `_resolveTimeRange()`

```javascript
_resolveTimeRange(input = {}, scope = {}) {
  // Fault scope: 支持嵌套 faultWindow + baselineWindow
  // 普通 scope: sanity check — 不超过 1 年前或 1 天后
  const MAX_PAST_SEC = 365 * 86400;  // 1 year sanity bound
  if (!start || start < now - MAX_PAST_SEC || start > now + 86400) {
    start = now - 86400; // 默认最近 24 小时
  }
  if (!end || end < now - MAX_PAST_SEC || end > now + 86400) {
    end = now;
  }
}
```

| > 7 天 | 86400 秒（1 天） |

### 7.2 关键设计决策详解

#### 决策 1: LLM 不计算时间戳

**背景**: LLM 自行计算 Unix 时间戳频繁出错（年份错 30%，月日错 20%）。

**方案**: LLM 只传递时间描述（`last1hour`、`today`），由插件用 `Date.now()` 计算出实际的 `start/end`。

**实现位置**:
- 插件 `runSkillExecutor`: 无条件覆盖
- Skill 进程 `normalizeResolvedQueryTimeRange`: 最后一次修正

**相关文档**:
- [2026-06-29-时间描述替代时间戳方案.md](./2026-06-29-时间描述替代时间戳方案.md)
- [2026-06-29-服务器时间强制覆盖方案.md](./2026-06-29-服务器时间强制覆盖方案.md)

#### 决策 2: 防御深度

三层防护：
1. **插件层** — 无条件覆盖（主防线）
2. **契约校验层** — `validateResolvedQueryTimeContract` 阻止违规
3. **Skill 进程层** — `autoCorrectTimestampIfStale` 最后修正

#### 决策 3: 分钟对齐

所有查询时间戳对齐到 60 秒边界：
- NAPM API 以分钟为最小粒度
- 缓存友好（同一分钟内的查询可复用缓存）
- 避免秒级精度带来的不确定性

#### 决策 4: 单一本地时区

- 服务器和 NAPM 设备都在 UTC+8
- 不需要跨时区转换
- 简单可靠，但缺少多时区扩展性

### 7.3 已知问题与待改进

| 问题 | 影响 | 改进方向 |
|------|------|---------|
| 硬编码时区 | 巡检报告时间展示只支持 Asia/Shanghai | 从 NAPM 设备属性读取时区或支持配置 |
| 无历史时间查询兜底 | 用户查询"上周三"时 LLM 仍需计算具体日期 | 扩展 `timeRange.key` 语义支持绝对日期描述 |
| custom 时间范围容差粗糙 | custom 键给 2h 容差，可能覆盖用户精确意图 | 改进 custom 时间范围的解析和验证 |

| 无 NTP 监控 | 假定服务器时钟准确，没有主动检测 | 添加时钟偏移检测 |

## 附录: 时间处理 FAQ

### Q: 为什么使用 Unix 秒而不是毫秒？
A: NAPM API 使用 Unix 秒作为时间戳单位。整个系统统一使用秒以避免混淆。`Date.now()` 返回毫秒，使用时需除以 1000。

### Q: 如果服务器时钟不准怎么办？
A: 当前没有时钟偏移检测。信任服务器 NTP 已同步。如果时钟偏差 > 1 小时，会导致 NAPM 返回空数据。建议在生产环境启用 NTP 监控。

### Q: LLM 传了 start/end 会怎样？
A: 在插件层 `runSkillExecutor` 中会被**无条件覆盖**。这是设计如此——LLM 不可信，服务器时间才是真相来源。

### Q: today 的时间范围是怎么算的？
A: `today` = 今日 00:00:00 ~ 当前时间（分钟取整）。不是完整的一天，而是"从今天 0 点到现在的数据"。

### Q: yesterday 呢？
A: `yesterday` = 昨日 00:00:00 ~ 昨日 23:59:00（分钟取整）。注意结束时间是 23:59 而不是 24:00，这是有意设计的——最后 1 分钟留给数据聚合缓冲。

### Q: 为什么 custom 时间有 2 小时容差？
A: 用户可能说"查昨天上午 10 点到 11 点"——LLM 算的时间戳可能和服务器计算的"昨天 10:00"有 1-2 小时偏差（时区、对齐问题）。2 小时容差用于保护这类合理请求。而相对键（如 last1hour）只给 1 小时容差——LLM 没有理由偏差 >1 小时。
