# 当前真实流程

最后更新：2026-05-10

## 一、先记住最简链路

```text
企业微信用户
  -> wecom-openclaw-plugin
  -> OpenClaw 主链
  -> napm-openclaw-plugin
  -> openclaw-napm-query skill
  -> NAPM / NetInside WebService
  -> skill 输出 narration contract
  -> OpenClaw / WeCom 渲染最终中文回复
```

这条链路里：

- `WeCom` 负责接入和结果承载
- `OpenClaw 主链` 负责理解和决策
- `napm-openclaw-plugin` 负责 NAPM 路由、守卫、overview 纠偏
- `Skill` 负责结构化执行
- `NAPM API` 只负责提供数据

---

## 二、按步骤理解

### 1. 用户在企业微信提问

例如：

- `现在应用整体情况怎么样？`
- `现在业务整体情况怎么样？`
- `现在业务组整体情况怎么样？`
- `现在流量最大的地址是什么？`

消息先进入 `wecom-openclaw-plugin`。

这一层不是主理解层，但会负责：

- 收消息
- 把消息送进 OpenClaw
- 接收结构化结果
- 在结果回写时做一部分 overview 呈现保护

### 2. OpenClaw 主链判断问题性质

OpenClaw 主链当前应该先做这些判断：

- 这是不是 NAPM 范围的问题
- 是不是边界外问题
- 是不是 follow-up
- 是否需要澄清
- 是否应该直接进入 overview

这一层的目标，是形成结构化的 `resolvedQuery` 或明确的策略动作，而不是让下游继续猜。

### 3. napm-openclaw-plugin 接管 NAPM 路由

当问题进入 NAPM 主链后，`napm-openclaw-plugin` 会继续处理：

- 强制 NAPM 相关问题优先走 `napm-skill-query`
- 拦截危险工具调用
- 对 direct NAPM tool 做 reroute
- 对 overview 问句注入 / 修正 `resolvedQuery`
- 在最终回消息前，检查当前问句与缓存结果 scene 是否一致

这里要特别注意：

**如果当前问句是 overview，哪怕前面已经出现了错误的对象类型或旧缓存，这一层也应该按当前问句重新纠偏。**

### 4. skill 执行结构化查询

`openclaw-napm-query` skill 负责：

- 接收 `resolvedQuery`
- 规范化参数
- 校验对象、指标、时间窗
- 做 metadata 查询、路径规划、服务构造
- 执行 `topValues / averageValues / timeValues / overview`
- 输出 narration contract

它现在应该被理解成：

**查询执行器**

而不是：

**主自然语言理解器**

### 5. overview 问题走 overview-module

如果问句属于“整体情况 / 总览 / 概览”，skill 不应该把它当成单个 TopN 去答，而应该进入 overview 流程。

当前收口后的 scene 是：

- `应用整体` -> `application`
- `业务整体` -> `business`
- `业务组整体` -> `business_group`
- `网络整体` -> `network`
- `系统整体` -> `system`
- `安全整体` -> `security`

scene 进入后，再由 `overview-module` 选取对应模块组合出整体结论。

### 6. skill 输出 narration contract

skill 最终不应该只返回一堆 rows，也不应该只回一句硬编码文案。

它应输出统一 narration contract，至少包括：

- `responseType`
- `timeRange`
- `summary`
- `structuredRows / structuredSeries`
- `overview modules`
- `narrationStructure`

这份结构再交给上层统一组织中文回复。

### 7. OpenClaw / WeCom 渲染最终回复

最终中文回复不是简单打印 JSON，而是基于 narration contract 做结果表达。

这里当前要遵守两个关键原则：

- 如果是普通 query / topn / trend，可以按结构化结果正常渲染
- 如果是 `overview`，必须按“总览/概览”口径总结，不能擅自缩成某个单一维度

例如：

- 问“应用整体”，不能最后说成“按业务组看……”
- 问“业务组整体”，不能被渲染成“应用分布排行”

## 三、当前最重要的对象语义

| 用户表述 | 当前对象 |
| --- | --- |
| 应用 | `DefinedApp` |
| 业务 | `WebApplication` |
| 业务组 | `BusinessGroup` |
| IP网段 | `Prefix24` |
| 会话 | `IPConversation` |
| 监控口 / 接口 | `MonitoredPort` / `Interface` 相关能力 |

必须记住：

- `应用 != 业务`
- `业务 != 业务组`
- 普通“业务”默认应落到 `WebApplication`
- 只有明确出现“组/分组/工作组”时才应落到 `BusinessGroup`

---

## 四、为什么之前流程理解会出错

旧理解最大的问题，是把这个项目仍然看成：

```text
用户提问
  -> skill 自己做意图理解
  -> skill 自己猜对象
  -> skill 自己决定执行
  -> 返回结果
```

但当前真实情况不是这样。

真实情况是：

- 主理解层已经上移到 `OpenClaw 主链 + napm-openclaw-plugin`
- skill 主要负责执行
- WeCom 还会参与结果承载与 overview 呈现保护

所以以后排查问题时，不能只盯 skill。

---

## 五、排查问题时的正确顺序

如果以后再遇到“问的不对、答的也不对”，建议按下面顺序看：

### 1. 先看是不是主链理解错了

检查：

- 当前问句有没有被识别成 NAPM
- 是否被错误识别成边界外
- `resolvedQuery` 的对象类型、service、scene 是否正确

### 2. 再看 napm-openclaw-plugin 有没有改歪

检查：

- 是否走了 `napm-skill-query`
- 是否被 direct tool reroute
- 是否 overview scene 被注入错了
- 是否 before_message_write 阶段沿用了错误缓存

### 3. 再看 skill 执行是否正确

检查：

- 对象类型是否符合预期
- 时间窗是否正确
- overview scene 是否匹配
- 选的 overview modules 是否正确

### 4. 最后看 WeCom 渲染是否把结果说歪

检查：

- `responseType` 是否被识别错
- `overview` 是否被 `displayText` 短路
- 最终文字有没有从“总览”被改成“单维度结论”

---

## 六、当前应该坚持的流程观

以后再看这个项目，建议脑子里只保留下面这套模型：

```text
WeCom = 通道与结果承载
OpenClaw 主链 = 大脑
napm-openclaw-plugin = NAPM 路由与守卫
Skill = 执行器
NAPM API = 数据源
Narration Contract = 结果交接格式
```

这比“skill 自己负责一切”的旧理解，更符合现在真实运行状态。
