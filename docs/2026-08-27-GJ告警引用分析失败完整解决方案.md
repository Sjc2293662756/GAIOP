# GJ 告警引用分析失败完整解决方案

## 1. 文档信息

- 日期：2026-08-27
- 问题：企业微信新会话发送 `分析告警 GJ-QFH9QC4Z` 后，未执行告警数据包分析，反而返回英文内部推理。
- 当前生产版本：`1.1.0-rc.29`
- 当前状态：根因已通过生产日志和无外发回放确认；运行时代码和回归测试已按本方案修复，本地全量校验通过，尚未生成发布包或部署生产。

## 2. 结论摘要

这次故障不是告警引用档案丢失，也不是 NAPM 数据包接口本身失败，而是两个缺陷叠加：

1. 组合工具的公开描述和输入 Schema 仍把 `eventId/start/end` 写成必需的原始输入，没有把 `GJ-...` 引用编号声明为完整合法入口。模型因此没有调用 `napm-alert-packet-analysis`。
2. 所有非组合工具都被 guard 拦截后，模型生成的英文内部推理没有被企业微信出口识别为告警数据包场景，最终作为普通最终消息发送。

必须同时修复工具契约和输出门禁。只改共享档案、只改推送文案或只放宽 guard 都不能闭环。

## 4. 根因分层

### 4.1 直接根因：组合工具入口无法表达引用模式

用户输入是业务引用编号，模型看到的工具入口却要求内部定位字段。结果是：

```text
用户：分析告警 GJ-QFH9QC4Z
        |
        v
模型认为缺少 eventId/start/end
        |
        v
没有调用 napm-alert-packet-analysis
        |
        v
尝试告警查询、exec、memory_search
        |
        v
全部被 guard 拦截
```

### 4.2 设计缺陷：路由判断和输出判断不对称

`isAlertPacketAnalysisPrompt` 能识别 `GJ-...` 加“分析”语义；但裸引用请求不一定同时被 `isAlertEventPrompt` 和 `isNapmRelatedPrompt` 识别为告警/NAPM 场景。

结果是：

- `before_tool_call` 知道这是告警数据包请求，并正确拦截了错误工具；
- `message_sending` 却没有进入告警数据包的输出保护分支。

这属于同一请求使用了不同场景分类器，导致入口门禁比出口门禁严格。

### 4.3 安全缺陷：无工具结果时允许内部推理作为最终消息

当前出口逻辑只在 NAPM 场景已被识别，或已经存在工具结果时，才取消英文推理。对于本次请求：

- 没有成功工具结果；
- `isAlertEventPrompt` 返回 false；
- `isNapmRelatedPrompt` 返回 false；
- `shouldCancelNapmPreviewMessage` 因此返回 false。

本地回放中，`before_message_write` 和 `message_sending` 对同样的英文文本均返回 `undefined`，与生产泄漏结果一致。

### 4.4 排除项：共享档案不是本次根因

共享档案在请求前已生成、存在且可读。`/dev/shm` 在主机重启后会清空，这是长期可靠性风险，但不解释本次 10:02 的失败。

## 5. 目标设计

### 5.1 用户入口

企业微信只展示并接受：

```text
分析告警 GJ-QFH9QC4Z
```

用户永远不需要填写：

```text
eventId
start
end
suggestedPacketQuery
```

### 5.2 内部执行链路

```text
用户发送 GJ 引用
  -> 统一识别为 alert-packet 场景
  -> napm-alert-packet-analysis 接收 prompt + referenceId
  -> before_tool_call 从共享档案恢复 eventId/start/end/triggerMetrics
  -> alertsDetail 获取告警详情和数据包候选
  -> 单候选自动分析；多候选返回候选编号
  -> napm-packet-analysis 内部执行具体数据包分析
  -> 按 triggerMetrics 使用专项分析画像
  -> 生成确定性中文结果
  -> 企业微信出口只发送确定性结果
```

### 5.3 两种合法内部输入模式

组合工具同时支持：

1. 引用模式：`prompt + referenceId`，由插件恢复内部字段。
2. 兼容模式：`prompt + eventId + start + end`，用于旧式可信内部调用和回放。

两种模式最终都必须进入同一个 `AlertPacketWorkflowService`，不能分叉出第二套分析逻辑。

## 6. 具体修复方案

### 6.1 修改组合工具 Schema

将固定必填字段改成两个合法输入分支。建议使用 `anyOf`，而不是 `oneOf`：因为插件在 hook 中恢复后可能同时保留 `referenceId` 和数字字段，`anyOf` 能兼容校验发生在 hook 前或 hook 后的运行时。

示意契约：

```js
parameters: {
  type: 'object',
  properties: {
    prompt: { type: 'string' },
    eventId: { type: 'string', pattern: '^\\d+$' },
    start: { type: 'number' },
    end: { type: 'number' },
    referenceId: { type: 'string', pattern: '^GJ-[A-Z2-9]{6,16}$' },
    candidateId: { type: 'string', pattern: '^GJ-[A-Z2-9]{6,16}-P\\d{1,3}$' },
    triggerMetrics: { type: 'object', additionalProperties: true },
    packetCandidate: { type: 'object', additionalProperties: true },
    referenceErrorCode: { type: 'string' },
    traceId: { type: 'string' }
  },
  anyOf: [
    { required: ['prompt', 'referenceId'] },
    { required: ['prompt', 'eventId', 'start', 'end'] }
  ],
  additionalProperties: false
}
```

额外要求：

- `prompt` 仍然必填，便于绑定当前轮次和审计；
- 只有 `prompt` 的输入必须拒绝；
- `referenceErrorCode` 由插件生成，不能由模型伪造；
- 数字字段恢复后仍由 `AlertPacketWorkflowService` 做秒级、窗口顺序和最大时长校验；
- `timeRange` 不得进入组合工具内部参数。

### 6.2 修改工具描述和系统路由文案

组合工具描述必须明确写出引用模式：

```text
用于“分析告警 GJ-XXXXXX”或带数字 eventId/start/end 的告警数据包分析。
当输入包含 GJ 引用时，只传 prompt 和 referenceId；插件会从共享告警档案恢复内部事件号、时间窗口和告警指标。
不要要求用户提供 eventId、start、end，也不要改调用 napm-alert-query、napm-packet-analysis 或 exec。
```

路由规则必须同时覆盖：

- `分析告警 GJ-...`
- `查看告警 GJ-... 数据包`
- `分析 GJ-...-P1`
- 旧式完整数字参数请求

系统提示中的 `ALERT_PACKET_WORKFLOW_REQUIRED` 要明确说明：`GJ-...` 是完整业务入口，不是缺少字段的半成品。

### 6.3 统一场景分类器

不能让工具 guard 和消息出口使用不同判定标准。建议将以下规则集中到同一个纯函数：

```text
isAlertPacketAnalysisPrompt(prompt)
```

该函数识别以下任一组合：

- `GJ-...` + 分析/查看/定位/数据包/报文/抓包/继续；
- 告警 + 数据包语义 + 数字 eventId；
- 告警候选编号 `GJ-...-P1` + 分析语义。

统一结果应被以下位置复用：

- 系统路由上下文；
- `before_tool_call`；
- `before_message_write`；
- `message_sending`；
- 结果交付和重复交付门禁。

同时，`isAlertEventPrompt`、`isNapmRelatedPrompt` 和 turn state 应把有效 `GJ-...` 分析请求标记为告警/NAPM 相关，避免出口误判为普通对话。

### 6.4 加固企业微信出口

出口必须遵循以下顺序：

1. 工具调用进度消息：有工具调用标记或流式标记时直接取消，不发送给用户。
2. 告警数据包场景且已有成功/失败工具记录：只发送确定性中文结果。
3. 告警数据包场景但没有工具记录：取消模型内部推理，并发送固定中文失败提示，例如：

   ```text
   当前告警引用尚未完成数据包分析，系统未执行推测性分析。请稍后重试该告警引用。
   ```

4. 任何命中内部推理特征的英文最终消息，在企业微信渠道不得直通。

禁止把以下内容发送给用户：

- guard、schema、tool attempt、validation、reference archive 等内部过程；
- `eventId/start/end` 原始定位字段；
- 未经工具结果证明的“没有档案”“需要原始通知”等判断。

### 6.5 保留告警指标专项分析

引用恢复后必须完整保留：

- 指标名称、指标编码；
- 实际值和单位；
- 严重级别；
- 触发条件；
- `profileId/profileVersion`；
- 指标对应的证据检查项。

例如 `server_user_experience_time` 应重点分析：

- 服务端响应等待；
- HTTP 响应耗时；
- TCP RTT；
- TCP 重传；
- 告警窗口附近的会话相关性。

不能因为引用入口变短而退化成通用协议统计。

### 6.6 单数据包候选规则

- 只有一个候选：自动分析并在结果中标明候选编号；
- 多个候选：返回 `GJ-...-P1`、`GJ-...-P2` 等选择项，禁止默认分析第一个；
- 用户发送候选分件号后，只分析该候选；
- 没有候选：返回“未找到可执行数据包候选”，不得猜测 IP 或下载地址。

### 6.7 本轮已实施的代码修复

- `napm-alert-packet-analysis` Schema 改为 `anyOf` 双模式：接受 `prompt + referenceId` 或兼容旧式的 `prompt + eventId + start + end`。
- 工具描述明确 `分析告警 GJ-XXXXXX` 是完整入口，并禁止要求用户补充内部字段或改调其他工具。
- `GJ-...` 分析请求在告警事件、NAPM 相关性和工具/消息出口中统一识别为告警数据包场景。
- WeCom 的告警数据包请求命中英文内部推理时直接取消发送；无已验证结果时使用中文固定兜底，不泄露 guard、Schema 或内部定位字段。
- `before_message_write` 同样执行告警数据包内部推理替换，覆盖非流式最终消息路径。

## 8. 发布和回滚方案

### 8.1 发布顺序

1. 在干净提交上修改 Schema、描述、统一分类器和企业微信出口。
2. 先运行新增回归测试，再运行全量测试和 lint。

5. 执行安装器 dry-run，确认会同时覆盖 Gateway 插件和 watcher 运行时文件。
6. 正式安装并确认 Gateway、系统级 watcher 都是 `active/running`。
7. 用 stub 或受控测试告警验证消息正文；不得用真实企业微信群消息做未经批准的压力测试。
8. 再用一条真实但可控的告警引用执行跨会话分析验收。

### 8.2 生产验收重点

- 日志出现 `napm-alert-packet-analysis` 调用，而不是错误工具被反复拦截；
- 出现引用恢复成功的审计事件；
- `eventId/start/end` 只存在于内部审计或工具参数，不出现在企业微信正文；
- 指标画像仍为告警实际指标；
- 多候选时不会自动取第一个；
- 同一结果重复发送只交付一次；
- 英文内部推理不会到达企业微信。

### 8.3 回滚条件

出现以下任一情况立即回滚到上一稳定发布包：

- 普通告警查询被错误路由到数据包组合工具；
- 合法数字参数请求被 Schema 拒绝；
- 组合工具恢复出的窗口不完整或跨越限制；
- 指标画像丢失，分析退化成通用统计；
- 企业微信仍收到内部推理或内部定位字段；
- watcher 或 Gateway 无法恢复为 active/running。

## 9. 保存策略和长期风险

- 告警引用档案：默认 7 天；
- 数据包候选元数据：跟随告警档案保存 7 天；
- 下载的 pcap/cap 文件：默认 24 小时；
- 当前默认共享目录位于内存文件系统，主机重启会清空。

本次故障不是由目录清空造成的，但生产若要求跨重启保留 7 天，必须由管理员提供持久可写目录，并配置 `NAPM_ALERT_REFERENCE_DIR` 或 watcher 的 `alertReference.baseDir`，然后重新执行完整发布验收。
