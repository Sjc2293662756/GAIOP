# NAPM 故障分析 v2 设计方案

> 日期：2026-06-24
> 状态：已落地
> Skill：`openclaw-napm-fault-diagnosis`
> 报告模板：`napm_fault_diagnosis_v2`

---

## 一、背景与动机

### 1.1 v1 的问题

v1 的故障分析采用"一次性查询→聚合→填模板"模式（`SummaryService._planFault()` + `DiagnosticFixedTemplateService`），与公司实际的故障分析流程存在根本性差异：

| 问题 | 说明 |
|------|------|
| 流程扁平 | 一次查全部 API，不管当前诊断阶段是否需要 |
| 无分层 | 没有区分"系统指标判断"和"数据包深入验证"两个阶段 |
| 无跳转 | 无法从一个分析流程跳到另一个（如网络慢→发现某应用异常→进入应用分析） |
| 无人工判断点 | 系统自动推断根因，但实际分析中许多判断需要人工根据上下文决策 |
| 报告结构不匹配 | 6章固定模板 vs 公司 §8 结构（基本信息→分析过程→证据→根因→建议→验证） |

### 1.2 设计依据

本方案基于两份公司内部文档：

1. **《故障分析流程整理_基于项目背景资料》** — 6 大类故障分析流程、判断逻辑表、流程跳转关系、报告输出 §8 结构
2. **《故障分析流程整理_系统指标与数据包分层版》** — 系统指标层与数据包层的明确分工原则、各流程的 NAPM 指标映射

### 1.3 核心设计原则

> **系统先查指标，指标只能说明趋势、对象和异常方向；当需要确认报文级原因时，再下载数据包进行深入分析。**

```
场景识别 → 系统指标查询 → 指标判断（趋势+对象+方向）
  ├─ 指标足够 → 输出初步结论
  └─ 触发数据包条件 → 建议下载数据包 → 包级验证 → 输出根因
```

## 二、架构设计

### 2.1 自动化程度

采用 **"数据采集自动化 + 人工判断"** 模式：

- 系统自动查询 NAPM 指标，呈现数据
- 系统根据判断规则给出提示（这可能是X，那可能是Y）
- 人工根据数据和提示做出判断和流程跳转决策
- 系统累积证据，最终自动汇总生成报告

### 2.2 三层架构

```
┌─────────────────────────────────────────────┐
│  交互层：企微/OpenClaw                        │
│  接收用户描述 → 展示步骤结果 → 收集用户判断      │
└──────────────────┬──────────────────────────┘
                   ▼
┌─────────────────────────────────────────────┐
│  逻辑层：openclaw-napm-fault-diagnosis       │
│  FlowRouter(场景识别+跳转) → Steps(NAPM查询)  │
│  → Service(编排+状态) → ReportBuilder(报告)   │
└──────────────────┬──────────────────────────┘
                   ▼
┌─────────────────────────────────────────────┐
│  数据层：复用现有 Skill                       │
│  SummaryClient(NAPM指标) + packet-analysis    │
│  + openclaw-napm-report(.docx生成)            │
└─────────────────────────────────────────────┘
```

### 2.3 与现有 Skill 的关系

```
openclaw-napm-fault-diagnosis (新建)
  ├── 复用 SummaryClient (openclaw-napm-summary)  — NAPM 系统指标查询
  ├── 触发 openclaw-napm-packet-analysis          — 数据包深入分析
  └── 调用 openclaw-napm-report                   — 生成 .docx 报告
```

v1 代码全部保留，v2 通过独立 Skill + 独立 templateId 区分，零冲突。

## 三、流程设计

### 3.1 支持的流程（本次落地）

| 流程 ID | 中文名称 | 步骤数 | 适用场景 |
|---------|---------|:--:|------|
| `network_slow` | 网络慢/网络运行异常 | 4 步 | 全网慢、带宽占满、流量异常 |
| `bs_app_slow` | B/S 架构业务慢 | 3 步 | Web 页面 4xx/5xx 报错、页面错误分析、状态码详情 |
| `cs_app_slow` | C/S 架构应用慢 | 2 步 | 客户端软件慢、数据库访问慢 |

### 3.2 流程 1：网络慢/网络运行异常

```
Step 1: 总流量趋势
  查询: TotalTraffic TPIO/TPI/TPO timeValues
  判断: 带宽拥塞？方向异常？包速异常？流量正常？
  跳转: [继续Top对象, 看网络质量, 转应用分析]

Step 2: Top 对象
  查询: DefinedApp/IPAddress/BusinessGroup/IPConversation Top10 TPIO
  判断: 某应用/主机/工作组/会话异常？
  跳转: [继续网络质量, 转应用分析, 转安全异常]

Step 3: 网络质量
  查询: IPAddress/BusinessGroup/DefinedApp 的 RTTI/RTTO/PLI/PLO/RTDI/RTDO
  判断: 拥塞还是链路质量？丢包集中在哪？
  跳转: [继续连接失败, 转网络质量专项, 建议下载包]

Step 4: 连接失败和异常
  查询: IPAddress/DefinedApp/BusinessGroup 的 RFCI/RFCO/FLSI/FLSO
  判断: 单主机？多主机同目标？端口集中？未知应用？
  触发: 重传率高/失败率高/包速异常→建议下载数据包
  跳转: [转安全异常, 转连接失败, 生成报告]
```

### 3.3 流程 2：B/S 架构业务慢

```
Step 1: 查询业务 4xx/5xx 报错
  查询: WebApplication PGHTTP400/PGHTTP400PCT/PGHTTP500/PGHTTP500PCT (时序+Top10)
        + PGBYTI/PGBYTO (时序)
  判断: HTTP 400升高？HTTP 500升高？两者同时升高？报错正常？
  跳转: [继续页面分析, 转连接失败]

Step 2: 页面错误分析（按访问数排序 Top 20）
  查询: WebApplication→PageFamily
        PGNPGE,PGNOBJE,PGHTTP200,PGHTTP300,PGHTTP400,PGHTTP500,PGSLPCT,PGTME
        排序: PGNPGE(访问数), Top 20
  表格: 每行一个页面 — 访问数/响应数/200/300/400/500/慢页面率/页面延时
  判断: 某页400突出？某页500突出？访问最高页错误多？错误分散？
  跳转: [继续状态码详情, 建议下载包]

Step 3: 页面状态码详情分析
  数据来源: Step 2 结果（无需新 NAPM 查询）
  表格: 每个页面展开一行，展示完整状态码分布
  判断: 单页集中错误？多页500 → 公共组件？多页400 → 认证网关？低频高错误率？
```

### 3.4 流程 3：C/S 架构应用慢

```
Step 1: 应用运行状况
  查询: Application/DefinedApp TPIO/TPI/TPO/CONI/CONO/SCSI/SCSO/FLSI/FLSO
  判断: 失败数？建连时间？服务器响应？重传率？
  跳转: [继续拆分耗时, 转连接失败, 转网络质量]

Step 2: 拆分用户体验
  查询: Application CSTI/CSTO/SRTI/SRTO/DTTI/DTTO/RTDI/RTDO/UETI/UETO
  判断: 建连时间/服务器响应/数据传输/重传时间分布
  触发: 建连时间长/失败率高/重传率高/服务器响应原因不清→建议下载包
```

### 3.5 流程跳转

```
网络慢中的任意步骤 → 用户判断后可跳转:
  ├─ 某应用/主机异常 → B/S应用慢 或 C/S应用慢
  ├─ 丢包重传为主   → 网络质量专项 [后续]
  ├─ 失败/未知/外连  → 安全异常 [后续]
  └─ 连接失败为主   → 连接失败/RST [后续]

B/S应用慢中的任意步骤 → 用户判断后可跳转:
  ├─ 网络侧指标异常 → 网络慢
  └─ 网络时间长/重传高 → 网络质量专项 [后续]

C/S应用慢中的任意步骤 → 用户判断后可跳转:
  ├─ 网络侧流量异常 → 网络慢
  └─ 重传率升高 → 网络质量专项 [后续]
```

## 四、分层设计

### 4.1 系统指标层（NAPM 可查）

| 公司流程需要的指标 | NAPM 对应指标 | NAPM 服务 |
|------|------|------|
| 吞吐量、字节数 | TPIO, TPI, TPO | `timeValues`, `topValues` |
| 往返时间 | RTTI, RTTO | `topValues`, `timeValues` |
| 丢包情况 | PLI, PLO | `topValues`, `timeValues` |
| 重传时延/重传率 | RTDI, RTDO | `topValues` |
| 请求数/成功数/失败数 | RQSI/RQSO, SCSI/SCSO, FLSI/FLSO, RFCI/RFCO | `topValues` |
| 连接建立时间 | CSTI, CSTO | `topValues` |
| 服务器响应时间 | SRTI, SRTO | `topValues` |
| 数据传输时间 | DTTI, DTTO | `topValues` |
| 首包时间 | T2FBI, T2FBO | `topValues` |
| 首次应用响应时间 | IARTI, IARTO | `topValues` |
| 用户体验时间 | UETI, UETO | `topValues` |
| 慢访问/慢页面 | PGSLPCT, PGNSLPGE, PGTME | `topValues`, `timeValues` |
| HTTP 状态码 | PGHTTP400, PGHTTP500 | `topValues` |
| 页面流量/大小 | PGBYTI, PGBYTO | `topValues` |
| 连接数 | CONI, CONO | `topValues` |
| 交互数/交互率 | INRI, INRO | `topValues` |

### 4.2 数据包层（不可用指标直接判断）

以下结论**必须在系统指标触发条件后，进入数据包分析才能确认**：

- RST 方向、TTL、Seq/Ack
- SYN 无响应原因
- Zero Window / Window Full / Duplicate ACK / Out-of-order
- ARP 源 MAC、广播频率
- ICMP 不可达具体类型
- HTTP 请求/响应具体内容
- Payload 特征（挖矿/木马/外连内容）

### 4.3 数据包触发条件

以下任一满足时，系统提示"建议下载数据包"：
- 重传率或包重传率异常高
- 失败数/失败率异常高
- 每秒数据包数异常高但字节数不高
- 连接建立时间异常高
- 系统指标无法区分应用慢还是网络慢
- 某会话流量异常高
- 存在未知应用或主动外连

## 五、报告设计（公司 §8 结构）

```
封面: 故障名称 + 分析类型 + 时间范围

1 基本信息
  ├─ 故障名称 / 分析时间范围
  ├─ 分析类型: [网络运行异常 | B/S业务慢 | C/S应用慢]
  ├─ 涉及对象 / 故障级别 / 受影响对象
  └─ 执行步骤数

2 分析过程 (动态 — 按实际执行步骤生成)
  ├─ 2.1 Step 1: [步骤名称]
  │   ├─ 查询数据描述
  │   ├─ 判断提示（系统指标 → 判断方向）
  │   ├─ 数据包触发条件（如有）
  │   ├─ 用户判断
  │   └─ NAPM 查询结果表格
  ├─ 2.2 Step 2: [步骤名称]
  │   └─ ...
  └─ 2.N Step N

3 证据项
  └─ 分析步骤与查询汇总表

4 根因判断
  ├─ 基于 N 个步骤的证据
  ├─ 系统指标分析发现（逐条列出）
  ├─ 数据包分析触发统计
  └─ 综合判断

5 处置建议
  └─ 建议项列表

6 验证方式
  └─ 验证项列表
```

### v1 报告 vs v2 报告

| | v1 | v2 |
|------|------|------|
| 结构 | 6章固定模板 | §8 动态结构 |
| 分析过程 | 无 | 按实际执行步骤逐条记录 |
| 判断逻辑 | 系统自动推断 | 系统提示 + 人工判断记录 |
| 数据包 | 仅可选第5章 | 每步触发条件 + 独立证据 |
| 渲染方式 | DiagnosticFixedTemplateService | 通用渲染（动态 sections） |
| 章节数 | 固定 ~46 | 动态（3步骤 ~= 18 sections） |

## 六、交互模式

```
企微用户: "分析网络慢，昨天 14:00-16:00"
  ↓
OpenClaw 解析意图 → openclaw-napm-fault-diagnosis
  ↓
FlowRouter.classify("全网慢") → network_slow
  ↓
Service.executeStep("network_slow", "step1_traffic_trend")
  ↓
Steps 构建 NAPM 查询 → SummaryClient 执行
  ↓
返回: {
  data: 趋势图数据,
  hints: ["总吞吐量明显升高→可能存在带宽占用或异常流量", ...],
  nextOptions: ["继续Top对象", "看网络质量", "转应用分析", "生成报告"],
  packetTrigger: null
}
  ↓
OpenClaw 呈现给用户
  ↓
用户: "继续看 Top 对象"
  ↓
Service.nextAction(session, "继续下一步")
  ↓
... step2 → step3 → ...
  ↓
用户: "生成报告"
  ↓
ReportBuilder.build(session) → 18 sections → openclaw-napm-report → .docx
```
