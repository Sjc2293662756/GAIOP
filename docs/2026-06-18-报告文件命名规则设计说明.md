# 报告文件命名规则设计说明

> 日期：2026-06-18
> 状态：已落地

## 1. 背景

原报告文件命名格式为：

```
napm-{reportType英文}-{YYYYMMDD}-{HHmmss}-{6位随机码}.docx
```

例如 `napm-inspection_report-20260618-143052-x7k9m2.docx`。该方案机器可读但人不友好——用户拿到文件后无法从文件名直观识别报告内容与来源。

## 2. 设计原则

1. **人可读优先** — 文件名直接反映报告内容与类型
2. **可追溯** — 包含时间戳，精确到秒
3. **类型驱动** — 不同报告类型对应不同的命名公式
4. **可扩展** — 新增报告类型只需在映射表追加一行
5. **无随机码** — 去掉无意义的 6 位随机后缀，同一秒内多份同名报告在实际场景中几乎不会发生

## 3. 命名规则

### 3.1 分隔符

统一使用下划线 `_` 作为所有组成部分之间的分隔符。

### 3.2 常规报告（巡检、综述、快速、对比、运维）

```
{SystemName}_{类型中文}_{YYYYMMDD}_{HHmmss}.docx
```

| 报告类型 | reportType | 示例文件名 |
|---|---|---|
| 巡检报告 | `inspection_report` | `网深科技流量分析系统_巡检报告_20260618_143052.docx` |
| 综述报告 | `summary_report` | `Netlnside流量分析系统_综述报告_20260618_090315.docx` |
| 快速报告 | `quick_report` | `NAPM_快速报告_20260618_103015.docx` |
| 对比报告 | `comparative_report` | `NAPM_对比报告_20260618_110000.docx` |
| 运维报告 | `operation_report` | `NAPM_运维报告_20260618_120000.docx` |

### 3.3 故障分析报告

```
{FaultName}_故障分析报告_{YYYYMMDD}_{HHmmss}.docx
```

| 场景 | 示例文件名 |
|---|---|
| 端口故障 | `核心交换机端口故障_故障分析报告_20260618_143052.docx` |
| IP 丢包 | `192.168.1.1丢包严重分析_故障分析报告_20260617_221045.docx` |
| 应用告警 | `应用告警综合分析_故障分析报告_20260618_080000.docx` |

### 3.4 时间戳格式

```
YYYYMMDD_HHmmss
```

日期与时间之间使用下划线分隔（旧格式为短横线 `-`）。

## 4. 元数据字段

### 4.1 `systemName` — 系统/产品名称

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1 | `report.systemName` | 调用方显式传入 |
| 2 | `report.dataSource.system` | 数据源标识 |
| 3 | `"NAPM"` | 最终兜底 |

巡检报告额外优先级：`inspection.customerName` → `"网深科技流量分析系统"`（模板默认值）。

调用方可在报告 payload 中设置 `systemName` 覆盖所有默认值：

```json
{
  "reportType": "inspection_report",
  "systemName": "Netlnside流量分析系统",
  "title": "Netlnside流量分析系统巡检报告",
  "sections": [...]
}
```

### 4.2 `faultName` — 故障名称（仅 `diagnostic_report`）

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1 | `report.faultName` | 调用方显式传入 |
| 2 | `report.title` | 从报告标题推导 |
| 3 | `"未命名故障"` | 最终兜底 |

故障名称应准确反映诊断分析的故障对象，例如端口故障、IP 丢包、应用异常等。

```json
{
  "reportType": "diagnostic_report",
  "faultName": "核心交换机端口故障",
  "title": "核心交换机端口故障分析报告",
  "sections": [...]
}
```

### 4.3 报告类型 → 中文名称映射

```js
const REPORT_TYPE_CN = {
  quick_report: '快速报告',
  diagnostic_report: '故障分析报告',
  comparative_report: '对比报告',
  operation_report: '运维报告',
  inspection_report: '巡检报告',
  summary_report: '综述报告'
};
```

新增报告类型只需在此映射表追加一行即可。

## 5. 文本净化规则

`sanitizeFileSegment` 对文件名中的文本部分执行以下处理：

| 步骤 | 操作 |
|---|---|
| 1 | 替换路径特殊字符 `\ / : * ? " < > \|` → `_` |
| 2 | 替换空白符（空格等） → `_` |
| 3 | 合并连续多个 `_` 为一个 |
| 4 | 去掉首尾的 `_` |
| 5 | 截断到 80 字符 |

## 7. 返回值扩展

报告生成成功时的返回值新增以下字段：

```json
{
  "ok": true,
  "reportId": "网深科技流量分析系统_巡检报告_20260618_143052",
  "title": "北京烟草流量分析系统健康检查报告",
  "format": "docx",
  "fileName": "网深科技流量分析系统_巡检报告_20260618_143052.docx",
  "filePath": "/path/to/output/网深科技流量分析系统_巡检报告_20260618_143052.docx",
  "auditPath": "/path/to/output/网深科技流量分析系统_巡检报告_20260618_143052.json",
  "downloadUrl": "/reports/...",
  "generatedAt": "2026-06-18T14:30:52.000+08:00",
  "systemName": "网深科技流量分析系统",
  "faultName": null
}
```

| 新增字段 | 类型 | 说明 |
|---|---|---|
| `fileName` | `string` | 完整文件名（含扩展名） |
| `systemName` | `string\|undefined` | 系统/产品名称 |
| `faultName` | `string\|undefined` | 故障名称，仅 `diagnostic_report` 时有值 |

## 9. 扩展指南

后续新增报告类型时，仅需两步：

1. 在 `REPORT_TYPE_CN` 映射表追加中文名称
2. 在 `SUPPORTED_REPORT_TYPES` 集合中追加新类型

常规报告命名公式自动适用，故障类型需额外提供 `faultName` 字段。
