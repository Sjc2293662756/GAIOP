# NAPM 查询语义解析与参数改写问题整改说明

## 1. 背景

2026-07-29 对两次 `topValues` 查询进行了生产日志核查：

1. “查询过去1小时总流量最高的5个IP”最终只返回 1 条。
2. 明确指定固定 WebService 参数的 Top5 查询最终执行成了当前时间窗口的 Top10，且指标集合由 `BYTI,BYTO,BYTIO` 收缩为 `BYTIO`。

日志证明问题发生在 OpenClaw 插件的查询规范化和自动修复阶段。NAPM 后端按照最终收到的 `topCount` 正常返回对应条数，没有证据表明后端 TopN 服务异常。

## 2. 已确认事实

### 2.1 自然语言 Top5 查询

原始结构化参数已经包含：

```json
{
  "service": "topValues",
  "metric": "BYTIO",
  "topCount": 5,
  "groups": [{ "type": "IPAddress" }],
  "timeRange": {
    "key": "lastNminutes",
    "displayText": "过去1小时"
  }
}
```

因缺少 `queryModeKey`、`metrics`、`topMetric`、`start`、`end`，插件触发自动修复。修复器重新解析整句文本，将 `topCount` 改成 1，最终 API 请求携带 `topCount=1`，后端返回 1 条。

### 2.2 固定参数 Top5 查询

用户明确指定：

```text
service=topValues
numGroups=1
groupType1=IPAddress
start=1785310980
end=1785314580
metrics=BYTI,BYTO,BYTIO
topMetric=BYTIO
topCount=5
csv=true
```

第二次工具调用进入插件时，固定 `start/end`、三项 `metrics`、`topMetric`、`topCount=5` 均已存在，仅缺少 canonical `queryModeKey`。自动修复仍整体重建查询，最终执行参数变为：

```text
start=1785311160
end=1785314760
metrics=BYTIO
topMetric=BYTIO
topCount=10
json=true
```

时间窗口整体向后移动 180 秒。原时间戳和执行时间戳都已按分钟对齐，因此这不是取整误差，而是固定时间被当前相对时间窗口覆盖。

两次实际请求均为 `topCount=10`，后端均返回 10 条。这排除了“后端存在 TopN 最小值或 page_size 限制”的推测。

## 3. 问题清单

### 3.1 双重语义解析

项目约定由上游构造 `resolvedQuery`，查询 Skill 只执行结构化查询。但插件在结构不完整时再次调用 `NapmResolvedQueryResolverService` 解析自然语言，形成两套语义来源：

```text
上游 resolvedQuery -> 插件本地 Resolver -> 查询执行器
```

本地 Resolver 的推断结果当前可以覆盖上游已经明确的字段。

### 3.2 自动修复整体覆盖

`maybeAutoRepairResolvedQuery()` 当前执行：

```js
prepared.resolvedQuery = repaired.resolvedQuery;
```

它没有区分“需要补齐的字段”和“已经有效的字段”，导致只缺一个字段时仍覆盖 `metrics`、`topCount`、`start/end` 等关键参数。

### 3.3 字段优先级缺失

当前没有定义字段级来源和优先级。整改后必须遵守：

```text
有效的显式结构化参数
  > 用户文本中的明确约束
  > Resolver 推断值
  > 系统默认值
```

### 3.4 TopN 数量语法不完整

当前只可靠识别“前5”和“Top5”，不能正确识别：

- 最高的5个IP
- 最大10个业务
- 返回5条
- topCount=5
- topCount: 5

包含“最高/最大/最多”但未命中旧数量正则时会错误回退到 1；包含 `topCount=5` 但没有单数词时会错误回退到默认 10。

### 3.5 时间参数契约冲突

工具说明把 `lastNminutes`、`lastNhours` 写成可直接使用的 key，但时间解析器只接受 `last60minutes`、`last2hours` 等包含实际数字的 key。

同时，固定 `start/end` 和相对 `timeRange.key` 缺少互斥及优先级规则，导致固定时间可能被相对时间覆盖。

### 3.6 指标集合丢失

Resolver 只生成：

```js
metrics: [metricMatch.metric]
```

因此显式 `BYTI,BYTO,BYTIO` 被收缩为 `BYTIO`。排序指标正确不代表展示指标集合可以被删除。

### 3.7 raw 参数与 canonical 参数混用

正常执行器读取 `groups`，而不是 `numGroups/groupType1..n`；执行入口又允许未声明字段进入。结果是 raw 参数看似被接受，实际依赖二次语义解析重新构造 canonical 参数。

整改目标不是让普通用户绕过生产 Skill 直连后端，而是：

- 普通查询只接受并执行 canonical `resolvedQuery`。
- raw WebService 参数若未提供独立、受控的开发诊断契约，应明确拒绝，不得静默改写后伪装成原样执行。

### 3.8 结构校验缺少语义一致性

当前校验主要判断必填字段是否存在。`topCount=1`、`topCount=5`、`topCount=10` 在结构上都合法，但校验器不会比较原始明确参数与最终参数。

### 3.9 结果叙述缺少执行事实约束

已观察到以下无依据叙述：

- 实际请求 `topCount=1` 时，推断“其他 IP 流量过低或无数据”。
- 实际请求 `topCount=10` 时，声称执行的是 Top5，并推测后端存在最小返回限制。
- 回复中的 BYTIO 排名未保持数值降序。

回复层必须以实际执行参数和结构化结果为唯一事实源，不得用用户原始期望替代实际请求，也不得从“返回条数等于请求上限”推断数据稀疏。

### 3.10 CSV 与 JSON 的定性

后端同时支持 CSV 和 JSON。查询 Skill 内部统一使用 JSON 更便于稳定解析，因此 `csv=true -> json=true` 不作为业务查询故障。

需要修正的是回复契约：不得承诺“所有参数原样透传”后又隐藏格式标准化。普通生产查询可以明确说明内部使用 JSON 结构化结果；只有独立 raw 诊断模式才需要严格保留传输格式。

## 4. 整改设计

### 4.1 字段级补全代替整体重建

新增字段级合并逻辑，仅使用 Resolver 结果补齐缺失或无效字段。以下有效字段必须保留：

```text
service, queryModeKey, groups, metric, metrics, topMetric,
topCount, start, end, timeRange, format, semanticConstraints
```

合并时记录每个字段来源，并生成修复差异。已存在的关键字段若与推断结果冲突，以有效显式字段为准；无法安全判断时返回结构化冲突，禁止请求后端。

### 4.2 canonical 参数机械归一化

对可无损转换的 raw 形态做机械转换，不重新解释业务语义：

- `groupType1..n/groupArgument1..n` 转成 `groups`。
- `metrics` 字符串转成有序数组。
- `topCount`、`start`、`end` 转成有效数字。
- `csv/json` 仅归一为内部格式策略，不改变查询语义。

### 4.3 时间模式互斥

定义两种执行时间来源：

- `relative`：使用具体 `timeRange.key`，由统一时间解析器生成根级 `start/end`。
- `fixed`：使用显式根级 `start/end`，不得被相对 key 或当前服务器时间覆盖。

不支持的 key 必须明确失败，禁止回退后静默执行其他时间窗口。

### 4.4 TopN 和指标集合解析

TopN 识别按以下优先级：

1. 显式 `topCount=5` / `topCount: 5`。
2. “前5” / “Top5”。
3. “最高的5个” / “返回5条”等数量短语。
4. 无显式数量时，“谁/哪个”才回退到 1。
5. 其余排行查询使用受控默认值。

指标解析必须区分排序指标与展示指标集合，并保证 `topMetric` 包含在 `metrics` 中。

### 4.5 执行前一致性校验

请求后端前至少校验：

- `topCount` 为允许范围内的正整数。
- `topMetric` 存在于 `metrics`。
- 固定时间与相对时间不冲突。
- `end > start` 且时间戳按分钟对齐。
- `semanticConstraints.targetObjectType` 与最终 group 终点一致。
- 自动修复没有覆盖有效显式关键字段。

### 4.6 结果叙述约束

结构化叙述输入必须携带：

- 实际执行的时间、指标、分组、排序指标和 `topCount`。
- 实际返回条数。
- 是否达到请求上限。
- 禁止从“返回条数等于上限”推断没有更多数据。
- TopN 结果的排序一致性状态。

排序不符合 `topMetric` 方向时，应返回结构化警告或失败，不应生成看似可信的排名。

## 5. 验收标准

### 5.1 案例一

输入“查询过去1小时总流量最高的5个IP”后，最终执行参数必须满足：

```text
service=topValues
queryModeKey=topn
groups=[IPAddress]
metrics=[BYTIO]
topMetric=BYTIO
topCount=5
end-start=3600
```

### 5.2 案例二

当 canonical 查询已经包含固定时间和指标集合时，即使缺少 `queryModeKey`，补全后必须保持：

```text
start=1785310980
end=1785314580
metrics=[BYTI,BYTO,BYTIO]
topMetric=BYTIO
topCount=5
groups=[IPAddress]
```

只允许补充 `queryModeKey=topn` 等缺失字段，不得重新计算时间或缩减指标。

### 5.3 失败保护

- `lastNminutes` 必须返回不支持的时间 key 错误，不能执行默认窗口。
- 原始明确字段与推断字段冲突且无法机械消解时，必须停止执行。
- 任何失败不得沿用旧会话结果生成新结论。

### 5.4 测试范围

- Resolver 单元测试：TopN 语法、指标集合、时间语义。
- 插件边界测试：字段级补全和关键字段保留。
- 查询执行测试：最终请求参数逐项断言。
- 叙述契约测试：条数解释、实际参数、排序一致性。
- 现有定向测试和全量 Jest 回归。
