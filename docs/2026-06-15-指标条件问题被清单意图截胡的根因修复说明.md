# 指标条件问题被清单意图截胡的根因修复说明

## 背景

企业微信测试：

```text
近一天400报错最多的业务是谁？
在其他web应用中，有哪些页面出现400错误？
```

第二个问题的正确语义不是“列出 WebApplication 清单”，而是：

```text
在 WebApplication=其他Web应用 的范围内，
按 PageFamily 页面族统计 PGHTTP400，
返回 HTTP 400 数量排行。
```

## 错误现象

系统先把问题理解为 object inventory：

```json
{
  "service": "groups",
  "queryModeKey": "metadata",
  "groups": [{ "type": "WebApplication" }],
  "semanticConstraints": {
    "operation": "metadata_list",
    "workflowType": "object_inventory",
    "targetObjectType": "WebApplication"
  }
}
```

然后模型在后续回答中尝试：

- 先查 WebApplication 聚合。
- 再尝试 PageFamily。
- 再尝试双层 group。
- 最后用全局 PageFamily 结果近似回答。

这说明主链 resolvedQuery 一开始就不准确，后续是在临场补救。

## 根因

这不是单个关键词缺失，而是工作流分类缺少语义证据仲裁。

旧逻辑大致是：

```text
看到“有哪些”
  -> object_inventory
  -> groups metadata
```

问题是，“有哪些页面出现400错误”里的“有哪些”不是清单意图，而是指标条件下的结果集合意图。

应该先看是否存在指标/质量/错误证据：

```text
400 / 500 / 错误 / 报错 / 异常 / 失败 / 慢 / 响应时间 / 丢包 / 重传 / 吞吐 / 流量
```

如果存在，就应归类为可执行数据查询，而不是元数据清单。

## 修复原则

本次不是为“其他web应用 + 400”单点写死，而是引入统一原则：

```text
指标证据优先于清单措辞。
```

也就是说：

- `系统中有哪些业务` -> object_inventory。
- `业务有哪些指标` -> metric_inventory。
- `有哪些页面出现400错误` -> metric_topn。
- `哪些客户端访问失败最多` -> metric_topn。
- `哪些业务响应慢` -> metric_topn / metric_average。

## 修改内容

### 1. 重写 WorkflowClassifierService

文件：

```text
skills/openclaw-napm-query/services/WorkflowClassifierService.js
```

将原来乱码且顺序命中的正则，改为 UTF-8 的语义优先级分类：

```text
drilldown_catalog
metric_inventory
metric_condition_over_inventory
object_inventory
metric_timeseries
metric_average
metric_topn
overview
```

关键新增规则：

```text
hasMetricConditionIntent(text) && (hasRankingIntent(text) || hasQuestionListIntent(text))
  -> workflowType = metric_topn
  -> reason = metric_condition_over_inventory
```

### 2. 修复 resolvedQuery 构造顺序

文件：

```text
skills/openclaw-napm-query/services/NapmResolvedQueryResolverService.js
```

`resolveMetadataPrompt()` 现在只处理真正的：

```text
drilldown_catalog
metric_inventory
object_inventory
```

如果分类器已经判定为 `metric_topn`，metadata 解析器必须让路，避免再次截胡。

### 3. 增加 HTTP 状态码指标归一化

同一文件新增兜底：

```text
400 / 4xx / 400错误 / 400报错 / 错误...400 -> PGHTTP400
500 / 5xx / 500错误 / 500报错 / 错误...500 -> PGHTTP500
```

这样不依赖配置文件中某个具体别名是否完整。

### 4. 增加页面目标路径推断

当问题中出现“页面 / 页面族 / PageFamily / page”并且是指标查询时，目标路径固定为：

```json
[
  { "type": "WebApplication", "argument": "其他Web应用" },
  { "type": "PageFamilies" },
  { "type": "PageFamily" }
]
```

如果没有指定“其他Web应用”，则仍使用：

```json
[
  { "type": "WebApplication" },
  { "type": "PageFamilies" },
  { "type": "PageFamily" }
]
```

### 5. 更新 query workflow contract

文件：

```text
skills/openclaw-napm-query/references/query-workflow-contract.md
```

追加 `Metric-Condition Arbitration Addendum`，明确：

```text
有哪些 + 400错误
```

不是清单查询，而是指标查询。

## 后续注意

这次只修“语义分类和 resolvedQuery 构造”。

企业微信中的“近一天”追问继承属于会话上下文问题：如果用户上一轮问了“近一天”，下一轮没显式时间，应该继承上一轮时间范围。这和本次根因不同，后续可单独审计 sessionState / follow-up inheritance。
