# NAPM 综述报告生成与企业微信交付链路故障复盘

日期：2026-08-13  
问题发生时间：2026-08-12 13:32 - 15:48  
实施范围：NAPM OpenClaw 插件的综述报告识别、工具编排、报告源交接、结果改写和企业微信附件交付  
当前状态：第二阶段媒体投递修复已部署到测试服务器，Gateway 运行正常；本地完整回归及远端无外发端到端验证通过，待真实企业微信入站最终验收。

## 1. 结论

本次不是单一的“NAPM 没查到数据”，而是报告请求在多个阶段存在独立流程缺陷：

1. `napm-summary` 和 `napm-report-export` 已成功执行时，最终成功结果仍可能被通用 NAPM 门禁提示覆盖。
2. `/new` 后的首轮综述报告请求可能没有触发工具调用，直接进入“本轮未拿到有效 skill 结果”的兜底分支。
3. “业务”和“应用”的 scope 映射不够明确，业务报告存在选错数据范围的风险。
4. 报告已生成但附件未交付后，用户追问“报告呢？没有给我？”不会重新执行或重放报告，而是返回通用失败提示。
5. Gateway 会把上一轮 Word 附件继承到追问轮；原始报告路径和企业微信 outbound UUID 副本未被识别为同一文件，导致同一附件上传两次。

因此，看到以下提示时不能直接判断为“查询无数据”或“NAPM 接口报错”：

```text
当前问题必须经 NAPM skill 执行后才能回答。
本轮未拿到有效 skill 结果，因此不展示主链推理、临时脚本或排查过程。
请以技能执行结果为准。
```

该提示只表示最终交付门禁在当前轮没有关联到它认可的结果。它可能对应未调用工具、工具结果与 turn 失配、成功结果被覆盖或附件交付失败，必须结合工具调用和审计事件判断。

13:36 用户追问后，`napm-report-export` 实际生成了 Word 文件，最终回复却再次被“本轮未拿到有效 skill 结果”覆盖。

这说明查询和导出本身成功，失败发生在结果绑定及最终消息改写阶段。

2026-08-12 15:19，请求“给我业务的最近七天的综述报告”时出现相同现象。

这两次不能解释为“最近七天没有数据”。原始链路没有产生有效工具结果，属于首轮工具编排缺失。

### 2.3 报告文本成功但追问后出现失败提示和两个附件

2026-08-12 15:45 左右，请求“给我应用的最近七天的综述报告”后，界面显示：

```text

格式：docx
下载链接：/reports/...
文件路径：/home/netinside/.openclaw/workspace/skills/openclaw-napm-report/output/...
```

但首轮没有可见附件。15:48 用户追问“报告呢？没有给我？”后：

- 助手显示通用 skill 失败提示；
- 同一个 `napm_应用综述报告_20260812_154540.docx` 附件出现两次；
- 两份附件大小相同，企业微信 outbound 文件名只在 UUID 后缀上表现为传输副本。

该现象证明“报告生成”“回复文本”“附件投递”是三个不同阶段，任一阶段成功都不能替代端到端交付验收。

## 3. 日志证据与判定

### 3.1 15:45 应用报告实际生成成功

审计链出现：

```text

report_generated
reportId=napm_应用综述报告_20260812_154540
```

这些事件依次证明：

1. `napm-summary` 生成的结构化 `reportData` 已保存。
2. `napm-report-export` 已解析到正确的 `reportSourceId`。
3. Word 文件已实际生成。

所以这次故障不是 NAPM 查询无数据，也不是 Word 生成失败，而是生成后的消息和附件交付异常。

### 3.2 15:48 追问未调用工具

追问轮没有新的 `napm-summary` 或 `napm-report-export` 调用，模型只生成通用失败文本。随后日志显示同一个 outbound Word 文件在相邻时间被上传两次。

由此可排除：

- NAPM 查询接口在追问轮报错；
- 报告导出工具在追问轮报错；
- 用户请求了两份不同报告。

真实问题是：追问语义未被识别为报告交付补偿，同时历史媒体被 Gateway 继承，媒体去重又无法合并原始路径和 outbound UUID 路径。

### 3.3 原始会话证据

本次排查使用的原始会话记录：

```text

```

生产排查时应优先检查原始会话中的 `user -> assistant -> toolResult -> assistant` 序列，再结合插件审计和企业微信上传日志，避免只根据用户界面文案判断工具是否执行。

## 4. 根因分析

### 4.1 成功报告没有稳定绑定当前 turn

原链路更关注“当前会话最近一次 NAPM 结果”，没有在所有最终消息 hook 中优先消费“当前 `turnId` 的成功报告”。当模型随后产生通用门禁文案时，`before_message_write` 或 `message_sending` 仍可能把成功报告视为当前轮无效结果。

结果是：工具已经成功，用户却看到失败提示。

### 4.2 报告流程依赖模型主动完成两段工具调用

综述报告必须执行：

```text
napm-summary
  -> reportSourceId
  -> napm-report-export
  -> docx
```

`/new` 后模型没有稳定地产生这组调用，门禁只负责阻止无依据回答，没有负责补齐缺失的报告工作流。因此首轮可直接落入通用失败提示。

### 4.3 scope 语义映射存在歧义

NAPM 报告支持六种 scope。此前自动流程没有把自然语言对象和工具参数固定为唯一映射，尤其“业务”与“应用”容易混用。

本次确定的标准映射为：

| 用户语义 | scope.type | 报告口径 |
| --- | --- | --- |
| 系统、全局、NAPM | `global` | 全局综述 |
| 业务 | `webApplication` | 业务综述 |
| 应用 | `application` | 应用综述 |
| 业务组 | `businessGroup` | 业务组综述 |
| 网络 | `network` | 网络综述 |
| 告警 | `alert` | 告警综述 |

### 4.4 报告交付追问未进入补偿流程

“报告呢”“报告在哪里”“没有给我”“重新发一下”等话术，本质是对上一份成功报告的交付追问，不是新的数据查询请求。

旧逻辑没有将其识别为 `resultDeliveryFollowUp`，因此既不会取回最近成功报告，也不会构造带 `mediaUrl/mediaUrls` 的发送结果，最终只能落入通用门禁。

### 4.5 媒体去重使用了不稳定的路径身份

同一个报告在链路中可能出现两种路径：

```text
/home/netinside/.openclaw/workspace/skills/openclaw-napm-report/output/
napm_应用综述报告_20260812_154540.docx

/home/netinside/.openclaw/media/outbound/
napm_应用综述报告_20260812_154540---<uuid>.docx
```

旧去重逻辑按完整 URL 或路径判断，两者会被当成不同文件。另外，Gateway 可能把上一轮媒体带入下一轮，导致非报告消息携带过期附件。

## 5. 已实施修复

### 5.1 当前轮成功报告优先交付

报告导出结果写入 `ConversationOperationState` 时绑定 `scope + turnId`。在 `before_message_write` 和 `message_sending` 中，当前轮存在成功 `napm-report-export` 结果时，优先重建正式报告回复，不再允许通用失败提示覆盖成功结果。

报告回复包含：

- 报告标题；
- 文件格式；
- 下载链接；
- 文件路径；
- 可供通道发送的媒体路径。

### 5.2 增加首轮自动补偿链路

当消息明确属于综述报告请求、当前 turn 又没有新鲜导出结果时，`message_sending` 自动执行：

```text
识别 scope 和时间范围
  -> napm-summary
  -> 取得当前 reportSourceId
  -> napm-report-export(reportSourceId)
  -> 返回文本和 Word 媒体
```

时间范围“最近七天”固定解析为：

```json
{
  "timeRange": {
    "key": "last7days"
  }
}
```

自动导出显式携带本轮 `reportSourceId`，避免同一会话存在多份报告源时导出错误报告。

相关审计事件：

```text
napm_automatic_summary_started
napm_automatic_summary_completed
napm_automatic_summary_failed
```

### 5.3 固化六类 scope 映射

`buildAutomaticSummaryToolArgs` 统一负责报告对象、标题和时间范围推导。业务报告使用 `webApplication`，应用报告使用 `application`，不再由模型自由猜测。

### 5.4 增加报告交付追问重放

`isResultDeliveryFollowUpPrompt` 新增对以下表达的识别：

```text
报告呢
报告在哪里
没有给我
没给我
重新发一下
再发一遍
```

当上一轮存在同会话成功报告时，插件直接重放最近报告的正式文本和文件路径，不重复查询 NAPM，也不重新生成 Word。

成功命中时记录：

```text
napm_report_followup_replayed
```

### 5.5 修复过期附件继承和重复上传

媒体交付增加两层约束：

1. 非报告轮检测到 `.docx` 或 `.pdf` 时移除媒体；如果消息只有过期媒体则取消该 payload。
2. 同会话、同 `turnId` 内按规范化报告文件名去重；去掉 outbound 路径附加的 `---UUID` 后再比较。

因此原始报告路径与企业微信 outbound 副本会被识别为同一逻辑文件。同一 turn 的重复发送被取消，用户明确在新 turn 要求重发时仍允许交付。

相关审计事件：

```text
napm_stale_report_media_suppressed
napm_plugin_duplicate_media_suppressed
napm_plugin_duplicate_media_trimmed
```

## 6. 修复后的端到端流程

```text
用户请求综述报告
  -> 识别报告意图、scope、timeRange
  -> 模型正常调用工具，或发送阶段启动自动补偿
  -> napm-summary 保存 reportData 并返回 reportSourceId
  -> napm-report-export 按当前 reportSourceId 生成 Word
  -> 成功结果绑定 scope + turnId
  -> 最终消息优先返回报告文本和媒体
  -> 企业微信上传一次附件

用户追问“报告呢？”
  -> 识别为交付追问
  -> 读取同会话最近成功报告
  -> 在新 turn 重放文本和附件
  -> 同 turn 的重复媒体被取消
```

## 10. 生产判障手册

后续再出现“不给报告”时，按以下顺序判断，不要直接归因为查询无数据。

| 日志或审计现象 | 判定 | 排查方向 |
| --- | --- | --- |
| 没有 `napm-summary` 调用 | 工具编排未启动 | 报告意图识别、`/new` 首轮状态、自动补偿入口 |
| 有 `napm-summary`，结果 `ok=false` | 数据采集失败 | NAPM API、认证、时间范围、scope 参数 |
| 有 `report_source_stored`，没有 `report_export_source_resolved` | 报告源未交接到导出 | `reportSourceId`、可信会话范围、工具调用参数 |
| 有 `report_export_source_resolved`，没有 `report_generated` | 导出失败 | 报告模板、文件权限、格式和输出目录 |
| 有 `report_generated`，用户只见失败提示 | 最终改写失败 | `turnId` 绑定、`before_message_write`、`message_sending` |
| 有 `report_generated`，有文本但无附件 | 通道媒体交付失败 | `mediaUrl/mediaUrls`、outbound 转换、企业微信上传日志 |
| 出现 `napm_report_followup_replayed` | 追问补偿已命中 | 继续检查后续上传和 ACK |
| 出现 `napm_plugin_duplicate_media_suppressed` | 同 turn 重复附件已拦截 | 属预期行为，检查第一份 payload 是否送达 |
| 出现 `napm_stale_report_media_suppressed` | 非报告轮继承了历史附件 | 属保护行为，继续追查 Gateway 的媒体继承来源 |
| 同一逻辑文件两次 `Upload complete` | 通道仍重复发送 | 检查 turnId、规范化文件名和插件是否加载最新版本 |

### 建议日志关联字段

## 12. 后续改进

1. 将“报告生成成功”和“通道附件 ACK 成功”拆分为两个可观测状态，避免只凭 `report_generated` 宣告端到端成功。
2. 为企业微信媒体转换边界增加集成测试，验证 `filePath -> outbound copy -> upload -> ACK` 的单次交付。
3. 为自动补偿失败返回明确错误码和阶段，不再静默回落到通用门禁提示。
4. 建立报告链路监控：统计 `report_generated` 后无媒体发送、重复上传、追问重放和自动补偿失败次数。
5. 后续多实例部署时继续保证 `reportSourceId`、会话范围和 turn 生命周期在共享存储中一致。

## 13. 最终结论

本次问题的核心不是报告数据查询能力，而是从“用户意图”到“工具调用”、从“报告源”到“Word 生成”、再从“成功结果”到“企业微信附件”的完整交付状态没有统一收口。

修复后，首次请求具备自动补偿，报告结果按当前 turn 优先交付，六类 scope 显式映射，交付追问可以重放最近成功报告，历史附件不会污染非报告轮，同一逻辑文件也不会因 outbound UUID 副本而重复上传。

### 14.3 真正根因：错误理解 `message_sending` 契约

OpenClaw 2026.5.4 的正式类型为：

```ts
type PluginHookMessageSendingResult = {
  content?: string;
  cancel?: boolean;
};
```

运行时 `runMessageSending` 合并插件返回值时也只保留：

```js
{
  content,
  cancel
}
```

delivery 层只使用 `result.content` 覆盖原 payload 的 `text`。所以 NAPM 插件即使从 `message_sending` 返回：

```js
{
  content,
  mediaUrl,
  mediaUrls
}
```

`mediaUrl/mediaUrls` 也会被 OpenClaw 丢弃。

此前 Hook smoke 直接断言插件 handler 的原始返回值包含媒体，没有模拟 OpenClaw 的 hook 结果归并，因此产生了假阳性。这也是本地测试通过、真实企业微信仍无附件的原因。

### 14.4 修复方案：使用原生 `reply_dispatch`

OpenClaw 的 `reply_dispatch` 提供 `ReplyDispatcher`，其 `sendFinalReply()` 正式接收支持媒体的 `ReplyPayload`：

```ts
type ReplyPayload = {
  text?: string;
  mediaUrl?: string;
  mediaUrls?: string[];
};
```

插件现在对明确的综述报告请求直接接管 dispatch：

```text
reply_dispatch
  -> 解析当前会话、turn、scope 和 timeRange
  -> 执行 napm-summary
  -> 显式传递 reportSourceId
  -> 执行 napm-report-export
  -> dispatcher.sendFinalReply({ text, mediaUrl, mediaUrls })
  -> handled=true，阻止默认模型链路再次发送
```

如果当前 turn 已有成功报告，则直接发送该结果；“报告呢”等交付追问也通过同一原生 dispatcher 重放最近成功报告。

`message_sending` 继续承担文本保护、过程消息取消和旧运行时兼容兜底，但不再作为生产媒体注入入口。

### 14.5 同时消除重复 summary

16:54 的审计显示模型先调用一次 `napm-summary`，旧自动补偿又调用一次 `napm-summary` 后才导出。改由 `reply_dispatch` 在模型执行前接管后，明确的综述报告请求只执行一次确定性链路，不再依赖模型先调用一次工具。
