# 故障分析报告（diagnostic_report）固定模板设计方案

> 日期：2026-06-22
> 状态：已落地
> 模板 ID：`napm_fault_diagnosis_v1`

---

## 一、背景与动机

### 1.1 现状

项目中 `diagnostic_report`（故障分析报告）自报告技能第一阶段起即已注册为支持的报告类型，但一直走**通用渲染管线**（`ReportTemplateService.renderDocx()` 的 else 分支），只做简单的 sections 遍历 + table/chart/list 渲染，缺乏结构化的章节组织和智能叙述能力。

相比之下，`inspection_report` 和 `summary_report` 均已建立完整的固定模板体系：
- **巡检报告**：`InspectionFixedTemplateService` + `napm_traffic_health_inspection_v1.json`
- **综述报告**：`SummaryFixedTemplateService` + `napm_summary_overview_v1.json`

### 1.2 目标

为 `diagnostic_report` 补齐固定模板体系，使其能够：
- 承载故障概述、告警关联分析、流量异常分析、业务性能影响、数据包深度分析、根因建议六大模块
- 自动生成条件叙述（基于数据驱动的叙述规则）
- 预渲染 ECharts 图表（告警时序、流量趋势、Top 对象、业务劣化）
- 支持条件章节显隐（如有抓包数据才显示第5章）
- 同时接收 NAPM 告警/流量/业务数据 和 数据包分析结果

## 二、数据契约

### 2.1 reportData 顶层结构

```json
{
  "reportType": "diagnostic_report",
  "templateId": "napm_fault_diagnosis_v1",
  "fault": { "description": "...", "severity": "critical|major|minor", "timeline": [...], "recommendations": [...], "prevention": [...] },
  "alertAnalysis": { "overallStatus": "...", "summary": {...}, "timeline": [...] },
  "trafficAnalysis": { "trend": {...}, "baselineTrend": {...}, "topIPs": [...], "anomalies": [...] },
  "businessAnalysis": { "slowAccess": [...], "httpErrors": [...] },
  "packetAnalysis": { "protocolHierarchy": [...], "endpoints": [...], "conversations": [...], "dnsQueries": [...], "highlights": [...] }
}
```

### 2.2 各域数据说明

| 域 | 路径 | 类型 | 说明 |
|-----|------|------|------|
| 故障元信息 | `fault` | object | 故障描述、严重级别、受影响对象、事件时间线、建议措施 |
| 告警分析 | `alertAnalysis` | object | 告警概览（按类别+严重性统计）、告警时序、TOP 对象、未恢复告警 |
| 流量分析 | `trafficAnalysis` | object | 故障时段流量趋势（含统计）、可选基线对比、TOP IP、异常明细 |
| 业务分析 | `businessAnalysis` | object | 慢访问业务、HTTP 400/500 错误业务 |
| 数据包分析 | `packetAnalysis` | object/null | 协议分布、Top 端点、Top 会话、关键发现；可为 null |

### 2.3 与现有数据流的兼容

`ReportInputContractService.buildPacketReportData()` 产出的 `diagnostic_report` 数据不受影响：
- 如果传入 `reportData` 中已含 `fault`/`alertAnalysis`/`trafficAnalysis`/`businessAnalysis` 等域 → 走固定模板渲染
- 如果仅含 `sections`（无模板 ID）→ 仍走通用渲染管线（向后兼容）

通过 `templateId: "napm_fault_diagnosis_v1"` 显式触发新模板。

## 三、模板章节设计

### 3.1 章节总览

```
封面 + 目录

1 故障概述
  1.1 故障基本信息（keyValueTable → 改用 table + faultBasicInfo rowBuilder）
  1.2 故障时间线（条件：fault.timeline 存在时显示）
  1.3 综合影响评估（healthSummary + 叙述）

2 告警关联分析
  2.1 告警概览（按类别统计表）
  2.2 告警时序（ECharts 折线图）
  2.3 关联告警详情（未恢复告警列表）
  2.4 告警结论（叙述）

3 流量异常分析
  3.1 流量趋势（ECharts 折线图）
  3.2 流量异常明细（条件：trafficAnalysis.anomalies 存在时显示）
  3.3 Top 受影响对象（条件：trafficAnalysis.topIPs 存在时显示 — 图表+表格）
  3.4 流量结论（叙述）

4 业务性能影响
  4.1 慢访问状况（ECharts 柱状图 + 表格）
  4.2 HTTP 错误状况（ECharts 柱状图 + 表格）
  4.3 业务结论（叙述）

5 数据包深度分析（条件：packetAnalysis 存在时整章显示）
  5.1 协议分布（条件：protocolHierarchy 存在）
  5.2 关键端点与会话（条件：endpoints/conversations 存在）
  5.3 关键发现（条件：highlights 存在，使用 dataParagraphs）
  5.4 数据包结论（叙述）

6 根因分析与建议
  6.1 根因判断（叙述）
  6.2 修复建议（dataParagraphs，从 fault.recommendations 读取）
  6.3 预防措施（dataParagraphs，从 fault.prevention 读取）
```

### 3.2 Section 类型使用统计

| 类型 | 数量 | 用途 |
|------|------|------|
| `heading` | 16 | L1/L2 章节标题 |
| `table` | 13 | 数据绑定表格（通过 rowBuilder） |
| `paragraphs` | 7 | 说明性文本、封面信息 |
| `narrative` | 6 | 条件叙述（每章一个结论） |
| `chartSlot` | 5 | ECharts 图表槽位 |
| `dataParagraphs` | 3 | 数据驱动的建议/预防/发现段落 |
| `cover` | 1 | 封面 |
| `toc` | 1 | 目录 |
| `pageBreak` | 2 | 分页 |

### 3.3 条件显隐机制

模板 section 新增 `condition` 字段，使用与叙述规则相同的条件语法：

```json
{
  "id": "packet_heading",
  "type": "heading",
  "title": "5 数据包深度分析",
  "level": 1,
  "condition": "packetAnalysis exists"
}
```

条件章节包括：
- `fault.timeline exists` — 故障时间线表和标题
- `trafficAnalysis.anomalies exists` — 流量异常明细
- `trafficAnalysis.topIPs exists` — Top 受影响对象
- `packetAnalysis exists` — 整个第5章（含所有子章节）
- `packetAnalysis.protocolHierarchy exists` — 协议分布表
- `packetAnalysis.endpoints exists` — 端点表
- `packetAnalysis.conversations exists` — 会话表
- `packetAnalysis.highlights exists` — 关键发现

当 `packetAnalysis` 为 null/undefined 时，第5章及其所有子章节**完全不渲染**，且不影响目录结构和后续章节编号。

## 四、叙述规则设计

### 4.1 规则组定义

| 规则组 ID | 绑定章节 | mode | 触发场景 |
|-----------|---------|------|---------|
| `fault.overview` | 1.3 综合影响评估 | `first` | 按严重级别和事件数量生成概述 |
| `alert.conclusion` | 2 告警结论 | `first` | 按紧急告警数量和未恢复状态生成结论 |
| `traffic.conclusion` | 3 流量结论 | `first` | 按异常类型（缺失/零流量/尖峰）和与告警的关联生成 |
| `business.conclusion` | 4 业务结论 | `first` | 按慢访问和 HTTP 错误组合情况生成 |
| `packet.conclusion` | 5 数据包结论 | `first` | 区分有/无数据包数据 |
| `root_cause` | 6.1 根因判断 | `first` | 综合告警+流量+异常数据推断根因 |

### 4.2 条件语法增强

在巡检报告的条件语法基础上，新增 **AND/OR** 组合支持（从摘要报告继承）：

```
"alertAnalysis.summary.critical > 3 AND trafficAnalysis.anomalies.length > 0"
"businessAnalysis.slowAccess.length == 0 AND businessAnalysis.httpErrors.length == 0"
```

评估顺序：`exists/empty` → `比较运算` → `AND` → `OR` → `truthy`

### 4.3 变量插值

所有叙述文本支持 `{{ path.to.value }}` 语法进行数据插值，如：

```
"流量在 {{trafficAnalysis.anomalies.0.time}} 出现显著异常：{{trafficAnalysis.anomalies.0.description}}"
```

## 五、图表规格设计

### 5.1 图表清单

| chartId | 标题 | 类型 | 数据路径 | 系列 |
|---------|------|------|---------|------|
| `alert.timeline` | 告警时序图 | line | `alertAnalysis.timeline` | critical_total, major_total, minor_total |
| `traffic.trend` | 故障时段流量趋势图 | line | `trafficAnalysis.trend.dataset` | TPIO, TPI, TPO |
| `traffic.topIPs` | Top 受影响 IP | bar | `trafficAnalysis.topIPs` | TPIO, TPI, TPO |
| `business.slowAccess` | 慢访问业务 | bar | `businessAnalysis.slowAccess` | slowCount, avgPageDelayMs |
| `business.httpErrors` | HTTP 错误业务 | bar | `businessAnalysis.httpErrors` | http400, http500 |

### 5.2 图表预渲染

所有图表在 `renderDocx()` 阶段通过以下流程预渲染为 PNG：
```
chartSpec → buildEChartsOption() → ECharts SSR (SVG) → sharp (PNG buffer) → ImageRun in docx
```

无数据或渲染失败时，回退为静态 key-value 表格显示图表元信息。

## 六、Row Builder 设计

### 6.1 新增 Builder 清单

| rowBuilder | 数据来源 | 表格列 |
|-----------|---------|--------|
| `faultBasicInfo` | `fault{}` + `timeRange{}` | 项目, 内容 |
| `faultTimeline` | `fault.timeline[]` | 时间, 事件, 类型 |
| `healthSummary` | 综合各域数据 | 评估维度, 状态, 说明 |
| `alertCategoryStats` | `alertAnalysis.summary.byCategory[]` | 告警类别, 总数, 紧急, 重大, 轻微 |
| `alertDetails` | `alertAnalysis.summary.unresolvedAlerts[]` | 告警ID, 名称, 级别, 类别, 对象, 开始时间 |
| `trafficAnomalies` | `trafficAnalysis.anomalies[]` | 时间, 指标, 描述, 严重级别 |
| `trafficTopIPs` | `trafficAnalysis.topIPs[]` | 序号, IP, 总流量, 入流量, 出流量 |
| `businessSlowTable` | `businessAnalysis.slowAccess[]` | 序号, 业务, 慢访问占比, 慢访问次数, 平均时延 |
| `businessErrorTable` | `businessAnalysis.httpErrors[]` | 序号, 业务, HTTP400, HTTP500 |
| `packetProtocol` | `packetAnalysis.protocolHierarchy[]` | 序号, 协议, 帧数, 字节数 |
| `packetEndpoints` | `packetAnalysis.endpoints[]` | 序号, 地址, 数据包数, 字节数 |
| `packetConversations` | `packetAnalysis.conversations[]` | 序号, 源地址, 目标地址, 数据包数, 字节数 |

### 6.2 healthSummary 特殊逻辑

`healthSummary` 是综合性 rowBuilder，它不绑定单一数据路径，而是**聚合多个域的摘要数据**生成行：

1. **告警态势**：取决于 `alertAnalysis.summary.critical/total` → 正常 / 需关注 / 异常
2. **流量状况**：取决于 `trafficAnalysis.anomalies/stats` → 正常 / 异常
3. **业务性能**：取决于 `businessAnalysis.slowAccess/httpErrors` → 正常 / 需关注
4. **数据包分析**（条件）：取决于 `packetAnalysis.highlights` → 正常 / 异常
5. **综合评估**：取决于 `alertAnalysis.overallStatus` → 正常 / 需关注 / 异常

## 七、诊断模板渲染引擎

### 7.1 继承关系

```
InspectionFixedTemplateService (1384行，基础引擎)
  └── DiagnosticFixedTemplateService (430行，新增)
```

### 7.2 覆盖的方法

| 方法 | 覆盖原因 |
|------|---------|
| `constructor()` | 指向 `templates/diagnostic/`，默认 templateId `napm_fault_diagnosis_v1` |
| `buildContext()` | 围绕 `fault` + `alertAnalysis` + `trafficAnalysis` + `businessAnalysis` + `packetAnalysis` 构建上下文 |
| `buildRowsForSection()` | 新增 12 个诊断专用 rowBuilder，未识别时回退父类 |
| `renderNarrative()` | 使用本地 AND/OR 感知的 `buildNarrativeTexts()` |
| `buildChildren()` | 过滤 `condition` 字段为 false 的章节 |
| `preRenderCharts()` | 跳过无数据的图表（避免渲染空白 PNG） |
| `renderDocx()` | 完整的文档构建流程（pre-render → filter → build → post-process） |

### 7.3 复用的父类能力

以下方法直接从 `InspectionFixedTemplateService` 继承，无需覆盖：
- `renderSection()` — 章节类型分发
- `renderCover()`, `renderToc()`, `renderParagraphs()`, `renderStaticTable()`, `renderKeyValueTable()`, `renderTableSection()`, `renderDataParagraphs()`, `renderChartSlot()`
- `buildEChartsOption()` — NAPM 色系图表构建
- `renderChartPngBuffer()` — ECharts SSR → PNG
- JSZip 后处理（Heading1Char/Heading2Char 字符样式补丁）
- `loadTemplate()`, `loadNarrativeRules()`, `loadChartSpecs()` — 模板加载与缓存

## 八、集成点

### 8.1 ReportTemplateService 路由

```javascript
// renderDocx(report) 中新增：
if (report.reportType === 'diagnostic_report' || report.templateId === 'napm_fault_diagnosis_v1') {
  return this.renderDiagnosticDocx(report);
}
```

### 8.2 ReportGenerationService 校验

`diagnostic_report` 被标记为固定模板类型，不再强制要求 `sections` 数组：
```javascript
const usesFixedTemplate = reportType === 'inspection_report' || reportType === 'summary_report' || reportType === 'diagnostic_report';
```

### 8.3 文件命名（无需修改）

沿用现有规则：`{FaultName}_故障分析报告_{YYYYMMDD}_{HHmmss}.docx`

## 九、后续扩展

### 9.1 数据采集 Skill（待建设）

当前故障分析报告的数据需由上游 skill 提供。建议后续新建 `openclaw-napm-fault-diagnosis` skill：
- 接收故障描述（时间范围、受影响对象、故障现象）
- 自动查询告警（时间窗内 + 前后对照基线）
- 查询流量趋势异常（缺失点、尖峰、零流量段）
- 查询业务性能劣化（慢访问、HTTP 错误）
- 查询受影响设备的健康状态
- 关联数据包分析结果（如有）
- 产出标准化的 `reportData`

### 9.2 基线对比图表

当前 `traffic.trend` 图表仅展示故障时段数据。如果 ECharts SSR + 当前数据模型支持，可增加基线叠加：
- 方案 A：在 `trafficAnalysis.baselineTrend.dataset` 中提供基线数据，图表层叠加双数据集
- 方案 B：拆为两个并排图表（故障时段 vs 正常基线时段）

### 9.3 多故障关联分析

如果一次故障诊断涉及多个相关联的故障事件，可通过 `fault.relatedEvents[]` 扩展，并在模板中增加关联故障对比表。
