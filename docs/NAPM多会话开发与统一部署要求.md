# NAPM 多会话开发与统一部署要求

状态：强制执行

当前基线：`main` / `v1.1.0-rc.37`

适用范围：所有 NAPM 修改任务、整合任务、发布任务和服务器部署任务

## 1. 最重要的规则

多个会话可以同时开发，但不能同时部署。所有会话分成两种角色：

```text
修改任务（可以有多个）
  -> 各自在独立分支修改、测试、提交
  -> 不改版本、不打包、不部署

整合部署任务（只能有一个）
  -> 盘点并合并用户确认的修改分支
  -> 统一版本、统一测试、生成一个 ZIP
  -> staged / dry-run
  -> 得到正式切换批准后安装
```

服务器上永远只安装整合任务生成的完整发布包。任何修改任务都不得把自己的几个文件直接上传服务器。

## 2. 唯一仓库

所有新任务必须使用：

```text
G:\my_file\项目测试\观枢·智维平台-GAIOP\NAPM_skill_unified
```

以下目录仅作历史备份：

```text
G:\my_file\项目测试\观枢·智维平台-GAIOP\skill_project\NAPM_skill
G:\my_file\项目测试\观枢·智维平台-GAIOP\project_3\NAPM_skill
```

禁止从旧目录修改、打包或部署。

## 3. 修改任务的职责

每个问题建立独立分支，例如：

```text
codex/fix-alert-display
codex/fix-packet-analysis
codex/napm-turn-decision-phase1
```

修改任务可以：

- 阅读代码和日志；
- 修改约定范围内的代码和文档；
- 增加测试；
- 运行定向测试和必要的质量检查；
- 把本任务改动提交到自己的分支。

修改任务禁止：

- 直接修改 `main`；
- 修改 `package.json` 或 `package-lock.json` 的发布版本号；
- 创建、移动或删除版本标签；
- 执行 `npm run release:build`；
- 上传发布包或源文件到服务器；
- 运行正式安装、回滚或服务重启；
- 自行把自己的分支合入 `main`；
- 清理其他分支或 worktree。

任务完成时必须报告：

```text
分支名：
提交号：
改动内容：
测试结果：
是否修改版本号：否
是否构建发布包：否
是否连接/修改服务器：否
遗留问题或风险：
```

## 4. 整合部署任务的职责

整合部署任务是一次发布的唯一负责人。同一时间只能有一个。

开始整合前必须盘点：

1. 当前 `main` 的提交和版本；
2. 每个候选分支的分支名、提交号和测试结果；
3. 哪些分支明确纳入本次发布；
4. 是否存在同文件修改、依赖关系或未提交改动；
5. 远端当前活动版本和 commit。

用户确认纳入范围后，从当前 `main` 建立唯一整合分支：

```text
codex/integrate-rc<N>
```

整合任务依次合并已确认分支并解决冲突。冲突解决必须保留各分支业务意图，不能简单选择某一侧覆盖。合并完成后统一升级版本号，已使用过的 RC 号不得复用。

## 5. 发布质量门禁

整合分支必须是干净提交，并至少通过：

```powershell
npm test -- --runInBand --silent
npm run lint
npm run verify:runtime-contract
```

质量检查全部通过后，才允许执行：

```powershell
npm run release:build
```

构建结果必须是唯一完整 ZIP：

```text
dist\NAPM_skill-<版本>-<短提交号>.zip
```

必须记录：

- 版本号；
- 完整 commit；
- ZIP 文件名和大小；
- 本地 SHA-256；
- 测试、lint 和 runtime contract 结果。

禁止人工拼包、修改 ZIP 内文件或逐文件上传。

## 6. 两级部署授权

### 6.1 准备候选版本

用户说以下内容时：

```text
准备 rc.38
制作 rc.38
开始 rc.38 的部署准备
```

仅授权执行：

```text
整合 -> 本地检查 -> 构建唯一 ZIP -> 上传 -> 校验 SHA-256
     -> 独立目录解压 -> verify-staged-release.sh
     -> install-release.sh --dry-run
```

这一级不得运行正式安装，不得切换活动代码，不得重启 Gateway 或 watcher。

### 6.2 正式切换

只有用户明确说以下内容或同等明确指令时：

```text
批准正式切换 rc.38
正式安装 rc.38
```

才允许执行：

```bash
bash scripts/install-release.sh
```

版本号必须与用户批准的版本完全一致。若远端活动版本、commit、SHA-256 或 dry-run 结果发生变化，应停止并重新报告，不能沿用旧批准。

## 7. 正式安装前检查

必须确认：

- 上传包 SHA-256 与本地一致；
- `RELEASE-MANIFEST.json` 的版本和完整 commit 与整合提交一致；
- staged 校验通过；
- dry-run 明确允许升级；
- 远端当前活动版本已识别，没有同版本不同 commit；
- Gateway 和 watcher 的部署前状态已记录；
- 安装脚本会建立可用备份；
- 没有另一个部署任务正在运行。

任一项不满足即停止。

## 8. 安装后验收

正式安装成功后必须核对：

- workspace manifest 与 extension manifest 都是批准的版本和完整 commit；
- 活动 extension 文件来自本次发布包；
- Gateway 为 `active`；
- 正确作用域的 watcher 为 `active`；
- `18789` 端口正常监听；
- 8 个生产工具入口和插件运行时契约通过；
- 进程没有引用 `(deleted)` 文件；
- 启动日志没有新的 NAPM 加载错误；
- 自动备份路径和校验文件存在。

失败时停止继续覆盖，保留输出和备份路径，先确认自动回滚结果。

## 9. 验收后的版本管理

部署和现场验收通过后：

1. 创建不可移动的版本标签，例如 `v1.1.0-rc.38`；
2. 将整合分支合入 `main`；
3. 确认 `main`、标签和服务器活动 manifest 指向同一提交；
4. 后续新修改任务从新的 `main` 开始。

GitHub 推送与服务器部署分开授权。未得到明确推送批准时，不执行 `git push`，尤其禁止 `--force`。

## 10. 冲突和并发处理

多个会话修改同一个文件不会直接影响服务器，但合并时可能产生 Git 冲突。处理原则：

- 所有冲突只在整合分支解决；
- 修改任务不得为了避开冲突而覆盖其他任务文件；
- 整合后必须重新运行全部质量门禁；
- 某分支依赖另一个分支时，必须记录依赖和合并顺序；
- 发现未提交或来源不明的改动时保留现场并报告，不擅自撤销；
- 正式部署期间，所有其他会话暂停服务器写操作。

## 11. 发给其他修改会话的标准话术

新建或继续修改任务时，可以直接发送：

```text
本任务只负责【填写具体问题】的代码修改和测试。

统一仓库：G:\my_file\项目测试\观枢·智维平台-GAIOP\NAPM_skill_unified
请基于当前 main 建立独立 codex/<topic> 分支；如果任务已经有分支，不要换分支或覆盖其他 worktree。

请完成代码修改、相关回归测试并提交到本任务分支。不要修改 package.json/package-lock.json 的发布版本号，不要创建标签，不要构建发布 ZIP，不要上传服务器，不要重启服务，不要部署，不要合并 main。

结束时请明确告诉我：分支名、提交号、改动文件/功能、测试结果、遗留风险，并确认“未改版本、未打包、未连接或修改服务器”。
```

对于已经打开、正在工作的旧会话，可以发送：

```text
补充统一要求：继续在你当前分支完成本问题，不要切换或改写其他分支。只允许修改、测试并提交；禁止改发布版本号、打标签、打包、上传、部署、重启服务或合并 main。完成后报告分支名、提交号、测试结果和遗留风险。后续由唯一整合部署任务统一合并和发布。
```

## 12. 发给整合部署会话的标准话术

准备新版本时，可以发送：

```text
你是本次唯一整合部署任务。请以当前 main 为基线，先盘点以下已完成分支的提交、测试、依赖和冲突：【填写分支列表】。

先给出准备纳入本次版本的清单，不要遗漏其他会话的未合并改动。得到我确认后，建立 codex/integrate-rc<N>，统一合并、解决冲突、升级唯一版本号并运行全量测试、lint、runtime contract。只构建一个完整 ZIP。

完成 staged 验证和 install-release.sh --dry-run 后停下并报告，不要正式安装或重启服务。只有我明确说“批准正式切换 rc<N>”后才能执行正式安装。
```

## 13. 当前版本起点

本规则建立时的统一状态：

```text
已部署运行时基线       -> 1.1.0-rc.37 / 29b99110
v1.1.0-rc.37         -> 29b99110
测试服务器活动版本     -> 1.1.0-rc.37 / 29b99110
main 包版本           -> 1.1.0-rc.37（可包含后续纯文档治理提交）
下一个可用候选版本     -> rc.38（以实际发布时盘点为准）
```

纯文档治理提交不代表服务器重新发布，也不得用 `rc.37` 从新提交重新构建发布包。下一次包含代码或文档的新发布必须升级为新的唯一 RC。若实际状态与本节不同，以 Git、发布 manifest 和服务器只读检查结果为准，并先更新文档再发布。
