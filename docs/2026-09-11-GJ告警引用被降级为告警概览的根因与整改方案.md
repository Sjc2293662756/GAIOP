# GJ 告警引用被降级为告警概览的根因与整改方案

## 1. 文档信息

- 日期：2026-09-11
- 问题发生时间：2026-09-10
- 适用范围：企业微信中的 `GJ-...` 告警引用、告警详情恢复、告警关联数据包分析
- 当前判断：根因已由远端运行时与日志证据确认；修复代码已在开发分支，生产尚未完成整合发布和切换
- 非本文范围：普通告警概览、普通单 IP 数据包查询、普通业务组数据包查询

## 2. 用户现象

用户发送：

```text
分析告警 GJ-NKHAQSBC
```

实际收到的是“最近 24 小时告警查询结果”，告警总数为 0，而不是该引用对应的告警详情或告警数据包分析。

这不是“最近 24 小时没有告警”可以解释的结果。`GJ-NKHAQSBC` 是一条跨会话告警引用，必须先恢复引用档案，再进入告警数据包组合流程。

## 3. 远端证据

### 3.1 实际调用序列

远端 2026-09-10 的调用链为：

| 顺序 | 实际行为 | 结果 |
| --- | --- | --- |
| 1 | 用户发送 `分析告警 GJ-NKHAQSBC` | 入站成功 |
| 2 | 调用 `napm-alert-query`，传入 `eventIds=["GJ-NKHAQSBC"]` | HTTP 400；GJ 引用不是普通告警 API 的数字事件 ID |
| 3 | 模型重试并加入 `last24hours` | 请求被执行成 `alertsSummary` |
| 4 | 返回最近 24 小时告警概览 | 0 条，掩盖了前一步路由错误 |

本次没有出现以下关键事件：

```text
napm-alert-packet-analysis
alertsDetail
napm_plugin_alert_packet_wrong_tool_blocked
```

因此，本次不是组合工具执行失败，而是根本没有进入组合工具。

### 3.2 引用档案存在

远端共享档案中存在 `GJ-NKHAQSBC`，已恢复到以下事实：

| 字段 | 值 |
| --- | --- |
| eventId | `821387` |
| 告警名称 | 网络工作组延时增大 |
| 对象 | ESXI主机 |
| 级别 | 重大 |
| 数据包窗口 | `1789026960` 至 `1789027200` |
| `packet.candidates` | `[]` |
| 默认有效期 | 7 天 |

`packet.candidates=[]` 只表示本次复合工作流尚未运行、尚未生成候选，不表示告警不存在或没有数据包。

### 3.3 远端与本地运行时代码不一致

对远端活动运行时进行函数回放：

```text
isAlertPacketAnalysisPrompt("分析告警 GJ-NKHAQSBC") = false
isAlertEventPrompt("分析告警 GJ-NKHAQSBC") = false
```

同样输入在当前开发代码中为 `true`。当前代码已经包含：

- `extractAlertReference`：识别 `GJ-...` 和候选分件号；
- `resolveAlertReferenceInput`：读取共享档案并恢复可信字段；
- `napm-alert-packet-analysis`：组合工具唯一入口；
- 错误工具拦截和引用不存在/过期的明确错误。

结论是：生产实际运行的插件包没有包含或没有加载这组引用还原逻辑。仅重启当前旧服务不会改变代码，因此不能解决本问题。

## 4. 根因

### 4.1 直接根因：GJ 引用没有在路由入口被识别

正确链路应为：

```text
GJ-NKHAQSBC
  -> 读取告警引用档案
  -> 恢复 eventId/start/end/triggerMetrics
  -> napm-alert-packet-analysis
  -> alertsDetail
  -> packet analysis
```

远端实际链路却是：

```text
GJ-NKHAQSBC
  -> napm-alert-query
  -> HTTP 400
  -> alertsSummary(last24hours)
  -> 返回告警概览
```

### 4.2 保护缺口：普通告警查询失败后允许降级为概览

`GJ-...` 不是普通告警查询的 `eventId`。一旦请求已被识别为告警数据包引用，错误工具必须 fail-closed：

- 禁止调用 `napm-alert-query`；
- 禁止调用 `alertsSummary`、`alertsSummaryTimeLine`；
- 禁止调用普通 `napm-packet-analysis`；
- 禁止通过补充 `last24hours` 等参数把失败请求改造成另一个查询。

当前远端没有执行该门禁，所以模型在首个 400 后走了错误的恢复路径。

### 4.3 独立可靠性风险：档案默认位于临时内存目录

当前默认目录为 `/dev/shm/napm-alert-references`，默认保留 7 天，但主机重启会清空该目录。它不是本次 9/10 故障的直接原因，因为故障发生时档案仍在；它会造成后续“引用已过期/不存在”的假故障，必须单独整改。

## 5. 合理解决方案

### 5.1 统一 GJ 引用路由

在消息入口、工具前置校验和最终输出三处复用同一个结构化判断，不再分别写三套正则：

```text
isAlertPacketAnalysisPrompt(prompt)
```

至少覆盖：

```text
分析告警 GJ-NKHAQSBC
查看 GJ-NKHAQSBC 的数据包
继续分析 GJ-NKHAQSBC-P1
分析告警 GJ-NKHAQSBC 的关联报文
```

识别成功后必须固定路由到 `napm-alert-packet-analysis`。

### 5.2 由插件恢复内部字段

用户只需提供 `GJ-...`，不得要求用户补填内部字段。插件从可信档案恢复：

- `eventId`；
- 固定秒级 `start/end`；
- `triggerMetrics` 和分析画像；
- 已生成的数据包候选及其候选分件号。

组合工具应同时支持两种合法输入：

1. 用户引用模式：`prompt + referenceId`；
2. 兼容内部模式：`prompt + eventId + start + end`。

两种输入最终进入同一个告警数据包工作流，不能让模型自行重建时间戳或指标。

### 5.3 错误必须终止，不得退化为概览

建立明确错误码和确定性答复：

| 情况 | 结果 |
| --- | --- |
| 档案不存在 | `ALERT_REFERENCE_NOT_FOUND`，提示引用无效或已清理 |
| 档案过期 | `ALERT_REFERENCE_EXPIRED`，提示重新产生告警引用 |
| 候选分件号不存在 | `ALERT_PACKET_CANDIDATE_NOT_FOUND` |
| 组合工具执行失败 | 返回组合工作流失败原因，不调用告警概览兜底 |
| 只有普通告警概览意图 | 才允许调用 `napm-alert-query` |

最终输出必须来自组合工具结果；没有有效工具结果时，不得把模型的计划文本或普通概览作为替代答案发送给用户。

### 5.4 迁移告警档案到持久化目录

生产环境建议显式配置持久化目录，例如：

```text
NAPM_ALERT_REFERENCE_DIR=/var/lib/openclaw/napm-alert-references
```

并确保：

- Gateway 和 Syslog watcher 使用同一目录；
- `netinside` 对目录有读写权限；
- 写入采用临时文件 + 原子重命名；
- 清理任务按 `expiresAt` 删除过期档案；
- 目录空间、写入失败、读取失败进入审计日志和监控；
- 7 天 TTL 与业务要求保持一致，不能用“重启后清空”代替过期策略。

如果暂时不能提供持久化目录，必须在运行环境文档中明确：主机重启会使未过期的 GJ 引用失效，并把它作为发布验收的已知风险。

## 6. 当前代码与发布状态

当前开发分支 `codex/fix-packet-download-followup` 的提交 `009561f629ad493ca020242ea4a31ec655266a67` 已包含 GJ 引用识别、档案恢复、组合工具路由和相关测试；这只能证明开发代码具备修复，不能证明远端已生效。

已存在的回归覆盖包括：

- 仅 `prompt + referenceId` 的组合工具输入；
- 从 GJ 引用恢复 `eventId/start/end/triggerMetrics`；
- 引用不存在和过期的明确错误；
- 普通告警查询和普通数据包查询不被误路由；
- 组合工具失败时不交付模型计划文本。

## 7. 正确发布方案

不能采用“重启一下当前服务”作为修复方案。必须按统一发布流程执行：

1. 从当前 `main` 建立新的 `codex/integrate-rc<N>` 整合分支；`<N>` 使用尚未占用的 RC 编号，不复用旧编号。
2. 将 GJ 引用还原、组合工具强制路由、错误工具拦截、持久化目录配置和回归测试纳入整合分支。
3. 执行全量 Jest、lint、runtime contract 和告警数据包定向测试。
4. 执行 `npm run release:build`，生成一个完整发布 ZIP；禁止只替换单个插件文件。
5. 在远端 staged 环境验证：活动 manifest、插件 SHA-256、工具清单和运行时函数结果。
6. 执行 `install-release.sh --dry-run`，确认安装目标、回滚备份、服务范围和版本不会降级。
7. 只有用户明确批准正式切换后，才正式安装、重启 Gateway/watcher，并做部署后验收。

## 8. 发布后验收

### 8.1 必测成功路径

```text
/new
分析告警 GJ-NKHAQSBC
```

期望审计序列：

```text
GJ reference detected
napm-alert-packet-analysis invoked
alertsDetail requested
packet analysis requested/completed
deterministic final reply delivered
```

期望结果：返回该引用对应的告警对象、固定时间窗口、数据包候选/分析结果；不能显示“最近 24 小时告警总数 0 条”。

### 8.2 必测失败路径

```text
分析告警 GJ-NOT-FOUND
分析告警 GJ-EXPIRED1
分析告警 GJ-NKHAQSBC-P99
```

期望结果：分别返回引用不存在、引用过期、候选不存在；三者都不能调用 `alertsSummary` 兜底。

### 8.3 必测普通路径不回归

```text
最近 24 小时的告警情况
分析 101.254.114.238 最近 5 分钟的数据包情况
```

普通告警仍走 `napm-alert-query`，普通数据包仍走 `napm-packet-analysis`，不能被 GJ 专用门禁误拦截。

## 9. 验收判定

只有同时满足以下条件，才可把问题标记为已解决：

- 远端活动版本的完整 commit 和插件 SHA-256 与发布包一致；
- `GJ-...` 请求只调用 `napm-alert-packet-analysis`；
- 没有 `alertsSummary` 降级调用；
- `alertsDetail` 和数据包分析审计事件可追踪；
- 引用不存在/过期有确定性错误；
- 重启后仍能读取未过期引用，或已明确记录并接受临时目录风险；
- 正常告警概览和普通数据包查询回归通过。

在这些条件满足前，准确状态应写为：**开发修复已存在，生产故障尚未通过整合发布和验收闭环。**
