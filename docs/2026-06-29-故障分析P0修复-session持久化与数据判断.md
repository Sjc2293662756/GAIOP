# 故障分析 v2 P0 修复：Session 持久化 + B/S 数据判断

> 日期：2026-06-29
> 变更范围：`FaultDiagnosisService.js` + `FaultDiagnosisSteps.js` + `SKILL.md`

---

## 一、背景

v2 上线后有两个致命缺陷导致 OpenClaw 无法正常使用：

| P0 | 问题 | 后果 |
|:--:|------|------|
| P0-1 | session 无持久化 | OpenClaw 跨轮调用时状态丢失，多轮诊断无法进行 |
| P0-2 | B/S analyzeStepData 空壳 | 无论 NAPM 返回什么数据，判断提示永远匹配不到实际内容 |

## 二、P0-1：Session 序列化/反序列化

### 变更文件

`skills/openclaw-napm-fault-diagnosis/services/FaultDiagnosisService.js`

### 新增函数

| 函数 | 签名 | 说明 |
|------|------|------|
| `serializeSession(session)` | `session → JSON string` | 将 session 序列化为 JSON。截断 `rawData` 中的 `metricValues[].values` 至 50 条、`topValues` 至 20 条 |
| `deserializeSession(json)` | `JSON string → session` | 反序列化，校验 `v: 1` 版本号 |

### 修改方法

| 方法 | 变更 |
|------|------|
| `start(input)` | 新增 `sessionJson` 参数——如果传入则恢复 session 并继续；新增 `flowType` 参数——如果 OpenClaw 明确指定则跳过 `classify()`；新增 `action` 参数——恢复 session 后直接执行用户操作 |

### OpenClaw 调用模式

```
Turn 1: start({ description, timeRange, target, flowType })
  → 返回 { ok, sessionJson: "<...>", step: {...} }
  → OpenClaw 保存 sessionJson

Turn 2: start({ sessionJson: "<上一轮>", action: "继续下一步" })
  → 内部 deserializeSession → nextAction
  → 返回 { ok, sessionJson: "<新>", step: {...} }
  → OpenClaw 更新 sessionJson

Turn N: start({ sessionJson: "<上一轮>", action: "生成报告" })
  → 返回 { ok, reportReady: true, reportData: {...} }
  → OpenClaw 调 openclaw-napm-report 生成 docx
```

### 序列化规则

```javascript
// rawData 截断策略
MAX_RAW_DATA_KEYS = 5        // 每步最多保留 5 个查询标签
MAX_METRIC_VALUES_LENGTH = 50 // timeValues 最多保留 50 个数据点

// topValues 截断策略
topValues.slice(0, 20)       // 最多保留前 20 行
```

## 三、P0-2：B/S analyzeStepData 真实实现

### 变更文件

`skills/openclaw-napm-fault-diagnosis/services/FaultDiagnosisSteps.js`

### 新增工具函数

| 函数 | 说明 |
|------|------|
| `extractMetric(item, metricId)` | 从 NAPM `topValues` 条目中提取指定 metric 的 value |
| `extractTimeSeries(data, metricId)` | 从 NAPM `timeValues` 响应中提取指定 metric 的 values 数组 |
| `extractTopItems(data)` | 将 NAPM `topValues` 响应展平为 `[{ key, keyLabel, PGHTTP400, PGNPGE, ... }]` |
| `sum(arr)` / `avg(arr)` / `max(arr)` | 数值数组统计 |

### B/S Step1：4xx/5xx 报错分析

```javascript
_analyzeBsStep1(raw) {
  // 从 httpErrorsTrend（timeValues）提取 PGHTTP400/PGHTTP500 序列
  // 计算 total、avg、peak
  // avg400 > 10 或 peak400 > 100 → http400Up = true
  // total500 > 0 → http500Up = true（500 永远值得关注）
  // 两者都成立 → http400And500Up = true
  // 都不成立 → errorNormal = true

  // 从 httpErrorsTop（topValues）提取 PGHTTP400PCT/PGHTTP500PCT
  // 如有业务 >30% 400 → http400Up = true
  // 如有业务 >5% 500 → http500Up = true
}
```

### B/S Step2：页面错误分析

```javascript
_analyzeBsStep2(raw) {
  // 从 pageErrorAnalysis 展平所有页面数据
  // 遍历每个页面：统计 total400、total500、totalVisits
  // 找出 max400Page、max500Page、maxVisitsPage

  // 判断1: max400 / total400 > 50% → page400Dominant
  // 判断2: max500 / total500 > 50% → page500Dominant
  // 判断3: 无400/500但有慢页面率 → pageSlowDominant
  // 判断4: 访问最高页有错误 → topPageHighVisits
  // 判断5: 错误分散（>40% 页面有错且无单页主导）→ errorsScattered

  // 数据包触发: max500 > 10 → page500NeedContent
  // 数据包触发: max400 > 50 → page400NeedContent
}
```

### B/S Step3：页面状态码详情

```javascript
_analyzeBsStep3(raw) {
  // 数据来源：Step2 的 pageErrorAnalysis（由 Service 注入）
  // 统计：有多少页面有 500、有多少页面有 400

  // 判断: 仅1页有错且总页数多 → singlePageAllErrors
  // 判断: >3 页有500 → multiPage500（公共组件故障）
  // 判断: >5 页有400 → multiPage400（认证/网关异常）
  // 判断: 低访问量高错误率 → accessVsErrorMismatch
}
```

### 验证

```
高 400+500 数据 → http400Up=true, http500Up=true, http400And500Up=true ✅
低数据         → errorNormal=true ✅
页面集中 400   → page400Dominant=true, 5条提示匹配 ✅
Step3 页面数据 → 按页错误分布判断 ✅
```
