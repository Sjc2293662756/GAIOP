## 二、v1 故障分析报告

### 2.1 架构

```
用户输入
  ↓
SummaryService.run()   ← scope.type = "fault"
  ├── _planFault()     → 构建 NAPM 查询计划（6-10 次 API）
  ├── execute()        → 并行执行查询
  └── _aggregateFault() → 聚合 + 降幅计算 + 异常检测 + 告警关联
  ↓
SummaryReportDataService.buildFaultDiagnosisReportData()
  → reportType: "diagnostic_report", templateId: "napm_fault_diagnosis_v1"
  ↓
ReportInputContractService.normalizeReportInput()
  → 识别 openclaw_napm_fault_diagnosis_result.v1
  ↓
ReportTemplateService.renderDocx()
  → DiagnosticFixedTemplateService.renderDocx()
  → 6 章固定模板 .docx
```

### 2.2 触发方式

**方式 A：CLI 直接调用**

```bash
node skills/openclaw-napm-summary/scripts/run_summary.js --queryJson '{
  "scope": {
    "type": "fault",
    "focus": "all",
    "label": "故障分析",
    "fault": {
      "description": "核心交换机端口流量中断",
      "severity": "critical"
    }
  },
  "timeRange": {
    "faultWindow": { "start": 1780000000, "end": 1780007200 },
    "baselineWindow": { "start": 1779913600, "end": 1780000000 }
  }
}'
# → 输出 summary result（JSON）
# → 再调 openclaw-napm-report CLI 生成 docx
```

**方式 B：企微端 OpenClaw 调用**

```
Step 1: OpenClaw 调 openclaw-napm-summary
  传入: scope.type = "fault"
  返回: { alertAnalysis, trafficAnalysis, businessAnalysis, fault, ... }

Step 2: OpenClaw 调 openclaw-napm-report
  传入: 上一步返回的整个 result 作为 sourceResult
  → ReportInputContractService 自动识别 schema = openclaw_napm_fault_diagnosis_result.v1
  → 生成 .docx
```

**需要 OpenClaw 传递的关键参数：**

| 参数 | 作用 | 必填 |
|------|------|:--:|
| `scope.type` | 必须是 `"fault"` | ✅ |
| `scope.focus` | `"all"` / `"traffic"` / `"business"` — 决定查询哪些数据 | ✅ |
| `scope.fault.description` | 故障名（影响文件名） | ✅ |
| `scope.fault.severity` | `"critical"` / `"major"` / `"minor"` — 影响根因叙述 | ❌ |
| `timeRange.faultWindow` | `{start, end}` — 故障时间窗 | ✅ |
| `timeRange.baselineWindow` | `{start, end}` — 基线对比窗 | ❌ |
| `scope.target` | `{groupType, groupArgument, groupLabel}` — 聚焦对象 | ❌ |

### 2.3 能力清单

#### 数据采集

| 查询 | NAPM API | 指标 | 始终查询？ |
|------|---------|------|:--:|
| 告警概览 | `getAlertsSummary` | — | ✅ |
| 告警时序 | `getAlertsTimeline` | — | ✅ |
| 故障窗流量趋势 | `getTimeValues` | TPIO, TPI, TPO, PLI, PLO | ✅ |
| 基线窗流量趋势 | `getTimeValues` | TPIO, TPI, TPO | 基线窗存在时 |
| Top 受影响 IP | `getTopValues` | TPIO, TPI, TPO | ✅ |
| 业务慢访问 | `getTopValues` | PGSLPCT, PGNSLPGE, PGTME | focus=all/business 时 |
| 业务 HTTP 错误 | `getTopValues` | PGHTTP400, PGHTTP500 | focus=all/business 时 |
| 应用连接/失败/质量 | `getTopValues` | CONI/CONO, RFCI/RFCO, PLI/PLO/RTTI/RTTO | DefinedApp/Application 目标时 |
| 设备信息 | `getApplianceInfo` | — | ✅ |

#### 异常检测

| 检测项 | 逻辑 |
|------|------|
| 流量降幅 | `(baselineAvg - faultMin) / baselineAvg × 100%`，>30% 生成异常 |
| 缺失点 | `stats.missingPointCount > 0` → 异常 |
| 零流量片段 | `stats.zeroSegmentCount > 0` → 异常（critical） |
| 尖峰 | `stats.spikeCount > 0` → 异常 |
| 告警关联 | `critical > 0 AND anomalies > 0` → 强关联 |

#### 报告输出

| 章节 | 内容 |
|------|------|
| 封面 | 系统名 + 故障分析报告 + 故障名 + 时间 |
| 目录 | 1-2 级标题 |
| 1 故障概述 | 基本信息表（故障名/级别/时间/受影响对象）+ 时间线表 + 综合评估表 + 叙述 |
| 2 告警关联分析 | 告警概览表 + 告警时序图 + 关联告警详情表 + 叙述 |
| 3 流量异常分析 | 流量趋势图 + 异常明细表 + Top 受影响 IP 图表 + 叙述 |
| 4 业务性能影响 | 慢访问图表 + HTTP 错误图表 + 叙述 |
| 5 数据包深度分析 | 协议分布/端点/会话/关键发现（条件：有抓包数据时） |
| 6 根因分析与建议 | 根因叙述 + 修复建议 + 预防措施 |

| 图表 | 类型 | 数据绑定 |
|------|:--:|------|
| 告警时序图 | line | `alertAnalysis.timeline` |
| 流量趋势图 | line | `trafficAnalysis.trend.dataset` |
| Top 受影响 IP | bar | `trafficAnalysis.topIPs` |
| 慢访问业务 | bar | `businessAnalysis.slowAccess` |
| HTTP 错误业务 | bar | `businessAnalysis.httpErrors` |

| 叙述规则 | 触发条件 |
|------|------|
| fault.overview | 按 severity 分级 |
| alert.conclusion | 按 critical 数量 + 未恢复状态 |
| traffic.conclusion | AND/OR 组合（数量 + 类型 + 告警关联） |
| business.conclusion | AND/OR 组合（慢访问 + HTTP 错误） |
| packet.conclusion | 区分有/无数据包数据 |
| root_cause | 综合告警 + 流量 + 异常推断 |

| 条件章节 | 条件 |
|------|------|
| 故障时间线 | `fault.timeline` 非空 |
| 流量异常明细 | `trafficAnalysis.anomalies` 非空 |
| Top 受影响对象 | `trafficAnalysis.topIPs` 非空 |
| 第 5 章整章 | `packetAnalysis` 非空 |
| 协议分布 | `packetAnalysis.protocolHierarchy` 非空 |
| 端点表 | `packetAnalysis.endpoints` 非空 |
| 会话表 | `packetAnalysis.conversations` 非空 |
| 关键发现 | `packetAnalysis.highlights` 非空 |

#### 文件命名

```
{FaultName}_故障分析报告_{YYYYMMDD}_{HHmmss}.docx
```

示例：`核心交换机端口流量中断_故障分析报告_20260624_170213.docx`

### 2.4 数据流

```
┌─ 输入 ────────────────────────────────────────────────┐
│ scope:  { type:"fault", focus:"all", fault:{...} }     │

└───────────────────────────────────────────────────────┘
                        ↓
┌─ SummaryService.run() ────────────────────────────────┐

                        ↓
┌─ SummaryReportDataService ────────────────────────────┐

│  → reportType:"diagnostic_report"                      │

                        ↓

└───────────────────────────────────────────────────────┘
                        ↓
┌─ ReportTemplateService.renderDocx() ──────────────────┐

```

## 三、v2 故障诊断分析

### 3.1 架构

```
用户输入（故障描述 + 时间范围）
  ↓
FaultDiagnosisService.start()
  ├── FlowRouter.classify()     → 识别流程类型
  ├── Steps.buildQueries()      → 构建 NAPM 查询
  ├── Steps.analyzeStepData()   → 数据标记（⚠ 当前是空壳）
  ├── matchHints()              → 匹配判断提示
  └── return { data, hints, nextOptions }
  ↓
用户决策 → Service.nextAction(session, decision)
  ├── "继续下一步" → executeStep(nextStepId)
  ├── "转XXX"     → resolveJump() → executeStep(newFlow, step1)
  └── "生成报告"  → ReportBuilder.build(session)
  ↓
FaultDiagnosisReportBuilder.build(session)
  → reportData { templateId: "napm_fault_diagnosis_v2", sections: [...] }
  ↓
ReportTemplateService.renderDocx()
  → 通用渲染（动态 sections）→ .docx
```

### 3.2 触发方式

**仅企微端 OpenClaw 调用（无 CLI 脚本）。**

交互模型：

```
# 首次启动
用户: "分析网络慢问题，昨天 14:00-16:00"
  → OpenClaw 调 openclaw-napm-fault-diagnosis
  → Service.start({
      description: "分析网络慢问题，昨天14:00-16:00",
      timeRange: {
        faultWindow: {start: ..., end: ...},
        baselineWindow: {start: ..., end: ...}
      }
    })
  → 返回 step1 的数据 + 判断提示 + 下一步选项

# 继续诊断
用户: "继续看 Top 对象"
  → Service.nextAction(session, "继续下一步")
  → 返回 step2 的数据 + 提示 + 选项

# 跳转
用户: "转应用分析"
  → Service.nextAction(session, "转应用分析")
  → resolveJump() → flowType="bs_app_slow", stepId="step1"
  → 返回 B/S 应用慢 step1 的数据

# 生成报告
用户: "生成报告"
  → Service.nextAction(session, "生成报告")
  → ReportBuilder.build(session)
  → reportData → openclaw-napm-report → .docx
```

**需要 OpenClaw 传递的关键参数：**

| 参数 | 作用 | 必填 |
|------|------|:--:|
| `description` | 故障描述（用于场景识别 + 文件名） | ✅ |
| `timeRange.faultWindow` | `{start, end}` | ✅ |
| `timeRange.baselineWindow` | `{start, end}` — 基线对比 | ❌ |
| `target` | `{groupType, groupArgument, groupLabel}` — 分析对象 | ❌ |
| `fault.description` | 故障详细描述（覆盖 description） | ❌ |
| `fault.severity` | `"critical"` / `"major"` / `"minor"` | ❌ |
| `fault.affectedObjects` | `["10.1.1.0/24", "web-app-01"]` | ❌ |
| `fault.recommendations` | 修复建议列表 | ❌ |
| `fault.prevention` | 预防措施列表 | ❌ |

### 3.3 能力清单

#### 场景识别

| 关键词特征 | 识别结果 |
|------|------|
| `web/页面/url/http/登录慢/接口慢/400/500` | `bs_app_slow` (B/S 业务慢) |
| `客户端软件/数据库访问/非web/固定端口/能连上但/操作慢` | `cs_app_slow` (C/S 应用慢) |
| `全网/网络慢/带宽/拥塞/全局/整体` 或空 | `network_slow` (网络运行异常) |

#### 流程一：网络慢/网络运行异常（4 步）

| 步骤 | NAPM 查询 | 判断提示 | 跳转选项 |
|------|---------|---------|---------|
| step1: 总流量趋势 | TotalTraffic TPIO/TPI/TPO timeValues（故障窗 + 基线窗） | 5 条（带宽占用/方向异常/包速异常/流量正常） | 继续Top对象 / 转应用分析 |
| step2: Top 对象 | DefinedApp + IPAddress + BusinessGroup + IPConversation Top10 TPIO | 5 条（应用/主机/工作组/会话/分散） | 继续网络质量 / 转应用分析 / 转安全异常 |
| step3: 网络质量 | IPAddress + BusinessGroup + DefinedApp RTTI/RTTO/PLI/PLO/RTDI/RTDO Top10 | 6 条（拥塞/链路质量/工作组/主机/失败率/成功率） | 继续连接失败 / 转网络质量专项 |
| step4: 连接失败 | IPAddress + DefinedApp + BusinessGroup RFCI/RFCO/FLSI/FLSO Top10 | 4 条 + 5 条数据包触发条件 | 转安全异常 / 转连接失败 / 生成报告 |

#### 流程二：B/S 业务慢（3 步）

| 步骤 | NAPM 查询 | 判断提示 | 跳转选项 |
|------|---------|---------|---------|
| step1: 业务整体 | WebApplication PGSLPCT/PGNSLPGE/PGTME/PGHTTP400/PGHTTP500/PGBYTI/PGBYTO timeValues + Top10 | 6 条（访问量/慢访问/400/500/服务器/传输） | 继续异常URL / 转连接失败 |
| step2: 异常URL | WebApplication→PageFamily 慢URL/错误URL + →ClientIPs→IPAddress 慢客户端 | 6 条（某URL慢/500集中/400集中/多URL/少数客户端/某服务器） | 继续拆分耗时 / 建议下载包 |
| step3: 拆分耗时 | WebApplication PGTME/PGSVTM/PGNTME/UETI/UETO Top10 | 5 条 + 5 条数据包触发条件 | 建议下载包 / 生成报告 |

#### 流程三：C/S 应用慢（2 步）

| 步骤 | NAPM 查询 | 判断提示 | 跳转选项 |
|------|---------|---------|---------|
| step1: 应用运行状况 | Application/DefinedApp TPIO/TPI/TPO/CONI/CONO/SCSI/SCSO/FLSI/FLSO timeValues + Top10 | 6 条（失败/建连/服务器响应/传输/重传/用户体验） | 继续拆分耗时 / 转连接失败 / 转网络质量 |
| step2: 拆分用户体验 | Application CSTI/CSTO/SRTI/SRTO/DTTI/DTTO/RTDI/RTDO/UETI/UETO Top10 + RTTI/RTTO/PLI/PLO | 4 条 + 5 条数据包触发条件 | 建议下载包 / 转网络质量 / 生成报告 |

#### 流程跳转

| 从 | 到 | 触发关键词 |
|------|------|------|
| 网络慢 step2 | B/S 应用慢 step1 | "转应用分析" / "转业务分析" |
| 网络慢 step3 | 网络质量专项 [未实现] | "转网络质量" / "丢包重传为主" |
| 网络慢 step4 | 安全异常 [未实现] | "转安全异常" |
| 网络慢 step4 | 连接失败 [未实现] | "转连接失败" |
| B/S 应用慢 | 网络慢 | "网络侧异常" / "转网络分析" |
| B/S 应用慢 | 连接失败 [未实现] | "转连接失败" |
| B/S 应用慢 | 网络质量专项 [未实现] | "转网络质量" |
| C/S 应用慢 | 网络慢 | "转网络分析" |
| C/S 应用慢 | 网络质量专项 [未实现] | "转网络质量" |

```
│ 2. 构建 session { flowType, context, completedSteps:[] }│
│ 3. executeStep(session, "step1_traffic_trend")        │
│    ├── Steps.buildQueries() → NAPM 查询计划            │
│    ├── SummaryClient → NAPM API                       │
│    ├── Steps.analyzeStepData() → 数据标记（⚠空壳）     │
│    ├── matchHints() → 提示文本 + 数据包触发条件         │
│    └── return { session, step: {data,hints,nextOptions} }│
└───────────────────────────────────────────────────────┘
                        ↓
┌─ 用户决策 → Service.nextAction(session, decision) ────┐
│ decision = "继续下一步":                                │
│   getNextStep() → executeStep(nextStepId)              │
│ decision = "转应用分析":                                │
│   resolveJump() → flowType="bs_app_slow", step1        │
│ decision = "生成报告":                                  │
│   ReportBuilder.build(session)                         │
└───────────────────────────────────────────────────────┘
                        ↓
┌─ FaultDiagnosisReportBuilder.build(session) ──────────┐
│ 遍历 completedSteps:                                   │
│   → 步骤描述 (summary)                                  │
│   → 判断提示 (items)                                    │
│   → 数据包触发 (items)                                  │
│   → 用户判断 (summary)                                  │
│   → NAPM 数据表 (table)                                 │
│   → 证据汇总 (table)                                    │
│   → 根因判断 (summary)                                  │
│   → 处置建议 (items)                                    │
│   → 验证方式 (items)                                    │
│ output: reportData { templateId:"napm_fault_diagnosis_v2",│
│                      sections: [18 sections] }         │
└───────────────────────────────────────────────────────┘
                        ↓
┌─ ReportTemplateService.renderDocx() ──────────────────┐
│ 不匹配任何固定模板 → 通用渲染管线                       │
│ 遍历 sections[] → table/chart/items/summary            │
│ → .docx                                               │
└───────────────────────────────────────────────────────┘
```

## 五、不足分析

> **说明**：本分析聚焦 OpenClaw → Skill 调用链路，不考虑 CLI 需求。
> 用户通过企微 → OpenClaw → Skill 使用，OpenClaw 侧负责意图识别、参数构造、session 透传和结果展示。

### 5.1 致命级（阻断 OpenClaw 正常调用）

#### ❌ 不足 1：v2 session 无持久化（OpenClaw 跨轮调用状态丢失）

**影响**：OpenClaw 每次调用 `start()` 都会创建新 session。企微端用户说"继续下一步"时，OpenClaw 需要把上一轮的 session 传回来，但当前 session 只是一个内存对象，没有提供序列化方法。OpenClaw 无法在跨轮对话中保持诊断进度。

**位置**：`FaultDiagnosisService.js` — session 对象通过 JS 引用传递，无 `serializeSession()` / `deserializeSession()` 方法。

**根因**：`FaultDiagnosisService.start()` 每次创建新 session；`nextAction(session, decision)` 需要外部持有 session 引用。OpenClaw 作为调用方，需要在每轮对话中把 session JSON 序列化后透传。

**修复方案**：在 `FaultDiagnosisService` 中加入两个方法：
- `serializeSession(session)` → JSON 字符串（`completedSteps[].rawData` 需截断，避免超大 JSON）
- `deserializeSession(json)` → session 对象

OpenClaw 调用链变为：
```
Turn 1: start() → 返回 { sessionJson, step }
Turn 2: deserialize(sessionJson) → nextAction(session, "继续下一步") → 返回 { sessionJson, step }
Turn 3: deserialize(sessionJson) → nextAction(session, "生成报告") → { reportData }
```

工作量约 50 行。这是 P0 必须做的——否则 OpenClaw 无法完成多轮诊断。

---

#### ❌ 不足 2：v2 analyzeStepData 是空壳

**影响**：这是 v2 最核心的缺陷。公司流程中所有的"如果 X 指标 > Y 阈值，则判断为 Z"逻辑都没有实现。`_analyzeNetworkStep1/2/3/4`、`_analyzeBsStep1/2/3`、`_analyzeCsStep1/2` 共 9 个方法，全部只返回一个占位标记。

**位置**：`FaultDiagnosisSteps.js` 中的 `_analyzeNetworkStep1/2/3/4`、`_analyzeBsStep1/2/3`、`_analyzeCsStep1/2`

**当前行为**：
```javascript
_analyzeNetworkStep1(raw = {}) {
  const flags = {};
  if (raw.faultTrend) flags.hasFaultData = true;
  flags.trafficNormal = true;  // ← 永远返回"流量正常"，无论实际数据如何
  return flags;
}
```

**应有的行为**：根据公司流程的判断规则，对 rawData 做实际分析——

以 Step1 为例，应实现的逻辑：
```javascript
_analyzeNetworkStep1(raw = {}) {
  const flags = {};
  const trend = normalizeTimeSeries(raw.faultTrend);
  const tpioValues = trend.TPIO || [];
  const avg = average(tpioValues);
  const max = max(tpioValues);
  const ppsValues = trend.PPSI || [];

  // 判断1: 总吞吐量是否明显升高
  if (max > avg * 2) flags.totalBytesIncreased = true;
  // 判断2: 流入异常高
  const tpiAvg = average(trend.TPI || []);
  const tpiMax = max(trend.TPI || []);
  if (tpiMax > tpiAvg * 2.5) flags.inboundAbnormal = true;
  // 判断3: 流出异常高
  const tpoAvg = average(trend.TPO || []);
  const tpoMax = max(trend.TPO || []);
  if (tpoMax > tpoAvg * 2.5) flags.outboundAbnormal = true;
  // 判断4: 包速高但字节不高
  if (average(ppsValues) > 10000 && avg < 100000) flags.lowBytesHighPps = true;
  // 判断5: 流量正常
  if (!flags.totalBytesIncreased && !flags.inboundAbnormal && !flags.outboundAbnormal) {
    flags.trafficNormal = true;
  }

  return flags;
}
```

9 个方法都需要类似的实现。**这是当前 v2 最大的功能缺口——没有实际的数据判断，提示匹配基本无效。**

**修复方案**：逐步骤实现判断逻辑，参照公司文档的判断规则表。约 300-400 行代码。这是 P0 必须做的。

---

### 5.2 功能级（可用但不完善）

#### ⚠ 不足 3：6 类流程只实现了 3 类

未实现的流程：

| 流程 | 状态 | FlowRouter 是否可识别 |
|------|:--:|:--:|
| 用户/部门/客户端投诉 | 未实现 | 否（`classify()` 无此分支） |
| 连接失败/RST/超时/交易失败 | 未实现 | 否（跳转目标存在但无步骤定义） |
| 丢包/延时/重传网络质量专项 | 未实现 | 否（跳转目标存在但无步骤定义） |
| 安全异常/攻击/病毒/蠕虫/非法外连 | 未实现 | 否（跳转目标存在但无步骤定义） |

**影响**：跳转选项中提到的"网络质量专项""安全异常""连接失败"都不可用。用户选择跳转后只会回到当前流程的下一步。

---

#### ⚠ 不足 4：场景识别靠关键词，但 OpenClaw 可指定 flowType 绕过

**影响**：`classify()` 的关键词匹配在复杂描述下可能误判。但 OpenClaw 作为调用方可以在构造 input 时直接指定 `flowType`。

**当前状态**：`FaultDiagnosisService.start()` 未暴露 `flowType` 覆盖参数。

**修复方案**：在 `start()` 的 input 解析中增加 `flowType` 字段——如果 OpenClaw 传了，跳过 `classify()`，直接使用。工作量约 10 行。

---

#### ⚠ 不足 5：数据包分析未联动（需手动切换 Skill）

**影响**：系统提示"建议下载数据包"后，用户需手动去 `openclaw-napm-packet-analysis` 抓包。缺少：
- 自动生成抓包参数（五元组 + 时间范围）
- 一键触发抓包
- 抓包结果自动合并到报告证据项

**修复方案**：在 `nextOptions` 中加入"下载数据包"选项，调用 `openclaw-napm-packet-analysis`，将返回结果追加到 session 的 completedSteps。工作量约 100 行。

---

#### ⚠ 不足 6：无阈值可配置化

**影响**：即使补全了 `analyzeStepData`，判断阈值（如"升高"定义为几倍）是硬编码的，无法按业务场景调优。

**修复方案**：阈值写入配置文件（如 `templates/thresholds.v1.json`），支持按场景覆盖。工作量约 100 行。

---

### 5.3 报告级（输出质量问题）

#### ⚠ 不足 7：v2 报告无图表

**影响**：§8 结构的"证据项"应该包含趋势图、Top 排行图、丢包延时图等，但 v2 ReportBuilder 生成的 sections 全是 `summary` + `table` + `items`，没有 `chart` 类型。

**原因**：通用渲染管线的 `chart` section 需要 ECharts SSR 渲染（`preRenderCharts()` → PNG）。v2 ReportBuilder 既没有生成 `chart` section，也没有配 `chartSpecs`。

**修复方案**：在 `FaultDiagnosisReportBuilder._buildDataSection()` 中，当检测到 timeValues 数据时生成 `chart` section 而非 `table` section。需配 NAPM 色系图表规格。工作量约 150 行。

---

#### ⚠ 不足 8：数据表截断

**影响**：timeValues 数据最多展示 50 行（`Math.min(valCount, 50)`）。大时间窗口（如一天 1 分钟粒度 = 1440 行）会严重截断。

**修复方案**：同巡检模板的 `pickDatasetPoints()` 做法，取头尾各一半。工作量约 20 行。

---

#### ⚠ 不足 9：报告无封面

**影响**：通用渲染管线没有 `cover` 类型 section，报告直接以标题段落开始，缺乏专业封面。

**修复方案**：在 v2 报告最前面加一个 `summary` section 充当封面，包含故障名 + 分析类型 + 时间。工作量约 30 行。

---

### 5.4 v1 残留问题

#### ⚠ 不足 10：v1 的 fault scope 与 v2 命名混淆

**影响**：两个入口、两个 templateId。OpenClaw 不知道什么时候该用哪个。

**修复方案**：在各自的 SKILL.md 中明确区分：
- v1 — 一键快速报告（`openclaw-napm-summary` 的 `fault` scope）
- v2 — 分步诊断分析（`openclaw-napm-fault-diagnosis`）

---

#### ⚠ 不足 11：v1 的 one-shot 模式不符合公司流程

**影响**：v1 查了全部数据但不走分步判断，直接从原始数据跳到根因推断。与公司"先看流量→看Top对象→看网络质量→看连接失败"的逐步分析流程不一致。

**修复方案**：长期将 v1 废弃或作为 v2 "全部步骤一键执行"的快捷模式。
