## 2. NetInside API 层级理解

本次已经确认，“未知端口流量”在 NetInside 中对应的不是一个单独的 `security` group type，而是下面这条 4 层查询路径：

```text
TotalTraffic
  -> IPProtocol (TCP / UDP)
    -> OtherApps
      -> OtherApp
```

如果展开成 `topValues` 查询参数，核心结构是：

```text
type=topValues
numGroups=4
groupType1=TotalTraffic
groupType2=IPProtocol
groupArgument2=TCP 或 UDP
groupType3=OtherApps
groupType4=OtherApp
metrics=TPIO
topMetric=TPIO
topCount=10
```

这里各层的含义是：

- `TotalTraffic`：总流量入口
- `IPProtocol`：协议分层，必须落到 `TCP` 或 `UDP`
- `OtherApps`：其它/未知应用这一类容器节点
- `OtherApp`：具体未知端口/未知应用项

需要特别强调：

- `security` 在当前项目里只是一个“场景标签”或“理解提示”
- `security` 不是 NetInside API 查询路径中的真实 group type
- 真正执行查询时，仍然必须落到上面的 4 层 group 链路

## 3. 本次确定的最终规则

### 3.1 明确指定了 TCP

如果用户问法里明确带有 `TCP`，则只发起一条 `TCP` 直查。

例如：

```text
未知TCP端口流量Top10
未知 TCP 端口流量排行
```

对应执行规则：

```text
TotalTraffic -> IPProtocol(TCP) -> OtherApps -> OtherApp
```

不会再去查 `UDP`。

### 3.2 明确指定了 UDP

如果用户问法里明确带有 `UDP`，则只发起一条 `UDP` 直查。

例如：

```text
未知UDP端口流量排行
未知 UDP 端口流量 Top10
```

对应执行规则：

```text
TotalTraffic -> IPProtocol(UDP) -> OtherApps -> OtherApp
```

不会再去查 `TCP`。

### 3.3 没有明确说明 TCP 或 UDP

如果用户只问：

```text
未知端口流量排行
未知端口流量Top10
其它端口流量排行
```

则项目现在的处理方式是：

- 不归到 `overview`
- 不强行只查 `TCP`
- 不强行只查 `UDP`
- 而是直接拆成两条独立查询：
  - 一条 `TCP`
  - 一条 `UDP`

也就是说，“未指定协议”的默认行为已经固定为：

```text
分别查询 TCP 未知端口流量 + UDP 未知端口流量
```

### 3.4 本次规则不覆盖的问法

下面这些带有明显趋势/概览语义的问法，不在本次“未知端口流量 TopN 直查”硬规则里：

```text
未知端口流量趋势
未知端口流量变化
未知端口流量概览
未知端口流量整体情况
```

这类问法仍然需要上游继续做更细的意图判定，而不是直接套本次的 TopN 规则。

## 4. 项目内的实现落点

### 4.1 核心执行文件

本次主要修改文件：

- `skills/openclaw-napm-query/scripts/run_napm_query.js`
- `skills/openclaw-napm-query/scripts/overview-module.js`

### 4.2 `run_napm_query.js` 中新增/调整的能力

本次在 `run_napm_query.js` 中新增了以下逻辑：

- `isUnknownPortTrafficPrompt`
  - 判断当前问法是否属于“未知端口/未知应用流量”类问题
- `detectUnknownPortProtocol`
  - 判断用户是否明确指定了 `TCP` 或 `UDP`
- `buildPromptFallbackUnknownPortResolvedQuery`
  - 用于生成“明确协议时”的单协议直查 `resolvedQuery`
- `buildPromptFallbackUnknownPortDualProtocolResolvedQuery`
  - 用于生成“未指定协议时”的双协议直查 `resolvedQuery`
- `executeUnknownPortDualProtocolQuery`
  - 用于实际串行执行 `TCP` + `UDP` 两条查询，并合并结果

同时还做了以下接线：

- 在 `buildPromptFallbackResolvedQuery(...)` 中接入未知端口流量识别
- 在 `executeResolvedQuery(...)` 中接入 `topValues_multi_protocol`
- 在 `buildSummary(...)` 中补充双协议结果摘要
- 在 `module.exports.__test__` 中导出对应辅助函数，方便回归验证

### 4.3 `overview-module.js` 中的定位

`overview-module.js` 本次只补了一层场景提示：

- 当问法形态明显是“未知 TCP/UDP 端口/应用流量”时，可识别为 `security` 场景

但要注意：

- 这只是场景理解提示
- 不代表未指定协议时要走 `overview`
- 真正执行时，未指定协议的问法现在已经直接拆成 `TCP` + `UDP` 两条直查

## 8. 一个容易误解的点

当前运行模式下，`run_napm_query.js` 的命令行主入口默认是“上游下发 `resolvedQuery` 后执行”，并不是“本地随意拿自然语言 prompt 自己做全链路理解”。

因此如果直接在命令行执行：

```bash
node /home/netinside/.openclaw/skills/openclaw-napm-query/scripts/run_napm_query.js --prompt '未知端口流量排行'
```

当前更可能得到的是：

```text
UPSTREAM_RESOLVED_QUERY_REQUIRED
```

这不表示本次规则没有生效，只表示：

- 当前 CLI 主入口要求上游先完成理解
- 本次规则的验证应看 `resolvedQuery` 生成逻辑
- 或通过真实 OpenClaw 主链触发

所以后续排查这类问题时，不要把“CLI 直接传 `--prompt` 返回上游先解析”误判为本次改动失效。
