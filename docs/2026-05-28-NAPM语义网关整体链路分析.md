# NAPM 语义网关整体链路分析

分析日期：2026-05-28  
分析范围：当前工作区代码，包含当前未提交改动。  
远端验证：已在远端 OpenClaw 主机做只读链路探查和一次低风险 skill executor smoke；文档中的远端地址、账号、密码和上游 API 地址均使用占位符，不写入真实凭据。  
核心结论：当前项目不是传统 HTTP 网关形态，而是“OpenClaw Gateway 进程 + OpenClaw 扩展插件 + NAPM skill 运行时 + NetInside/NAPM WebService 客户端”的直接查询链路。生产链路必须以 `napm-skill-query` 为唯一入口，OpenClaw 主链负责自然语言理解与 `resolvedQuery` 构造，插件负责边界与强制路由，skill 负责结构化查询的校验、执行、归一化和叙述契约输出。

## 1. 项目定位

项目名：`NAPM Semantic Gateway`

当前仓库的真实职责可以概括为：

1. 给 OpenClaw 注册 NAPM 插件能力。
2. 强制 NAPM 相关请求经过单一生产工具 `napm-skill-query`。
3. 接收 OpenClaw 已经构造好的 `resolvedQuery`。
4. 将 `resolvedQuery` 转成 NetInside/NAPM WebService 参数。
5. 执行元数据查询、指标查询、概览分析、下钻目录查询等能力。
6. 返回结构化数据和 `OpenClaw` 可消费的中文回答叙述契约。

需要特别注意一个历史命名问题：

- 代码中仍有不少 `GatewayRequest`、`executeGatewayRequest`、`gatewayRequest` 命名。
- 这些名称现在主要表示“结构化执行请求”，不代表旧项目级 gateway 层仍然是当前主链。
- 当前 `SKILL.md` 已明确要求不要依赖旧 `src/routes`、项目级 `src/services` 或旧 gateway policy。

## 3. 当前端到端主链路

```text
用户问题
  -> OpenClaw 会话/消息
  -> napm-openclaw-plugin.remote.js
     -> message_received: 记录当前 prompt 是否 NAPM 相关
     -> before_prompt_build / before_agent_start: 注入 NAPM 路由政策
     -> before_tool_call: 只允许 napm-skill-query 作为生产查询入口
  -> OpenClaw 主链完成意图理解、对象口径、时间范围、指标、group path 构造
  -> 调用 napm-skill-query，传入 structured resolvedQuery
  -> 插件边界校验 resolvedQuery
  -> runSkillExecutor 启动 node skills/openclaw-napm-query/scripts/run_napm_query.js
  -> run_napm_query.js 解析 payload，进入 skill 执行链
  -> RequirementParserService.prepareGatewayExecution / executeGatewayRequest
  -> MetadataExecutionKernel 或 MetricExecutionKernel
  -> NapmClient
  -> NetInside / NAPM WebService
  -> 解析 JSON/CSV 结果
  -> OpenClawNarrationContractService 构造 narrationInput/displayText/summary
  -> 插件把结果交还 OpenClaw
  -> OpenClaw 生成最终中文回答
```

主链中最关键的边界是：

- `OpenClaw`：负责自然语言理解、范围判断、是否需要澄清、上下文继承、`resolvedQuery` 构造。
- `napm-openclaw-plugin`：负责工具注册、系统提示注入、hook 守卫、`resolvedQuery` 边界校验、调用 skill executor。
- `openclaw-napm-query skill`：负责执行结构化查询，不再正式承担 prompt 到 query 的主链解析。
- `NapmClient`：负责最终访问 NAPM WebService，补充账号密码、构造请求、脱敏日志。

远端真实主链可以展开为：

```text
OpenClaw Gateway(:18789)
  -> ~/.openclaw/extensions/napm-openclaw-plugin/index.mjs
  -> ~/.openclaw/extensions/napm-openclaw-plugin/index.js
  -> execFile("node", [
       "~/.openclaw/skills/openclaw-napm-query/scripts/run_napm_query.js",
       "--payload",
       "<structured payload>"
     ])
  -> ~/.openclaw/skills/openclaw-napm-query/scripts/run_napm_query.js
  -> ~/.openclaw/skills/openclaw-napm-query/services/*
  -> ~/.openclaw/src/utils/* and ~/.openclaw/src/constants/*
  -> ~/.openclaw/config/*.json
  -> NetInside / NAPM WebService
```

## 4. 插件层链路

### 4.1 插件入口

入口文件：

- `napm-openclaw-plugin.index.mjs`
- `napm-openclaw-plugin.remote.js`
- `openclaw.plugin.json`

`napm-openclaw-plugin.index.mjs` 的加载逻辑是：

```text
try require('./index.js')
catch MODULE_NOT_FOUND -> require('./napm-openclaw-plugin.remote.js')
```

所以在当前仓库没有 `index.js` 的情况下，实际插件实现来自 `napm-openclaw-plugin.remote.js`。

`openclaw.plugin.json` 声明：

- 插件 id：`napm-openclaw-plugin`
- 激活能力：`tool`、`hook`
- 工具合约：`napm-skill-query`

### 4.2 注册的生产工具

生产工具只有一个：

```text
napm-skill-query
```

工具参数重点：

- `prompt` / `userQuery`：仅保留原始问题，用于追踪，不能替代结构化查询。
- `decision`：可选，上游决策 trace。
- `intent`：可选，上游意图 trace。
- `resolvedQuery`：必需，生产查询的真正输入。
- `sessionState`：可选，多轮上下文。

其中 `resolvedQuery` 对可执行数据查询有强约束：

- `topValues`
- `averageValues`
- `timeValues`
- `overview`
- `topValues_multi_protocol`

这些 service 必须在根级字段放置：

```json
{
  "start": 1779638400,
  "end": 1779724740
}
```

不能只放在：

```json
{
  "timeRange": {
    "start": 1779638400,
    "end": 1779724740
  }
}
```

`timeRange` 在当前契约中只是声明性元数据，主要用于 `key`、`displayText`。

### 4.3 Hook 守卫

插件注册了多类 hook，核心作用如下：

| Hook | 作用 |
| --- | --- |
| `message_received` | 记录会话级 guard state，判断当前消息是否 NAPM 相关、系统监控相关或越界。 |
| `before_prompt_build` / `before_agent_start` | 注入 NAPM 路由系统提示，要求 NAPM 请求必须走 `napm-skill-query`。 |
| `before_tool_call` | 拦截旧直连工具和非授权工具；校验 `napm-skill-query` 的 `resolvedQuery`；必要时重写参数。 |
| `message_sending` | 防止把中间推理、绕过 skill 的过程、手工层级推测等内容直接发给用户。 |

被明确移除或阻断的旧工具：

- `napm-topn`
- `napm-average`
- `napm-timeseries`

当当前 prompt 被识别为 NAPM 相关时，除 `napm-skill-query` 外，生产链路不应调用 shell、exec、部署、配置修改等系统操作工具。开发诊断工具 `napm-resolve-query`、`napm-mainflow-query` 只有在 `NAPM_ENABLE_DEV_RESOLVER_TOOLS=true` 时才注册。

### 4.4 插件调用 skill 的方式

插件通过 `runSkillExecutor(args)` 启动 skill：

```text
node skills/openclaw-napm-query/scripts/run_napm_query.js --payload <json>
```

在远端实际是：

```text
node ~/.openclaw/skills/openclaw-napm-query/scripts/run_napm_query.js --payload <json>
```

payload 中包含：

- `traceId`
- `prompt`
- `userQuery`
- `decision`
- `intent`
- `resolvedQuery`
- `sessionState`
- `clarificationContext`

执行环境会默认补：

```text
NETINSIDE_TLS_INSECURE=true
FORCE_COLOR=0
NO_COLOR=1
```

插件会从 stdout 尾部提取 JSON 作为 skill 结果，因此 skill 最后必须输出可解析的 JSON 对象。

## 5. resolvedQuery 构造与边界

### 5.1 当前生产原则

当前主链是 `resolvedQuery-first`：

- 没有 `resolvedQuery` 时，skill 不会从 prompt 本地猜查询。
- 缺失 `resolvedQuery` 会返回中文 fallback contract，要求 OpenClaw 先完成结构化意图解析。
- `decision` 只是 trace 和 guardrail，不是执行前置阻塞条件。

### 5.2 相关服务

| 服务 | 作用 |
| --- | --- |
| `PromptRoutingService` | 对明显场景做快速路由识别，例如 overview、指标清单、业务对象清单、层级目录。 |
| `NapmResolvedQueryResolverService` | 轻量级 prompt -> `resolvedQuery` 解析器，主要用于高确定性的元数据清单和 TopN 场景；生产中更像诊断/辅助能力。 |
| `ResolvedQueryTimeRangeService` | 时间范围唯一构造者之一，负责最近 1 小时、最近 24 小时、今天、昨天等时间窗口，并按分钟对齐。 |
| `ResolutionSpecService` | 读取 `config/napm-resolution-spec.v1.json`，提供 service 契约和配置访问。 |
| `WorkflowClassifierService` | 根据文本识别 object inventory、metric inventory、drilldown catalog、topn、average、trend、overview 等 workflow。 |
| `ObjectOntologyService` | 读取对象本体，识别对象别名、对象歧义和实例来源。 |

### 5.3 时间契约

`config/napm-resolution-spec.v1.json` 明确规定：

- 时间戳单位：秒。
- 可执行时间字段：根级 `start`、`end`。
- `start/end` 必须按 60 秒边界对齐。
- `timeRange.start/timeRange.end` 不能替代根级字段。

`ResolvedQueryTimeRangeService` 负责常见时间：

| 用户时间语义 | key | 构造规则 |
| --- | --- | --- |
| 最近 1 小时 | `last1hour` | 当前分钟向前 3600 秒。 |
| 最近 24 小时 | `last24hours` | 当前分钟向前 86400 秒。 |
| 今天 | `today` | 本地当天 00:00:00 到 23:59:00。 |
| 昨天 | `yesterday` | 本地上一天 00:00:00 到 23:59:00。 |
| 最近 N 分钟/小时/天 | `lastNminutes/hours/days` | 相对当前分钟回溯。 |

## 6. Skill 执行器链路

主入口：

```text
skills/openclaw-napm-query/scripts/run_napm_query.js
```

### 6.1 输入解析

`resolveInput(args, payload)` 会按顺序获取：

1. `prompt`
2. `decision`
3. `intent`
4. `session`
5. `resolvedQuery`

`resolvedQuery` 来源优先级：

1. `--queryJson`
2. `--resolvedQuery`
3. `payload.resolvedQuery`

如果没有 `resolvedQuery`，会抛出 `UPSTREAM_RESOLVED_QUERY_REQUIRED`，最终被包装成中文决策结果，而不是低层英文错误。

### 6.2 执行前特殊分支

进入真实查询前有几类短路：

| 分支 | 条件 | 输出 |
| --- | --- | --- |
| 敏感凭据保护 | prompt 命中密码、token 等敏感信息请求 | `security_refusal` 决策结果 |
| 澄清问题 | `clarificationGate.required=true` | 中文澄清 contract |
| 执行守卫 | `resolvedQuery.executionGuard.blockExecution=true` 且不是 overview | 中文澄清/阻断 contract |
| 下钻目录 | `service=drilldownCatalog` | 从静态/本地 hierarchy 构造目录结果 |

### 6.3 executeResolvedQuery 分发

`executeResolvedQuery(prompt, resolvedQuery, payload, intentResult)` 是主要调度点：

```text
topValues_multi_protocol
  -> executeUnknownPortDualProtocolQuery

overview + analysisPipeline.discoveryQuery
  -> discovery top query
  -> 锁定对象
  -> 构造 focused overview
  -> executeOverviewModule

overview
  -> executeOverviewModule

其他 service
  -> RequirementParserService.executeGatewayRequest
```

## 7. RequirementParserService 执行主链

核心文件：

```text
skills/openclaw-napm-query/services/RequirementParserService.js
```

虽然名字叫 `RequirementParserService`，但当前主要职责是运行时执行服务：

1. 对结构化查询做准备和收口。
2. 规范 metric、groups、topCount、granularity。
3. 结合静态和动态元数据做最终校验。
4. 根据 workflow/service 选择执行内核。
5. 调用 NAPM。
6. 解析结果。
7. 分类失败并返回结构化错误。

### 7.1 prepareGatewayExecution

这一步负责执行前准备，主要会用到：

- `QueryMetadataConstraintService`
- `NapmMetadataService.reviewQuery`
- `GroupPathPlannerService`
- `ExecutionKernelPolicy`

处理重点：

- `Application` 顶层对象归一到 `DefinedApp`。
- 指标字段统一大写。
- `metrics` 与 `metric/topMetric` 互相补齐。
- `topCount` 限制在合理范围。
- `timeValues.granularity` 归一到支持粒度。
- 对 group path 做静态路径规划和必要的动态元数据检查。
- 根据上游 metadata 结果决定是否允许修复或 fallback。

### 7.2 执行内核选择

`ExecutionKernelPolicy.resolveExecutionKernel(query)` 根据 workflow/service 选择：

```text
metadata kernel:
  groups
  metrics
  metricsForGroup
  drilldownCatalog
  applications
  businessGroups
  groupArguments

metric kernel:
  topValues
  averageValues
  timeValues
  overview
  alertsSummary
```

同时会校验 workflow 与 service 是否冲突：

- metadata workflow 不能执行 metric service。
- metric workflow 不能执行 metadata service。

冲突时抛出：

```text
WORKFLOW_SERVICE_CONTRACT_MISMATCH
```

## 8. 元数据查询链路

入口：

```text
MetadataExecutionKernel.execute()
```

### 8.1 指标清单

当：

```json
{
  "service": "metrics",
  "groups": [{ "type": "WebApplication" }]
}
```

链路为：

```text
MetadataExecutionKernel
  -> NapmMetadataService.getMetricsForGroupPath(groups)
  -> NAPM type=metricsForGroup
  -> filterMetricInventoryForOwnership
  -> response.data = ownedMetrics
```

`filterMetricInventoryForOwnership` 会使用 `src/constants/objectMetricOwnership.js`，保证：

- WebApplication、PageFamily、User、ClientBusinessGroup 只展示业务/Web 体验指标为主。
- TotalTraffic、IPAddress、BusinessGroup、DefinedApp 等展示网络、连接、应用性能等非 Web 业务指标。

这也是“业务都可以查哪些指标”必须落在 `WebApplication` 口径的原因。

### 8.2 对象清单

当：

```json
{
  "service": "groups",
  "groups": [{ "type": "WebApplication" }]
}
```

链路为：

```text
MetadataExecutionKernel
  -> NapmMetadataService.resolveObjectInstanceProviderMetadata(objectType)
  -> NapmMetadataService.listObjectInstances(objectType)
  -> 根据 provider 选择 southbound API
```

对象实例来源由 `ObjectMetadataRegistry` 和 `ObjectOntologyService` 控制：

| 对象 | 实例来源 |
| --- | --- |
| `WebApplication` | `applications` API，过滤 `Type=3`。 |
| `DefinedApp` | `applications` API，过滤 `Type=2`。 |
| `CompositeApplication` | `applications` API，过滤 `Type=4`。 |
| `BuiltinApplication` | `applications` API，过滤 `Type=1`。 |
| `BusinessGroup` | `businessGroups` API。 |
| `PageFamily` / `User` / `OtherApp` 等 | `groupArguments` API。 |

重要边界：

- 对象实例清单必须来自 southbound live API。
- `groups-tree.static.json` 只能描述 hierarchy，不应用作应用清单真实来源。
- 清单查询中 `argument:"all"` 是非法形态，表示全量清单时应省略 `argument`。

### 8.3 下钻目录

`service=drilldownCatalog` 使用本地 group tree 优先回答结构问题：

```text
run_napm_query.js
  -> buildHierarchyCatalogPayloadFromResolvedQuery
  -> NapmMetadataService.getTopLevelDrilldownCatalog / getDrilldownPathsForGroupType
  -> buildHierarchyCatalogContract
```

这里回答的是“结构可达性”，不是“某条路径一定可执行”。运行时可执行性和指标兼容性仍要依赖 `metricsForGroup` 或真实 API 校验。

## 9. 指标查询链路

入口：

```text
MetricExecutionKernel.execute()
```

支持的核心 service：

- `topValues`
- `averageValues`
- `timeValues`

### 9.1 URL 参数构造

`MetricExecutionKernel` 会构造：

```text
type=<service>
start=<root-level start>
end=<root-level end>
json=true
metrics=<metric csv>
topMetric=<topMetric, only topValues>
topCount=<topCount, only topValues>
granularity=<granularity, only timeValues>
groupType1=<type>
groupArgument1=<argument>
...
numGroups=<groups.length>
```

group 参数由 `GroupBuilder.buildGroupParams(groups)` 生成：

```json
{
  "groupType1": "WebApplication",
  "groupArgument1": "xxx",
  "groupType2": "ClientIPs",
  "numGroups": 2
}
```

### 9.2 请求执行

最终请求由 `NapmClient.get(params)` 发出：

```text
NapmClient
  -> buildOrderedParams({ UserName, Password, ...params })
  -> axios GET
  -> 返回 JSON 或 CSV
```

日志中通过 `maskSensitiveParams` 和 `buildSafeUrl` 对账号密码脱敏。

### 9.3 结果解析

`RequirementParserService.parseNapmPayload(rawPayload)` 支持：

- 数组 JSON：原样返回。
- 对象 JSON：包装为单元素数组。
- JSON 字符串：解析后返回。
- CSV 字符串：用 `CsvParser.parseSync` 解析。
- 空字符串或未知格式：返回空数组。

## 10. Overview 概览链路

概览入口：

```text
skills/openclaw-napm-query/scripts/overview-module.js
```

概览不是单个 API，而是一组候选查询的编排执行。

### 10.1 概览输入

典型 `resolvedQuery`：

```json
{
  "service": "overview",
  "queryModeKey": "overview",
  "overviewScene": "network",
  "start": 1779638400,
  "end": 1779724740,
  "groups": [],
  "semanticConstraints": {
    "operation": "overview",
    "overviewScene": "network"
  }
}
```

`overviewScene` 主要包括：

- `system`
- `business`
- `business_group`
- `application`
- `network`
- `security`

`overviewDepth` 主要包括：

- `fast`
- `standard`
- `deep`

### 10.2 概览编排步骤

```text
executeOverviewModule
  -> resolveOverviewScene
  -> resolveOverviewDepth
  -> getOverviewBudget
  -> resolveOverviewTimeRange
  -> listOverviewCandidates(scene)
  -> loadOverviewMetadataReviewSafely
  -> extractOverviewSlots
  -> buildOverviewPlan
  -> compileOverviewPlan
  -> executeOverviewPlan
  -> reduceOverviewResults
```

### 10.3 候选模块

候选模块定义在：

```text
OverviewCandidateRegistry.js
```

每个 candidate 包含：

- `id`
- `label`
- `scenes`
- `role`
- `priority`
- `minDepth`
- `request`
- `capability`
- `cost`
- 可选 `childCandidateIds`

例如网络概览可能选：

- IP 吞吐排行
- IP 连接失败排行
- 总体流量趋势

业务概览可能选：

- WebApplication 访问排行
- WebApplication 响应时间排行
- HTTP 500/400 排行
- 慢页面排行

### 10.4 预算模型

`OverviewBudget.js` 定义：

| depth | maxQueries | maxChildren | timeoutMs | retry |
| --- | ---: | ---: | ---: | ---: |
| `fast` | 3 | 0 | 8000 | 0 |
| `standard` | 5 | 2 | 15000 | 0 |
| `deep` | 8 | 4 | 30000 | 1 |

执行器串行跑 root query，并在预算允许时根据 root 结果派生 child query。

### 10.5 discovery + focused overview

复合问题如：

```text
先找到失败最多的 IP，再分析它
```

链路是：

```text
overview resolvedQuery with analysisPipeline.discoveryQuery
  -> discoveryQuery 先执行 TopN
  -> deriveDiscoveryFocusSelection 锁定对象
  -> buildFocusedOverviewResolvedQuery
  -> executeOverviewModule
```

返回结果会包含：

- `discovery.service`
- `discovery.targetObjectType`
- `discovery.selectedObject`
- `discovery.metric`
- focused overview 结果

## 11. 多协议 TopN 链路

`service=topValues_multi_protocol` 用于未知端口等双协议场景。

链路：

```text
executeUnknownPortDualProtocolQuery
  -> 遍历 resolvedQuery.protocolQueries
  -> 每个 protocolQuery 调 RequirementParserService.executeGatewayRequest
  -> 合并 rows
  -> 每行补充 protocol 字段
```

如果所有协议查询失败，返回：

```text
UNKNOWN_PORT_PROTOCOL_QUERIES_FAILED
```

如果没有 `protocolQueries`，返回：

```text
UNKNOWN_PORT_PROTOCOL_QUERIES_MISSING
```

## 12. 输出契约链路

输出构造入口：

```text
OpenClawNarrationContractService.buildOpenClawReplyContract
```

目标是把执行结果统一成 OpenClaw 可消费结构：

```json
{
  "ok": true,
  "decision": {},
  "intent": {},
  "resolvedQuery": {},
  "data": [],
  "responseMode": "machine_narration_input",
  "narrationBy": "openclaw",
  "narrationInput": {
    "schema": "openclaw_napm_narration.v1",
    "type": "query_result",
    "summary": {},
    "result": {
      "narrationStructure": {}
    },
    "renderPolicy": {},
    "followUp": {}
  },
  "summary": {},
  "error": null
}
```

关键规则：

- 所有数据回答都要带数据时间范围。
- 如果结果为空，也要说明查询的指标、对象、时间范围和范围。
- 默认不把上游 API URL 展示给用户，除非 `SHOW_UPSTREAM_API_IN_REPLY=true`。
- 错误由 `ExecutionFailureClassifier` 归一化后进入 `error`。

## 15. 失败与保护路径

| 场景 | 触发位置 | 结果 |
| --- | --- | --- |
| 没有 `resolvedQuery` | 插件校验或 skill `resolveInput` | 返回要求 OpenClaw 先构造 `resolvedQuery` 的中文 contract。 |
| 可执行查询缺少根级 `start/end` | 插件 `validateResolvedQueryAgainstSpec` | 阻断工具调用或返回 boundary failure。 |
| `start/end` 不按分钟对齐 | 插件和 `QueryValidator` | 阻断或返回 `QUERY_SHAPE_INVALID`。 |
| workflow/service 冲突 | `ExecutionKernelPolicy.assertWorkflowServiceContract` | `WORKFLOW_SERVICE_CONTRACT_MISMATCH`。 |
| metric/group 不兼容 | `QueryMetadataConstraintService` + 动态 metadata review | 记录 warning；在允许修复时替换；否则保留并让真实执行暴露结果。 |
| group path 被上游拒绝 | `buildUpstreamPathGuard` | 返回 `UPSTREAM_GROUP_PATH_NOT_SUPPORTED`，附候选路径。 |
| 多层 groups 清单无法稳定返回 | `isMultilevelGroupsInventoryQuery` | 返回 `MULTILEVEL_GROUPS_INVENTORY_NOT_EXECUTABLE`。 |
| 对象清单使用 `argument:"all"` | `assertMetadataInventoryArgumentContract` | 返回 `INVALID_METADATA_INVENTORY_ARGUMENT`。 |
| 试图绕过 skill 讲手工过程 | 插件 `message_sending` | 替换为 skill 结果或提示必须走 skill。 |
| 旧直连工具调用 | 插件 `before_tool_call` | 阻断并要求使用 `napm-skill-query`。 |

## 19. 排障入口建议

### 19.1 用户问了 NAPM 问题但没有查数据

优先看：

1. `logs/audit.log`
2. 是否出现 `napm_plugin_resolved_query_blocked`
3. 是否出现 `napm_skill_missing_resolved_query`
4. `resolvedQuerySummary` 中是否有 `service/start/end/groups/metrics`

### 19.2 明明是业务清单却返回了应用协议

优先检查：

1. prompt 是否被识别为 plain `业务`。
2. `resolvedQuery.groups[0].type` 是否为 `WebApplication`。
3. 是否误用了 `DefinedApp` 或 `Application`。
4. `MetadataExecutionKernel` 是否走了 `applications Type=3`。

### 19.3 自动识别应用清单异常

优先检查：

1. `resolvedQuery.groups[0].type` 是否为 `CompositeApplication`。
2. 是否误加了 `argument:"all"`。
3. `NapmMetadataService.filterApplicationsByProvider` 是否按 Type=4 过滤。

### 19.4 指标清单口径异常

优先检查：

1. `service=metrics`
2. `groups[0].type`
3. `objectMetricOwnership.filterMetricsForObjectType`
4. `NapmMetadataService.getMetricsForGroupPath`
5. 是否把 plain `业务` 错映射到 `BusinessGroup`

### 19.5 时间范围异常

优先检查：

1. 根级 `start/end` 是否存在。
2. 是否按 60 秒对齐。
3. `timeRange.start/end` 是否被错误当成执行字段。
4. `resolutionHints.time` 是否记录构造来源。

### 19.6 下钻路径异常

优先检查：

1. 是否使用 `service=drilldownCatalog`。
2. 是否从 `NapmMetadataService.getDrilldownPathsForGroupType` 返回。
3. 是否误把 `children=[]` 的单个节点当作全局结论。
4. 是否混淆“结构可达性”和“运行时可执行性”。

### 19.7 overview 没有结果

优先检查：

1. `overviewScene` 是否正确。
2. `overviewDepth` 对应预算是否太小。
3. `metadataReview.warnings`。
4. `overview.executionMeta.successCount/failedCount/queryCount`。
5. 各 candidate 的 `skippedCandidates` 原因。

### 19.8 远端确认是否走了真实 skill

远端优先看：

```text
~/.openclaw/logs/audit.log
```

如果同一个 `traceId` 或同一个 prompt 能看到：

```text
napm_plugin_skill_executor_invoked
napm_skill_resolved_query_received
napm_skill_execution_completed
napm_plugin_skill_executor_completed
```

则说明请求已经通过插件调用了远端 skill executor。

如果只能看到 OpenClaw 会话日志，看不到 `napm_skill_*`，常见原因是：

1. 插件没有被 OpenClaw 加载。
2. `before_tool_call` 阶段被 `resolvedQuery` 边界拦截。
3. OpenClaw 主链没有构造 `resolvedQuery`。
4. 请求被识别为非 NAPM 范围。
5. executor 路径或远端 `.env` 配置异常。

### 19.9 远端 executor 手工 smoke

只读/低风险验证可以使用 metadata 类查询，例如指标清单：

```text
cd ~/.openclaw
node skills/openclaw-napm-query/scripts/run_napm_query.js --payload '<json payload>'
```

建议 payload 使用：

```json
{
  "traceId": "manual-smoke",
  "prompt": "业务都可以查哪些指标",
  "resolvedQuery": {
    "service": "metrics",
    "queryModeKey": "metadata",
    "groups": [{ "type": "WebApplication" }],
    "format": "json",
    "userRequirement": "业务都可以查哪些指标",
    "semanticConstraints": {
      "operation": "metadata_list",
      "workflowType": "metric_inventory",
      "targetObjectType": "WebApplication"
    }
  }
}
```

成功时应看到：

```text
ok=true
service=metrics
responseMode=machine_narration_input
narrationBy=openclaw
data/rows 有若干指标
error=null
```

这个 smoke 不需要写入数据，不需要修改远端服务，也不会绕过当前 skill 执行链。

## 20. 当前链路的设计重点

当前代码的核心设计取向是“强边界、强契约、弱猜测”：

1. 生产查询必须有 `resolvedQuery`。
2. 自然语言理解放在 OpenClaw 主链，不放在 skill 执行层临场猜。
3. 数据查询、元数据查询、概览分析走不同分支，但最后统一为 OpenClaw narration contract。
4. 对象清单、层级结构、指标兼容性分别有不同 truth source：
   - 对象实例：southbound live API。
   - 层级结构：static/live groups tree。
   - 指标兼容性：`metricsForGroup` live API。
   - 语义策略：本地 spec/ontology/constants。
5. 插件层会主动阻断旧工具、系统工具和手工推理泄露，避免 NAPM 问题绕开 skill。

## 21. 一句话调用图

```text
OpenClaw Gateway 理解问题并构造 resolvedQuery
  -> ~/.openclaw/extensions/napm-openclaw-plugin/index.js 验证并只允许 napm-skill-query
  -> ~/.openclaw/skills/openclaw-napm-query/scripts/run_napm_query.js 执行结构化查询
  -> RequirementParserService 准备和分发
  -> MetadataExecutionKernel / MetricExecutionKernel / OverviewModule
  -> NapmClient 请求 NetInside/NAPM
  -> parseNapmPayload 归一化数据
  -> OpenClawNarrationContractService 生成 narrationInput
  -> OpenClaw 输出中文答案
```
