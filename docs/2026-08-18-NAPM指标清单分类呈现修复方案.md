# NAPM 指标清单分类呈现修复方案

## 1. 问题范围

`1.1.0-rc.8` 修复了业务指标查询被门禁误覆盖、指标代码被模型改写和旧 turn 结果复用的问题。修复后，`业务有哪些指标可以用？` 能稳定返回真实的 26 个 `WebApplication` 指标，但最终答案按 `1...26` 逐项平铺。

用户确认的正确格式是：按运维语义分类、合并同一指标族、保留指标代码和单位，并在末尾给出小结及下一步查询建议。逐行平铺虽然事实正确，但不符合企业微信中的可读性要求。

## 2. 现象与影响

### 2.1 正确格式

- 顶部说明对象类型和真实指标总数。
- 使用“流量/吞吐、连接/TCP、时延/响应、可靠性、体验”等分类标题，或业务对象对应的“业务网络、业务访问、业务性能、响应代码、页面优化”。
- 同一指标族合并为一条，例如“页面访问”同时列出访问数 `PGNPGE` 和访问率 `PGRT`。
- 指标代码、方向、单位均来自本次 Skill rows。
- 末尾包含基于本次返回结果的小结和下一步建议。

### 2.2 错误格式

- 26 个指标按原始返回顺序编号平铺。
- 页面访问、HTTP 状态码、页面优化等相关指标彼此分散。
- 用户需要自行理解英文代码之间的关系，可扫描性和运维可用性明显下降。

### 2.3 影响范围

`buildMetricListDisplayText()` 是 `metric_list` 的统一确定性出口，`message_sending` 和 `before_message_write` 都会使用它。因此问题不只影响业务指标；应用、网络和工作组等指标清单在相同版本下也可能退化为逐行平铺。

## 3. 根因

### 3.1 rc.8 的安全修复缺少独立呈现层

为防止模型把 `PGRT` 改写成 `PGNPGE`，rc.8 将最终指标清单改为由 Skill rows 确定性直出。该方向正确，但 `buildMetricListDisplayText()` 只实现了“对象标题 + 逐行编号”，没有实现分类和指标族合并。

### 3.2 查询归属事实没有进入最终呈现

项目已经在以下位置维护指标分类事实：

- `src/constants/objectMetricOwnership.js`
- `src/constants/metricDomains.js`
- `references/metric-category-mapping.md`

现有叙述契约只把这些分类用于约束说明，没有用它们构造最终 `displayText`。

### 3.3 不能把问题重新交给模型自由改写

恢复模型自由整理会重新引入指标代码、单位和对象范围被改写的风险。正确修复不是放开最终 Hook，而是在真实 Skill rows 与最终文本之间增加确定性的指标清单呈现层。

## 4. 解决方案

### 4.1 新增统一呈现服务

新增：

```text
skills/openclaw-napm-query/services/MetricInventoryPresentationService.js
```

服务输入本轮真实 Skill rows 和对象类型，输出结构化呈现模型：

```js
{
  objectType: 'WebApplication',
  objectLabel: '业务',
  metricCount: 26,
  sections: [
    { title: '业务网络', items: [] },
    { title: '业务访问', items: [] },
    { title: '业务性能', items: [] },
    { title: '响应代码', items: [] },
    { title: '页面优化', items: [] }
  ],
  displayText: '...'
}
```

`OpenClawNarrationContractService.buildMetricListDisplayText()` 保留为兼容入口，但内部委托给新服务。插件两个最终 Hook 继续使用同一入口，不分别维护格式化逻辑。

### 4.2 分类必须基于项目既有事实

- 使用 `getMetricCategoriesForObjectType()` 确定对象的指标分类范围。
- 使用 `getMetricCategoriesForMetric()` 确定每个真实 metric ID 的分类。
- 指标族只负责呈现合并和角色名称，不改变指标归属。
- `WebApplication` 的 26 项按“业务网络、业务访问、业务性能、响应代码、页面优化”呈现。
- 非业务对象按“流量/吞吐、连接/TCP、时延/响应、可靠性、体验”呈现。

### 4.3 真实 rows 是唯一事实源

- 只展示本轮 rows 实际返回的指标。
- 指标代码和单位来自 rows，不从示例或模型补齐。
- 已知指标的中文分类、指标族和成员角色来自版本化呈现映射；未知指标的名称直接采用 rows 中的 label。
- 同一 metric ID 在最终文本中只出现一次。
- 不得为了凑齐指标族而补入未返回的指标。
- 无法识别的新指标进入“其他指标”，不能丢弃或猜测归属。

### 4.4 确定性合并同一指标族

示例：

```text
业务（WebApplication）共返回 26 个指标，按类别整理如下：

业务访问
• 页面访问（访问数 PGNPGE，pages；访问率 PGRT，pages/min）

响应代码
• HTTP 响应数（PGNOBJE，objects）
• HTTP 状态码数量（100 PGHTTP100 / 200 PGHTTP200 / ...，objects）
• HTTP 状态码占比（100 PGHTTP100PCT / 200 PGHTTP200PCT / ...，%）
```

单位相同的成员合并到条目末尾；单位不同时分别跟随各自成员，避免错误合并。

### 4.5 输出边界保持不变

- 不修改自然语言路由、`resolvedQuery`、南向查询或当前 turn 证据门禁。
- 不恢复模型对指标清单代码和单位的自由改写权。
- `message_sending` 与 `before_message_write` 继续确定性直出同一份分类文本。
- 没有本轮成功 Skill 结果时，仍不得复用历史指标数据。

## 5. 验收标准

1. `业务有哪些指标可以用？` 的 26 个真实指标形成五个业务分类，不再出现 `1...26` 平铺。
2. `BusinessGroup` 的 68 个真实指标形成五个运维分类，保持用户确认的图一风格。
3. 每个本轮返回的 metric ID 在最终文本中恰好出现一次。
4. 最终文本不包含任何未返回 metric ID。
5. 未知 metric ID 进入“其他指标”，名称、代码和单位保持原值。
6. `PGRT` 仍表示页面访问率，不得被写成 `PGNPGE`。
7. `message_sending` 和 `before_message_write` 输出一致。
8. 原有业务对象清单门禁、当前 turn 证据门禁及应用/网络/工作组查询不回归。

## 6. 验证与发布边界

修改完成后依次执行：

- 指标呈现服务专项测试。
- OpenClaw narration contract 与插件双 Hook 回归。
- 全量 Jest、lint、Node 语法、运行时契约和 `git diff --check`。

测试服务器部署必须得到明确指令，并继续使用统一发布包、隔离验证、dry-run 和正式安装流程，不能逐文件覆盖远端。
