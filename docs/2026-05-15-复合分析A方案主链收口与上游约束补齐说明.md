# 2026-05-15 复合分析 A 方案主链收口与上游约束补齐说明

最后更新：2026-05-15

## 1. 背景

前面已经确认本项目里“综合分析 / 深度分析”这类问法，不应该直接压成单条 `averageValues`、`timeValues` 或随意拼接的临时查询。

这类问题的正确链路应为：

```text
先找到一个对象
  -> 锁定该对象
  -> 对该对象做 focused overview
  -> 输出中文综合结论
```

本次改造继续坚持两条原则：

1. 不修改企业微信插件业务逻辑，插件只承担传递与回包职责。
2. 改造集中在 `openclaw-napm-query` skill 主链，让 OpenClaw 上游和 skill 运行时都沿着同一条链路工作。

## 2. 最终方案

本次采用 A 方案落地：

1. 外层仍然使用现有 `service=overview`。
2. 在 `resolvedQuery.analysisPipeline.discoveryQuery` 中放“对象发现”步骤。
3. 运行时先执行 discovery。
4. 从 discovery 结果中提取 `selectedObject`。
5. 把请求改写为 focused `overview`。
6. 将 discovery 信息挂回 overview / narration contract，供最终中文回答使用。

这意味着项目中的复合分析主链正式收敛为：

```json
{
  "service": "overview",
  "analysisPipeline": {
    "discoveryQuery": {
      "service": "topValues"
    }
  }
}
```

而不是：

- 直接把“先找谁再分析它”压成一条 `averageValues`
- 直接把“综合分析”理解成单次 `timeValues`
- 在企业微信插件中继续堆业务特例

## 3. 本次改动范围

### 3.1 运行时改动

核心运行时改动位于：

- `skills/openclaw-napm-query/scripts/run_napm_query.js`
- `skills/openclaw-napm-query/scripts/OverviewCandidateRegistry.js`
- `skills/openclaw-napm-query/scripts/OverviewPlanner.js`
- `skills/openclaw-napm-query/scripts/overview-module.js`
- `skills/openclaw-napm-query/scripts/OverviewResultReducer.js`
- `skills/openclaw-napm-query/services/OpenClawNarrationContractService.js`

主要能力补齐如下：

1. `overview` 查询支持内置 `analysisPipeline.discoveryQuery`。
2. discovery 结果可提取为 `selectedObject`。
3. 当对象被锁定后，overview 规划器优先选取与该对象相关的 focused 模块。
4. narration contract 中可带出 discovery 信息，便于最终回答说明“先找到了谁，再分析了谁”。

### 3.2 上游约束补齐

为了避免这条链路只存在于运行时代码里，本次同时补齐了上游提示与参考规则：

- `skills/openclaw-napm-query/agents/openai.yaml`
- `skills/openclaw-napm-query/references/service-modes.md`
- `skills/openclaw-napm-query/SKILL.md`

补齐后的约束重点为：

1. “先找最...的对象，再分析它”不是单步 `averageValues / timeValues`。
2. 这类问题应构造成 `overview + analysisPipeline.discoveryQuery`。
3. discovery metric 必须和选择语义一致。
4. 对象已明确时，不再做 discovery，直接 focused `overview`。
5. discovery 与 focused overview 默认共用同一时间范围。

## 4. 为什么这次没有改企业微信插件

这是本次改造中非常明确的边界。

原因如下：

1. 企业微信插件不应该继续承担业务理解职责。
2. 如果把“先找对象再分析”的逻辑继续堆到插件里，后续每种问法都要在插件重复补特例，复杂度会继续上升。
3. 本项目当前正确的职责分层应为：

```text
企业微信插件
  -> 传输、回包、保护

OpenClaw
  -> 语义理解、resolvedQuery 生成

openclaw-napm-query skill
  -> 校验、执行、overview 编排、narration contract
```

因此本次坚持只改 skill 主链与上游约束，不再把业务判断塞回插件。

## 5. 验证结果

本次进行了轻量回归验证，结果全部通过：

1. `npx jest test/run-napm-query-input-contract.test.js --runInBand`
2. `npx jest test/overview-module.test.js --runInBand`
3. `npx jest test/openclaw-narration-contract.test.js --runInBand`

验证覆盖的重点包括：

1. 复合分析 resolvedQuery 形态仍然正确。
2. 运行时会先执行 discovery，再转 focused overview。
3. focused IP 分析模块会被优先选中。
4. narration contract 会带上 discovery 信息。

## 6. 本次结论

本次改造后，项目中“先找到一个对象，然后对这个对象进行综合分析”已经收口为统一主链：

```text
discover object
  -> lock object
  -> focused overview
  -> Chinese narration
```

而且这条链路已经同时体现在：

1. 运行时代码
2. 上游 prompt 约束
3. 参考文档
4. 测试用例

这比只在本地代码里偷偷兼容更稳，也更符合当前项目“OpenClaw 负责理解，skill 负责执行”的整体方向。
