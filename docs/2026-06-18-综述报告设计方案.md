# 综述报告（summary_report）设计方案

日期：2026-06-18

## 1. 背景

NAPM 报告系统目前已注册 6 种报告类型，其中 `inspection_report`（巡检报告）拥有完整的固定模板驱动渲染链路（模板 JSON → 数据绑定 → ECharts 图表 → 叙述规则 → docx），其余类型走通用渲染路径。

`summary_report`（综述报告）已在三个层面完成注册：

- `ReportGenerationService.SUPPORTED_REPORT_TYPES` 包含 `summary_report`
- `ReportStorageService.REPORT_TYPE_CN` 包含 `summary_report: '综述报告'`
- 文件命名规则中已引用综述报告

但以下能力缺失：

- 无专用报告模板 JSON
- 无数据聚合编排技能
- `ReportTemplateService.renderDocx()` 无 `summary_report` 分发路由
- `ReportInputContractService` 无 `buildSummaryReportData()`

本文档给出综述报告的完整设计方案，作为后续实现的依据。

## 2. 两层综述模型

"综述"在 NAPM 语境下有两种粒度，本设计将两者统一在一套模板+数据契约中：

### 2.1 全局综述（Global Summary）

对**整个流量分析系统**做跨维度总览。回答的问题是："过去一段时间，系统整体状况怎么样？"

- 覆盖所有告警类别
- 覆盖 TotalTraffic 全局流量趋势
- Top N 排名（Top IP、Top 应用、Top 慢访问业务）
- 目标读者：管理决策层、运维负责人

### 2.2 分类综述（Scoped Summary）

聚焦到**某一个具体对象**做深度综述。回答的问题是："过去一段时间，`239web` 这个应用的整体状况怎么样？"

按 NAPM 维度体系，支持以下分类综述：

| scope.type | 中文名 | 聚焦对象 | 典型问题 |
|------------|--------|---------|---------|
| `global` | 全局综述 | 整个系统 | 系统整体运行状况如何？ |
| `network` | 网络综述 | 网络层（IP/IP会话/接口） | 网络流量和丢包情况如何？ |
| `webApplication` | 业务综述 | 指定 Web 应用 | 某个 Web 应用的流量、慢访问、错误状况？ |
| `application` | 应用综述 | 指定应用（端口/协议级） | 某个应用的流量和连接状况？ |
| `businessGroup` | 业务组综述 | 指定业务组 | 某个业务组的整体状况？ |
| `alert` | 告警综述 | 告警数据（可限定类别/对象） | 告警态势和趋势如何？ |

### 2.3 全局 vs 分类：核心区别

| 维度 | 全局综述 | 分类综述 |
|------|---------|---------|
| 流量趋势 | TotalTraffic（总流量） | `groupType=指定类型, groupArgument=指定对象` |
| 排行 | Top N 各对象 | Top N 下级维度（如应用到 IP） |
| 告警 | 全类别、全对象 | 按 groupType + group 过滤 |
| 业务性能 | 所有 WebApplication | 仅指定对象 |
| 覆盖指标 | TPIO/TPI/TPO（核心） | 核心 + 质量指标（PLI/PLO/PGTME）+ 错误指标 |
| 模板章节 | 全部 5 章 | 部分章节（按 scope 开关） |
| 报告标题 | `{系统名}_全局综述报告` | `{对象名}_{分类名}综述报告` |

## 3. 综述范围系统（Scope System）

### 3.1 scope 数据模型

```json
{
  "scope": {
    "type": "global | network | webApplication | application | businessGroup | alert",
    "label": "全局 | 网络 | 业务 | 应用 | 业务组 | 告警",
    "target": {
      "groupType": "WebApplication",
      "groupArgument": "239web",
      "groupLabel": "239web"
    }
  }
}
```

- `scope.type = "global"` 时，`target` 为 `null`
- `scope.type != "global"` 时，`target` 必填，指定聚焦的对象

### 3.2 scope.type 与 NAPM groupType 的映射

NAPM 的数据查询以 `groupType` + `groupArgument` 定位对象：

```
网络综述 (network)
  ├── TotalTraffic     → 全局流量趋势
  ├── IPAddress        → 指定 IP 的流量/丢包/延迟
  ├── IPConversation   → 指定 IP 会话
  └── Interface        → 指定网络接口

业务综述 (webApplication)
  └── WebApplication   → 指定 Web 应用的流量/慢访问/HTTP错误

应用综述 (application)
  └── Application      → 指定应用的流量/连接

业务组综述 (businessGroup)
  └── BusinessGroup    → 指定业务组的流量

告警综述 (alert)
  └── 不限 groupType   → 可限定告警类别和对象，也可不限
```

### 3.3 分类综述的指标集

分类综述比全局综述多出**质量指标**和**错误指标**，因为聚焦到单个对象后，这些细节指标才有意义：

| 指标类别 | 指标短码 | 含义 | 单位 | 适用于 |
|----------|---------|------|------|--------|
| 流量 | TPIO | 总吞吐量 | bps | 全部 |
| 流量 | TPI | 流入吞吐量 | bps | 全部 |
| 流量 | TPO | 流出吞吐量 | bps | 全部 |
| 质量 | PLI | 丢包率(入) | % | network/webApplication/application |
| 质量 | PLO | 丢包率(出) | % | network/webApplication/application |
| 质量 | PGTME | 页面平均时延 | ms | webApplication |
| 质量 | PGSLPCT | 慢访问占比 | % | webApplication |
| 质量 | PGNSLPGE | 慢访问页面数 | 个 | webApplication |
| 错误 | PGHTTP400 | HTTP 400 错误数 | 个 | webApplication |
| 错误 | PGHTTP500 | HTTP 500 错误数 | 个 | webApplication |

### 3.4 scope 如何驱动模板章节

同一份模板 JSON，通过 `scope.type` 控制章节显隐：

```
章节                         global  network  webApp  app  bizGrp  alert
─────────────────────────────────────────────────────────────────────
封面                          ✓       ✓       ✓      ✓     ✓      ✓
目录                          ✓       ✓       ✓      ✓     ✓      ✓
1. 报告概述                    ✓       ✓       ✓      ✓     ✓      ✓
  1.1 设备信息                 ✓       ✓       ✓      ✓     ✓      ✓
  1.2 综合健康评估             ✓       ✓       ✓      ✓     ✓      ✓
2. 告警态势                    ✓       ✓       ✓      ✓     ✓      ✓ (核心章)
  2.1 告警概览（按类别）        ✓       ✓       ✓      ✓     ✓      ✓
  2.2 告警趋势图               ✓       ✓       ✓      ✓     ✓      ✓
  2.3 Top 告警对象             ✓       -       -      -     -      -
  2.4 未恢复告警               ✓       ✓       ✓      ✓     ✓      ✓
3. 流量总览                    ✓       ✓       ✓      ✓     ✓      -
  3.1 流量趋势图               ✓       ✓       ✓      ✓     ✓      -
  3.2 流量质量指标             -       ✓       ✓      ✓     ✓      -
  3.3 Top 流量对象             ✓       -       -      -     -      -
  3.4 下级维度分布（钻取）      -       ✓       ✓      ✓     ✓      -
4. 业务性能                    ✓       -       ✓      -     -      -
  4.1 慢访问趋势/Top          ✓       -       ✓      -     -      -
  4.2 HTTP 错误趋势/Top       ✓       -       ✓      -     -      -
5. 结论与建议                   ✓       ✓       ✓      ✓     ✓      ✓
```

> `-` = 该 scope 下不适用/不渲染。`✓ (核心章)` = 对该 scope 是最重要的章节。

## 4. 数据查询计划（按 scope）

### 4.1 全局综述（global）

来源：`openclaw-napm-alert-query` + `openclaw-napm-query`

| # | API | 关键参数 | 用途 | 模板章节 |
|---|-----|---------|------|---------|
| G1 | `alertsSummary` | start/end | 全类别告警统计 + Top告警对象 | 2.1 / 2.3 |
| G2 | `alertsSummaryTimeLine` | start/end | 全类别告警趋势时序 | 2.2 |
| G3 | `alertsDetail` | eventids（未恢复告警） | 未恢复告警详情 | 2.4 |
| G4 | `timeValues` | groups=TotalTraffic, metrics=TPIO,TPI,TPO | 全局流量趋势 | 3.1 |
| G5 | `topValues` | groups=IPAddress, topMetric=TPIO, topCount=10 | Top 10 流量 IP | 3.3 |
| G6 | `topValues` | groups=WebApplication, topMetric=TPIO, topCount=10 | Top 10 流量应用 | 3.3 |
| G7 | `topValues` | groups=WebApplication, metrics=PGSLPCT,PGNSLPGE,PGTME, topMetric=PGSLPCT, topCount=10 | 慢访问 Top | 4.1 |
| G8 | `topValues` | groups=WebApplication, metrics=PGHTTP400,PGHTTP500, topMetric=PGHTTP500, topCount=10 | HTTP 错误 Top | 4.2 |
| G9 | `applianceInfo` | — | 设备基本信息（可选） | 1.1 |

**查询次数：8~9 次**（可并行执行 6 路：G1+G2+G4+G5+G6+G7+G8 同时发出，G3 和 G9 可选）

### 4.2 网络综述（network）

聚焦对象：`TotalTraffic` 或 `IPAddress={ip}` 或 `Interface={name}`

| # | API | 关键参数 | 用途 |
|---|-----|---------|------|
| N1 | `alertsSummary` | start/end，之后按 groupType 过滤 | 该网络对象的告警 |
| N2 | `alertsSummaryTimeLine` | start/end | 告警趋势 |
| N3 | `timeValues` | groups=TotalTraffic (或指定 IPAddress/Interface), metrics=TPIO,TPI,TPO,PLI,PLO | 流量+丢包趋势 |
| N4 | `topValues` | groups=IPAddress (或 IPConversation), topMetric=TPIO, topCount=10 | 下级维度排行 |
| N5 | `applianceInfo` | — | 设备信息 |

**查询次数：4~5 次**

### 4.3 业务综述（webApplication）

聚焦对象：`WebApplication={name}`（如 `239web`）

| # | API | 关键参数 | 用途 |
|---|-----|---------|------|
| W1 | `alertsSummary` | start/end，按 groupType=WebApplication, group=指定name 过滤 | 该业务的告警 |
| W2 | `alertsSummaryTimeLine` | start/end | 告警趋势 |
| W3 | `timeValues` | groups=WebApplication, groupArgument=指定name, metrics=TPIO,TPI,TPO,PGSLPCT,PGTME,PGHTTP400,PGHTTP500 | 该业务的全部指标趋势 |
| W4 | `topValues` | groups=WebApplication→ClientIPs→IPAddress (或 PageFamily), topMetric=TPIO, topCount=10 | 钻取：哪些 IP/页面 在访问该业务 |
| W5 | `topValues` | groups=WebApplication, groupArgument=指定name, metrics=PGSLPCT,PGTME, topMetric=PGSLPCT, topCount=10 | 慢访问详情 |
| W6 | `topValues` | groups=WebApplication, groupArgument=指定name, metrics=PGHTTP400,PGHTTP500, topMetric=PGHTTP500, topCount=10 | HTTP 错误详情 |

**查询次数：5~6 次**（注意：W3 将多个指标合并在一次 timeValues 调用中，不同于全局综述需要分别查 Top N）

### 4.4 应用综述（application）

聚焦对象：`Application={name}`

| # | API | 关键参数 | 用途 |
|---|-----|---------|------|
| A1 | `alertsSummary` | 按 groupType=Application, group=指定name 过滤 | 该应用的告警 |
| A2 | `timeValues` | groups=Application, groupArgument=指定name, metrics=TPIO,TPI,TPO,PLI,PLO | 流量+丢包趋势 |
| A3 | `topValues` | groups=Application→IPAddress, topMetric=TPIO, topCount=10 | 钻取：Top 访问 IP |

**查询次数：3 次**

### 4.5 业务组综述（businessGroup）

聚焦对象：`BusinessGroup={name}`

| # | API | 关键参数 | 用途 |
|---|-----|---------|------|
| B1 | `alertsSummary` | 按 groupType=BusinessGroup, group=指定name 过滤 | 该业务组的告警 |
| B2 | `timeValues` | groups=BusinessGroup, groupArgument=指定name, metrics=TPIO,TPI,TPO | 流量趋势 |
| B3 | `topValues` | groups=BusinessGroup→WebApplication (或 IPAddress), topMetric=TPIO, topCount=10 | 钻取：下级对象排行 |

**查询次数：3 次**

### 4.6 告警综述（alert）

聚焦对象：可限定告警类别（如仅 `networkAlerts`）或告警对象，也可不限（退化为全局综述的告警章节）

| # | API | 关键参数 | 用途 |
|---|-----|---------|------|
| L1 | `alertsSummary` | start/end，可选 filter | 告警统计 |
| L2 | `alertsSummaryTimeLine` | start/end | 告警趋势 |
| L3 | `alertsDetail` | eventids | 关键告警详情 |

**查询次数：2~3 次**

### 5.2 overallStatus 计算规则

```text
if alertSummary.critical > 0  →  "critical"
else if alertSummary.major > 0  →  "warning"
else if trafficSummary.trend.stats.missingPointCount > 0  →  "warning"
else if trafficSummary.trend.stats.spikeCount > 0  →  "warning"
else if businessSummary.slowAccess.length > 0  →  "warning"
else  →  "ok"
```

## 6. 模板设计

### 6.1 设计策略

**一份模板覆盖全部 scope。** 每个 section 增加 `scopes` 字段声明它在哪些 scope 下渲染。模板渲染引擎根据 `reportData.scope.type` 决定是否跳过某个 section。

```json
{
  "id": "traffic_top_objects",
  "type": "table",
  "scopes": ["global"],
  "rowBuilder": "trafficTopObjects",
  ...
}
```

- `scopes: ["global"]` → 仅在全局综述中渲染
- `scopes: ["webApplication", "application", "businessGroup"]` → 在多个分类综述中渲染
- `scopes` 字段省略 → 全部 scope 都渲染

### 6.2 模板元信息

```json
{
  "schema": "openclaw_napm_summary_template.v1",
  "templateId": "napm_summary_overview_v1",
  "version": "1.0.0",
  "titlePath": "title",
  "description": "NAPM 综述报告统一模板。通过 scope 字段驱动章节显隐，一套模板覆盖全局综述、网络综述、业务综述、应用综述、业务组综述和告警综述。",
  "page": {
    "margin": { "top": 1000, "right": 900, "bottom": 1000, "left": 900, "header": 450, "footer": 450 },
    "header": {
      "leftImage": { "path": "templates/inspection/company-logo.png", "width": 110, "height": 32 },
      "left": "网深科技流量分析系统",
      "right": "{{summary.customerName}}{{summary.projectName}}{{scope.label}}报告"
    },
    "footer": {
      "center": "第 {{pageNumber}} 页 / 共 {{totalPages}} 页",
      "right": "{{summary.reportDate}}"
    }
  }
}
```

页眉中的 `{{scope.label}}` 会自动渲染为"全局"/"网络"/"业务"/"应用"/"业务组"/"告警"。

### 6.3 完整章节定义（含 scope 控制）

```
封面（全部 scope）
  cover                          → type: cover, scopes: ["*"]
  cover_date                     → type: paragraphs, "{{summary.reportDate}}"
  cover_break                    → type: pageBreak

目录（全部 scope）

  6. 修改 ReportTemplateService 增加 summary_report 分发路由

Phase 3: 数据聚合
  7. 新建 openclaw-napm-summary 技能
  8. 实现 scope 路由：根据 scope.type 选择对应的查询计划
  9. 实现多源并行查询 + 数据聚合逻辑
  10. 输出标准 reportData（含 scope 字段）给 openclaw-napm-report

  12. 再扩展 network / application / businessGroup / alert
  13. 单元测试 + 端到端测试
```

### 10.4 建议的分批交付策略

| 批次 | scope | 理由 |
|------|-------|------|
| **第一批** | `global` + `webApplication` | 全局综述覆盖最广，业务综述是最典型的分类综述 |
| **第二批** | `alert` | 告警综述相对独立，章节最少，实现最快 |
| **第三批** | `network` + `application` + `businessGroup` | 与 webApplication 模式相同，参数化即可 |

## 11. 复用分析

`SummaryFixedTemplateService` 与 `InspectionFixedTemplateService` 的关系：

| 能力 | 复用方式 | 说明 |
|------|---------|------|
| 模板加载 | **直接复用** | 读取 JSON，逻辑一致 |
| scopes 过滤 | **新增** | 按 `scope.type` 过滤 sections/charts/narratives |
| 图表渲染 | **直接复用** | ECharts SSR 管线 |
| docx 构建 | **直接复用结构** | 页面设置、页眉页脚、封面、目录、heading、表格、图表嵌入 |
| 叙述渲染 | **直接复用** | 评估 when 条件 + 文本插值，新增 scopes 过滤 |
| rowBuilder | **部分新增** | `deviceInfo`/`alertCategoryStats`/`unresolvedAlerts` 等需新增；`trafficTopObjects` 可复用巡检的通用表格逻辑 |

建议：`SummaryFixedTemplateService` 继承 `InspectionFixedTemplateService`，覆盖以下方法：

- `filterSectionsByScope(template, scope)` — 新增，按 scopes 过滤
- `buildRowsForSection(section, context)` — 覆盖，增加新的 rowBuilder case
- `renderSection(section, context)` — 覆盖，增加 scope 条件渲染
