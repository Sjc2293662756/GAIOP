# 2026-05-06 多层路径钻取补强说明

## 一、背景

当前项目已切到 Skill 直连查询链路，不再依赖旧网关做请求收敛。

在这一模式下，NAPM 本身支持多层 group path 查询，例如：

- `WebApplication -> ClientIPs -> IPAddress`
- `BusinessGroup -> MemberIPs -> IPAddress`
- `BusinessGroup -> Applications -> DefinedApp`

但此前执行入口 `skills/openclaw-napm-query/scripts/run_napm_query.js` 主要依赖上游直接传入完整 `resolvedQuery`，对“上一轮结果继续下钻”的承接不够，导致下面两类问题容易出现：

1. 上一轮查到了对象范围，但下一轮追问时 scope 没有继承下来
2. 用户明确说“继续下钻 / 看明细”，系统也没有稳定补出下一层 group path

## 二、本次修改

本次在 `skills/openclaw-napm-query/scripts/run_napm_query.js` 中补入了多层路径钻取的最小可用增强，重点包括：

### 1. 接入 session 继承能力

新增：

- `normalizeSessionState`
- `hasUsableSessionContext`
- `applySessionContinuationToResolvedQuery`

作用：

- 从 session 中读取 `last_groups / last_metric / last_time_range`
- 当当前轮 `resolvedQuery` 缺少这些信息时，自动继承上一轮结果上下文

这样追问时不会轻易把上层范围丢掉。

### 2. 增加“下钻型问法”识别

新增：

- `isDrilldownPrompt`

当前识别的典型词包括：

- 继续
- 接着
- 往下
- 下钻
- 深入
- 明细
- 详情
- 展开
- 下一层
- 具体看

只有在明确出现这类问法时，才会尝试把路径往下一层补，避免普通追问被误下钻。

### 3. 增加常见路径的默认补深规则

新增：

- `inferDrilldownPathFromPrompt`

当前已补强的常见路径如下：

#### WebApplication

- 默认下钻：`WebApplication -> ClientIPs -> IPAddress`
- 显式说“客户端”：`WebApplication -> ClientIPs -> IPAddress`
- 显式说“服务端/服务器”：`WebApplication -> ServerIPs -> IPAddress`
- 显式说“页面”：`WebApplication -> PageFamily`

#### BusinessGroup

- 默认下钻：`BusinessGroup -> MemberIPs -> IPAddress`
- 显式说“成员IP/成员”：`BusinessGroup -> MemberIPs -> IPAddress`
- 显式说“连接IP/对端IP”：`BusinessGroup -> ConnectedIPs -> IPAddress`
- 显式说“应用”：`BusinessGroup -> Applications -> DefinedApp`
- 显式说“会话”：`BusinessGroup -> IPConversations -> IPConversation`

#### Prefix24

- 默认下钻：`Prefix24 -> MemberIPs -> IPAddress`
- 也支持按“连接IP / 应用 / 会话”走对应路径

#### IPAddress

- 默认下钻：`IPAddress -> ConnectedIPs -> ConnectedIP`
- 显式说“应用”：`IPAddress -> Applications -> DefinedApp`

### 4. 保持“显式当前查询优先”

如果当前轮 `resolvedQuery` 已经明确给出了 `groups`，则：

- 普通追问：保留当前 `groups`
- 明确下钻问法：在当前 `groups` 基础上补下一层

不会被 session 里的老范围粗暴覆盖。

## 三、当前效果

以 session 中上一轮对象为：

```json
[
  { "type": "WebApplication", "argument": "回溯238web" }
]
```

若当前轮用户说：

- `继续下钻`
- `看明细`

则当前执行侧会自动补成：

```json
[
  { "type": "WebApplication", "argument": "回溯238web" },
  { "type": "ClientIPs", "argument": null },
  { "type": "IPAddress", "argument": null }
]
```

并同时继承上一轮：

- `last_metric`
- `last_time_range`

## 四、验证情况

新增测试文件：

- `test/run-napm-query-drilldown-continuation.test.js`

已验证：

1. 能识别下钻型问法
2. 能从 `WebApplication` 默认补到 `ClientIPs -> IPAddress`
3. 能从 `BusinessGroup` 显式补到 `Applications -> DefinedApp`
4. 能从 session 继承 `groups / metric / time`
5. 非下钻问法不会错误改写当前显式 `groups`

同时通过：

- `test/run-napm-query-meta-followup.test.js`

## 五、当前边界

本次补强后，项目已经具备“常见连续追问可稳定下钻”的能力，但仍不是完整自由规划引擎。

当前仍需注意：

1. 主要支持常见对象链路，不是所有 group path 都已穷举
2. 更复杂的自然语言下钻，仍可能需要继续补规则
3. 仓库内目前仍没有独立的 `PathResolveService.js` 实现，说明完整路径解析器尚未单独成型

## 六、结论

本次修改后，“多层路径钻取”已经从“底层能查，但连续追问不稳”，提升到“常见连续追问可以稳定继承并继续下钻”。

这一步主要解决的是执行链末端的问题：即便上游没有把完整路径一次性传好，Skill 也能结合 session 把最近一次作用域接回来，再补成可执行的多层 `groups` 路径。
