# 项目钻取实现总结

## 1. 文档目的

本文档用于总结当前 NAPM Semantic Gateway 项目中“钻取（drilldown）”相关能力的实现方式，说明系统如何：

- 描述可钻取的对象层级结构
- 根据用户自然语言推断钻取路径
- 在多轮对话中继承上文 scope 继续下钻
- 在上游 NAPM 接口不稳定时执行兼容性降级

本文档聚焦“实现机制”，不聚焦某一次线上问题排查过程。

---

## 2. 钻取能力的总体定义

在本项目里，“钻取”不是单一动作，而是一个组合能力，包含以下 4 个环节：

1. 结构定义  
   先定义“哪些对象可以往下钻，以及能钻到什么对象”。

2. 路径规划  
   根据当前对象和用户问法，把不完整的目标补成完整的 group path。

3. 查询组装  
   将 group path、指标、时间范围、上下文组装成最终的 gateway request。

4. 执行与续钻  
   真正执行 NAPM 查询，并在多轮对话里继承上一轮的结果上下文继续钻取。

因此，项目里的钻取实现不是“写死某几个 API 路径”，而是“静态结构 + 动态规划 + 上下文续接 + 执行降级”的组合体系。

---

## 3. 总体架构

当前钻取相关实现主要分布在以下几个模块：

- `config/groups-tree.static.json`
  - 静态 group 树定义
- `skills/openclaw-napm-query/services/NapmMetadataService.js`
  - 读取 group 树、枚举可钻取路径、输出目录型元数据
- `skills/openclaw-napm-query/services/GroupPathPlannerService.js`
  - 基于当前 group 和 prompt 自动规划钻取路径
- `skills/openclaw-napm-query/services/RequirementParserService.js`
  - 将规划结果并入 gateway request，并处理多层路径 fallback
- `skills/openclaw-napm-query/scripts/run_napm_query.js`
  - 在最终执行前根据 session 做多轮续钻、补 metric/time/groups

这几个模块的职责边界如下：

- `NapmMetadataService`
  负责“结构知道什么”
- `GroupPathPlannerService`
  负责“应该往哪条路径钻”
- `RequirementParserService`
  负责“最终请求怎么拼”
- `run_napm_query.js`
  负责“多轮情况下怎么继承上一次上下文”

## 4. 静态结构层：group 树如何描述钻取关系

### 4.1 静态来源

当前项目将 group 树存储在：

- `config/groups-tree.static.json`

该文件描述了各类顶层和中间层对象之间的父子结构。例如：

- `BusinessGroup`
  - `MemberIPs`
    - `IPAddress`
  - `Applications`
    - `DefinedApp`
  - `ConnectedIPs`
    - `IPAddress`
  - `IPConversations`
    - `IPConversation`

这类结构并不直接等于“最终 query 参数”，但它决定了系统允许的钻取方向。

### 4.2 结构读取与标准化

`NapmMetadataService` 会优先加载本地静态 group 树，并将其标准化。

关键实现：

- `getGroupsTree()`
- `getTopLevelGroups()`

文件位置：

- `skills/openclaw-napm-query/services/NapmMetadataService.js`

### 4.3 如何列出某个对象的下钻路径

当用户询问：

- “业务组都有哪些下钻路径？”
- “IP地址支持哪些下钻路径？”

系统会调用：

- `getDrilldownPathsForGroupType(groupType, options)`

它的工作流程是：

1. 在 group 树中找到目标节点
2. 从目标节点递归向下枚举所有 path
3. 输出：
   - 直接子方向 `directChildren`
   - 全量路径 `paths`
   - 路径深度、终点对象类型、是否可查询等信息

相关实现：

- `getDrilldownPathsForGroupType(...)`
- `getTopLevelDrilldownCatalog(...)`
- `buildDirectDrilldownOptions(...)`
- `collectDrilldownPathRecords(...)`

文件位置：

- `skills/openclaw-napm-query/services/NapmMetadataService.js`

### 4.4 这一层解决的问题

这一层解决的是：

- 系统“知道”结构上有哪些可走路径
- 可以回答目录型问题
- 可以为后续路径规划提供候选路径集合

它不负责：

- 猜用户意图
- 补齐时间范围和指标
- 多轮对话中的续钻继承

## 5. 路径规划层：如何从自然语言补全钻取路径

### 5.1 规划目标

用户通常不会直接给完整路径，而是只说：

- “看这个业务组下面的应用”
- “继续看成员 IP”
- “看连接 IP”
- “看会话”

系统需要把这些自然语言补全成真正的 group path。

例如：

- `BusinessGroup(服务器网段) + 看应用`
  ->
  `BusinessGroup(服务器网段) -> Applications -> DefinedApp`

### 5.2 关键词概念识别

`GroupPathPlannerService` 内置了一组 prompt concept：

- `application`
- `member_ip`
- `connected_ip`
- `connected_group`
- `conversation`
- `page_family`
- `user`

每个 concept 都有：

- 匹配词
- 倾向的 container
- 倾向的 terminal

例如：

- “应用 / application / 协议”
  倾向于：
  - `Applications`
  - `DefinedApp`

文件位置：

- `skills/openclaw-napm-query/services/GroupPathPlannerService.js`

### 5.3 默认分支定义

除了 prompt concept 之外，系统还给每个顶层对象定义了默认下钻分支。

例如：

- `BusinessGroup`
  - `MemberIPs -> IPAddress`
  - `Applications -> DefinedApp`
  - `ConnectedIPs -> IPAddress`
  - `IPConversations -> IPConversation`

- `IPAddress`
  - `ConnectedIPs -> ConnectedIP`
  - `Applications -> DefinedApp`
  - `ConnectedGroups -> BusinessGroup`

这部分定义在：

- `DEFAULT_BRANCHES`

文件位置：

- `skills/openclaw-napm-query/services/GroupPathPlannerService.js`

### 5.4 路径评分与选择

核心方法：

- `planPath(query, prompt, options)`

其处理流程是：

1. 取当前已有的 `groups`
2. 找出 anchor type
3. 从静态结构中收集候选路径
4. 根据 prompt concept、target type、是否为 drilldown 问法进行评分
5. 选择分数最高的路径
6. 输出 `plannedGroups`

同时还会给出：

- `strategy`
- `confidence`
- `followUpAction`
- `pathPlanning`

这样后续模块就不需要重新猜路径。

关键实现：

- `planPath(...)`
- `scoreCandidate(...)`
- `buildPlannedGroups(...)`

文件位置：

- `skills/openclaw-napm-query/services/GroupPathPlannerService.js`

### 5.5 这一层解决的问题

这一层解决的是：

- “用户没把路径说完整”的问题
- “需要把一个模糊的下钻目标补成完整 group path”的问题

它不负责：

- 查询执行
- 多轮 session 继承
- 上游 API 不稳定时的 fallback

## 6. 查询组装层：如何把钻取路径变成最终请求

### 6.1 组装入口

`RequirementParserService` 是 group path 真正进入查询请求的核心模块。

它会综合：

- 用户问法
- 语义解析结果
- 静态路径规划结果
- 模板绑定结果
- context groups

最终得到可执行的 `gatewayRequest`。

### 6.2 将静态路径规划并入请求

关键方法：

- `applyStaticGroupPathPlanning(gatewayRequest, userRequirement)`

其作用是：

1. 调用 `GroupPathPlannerService.planPath(...)`
2. 如果规划成功：
   - 覆盖 `request.groups`
   - 挂上 `request.pathPlanning`
   - 设置 `semanticConstraints.targetObjectType`

这一步非常关键，因为后续执行层依赖这里产出的结构化 path。

文件位置：

- `skills/openclaw-napm-query/services/RequirementParserService.js`

### 6.3 稳定模板如何补 group argument

当命中稳定 query template 时，会调用：

- `buildGroupsFromStableTemplate(groupPath, existingGroups, contextGroups, userRequirement)`

它会从以下来源补 argument：

- 已有 `existingGroups`
- `contextGroups`
- 从用户问法里抽取的 argument

例如：

- `BusinessGroup(服务器网段)`
- `DefinedApp(HTTPS)`

这样可以把“只有路径，没有参数”的模板变成真正可执行的 group 列表。

文件位置：

- `skills/openclaw-napm-query/services/RequirementParserService.js`

### 6.4 单层 metadata 的直接处理

对于单层对象查询，例如：

- “有哪些业务组”
- “有哪些应用”

如果服务类型是 `groups` 且只有 1 层 group，系统不会强行走多层钻取，而是直接用 metadata named list。

例如：

- `BusinessGroup` -> `getBusinessGroups()`

相关实现：

- `if (queryRequest.service === 'groups' && metadataGroups.length === 1) { ... }`

文件位置：

- `skills/openclaw-napm-query/services/RequirementParserService.js`

## 7. 执行层：多轮对话中的续钻是怎么实现的

### 7.1 session 中保存什么

`run_napm_query.js` 在执行续钻时依赖 session 中的以下字段：

- `last_groups`
- `last_metric`
- `last_time_range`
- `last_result_available`
- `turn_expiry`

这些字段组成续钻上下文。

关键方法：

- `normalizeSessionState(session)`
- `hasUsableSessionContext(session)`

文件位置：

- `skills/openclaw-napm-query/scripts/run_napm_query.js`

### 7.2 如何判断这轮是不是“继续钻”

系统会检查当前 prompt 是否包含续钻语义，例如：

- “继续”
- “往下钻”
- “明细”
- “详情”
- “展开”

关键方法：

- `isDrilldownPrompt(prompt)`

文件位置：

- `skills/openclaw-napm-query/scripts/run_napm_query.js`

### 7.3 如何在已有 scope 上补下一层路径

关键方法：

- `inferDrilldownPathFromPrompt(groups, prompt)`

它会基于上一轮 `groups` 继续往下补：

- `BusinessGroup` + “应用”
  -> `Applications -> DefinedApp`

- `BusinessGroup` + “成员IP”
  -> `MemberIPs -> IPAddress`

- `BusinessGroup` + “会话”
  -> `IPConversations -> IPConversation`

也支持一些默认分支：

- 如果用户只是说“继续下钻”
  且当前 path 只是 `BusinessGroup`
  默认优先走：
  - `MemberIPs -> IPAddress`

文件位置：

- `skills/openclaw-napm-query/scripts/run_napm_query.js`

### 7.4 如何把 session 继承到本轮 resolvedQuery

真正的续钻入口是：

- `applySessionContinuationToResolvedQuery(resolvedQuery, prompt, session)`

它会做：

1. 如果 session 不可用：
   - 仅尝试静态 path planning

2. 如果 session 可用：
   - 继承上轮 `groups`
   - 按续钻话术补 path
   - 继承上轮 `metric`
   - 继承上轮 `timeRange`
   - 最后再跑一次静态 path planning 做补强

这一步是项目里“多轮续钻”的核心。

文件位置：

- `skills/openclaw-napm-query/scripts/run_napm_query.js`

## 8. 多层执行失败时的 fallback 机制

### 8.1 为什么需要 fallback

即使结构上路径存在，NAPM 上游接口也不一定能稳定返回多层结果。

常见问题包括：

- `groups` 服务对多层 child inventory 返回不稳定
- `averageValues` 在多层路径下不稳定

因此项目实现了执行时的降级策略。

### 8.2 groups 多层 inventory fallback

当多层 `groups` 查询拿不到稳定 child inventory 时，系统会退化为：

- `topValues(metric)` scoped inventory fallback

也就是：

- 不再依赖 `groups` 返回 child list
- 改用某个合适的 metric 查 top rows，再把 rows 转成 inventory

相关实现：

- `buildInventoryRowsFromTopValues(...)`
- 多层 groups fallback 逻辑

文件位置：

- `skills/openclaw-napm-query/services/RequirementParserService.js`

### 8.3 多层 averageValues fallback

当原始服务为 `averageValues`，但多层路径不稳定时，系统会自动改成：

- `topValues`

并附带 warning，说明这是兼容性降级而不是原始直查结果。

关键实现：

- `buildMultilevelDataServiceFallbackQuery(...)`
- `buildMultiLevelServiceCompatibilityWarning(...)`

文件位置：

- `skills/openclaw-napm-query/services/RequirementParserService.js`

### 8.4 这一层解决的问题

这一步解决的是：

- “结构上可钻，但上游接口执行不稳定”的问题

它的目标不是保证结果一定完整，而是尽量让“结构存在的路径”在运行时也有可用输出。

---

## 9. 当前实现已经具备的能力

截至目前，钻取实现已经具备以下能力：

1. 可以基于静态 group 树列出顶层对象的下钻目录
2. 可以把自然语言中的钻取目标补成结构化 group path
3. 可以在多轮对话中继承已有 `scope / metric / time range`
4. 可以在多层路径执行不稳定时做 runtime fallback
5. 可以将 `BusinessGroup / IPAddress / WebApplication` 等对象纳入统一钻取体系

---

## 10. 当前实现的主要边界

当前实现的主要短板不在“静态路径枚举”，而在“结果项选中式续钻”。

典型表现为：

1. 第一轮：
   - “现在业务组的情况怎么样？”
   - 系统返回业务组排行或概览，里面出现“服务器网段”

2. 第二轮：
   - 用户只说“看一下服务器网段的情况”

这时系统不一定能稳定把“服务器网段”恢复为：

- `BusinessGroup(服务器网段)`

换句话说，当前实现更擅长：

- 已知 scope 上继续往下钻

而不是稳定处理：

- 从上一轮返回结果中“选中一个对象名”再继续问

这说明当前瓶颈主要在：

- 上一轮结果对象如何沉淀为下一轮的结构化锚点

而不是 group 树本身、path planner 本身或多层 fallback 本身。

---

## 11. 一句话结论

项目中的钻取实现，本质上是：

- 用静态 group 树定义可达结构
- 用路径规划器把自然语言补成完整 path
- 用 requirement parser 组装成最终查询
- 用 run-time session continuation 处理多轮续钻
- 用 fallback 兜底上游多层执行不稳定

因此它已经不是“写死几条路径”的简单实现，而是一套“结构驱动 + 上下文驱动 + 兼容性兜底”的钻取体系。
