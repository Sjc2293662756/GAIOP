## 二、三步诊断流程

```
接口: averageValues

指标: PGNPGE, PGTME, PGNSLPGE, PGSLPCT, PGHTTP400, PGHTTP500, PGBYTI, PGBYTO
```

**URL 示例**:

### Step2: 页面错误分析 Top 20 (topValues 三层钻取)

```
接口: topValues
参数: numGroups=3
      groupType1=WebApplication, groupArgument1=<业务名>
      groupType2=PageFamilies
      groupType3=PageFamily
指标: PGNPGE, PGNOBJE, PGHTTP200, PGHTTP300, PGHTTP400, PGHTTP500
排序: topMetric=PGHTTP500, topCount=20
```

**URL 示例**:
```
https://101.254.114.238/webservice/NetInside?UserName=GAIOP&Password=***&type=topValues
  &numGroups=3
  &groupType1=WebApplication&groupArgument1=回溯238web
  &groupType2=PageFamilies&groupType3=PageFamily
  &metrics=PGNPGE,PGNOBJE,PGHTTP200,PGHTTP300,PGHTTP400,PGHTTP500
  &start=1782805440&end=1782809040&topMetric=PGHTTP500&topCount=20&json=true
```

**⚠ 参数顺序敏感**: NAPM 要求 `numGroups/groupType*/groupArgument*` 在 `metrics/start/end` 之前。`SummaryClient._buildGroupParams` 已将 group 参数前置。

**返回格式**: `[{group:{type:'PageFamily',argument:8573230}, groupPath:'...>page 8573230/http://...', metricValues:[...]}]`

**数据处理**: `_extractStep2Data()` → 解析 groupPath 提取页面 URL，遍历 metricValues

**表格展示** (按访问数降序):
| 名称 | 访问次数[次] | 响应次数[次] | 200错误次数[次] | 300错误次数[次] | 400错误次数[次] | 500错误次数[次] |
|------|-------------|-------------|---------------|---------------|---------------|---------------|

### Step3: 逐页访问明细 (pageViews)

```
接口: pageViews
参数: pageFamilyId=<从Step2 groupPath正则提取>, start, end
提取: String(groupPath).match(/page\s+(\d+)/i)[1]
过滤: 跳过 HTTP 200，仅展示异常状态码 (非 200)
```

**URL 示例**:
```
https://101.254.114.238/webservice/NetInside?UserName=GAIOP&Password=***&type=pageViews
  &pageFamilyId=8573088&start=1782805440&end=1782809040&json=true
```

**返回格式**: `[{startTime, page, clientIp, httpStatus, http200S, http400S, http500S, httpResponses}, ...]`

**过滤规则**: `_extractStep3Data` 中跳过 `httpStatus === '200'` 的记录，表格仅展示异常访问。

**表格展示** (每行一次非 200 访问):
| 开始时间 | 页面 | 客户端IP | 状态码 | 200错误 | 400错误 | 500错误 | 响应数 |
|---------|------|---------|--------|--------|--------|--------|--------|

## 三、数据处理链路

### 3.1 运行时数据流

```
FaultDiagnosisService.run(input)
  ├── start() → 创建 session { flowType, context, completedSteps:[] }
  ├── executeStep(session, 'step1_4xx_5xx_overview')
  │     ├── Steps.buildQueries() → NAPM 查询计划
  │     ├── SummaryClient 执行 → rawData.businessOverview
  │     ├── Steps.analyzeStepData() → 判断标记 (http400Up, http500Up...)
  │     ├── matchHints() → 判断提示文本
  │     └── session.completedSteps.push({ rawData, hints, ... })
  ├── executeStep(session, 'step2_page_error_analysis') → 同上
  ├── executeStep(session, 'step3_page_status_detail') → 同上
  └── _buildBsTemplateData(session)
        ├── diagnosis.step1 = _extractStep1Data(raw)
        │     → { topApps:[{PGNPGE,PGTME,...,PGHTTP400,PGHTTP500,...}], http400Total, http500Total, http400Pct }
        ├── diagnosis.step2 = _extractStep2Data(raw)
        │     → { pages:[{pageUrl,PGNPGE,PGNOBJE,PGHTTP200-500},...] }
        └── diagnosis.step3 = _extractStep3Data(raw)
              → { pageDetails:[{startTime,page,clientIp,httpStatus,http200S,http400S,http500S,httpResponses},...] }
```

### 3.2 关键数据提取函数

| 函数 | 位置 | 用途 |
|------|------|------|
| `_extractMetricValues(data)` | FaultDiagnosisService.js | averageValues 响应 → 扁平对象 |
| `_flatMV(mvList)` | FaultDiagnosisService.js | metricValues 数组 → `{metricId: value}` |
| `_extractStep1Data(raw)` | FaultDiagnosisService.js | Step1 raw → diagnosis.step1 |
| `_extractStep2Data(raw)` | FaultDiagnosisService.js | Step2 raw → diagnosis.step2 |
| `_extractStep3Data(raw)` | FaultDiagnosisService.js | Step3 raw → diagnosis.step3（跳过 httpStatus=200） |
| `_flattenPageItem(item, metricIdOrder)` | FaultDiagnosisService.js | 单页条目 → 扁平 row（含 NAPM metric ID 缓存） |
| `resolveGroupArg(target)` | FaultDiagnosisSteps.js | groupArgument \|\| groupLabel 回退 |
| `flattenMetricItem(item)` | FaultDiagnosisSteps.js | 分析用：item → `{key, keyLabel, PGNPGE, ...}` |
| `extractTopItems(data)` | FaultDiagnosisSteps.js | NAPM 格式 A/B → 统一数组 |

## 四、模板渲染

### 4.1 渲染引擎

`BsFaultTemplateService` extends `InspectionFixedTemplateService`

| 方法 | 用途 |
|------|------|
| `buildContext(report)` | 提取 `report.diagnosis` 到 `context.diagnosis`，供 `{{diagnosis.xxx}}` 插值 |
| `buildRowsForSection(section, context)` | 分发 rowBuilder: `bsErrorOverview` / `bsPageErrors` / `bsPageDetails` / `bsEvidence` |
| `renderNarrative(section, context)` | AND/OR 条件叙述 (`bs.root_cause` 规则组) |
| `renderDocx(report)` | 加载模板 → preRender → build → pack → JSZip 后处理 |

### 4.2 Row Builder 函数

| builder | 数据来源 | 表格列 |
|---------|---------|--------|
| `bsErrorOverview` | `diagnosis.step1.topApps[0]` | 指标 \| 数值 (key-value) |
| `bsPageErrors` | `diagnosis.step2.pages[]` | 名称 \| 访问次数 \| 响应次数 \| 200/300/400/500错误次数 |
| `bsPageDetails` | `diagnosis.step3.pageDetails[]` | 开始时间 \| 页面 \| 客户端IP \| 状态码 \| 200/400/500错误 \| 响应数 |
| `bsEvidence` | diagnosis.step1/2/3 | 步骤 \| 查询指标 \| 数据量 |

### 4.3 叙述规则 (`bs-narrative-rules.v1.json`)

| 条件 | 叙述 |
|------|------|
| `http500Total > 0 AND http400Total > 100` | 同时存在 400+500 错误 |
| `http400Total > 0 AND http500Total == 0` | 仅 400 错误，服务端正常 |
| `http500Total > 0` | 存在 500 服务端错误 |
| `http400Total == 0 AND http500Total == 0` | 无错误 |
| `default` | 标准化流程完成 |

## 六、JSON 中文引号问题

> 日期：2026-07-03
> 现象：OpenClaw 日志报 `JSON parse error at position 1955`

### 6.1 根因

模板 JSON `napm_bs_fault_diagnosis_v2.json` 第 39 行：

```
"本次分析按照"整体错误总览—页面级定位—请求明细下钻"的思路展开..."
              ↑ U+201C (左双引号) 被编辑器存成了 U+0022 (ASCII 双引号)
```

U+201C `"` 和 ASCII `"` 在某些编辑器中显示一致，但 JSON 解析器只认 ASCII `"` 为字符串边界。这导致字符串被意外截断。

### 6.2 修复

将中文引号 `"…"` 替换为方括号 `【…】`，彻底避免歧义。

### 6.3 防范

- 所有 JSON 模板文件在本地用 `JSON.parse()` 验证后再推送
- 模板中的中文标点优先使用 `【】` `——` 等无歧义字符

## 七、OpenClaw 路由不稳定问题

> 日期：2026-07-03
> 现象：同一用户、同一句话，第一次走错（napm-alert-query），第二次走对（直接执行 run_fault_diagnosis.js）

### 7.1 表现

| 调用 | 时间 | OpenClaw 路由 | 结果 |
|------|------|------|:--:|
| 第 1 次 | 11:06 | `napm-alert-query` analysis 模式 | Step2 数据不全、Step3 全空 |
| 第 2 次 | 11:10 (`/new` 后) | 直接执行 `run_fault_diagnosis.js` | 三步全部正确 |

### 7.2 根因

会话上下文污染：第 1 次调用时 OpenClaw 的会话状态残留了之前的路由偏好，导致它选了 `napm-alert-query` 而非执行故障诊断脚本。`/new` 清空会话后路由恢复正常。

### 7.3 影响

`napm-alert-query` 的 analysis 模式不会执行完整的 B/S 三步流程——它不查询 PGNOBJE/PGHTTP200/PGHTTP300（Step2 指标不全），也不会调用 pageViews（Step3 完全缺失）。因此即使模板渲染正确，报告内容也会残缺。

### 7.4 缓解措施

- SKILL.md 的 `🚨 路由规则` 表已列出明确的路由映射
- 插件 `before_tool_call` hook 有 guard 拦截 `napm-skill-query` / `napm-alert-query` 在故障诊断场景下的误用
- **但 LLM 路由本质上不可靠**——guard 的 `activePrompt` 可能与会话上下文不一致
