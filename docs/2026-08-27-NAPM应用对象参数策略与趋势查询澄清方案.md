# NAPM 应用对象参数策略与趋势查询澄清方案

日期：2026-08-27  
状态：代码已实施并完成本地验证，尚未制作发布包或部署  
范围：`skills/openclaw-napm-query`、`napm-skill-query` 插件契约、查询服务、对象/指标映射、追问和相关测试

## 1. 背景与结论

用户询问“最近 7 天应用流量趋势如何？”时，系统将“应用”解析为 `DefinedApp`，将指标解析为 `TPIO`，但没有得到具体应用名称，仍然发起了查询，最后以“未查到数据”结束。这个结果不能说明“应用没有流量”，只能说明当前请求的对象范围不完整，或者该完整对象/指标/时间组合确实没有数据。

当前应明确以下口径：

1. 普通“应用”是 `DefinedApp`，来自 `applications` 的 `Type=2`；“业务/Web 应用”是 `WebApplication`，来自 `Type=3`。
2. `DefinedApp` 表示应用对象维度，不代表所有应用的汇总。应用没有可直接替代“总流量”的特殊语义。
3. `TotalTraffic` 才是全局/整体流量范围；它是对象范围，不是指标别名。
4. `TPIO` 表示吞吐/流量速率，`BYTIO` 表示累计字节流量。指标选择不能替代对象参数。
5. 对单个应用做趋势或平均值查询时，应携带具体应用名称，例如 `DefinedApp + argument="HTTP"`。没有名称时应先追问，不应先调用南向接口再把空数组解释成无数据。
6. “应用排行”或“应用清单”是发现/枚举语义，可以暂时不指定单个应用；不能把这种可选参数规则简单套用到单对象趋势查询。

## 2. 当前整体调用链

```text
用户自然语言
  -> OpenClaw 识别意图并构造 resolvedQuery
  -> napm-skill-query 插件归一化与边界校验
  -> skills/openclaw-napm-query/scripts/run_napm_query.js
  -> RequirementParserService 解析服务、对象、指标和查询模式
  -> NapmMetadataService 动态审查对象、参数、指标、粒度
  -> QueryValidator / MetricExecutionKernel 执行前校验
  -> NapmClient 调用 NAPM WebService
  -> 结果解析、归一化、summary/narrationInput
  -> OpenClaw 生成中文最终回答
```

Skill 的职责边界已经要求上游构造完整 `resolvedQuery`，Skill 负责规范化、元数据校验、执行和机器可读结果。追问理解和澄清策略主要由 OpenClaw 及其会话上下文负责；Skill 不能从缺失的对象参数中猜测一个应用。

## 3. 对象、指标和服务口径

| 用户语义 | 对象/指标 | 参数规则（目标规则） |
| --- | --- | --- |
| 某个已定义应用的趋势/平均值 | `DefinedApp` + `TPIO` 或其他兼容指标 | 必须有具体 `argument` |
| 某个 Web 应用/业务系统的趋势/平均值 | `WebApplication` + 兼容指标 | 必须有具体 `argument` |
| 全局/整体/总流量趋势 | `TotalTraffic` + `TPIO` 或 `BYTIO` | 不需要 `argument`，携带 `argument` 应报错 |
| 应用流量排行 | `topValues` + `DefinedApp` | 可不指定单个应用，由查询发现对象 |
| 应用对象清单 | `groups` + `DefinedApp` | 可不指定单个应用，返回目录对象 |
| 各应用多对象趋势 | `timeValues` + 多对象/维度语义 | 当前没有形成独立、可验收的策略，应单独设计，不得由单对象规则隐式推断 |

应区分以下两类说法：

- “应用流量趋势”通常是在问一个具体应用的时间序列，缺名称时应追问“要查询哪个应用”。
- “各应用流量排行/有哪些应用”是发现或枚举，不代表存在一个名为“应用总流量”的对象。

## 4. 实施前缺陷与修复结果

### 4.1 参数必填信息没有形成条件契约（已修复）

实施前，配置和代码只部分表达了参数要求：

- `napm-resolution-spec.v1.json` 有服务级 `required/optional` 字段，也有运行时元数据标记 `groupArgumentExistence=true`。
- `napm-openclaw-plugin.remote.js` 对 `groups` 的主要检查是数组非空；没有根据 `service + queryModeKey + group.type` 判断 `argument` 是否必填或禁止。
- `GroupBuilder.buildGroupParams()` 只有在 `group.argument` 非空时才生成 `groupArgument1`，缺失参数会被静默省略。
- `NapmMetadataService.reviewQuery()` 只在参数已经提供时校验名称是否存在，没有把“对象定义要求参数但请求未提供”列为阻断问题。
- 因此配置声明了参数存在性要求，执行路径却没有统一执行该要求，造成配置、插件、元数据服务三套行为不一致。

### 4.2 已验证的本地复现

在本地 mock 执行链上，使用分钟对齐的有效 `start/end`，分别提交以下查询：

```json
{
  "service": "timeValues",
  "queryModeKey": "timeseries",
  "groups": [{ "type": "DefinedApp" }],
  "metric": "TPIO",
  "metrics": ["TPIO"],
  "granularity": 86400,
  "start": "<aligned-start>",
  "end": "<aligned-end>"
}
```

该请求可以通过当前对象/参数检查，生成 `groupType1=DefinedApp`、`numGroups=1`，但不生成 `groupArgument1`，mock 返回空数据。

增加应用参数：

```json
{
  "service": "timeValues",
  "queryModeKey": "timeseries",
  "groups": [{ "type": "DefinedApp", "argument": "HTTP" }],
  "metric": "TPIO",
  "metrics": ["TPIO"],
  "granularity": 86400,
  "start": "<aligned-start>",
  "end": "<aligned-end>"
}
```

执行参数会包含 `groupArgument1=HTTP`，mock 可以返回数据点。`TotalTraffic` 不带参数时可作为全局范围执行。

该复现只证明当前代码会放行不完整查询以及参数会如何生成；mock 没有连接真实南向服务，不能据此断言生产接口在所有时间范围一定返回空数据。

### 4.3 空结果掩盖了请求不完整（已修复）

`run_napm_query.js` 对合法执行但 `rows.length === 0` 的结果统一生成“未查到数据”。当前结果没有稳定区分：

- 对象或对象参数缺失导致的 `scope_incomplete`；
- 对象、指标、时间均完整但数据源确实为空的 `no_data`；
- 上游错误、元数据错误或执行失败。

这会使最终回答把“没有指定应用”误说成“应用没有有效数据”。本次修复已在执行前拦截该情况。

### 4.4 本次代码落地

- `napm-resolution-spec.v1.json` 新增按 `service + queryModeKey + groupType + operation` 计算的 `argumentPolicy`，支持 `required`、`optional` 和 `forbidden`。
- `ResolutionSpecService` 提供共享策略评估器；插件边界、`RequirementParserService` 准备阶段和直接执行阶段均复用该评估器。
- 缺少单对象应用参数时返回 `GROUP_ARGUMENT_REQUIRED` 和澄清 gate，不调用元数据或指标南向接口；`TotalTraffic` 携带参数返回 `GROUP_ARGUMENT_FORBIDDEN`。
- 明确提供但目录不存在的对象参数由元数据审查返回 `INVALID_GROUP_ARGUMENT`，保留候选对象信息；合法空结果仍按普通无数据路径处理。
- `ExecutionFailureClassifier` 将范围不完整与范围非法分别归类为 `QUERY_SCOPE_INCOMPLETE`、`QUERY_SCOPE_INVALID`，避免与合法 `no_data` 混淆。
- `napm-skill-query` 工具描述、Schema 和 standalone `SKILL.md` 已同步说明全局流量、单对象趋势/平均值以及排行/清单的参数差异。

## 5. 追问设计现状

项目已有通用 `ClarificationGateService`，可以根据以下信息生成澄清结果：对象歧义、实体候选、执行保护、缺少指标、时间范围和元数据问题。项目也已有轻量查询上下文及可信时间范围追问机制，用于在同一会话中安全继承部分查询信息。

实施前没有专门覆盖以下组合：

```text
DefinedApp + timeValues/averageValues + 缺少具体应用 argument
```

因此修复前“最近 7 天应用流量趋势如何？”可能先执行一个缺少 `groupArgument` 的请求，再返回空结果，而不是在执行前提出澄清；现在会先返回具体应用名称澄清。

追问不能通过“所有包含应用的问句都自动选择一个应用”解决，也不能通过把所有 `hasArgument=true` 对象都改成无条件必填解决。排行和清单需要保留无参数入口，且“那最近 7 天的呢？”这类时间追问必须继承完整、可信的上一轮查询，而“那你呢？”不能获得 NAPM 工具权限。

## 6. 影响范围

### 直接影响

- 应用单对象趋势/平均值请求可能发送无效或无意义的南向请求。
- 用户看到“未查到数据”，无法知道缺少的是具体应用名称。
- 模型可能把空结果归因为数据不存在，而不是请求范围未闭合。
- 查询审计中会出现缺失 `groupArgument` 的可执行请求，降低问题定位能力。

### 不应被误伤的能力

- `TotalTraffic` 全局趋势不需要应用名称。
- `topValues + DefinedApp` 可以用于发现应用排行。
- `groups + DefinedApp` 可以用于应用清单。
- 已明确提供合法应用名称的查询仍应直接执行；名称不存在时应给出候选或结构化错误。

## 7. 解决方案与落地状态

### 7.1 建立按查询模式计算的 `argumentPolicy`（已落地）

在 resolution spec 中增加可审计的条件策略，而不是只保留对象级 `hasArgument`：

```json
{
  "groupType": "DefinedApp",
  "service": "timeValues",
  "queryModeKey": "timeseries",
  "operation": "single_object_value",
  "argumentPolicy": "required"
}
```

建议至少支持三种策略：

- `required`：缺失时不得调用南向接口；
- `optional`：可以查询对象集合或发现排行；
- `forbidden`：例如 `TotalTraffic` 不允许携带应用参数。

策略优先级建议为：显式服务/查询模式规则 > 对象运行时元数据 > 默认兼容规则。所有策略必须同时出现在配置、插件 Schema/说明、Skill 解析器和测试夹具中。

### 7.2 在执行前增加统一参数审查（已落地）

由一个共享的参数策略评估器返回结构化结果，至少包含：

```text
policy: required | optional | forbidden
status: satisfied | missing | invalid | forbidden
groupType
argument
service
queryModeKey
```

插件边界先做轻量阻断，`RequirementParserService` 和 `NapmMetadataService` 再做同一规则的完整审查。这样可以防止绕过插件的 CLI/内部调用，也避免三处各自实现不同判断。

### 7.3 为缺少应用名称生成澄清 Gate（已落地）

新增结构化原因码，例如：

- `GROUP_ARGUMENT_REQUIRED`：当前单对象查询缺少对象名称；
- `INVALID_GROUP_ARGUMENT`：对象名称不在运行时目录；
- `GROUP_ARGUMENT_FORBIDDEN`：全局对象不接受参数。

对用户的首轮问题应类似：

```text
应用流量趋势需要指定具体应用名称。请告诉我要查询哪个应用；如果你想看全局流量，请改问“总流量趋势”。
```

若已从应用目录得到候选，展示最多有限数量的候选并允许用户直接选择；禁止静默选择第一个应用、把 `DefinedApp` 改成 `TotalTraffic`，或用历史结果代替当前查询。

### 7.4 区分不完整范围和合法空结果（已落地范围校验）

建议结果契约增加明确状态：

```text
scope_incomplete    对象/参数未闭合，等待澄清
no_data             查询完整且执行成功，但没有数据点
metadata_error      对象、参数、指标或粒度校验失败
execution_error     上游调用或解析失败
success             返回有效数据
```

只有 `no_data` 才允许使用“当前范围未返回数据点”的确定性表述；`scope_incomplete` 必须走澄清，不应进入普通空结果文案。

### 7.5 同步工具说明、Skill 文档和模型提示（已落地）

`napm-skill-query` 契约应明确：

- 全局/整体流量趋势使用 `groups=[{type:"TotalTraffic"}]`；
- 普通应用趋势使用 `groups=[{type:"DefinedApp", argument:"具体名称"}]`；
- `TPIO` 是速率，`BYTIO` 是累计字节量；
- 时间追问必须提交完整 `resolvedQuery`，不能只提交新的时间字段；
- 缺少必填对象参数时应追问，不得提交半成品查询。

### 7.6 保留并收紧上下文追问（本次未改变既有上下文授权边界）

已有查询上下文可以继续支持“那最近 7 天的呢？”这类安全时间变化，但授权条件应包含：同一会话、同一查询服务、指标和对象范围一致、时间或粒度确实变化、当前完整查询再次通过全部参数策略。上下文不得把缺失的应用名称静默补入新查询，也不得让身份问句或其他非查询问句获得工具权限。

## 8. 回归测试计划

### 契约与策略单元测试（已落地）

1. `DefinedApp + timeValues` 缺少参数返回 `GROUP_ARGUMENT_REQUIRED`，不构造 `groupArgument1`，不调用 `NapmClient`。
2. `DefinedApp + averageValues` 缺少参数同样阻断。
3. `DefinedApp + topValues` 无参数仍可执行排行/发现。
4. `groups + DefinedApp` 无参数仍可返回应用清单。
5. `TotalTraffic + timeValues` 无参数通过；携带参数返回 `GROUP_ARGUMENT_FORBIDDEN`。
6. 已提供应用名称但目录不存在时返回 `INVALID_GROUP_ARGUMENT` 和候选列表。

### 追问和结果测试（已落地核心路径）

1. “最近 7 天应用流量趋势如何？”只返回中文澄清，不发南向请求。
2. 用户补充“HTTP”后，生成 `DefinedApp + argument=HTTP` 并执行。
3. “最近 7 天总流量趋势如何？”直接使用 `TotalTraffic`，不追问应用。
4. 上一轮合法查询为空，后续“那最近 7 天的呢？”只在可信上下文有效时执行完整时间变更查询。
5. “那你呢？”不因上一轮查询上下文获得 NAPM 工具权限。
6. 完整查询无数据返回 `no_data`；缺参数返回 `scope_incomplete`；两者不能共用同一最终文案。

### 集成与运行时契约（已验证）

- 插件 schema、`resolvedQuery` 归一化、`RequirementParserService`、`GroupBuilder` 和 `NapmMetadataService` 使用同一策略夹具。
- mock NAPM 服务验证参数是否实际落到 `groupType1/groupArgument1/numGroups`。
- 补齐查询工具契约测试后运行 `npm test`、`npm run lint`、`npm run verify:runtime-contract`。
- 当前实现已通过完整 Jest 101 个套件、818 个测试，`npm run lint` 和 `npm run verify:runtime-contract`；未连接服务器、未制作发布包、未部署。

## 11. 待确认问题

1. “各应用趋势”是否需要支持一个无参数、多序列 `timeValues` 查询，还是统一要求先选择一个应用；这会影响 `DefinedApp + timeValues` 的策略粒度。
2. 应用目录候选是展示名称、内部值，还是同时展示二者；需要与现有 `applications` 元数据返回字段统一。
3. “应用流量”默认使用 `TPIO`（速率）还是 `BYTIO`（累计量）应继续以用户语义区分，并在最终回答中显示单位。
