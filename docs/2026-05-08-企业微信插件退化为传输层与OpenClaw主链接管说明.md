# 2026-05-08 企业微信插件退化为传输层与 OpenClaw 主链接管说明

## 一、背景

此前企业微信插件实际上仍保留了一条本地 NAPM 直连链路，典型表现为：

- 本地判断是不是 NAPM 问题；
- 本地判断是不是边界外问题；
- 本地决定是否拦截；
- 本地决定是否直接调用 NAPM skill；
- 本地决定部分拒答/引导文案。

这会带来一个根本问题：

**企微插件抢走了原本应该属于 OpenClaw 主链的理解、边界判断、引导和调度权能。**

因此会出现：

1. 用户以为是 OpenClaw 在回答，实际部分问题被企微插件提前拦截；
2. 同一类问题在不同入口下行为不一致；
3. 修改边界判断时，总是被迫先改企微插件；
4. OpenClaw 无法真正统一负责：
   - 领域边界
   - 追问判断
   - 澄清判断
   - 拒答与引导
   - 最终组织语言

## 二、本次目标

本次调整的目标非常明确：

### 企微插件退化为传输层

企微插件只负责：

- 接收企业微信消息
- 解析文本/图片/文件
- 透传上下文给 OpenClaw
- 回传 OpenClaw 的结果
- 保留必要的凭证安全拦截

### OpenClaw 主链统一接管

由 OpenClaw 统一负责：

- 是否属于 NAPM 范围
- 是否属于边界外问题
- 是否是追问
- 是否需要澄清
- 是否拒答并如何引导
- 如何组织最终中文回复

## 三、本次实际修改内容

### 1. 降级 `tryHandleNapmQuery`

远端运行插件中原有函数：

- `tryHandleNapmQuery(...)`

此前承担的是：

- 本地 NAPM 语义识别
- 本地边界拦截
- 本地 skill 预执行
- 本地拒答/引导

本次已将其改为**传输层兼容壳**：

- 不再进行本地语义判断
- 不再进行本地边界判断
- 不再本地抢先执行 NAPM 查询
- 仅记录一条 transport-only 日志后直接 `return false`

当前行为变为：

```js
Transport-only mode enabled; skipping local NAPM semantic routing
```

即：

**企微插件不再本地决定“这是不是 NAPM 问题、该不该查、该不该拦”。**

### 2. 保留全局凭证安全拦截

在 `processWeComMessage(...)` 中仍保留：

- `isCredentialDisclosureRequest(text)`
- `buildWeComCredentialBoundaryReply()`

这是刻意保留的唯一“本地兜底能力”。

原因：

- 账号、密码、token、凭证等属于安全红线；
- 这类内容不需要走上游语义判断；
- 插件层可直接拒绝，避免敏感信息继续流转。

### 3. 主流程改为统一进入 OpenClaw 主链

当前企微消息主流程仍然是：

1. 解析消息
2. 发送 thinking
3. 做凭证安全检查
4. 构造 `ctxPayload`
5. 调用：
   - `routeAndDispatchMessage(...)`
   - `dispatchReplyWithBufferedBlockDispatcher(...)`

也就是说：

**除了凭证安全拦截外，其余消息已经统一交由 OpenClaw 主链处理。**

```bash
systemctl --user restart openclaw-gateway.service
```

重启后验证结果：

- 网关重新启动成功
- 企业微信 WebSocket 重新认证成功
- 远端运行包中已出现：
  - `Transport-only mode enabled; skipping local NAPM semantic routing`

说明本次改动已进入真实运行态。

## 六、当前链路职责划分

### 企业微信插件当前职责

- 消息接入
- 文件/图片处理
- 上下文透传
- 回复下发
- 凭证泄露安全拦截

### OpenClaw 当前职责

- 领域边界判断
- 是否 NAPM 内问题判断
- 澄清/追问判断
- 调度 skill
- 组织拒答与引导
- 组织最终回答

### NAPM skill 当前职责

- 语义落地到查询结构
- 构造 resolvedQuery
- 执行 NAPM 查询
- 返回结构化结果和叙述素材

## 七、预期收益

本次收口后，最大的变化是：

### 1. 企微不再“抢答”

不会再由企业微信插件本地决定：

- `什么是玫瑰`
- `今天天气`
- `需要`
- `继续`
- `现在网络情况怎么样`

这类问题是否属于 NAPM、是否要拒绝、是否要引导，都会交给 OpenClaw 主链统一判断。

### 2. 入口行为更一致

后续如果同样的问题在不同上下文里表现不一致，就应该优先查：

- OpenClaw 主链提示词
- OpenClaw 的技能调度
- skill 的领域边界与结果组织

而不是继续优先怀疑企微插件本地判断。

### 3. 后续优化点更明确

后面如果还要继续收口，正确方向应是：

1. 在 OpenClaw 主链补齐领域白名单/边界拒答能力；
2. 在 OpenClaw 主链补齐追问理解能力；
3. 在 skill / planner 层优化结构化查询与回答组织；
4. 企微插件维持“薄接入层”角色。

## 八、当前仍保留的历史残留

虽然主流程已经退化为 transport-only，但远端插件文件中仍保留了一些历史函数定义，例如：

- `looksLikeNapmQuery`
- `detectWeComHardBoundary`
- `buildWeComGeneralBoundaryReply`
- `buildWeComSystemBoundaryReply`
- `requestNapmSkillQuery`

当前状态是：

- **这些函数定义还在文件里**
- **但主流程已经不再依赖它们做本地语义决策**

后续如果继续做深度清理，可以再把这些未参与主流程的遗留定义清掉。

## 九、结论

本次已完成关键架构收口：

**企业微信插件从“会判断、会拦截、会直查”的半业务层，退回为“接入与转发为主的传输层”。**

同时：

**OpenClaw 主链重新拿回了领域边界、引导、追问、澄清与技能调度的主决策权。**

这才是后续继续优化整个系统行为的一条正确主线。
