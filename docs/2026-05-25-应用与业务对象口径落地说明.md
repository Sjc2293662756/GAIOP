# 应用与业务对象口径落地说明

日期：2026-05-25

## 背景

本次修改以 `napm-应用与业务对象说明-2026-05-23.md` 作为应用/业务对象的领域事实来源，将项目中的对象实例清单策略调整为：

- `applications` API 是应用类对象实例清单的真相源。
- `applications.Type` 用于区分不同应用对象类型。
- `groupType` 仍然只表示运行时查询维度，不等同于清单来源。

这次收口的重点是把“系统里有哪些业务/应用”和“按哪个 groupType 执行指标查询”拆开，避免再次把业务对象、协议应用、未知应用混成同一份列表。

## 当前对象口径

| 用户语义 | 语义对象 | 实例清单来源 | Type 过滤 | 执行维度 |
| --- | --- | --- | --- | --- |
| 业务 / 业务系统 / Web 应用 | `WebApplication` | `applications` | `Type=3` | `groupType=WebApplication` |
| 已定义应用 / 服务器应用 | `DefinedApp` / `Application` | `applications` | `Type=2` | `groupType=DefinedApp` |
| 自动识别应用 / 特征识别应用 / 复合协议 / 复合应用 / 多协议应用 | `CompositeApplication` | `applications` | `Type=4` | 当前执行映射为 `groupType=DefinedApp` |
| 内置端口应用 / 系统内置应用 | `BuiltinApplication` | `applications` | `Type=1` | 当前映射为 `DefinedApp` |
| 业务组 / 工作组 | `BusinessGroup` | `businessGroups` | 不适用 | `groupType=BusinessGroup` |
| 未知应用 / 未知端口流量 | `OtherApp` | `groupArguments` | 不适用 | `groupType=OtherApp` |
| 页面族 / 用户 / 客户端业务组 | `PageFamily` / `User` / `ClientBusinessGroup` | `groupArguments` | 不适用 | 对应 groupType |

## 修改内容

### 1. 对象实例 provider 收口

修改文件：

- `skills/openclaw-napm-query/services/ObjectMetadataRegistry.js`

调整后：

- `WebApplication` 不再走 `groupArguments`，改为 `applications Type=3`。
- `DefinedApp` / `Application` 走 `applications Type=2`。
- 新增 `CompositeApplication`，走 `applications Type=4`，覆盖自动识别应用/复合协议/复合应用，不再混入 `DefinedApp`。
- 新增 `BuiltinApplication`，走 `applications Type=1`。
- `OtherApp` 保持运行时对象口径，走 `groupArguments`。
- provider 元数据新增 `executionGroupType`、`applicationTypeFilter`、`applicationCatalogRole`。

### 2. 元数据服务增加 Type 过滤

修改文件：

- `skills/openclaw-napm-query/services/NapmMetadataService.js`

调整后：

- `listObjectInstances()` 在 provider 为 `applications` 时，会按 `applicationTypeFilter` 过滤。
- `normalizeNamedList()` 保留南向 `Type`、`Description`、`Status`、`Id` 等字段。
- 返回对象统一补充审计字段：
  - `requestedObjectType`
  - `effectiveObjectType`
  - `executionGroupType`
  - `providerType`
  - `source`
  - `applicationType`
  - `applicationTypeFilter`
  - `applicationCatalogRole`
  - `fallbackUsed`

### 3. resolver 元数据清单语义增强

修改文件：

- `skills/openclaw-napm-query/services/NapmResolvedQueryResolverService.js`

调整后：

- “系统中有哪些业务 / Web 应用 / 业务系统”稳定落到 `WebApplication`。
- “系统中有哪些已定义应用 / 服务器应用 / 协议应用”稳定落到 `DefinedApp`。
- “系统中有哪些自动识别应用 / 特征识别应用 / 复合协议 / 复合应用 / 多协议应用”稳定落到 `CompositeApplication`。
- “系统中有哪些内置应用 / 内置端口应用”稳定落到 `BuiltinApplication`。
- “系统中有哪些未知应用 / 未知端口”稳定落到 `OtherApp`。

注意：plain “系统中有哪些应用” 是歧义问法，不能默认等同 `DefinedApp`，也不能直接返回 `applications` 全量目录。构造阶段应澄清用户要看 `WebApplication(Type=3)`、`DefinedApp(Type=2)`、`BuiltinApplication(Type=1)`、`CompositeApplication(Type=4)` 还是 `OtherApp`。

同时，`groups-tree.static.json` 中的 `Application` 节点只用于层级/下钻结构，不是应用清单真相源，不能用它解释“系统中有哪些应用/已定义应用/业务”。

### 4. 提示和参考文档同步

修改文件：

- `skills/openclaw-napm-query/agents/openai.yaml`
- `skills/openclaw-napm-query/references/openclaw-integration.md`

- 清单：`applications Type=3`
- 执行：`groupType=WebApplication`

## resolvedQuery 示例

### 系统中有哪些业务？

```json
{
  "service": "groups",
  "queryModeKey": "metadata",
  "groups": [{ "type": "WebApplication" }],
  "format": "json",
  "semanticConstraints": {
    "operation": "metadata_list"
  }
}
```

执行时会通过 `NapmMetadataService.listObjectInstances("WebApplication")` 查询 `applications` 并过滤 `Type=3`。

### 系统中有哪些已定义应用？

```json
{
  "service": "groups",
  "queryModeKey": "metadata",
  "groups": [{ "type": "DefinedApp" }],
  "format": "json",
  "semanticConstraints": {
    "operation": "metadata_list"
  }
}
```

执行时会查询 `applications` 并过滤 `Type=2`。

### 系统中有哪些自动识别应用 / 复合协议？

```json
  "groups": [{ "type": "CompositeApplication" }],
  "format": "json",
  "semanticConstraints": {
    "operation": "metadata_list"
  }
}
```

执行时会查询 `applications` 并过滤 `Type=4`。

### 系统中有哪些内置应用？

新增/更新覆盖点：

- `WebApplication` 清单必须走 `applications Type=3`。
- `DefinedApp` 清单必须走 `applications Type=2`。
- `CompositeApplication` 清单必须走 `applications Type=4`。

## 后续建议

- 如需让 `OtherApp` 也完全符合文档中的“运行时 OtherApp 查询”语义，可以继续补一个专用 provider，例如 `runtimeOtherApp`，避免长期复用通用 `groupArguments` 名称。
- 可以把 `applicationTypeFilter` 下沉到配置文件，后续若南向 Type 定义变化，不需要改代码。
- 最终回答层建议展示 `applicationType` 和 `applicationCatalogRole`，便于排查“业务对象”和“协议应用”是否混池。
