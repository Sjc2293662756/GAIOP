# NAPM 巡检报告用户时间窗口与流量分析修改方案

日期：2026-08-26  
适用范围：`openclaw-napm-inspection`、`openclaw-napm-report`、巡检报告模板与图表配置，以及报告请求的时间范围传递链路  
阶段：代码修改已完成并通过本地验证；本文件同时记录实施边界，不包含发布包制作或远端部署。

## 1. 背景与现状

历史巡检报告的固定窗口与本次改造后的行为如下：

| 内容 | 历史默认窗口 | 当前行为 |
| --- | --- | --- |
| 流量健康趋势 | 最近 1 小时、最近 1 天 | 用户主窗口 + 必要的截止时辅助窗口 |
| 业务性能慢访问、HTTP 400/500 | 最近 7 天 | 用户指定范围；未指定时仍为 `topValues` 七天聚合 |

巡检阶段已经完成“固定窗口内动态选粒度”的修复。当前支持 `60/300/3600/86400` 秒，默认最大点数预算为 120；接口返回合法 `raw.granularity` 时，实际时间轴、统计和图表优先使用响应粒度，同时保留 `requestedGranularity`、`actualGranularity`、`granularityMismatch` 和 `granularitySource`。

此前用户选择的完整时间范围尚未贯穿巡检链路，现已完成贯通：

1. `InspectionReportDataService` 现在生成并传递包含 `start/end/key/mode/timezone` 的窗口契约。
2. `InspectionTrafficAnalysisService.collect()` 以 `primaryWindow` 生成主图，并按范围生成可选的最近 1 天/最近 1 小时辅助图。
3. `InspectionBusinessPerformanceService` 在用户指定范围时复用主窗口；未指定时继续使用最近 7 天聚合。
4. 报告模板和图表绑定已切换到动态窗口字段，同时保留 `recentHour`、`recentDay` 兼容读取。

因此，系统现在能把“最近 7 天、最近 30 天、最近一个季度、最近一年”等用户意图作为报告主时间窗口，并根据跨度选择查询粒度。年度等超过点数预算的窗口继续使用后端支持的日粒度请求，再在报告侧按 `Asia/Shanghai` 本地周边界做平均聚合，数据集明确记录 `calendar_week_average`，不伪装成后端周粒度。

## 2. 修改目标

1. 报告请求支持用户指定滚动窗口、自然日历窗口或自定义起止时间。
2. 用户指定的范围成为报告的 `primaryWindow`，其流量趋势图使用与跨度匹配的动态粒度。
3. 最近 1 小时和最近 1 天不再冒充大范围报告的主窗口；需要保留时，明确标记为报告截止时的辅助状态窗口。
4. 图表横轴、统计、标题、查询证据和实际接口响应使用同一个最终有效时间范围和实际粒度。
5. 保留旧字段和旧模板的兼容读取，避免历史报告数据失效。

## 3. 核心设计

### 3.1 报告窗口与辅助窗口分离

统一使用以下概念：

```text
reportWindow：用户请求的报告范围及解析结果
primaryWindow：报告主分析窗口，默认等于 reportWindow
contextWindows：报告截止时的辅助状态窗口，例如最近 1 天、最近 1 小时
```

推荐行为：

| 请求情况 | 主窗口 | 辅助窗口 |
| --- | --- | --- |
| 未指定范围 | 保持兼容，主分析仍为最近 1 小时 | 最近 1 天 |
| 用户选择不超过 1 天的范围 | 用户选择的范围 | 仅在不重复且确有价值时保留最近 1 小时/1 天 |
| 用户选择超过 1 天的范围 | 用户选择的范围 | 最近 1 天、最近 1 小时，均以报告截止时刻计算 |

例如用户请求最近 7 天巡检，报告应包含：

```text
最近 7 天流量分布趋势                 （主图）
报告截止时最近 1 天流量分布状况         （辅助图）
报告截止时最近 1 小时流量分布状况        （辅助图）
```

“最近 1 小时”与“最近 1 天”并不冲突，因为它们是嵌套窗口：

```text
最近 1 小时 ⊂ 最近 1 天 ⊂ 最近 7 天
```

但只展示最近 1 小时和最近 1 天、却把报告称为“最近 7 天巡检”，会造成业务语义误导，必须增加主窗口图或调整报告标题。

### 3.2 统一窗口契约

报告输入建议增加统一对象：

```json
{
  "reportWindow": {
    "mode": "rolling",
    "key": "last7days",
    "start": 0,
    "end": 0,
    "timezone": "Asia/Shanghai",
    "displayText": "最近7天"
  },
  "primaryWindow": {
    "id": "traffic-primary",
    "start": 0,
    "end": 0,
    "durationSeconds": 604800,
    "timezone": "Asia/Shanghai"
  },
  "contextWindows": [
    { "id": "recent-day", "key": "last1day" },
    { "id": "recent-hour", "key": "last1hour" }
  ]
}
```

说明：示例中的 `start/end` 仅表示字段位置，不是可执行时间戳。实际值必须由服务器时间解析器生成，不能由模型计算或写入文档示例作为真实数据。

窗口模式必须明确区分：

- `rolling`：滚动最近 N 分钟/小时/天，例如 `last7days`、`last30days`、`last90days`、`last365days`。
- `calendar`：自然季度/自然年度，例如 `currentQuarter`、`previousQuarter`、`currentYear`、`previousYear`。
- `custom`：用户明确给出的起止日期时间，必须校验两端完整、`end > start` 和时区。

`last90days` 与“最近一个季度”不能混为一谈；前者是滚动 90 天，后者通常是当前自然季度。`last365days` 与“今年”同理。

### 3.3 时间粒度选择

粒度由窗口跨度和最大点数预算共同决定，而不是由报告标题硬编码：

```text
目标点数 = 窗口时长 / 候选粒度
选择能满足点数预算的最小支持粒度
```

当前候选粒度：

```text
60s / 300s / 3600s / 86400s
```

推荐结果：

| 窗口 | 推荐粒度 | 说明 |
| --- | ---: | --- |
| 1 小时 | 60 秒 | 约 60 点 |
| 3 小时 | 300 秒 | 约 36 点 |
| 1 天 | 3600 秒 | 约 24 点 |
| 7 天 | 86400 秒 | 约 7 点 |
| 30 天 | 86400 秒 | 约 30 点 |
| 90 天/滚动季度 | 86400 秒 | 约 90 点 |
| 365 天 | 后端请求 86400 秒，报告侧有效 604800 秒 | 约 53 点；按上海本地周边界平均聚合，避免依赖后端周粒度 |

年度窗口统一采用兼容后端的日粒度查询，再在报告侧按本地周边界聚合，并在 `effectiveGranularity` 中标明“日查询、周聚合”，不能伪装成后端直接返回周粒度。

短窗口的 `end` 向下对齐到分钟；小时、日、周等较大粒度需要按 `Asia/Shanghai` 的本地边界对齐，并保存请求范围和对齐后的 `effectiveWindow`，避免用户看到的标题与实际查询范围不一致。

### 3.4 时间戳、时区和横轴

1. 所有执行时间使用 Unix 秒，并由统一时间解析器生成。
2. 报告时区显式固定为 `Asia/Shanghai`，不能依赖 Node 进程的本地时区。
3. 以接口响应的合法 `actualGranularity` 生成横轴；请求粒度只作为请求证据。
4. 缺少合法 `interval.start` 时不得回退到 0 或生成 1970 年横轴，应进入结构化警告/占位状态。
5. 多指标必须共享同一 `xData`；缺点保留 `null`，禁止把缺失值静默改成 0。
6. 空数据不生成空白 PNG，报告中使用“该窗口无可用数据”的占位内容并保留查询证据。

## 4. 报告内容与标题设计

报告模板不再把“最近 1 小时”“最近 1 天”写死在章节标题中，而应从窗口对象生成：

```text
${primaryWindow.displayText}流量分布趋势
${contextWindow.displayText}流量分布状况
```

推荐标题示例：

| 用户请求 | 主图标题 | 辅助图标题 |
| --- | --- | --- |
| 最近 7 天 | 最近7天流量分布趋势 | 报告截止时最近1天 / 最近1小时流量分布状况 |
| 最近 30 天 | 最近30天流量分布趋势 | 报告截止时最近1天 / 最近1小时流量分布状况 |
| 最近一个季度 | 当前自然季度流量分布趋势 | 报告截止时最近1天 / 最近1小时流量分布状况 |
| 最近一年 | 最近365天流量分布趋势，或今年流量分布趋势 | 报告截止时最近1天 / 最近1小时流量分布状况 |

主窗口和辅助窗口必须分别展示有效起止时间、时区、粒度和数据状态。固定模板新增流量窗口元数据表；旧报告继续支持 `recentHour`、`recentDay` 字段；当前实现使用 `trafficAnalysis.primary`、`trafficAnalysis.contextWindows`（并提供 `contextDay/contextHour` 便捷字段），模板继续保留 v1 读取能力。

## 5. 实施范围与步骤

### 第一阶段：输入时间范围贯通（已完成）

1. 检查 `napm-report-export` 上游如何构造 `executionTimeRange`。
2. 将完整 `start/end/key/mode/timezone` 传入 `InspectionReportDataService`。
3. 对相对窗口、自然窗口和自定义窗口做统一解析和校验。

### 第二阶段：巡检采集改造（已完成）

1. `InspectionTrafficAnalysisService.collect()` 接收 `primaryWindow`。
2. 主流量查询使用用户窗口，并按跨度选择粒度。
3. 大范围请求按约定生成最近 1 天、最近 1 小时辅助窗口。
4. 保留 `recentHour/recentDay` 兼容字段，避免旧调用方失效。

### 第三阶段：业务性能范围改造（已完成）

1. `InspectionBusinessPerformanceService` 默认继续使用最近 7 天，保证未指定范围时行为不变。
2. 用户明确选择报告范围时，慢访问和 HTTP 400/500 的聚合查询改用 `primaryWindow`。
3. 明确该部分是 `topValues` 聚合，不承诺生成与流量趋势相同的时间序列粒度。

### 第四阶段：报告模板和图表绑定（已完成）

1. 新增窗口元数据字段和动态标题字段。
2. 主图、辅助图分别绑定 `primaryTraffic`、`contextTraffic`。
3. 图表规格读取实际粒度、时区、空数据状态和 `null` 缺点。
4. 如模板结构发生不兼容，新增巡检模板 v2，并保留 v1 兼容渲染。

### 第五阶段：回归验证与发布（本地验证已完成，发布待批准）

1. 运行巡检专项测试、报告模板测试和图表渲染测试。
2. 运行 lint、全量 Jest、runtime contract、`node --check` 和 `git diff --check`。
3. 运行安装 dry-run 和 staged 验证（发布前执行）。
4. 仅在明确批准后按统一版本管理流程构建发布包和部署；当前未连接服务器、未制作部署包、未重启或部署远端服务。

## 6. 回归测试矩阵

### 窗口与边界

- 未指定范围：仍生成最近 1 小时和最近 1 天兼容结果。
- 最近 1 小时、最近 1 天、最近 3 小时。
- 最近 7 天、最近 30 天、最近 90 天、最近 365 天。
- `currentQuarter`、`previousQuarter`、`currentYear`、`previousYear`。
- `custom` 起止时间、缺一端、`end <= start`、超保留期。
- 精确跨小时、跨天、跨周、夏令时/时区配置边界（即使当前生产时区固定，也要防止进程 TZ 影响结果）。

### 粒度与图表

- 60/300/3600/86400 秒选择边界，以及年度超预算时的日查询、报告侧周聚合路径。
- 请求粒度与响应粒度相同、不同、缺失、非法。
- `interval.start/end` 缺失、非分钟对齐、响应范围被后端修正。
- 多指标长度不一致、`null`、`undefined`、`NaN`、真实 0 值。
- 空数据不渲染空白 PNG，非空数据的 `xData` 与每条 series 长度一致。
- 在 `TZ=UTC` 和 `TZ=Asia/Shanghai` 下横轴展示一致。
- 主窗口与辅助窗口不重复，标题、数据字段和查询证据一一对应。

## 7. 验收标准

1. 用户选择的时间范围出现在报告主窗口标题、查询证据和实际图表中。
2. 最近 1 小时/最近 1 天只作为默认兼容窗口或明确标记的辅助状态窗口。
3. 7 天、30 天、季度和年度请求不再只生成固定的 1 小时/1 天图而冒充大范围分析。
4. 粒度由跨度、点数预算和后端能力决定，图表使用实际响应粒度。
5. 请求/实际粒度、请求/有效窗口、时区和数据状态可审计。
6. 空数据、缺少起始时间、跨边界和时区切换不会产生错误横轴或伪造 0 值。
7. 未指定时间范围的旧调用和历史报告保持兼容。
8. 代码实施完成后，专项测试、全量测试、lint、runtime contract 和 staged 验证全部通过，才允许进入部署审批。

## 8. 当前未决事项

1. 需要确认用户选择超过 1 天时是否始终保留两个辅助窗口，还是由报告类型配置开关控制。
2. 需要确认“最近一个季度/最近一年”产品语义采用滚动窗口还是自然日历窗口；实现时已通过 `mode` 明确区分，不能依赖标题猜测。

## 9. 非目标与安全边界

本方案不修改告警时间桶、故障诊断基线窗口或综述报告的独立粒度策略；这些模块应在后续统一时间窗口契约工作中单独评估。方案阶段不连接服务器、不制作部署包、不重启或部署远端服务。
