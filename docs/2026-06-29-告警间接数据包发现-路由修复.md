# 告警间接数据包发现 — 路由修复

> 日期：2026-06-29 | 关联：[告警间接数据包发现方案](./2026-06-29-告警间接数据包发现方案.md)

---

## 1. 测试场景

```
用户: 分析这个告警数据包 696902 1782716220 1782723420
```

预期行为：先查告警详情 → 发现是业务告警 → 间接发现嫌疑 IP → 给出数据包下载链接。

实际行为：AI 直接调 packet-analysis 的 `packetsPreview?id=696902` → 403 → 失败。

---

## 2. 根因

### 2.1 路由断点

[agents/openai.yaml](../skills/openclaw-napm-alert-query/agents/openai.yaml#L25) 的 boundary 规则：

```yaml
- 数据包, 报文, 抓包, pcap/cap, packetsDown, packetsPreview, DownServlet -> openclaw-napm-packet-analysis.
```

用户说"告警**数据包**"，关键词"数据包"命中此规则 → OpenClaw 直接跳到 packet-analysis，**跳过了 alert-query**。alert-query 的 indirect discovery 逻辑根本没被执行到。

### 2.2 对比

| 步骤 | 实际发生的（错误） | 应该发生的（正确） |
|------|-------------------|-------------------|
| 1 | packet-analysis: packetsPreview?id=696902 | alert-query: alertsDetail?eventids=696902 |
| 2 | 403 → 失败 | 获取告警详情 (linkType=1, group="HTTPS", categoryType=68) |
| 3 | — | shouldDiscover() → true |
| 4 | — | topValues(WebApplication→ClientIPs→IPAddress) |
| 5 | — | 返回 candidate IPs + suggestedPacketQuery |
| 6 | — | 用 candidate IPs 调 packet-analysis |
| 7 | AI 说"无权限" | AI 说"发现 X 个嫌疑 IP，可下载数据包" |

### 2.3 本质

不是代码逻辑问题（indirect discovery 代码正确），是 **OpenClaw 跨 skill sequencing 规则缺失**：

- alert-query → packet-analysis 的"先查告警、再发现 IP、最后抓包"链路没有被声明
- 用户提到的"数据包"关键词直接命中了 packet-analysis 的独占路由规则

---

## 3. 修复方案

### 3.1 修改 alert-query 的 agents/openai.yaml

在 boundary 规则中增加一条**优先级更高的规则**，明确"告警数据包"或"分析告警 <eventId> 的数据包"的 sequencing：

```yaml
Cross-skill sequencing for alert packet analysis:
- When the user says "告警数据包", "分析这个告警的数据包", "告警 <eventId> 的数据包",
  or any request that combines an alert event ID with packet analysis intent,
  OpenClaw MUST call this skill (alert-query) FIRST to get alert details and
  packetHandoff (which may include indirect discovery candidates for business/app alerts).
  Only after receiving the packetHandoff result should OpenClaw call
  openclaw-napm-packet-analysis with the candidate IPs or event IDs from packetHandoff.
- The packet skill's "数据包 -> packet-analysis" rule does NOT override this sequencing.
  "告警数据包" means "alert THEN packet", not "packet directly".
```

### 3.2 修改 packet-analysis 的 agents/openai.yaml

在 packet-analysis 的 routing 规则中增加一条回退规则：

```yaml
- If the user provides an alert event ID (numeric ID without IP addresses) and asks
  for packet analysis ("告警数据包", "分析告警 XXX 的数据包"), do NOT call this skill
  directly. Route to openclaw-napm-alert-query first to obtain alert details and
  packetHandoff candidates. Then call this skill with the resolved IPs or event IDs.
```

### 3.3 修改 alert-query 的 SKILL.md

在 Input Contract 的 modes 中补充 `packet_discovery` 使用场景说明。

## 4. 修改清单

| 文件 | 修改内容 |
|------|---------|
| `skills/openclaw-napm-alert-query/agents/openai.yaml` | boundary 中新增"告警数据包"跨 skill sequencing 规则（27-43行） |
| `skills/openclaw-napm-packet-analysis/agents/openai.yaml` | 新增 Alert event ID routing guard，告警 ID 场景回退到 alert-query（7-17行） |

### 4.1 alert-query agents/openai.yaml 实际修改

```yaml
# 新增: Critical cross-skill sequencing — "告警数据包" (alert packet)
- When the user says "告警数据包", "分析告警的数据包", "告警 <eventId> 的数据包",
  "分析这个告警数据包 <eventId>", or any request that combines an alert event ID
  with packet analysis intent, OpenClaw MUST call THIS skill FIRST (mode=detail or
  mode=detail_with_timeseries) to obtain alert details and packetHandoff.
- packetHandoff may contain:
    * Direct candidates (linkType=2 or IP-based) for immediate packet download
    * Indirect discovery candidates (business/app/group alerts where the skill
      automatically finds suspicious IP conversations via topValues)
- Only AFTER receiving the packetHandoff result should OpenClaw call
  openclaw-napm-packet-analysis with the resolved IPs or event IDs from the candidates.
- The packet skill's "数据包 -> packet-analysis" rule does NOT override this.
  "告警数据包" means "alert detail FIRST, then packet", not "packet directly".
```

同时保留了纯数据包场景（不涉及告警 ID）的路由到 packet-analysis 的规则。

### 4.2 packet-analysis agents/openai.yaml 实际修改

```yaml
# 新增: Alert event ID routing guard
- If the user provides an alert event ID (a numeric ID without IP addresses) and asks
  for packet analysis ("告警数据包", "分析告警 <id> 的数据包", "alert <id> packet"),
  do NOT call this skill directly with criteria.id.
- Instead, route to openclaw-napm-alert-query FIRST to obtain alert details and
  packetHandoff candidates (which may include indirect discovery results for
  business/app/group alerts where the alert group is not an IP address).
- Then call this skill with the resolved IPs or event IDs from the packetHandoff result.
```

### 4.3 alert-query SKILL.md 实际修改

在 Boundary 部分新增 "告警数据包" Cross-Skill Sequencing 章节：

```
Step 1: THIS skill (alert-query) FIRST → get alert detail + packetHandoff
Step 2: openclaw-napm-packet-analysis SECOND → use resolved IPs/event IDs
```

明确标注：DO NOT skip Step 1。

## 6. 第二轮测试：告警 696909（2026-06-29 16:13）

### 6.1 现象

```
用户: "分析这个告警数据包 696909 1782717000 1782724200"
AI: 先调 alert-query → 获取告警详情（安全事件，group="NetInsideNAPM"）
    → packetHandoff = null
    → AI 说 "告警详情中未自动带出数据包信息"
    → AI 绕过 null 结果，直接调 packet-analysis
    → packetsPreview 返回空 → 失败
```

### 6.2 根因

**路由修复生效了**（先走了 alert-query），但 AI 看到 `packetHandoff=null` 后自行决定绕过 skill 结果直接调 packet-analysis。

为什么 packetHandoff 是 null？

| 条件 | 结果 |
|------|------|
| linkType=2? | 否（安全事件告警通常是 linkType=1） |
| looksLikeIp("NetInsideNAPM")? | false |
| shouldDiscover()? | **false** — categoryType 不在 {14,25,63,68} 中 |

`securityAlerts` 告警的 `categoryType` 不在 `DISCOVERY_GROUP_CHAIN_MAP` 覆盖范围内。这是**正确的设计**——安全事件告警（尤其是平台自身测试告警）没有可发现的业务 IP 会话。null 就是正确答案。

### 6.3 修复

在两个 `agents/openai.yaml` 中新增 null 终止规则：

**alert-query 侧：**
```yaml
- If packetHandoff is null or has available=false, STOP. Do NOT call
  openclaw-napm-packet-analysis directly as a fallback. The null result IS the answer:
  this alert has no associated packet data and indirect discovery found no candidates.
```

**packet-analysis 侧：**
```yaml
- If alert-query returns packetHandoff=null or available=false, do NOT call this skill
  as a fallback. Alert-query's null result is authoritative.
```

## 7. 完整修复总结

三次迭代后，完整的"告警数据包"链路保护：

```
用户说"告警数据包 <eventId>"
  │
  ├─ Rule 1 (路由): 先调 alert-query，不直接调 packet-analysis  ← 第一轮修复
  │
  ├─ Rule 2 (执行): alert-query 获取详情 + 间接发现
  │     ├─ 直接路径 (linkType=2 或 IP) → 返回 candidates
  │     ├─ 间接发现 (categoryType∈{14,25,63,68}) → 返回 candidates
  │     └─ 无匹配 → 返回 null
  │
  └─ Rule 3 (终止): packetHandoff=null → STOP  ← 本次修复
        不准回退到 packet-analysis
        告诉用户: "该告警无可关联的数据包"
```

```
用户: "分析这个告警数据包 696902 1782716220 1782723420"
  │
  ├─ OpenClaw 识别: "告警数据包" → alert→packet sequencing
  │
  ├─ Step 1: 调用 openclaw-napm-alert-query (mode=detail, eventIds=["696902"])
  │     ├─ alertsDetail → 获取告警详情
  │     │   linkType=1, group="HTTPS", categoryType=68 (WebApplication)
  │     │   metrics=["UEII", "UEIO"], start=1782716220, end=1782723420
  │     │
  │     ├─ shouldDiscover() → true
  │     ├─ topValues(WebApplication→ClientIPs→IPAddress, topMetric=PGNPGE)
  │     └─ packetHandoff = {
  │           available: true,
  │           reason: "ALERT_INDIRECT_PACKET_VIA_DISCOVERY",
  │           candidates: [
  │             { rank: 1, ip: "x.x.x.x", suggestedPacketQuery: {...} },
  │             ...
  │           ]
  │         }
  │
  └─ Step 2: OpenClaw 渲染 narration + packetHandoff
        → "告警 696902 为业务告警(HTTPS)，
           发现 5 个嫌疑客户端 IP，可选择下载对应数据包：
           1. x.x.x.x → [下载数据包]
           2. y.y.y.y → [下载数据包]"
```
