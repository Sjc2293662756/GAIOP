# NAPM 混合查询架构设计方案

日期：2026-06-23
状态：待评审

---

## 1. 问题定义

### 1.1 现状

```
用户千变万化的问法
  → DeepSeek Chat LLM 完整构造 resolvedQuery（14s，错误率 40%+）
  → 插件自动修复 LLM 错误（9ms）
  → NAPM API 执行（0.7s）
  → LLM 生成中文叙述（2.8s）
────────────────────────────────────────────────
总耗时: 17.5s，其中 LLM 推理占 96%
```

### 1.2 核心矛盾

| | LLM | 规则引擎 |
|------|-----|---------|
| 理解千变万化的问法 | ✅ 擅长 | ❌ 正则匹配脆弱 |
| 精确映射到 metric code | ❌ 经常错（14s 还漏字段） | ✅ 9ms 零错误 |
| 时间范围计算 | ❌ 算错年份（2025 vs 2026） | ✅ Date.now() 永远不会错 |
| 补全必填字段 | ❌ 漏 queryModeKey/metrics/topMetric | ✅ 模板补齐 |

**LLM 擅长理解语义但不会精确构造；规则引擎擅长精确构造但不会理解语义。**

### 1.3 目标

- 简单查询（丢包排行、报错排行、流量排行等高频场景）：**< 5s**
- 复杂查询（综合分析、多指标对比等低频场景）：**< 10s**
- resolvedQuery 正确率：100%（规则引擎保证）

---

## 2. 架构设计

### 2.1 核心思路：LLM 只做语义实体提取，规则引擎做精确构造

```
                    用户输入："哪个地址丢包最厉害？"
                              │
              ┌───────────────┴───────────────┐
              │   Phase 1: 语义实体提取 (LLM)  │
              │   输入: 用户原始文本            │
              │   输出: 5个语义实体的 JSON       │
              │   耗时: ~1-2s                  │
              └───────────────┬───────────────┘
                              │
              ┌───────────────┴───────────────┐
              │   Phase 2: Query Construct (规则引擎) │
              │   输入: 语义实体 JSON           │
              │   输出: 完整的 resolvedQuery     │
              │   耗时: 9ms                    │
              └───────────────┬───────────────┘
                              │
              ┌───────────────┴───────────────┐
              │   Phase 3: NAPM Execution      │
              │   耗时: ~700ms                 │
              └───────────────┬───────────────┘
                              │
              ┌───────────────┴───────────────┐
              │   Phase 4: 中文叙述生成 (LLM)  │
              │   输入: 查询结果 + narrationContract │
              │   输出: 用户可读的中文回答       │
              │   耗时: ~2-3s                  │
              └───────────────────────────────┘

总耗时: 1-2s + 9ms + 0.7s + 2-3s ≈ 4-6s
```

### 2.2 为什么 Phase 1 只要 1-2s 而不是 14s？

Phase 1 只让 LLM 做 5 选 1 的分类任务（extraction），不是自由文本生成（generation）：

| | 当前（generation） | 优化后（extraction） |
|------|------|------|
| LLM 任务 | 完整构造 JSON，思考字段名、格式、时间戳 | 从预定义选项中选最匹配的标签 |
| 输出长度 | ~500 token（完整 resolvedQuery） | ~50 token（5 个枚举值） |
| 自由度 | 高（容易出错） | 低（受 schema 约束） |
| 推理深度 | 需要"会写 JSON" | 只需要"会分类" |

### 3.2 提取 Prompt（极致精简）

发给 LLM 的 prompt 只有 ~20 行，不是 78 行：

```
Extract 5 entities from the user's NAPM query. Return ONLY valid JSON, no explanation.

User query: "最近丢包最严重的IP是谁？"

Fill in each field using the candidates below. Use "unknown" if no candidate matches.

1. metricDomain: packet_loss | error_http | error_connection | traffic | latency | packet_count | connection | page_visits | retransmission
2. objectType: IPAddress | WebApplication | BusinessGroup | DefinedApp | Prefix24
3. queryMode: ranking | average | trend | inventory | overview
4. timeScope: last5minutes | last1hour | last24hours | last7days | last30days
5. topCount: 1 | 5 | 10 | 20

Return: {"metricDomain":"...","objectType":"...","queryMode":"...","timeScope":"...","topCount":...}
```

## 4. 规则映射引擎

### 4.1 Metric Domain → Metric Codes

```
packet_loss       → {metric: "PLI", metrics: ["PLI"], topMetric: "PLI"}
error_http        → {metric: "PGHTTP400", metrics: ["PGHTTP400","PGHTTP500"], topMetric: "PGHTTP400"}
                   + context: if objectType=WebApplication → default
                   + context: if objectType=BusinessGroup → error_connection
error_connection  → {metric: "RFCI", metrics: ["RFCI","RFCO"], topMetric: "RFCI"}
traffic           → {metric: "TPIO", metrics: ["TPIO"], topMetric: "TPIO"}
latency           → {metric: "TRTI", metrics: ["TRTI"], topMetric: "TRTI"}
                   + context: if objectType=WebApplication → "PGTME"
packet_count      → {metric: "PKIO", metrics: ["PKIO"], topMetric: "PKIO"}
connection        → {metric: "CONI", metrics: ["CONI","CCNI"], topMetric: "CONI"}
page_visits       → {metric: "PGNPGE", metrics: ["PGNPGE"], topMetric: "PGNPGE"}
retransmission    → {metric: "RTXI", metrics: ["RTXI","RTXO"], topMetric: "RTXI"}
```

### 4.2 Object Type → groups

```
IPAddress       → groups: [{type: "IPAddress"}]
WebApplication  → groups: [{type: "WebApplication"}]
BusinessGroup   → groups: [{type: "BusinessGroup"}]
DefinedApp      → groups: [{type: "DefinedApp"}]
Prefix24        → groups: [{type: "Prefix24"}]
```

### 4.3 Query Mode → Service + queryModeKey

```
ranking    → service: "topValues", queryModeKey: "topn"
average    → service: "averageValues", queryModeKey: "average"
trend      → service: "timeValues", queryModeKey: "timeseries"
inventory  → service: "groups", queryModeKey: "metadata"
overview   → service: "overview", queryModeKey: "overview"
```

### 4.4 Time Scope → Unix Timestamps

```
last5minutes → start: now-300, end: now
last1hour    → start: now-3600, end: now
last24hours  → start: now-86400, end: now
last7days    → start: now-604800, end: now
last30days   → start: now-2592000, end: now
```

所有时间戳由 `ResolvedQueryTimeRangeService` 生成，使用 `Date.now()` 并自动对齐到分钟边界。

### 4.5 完整映射示例

输入实体：
```json
{"metricDomain":"packet_loss","objectType":"IPAddress","queryMode":"ranking","timeScope":"last1hour","topCount":1}
```

输出 resolvedQuery：
```json
{
  "service": "topValues",
  "queryModeKey": "topn",
  "metric": "PLI",
  "metrics": ["PLI"],
  "topMetric": "PLI",
  "groups": [{"type": "IPAddress"}],
  "topCount": 1,
  "start": 1782205500,
  "end": 1782209100,
  "timeRange": {"key": "last1hour", "displayText": "最近1小时"},
  "format": "json",
  "userRequirement": "最近丢包最严重的IP是谁？",
  "semanticConstraints": {"operation": "rank_top", "targetObjectType": "IPAddress", "workflowType": "metric_topn"}
}
```

## 5. 多级回退策略

不是所有查询都能被实体提取覆盖。设计三层回退：

```
Level 1: 规则直通（无 LLM 参与）
  ├─ 触发条件: 正则匹配高频模板
  │   - "丢包 + IP + 最" → PLI + IPAddress + ranking
  │   - "报错 + 业务 + 最多" → PGHTTP400 + WebApplication + ranking
  │   - "流量 + IP + 排行" → TPIO + IPAddress + ranking
  ├─ 实现: resolveTopValuesPrompt() 直接用正则 + 别名表
  └─ 耗时: ~1s（全本地，无 LLM 参与）

Level 2: 实体提取 + 规则构造（本方案核心）
  ├─ 触发条件: Level 1 失败（queryMode 非 ranking 或 metricDomain 不明确）
  ├─ 实现: LLM 提取实体 → 规则引擎映射
  └─ 耗时: ~4-6s（LLM 提取 1-2s + 映射 9ms + API 0.7s + 叙述 2-3s）

Level 3: LLM 完整构造（兜底）
  ├─ 触发条件: Level 2 也失败（用户意图过于复杂/模糊）
  ├─ 实现: 当前流程（LLM 完整构造 resolvedQuery）
  ├─ 耗时: ~17s
  └─ 适用: 综合分析、多轮对话、自定义组合查询
```

## 7. 预期效果

### 7.1 耗时对比

| 场景 | 当前 | 优化后 | 改善 |
|------|------|--------|------|
| "丢包最严重的IP" (Level 1) | 10-17s | **~4s** | -73% |
| "哪个业务报错最多" (Level 2) | 6m20s (第一次) / 17s | **~5s** | -70% |
| "对丢包最严重的IP做综合分析" (Level 3) | 25-30s | 25-30s | — (兜底) |

### 7.2 正确率对比

| | 当前 | 优化后 |
|------|------|--------|
| resolvedQuery 完整性 | LLM 产出 60%+ 缺字段 | **规则引擎 100% 完整** |
| 指标映射正确率 | LLM 经常 PLI ↔ PGHTTP 混 | **规则引擎 100% 正确** |
| 时间戳正确率 | LLM 算错年份 (~20%) | **Date.now() 零错误** |

### 7.3 Level 命中分布预测

```
Level 1 (规则直通):  ~60% 查询  → ~4s
Level 2 (实体提取):  ~30% 查询  → ~5s
Level 3 (LLM兜底):   ~10% 查询  → ~17s

加权平均耗时: 0.6×4 + 0.3×5 + 0.1×17 ≈ 5.6s  (vs 当前 17s, 改善 67%)
```

## 8. 风险与应对

| 风险 | 概率 | 应对 |
|------|------|------|
| LLM 实体提取也耗时 >2s | 中 | 先用 Level 1 正则覆盖 60%，减少 LLM 调用次数 |
| 实体提取 prompt 太小，LLM 理解不准 | 中 | 保留 Level 3 兜底；提取失败时自动回退 |
| 高频模板覆盖不全 | 高 | 审计日志追踪 Level 2 命中，持续补充 Level 1 正则 |
| 同义词未在 candidates 中列出 | 中 | LLM 天然具有语义泛化能力，这是用 LLM 做提取而非正则的原因 |
