# NAPM 告警查询真实发送链路修复方案

> 后续验证状态（2026-08-19）：本方案已随 `1.1.0-rc.12` 部署，但真实企业微信测试证明其核心时序假设不成立。OpenClaw 会在 Agent 和 `napm-alert-query` 执行前调用普通 `reply_dispatch`，因此该 Hook 当时尚未持有当前轮告警结果，无法发送 canonical 文本。该问题仍未解决，现已暂缓修改；后续处理以《2026-08-19-NAPM告警查询前置直达发送暂缓记录》为准。

## 1. 问题现象

rc.11 部署后，用户在企业微信查询“最近一小时系统有哪些告警”，仍收到模型自由归纳的告警摘要。错误文本包含“按严重程度”“Top5”“代表性事件”“主要触发指标”等段落，没有按告警 Skill 契约展示完整七类告警和聚合明细。

这不是告警数据错误，也不是 `AlertNarrationContractService` 格式错误。rc.11 已经生成了正确文本，但没有把它送入企业微信真正使用的发送队列。

## 2. 远端证据

2026-08-19 11:40 的真实会话形成了完整差分证据：

1. `napm-alert-query` 在当前 `turnId` 中执行成功，告警总数为 207。
2. Tool 结果包含 1198 字符的 `narrationInput.displayText`，具备 `①` 至 `⑦`、空类别“无告警记录”和分类聚合明细。
3. 模型另外生成了 773 字符的自由摘要，包含 `Top5` 和“主要触发指标”。
4. `before_message_write` 执行确定性替换后，会话 JSONL 中保存的 assistant 消息是正确的 1198 字符文本。
5. 企业微信通道日志中的最终 payload 仍是模型生成的 773 字符文本，且与用户截图一致。
6. 当前轮没有出现 `message_sending` 的确定性交付事件。

因此，同一轮存在两份最终文本：会话转录正确，企业微信发送错误。

## 3. 根因

测试服务器使用 OpenClaw `2026.5.4`。该运行时中：

- `before_message_write` 的输入输出是 `AgentMessage`，作用于消息写入和会话转录；它不是企业微信最终发送队列的所有者。
- `message_sending` 虽然支持 `{ content, cancel }`，但当前 WeCom agent-final 链路没有触发该 Hook。
- `reply_dispatch` 提供原生 `ReplyDispatcher`，只有 `dispatcher.sendFinalReply()` 排队的 `ReplyPayload` 才能确定性进入当前企业微信发送链路。

rc.11 的单元测试和远端 Hook smoke 直接调用了 `message_sending` / `before_message_write` handler，并断言 handler 返回值正确。它们没有模拟 OpenClaw 的真实 `reply_dispatch` 和通道发送，因此只能证明函数行为，不能证明用户实际收到该文本，形成假阳性。

## 4. 修复方案

### 4.1 使用原生最终发送入口

在插件现有 `reply_dispatch` 中，报告处理之前检查当前轮普通告警结果：

1. 当前请求不是 tail dispatch、禁止发送或 suppressed delivery。
2. 当前会话和当前 `turnId` 均有效。
3. 记录来源严格为 `napm-alert-query`。
4. 记录属于当前轮、执行成功并符合告警 Skill schema。
5. 当前请求不是报告导出、综述报告或告警数据包复合流程。

全部满足时，以 `buildAlertQueryReply(record.result)` 取得 Skill 的 canonical `displayText`，调用：

```js
dispatcher.sendFinalReply({ text: canonicalText })
```

成功排队后返回：

```js
{
  handled: true,
  queuedFinal: true,
  counts
}
```

`handled: true` 阻止 OpenClaw 再把模型自由摘要送入默认通道。

### 4.2 单次交付

交付前通过 `ConversationOperationState.prepareFinalContent()` 固定当前轮文本，再用 `claimPreparedFinalDelivery()` 对 `conversationKey + turnId` 做一次性认领。

重复触发同一轮 `reply_dispatch` 时：

- 不再调用 `sendFinalReply()`；
- 返回 `handled: true, queuedFinal: false`；
- 记录 `napm_alert_duplicate_reply_dispatch_suppressed` 审计事件。

这同时避免默认模型文本在重复分支中泄漏。

### 4.3 保留兼容 Hook

- `before_message_write` 继续把会话转录改为 canonical 文本，使历史上下文与用户实际收到的内容一致。
- `message_sending` 保留为其他通道或旧运行时的兼容保护，但不再作为当前 WeCom 生产验收依据。
- 告警生产验收必须出现 `napm_alert_reply_dispatched`，且企业微信 final payload 与 canonical 文本一致。

## 5. 隔离边界

本修复只接管当前轮成功的普通 `napm-alert-query`：

- 无当前轮告警结果时不接管；
- 上一轮或其他会话的告警结果不接管；
- `napm-alert-packet-analysis` 保持现有复合流程；
- 报告和 Word/PDF 交付保持现有报告 `reply_dispatch`；
- `napm-skill-query`、巡检、综述、故障诊断和普通数据包输出不变。

## 6. 回归测试

新增真实 `ReplyDispatcher` 形状的测试，覆盖：

1. 当前轮告警 canonical 文本只调用一次 `sendFinalReply()`。
2. 重复 dispatch 被认领状态抑制。
3. 无当前轮告警结果不接管。
4. 上一轮告警结果不跨轮发送。
5. Word/报告请求不被普通告警文本抢占。
6. 既有报告交付、告警生命周期和 turn state 测试继续通过。

## 7. 发布验收

代码通过全量测试、lint 和运行时 Tool 契约后，升级为新的 rc 版本并按统一部署流程发布。远端验收不能只运行 Hook handler smoke，必须同时核对：

- Tool `displayText` 指纹；
- `napm_alert_reply_dispatched` 的 `conversationKey + turnId + fingerprint`；
- 企业微信最终 payload 文本指纹；
- 单轮只有一个 final payload 和一次 ACK。
