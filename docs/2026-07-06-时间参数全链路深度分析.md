## 一、问题背景

时间参数是 NAPM 系统中最核心的参数之一——它决定了查询哪个时间窗口的数据。但当前存在以下问题：

1. **LLM 计算时间戳不可靠**：年份错（2025 vs 2026）概率 ~30%，月日错概率 ~20%
2. **多层"覆盖"逻辑交织**：Plugin 层覆盖 → Skill 层校验修正 → 业务层再次解析
3. **多个时间字段并存**：`start/end`（root-level）、`timeRange.start/end`（嵌套）、`timeRange.key`（描述）、`resolutionHints.time`（来源标记）
4. **业务 Skill 各自有一套时间解析**：SummaryService、FaultDiagnosisService、Inspection 各自 `_resolveTimeRange`

本文档从头到尾追踪**一条完整的时间链路**，标出每个环节对时间参数做了什么操作。

## 三、每个 Stage 的时间处理逻辑

### Stage 1: LLM 构造 Tool Call

**文件**: 无（LLM 运行时行为），System Context 在 `napm-openclaw-plugin.remote.js` line 5235-5284

**LLM 看到的时间相关指令**（来自 `buildNapmRoutingSystemContext()`）:

```
Time contract: set `timeRange.key` to last1hour|last24hours|today|yesterday|last7days|last30days. 
The plugin computes start/end from the server clock automatically. 
Do NOT calculate or pass start/end timestamps — leave them empty.

Example: `{service:"topValues", timeRange:{key:"last1hour", displayText:"最近1小时"}}`. 
Do NOT pass start/end.
```

**Tool Definition 中的描述**（line 4582-4597）:

```javascript
start: {
  type: 'number',
  description: 'Auto-filled by plugin from timeRange.key. Do NOT calculate or fill this yourself.'
},
end: {
  type: 'number',
  description: 'Auto-filled by plugin from timeRange.key. Do NOT calculate or fill this yourself.'
},
timeRange: {
  type: 'object',
  description: 'REQUIRED: set key to last1hour|last24hours|today|yesterday|last7days|last30days. 
                Plugin auto-computes start/end from key. Do NOT set start/end yourself.',
  properties: {
    key: { type: 'string', description: 'last1hour|last24hours|today|yesterday|last7days|last30days' },
    displayText: { type: 'string' }
  }
}
```

**LLM 理论行为**:
- 从用户输入推断 timeRange.key（如 "最近1小时" → "last1hour"）
- 填入 `timeRange: { key: "last1hour", displayText: "最近1小时" }`
- **不填** `start` / `end`
- **不填** `timeRange.start` / `timeRange.end`

**LLM 实际可能行为**（混乱源 #1）:
- ✅ 正确：只传 key，不传 start/end
- ❌ 错误A：传了 key 但也自己算了 start/end（年份可能错）
- ❌ 错误B：没传 key，直接传了 start/end
- ❌ 错误C：把 start/end 放在 timeRange 下面而非 root-level
- ❌ 错误D：传了错误的 key（如把"今天"传成"last24hours"）

### Stage 2: before_tool_call Hook

**文件**: `napm-openclaw-plugin.remote.js`, line 5404-5701

**处理流程**:

```
1. 从 event.params 取 toolParams
2. buildCanonicalSkillToolParams(activePrompt, toolParams)
   └→ prepareSkillExecutionArgs(nextParams)
      └→ maybeAutoRepairResolvedQuery(prepared)  ← 关键！
         ├→ validateResolvedQueryAgainstSpec(prepared.resolvedQuery)
         │  ├─ 检查: root-level start/end 必须对齐 60 秒
         │  ├─ 检查: 不能只有 timeRange.start/end 没有 root-level start/end
         │  └─ 检查: relative_time_range_stale_or_miscalculated
         │
         └→ 如果 validation 失败且可自动修复:
            └→ buildResolvedQueryForPrompt(prompt)
               (调用 NapmResolvedQueryResolverService 重新构造 resolvedQuery)
```

**关键点**: 
- `validateResolvedQueryAgainstSpec` 在此阶段**只做校验，不修改时间值**
- 如果 LLM 在 `timeRange` 里传了 `start/end` 而 root-level 没有 → 直接 block
- 如果 root-level `start/end` 不对齐 60 秒 → 直接 block
- 如果 `relative_time_range_stale` → 尝试 auto-repair

**此时 `resolvedQuery` 中的时间字段状态**:
- 可能是 LLM 填的（如果有的话）
- 尚未被 Plugin 覆盖

### Stage 4: runSkillExecutor 【★主防线★】

**文件**: `napm-openclaw-plugin.remote.js`, line 2604-2648

这是**整个系统中最关键的时间处理点**。

```javascript
async function runSkillExecutor(args = {}) {
  // ...
  const payload = buildSkillPayload(preparedArgs);  // 组装 payload

  // ★★★ 时间覆盖逻辑 (line 2618-2648) ★★★
  if (isPlainObject(payload.resolvedQuery)) {
    const rq = payload.resolvedQuery;
    const needsTime = ['topValues','averageValues','timeValues','overview','topValues_multi_protocol'];
    
    if (needsTime.includes(String(rq.service || '').trim())) {
      const now = Math.floor(Date.now() / 1000);           // ① 取服务器当前时间(秒)
      const floor = (v) => Math.floor(v / 60) * 60;        // ② 分钟取整函数
      const timeKey = String(rq.timeRange?.key || '').trim() || 'last1hour';  // ③ 取key，默认last1hour

      let start, end;
      if (timeKey === 'today') {
        // 今日 00:00:00 ~ now
        const d = new Date(now * 1000); d.setHours(0,0,0,0);
        start = floor(d.getTime() / 1000);
        end = floor(now);
      } else if (timeKey === 'yesterday') {
        // 昨日 00:00:00 ~ 23:59:00
        const d = new Date(now * 1000); d.setDate(d.getDate() - 1); d.setHours(0,0,0,0);
        start = floor(d.getTime() / 1000);
        end = floor(start + 86340);
      } else {
        // 相对时间: now - duration ~ now
        const DURATION_MAP = {
          last5minutes: 300, last1hour: 3600, last24hours: 86400,
          last1day: 86400, last7days: 604800, last30days: 2592000
        };
        const duration = DURATION_MAP[timeKey] || 3600;
        start = floor(now - duration);
        end = floor(now);
      }

      rq.start = start;    // ④ 无条件覆盖！
      rq.end = end;        // ④ 无条件覆盖！
      if (!isPlainObject(rq.timeRange)) rq.timeRange = {};
      rq.timeRange.key = timeKey;  // ⑤ 确保 key 一致
    }
  }

  // 序列化 payload 为 JSON
  // spawn 子进程: node run_napm_query.js --payload '<json>'
  const { stdout, stderr } = await execFileAsync('node', [
    NAPM_SKILL_EXECUTOR, '--payload', JSON.stringify(payload)
  ], { ... });
}
```

**关键行为**:

| 行为 | 说明 |
|------|------|
| **无条件覆盖** | 不管 LLM 传了什么 start/end，一律用 `Date.now()` 重新计算 |
| **默认 last1hour** | 如果 LLM 没传 timeRange.key，默认 3600 秒 |
| **只对需要的 service** | 仅 topValues, averageValues, timeValues, overview, topValues_multi_protocol |
| **today 语义** | 今日 00:00:00 ~ 当前时刻，不是完整的一天 |
| **yesterday 语义** | 昨日 00:00:00 ~ 昨日 23:59:00（留最后 1 分钟缓冲） |

**潜在混乱点**:
- LLM 传的 `timeRange.key` 如果本身就错了（如"昨天"传了"today"），Plugin 会用错误 key 计算→查错时间窗口
- `custom` key 不在 DURATION_MAP 中 → 落到 default 3600s → 可能不是用户想要的

#### 5c. normalizeResolvedQueryTimeRange 【★第二道防线★】 (line 465)

```javascript
function normalizeResolvedQueryTimeRange(query = {}) {
  // ① floorToMinute — 二次确保分钟对齐
  if (Number.isFinite(Number(query.start)) && Number(query.start) > 0) {
    query.start = floorToMinute(query.start);
  }
  if (Number.isFinite(Number(query.end)) && Number(query.end) > 0) {
    query.end = floorToMinute(query.end);
  }

  // ② validateTimeRangeFreshness — 年份校验 + 400天容差
  if (Number.isFinite(Number(query.start)) && Number.isFinite(Number(query.end))) {
    const freshness = validateTimeRangeFreshness(query.start, query.end);
    if (!freshness.ok) {
      // ③ autoCorrectTimestampIfStale — 年份修正（保留月日时分秒）
      const correctedStart = autoCorrectTimestampIfStale(query.start);
      const correctedEnd = autoCorrectTimestampIfStale(query.end);
      
      // ④ 审计日志
      logAudit('napm_skill_time_range_stale_corrected', {
        originalStart: query.start,
        originalEnd: query.end,
        correctedStart,
        correctedEnd,
        issues: freshness.issues,
        serverTime: freshness.nowSeconds
      });
      
      query.start = correctedStart;
      query.end = correctedEnd;
    }
  }

  // ⑤ 删除嵌套的 timeRange.start/end（防止混淆）
  if (query.timeRange && typeof query.timeRange === 'object') {
    delete query.timeRange.start;
    delete query.timeRange.end;
  }
  
  // ⑥ 递归处理 discoveryQuery
  if (query.analysisPipeline?.discoveryQuery) {
    query.analysisPipeline.discoveryQuery = stripDiscoveryQueryExecutionTime(
      normalizeResolvedQueryTimeRange(query.analysisPipeline.discoveryQuery)
    );
  }
  
  // ⑦ 递归处理 protocolQueries
  if (Array.isArray(query.protocolQueries)) {
    query.protocolQueries = query.protocolQueries.map(...);
  }
  
  return query;
}
```

**关键行为**:

| 行为 | 说明 |
|------|------|
| `floorToMinute` | 二次确保分钟对齐（Plugin 已对齐过，但再做一次） |
| `validateTimeRangeFreshness` | 检查年份是否匹配（`isTimestampFresh`） |
| `autoCorrectTimestampIfStale` | **只修正年份**，保留月日时分秒 |
| 删除嵌套 start/end | 确保 `timeRange.start/end` 不存在，避免下游混淆 |
| 审计日志 | 记录每次修正 |

**`isTimestampFresh` 逻辑** (ResolvedQueryTimeRangeService.js line 173):

```javascript
function isTimestampFresh(timestamp, nowSeconds) {
  // ① 年份不匹配 → 直接判定为 false（不管距离多远）
  const tsYear = new Date(value * 1000).getFullYear();
  const nowYear = new Date(nowSeconds * 1000).getFullYear();
  if (tsYear !== nowYear) return false;
  
  // ② 同年但距离 > 400 天 → 也判定为 false
  return Math.abs(nowSeconds - value) <= MAX_TIMESTAMP_AGE_SECONDS; // 400天
}
```

**`autoCorrectTimestampIfStale` 逻辑** (line 204):

```javascript
function autoCorrectTimestampIfStale(timestamp, nowSeconds) {
  // ① 年份不匹配 → 替换年份为当前年
  if (tsDate.getFullYear() !== nowDate.getFullYear()) {
    tsDate.setFullYear(nowDate.getFullYear());
    return alignToMinute(Math.floor(tsDate.getTime() / 1000));
  }
  // ② 时间戳新鲜 → 原值返回
  if (isTimestampFresh(timestamp, nowSeconds)) return Number(timestamp);
  // ③ 距离太远（>400天且同年）→ 仍然修正年份
  tsDate.setFullYear(nowDate.getFullYear());
  return alignToMinute(Math.floor(tsDate.getTime() / 1000));
}
```

**重要**: `autoCorrectTimestampIfStale` 保留月日时分秒，只改年份。如果 LLM 算错了月份（如 6 月算成 3 月），此函数**无法修正**（因为同年月份错误仍在 400 天容差内）。

#### 8a. napm-summary → SummaryService._resolveTimeRange()

**文件**: `skills/openclaw-napm-summary/services/SummaryService.js`, line 1275

```javascript
_resolveTimeRange(input = {}, scope = {}) {
  const now = Math.floor(Date.now() / 1000);
  const MAX_PAST_SEC = 365 * 86400;  // 1 年边界

  let start = Number(input.start) || 0;
  let end = Number(input.end) || 0;

  // ★ Sanity check: 拒绝超过 1 年前或 1 天后的时间戳
  if (!start || start < now - MAX_PAST_SEC || start > now + 86400) {
    start = now - 86400;  // ← 默认 24 小时
  }
  if (!end || end < now - MAX_PAST_SEC || end > now + 86400) {
    end = now;             // ← 默认当前时间
  }
  return { start, end, displayText };
}
```

**注意**: Summary 不走 Plugin 的 runSkillExecutor 时间覆盖！它直接接收 LLM 传的 start/end。如果 LLM 传了错误时间戳，只能靠 sanity check 拦截。

## 五、混乱点分析

### 混乱点 #1: LLM 不一定遵守"不填 start/end"的指令

**现象**: 尽管 Tool Definition 和 System Context 都明确说 "Do NOT calculate or pass start/end"，LLM 有时仍会自行计算。

**原因**: LLM 的指令遵循不是 100%，特别是在复杂多轮对话中。

**影响**: 
- 如果 LLM 填了 start/end → Plugin 的 `runSkillExecutor` 会**无条件覆盖** → 没有实际影响
- 如果 LLM 填了 `timeRange.start/end` 而非 root-level → Plugin 的契约校验会**直接 block**

**当前缓解**: 
- Stage 4 无条件覆盖（最有效）
- Stage 3 契约校验阻止嵌套 start/end

### 混乱点 #2: "无条件覆盖"对 custom 和其他未知 key 的处理

**现象**: Plugin 的 DURATION_MAP 只包含 7 个 key:

```javascript
const DURATION_MAP = { 
  last5minutes: 300, last1hour: 3600, last24hours: 86400, 
  last1day: 86400, last7days: 604800, last30days: 2592000 
};
```

如果 LLM 传了不在此 Map 中的 key（如 `custom`、`last3days`）：
- `DURATION_MAP[timeKey]` → `undefined`
- `|| 3600` → 默认 1 小时
- 用户可能想要 3 天，结果只查了 1 小时

**影响**: 静默错误——没有报错，但结果不是用户想要的。

### 混乱点 #3: 业务 Skill 不走 Plugin 时间覆盖

**现象**: `napm-summary`、`napm-fault-diagnosis`、`napm-inspection` 等有自己的工具入口和独立的 `runXxxExecutor` 函数，不走 `runSkillExecutor`。

**具体**:
- `napm-summary` → `runSummaryExecutor`（line 2944）→ SummaryService 有独立的 `_resolveTimeRange`
- `napm-fault-diagnosis` → `runFaultDiagnosisExecutor` → FaultDiagnosisService 有独立的 `_resolveTimeRange`
- `napm-inspection` → `runInspectionExecutor` → 固定查最近 1 小时

**检查**: 这些入口有没有类似的时间覆盖逻辑？

查看 `runSummaryExecutor`:

```javascript
// line 2944
if (!criteria.start && !criteria.end && !hasEventIds) {
  const end = Math.floor(Date.now() / 1000 / 60) * 60;
  criteria.start = end - 3600;  // 默认 1 小时
}
```

查看 `runFaultDiagnosisExecutor` (line 3086):

```javascript
// 没有显式的时间覆盖！直接传 timeRange
```

**影响**: 这些 Skill 的 LLM 传入的 timeRange 没有经过 Plugin 层的时间覆盖，只有 Skill 内部的 sanity check。如果 LLM 传了错误时间戳，可能不会被修正。

### 混乱点 #4: 多个"默认时间"不一致

| 位置 | 默认时间 | 场景 |
|------|---------|------|
| Plugin runSkillExecutor | 3600s (1小时) | timeRange.key 为空或未知时 |
| run_napm_query normalizeResolvedQueryTimeRange | 不设默认，只修正已有值 | |
| SummaryService._resolveTimeRange | 86400s (24小时) | start 无效时 |
| FaultDiagnosisService._resolveTimeRange | 7200s (2小时) fault window / 86400s (24小时) 普通 |
| Inspection | 3600s (1小时) | 固定 |
| TimeUtils.parseTimeRange | 昨天 (yesterday) | 未知 timeRange 时 |

**影响**: 同一个"没指定时间"的查询，走不同 Skill 可能拿到不同时间窗口的数据。

### 混乱点 #5: autoCorrectTimestampIfStale 无法修正月份错误

**现象**: 如果 LLM 把 6 月 29 日算成了 3 月 12 日：

- 年份相同（2026）
- 距离当前时间: 约 109 天 < 400 天容差
- `isTimestampFresh` 返回 `true`
- **不会被修正**

**影响**: 静默错误——查的是 3 月份的数据而非 6 月份的。

### 混乱点 #6: today 语义的不一致

| 位置 | today 的 end | 说明 |
|------|-------------|------|
| Plugin runSkillExecutor | `floor(now)` | 当前时刻 |
| TimeUtils.parseTimeRange | `getDayEndExclusive(0)` = 明天 00:00 | 完整一天 |

**影响**: 不同代码路径对 "today" 的理解不同。

### 混乱点 #7: 远端时间戳传递时的序列化/反序列化

`runSkillExecutor` 中：
```javascript
const { stdout, stderr } = await execFileAsync('node', [
  NAPM_SKILL_EXECUTOR,
  '--payload',
  JSON.stringify(payload)   // ← resolvedQuery 序列化为 JSON 字符串
], { ... });
```

Skill 子进程中：
```javascript
const payload = parseJsonArg('--payload', args.payload) || {};
const resolvedQuery = input.resolvedQuery || {};
```

**潜在问题**: JSON 序列化/反序列化过程中，大整数（Unix 秒）不会丢失精度，因为 JavaScript number 可以安全表示到 2^53。Un*x 秒（10 位数）安全。

### 混乱点 #8: nowSeconds 的不一致

在不同校验函数中，`nowSeconds` 的获取方式：

- Plugin `runSkillExecutor`: `Math.floor(Date.now() / 1000)` — 直接在函数内计算
- `isTimestampFresh`: 参数传入，默认 `Math.floor(Date.now() / 1000)`
- `validateRelativeTimeRangeFreshness`: 通过 `options.nowSeconds` 传入
- `validateResolvedQueryAgainstSpec`: 通过 `getResolvedQueryValidationOptions` 传入

**影响**: 如果 `options.nowSeconds` 和实际的 `Date.now()` 不同（虽然通常一致），可能导致校验结果不一致。

## 六、谁在"覆盖"谁？覆盖关系总览

```
                    ┌──────────────────────────────┐
                    │     LLM 传入的时间参数         │
                    │  (timeRange.key / start/end)  │
                    └──────────────┬───────────────┘
                                   │
            ┌──────────────────────┼──────────────────────┐
            │                      ▼                      │
            │    ┌─────────────────────────────────┐      │
            │    │  Stage 2-3: 契约校验             │      │
            │    │  只校验，不修改时间值              │      │
            │    │  如果 timeRange 内有 start/end    │      │
            │    │  且 root-level 没有 → BLOCK       │      │
            │    └──────────────┬──────────────────┘      │
            │                   │ (通过校验)               │
            │                   ▼                         │
            │    ┌─────────────────────────────────┐      │
            │    │  Stage 4: Plugin 无条件覆盖 ★    │      │
            │    │  rq.start = computed_start       │      │
            │    │  rq.end = computed_end            │      │
            │    │  来源: Date.now()                 │      │
            │    │  覆盖范围: start/end (全部)        │      │
            │    └──────────────┬──────────────────┘      │
            │                   │                         │
            │                   ▼                         │
            │    ┌─────────────────────────────────┐      │
            │    │  Stage 6: Skill 修正 ★           │      │
            │    │  floorToMinute(start/end)         │      │
            │    │  autoCorrectTimestampIfStale      │      │
            │    │  来源: Date.now() (校验用)        │      │
            │    │  覆盖范围: 只修正异常的 start/end  │      │
            │    │  删除: timeRange.start/end        │      │
            │    └──────────────┬──────────────────┘      │
            │                   │                         │
            │                   ▼                         │
            │    ┌─────────────────────────────────┐      │
            │    │  Stage 8: 业务 Skill 各自处理    │      │
            │    │  Summary: sanity check + 默认24h  │      │

            │    │  Inspection: 固定 1h              │      │
            │    │  Alert: 精确窗口 / ±1天 / 7天    │      │
            │    └─────────────────────────────────┘      │
            └──────────────────────────────────────────────┘

覆盖强度:
  ★★★ Stage 4: 无条件覆盖 (主防线)
  ★★  Stage 6: 条件修正 (最后防线，只修异常值)
  ★    Stage 8: 各自 sanity check (业务防线)
```
