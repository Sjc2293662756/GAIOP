# NAPM 告警跨会话数据包分析引用封装方案

## 1. 文档信息

- 日期：2026-08-26
- 状态：告警引用主链路已完成生产部署（2026-08-26）；复制格式优化已完成本地回归，待发布
- 适用范围：NAPM Syslog 告警推送、OpenClaw 告警查询、告警关联数据包分析
- 目标：隐藏 `eventId/start/end` 等内部参数，同时保证跨会话、按告警指标、按单个数据包候选准确分析

## 2. 背景与问题

当前告警推送会把下面这类内部参数直接放到企业微信消息中：

```text
分析告警数据包 eventId=795097 start=1787647440 end=1787647680
```

这些字段对系统定位告警和数据包是必要的，但对用户不友好。更重要的是，告警推送进程与用户查询进程不一定属于同一个会话，不能依赖当前聊天上下文保存这些参数。

同时，数据包分析不能退化为通用的协议统计。告警中携带的指标、实际值、单位、阈值和严重级别必须继续传入数据包分析，并决定分析重点。例如“用户体验时间（服务器）”应重点检查服务端响应等待、TCP RTT、重传、HTTP 响应耗时和告警时间点附近的异常会话。

## 3. 方案概述

采用“短引用编号 + 共享告警档案 + 数据包候选分件号”的方式：

```text
告警推送
  -> 生成告警引用编号
  -> 将完整告警上下文写入共享存储
  -> 企业微信只展示用户可读信息和引用编号

用户在任意会话发送引用编号
  -> 从共享存储读取告警档案
  -> 还原事件、时间窗口、触发指标和分析画像
  -> 查找数据包候选
  -> 单候选自动分析，多候选要求用户选择
  -> 使用对应指标画像完成专项数据包分析
```

用户看到的示例：

~~~text
💬 深入分析

请复制下面这条指令发送给观枢AI：

```
分析告警 GJ-K7M4Q2
```
~~~

用户不需要看到或手工填写 `eventId`、Unix 时间戳、`suggestedPacketQuery` 等内部字段。

## 13. 生产部署与实测闭环

### 13.1 日志定位到的真实根因

- 企业微信推送来源是系统级 `napm-syslog-watcher.service`，不是用户级同名服务。
- 原部署脚本只检查 `systemctl --user`，系统级旧进程未被重启，因此继续发送旧格式。
- 重启旧进程后 journal 复现 `Cannot find module 'iconv-lite'`；该模块已加入顶层生产依赖。
- 依赖补齐后又复现 systemd `ProtectHome=read-only` 导致默认 HOME 状态目录 `ENOENT`；系统级服务与 Gateway 的默认共享目录统一为 `/dev/shm/napm-alert-references`。显式设置 `NAPM_ALERT_REFERENCE_DIR` 或 `alertReference.baseDir` 时仍可覆盖为主机持久化目录。

### 13.2 部署版本

- `1.1.0-rc.24`：原推送代码已部署，但系统级 watcher 未重启。
- `1.1.0-rc.27`：补齐系统级 watcher 控制、`iconv-lite` 依赖、运行目录适配和回退白名单；因 Gateway 插件仍固定旧目录，最终未作为闭环版本保留。
- `1.1.0-rc.28`：同步 Gateway 插件默认引用目录并完成最终部署；Git 提交 `f26ac73747e4a3fb9d6d39b12ed82cb163731fb4`。

### 13.3 实测证据

- 部署后系统 watcher：`MainPID=1894652`、`ActiveState=active`、`SubState=running`、工作目录无 `(deleted)`。
- Gateway：`ActiveState=active`、`SubState=running`，端口 18789 正常监听。
- journal 在 18:37:15、18:38:15 发现真实告警，并分别记录 18:37:20、18:38:18 已推送企业微信。
- 生产代码 stub 复现正文只展示 `告警引用：GJ-XLUN49AN` 和独立代码块 `分析告警 GJ-XLUN49AN`，未出现 `eventId`、`start`、`end` 或 `Event ID`。
- 独立 Gateway 进程输入 `分析告警 GJ-XLUN49AN` 成功还原：`eventId=795097`、数据包窗口 `1787647320~1787647560`、指标画像 `server_user_experience_time`，并保留“用户体验时间（服务器）=2311.6599 毫秒”和原触发条件。

### 13.4 运行注意事项

当前服务器未授予 `netinside` 修改系统级 systemd unit 的权限，安装器在服务运行时采用冻结并终止已核验 `netinside` watcher 主进程的方式触发 systemd 自动拉起。引用目录默认位于 `/dev/shm`，机器重启会清空；若要满足跨重启保留 7 天，应由管理员创建可写持久目录并设置 `NAPM_ALERT_REFERENCE_DIR` 或 `alertReference.baseDir`，再按完整发布流程验证。

## 4. 核心术语

### 4.1 告警引用编号

告警引用编号用于定位一条完整告警档案，例如：

```text
GJ-K7M4Q2
```

它是随机生成的业务引用码，不编码 `eventId`、IP 或时间戳，也不能从编号反推出内部参数。

### 4.2 数据包候选分件号

一个告警可能关联多个 IP 会话或数据包下载候选。候选分件号用于精确选择其中一个，例如：

```text
GJ-K7M4Q2-P1
GJ-K7M4Q2-P2
```

告警引用编号定位告警，分件号定位该告警下的一个具体数据包候选。

本文中的“单数据包”指一个明确的数据包下载候选或 pcap 文件。如果未来需要定位 pcap 内的单个报文帧，应另行增加帧级过滤能力。

### 4.3 告警指标分析画像

指标分析画像是由告警指标决定的专项分析规则，包含：

- 指标匹配规则；
- 需要提取的数据包证据；
- 重点检查的异常类型；
- 最终报告的叙述要求；
- 指标不支持时的降级边界。

## 5. 用户交互设计

### 5.1 告警推送内容

推送保留用户能理解的告警信息：

~~~text
⚠️ NAPM 告警通知

告警名称：告警推送应用测试1
严重级别：轻微
告警类别：应用性能告警
监控对象：回溯238web
指标：用户体验时间（服务器）=2311.6599毫秒

💬 深入分析
请复制下面这条指令发送给观枢AI：

```
分析告警 GJ-K7M4Q2
```
~~~

推送中隐藏：

- `eventId`；
- `start`、`end` Unix 时间戳；
- `suggestedPacketQuery`；
- 内部 API URL；
- 认证参数、Cookie、密码和 token。

### 5.2 用户请求形式

第一版支持以下表达：

```text
分析告警 GJ-K7M4Q2
分析 GJ-K7M4Q2
查看告警 GJ-K7M4Q2
分析 GJ-K7M4Q2-P1
继续分析 GJ-K7M4Q2-P1
```

引用编号应由确定性解析器优先识别，不交由模型自行猜测内部字段。

### 5.3 多候选交互

用户发送告警编号后，如果发现多个候选，系统先返回：

```text
该告警找到 2 个相关数据包，请选择：

1. GJ-K7M4Q2-P1
   客户端 10.1.1.10 -> 服务端 10.1.1.20

2. GJ-K7M4Q2-P2
   客户端 10.1.1.11 -> 服务端 10.1.1.20

请回复：分析 GJ-K7M4Q2-P1
```

系统不得在多个候选时无提示地默认选择第一个。

建议新增版本化结构，避免后续字段变化破坏旧引用：

```json
{
  "schemaVersion": 1,
  "referenceId": "GJ-K7M4Q2",
  "status": "PUSHED",
  "source": "syslog",
  "idempotencyKey": "event:795097",
  "alert": {
    "alertId": "120",
    "eventId": "795097",
    "name": "告警推送应用测试1",
    "category": "应用性能告警",
    "object": "回溯238web",
    "severity": "轻微",
    "start": 1787647440,
    "end": 1787647680,
    "linkType": 1,
    "categoryType": 68
  },
  "triggerMetrics": [
    {
      "code": "用户体验时间（服务器）",
      "label": "用户体验时间（服务器）",
      "value": 2311.6599,
      "unit": "毫秒",
      "condition": "用户体验时间（服务器） > 2000",
      "severity": "轻微"
    }
  ],
  "analysis": {
    "profileId": "server_user_experience_time",
    "profileVersion": 1,
    "focus": "服务端用户体验时间专项分析"
  },
  "packet": {
    "bufferSeconds": 120,
    "candidates": []
  },
  "createdAt": "2026-08-25T16:46:18+08:00",
  "updatedAt": "2026-08-25T16:46:18+08:00",
  "lastSeenAt": "2026-08-25T16:46:18+08:00",
  "expiresAt": "2026-09-01T16:46:18+08:00"
}
```

### 6.1 必须保存的内容

- 告警引用编号；
- 事件 ID 和告警规则 ID；
- 告警原始时间窗口；
- 告警名称、类别、对象和级别；
- 指标代码或名称、显示名称、实际值、单位；
- 触发条件；
- 指标分析画像；
- 数据包候选和候选状态；
- 创建、更新、最近收到和过期时间。

### 6.2 禁止保存的内容

- 明文密码；
- API Key、token、Cookie、Authorization；
- 未脱敏的数据包下载 URL；
- 完整 pcap 内容；
- 与分析无关的原始认证头。

数据包文件由数据包技能自己的存储策略管理，不嵌入告警档案。

## 7. 共享存储设计

### 7.1 存储抽象

新增独立的 `AlertReferenceStore`，上层不直接依赖具体存储介质，至少提供：

```text
put(record)
get(referenceId)
update(referenceId, patch)
findByEventId(eventId)
claim(referenceId, lease)
pruneExpired()
```

不直接复用报告源存储或工具调用上下文存储。它们的生命周期、权限边界和数据结构不同。

### 7.2 当前部署的实现建议

当前为单机多进程场景时，先使用共享目录下的 JSON 文件实现：

- 告警监听进程负责写入；
- OpenClaw 查询进程负责读取；
- 每条记录单独一个文件；
- 使用临时文件写入后原子改名；
- 文件和目录限制访问权限；
- 读写失败不能导致进程退出。

### 7.3 后续多实例实现

如果 Gateway 或 Syslog Watcher 扩展到多台机器或多个实例，将 `AlertReferenceStore` 替换为 Redis 或数据库适配器，保持上层接口不变。

### 7.4 过期与清理

默认保存策略：

```text
告警档案：7天
数据包候选：跟随告警档案，7天
下载的 pcap/cap 文件：24小时
分析结果摘要：7天
```

当前实现配置项：

```text
NAPM_ALERT_REFERENCE_DIR=<共享告警引用目录>
NAPM_ALERT_REFERENCE_TTL_MS=604800000
NAPM_ALERT_REFERENCE_MAX_ENTRIES=10000
ALERT_REFERENCE_PACKET_ARTIFACT_TTL_HOURS=24
```

兼容旧的数据包配置 `PACKET_RETENTION_HOURS`；当请求没有显式 `filePolicy.retentionHours` 时，优先使用 `ALERT_REFERENCE_PACKET_ARTIFACT_TTL_HOURS`，默认仍为 24 小时。告警档案和候选由 `AlertReferenceStore` 共享 JSON 目录保存，数据包文件继续由数据包 Skill 独立管理。

清理触发点：

1. 读取时发现过期，立即删除并返回过期提示；
2. 服务启动时执行一次清理；
3. 后台定时清理过期档案和数据包文件。

## 8. 编号生成与安全

### 8.1 编号格式

建议使用随机、不连续、不可反推的编号：

```text
GJ-K7M4Q2
```

编号不包含：

- eventId；
- Alert ID；
- IP 地址；
- Unix 时间戳；
- 告警名称的可逆编码。

多候选分件号可以使用：

```text
GJ-K7M4Q2-P1
```

其中父编号负责不可猜测性，`P1` 只表示候选序号。

### 8.2 访问边界

引用编号本质上是一个短期访问凭证，因此：

- 编号必须由安全随机源生成；
- 编号不能过短；
- 过期后不可恢复读取；
- 读取失败不返回内部事件信息；
- 访问和失败次数应写入审计日志；
- 如企业微信上下文能取得企业用户 ID，可增加用户绑定校验。

第一版如果无法取得稳定用户身份，则使用“高随机性 + 7天过期”作为主要保护措施。

## 9. 完整业务流程

### 9.1 告警推送流程

```text
Syslog 到达
  -> 解析告警
  -> 查询告警详情
  -> 提取事件、时间和触发指标
  -> 生成或复用告警引用编号
  -> 解析分析画像
  -> 写入共享存储
  -> 推送用户可读通知
```

如果没有可靠的事件 ID，不能生成可准确定位的分析编号，应只推送普通告警通知，并提示暂不支持深度定位。

### 9.2 用户首次分析流程

```text
用户发送“分析告警 GJ-K7M4Q2”
  -> 解析引用编号
  -> 从共享存储读取档案
  -> 校验存在、未过期、状态可分析
  -> 使用事件 ID、时间窗口、触发指标查询告警详情
  -> 执行关联数据包发现
```

结果分三类：

- 无候选：告知当前没有可分析数据包；
- 一个候选：进入数据包预览和分析；
- 多个候选：保存候选并要求用户选择分件号。

### 9.3 指定分件分析流程

```text
用户发送“分析 GJ-K7M4Q2-P1”
  -> 读取父告警档案和 P1 候选
  -> 恢复 P1 的结构化 packetQuery
  -> 强制覆盖告警的权威时间窗口
  -> 透传指标分析画像
  -> 执行 preview
  -> 根据风险决定下载或请求确认
  -> 下载并执行 tshark/capinfos
  -> 提取指标相关证据
  -> 输出专项根因分析
```

用户不能通过修改提示词覆盖档案中的 eventId、时间窗口或候选 IP。

## 10. 单候选与多候选规则

### 10.1 单候选

只有一个可信候选时可以自动分析。

### 10.2 多候选

多候选时必须先返回列表，不自动下载所有候选，也不默认选择第一个。

### 10.3 候选状态

每个候选建议维护：

```text
DISCOVERED
SELECTED
PREVIEW_PENDING
ANALYZING
COMPLETED
FAILED
EXPIRED
```

候选的 `packetQuery` 只保存结构化条件，例如 IP、时间、业务页面和分析选项，不保存带认证参数的完整 URL。实际 URL 由数据包技能在运行时生成。

## 11. 指标专项分析设计

### 11.1 指标解析优先级

画像匹配按以下顺序执行：

1. 指标代码；
2. 标准指标名称；
3. 中文显示名称和别名；
4. 未匹配时使用未知指标画像。

不能仅根据告警名称猜测指标类型。

### 11.2 第一版画像

| 画像 | 重点证据 |
| --- | --- |
| `server_user_experience_time` | 服务端响应等待、HTTP 响应耗时、TCP RTT、重传、异常会话 |
| `network_user_experience_time` | RTT、重传、丢包、方向、异常时间点 |
| `page_load_time` | DNS、TCP、TLS、HTTP、首字节和页面请求链 |
| `http_error_rate` | HTTP 4xx/5xx、请求 URL、服务端响应和关联会话 |
| `tcp_retransmission` | 重传次数、重传时间点、关联 TCP 会话 |
| `network_latency` | RTT 分布、客户端/服务端方向和高延迟会话 |

### 11.3 “用户体验时间（服务器）”画像

该画像必须围绕以下问题组织结果：

1. 指标实际值是否超过阈值；
2. 告警时间段内是否存在服务端响应等待升高；
3. 是否存在 TCP RTT、重传或连接建立异常；
4. 是否能定位到具体 IP 会话和时间点；
5. 数据包证据是否与告警时间窗口一致；
6. 哪些证据支持或不支持“服务端响应变慢”的判断。

最终结果不能只返回协议分布。必须返回指标相关的证据状态：

```json
{
  "alertEvidence": {
    "profileId": "server_user_experience_time",
    "metric": "用户体验时间（服务器）",
    "actualValue": 2311.6599,
    "threshold": 2000,
    "relatedSessions": [],
    "timelineFindings": [],
    "evidenceStatus": "SUPPORTED"
  }
}
```

`evidenceStatus` 至少支持：

```text
SUPPORTED
PARTIAL
NOT_CAPTURED
UNSUPPORTED_PROFILE
```

### 11.4 未知指标处理

如果指标没有画像，不能伪装成完成了专项分析：

```text
已定位告警数据包，但当前未配置该指标的专项分析规则。
已保留通用网络证据，无法对该指标给出完整根因判断。
```

通用协议统计只能作为辅助信息，不能替代专项结论。

## 12. 状态机与幂等

告警档案状态建议为：

```text
PUSHED
RESOLVING
CANDIDATES_READY
CANDIDATE_SELECTED
PREVIEW_PENDING
ANALYZING
COMPLETED
EXPIRED
ALERT_DETAIL_NOT_VISIBLE
NO_PACKET_CANDIDATE
PACKET_ANALYSIS_FAILED
```

重复处理规则：

- 使用 `eventId + alertId` 作为幂等键；
- 同一事件7天内重复推送时复用原编号；
- 更新最新指标值、告警结束时间和 `lastSeenAt`；
- 已有完成结果时重复请求直接复用结果；
- 正在分析时使用短租约，阻止重复下载；
- 租约失效后允许下一次请求接管。

## 13. 异常提示

### 编号不存在

```text
没有找到告警编号 GJ-K7M4Q2，请检查编号是否完整。
```

### 编号过期

```text
告警编号 GJ-K7M4Q2 已过期，无法继续定位数据包。
```

### 告警详情未同步

```text
告警已收到，但详细事件还未同步完成，请稍后重新分析。
```

### 没有数据包

```text
已找到告警，但当前没有可分析的数据包。
```

### 多个数据包

```text
已找到多个候选数据包，请先选择一个分件号。
```

### 数据包风险过高

```text
已找到目标数据包，但预计文件较大，需要先缩小时间范围或确认下载。
```

## 14. 安全与隐私要求

- 用户通知不展示 `eventId/start/end` 等内部定位字段；
- 共享档案不保存密码、token、Cookie 和未脱敏 URL；
- 日志中只记录引用编号、哈希化范围和状态，不记录认证信息；
- 数据包下载 URL 继续由运行环境注入认证并在展示时脱敏；
- 引用编号过期后删除或不可读；
- 文件存储目录限制访问权限；
- 不使用零宽字符、HTML 注释或 Base64 将参数藏进用户文本；
- 不允许用户提示词覆盖档案中的权威时间和候选条件。

## 15. 测试规划

### 15.1 存储测试

- 推送进程写入后，独立进程可以读取；
- 原子写入不会产生半截 JSON；
- 过期后读取失败并清理；
- 同一事件重复写入返回同一个引用编号；
- 记录达到上限后按策略清理旧记录；
- 并发读取和更新不会破坏状态。

### 15.2 通知测试

- 通知中不出现 `eventId`、`start`、`end`；
- 通知包含告警名称、级别、对象、指标和引用编号；
- 通知不出现密码、token、Cookie 或内部下载 URL；
- 没有可靠事件 ID 时不生成虚假的分析编号。

### 15.3 跨会话测试

- 进程 A 推送，进程 B 查询；
- 不依赖会话上下文仍能还原完整参数；
- 查询会话与推送会话完全不同仍能完成分析；
- `/new` 或新会话不会影响已保存引用。

### 15.4 候选测试

- 单候选自动分析；
- 多候选不自动选第一个；
- `-P1` 只分析 P1；
- 不存在的分件号不能读取其他候选；
- 候选过期后不能继续下载。

### 15.5 指标专项测试

- “用户体验时间（服务器）”匹配正确画像；
- 指标值、单位、阈值和级别完整透传；
- 分析结果包含 `alertEvidence`；
- 缺少服务端证据时返回 `NOT_CAPTURED` 或 `PARTIAL`，不编造结论；
- 未知指标返回 `UNSUPPORTED_PROFILE`，不伪装成专项分析完成。

### 15.6 数据包安全测试

- 结构化 packetQuery 不包含密码和 token；
- 生成的 URL 认证参数只在运行时注入；
- 用户回复不能覆盖权威时间、IP 或候选条件；
- 重复分析请求不会重复下载相同数据包。

使用一条真实测试告警验证：

```text
1. Syslog 收到告警

3. 在新会话发送“分析告警 GJ-xxxxxx”
```

## 19. 结论

本方案的关键不是把专业参数藏到一段文本中，而是建立一条独立的、跨会话的告警引用链：

```text
告警引用编号
  -> 完整告警档案
  -> 告警指标分析画像
  -> 数据包候选分件号
  -> 单候选数据包分析
  -> 指标相关证据和根因结论
```

这样可以同时满足：

- 用户不需要看到或输入专业参数；
- 告警推送和查询可以跨会话、跨进程；
- 数据包分析不会丢失告警指标上下文；
- 多数据包时不会误选错误对象；
- 引用和数据包都有明确的保存和过期策略；
- 后续可以从单机文件存储平滑升级到 Redis 或数据库。
