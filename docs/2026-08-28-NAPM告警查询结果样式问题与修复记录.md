# NAPM 告警查询结果样式问题与修复记录

## 1. 用户现象

企业微信查询“最近一天/最近三天系统有哪些告警”时，分类汇总行例如：

```text
网络性能告警 — 8 条（🔴 2 / 🟠 4 / 🟢 2）
```

没有像告警名称行一样明显加粗。此前 `v1.1.0-rc.33` 已把分类汇总行包在 `**...**` 中，但真实截图中该行仍接近普通正文，`# 告警名称...` 行反而更醒目。截图还暴露出长结果中分类汇总、告警名称和告警明细的视觉层级不一致。

## 2. 样式由谁决定

告警样式不是由企业微信数据接口决定，而是由三层共同决定：

1. `skills/openclaw-napm-alert-query/services/AlertNarrationContractService.js` 生成 Skill 的 canonical `narrationInput.displayText`，决定内容、顺序、字段和 Markdown 标记。
2. `napm-openclaw-plugin.remote.js` 在生产链路优先透传 `displayText`；只有 Skill 缺少该字段时，才调用插件兼容 formatter。
3. OpenClaw/企业微信通道负责把文本 Markdown 渲染成最终视觉样式。该通道对行内 `**...**` 的呈现层级弱于 `#` 标题，因此“源码已加粗”不等于“所见足够突出”。

`reply_dispatch` 负责当前轮确定性文本进入企业微信发送队列，`before_message_write` 负责会话转录一致性；二者不应重新组织告警事实。

## 3. 已解决问题

- 告警摘要由 Skill 生成确定性 `displayText`，插件和模型不再自由改写。
- 普通 summary、timeline、detail、通知字段等结果统一经过告警 Tool 契约交付。
- 分类统计包含总数和紧急/重大/轻微数量。
- 告警按类别、名称和严重程度聚合；对象、触发次数、持续时长和开始时间有固定格式。
- 空类别可显示“无告警记录”，多条结果按分隔线拆开，避免混成一段。
- 当前轮通过 `reply_dispatch` 单次交付 canonical 文本，避免模型答案重复或覆盖。
- `v1.1.0-rc.33` 已验证统计字段和 `**...**` 标记存在，排除了旧版本未生效、数据错误和旧 Gateway 进程等原因。

## 4. 本次修复前仍未解决的问题

- 仅使用行内 `**...**` 时，企业微信所见层级仍不够醒目。
- canonical formatter 与插件 fallback formatter 分别维护，存在格式漂移风险。
- fallback 只展示有告警的类别，严重程度统计还单独占一行，与 canonical 的七类完整展示规则不完全一致。
- 缺少真实企业微信渲染快照回归，单元测试只能验证原始文本标记。

## 5. 复现路径与证据

### 本地确定性复现

```powershell
npm test -- --runInBand --silent test/alert-query-services.test.js test/napm-openclaw-plugin-alert-query.test.js
```

在修复前，canonical 输出包含：

```text
**① 网络性能告警 — 8 条（🔴 1 / 🟠 0 / 🟢 0）**
```

但插件 fallback 输出没有同样的严重程度内联统计，且两者都不是标题行。修复测试把预期收紧为：

```text
# **① 网络性能告警 — 8 条（🔴 1 / 🟠 0 / 🟢 0）**
```

同时断言不能退化回仅有 `**...**` 的行。

### 真实链路复现

使用企业微信提出最近一天或最近三天的全量告警查询，核对三份证据：

1. Tool 结果中的 `narrationInput.displayText`。
2. `napm_alert_reply_dispatched` 对应的最终发送文本。
3. 企业微信实际截图。

rc.33 的前两份证据已经包含完整统计，只有第三份的视觉强调不足，因此根因在通道 Markdown 呈现层级，不在查询或聚合数据。

## 6. 根因结论

已确认根因是“行内加粗标记与企业微信标题渲染层级不一致”，并由两套 formatter 放大了维护风险。解决方案不是继续让模型提示自己加粗，而是让确定性 formatter 输出通道兼容的标题结构。

## 7. 本次实施修改

- 新增 `skills/openclaw-napm-alert-query/services/AlertDisplayFormatService.js`，集中生成分类汇总标题。
- canonical formatter 的有告警、空类别和“其他告警”分支统一输出 `# **...**`，包括序号、类别、总数和严重程度统计。
- 插件 fallback 复用同一 formatter，并把严重程度统计放回分类汇总行，避免同类结果拆成两种格式。
- `SKILL.md` 明确 `# **...**` 是分类汇总行契约：`#` 用于有限 Markdown 通道的行级层级，`**...**` 保留标准 Markdown 加粗语义。
- 回归测试覆盖 canonical 和 plugin fallback，确保不退化为仅行内加粗。

## 8. 稳定输出契约

summary 查询的分类汇总行必须满足：

```text
# **① 网络性能告警 — 412 条（🔴 157 / 🟠 114 / 🟢 141）**
```

并遵循以下规则：

- Skill 生成 `displayText`，模型原样返回，禁止总结、重排或翻译。
- 默认查询展示七个固定类别；零条类别紧随标题显示“无告警记录”。
- 类别内按“告警名称 + 严重程度”聚合，明细最多展示保留的聚合概览。
- 插件只在缺少 `displayText` 时兜底，且必须复用 `AlertDisplayFormatService`。
- 真实发送必须由当前轮 `reply_dispatch` 交付；不能用历史结果推断当前轮内容。

## 9. 验证状态与剩余事项

本次代码修改后的定向告警测试已通过（32 tests）。全量 Jest 已通过 100 个套件、806 项测试；`npm run lint`、`npm run verify:runtime-contract`、三个相关 JS 的 `node --check` 和 `git diff --check` 均通过。新版本发布包尚未构建。

`v1.1.0-rc.33` 仍是当前已部署版本；本次 `# **...**` 修复尚未部署远端，也未重启服务。剩余验收是生成新的 release candidate 后，在企业微信完成至少一条全量告警查询截图核对，确认分类汇总行视觉上明显高于正文且没有重复、截断或字段错位。
