## 3. 复审阻断一：伪造结构化分类可能选择错误 Tool

### 3.1 复现路径

直接调用 `resolveTurnIntent()`，传入：

- `route=napm_candidate`；
- 与正式契约相同的 `schemaVersion`；
- 与正式契约相同的 `source`；
- 手工构造并冻结的 `workflow/signals/facts`；
- `signals.alert=true`。

修复前，该对象虽然不是 `DomainIntentClassificationAdapter` 的真实产物，仍会被识别成告警意图并选择 `napm-alert-query`。

### 3.2 影响范围

- `TurnIntentResolver` 的信任边界不完整；
- 内部误用或伪造对象可能让公共门禁选择错误 Tool；
- 文档宣称“只接受 Adapter 产物”，实际实现却只检查版本字符串。

### 3.3 根因

Resolver 只校验 `classification.schemaVersion`，没有同时确认：

1. 对象是否由当前进程中的 Adapter 实际签发；
2. `source` 是否一致；
3. 外层对象及 `workflow/signals/facts` 是否均不可修改。

### 3.4 修复

- `DomainIntentClassificationAdapter` 使用模块私有 `WeakSet` 记录真实签发对象；
- 新增 `isDomainIntentClassification()`，统一检查：
  - 真实签发身份；
  - `schemaVersion`；
  - `source`；
  - 外层对象冻结状态；
  - `workflow/signals/facts` 冻结状态；
- `TurnIntentResolver` 只接受上述检查通过的对象；
- 缺失、复制、伪造或可变的分类对象不会选择任何 NAPM Tool，而是安全返回 `MODEL_OWNED`。

### 3.5 回归测试

新增测试使用“版本、来源、冻结状态看起来都正确，但不是 Adapter 签发”的对象。测试先稳定复现错误路由，再验证修复后结果为：

- `intentType=model_owned`；
- `handling=model_owned`；
- `expectedTool=null`。

## 4. 复审阻断二：平台身份快路径没有 Turn Admission Decision

### 4.1 复现路径

通过真实插件生命周期发送“你是谁？”：

1. 执行 `message_received`；
2. 读取当前 run/message 的 Guard State；
3. 检查 `turnAdmissionDecision`。

修复前，平台身份分支从 `buildConversationScopedGuardState()` 提前返回，`turnAdmissionDecision` 为 `undefined`。随后审计仍记录 `turn_admission_decided`，但 route、action、expectedTool、分类来源等字段为空。

### 4.2 影响范围

- “每个 run/message 都有不可变准入决定”的整体契约不成立；
- 身份轮形成公共门禁旁路；
- 审计事件名称与实际状态不一致。

### 4.3 根因

平台身份识别后直接返回 Guard State，没有经过：

- `TurnIntentResolver`；
- `TurnAdmissionCoordinator`；
- 分类版本和来源写入。

### 4.4 修复

- 删除平台身份分支的提前返回；
- 平台身份仍由既有分类器识别，但继续经过统一 Turn Intent 和 Turn Admission 流程；
- 最终生成：
  - `route=model_owned`；
  - `action=MODEL_OWNED`；
  - `intentType=model_owned`；
  - `handling=model_owned`；
  - `expectedTool=null`；
  - 完整 `classificationSchemaVersion/classificationSource`；
- 既有身份回答行为和“禁止调用 NAPM Tool”规则保持不变。

### 4.5 回归测试

新增真实 `message_received` 生命周期测试，验证平台身份轮：

- Decision 绑定当前 conversation、turn 和 run；
- Decision 为不可变对象；
- route/action/handling/intentType 明确；
- Tool 为空；
- 分类 schema/source 完整；
- 既有身份问题、身份后普通问题和身份轮 Tool 阻断测试继续通过。

## 10. 追加 P1：非关键词对象名恢复 Draft 后没有重建准入

### 10.1 现场差异

既有测试使用 `HTTP` 作为澄清回答。`HTTP` 本身会命中 NAPM 相关语义，因此 `buildConversationScopedGuardState()` 偶然生成可执行 Query Decision，掩盖了续答准入没有正式重建的问题。

当回答换成不含系统关键词的合法应用名“支付平台”时：

1. `QueryTurnCoordinator.resumePending()` 成功恢复并补全 Draft；
2. `turnPolicy` 被覆盖为 NAPM；
3. `turnAdmissionDecision` 却仍来自对“支付平台”短句的初始分类，保持 `MODEL_OWNED`；
4. `before_tool_call` 无法把 Query Tool 调用密封到可信 trace；
5. 返回 `TURN_ADMISSION_AUTHORIZATION_REQUIRED`，查询没有执行。

### 10.2 红灯复现

新增真实插件生命周期测试，不手工构造完整续查 Query：

1. “最近 7 天应用流量趋势如何？”进入正式 `CLARIFICATION`；
2. 校验 pending Draft 已由 Policy 规范化成缺少 argument 的 `DefinedApp`；
3. 新 run 只发送“支付平台”；
4. 断言本轮 Decision 应为 `EXECUTE_TOOL + napm-skill-query`。

修复前测试稳定失败，实际 Decision 为：

- `route=model_owned`；
- `action=MODEL_OWNED`；
- `expectedTool=null`；
- `reasonCode=semantic_model_fallback`。

### 10.3 根因

`message_received` 在 `resumedTurn` 存在时只覆盖 `turnPolicy`、`pendingQueryDraft`、父轮次和语义问题，没有覆盖 `turnIntent` 与 `turnAdmissionDecision`。后续 Hook 和 direct execute 正确执行了门禁，但看到的是旧 Decision，因此按设计拒绝。

### 10.4 修复方式

- 新增内部 `buildResumedQueryAdmissionState()`；
- 仅在 `resumePending()` 成功返回权威 Query Turn 时调用；
- 为新的 conversation/turn/run/message 生成不可变：
  - `intentType=query`；
  - `handling=single_tool`；
  - `route=napm_candidate`；
  - `action=EXECUTE_TOOL`；
  - `expectedTool=napm-skill-query`；
  - `workflow=query_clarification_continuation`；
  - `reasonCode=QUERY_CLARIFICATION_RESUMED`；
- 保留分类 schema/source；
- 不把短回答重新交给跨 Skill 序号选择解析器，pending Query 恢复本身就是本轮唯一权威来源。

### 10.5 正反回归

正向测试：有正式 pending 时仅回复“支付平台”，插件恢复 Draft、补入 `DefinedApp.argument=支付平台`、生成新 Decision，Query Hook 和 execute 通过，并且南向只调用一次。

反向测试：没有 pending 时直接发送“支付平台”并尝试 `clarificationAnswer`，本轮保持 `MODEL_OWNED`，Tool 在 Skill、Client 和南向调用前阻断，南向调用次数为 0。

完整 Query Turn 生命周期套件当前为 51 项，全部通过；全量测试为 116 个套件、1043 项，全部通过。lint、8 Tool runtime contract、差异和语法门禁也已再次通过。
