# NAPM 单对象综述目标丢失与故障报告降级修复方案

## 1. 问题背景

2026-08-20 企业微信真实请求：

```text
给我回溯238web的综述报告！
```

实际生成并发送：

```text
napm_全局综述报告_20260820_174428.docx
```

测试服务器日志确认，请求进入 `napm-summary` 后从 `TotalTraffic` 全局计划开始，最终 `reportType=summary_report`、报告 ID 为全局综述。企业微信只是按插件提供的文件路径发送附件，不是通道改名或显示错误。

## 2. 影响范围

| 场景 | 当前行为 | 影响判定 |
| --- | --- | --- |
| 单个业务综述 | 退化为全局或业务整体综述 | 确定受影响 |
| 单个应用综述 | 退化为应用整体综述 | 确定受影响 |
| 业务故障分析报告 | 正常目录下可选择 BS 模板；目录失败后 target 为空 | 存在独立降级风险 |
| 应用故障分析报告 | 正常目录下可选择 CS 模板；目录失败时可能误选 BS 模板 | 存在独立降级风险 |

## 3. 根因

### 3.1 自动综述入口丢失具体对象

`buildAutomaticSummaryToolArgs()` 只从场景词推导 `scope.type`，没有解析和传递 `scope.target`。

`SummaryService` 的正式契约根据以下字段区分维度整体和单对象：

```json
{
  "scope": {
    "type": "webApplication",
    "label": "业务",
    "target": {
      "groupType": "WebApplication",
      "groupArgument": "回溯238web",
      "groupLabel": "回溯238web"
    }
  }
}
```

缺少 `target` 时，Summary Skill 会按设计执行维度整体计划；这不是 Summary Skill 内部错误。

### 3.2 命名请求没有失败闭合

旧入口无法确认对象时仍继续调用 `napm-summary`，使“单对象解析失败”静默变成“整体报告成功”，用户收到内容正确但对象范围错误的 Word。

### 3.3 故障诊断目录失败后错误回退

`FaultDiagnosisService` 正常情况下通过 applications 目录决定类型：Type=3 为 WebApplication/BS，Type=2 为 DefinedApp/CS。目录不可用或对象未命中时，旧逻辑回退关键词分类并允许 `target=null` 继续执行。

`HTTPS应用故障分析报告` 在该回退路径中会因 `HTTPS` 包含 `http` 而先命中 BS 关键词，生成错误类型报告。

## 4. 设计原则

1. 报告分类器只决定巡检、综述、故障等工作流，不猜具体对象。
2. 具体对象必须由 NAPM 动态目录确认，不能由名称风格或模型猜测决定类型。
3. 命名对象请求解析失败时禁止降级为整体或全局报告。
4. 正常的系统全局、业务整体、应用整体综述继续允许不带 `scope.target`。
5. 巡检、告警、普通查询和现有附件交付链路不进入本次修改范围。

## 5. 解决方案

### 5.1 共享对象解析服务

新增 `skills/shared/NapmObjectTargetResolver.js`，输出以下稳定状态：

```text
overall
resolved
target_not_found
target_ambiguous
catalog_unavailable
```

解析策略：

- 通过 `NapmMetadataService.listObjectInstances()` 读取 WebApplication 和 DefinedApp 实时目录。
- 使用用户原句与真实目录名称匹配，名称最长的精确目录项优先。
- 显式“业务/应用”只用于同名对象消歧，最终类型仍以目录为准。
- 文本清理只用于判断请求是否包含潜在命名对象，不用于凭空构造对象。
- 对象不存在、同名歧义或目录不可用时返回失败状态。

### 5.2 自动综述入口

`runAutomaticSummaryReportDelivery()` 在调用工具前执行对象解析：

```text
ReportIntentClassifier
  -> NapmObjectTargetResolver
  -> buildAutomaticSummaryToolArgs(prompt, resolvedScope)
  -> napm-summary
  -> napm-report-export
```

命名对象解析失败时直接返回确定性提示，不调用 summary 和 export。成功时把完整 `scope.target` 传给现有 Summary Skill，并使用目标名称生成报告标题。

### 5.3 故障诊断入口

`FaultDiagnosisService.start()` 复用共享解析器：

- WebApplication → `bs_app_slow`。
- DefinedApp → `cs_app_slow`。
- WebApplication 页面性能语义仍可转为 `bs_page_perf`。
- 目录不可用、对象不存在、同名歧义、未指定对象均返回 `ok=false`、`reportReady=false`。
- 删除命名故障请求的关键词类型回退，不允许 `target=null` 执行查询。
- 报告标题和 `faultName` 使用已确认的对象名称。

## 6. 错误契约

| 状态 | 综述行为 | 故障诊断错误码 |
| --- | --- | --- |
| `target_not_found` | 不生成报告，提示确认名称 | `FAULT_TARGET_NOT_FOUND` |
| `target_ambiguous` | 不生成报告，提示明确业务或应用 | `FAULT_TARGET_AMBIGUOUS` |
| `catalog_unavailable` | 不生成报告，提示目录暂不可用 | `FAULT_TARGET_CATALOG_UNAVAILABLE` |
| 未指定具体故障对象 | 不执行诊断 | `FAULT_TARGET_REQUIRED` |

## 7. 回归矩阵

```text
回溯238web的综述报告
  -> WebApplication/回溯238web 单对象综述

回溯238web的业务综述报告
  -> WebApplication/回溯238web 单对象综述

HTTPS应用的综述报告
  -> DefinedApp/HTTPS 单对象综述

业务综述报告
  -> 业务整体综述，不要求 target

系统综述报告
  -> 全局综述，不要求 target

不存在对象的综述报告
  -> 不调用 summary/export，不生成附件

回溯238web业务故障分析报告
  -> bs_app_slow + napm_bs_fault_diagnosis_v2

HTTPS应用故障分析报告
  -> cs_app_slow + napm_cs_fault_diagnosis_v1

目录不可用
  -> 两类故障报告均失败闭合，不生成报告
```

## 8. 验收标准

1. 单对象综述南向查询携带正确的 `groupType` 和 `groupArgument`。
2. `回溯238web` 报告文件名使用业务对象名称，不再出现全局综述文件名。
3. `HTTPS` 使用 DefinedApp 单应用综述和 CS 应用故障模板。
4. 任一命名对象解析失败时，不出现 `TotalTraffic` 或维度整体报告兜底。
5. 每轮只调用一次 summary、一次 export，只发送一个 Word 附件。
6. 巡检、全局综述、维度整体综述、报告重发和附件去重测试保持通过。

## 2026-08-21 部署验收补充

`1.1.0-rc.16` 安装后的生产目录冒烟发现，`NapmObjectTargetResolver` 默认路径把
`NapmMetadataService` 当作构造函数使用，但该模块实际导出共享单例。异常被失败关闭
逻辑转换成 `catalog_unavailable`，因此不会误生成全局报告，但命名对象报告也无法继续。

修复方式是直接复用 `NapmMetadataService` 的单例导出，不改变目录真值、对象匹配、失败
关闭或报告路由规则。同时新增默认生产装配回归测试，防止只验证注入假目录的测试再次
掩盖模块导出契约不匹配。修复后定向回归 43 条、全量测试 737 条、lint 和 8 个生产工具
契约均通过；后续候选版本使用新版本号，不移动 `v1.1.0-rc.16` 标签。
