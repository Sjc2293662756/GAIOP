# NAPM 告警查询前置直达发送暂缓记录

## 1. 当前决定

2026-08-19 真实企业微信测试确认：`1.1.0-rc.12` 仍不能稳定把 `napm-alert-query` 生成的固定七分类文本作为最终回复发送给用户。

由于下一步修复会改变普通告警摘要请求的执行时序和最终发送所有权，存在重复查询、重复发送、错误抢占复杂告警请求等风险。本问题暂缓实施，保留现网 `1.1.0-rc.12`，不继续修改代码、不构建新版本、不部署服务器。

## 2. 已确认现象

用户请求“最近一小时系统都有那些告警？”后：

1. `napm-alert-query` 在当前轮成功执行，并生成 1083 字符 canonical 文本。
2. `before_message_write` 把 canonical 文本写入会话转录。
3. 企业微信实际收到的是 708 字符的模型自由摘要，包含严重程度、类型分布、Top 对象、主要指标和代表性事件。
4. 当前轮没有出现 `napm_alert_reply_dispatched`，说明 rc.12 的告警 `reply_dispatch` 分支未完成最终交付。

这说明告警 Skill 数据和固定格式生成正常，错误发生在 Tool 执行完成后的最终发送链路。

## 3. 根因

远端 OpenClaw `2026.5.4` 的真实生命周期为：

```text
message_received
→ reply_dispatch
→ Agent
→ napm-alert-query
→ 模型 final
→ WeCom 发送
```

rc.12 假定 `reply_dispatch` 会在 `napm-alert-query` 执行完成后取得当前轮结果。实际上普通模型回复路径只在 Agent 前调用该 Hook；当 Hook 运行时，当前轮 Tool 结果还不存在。

rc.12 的单元测试先调用 `rememberSkillResult()`，再调用 `reply_dispatch`，与生产时序相反。远端 smoke 也直接构造已有 Tool 结果后调用 Hook，因此两者均为假阳性。

同时已经确认：

- `before_message_write` 只修正会话转录，不拥有企业微信实际发送。
- 当前 WeCom agent-final 链路没有触发可替换内容的 `message_sending`。
- `before_agent_finalize` 只能要求模型继续或重试，不能直接替换最终发送文本。
- 当前 Tool 返回契约没有可跳过模型并直达通道的 `suppressModel`、`deliverAsFinal` 或同类标志。

## 4. 后续推荐方案

后续若恢复修改，推荐只为高置信度的普通告警摘要请求增加前置直达工作流：

```text
reply_dispatch 识别普通告警摘要请求
→ 构造结构化告警参数
→ 调用现有 alertQueryTool.execute()
→ 底层执行 napm-alert-query Skill
→ buildAlertQueryReply() 生成 canonical 文本
→ dispatcher.sendFinalReply()
→ 返回 handled: true，阻止模型再次回复
```

建议新增独立的 `AlertDirectDispatchService`，复用现有时间范围解析、告警严重程度枚举和七分类常量，不直接访问 NetInside API。

接管范围只包括参数能够完整、可靠解析的普通告警 summary/list 请求。告警详情、时间线、事件 ID、数据包、报告、通知字段解释和复杂对象过滤仍走现有 Agent + Tool 链路，避免把复杂自然语言全部降级为正则路由。

## 5. 必须控制的风险

1. 查询幂等：以 `conversationKey + turnId` 保证同轮只执行一次 `napm-alert-query`。
2. 发送幂等：同轮 canonical 文本只调用一次 `sendFinalReply()`。
3. 失败边界：Skill 已开始后若失败，返回确定性错误，不回退模型再次查询。
4. 意图隔离：复杂告警、报告、数据包和其他 NAPM Tool 不得被前置路径抢占。
5. 生产链路：前置路径仍必须调用 `napm-alert-query`，不得用 shell、curl 或底层 API 替代。
6. 真实验收：不能再以预置 Tool 结果后直接调用 Hook 的 smoke 作为成功依据。

## 6. 恢复实施时的测试门槛

测试必须按真实生命周期执行：

```text
message_received
→ reply_dispatch
→ reply_dispatch 内部执行 napm-alert-query
→ sendFinalReply
```

至少覆盖：

- “最近一小时系统都有那些告警？”无需预置 Tool 结果即可收到固定七分类文本。
- 同轮重复 dispatch 只查询一次、发送一次。
- 紧急、重大、轻微和七分类过滤正确。
- Skill 失败时返回确定性错误。
- 报告、时间线、详情、事件数据包不被前置路径接管。
- 其他 NAPM Tool 的回复行为不变。

部署后的真实企业微信验收必须同时看到：

- `napm_alert_direct_dispatch_started`
- `napm_alert_direct_dispatch_completed`
- `napm_alert_reply_dispatched`
- 企业微信 final payload 与 canonical 文本指纹一致
- 当前轮没有第二个模型 final
