# 数据包下载存储空间治理方案

## 背景

数据包文件通常比普通查询结果大很多。尤其在高速链路上，即使只下载几分钟的 pcap，也可能达到数 GB。当前 `openclaw-napm-packet-analysis` 已具备基础清理能力：

- 下载目录默认为 `$HOME/.openclaw/artifacts/openclaw-napm-packet-analysis`。
- 每次下载任务会创建一个独立 artifact 目录。
- artifact 目录带 `.packet-artifact` 标记。
- 默认 `PACKET_RETENTION_HOURS=24`，下载前会清理超过保留时间的 artifact。
- 早期代码默认 `PACKET_KEEP_FILES=false`，`download_analyze` / `preview_download_analyze` 分析完成后会删除原始 pcap，只保留 `download.meta.json` 和 `analysis.json`。本轮改造后，默认值已调整为 `PACKET_KEEP_FILES=true`。
- 默认 `PACKET_MAX_BYTES=524288000`，单次下载流式读取超过该阈值会中断。

这些策略能处理“时间过期”和“单文件过大”，但还缺少“按服务器磁盘剩余空间治理”的能力。若服务器磁盘整体使用率达到 80% 甚至更高，仅靠保留时间是不够的。

从用户体验和可复查角度看，后续建议调整默认策略：**分析完成后不再立即删除原始数据包，而是先保留原始包；当磁盘达到水位阈值或超过保留时间时，再统一清理。**

## 目标

建立一套面向生产环境的数据包存储治理策略：

- 下载前检查目标分区剩余空间。
- 下载前根据 preview 预计大小判断是否有足够空间。
- 下载后记录 artifact 元数据，便于按时间、大小、状态清理。
- 当存储使用率达到阈值时，按下载时间从旧到新清理。
- 保留近期原始包、分析结果和元数据，便于后续复核、追加分析和报告导出。
- 达到磁盘水位阈值后，优先删除旧原始大 pcap；必要时再删除整个旧 artifact。
- 防止并发下载任务同时清理或同时占满磁盘。
- 所有清理动作可审计，不误删非 packet skill 生成的文件。

## 核心原则

- 只清理带 `.packet-artifact` 标记的目录。
- 默认不在分析完成后立即删除原始 pcap/cap/zip。
- 达到清理阈值时优先删除旧原始 pcap/cap/zip 大文件，尽量保留 `download.meta.json` 和 `analysis.json`。
- 磁盘压力较高时，再删除整个旧 artifact 目录。
- 清理顺序按下载时间或目录修改时间从旧到新。
- 下载前、下载后都要检查磁盘水位。
- 高水位时阻断新下载，而不是下载后再补救。
- 所有阈值配置化。

## 配置项设计

建议新增或明确以下环境变量：

```text
PACKET_DOWNLOAD_DIR=$HOME/.openclaw/artifacts/openclaw-napm-packet-analysis
PACKET_RETENTION_HOURS=24
PACKET_KEEP_FILES=true
PACKET_MAX_BYTES=524288000

PACKET_STORAGE_WARN_PERCENT=75
PACKET_STORAGE_CLEAN_PERCENT=80
PACKET_STORAGE_TARGET_PERCENT=70
PACKET_STORAGE_BLOCK_PERCENT=90
PACKET_STORAGE_MIN_FREE_BYTES=2147483648
PACKET_STORAGE_RESERVE_MULTIPLIER=1.5
PACKET_STORAGE_CLEANUP_DRY_RUN=false
PACKET_STORAGE_LOCK_TIMEOUT_MS=30000
```

含义：

| 配置 | 默认值 | 说明 |
|---|---:|---|
| `PACKET_STORAGE_WARN_PERCENT` | 75 | 超过后在结果中提示存储压力 |
| `PACKET_STORAGE_CLEAN_PERCENT` | 80 | 超过后触发自动清理 |
| `PACKET_STORAGE_TARGET_PERCENT` | 70 | 清理目标水位，清到低于该值为止 |
| `PACKET_STORAGE_BLOCK_PERCENT` | 90 | 超过后阻断新下载 |
| `PACKET_STORAGE_MIN_FREE_BYTES` | 2GB | 下载前要求至少保留的空闲空间 |
| `PACKET_STORAGE_RESERVE_MULTIPLIER` | 1.5 | 预计文件大小的安全系数 |
| `PACKET_STORAGE_CLEANUP_DRY_RUN` | false | 只计算不删除，用于演练 |
| `PACKET_STORAGE_LOCK_TIMEOUT_MS` | 30000 | 并发清理锁等待时间 |

> 说明：本轮改造已将代码默认值调整为 `PACKET_KEEP_FILES=true`，用磁盘水位治理取代“分析后立即删除”。

## 下载前空间检查

下载前应执行：

```text
getDiskUsage(PACKET_DOWNLOAD_DIR)
  -> if usedPercent >= BLOCK_PERCENT: 阻断下载
  -> if usedPercent >= CLEAN_PERCENT: 先执行 cleanupByWatermark()
  -> if preview.estimatedBytes exists:
       requiredFree = estimatedBytes * RESERVE_MULTIPLIER + MIN_FREE_BYTES
       if freeBytes < requiredFree: 阻断下载或建议缩小时间范围
  -> if preview.estimatedBytes unknown:
       使用 PACKET_MAX_BYTES * RESERVE_MULTIPLIER 做保守预留
```

失败决策示例：

```json
{
  "ok": false,
  "error": {
    "code": "PACKET_STORAGE_NOT_ENOUGH_SPACE",
    "message": "当前下载目录所在分区可用空间不足，未执行数据包下载。"
  },
  "decision": {
    "next_action": "SUGGEST_NARROW_TIME_RANGE",
    "reason": "PACKET_STORAGE_PRESSURE",
    "message": "建议缩小时间范围，或等待旧数据包清理后再下载。"
  }
}
```

## 清理策略

### 第一层：过期清理

保留现有策略：

```text
cleanupExpiredArtifacts(downloadDir, retentionHours)
```

删除超过 `PACKET_RETENTION_HOURS` 的 artifact 目录。

### 第二层：水位清理

新增：

```text
cleanupArtifactsByWatermark(downloadDir, targetPercent)
```

触发条件：

```text
diskUsedPercent >= PACKET_STORAGE_CLEAN_PERCENT
```

清理顺序：

```text
1. 找到所有带 .packet-artifact 的目录
2. 按 createdAt / downloadedAt / mtime 从旧到新排序
3. 优先删除目录内原始包文件：
   *.pcap
   *.cap
   *.pcapng
   *.zip
4. 保留 download.meta.json / analysis.json / .packet-artifact
5. 每删除一批重新检查磁盘水位
6. 如果仍高于 targetPercent，再删除整个旧 artifact 目录
7. 清到 usedPercent <= PACKET_STORAGE_TARGET_PERCENT 或无可清理文件为止
```

### 第三层：阻断下载

如果清理后仍满足：

```text
diskUsedPercent >= PACKET_STORAGE_BLOCK_PERCENT
```

则不允许新下载。

## 并发控制

需要文件锁，避免多个下载任务同时清理。

建议锁文件：

```text
$PACKET_DOWNLOAD_DIR/.packet-storage-cleanup.lock
```

策略：

- 清理前获取锁。
- 锁超时后返回 `PACKET_STORAGE_LOCK_TIMEOUT`。
- 锁文件应记录 `pid`、`createdAt`。
- 如果锁进程不存在且锁超时，可清理 stale lock。

## 下载后处理

下载完成后：

```text
write download.meta.json
  -> 记录 bytes / downloadedAt / retention / storage 状态
  -> 如需分析，执行 tshark
  -> 默认保留原始 pcap，便于后续复核和追加分析
  -> 再执行一次 disk usage 检查
  -> 如果超过 CLEAN_PERCENT，触发水位清理
```

不建议继续把 `PACKET_KEEP_FILES=false` 作为生产默认值，原因是：

- 用户经常会基于“刚才那个包”追问，例如深入分析、重新导出报告、核对某个连接或协议。
- 如果分析后立即删除原始包，后续只能重新下载，既慢也可能因时间窗口变化拿不到同一份数据。
- 原始包是最强证据，应至少短期保留。
- 存储压力应该交给水位清理策略处理，而不是每次分析完成就无条件删除。

因此推荐：

```text
PACKET_KEEP_FILES=true
```

清理责任转移给：

```text
PACKET_RETENTION_HOURS
PACKET_STORAGE_CLEAN_PERCENT
PACKET_STORAGE_TARGET_PERCENT
PACKET_STORAGE_BLOCK_PERCENT
```

例外场景：

- 磁盘非常小。
- 数据包敏感，合规要求分析后立即销毁。
- 用户明确要求“不保留原包”。

这些场景可以显式设置：

```text
PACKET_KEEP_FILES=false
```

## 保留策略建议

### 默认生产策略

```text
PACKET_KEEP_FILES=true
PACKET_RETENTION_HOURS=24
PACKET_MAX_BYTES=524288000
PACKET_STORAGE_WARN_PERCENT=75
PACKET_STORAGE_CLEAN_PERCENT=80
PACKET_STORAGE_TARGET_PERCENT=70
PACKET_STORAGE_BLOCK_PERCENT=90
PACKET_STORAGE_MIN_FREE_BYTES=2147483648
```

含义：

- 分析完成后默认保留原始包。
- 原始包、元数据和分析结果默认保留 24 小时。
- 单次下载最大 500MB。
- 磁盘到 80% 自动清理。
- 清理目标是降到 70%。
- 磁盘到 90% 阻断新下载。

### 调试/问题复现策略

```text
PACKET_KEEP_FILES=true
PACKET_RETENTION_HOURS=6
PACKET_MAX_BYTES=1073741824
PACKET_STORAGE_CLEAN_PERCENT=75
PACKET_STORAGE_TARGET_PERCENT=65
```

含义：

- 保留原始包便于复查。
- 缩短保留时间，避免长期占用。

### 高风险小磁盘策略

```text
PACKET_KEEP_FILES=false
PACKET_RETENTION_HOURS=2
PACKET_MAX_BYTES=209715200
PACKET_STORAGE_CLEAN_PERCENT=70
PACKET_STORAGE_TARGET_PERCENT=60
PACKET_STORAGE_BLOCK_PERCENT=85
PACKET_STORAGE_MIN_FREE_BYTES=5368709120
```

适合磁盘较小或业务高峰期。

该策略是例外策略：牺牲复查体验，优先保护磁盘。

## 与 preview 风险评估联动

preview 阶段已经有：

```text
preview.overview.estimatedBytes
preview.risk.level
preview.risk.recommendation
```

存储治理应复用该信息：

```text
if preview.overview.estimatedBytes > availableFreeBytes:
  不下载
  建议缩小时间范围
```

如果 preview 没有返回预计大小：

```text
使用 PACKET_MAX_BYTES 作为最坏情况预留
```

这样可以避免“preview 未知但直接下载导致磁盘打满”。

## 实现改造点

文件：

```text
skills/openclaw-napm-packet-analysis/scripts/run_packet_analysis.js
```

建议新增函数：

```js
async function getDiskUsage(targetDir) {}
async function preflightStorageForDownload(task, preview) {}
async function cleanupArtifactsByWatermark(downloadDir, options) {}
async function listManagedPacketArtifacts(downloadDir) {}
async function deletePacketPayloadFiles(artifactDir) {}
async function acquireStorageCleanupLock(downloadDir) {}
async function releaseStorageCleanupLock(lock) {}
function buildStorageDecision(usage, preview, filePolicy) {}
```

改造位置：

```text
downloadPacket(task)
  -> cleanupExpiredArtifacts()
  -> preflightStorageForDownload()
  -> createArtifactDir()
  -> httpRequest(download)
  -> write meta
  -> removeDownloadedFileAfterAnalysisIfNeeded()
  -> post-download storage check
```

注意：当前 `downloadPacket()` 内部会直接创建 artifact 目录。建议调整为：

```text
先做 storage preflight
再 createArtifactDir
```

避免在空间不足时创建空目录。

## 推荐实施阶段

### 第一阶段：下载前空间预检

- 实现 `getDiskUsage()`。
- 下载前判断 `usedPercent` 和 `freeBytes`。

### 第二阶段：水位清理

- 实现 `cleanupArtifactsByWatermark()`。

### 第三阶段：结构化 storage 输出

- 在 JSON 结果中输出 `storage`。
- final answer 可解释“为什么没下载”。

### 第四阶段：后台定时清理

- 增加独立 cleanup 命令或脚本。
- 配置 systemd timer。

## 结论

推荐最终形成三道防线：

```text
preview 风险评估
  -> 估算下载大小和包数，避免不必要下载

download preflight
  -> 按磁盘水位和可用空间决定是否允许下载

watermark cleanup
  -> 超过 80% 自动按下载时间清理旧 artifact
```

这样可以在不影响正常小包分析的前提下，避免数据包下载把 OpenClaw 服务器磁盘打满。
