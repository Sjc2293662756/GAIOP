## 2. 全部修复明细

### 修复①：`filterEvents` 空 metrics 事件被误杀

**文件**: `skills/openclaw-napm-alert-query/services/AlertNormalizerService.js`
**问题**: NAPM `alertsDetail` API 对某些事件返回 `metrics: []`。AI 从 prompt 解析出指标名后将其作为 `criteria.metrics` 过滤条件，`filterEvents` 因 `[].some()` 返回 `false` 而误杀事件。
**修改**: 增加 `event.metrics.length > 0` 前置条件。

```javascript
// 修改前
if (criteria.metrics?.length && !event.metrics.some((metric) => criteria.metrics.includes(metric))) return false;

// 修改后
if (criteria.metrics?.length && event.metrics.length > 0 && !event.metrics.some((metric) => criteria.metrics.includes(metric))) return false;
```

### 修复②：WeCom "深入分析" 格式不含触发指标值

**文件**: `skills/openclaw-napm-syslog-watcher/services/WeComPushService.js`
**问题**: 旧格式为 `分析这个告警数据包 <elogid> <start> <end> <指标名>`，指标中文名被 AI 解析为过滤条件。且缺失触发指标的实际值、级别和条件。
**修改**: 新增独立的"触发指标值"、"告警级别"、"触发条件"上下文行。

```
// 修改前
分析这个告警数据包 716982 1783999560 1783999800 用户体验时间（服务器）

// 修改后
分析这个告警数据包 716982 1783999560 1783999800 用户体验时间（服务器）
触发指标值: 用户体验时间（服务器）=7363.4702毫秒
告警级别: 紧急
触发条件: 如果 用户体验时间（服务器） > 3000.0 则为 紧急...
```

### 修复③：`buildFocusAnalysis` 不支持外部指标注入

**文件**: `skills/openclaw-napm-alert-query/services/AlertIndirectPacketDiscoveryService.js`
**问题**: `buildFocusAnalysis` 仅从 `event.metrics` 提取，当 NAPM API 返回 `metrics: []` 时输出 `hasTriggerMetrics: false`，导致数据包分析报告无法聚焦于真实触发指标。
**修改**: 
- `buildFocusAnalysis(event)` → `buildFocusAnalysis(event, options)`
- 新增 `buildFocusFromExternalMetrics()` 函数，从 `options.alertTriggerMetrics` 注入 syslog 侧指标值
- `discover()` 调用处传入 `options`

```javascript
// 外部注入格式
options.alertTriggerMetrics = {
  names: ['用户体验时间（服务器）'],
  codes: ['UEII'],
  values: [7363.4702],
  units: ['毫秒'],
  condition: '>3000紧急',
  severity: '紧急'
};
```

### 修复④：`normalizeAnalysisOptions` 丢弃告警上下文

**文件**: `skills/openclaw-napm-packet-analysis/scripts/run_packet_analysis.js`
**问题**: `normalizeAnalysisOptions` 只提取 5 个开关型字段（level/includeDns/includeHttp/includeTls/includePorts），丢弃了 `suggestedPacketQuery.analysis` 中的 `metrics`/`metricLabels`/`values`/`instruction` 等告警上下文。导致 tshark 分析结果是普通协议分布，无告警聚焦。
**修改**: 
- 新增 `buildAlertAnalysisContext()` 保留告警上下文
- `analyzePacketFile` 的 result 新增 `alertContext` 字段
- `summarizeAnalysis` 透传 `alertContext`
- `buildNarrationInput` 新增 `renderPolicy.alertRenderHint`（AI 聚焦叙述指令）

---

### 修复⑤：远端 `.env` 缺少 TLS 配置

**文件**: 远端 `/home/netinside/.openclaw/workspace/.env`
**问题**: `AlertApiService`（alert-query）使用 `NETINSIDE_TLS_INSECURE=true`，但 `packet-analysis` 使用 `NETINSIDE_TLS_REJECT_UNAUTHORIZED`。`.env` 只有前者，导致 packet-analysis 以 `rejectUnauthorized:true` 连接 NAPM 自签证书时失败。
**修改**: 新增一行：

```bash
NETINSIDE_TLS_REJECT_UNAUTHORIZED=false
```

### 修复⑥：packet-analysis `.env` 加载路径不健壮

**文件**: `skills/openclaw-napm-packet-analysis/scripts/run_packet_analysis.js`
**问题**: `main()` 和 `handleSkillCall()` 仅从 `process.cwd()/.env` 加载，当 OpenClaw gateway 以非 workspace 目录为 cwd 启动时加载失败。
**修改**: 参照 `alert-query` 的 `loadDotEnvCandidates` 模式：
  - 新增 `workspaceRoot` 常量（从 `__dirname` 推算）
  - 新增 `loadDotEnvCandidates()` 函数
  - `main()` 和 `handleSkillCall()` 改为多路径依次尝试加载

```javascript
const workspaceRoot = path.resolve(__dirname, '..', '..', '..');

function loadDotEnvCandidates(filePaths = []) {
  for (const filePath of filePaths.filter(Boolean)) {
    loadDotEnv(filePath);
  }
}

// 调用
loadDotEnvCandidates([
  path.join(workspaceRoot, '.env'),
  path.join(process.cwd(), '.env'),
  process.env.OPENCLAW_HOME ? path.join(process.env.OPENCLAW_HOME, '.env') : null,
  process.env.HOME ? path.join(process.env.HOME, '.openclaw', '.env') : null,
]);
```

### 修复⑦：Plugin 拦截 packet 场景下的 exec/curl 绕过

**文件**: `napm-openclaw-plugin.remote.js`
**问题**: AI 在 packet prompt 场景下绕过 `napm-packet-analysis` skill，直接用 `bash`+`curl` 发 NAPM 包请求。导致：(a) 密码硬编码为错误值 `GAIOP2023.`（正确密码为 `GAIOP123`，在 `.env` 中），(b) `ips` 参数格式错误（用了 `|` 分隔而非多个 `ips` 参数），(c) 无 tshark 分析。
**修改**: 在 plugin 的 `beforeToolUse` 钩子中，当 `activePacketPrompt=true` 且工具为 shell 类（bash/exec/sh）且参数包含 NAPM 包接口 URL 时，强制拦截并提示必须使用 `napm-packet-analysis` skill。

```javascript
// 在 line 4988 之前插入
if (activePacketPrompt && isDangerousSystemTool(toolName)) {
  const paramsStr = JSON.stringify(toolParams).toLowerCase();
  const hasNapmPacketUrl = /101\.254\.114\.238/.test(paramsStr)
    && /(packetspreview|packetsdown|downservlet)/i.test(paramsStr);
  const hasCurlToNapm = /curl|wget/.test(paramsStr)
    && /101\.254\.114\.238/.test(paramsStr)
    && /(netinside|webservice)/i.test(paramsStr);
  if (hasNapmPacketUrl || hasCurlToNapm) {
    return {
      block: true,
      blockReason: 'Packet capture/download/analysis MUST use napm-packet-analysis skill...'
    };
  }
}
```

**部署**: 推送到 `/home/netinside/.openclaw/extensions/napm-openclaw-plugin/`（Gateway 实际加载位置）。

### 修复⑧：Plugin 阻止 packet 场景下 napm-skill-query 的 auto-repair 误修

**文件**: `napm-openclaw-plugin.remote.js`
**问题**: AI 拿到 `USE_CANDIDATES` 后没有调 `napm-packet-analysis`，而是调了 `napm-skill-query` 尝试手工查 IP 会话。Plugin 的 auto-repair 逻辑（line ~4843）在 `activePacketPrompt=true` 时仍会拦截 `napm-skill-query` 调用并"修复"成完全错误的 metric 查询（如把 `DefinedApp→IPConversations` 修成 `PGHTTP400+IPAddress`）。AI 连续三次失败后放弃，用 bash+curl 绕过。
**根因**: 审计日志证实 AI 在 14:05 时调了三次 `napm-skill-query`（分别是 "查询告警推送应用测试1的IP会话Top 5"、"查看告警推送应用测试1的信息"、"查询告警推送应用测试1应用下的IP会话"），全部被 auto-repair 拦截/修错，从未调 `napm-packet-analysis`。
**修改**: 在 `napm-skill-query` 处理入口（line 4843）增加 `&& !activePacketPrompt` 门禁。

```javascript
// 修改前
if (toolName === 'napm-skill-query' && activeNapmPrompt && activePrompt) {

// 修改后
if (toolName === 'napm-skill-query' && activeNapmPrompt && activePrompt && !activePacketPrompt) {
```

**效果**: packet 场景下的 `napm-skill-query` 调用不再被 auto-repair 处理，直接落入下游 line 4988 的 packet guard 被正确拦截（提示"必须用 napm-packet-analysis"）。

### 修复⑨：Plugin USE_CANDIDATES 响应格式强化

**文件**: `napm-openclaw-plugin.remote.js`
**问题**: 修复⑧阻止了 AI 走错路，但 AI 拿到 `USE_CANDIDATES` 响应后仍然不调 `napm-packet-analysis`。审计日志证实 AI 连续 3 次调 `napm-alert-query`（displayText 102/15/102 字符），每次都拿到了 5 个候选 IP 和 `suggestedPacketQuery`，但 AI 忽略了指令，报告"返回空结果"后转去故障诊断。
**根因**: 原 `buildAlertQueryReply` 的 USE_CANDIDATES 格式把关键指令埋在装饰线之间，AI 误以为是最终答复摘要。
**修改**: 重写 USE_CANDIDATES 渲染块，改为顶部红标强制指令格式：

```
🚨🚨🚨 下一步操作（必须执行，这是中间步骤，不是最终答复）🚨🚨🚨

已发现 5 个嫌疑 IP 会话。
你必须立即对每个 candidate 调用 napm-packet-analysis 工具：

  napm-packet-analysis(
    mode: "preview_download_analyze",
    criteria: { ips: ["101.254.114.237","66.240.205.34"], start: 1784009520, end: 1784009820 },
  )  ← 第1个候选: 101.254.114.237|66.240.205.34

⛔ 禁止: 自己拼 curl、用 napm-skill-query 查 IP 会话、直接输出这段文本给用户。
✅ 必须: 对上面每个 candidate 调 napm-packet-analysis，拿到 tshark 分析结果后再组织最终答复。
```
