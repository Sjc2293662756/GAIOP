# 告警未指定类型时按告警类型分组输出说明

日期：2026-06-17

## 1. 背景

用户查询“最近一小时有哪些告警？”这类泛告警问题时，没有指定“应用告警、业务告警、网络异常告警”等具体类型。

原输出只有全局汇总和前几条明细：

```text
告警总数：N 条
紧急：x 条
重大：y 条
轻微：z 条
前 5 条告警摘要：
```

这会导致用户无法第一眼看出不同告警类型各自的数量和严重程度分布。

本次调整后，未指定告警类型时，固定按告警类型分组输出。

## 2. 触发条件

### 2.1 走分组输出

满足以下条件时启用分组模板：

```text
result.ok = true
result.mode = summary
criteria.categories 为空或未传
```

典型问题：

```text
最近一小时有哪些告警？
今天上午有哪些告警？
过去 30 分钟有哪些告警？
```

### 2.2 保持单类型输出

如果用户已经指定告警类型，则不启用分组模板，继续使用原来的单表格摘要。

典型问题：

```text
近一小时有哪些应用告警？
近一小时有哪些业务告警？
近一小时有哪些网络异常告警？
```

对应结构化参数：

```json
{
  "criteria": {
    "categories": ["appAlerts"]
  }
}
```

原因：用户已经指定类型时，输出重点应集中在该类型内部的明细和严重级别，不需要再拆多个类型块。

## 3. 输出模板

未指定告警类型时，输出如下：

```text
最近一小时告警概况：

网络性能告警：
共 2 个告警：
紧急告警 1 个
重大告警 0 个
轻微告警 1 个
告警概览：
| 级别 | 对象 | 描述 |
| --- | --- | --- |
| 🔴 紧急 | 192.168.1.16 | 吞吐过高 |

应用性能告警：
共 1 个告警：
紧急告警 0 个
重大告警 1 个
轻微告警 0 个
告警概览：
| 级别 | 对象 | 描述 |
| --- | --- | --- |
| 🟠 重大 | HTTPS | 外部应用性能下降 |
```

每个告警类型固定包含：

- 类型标题。
- 总告警数。
- 紧急告警数。
- 重大告警数。
- 轻微告警数。
- 告警概览表。

## 4. 告警类型来源

类型来自后端 `alertsSummary` 返回的一级字段，也就是归一化后的 `event.category`。

当前支持：

| category | 展示名称 |
|---|---|
| `networkAlerts` | 网络性能告警 |
| `networkIssueAlerts` | 网络异常告警 |
| `appAlerts` | 应用性能告警 |
| `busAlerts` | 业务故障告警 |
| `userAlerts` | 用户体验告警 |
| `securityAlerts` | 安全事件告警 |
| `AIAlerts` | 智能分析告警 |

## 5. 统计口径

### 5.1 统计必须基于完整过滤结果

本次同步修复了一个重要口径问题：

原来 `run_alert_query.js` 先执行：

```js
sortAlertEvents(filterEvents(...)).slice(0, maxEvents)
```

然后再用截断后的 `events` 计算 `summary`。

这会导致：

- 后端实际有 30 条告警。
- `maxEvents = 5`。
- 汇总只显示 5 条。
- 分类型数量也只能看到前 5 条，明显不准。

### 5.2 新口径

现在链路改为：

```text
后端 alertsSummary
  -> normalizeSummary
  -> filterEvents
  -> sortAlertEvents
  -> fullEvents
  -> summary = analyzeEvents(fullEvents)
  -> result.events = fullEvents.slice(0, maxEvents)
```

也就是：

- `summary.total` 基于完整过滤后的告警。
- `summary.bySeverity` 基于完整过滤后的告警。
- `summary.byCategoryDetail` 基于完整过滤后的告警。
- `result.events` 只用于展示前 N 条，不影响总数。

## 6. 代码结构

### 6.1 `AlertAnalyzerService.js`

新增 `summary.byCategoryDetail`：

```json
[
  {
    "category": "networkAlerts",
    "categoryLabel": "网络性能告警",
    "total": 2,
    "bySeverity": {
      "critical": 1,
      "major": 0,
      "minor": 1,
      "unknown": 0
    },
    "overviewEvents": []
  }
]
```

职责：

- 按告警类型聚合数量。
- 按严重级别统计数量。
- 保留每类前几条概览事件，用于固定模板里的“告警概览”。

### 6.2 `run_alert_query.js`

调整摘要执行链路：

```js
const events = sortAlertEvents(filterEvents(normalizeSummary(rawSummary, query.options), query.criteria));
result.events = events.slice(0, query.options.maxEvents);
result.summary = analyzeEvents(events, query.options);
```

同时在 `result` 中保留：

```js
criteria: query.criteria
```

插件层据此判断是否指定了告警类型。

### 6.3 `napm-openclaw-plugin.remote.js`

新增判断：

```js
shouldRenderAlertCategorySections(result)
```

判断逻辑：

```text
mode = summary
criteria.categories 为空
```

新增渲染：

```js
buildAlertCategorySections(result.summary.byCategoryDetail, events)
```

职责：

- 将 `byCategoryDetail` 渲染为固定分组模板。
- 如果旧结果没有 `byCategoryDetail`，则兜底根据 `events` 临时聚合，但这种兜底只用于兼容旧缓存，不作为准确统计来源。

## 7. 链路关系

```text

  -> OpenClaw 工具选择
  -> napm-alert-query
  -> buildAlertExecutorPayload()
  -> run_alert_query.js
  -> AlertApiService.getSummary()
  -> 后端 alertsSummary API
  -> normalizeSummary()
  -> filterEvents()
  -> sortAlertEvents()
  -> analyzeEvents()
  -> summary.byCategoryDetail
  -> buildAlertQueryReply()
  -> 未指定 categories：按告警类型分组输出
  -> 指定 categories：保持单类型总表输出
```

## 8. 与指定类型查询的关系

这次修改不会改变以下问题的筛选口径：

```text
近一小时有哪些应用告警？
近一小时有哪些业务告警？
近一小时有哪些网络异常告警？
```

这些问题仍然先由 `AlertQueryValidator` / `applyPromptCategoryFilter` 归一化为后端分类：

```text
应用告警 -> appAlerts
业务告警 -> busAlerts
网络异常告警 -> networkIssueAlerts
```

然后 `filterEvents()` 只保留对应类型。

因此：

- 泛告警查询：按类型分组展示。
- 单类型告警查询：只展示该类型结果。

## 10. 复查重点

复查时重点看三点：

1. 泛告警问题是否没有传 `criteria.categories`。
2. `summary.total` 是否大于等于 `result.events.length`，避免被 `maxEvents` 截断。
3. 最终企微回复是否出现各告警类型块，而不是模型自由总结。

## 11. 告警概览触发字段补充

### 11.1 背景

用户希望“告警概览”不要只展示：

```text
级别 / 对象 / 描述
```

还需要把触发相关字段提取成可读语句，例如：

```text
服务器疑似遭受攻击触发：对象 101.254.114.242 触发了 1 次告警，持续时长为 1 分钟，开始时间为 2026-06-17 15:23。
```

### 11.2 输出调整

分类型模板中的“告警概览”表格改为：

```text
| 级别 | 对象 | 描述 | 触发概览 |
| --- | --- | --- | --- |
| 🟢 轻微 | 101.254.114.242 | 服务器疑似遭受攻击 | 服务器疑似遭受攻击触发：对象 101.254.114.242 触发了 1 次告警，持续时长为 1 分钟，开始时间为 2026-06-17 15:23。 |
```

### 11.3 字段来源

| 展示字段 | 来源字段 | 说明 |
|---|---|---|
| 告警描述 | `event.name` | 例如“服务器疑似遭受攻击” |
| 对象 | `event.group` | 例如 `101.254.114.242` |
| 触发次数 | `event.triggerCount` | 同一类型下按“对象 + 描述 + 级别”聚合后的次数 |
| 持续时长 | `event.period` | 优先使用后端持续时间；没有时用 `event.end - event.start` 兜底 |
| 开始时间 | `event.start` | Unix 秒，按 `Asia/Shanghai` 格式化为 `YYYY-MM-DD HH:mm` |

### 11.4 聚合口径

`AlertAnalyzerService.buildOverviewEvents()` 会在每个告警类型内部按以下字段聚合概览项：

```text
event.group + event.name + event.severity
```

聚合后：

- `triggerCount` 表示该对象同类告警触发次数。
- `start` 取最早开始时间。
- `end` 取最晚结束时间。
- `period` 对同组事件持续时间求和。

这样单条告警会显示“触发了 1 次告警”，重复告警会显示真实重复次数。

### 11.5 降级策略

如果字段缺失：

- 对象缺失：显示“未知对象”。
- 持续时长缺失：显示“未知”。
- 开始时间缺失：显示“未知”。

不会因为某个字段缺失导致整条告警概览不展示。

## 12. 2026-06-17 16:25 线上未按类型分类问题

### 12.1 现象

用户输入：

```text
最近一小时有哪些告警
```

线上回复按严重级别组织：

```text
🔴 紧急告警
🟠 重大告警
🟢 轻微告警
```

这不符合“未指定告警类型时必须按告警类型分类”的输出要求。

### 12.2 根因

插件层会把告警查询结果记入 `napmResultByPrompt`，最终回复阶段再用 `buildAlertQueryReply()` 强制替换模型自由总结。

但缓存 key 原先直接使用：

```js
String(prompt).trim().toLowerCase()
```

这会导致以下两个问题被视为不同 key：

```text
最近一小时有哪些告警
最近一小时有哪些告警？
```

如果工具调用记录使用了带问号的 prompt，而最终回复阶段 active prompt 是不带问号的用户原文，就可能取不到 remembered alert result，最终模型自由总结漏出。

### 12.3 修复

`normalizePromptKey()` 改为归一化空白和末尾标点：

```js
return String(prompt || '')
  .trim()
  .toLowerCase()
  .replace(/[\s　]+/g, '')
  .replace(/[?？!！。；;，,、：:]+$/g, '');
```

这样：

```text
最近一小时有哪些告警
最近一小时有哪些告警？
最近一小时有哪些告警！
```

都会命中同一个结果缓存。

### 12.4 新固定输出形态

未指定告警类型时，固定输出改为更贴近人工复查的分类摘要：

```text
最近一小时告警汇总：共 41 条

① 应用性能告警 — 27 条
🔴 紧急 7 条 | 🟠 重大 9 条 | 🟢 轻微 11 条
主要对象：Esxi-local、HTTPS、回溯238（内部应用性能下降）
告警概览：
- 🔴 内部应用性能下降触发：对象 Esxi-local 触发了 1 次告警，持续时长为 1 分钟，开始时间为 2026-06-17 15:25。

② 网络性能告警 — 5 条
🔴 紧急 3 条 | 🟢 轻微 2 条
主要对象：ESXI主机、CentOS测试1（网络工作组延时增大）
告警概览：
- 🔴 网络工作组延时增大触发：对象 ESXI主机 触发了 3 次告警，持续时长为 3 分钟，开始时间为 2026-06-17 15:20。
```

### 12.5 回归测试

新增测试：

```text

```

覆盖：

- 用户 prompt 不带问号。
- remembered result 使用带问号 prompt。
- 模型输出按严重级别自由总结。
- `message_sending` 必须改写为按告警类型分类的固定模板。

这说明最终文本仍然是模型自由总结，而不是插件层 `buildAlertQueryReply()` 的固定输出。

```text
告警概览：

```

### 13.2 追加修复

仅做 prompt key 归一仍不够保险。如果最终回复阶段：

- active prompt 和工具调用 prompt 不一致；
- 或会话 guard 状态丢失；
- 或模型输出文本本身被当成 fallback prompt；

就仍可能拿不到对应 prompt key 的 remembered result。

本次追加修复：

```js
const alertFollowUp = Boolean(
  isAlertEventPrompt(activePrompt)
  || isAlertSkillMetaFollowUpPrompt(activePrompt, guardState || conversationState)
  || conversationState?.alertRelated
  || guardState?.alertRelated
);
```

也就是说，只要当前文本本身能识别为告警事件问题/告警摘要语义，就允许从最近一次 `napm-alert-query` 结果兜底回捞。

## 14. 2026-06-17 17:27 最终输出仍被模型二次改写问题

### 14.1 现象

截图中的输出已经按告警类型分组，但仍不是固定模板：

```text
Let me先查一下最近一小时的告警...
① 应用性能告警 — 25 条
...
需要查看某条告警的详情或时间线分布吗？
```

这类输出说明：

- `napm-alert-query` 已经查到了数据。
- 模型也看到了分类结果。
- 但最终回复仍由模型重新组织，没有逐字使用插件固定模板。

### 14.2 线上证据

审计日志显示该轮确实调用了告警 skill：

```text
2026-06-17T09:27:35Z napm_alert_query_invoked mode=timeline prompt=最近一小时有哪些告警
2026-06-17T09:27:36Z napm_alert_query_invoked mode=summary prompt=最近一小时告警总结
2026-06-17T09:27:37Z napm_alert_query_completed service=alertsSummary eventCount=35
```

因此问题不是后端没数据，也不是 skill 没执行。

问题在最终答案阶段：

- `napm-alert-query` 工具返回了固定文本。
- 但模型没有被强约束必须逐字输出该文本。
- 企微最终消息 hook 不应作为唯一兜底，因为不同消息链路下可能不会稳定接管最终文本。

### 14.3 修复

将固定模板契约前移到工具返回和系统提示。

`napm-alert-query` execute 返回：

```js
{
  content: [{ type: 'text', text: renderedText }],
  finalAnswer: renderedText,
  renderedText,
  renderPolicy: {
    mode: 'verbatim_final_answer',
    instruction: 'Return finalAnswer exactly as-is to the user...'
  },
  details: {
    ...result,
    finalAnswer: renderedText,
    renderedText
  }
}
```

系统提示新增硬规则：

```text
Alert final-answer contract:
when napm-alert-query returns finalAnswer/renderedText/text content,
output that text verbatim as the final user-visible answer.
Do not paraphrase it, do not regroup by severity,
do not add "Let me" or "当前最需要关注",
and do not change the alert category order/template.
```

### 14.4 防回归测试

新增/更新测试：


覆盖：

## 15. 2026-06-17 18:22 继续被模型摘要化问题

### 15.1 现象

18:22 截图中，输出仍然不是固定模板，而是模型根据结构化数据重新写的摘要：

```text
① 应用性能告警 — 24 条（最多）
对象：可观测239、ALT-HTTP、HTTPS
集中出现在 17:58~18:00，持续 2~3 分钟
最需要关注的是...
```

这说明模型没有逐字输出 `finalAnswer`，而是继续从工具结果里的结构化 `details.summary/events` 自行组织。

### 15.2 根因

`napm-alert-query` 工具返回同时包含：

- `content.text`：固定模板。
- `finalAnswer/renderedText`：固定模板。
- `details`：完整结构化结果。

即使提示词要求逐字输出，模型仍可能读取 `details` 里的结构化数据并重新总结。

### 15.3 修复

收紧 `napm-alert-query` 工具返回：

```js
return {
  text: renderedText,
  content: [{ type: 'text', text: renderedText }],
  finalAnswer: renderedText,
  renderedText,
  renderPolicy: { mode: 'verbatim_final_answer', ... },
  metadata: {
    ok,
    mode,
    service,
    total,
    requestUrl
  }
}
```

删除对模型可见的完整 `details` 字段。

插件内部仍通过 `rememberSkillResult()` 保存完整 result，供后续追问详情/时间线/Debug API 使用；但最终模型不再直接看到完整结构化事件列表，降低二次改写概率。

### 15.4 防回归测试

测试要求：

```text
createAlertQueryToolDefinition().execute
```

源码中必须包含：

- `finalAnswer`
- `verbatim_final_answer`

且不能包含：

- `details:`
