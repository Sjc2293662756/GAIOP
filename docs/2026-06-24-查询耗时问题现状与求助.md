# NAPM 查询耗时问题：现状与求助

日期：2026-06-24

---

## 一、问题

用户通过企业微信问 "最近丢包最严重的IP是谁？" 这类简单 NAPM 查询，耗时 10-35 秒，且呈恶化趋势。

## 二、当前架构

```
企业微信消息
  → OpenClaw Gateway (端口 18789)
    → wecom 频道子系统
      → napm-openclaw-plugin (插件)
        → before_agent_start hook → 注入路由规则到 LLM 上下文
        → LLM Agent: main (使用 deepseek-chat / v4-flash)
          → openai.yaml agent prompt (35行规则)
          → LLM 推理 → 调时间工具 → 构造 resolvedQuery → 调 napm-skill-query
        → before_tool_call hook → 校验 resolvedQuery
        → 执行 NAPM skill:
          → MetricExecutionKernel → NapmClient HTTP → NetInside API (101.254.114.238)
        → 返回结果
      → LLM 生成中文叙述 → 回复用户
```

### 关键配置

```
模型: deepseek-chat (API: api.deepseek.com)
OpenClaw 配置: /home/netinside/.openclaw/openclaw.json
  服务器: 101.254.114.237 (Ubuntu, Node.js v22.14.0, 2核 8GB)
  频道: wecom (企业微信), sendThinkingMessage: true (必须保留)
```

## 三、试过的方案及结果

### 3.1 修复 Memory 子系统故障（✅ 有效）

**问题**：SQLite FTS5 模块缺失 + Embedding API 限流，每次查询浪费 7s。

**修复**：`/home/netinside/.openclaw/config.yaml` 中禁用 `memory.embeddings` 和 `memory.fts`。

**结果**：Memory 错误从每次 10 次重试降为 0。但总耗时未明显下降（17.5s）。

### 3.2 修复时间戳年份 Bug（✅ 有效）

**问题**：LLM 自行计算时间戳时用错年份（2025 vs 2026），导致 NAPM API 返回空数据。

**修复**：`ResolvedQueryTimeRangeService.js` 新增 `autoCorrectTimestampIfStale()`，在 skill 执行前自动修正错误年份。

**结果**：年份错误从 20% 降为 0。但 LLM 仍花费 14 秒构造 resolvedQuery。

### 3.3 精简 LLM prompt（⚠️ 效果不明）

**文件**：`skills/openclaw-napm-query/agents/openai.yaml`  
**改动**：78 行 → 35 行，移除规则引擎已覆盖的指标/对象映射规则。

**结果**：耗时未明显变化（10:32 查询仍 15.8s）。prompt 大小不是瓶颈。

### 3.4 插件层拦截：规则引擎优先（❌ 无效）

**思路**：在 `prepareSkillExecutionArgs` 和 `before_tool_call` 中，当 LLM 的 resolvedQuery 不合法时，用本地规则引擎（`NapmResolvedQueryResolverService`，9ms）替代。

**结果**：LLM 仍然自己构造 resolvedQuery（且越做越好，越来越不易触发拦截）。拦截点太靠后。

### 3.5 before_agent_start 预解析注入（❌ 无效）

**思路**：在 LLM 开始推理**之前**（`before_agent_start` hook），用规则引擎预解析 prompt，将完整 resolvedQuery 注入 LLM 系统上下文。同时在 `openai.yaml` 中增加 "如果系统上下文有 PRE-RESOLVED QUERY，直接使用" 的指令。

```
// 插件注入:
!!! PRE-RESOLVED QUERY — USE THIS EXACTLY !!!
{service:"topValues", metric:"PLI", metrics:["PLI"], topMetric:"PLI",
 groups:[{type:"IPAddress"}], topCount:1, start:..., end:..., ...}
```

**结果**：LLM **完全无视**预解析结果。每次仍然走完整流程：查记忆 → 调时间工具 → 构造 query → 漏必填字段 → 修正 queryModeKey → 重试 → 生成回答。

## 五、耗时构成（审计日志精确数据）

以 6/23 18:05 查询为例（唯一有完整审计日志的一次）：

```
LLM 推理构造 resolvedQuery:  14.0s (80%)  ← 花了14s，结果还是错的
LLM 生成中文叙述:             2.8s (16%)
插件修复 + NAPM API:         0.7s (4%)   ← 插件9ms修复，API 682ms返回
────────────────────────────────────────
总计:                        17.5s
```

**代码执行只需 0.7 秒，LLM 推理占了 96%。**

## 六、核心矛盾

1. **`sendThinkingMessage: true`（必须保留）** 导致 DeepSeek 模型走 chain-of-thought 模式。模型会强制一步步思考，无视系统上下文中注入的任何预解析指令。

2. **规则引擎 9ms 就能完成的事**（解析 prompt → 构造 resolvedQuery），LLM 花了 14-30 秒，且经常出错（漏必填字段、错 queryModeKey、错年份）。

3. **所有尝试在 LLM 推理前/中拦截的方案都失败了**——模型用自己的推理逻辑覆盖了外部注入。

## 八、求助要点

1. **如何让 `sendThinkingMessage: true` 模式下的 LLM 接受外部预解析结果？** 或者，thinking 模式下是否有办法跳过 resolvedQuery 构造这一步？

2. **是否有办法在 OpenClaw 插件层直接执行查询并返回结果，绕过 LLM agent 的推理过程？** 例如 hook 中调 `runMainflowQuery` 预执行，将结果文本注入上下文。

3. **DeepSeek 模型的 chain-of-thought 深度是否可以控制？** 是否有参数限制思考轮次或跳过特定步骤？

4. **OpenClaw 是否支持条件路由？** 例如简单 query 走极简 agent，复杂 query 走完整 agent。
