# 2026-05-14 Skill目录职责与后续改造聚焦点总结

最后更新：2026-05-14

## 1. 文档目的

本文用于总结当前仓库中以下几个目录在真实运行链路中的作用，以及后续改造时应该把精力集中在哪些文件上：

- `skills/openclaw-napm-query/references`
- `skills/openclaw-napm-query/scripts`
- `skills/openclaw-napm-query/services`
- `src`

同时，本文也对“哪些文件后续必须重点改”“哪些文件第一阶段先不要碰”给出收口建议，避免继续在非关键层面上反复修补，导致链路越来越复杂。

---

## 2. 一句话结论

这四个目录并不是“都没用了”，而是职责已经分层：

- `references`：知识资料层，不直接参与运行时执行。
- `scripts`：skill 入口层，仍在主链上。
- `services`：skill 执行核心层，仍在主链上。
- `src`：公共基础层，仍在主链上。

当前真正需要继续收口的，不是把这些目录删掉，而是逐步拿掉其中残留的“本地语义理解 / prompt fallback / 隐式 query 改写”职责，让它们回到执行器、校验器、基础设施的本位。

---

## 3. 当前真实链路中的分层定位

当前更准确的理解应当是：

```text
企业微信 / OpenClaw 接入
  -> OpenClaw 主链负责理解、边界判断、澄清判断、生成 resolvedQuery
  -> napm-openclaw-plugin 负责 NAPM 路由、守卫、结果保护
  -> skills/openclaw-napm-query/scripts/run_napm_query.js
  -> skills/openclaw-napm-query/services/*
  -> src/constants + src/utils
  -> NAPM / NetInside API
  -> narration contract
  -> OpenClaw / 通道最终回包
```

这里最关键的变化是：

- `OpenClaw 主链` 应该是主语义入口。
- `skill` 不再应该承担“自然语言大脑”角色。
- `services` 和 `scripts` 仍然非常重要，但更偏执行、校验、编排，而不是主理解。

---

## 4. 四个目录当前各自的作用

## 4.1 `references/`

目录：

- `skills/openclaw-napm-query/references`

当前作用：

- 规则知识库
- 指标定义与别名说明
- 对象层级与钻取说明
- service mode 说明
- OpenClaw 接入约束说明
- 供 `SKILL.md`、人工排查、说明性文档引用

当前状态判断：

- 基本不直接被运行时代码 `require`
- 不属于实时执行链主路径
- 属于“知识支撑层”

所以：

- 它不是当前线上行为的直接决定层
- 但仍然有知识价值
- 不是本轮收口的主修点

---

## 4.2 `scripts/`

目录：

- `skills/openclaw-napm-query/scripts`

当前作用：

- skill 的运行入口层
- overview 场景的模块组织层

其中最关键的文件是：

- `scripts/run_napm_query.js`

它当前负责：

- 接收 `payload / resolvedQuery / session`
- 统一整理输入
- 承接 clarification / executionGuard
- 判断是普通执行还是 overview
- 输出标准 narration contract

overview 相关脚本也仍然在主链上：

- `overview-module.js`
- `OverviewPlanner.js`
- `OverviewExecution.js`
- `OverviewPlanCompiler.js`
- `OverviewResultReducer.js`
- `OverviewCandidateRegistry.js`
- `OverviewBudget.js`

这些文件主要负责“整体情况 / 概览 / overview”场景，不属于历史摆设，而是当前仍在运行的子链路。

---

## 4.3 `services/`

目录：

- `skills/openclaw-napm-query/services`

当前作用：

- skill 执行核心层
- 结构化 query 的执行、校验、元数据 review、API 编排与结果 contract 生成

最关键文件包括：

- `RequirementParserService.js`
- `NapmMetadataService.js`
- `QueryMetadataConstraintService.js`
- `OpenClawNarrationContractService.js`
- `MetricMappingService.js`
- `GroupPathPlannerService.js`
- `NapmClient.js`
- `ClarificationGateService.js`
- `GroupBuilder.js`
- `DimensionMappingService.js`
- `QueryValidator.js`

当前状态判断：

- 这些文件依然直接处在执行主链上
- 不是“废弃目录”
- 但其中一部分文件仍残留“本地理解 / fallback / 隐式修正”职责，需要继续收口

也就是说：

- `services` 还在主链上
- 只是它以后不该继续承担“自然语言主理解器”角色

---

## 4.4 `src/`

目录：

- `src/constants`
- `src/utils`

当前作用：

- 公共基础能力
- 被 `scripts` 和 `services` 复用

当前主链中的关键公共文件包括：

- `src/constants/objectMetricOwnership.js`
- `src/constants/metricDomains.js`
- `src/constants/objectDimensions.js`
- `src/utils/TimeUtils.js`
- `src/utils/auditLogger.js`
- `src/utils/CsvParser.js`
- `src/utils/logger.js`

它们分别承担：

- 指标归属规则
- metric domain 规则
- 对象维度基础表
- 时间解析
- 审计与安全 URL 处理
- CSV 解析
- 公共日志

当前状态判断：

- 它们不是主语义理解层
- 但仍然是执行底座
- 没有这些，skill 执行链无法稳定运行

## 5. 当前主链上真正关键的文件

后续如果继续从代码层推进收口，最值得重点盯住的文件是：

- `skills/openclaw-napm-query/scripts/run_napm_query.js`
- `skills/openclaw-napm-query/services/RequirementParserService.js`
- `skills/openclaw-napm-query/services/NapmMetadataService.js`
- `skills/openclaw-napm-query/services/QueryMetadataConstraintService.js`
- `skills/openclaw-napm-query/services/OpenClawNarrationContractService.js`
- `src/constants/objectMetricOwnership.js`
- `src/constants/metricDomains.js`

这些文件分别决定：

- 统一入口怎么承接 `resolvedQuery`
- query 如何被执行期归一化
- 元数据 review 如何做
- 结构化 query 怎么被约束
- 最终 contract 怎么生成
- 指标归属规则是什么
- metric domain 规则是什么

---

## 6. 后续必须重点改的文件

## 6.1 `scripts/run_napm_query.js`

为什么必须改：

- 它是 skill 统一执行入口
- 目前仍保留 prompt fallback 逻辑
- 是实现“真正 resolvedQuery-only 主链”的关键口子

后续改造方向：

- 继续收掉 prompt fallback
- 上游没有 `resolvedQuery` 时统一返回结构化“上游未完成理解” contract
- 不再在这层继续承担自然语言主理解职责

---

## 6.2 `services/RequirementParserService.js`

为什么必须改：

- 它是当前执行编排中枢
- 仍包含部分语义兼容、模板 fallback、隐式修正逻辑
- 很多“看起来像执行问题，实际是语义被改写”的情况会在这里发生

后续改造方向：

- 保留执行编排职责
- 保留动态 metadata review、finalization、审计与执行
- 逐步弱化残留的自然语言理解色彩
- 避免继续在这里扩展“本地猜 query”的能力

---

## 6.3 `services/QueryMetadataConstraintService.js`

为什么必须改：

- 它是“受约束 resolvedQuery”最自然的代码落点
- 当前已经在做 metric/group/topCount/granularity 的规范化和兼容性检查
- 后续如果要实现“LLM 生成候选 resolvedQuery，代码决定能不能执行”，这里正好是核心约束层

后续改造方向：

- 强化为结构合法性和兼容性主校验器
- 允许有限、安全、可证明正确的规范化修正
- 遇到超出约束的问题时，不再静默改写用户真实语义，而是拒绝执行或要求澄清

---

## 6.4 第二批配套关注文件

这批文件不一定是第一刀就大改，但必须进入后续改造评审范围：

- `services/OpenClawNarrationContractService.js`
- `src/constants/objectMetricOwnership.js`
- `src/constants/metricDomains.js`

原因：

- narration contract 需要与新的 `decision + resolvedQuery` 主链对齐
- 指标归属和 metric domain 规则决定了结构化 query 的最终可执行边界

---

## 7. 第一阶段先不要碰的文件

## 7.1 `services/NapmClient.js`

建议：

- 第一阶段先不要碰

原因：

- 它是底层 API 客户端
- 当前主要问题不是通信层，而是主链理解与执行边界
- 过早改它容易把语义问题和 API 问题搅在一起

---

## 7.2 `services/NapmMetadataService.js`

建议：

- 第一阶段先不要大动主体结构

原因：

- 它是元数据、对象树、钻取路径、metricsForGroup 等运行时能力确认层
- 当前职责总体合理
- 当前主要矛盾不在它这里

可以继续依赖它、补日志、补使用方式，但不宜先重构它。

---

## 7.3 overview 子模块整套

建议：

- 第一阶段先不要大动

涉及文件包括：

- `overview-module.js`
- `OverviewPlanner.js`
- `OverviewExecution.js`
- `OverviewPlanCompiler.js`
- `OverviewResultReducer.js`
- `OverviewCandidateRegistry.js`
- `OverviewBudget.js`

原因：

- 这套确实在主链上
- 但它是相对独立的 overview 子系统
- 当前主要问题不是 overview 内部算法，而是主链语义入口没有完全收口

---

## 7.4 `references/`

建议：

- 第一阶段完全不要碰

原因：

- 它不是运行时代码主链
- 改它不会直接修复当前线上行为问题
- 它属于知识资料层，不是本轮收口焦点

---

## 7.5 `src/utils/*`

建议：

- 第一阶段不要改主体逻辑

原因：

- 这些是公共基础设施
- 当前更多是被依赖，而不是问题源头
- 除非发现明确 bug，否则应优先“用它们”，而不是“重写它们”

---

## 8. 当前最值得集中精力的改造面

如果后续要继续正式推进主链收口，第一批最值得集中改造的文件应收窄成：

- `skills/openclaw-napm-query/scripts/run_napm_query.js`
- `skills/openclaw-napm-query/services/RequirementParserService.js`
- `skills/openclaw-napm-query/services/QueryMetadataConstraintService.js`

第二批配套改：

- `skills/openclaw-napm-query/services/OpenClawNarrationContractService.js`
- `src/constants/objectMetricOwnership.js`
- `src/constants/metricDomains.js`

这条改造思路的核心不是“删目录”，而是：

- 让 OpenClaw 主链重新成为唯一主语义入口
- 让 skill 回到执行器、校验器、contract 生产者的本位
- 逐步收掉残留在本地代码里的 prompt fallback 和隐式 query 改写

---

## 9. 收口总结

这次梳理之后，可以把四个目录的定位统一成下面这套口径：

- `references` = 资料层
- `scripts` = 入口层
- `services` = 执行核心层
- `src` = 公共底座层

它们并不是“没用了”，而是：

- 不再都应该承担“主理解器”职责
- 但大部分仍然在当前运行主链上

后续真正要做的，不是把这些目录清空，而是把其中残留的主理解、prompt fallback、隐式改写能力逐步下线，让执行链变得更清晰、更稳定、更可维护。
