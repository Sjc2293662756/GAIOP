# NAPM 业务页面访问量排行对象漂移问题与解决方案

> 日期：2026-09-03
> 状态：问题已复现，方案已确认，尚未实施运行时代码修改
> 范围：Query Skill、Query Decision、Group Path Planner、Query Turn、多轮结果引用与排行叙述
> 关联文档：`docs/2026-09-03-NAPM页面访问详情查询能力缺口与统一解决方案.md`

## 1. 问题结论

用户问题：

```text
今天哪些业务页面访问量最高？
```

领域语义是“按页面访问量统计业务排行”，查询对象应为 `WebApplication`，指标应为 `PGNPGE`。正确的第一轮查询是：

```json
{
  "service": "topValues",
  "queryModeKey": "topn",
  "groups": [{ "type": "WebApplication" }],
  "metric": "PGNPGE",
  "topMetric": "PGNPGE",
  "timeRange": { "key": "today" }
}
```

现场结果却直接返回 URL 形式的 `PageFamily` 排行。问题不是统一意图分类器没有识别“业务”，而是后续路径规划把已经正确识别的 `WebApplication` 目标扩展成：

```text
WebApplication > PageFamilies > PageFamily
```

随后执行准备又把结构化目标从 `WebApplication` 覆盖成 `PageFamily`。Query Decision 只证明这条多级路径存在于静态 groups tree，没有证明用户本轮要求了下钻，因此错误查询仍被允许执行。

## 2. 正确的三轮业务链路

这三个问题必须是三个不同的 Query Turn，不能在第一轮提前下钻：

| 轮次 | 用户语义 | 查询对象与服务 | 预期结果 |
| --- | --- | --- | --- |
| 第一轮 | 今天哪些业务页面访问量最高？ | `topValues + WebApplication + PGNPGE` | 业务名称排行 |
| 第二轮 | 排名第一的都访问了什么？ | `WebApplication(argument=第一名业务) > PageFamilies > PageFamily` | 该业务下的页面族排行 |
| 第三轮 | 详细查看排名第一的前 20 个 | `pageViews(pageFamilyId, maxLimit=20)` | 选中页面族的访问实例详情 |

第一轮中的“页面访问量”是指标语义，不是要求把结果对象切换成页面族。只有第二轮出现明确的“该业务访问了什么/下面有哪些页面”等下钻操作，并且能从上一轮权威结果解析出具体业务时，才允许进入 `PageFamily`。

## 3. 本地复现证据

本次诊断未连接服务器，也没有调用南向接口。

### 3.1 统一分类结果正确

对原句调用 `WorkflowClassifierService.classifyWorkflow()`，稳定得到：

```json
{
  "targetObjectType": "WebApplication",
  "workflowType": "metric_topn",
  "reason": "ranking_intent"
}
```

因此“业务”已经被识别，问题发生在分类之后。

### 3.2 路径规划发生语义漂移

以正确的单 group Draft 为输入，并开启当前已有的显式路径修复后，`GroupPathPlannerService` 因原句包含“页面”命中 `page_family` 概念，自动生成：

```json
{
  "groups": [
    { "type": "WebApplication" },
    { "type": "PageFamilies" },
    { "type": "PageFamily" }
  ],
  "pathPlanning": {
    "strategy": "static_groups_tree",
    "anchorType": "WebApplication",
    "selectedPath": ["WebApplication", "PageFamilies", "PageFamily"]
  },
  "semanticConstraints": {
    "targetObjectType": "PageFamily",
    "workflowType": "metric_topn"
  }
}
```

这与现场返回 URL 排行的症状一致。

### 3.3 Query Decision 未阻断

把上述多级 Draft 交给 `QueryDecisionPolicy.evaluateQueryDecision()`，当前返回：

```json
{
  "action": "EXECUTE_QUERY",
  "reasonCode": "QUERY_READY",
  "southboundAllowed": true
}
```

说明现有多 group 校验只验证“路径是否真实存在、planner proof 是否完整”，没有验证“该路径是否得到本轮用户语义授权”。

## 4. 影响范围

### P1：首轮查询对象错误

业务排行变成跨业务汇总的页面族排行，用户无法知道哪个业务访问量最高。

### P1：多轮上下文被错误结果污染

第一轮若直接保存 `PageFamily` 结果，下一轮“排名第一的都访问了什么”会失去正确的业务锚点。后续 `pageViews` 即使参数合法，也可能继续分析错误范围。

### P1：技术合法被误当成语义合法

静态 groups tree 只能证明 `WebApplication > PageFamilies > PageFamily` 是 NAPM 支持的技术路径，不能证明用户在本轮要求了这条路径。

### P2：排行展示可信度不足

现场表格中的数值没有严格按访问量降序排列，却仍使用“排名”标签。需要确认是多级查询返回顺序异常、归一化顺序丢失，还是叙述层没有按数值排序。

### P2：现有回归测试缺少现场原句

当前测试覆盖业务 TopN、合法多级下钻和 `pageViews`，但没有锁定“今天哪些业务页面访问量最高？”这一复合表达。

## 5. 根因分解

### 根因一：页面概念匹配过宽

`GroupPathPlannerService` 把普通“页面”字样视为 `page_family` 路径概念。它没有区分：

- “业务页面访问量”中的页面指标修饰；
- “这个业务下面有哪些页面”中的对象下钻。

### 根因二：路径规划授权条件不足

当前 `shouldAttemptPlan()` 在发现任何路径概念时即可尝试规划。即使当前 group 已经等于结构化目标 `WebApplication`，且工作流只是普通 `metric_topn`，仍可能扩展终端对象。

### 根因三：请求目标被执行期逻辑覆盖

`RequirementParserService.applyStaticGroupPathPlanning()` 把规划后的终端 group 写回 `semanticConstraints.targetObjectType`。这会销毁“用户原始请求对象”证据，使后续策略无法判断是否发生语义漂移。

### 根因四：Query Decision 缺少目标/路径一致性校验

当前 `validateMultiGroupQueryContract()` 只校验 planner proof 和静态路径。它没有对比：

- 分类器给出的请求操作；
- 分类器给出的目标对象；
- Draft 声明的目标对象；
- 实际终端 queryable group；
- 是否存在明确且可信的下钻授权。

### 根因五：权威结果引用只覆盖页面族

当前 Query Turn 已能保存 `PageFamily` 排行投影，供下一轮 `pageViews` 使用；但尚未形成同等级的 `WebApplication` 排行引用，无法独立、可信地完成“第一名业务 -> 该业务页面”的第二轮补名和下钻。

## 6. 统一解决方案

修复不能只增加一个针对原句的正则。需要在意图、规划、决策、状态和叙述五个边界建立一致契约。

### 6.1 结构化意图成为不可变请求事实

`WorkflowClassifierService` 继续作为统一语义来源，并明确提供：

```json
{
  "operation": "ranking",
  "workflowType": "metric_topn",
  "targetObjectType": "WebApplication",
  "metricSemantic": {
    "metricId": "PGNPGE",
    "domain": "page_access_count"
  },
  "drilldownRequested": false
}
```

要求：

- `targetObjectType` 表示用户本轮要求返回的对象，不得被执行期修复覆盖；
- “页面访问量”由 Metric Semantic Normalizer 解释为 `PGNPGE`；
- 是否下钻由结构化 `operation/drilldownRequested` 表达，不由 Query Decision 新增同义正则；
- Prompt Routing、Workflow Classifier、Path Planner 和 Query Decision 不得各自定义一套“业务页面”规则。

### 6.2 收紧 Group Path Planner 的授权条件

普通排行、趋势和平均值满足以下条件时，不得扩展路径：

```text
currentTerminalType == structured targetObjectType
AND operation != drilldown
AND drilldownRequested != true
AND no trusted follow-up reference
```

即使 prompt 命中 `page_family` 概念，也只能把它作为候选信息，不能形成可执行路径。

只有以下情况可扩展 `WebApplication > PageFamilies > PageFamily`：

- 结构化操作明确为 `drilldown`；
- 当前轮绑定上一轮可信 `WebApplication` 结果引用；
- 已解析出具体 `WebApplication.argument`；
- planner proof 与静态 groups tree 一致。

### 6.3 分离 requested target 与 effective terminal

`RequirementParserService` 不再覆盖 `semanticConstraints.targetObjectType`。规划结果单独记录，例如：

```json
{
  "semanticConstraints": {
    "targetObjectType": "WebApplication"
  },
  "executionBinding": {
    "effectiveTerminalGroupType": "PageFamily"
  }
}
```

若是合法下钻，还应显式记录：

```json
{
  "pathPlanning": {
    "followUpAction": "drilldown",
    "sourceObjectType": "WebApplication",
    "targetObjectType": "PageFamily"
  }
}
```

这样 Query Decision 可以判断目标变化是用户授权的下钻，还是执行期漂移。

### 6.4 Query Decision 增加语义目标一致性门禁

在多 group 技术路径校验之外增加统一策略：

```text
普通 metric_topn / metric_timeseries / metric_average：
  terminalGroupType 必须等于 structured targetObjectType

明确 drilldown：
  允许 terminalGroupType 变化，但必须有可信来源引用、明确目标和静态路径证明
```

原句若收到 `PageFamily` 终端路径，应返回：

```json
{
  "action": "REJECT_QUERY",
  "outcome": "VALIDATION_FAILURE",
  "reasonCode": "SEMANTIC_TARGET_PATH_MISMATCH",
  "southboundAllowed": false
}
```

该失败进入现有一次 Query Attempt 修复预算；修复后的正确 Draft 应收口为单 group `WebApplication`。修复失败则终止，不允许带着错误 PageFamily 路径继续执行。

### 6.5 扩展 Query Turn 的权威排行引用

将当前只保存 `PageFamily` 的结果投影扩展为受控的通用 Query Result Reference：

```text
ResultReferenceSet
  - resultSetId
  - sourceTurnId
  - conversationKey
  - objectType
  - timeRange
  - rows[]
      - ordinal
      - rowRef
      - objectArgument / objectId
      - label
```

至少支持：

- `WebApplication`：保存业务名作为后续 group argument；
- `PageFamily`：保存可信 `pageFamilyId`；
- 后续是否支持访问实例引用，另按跨 Skill 安全边界设计。

第二轮用户只说“排名第一的都访问了什么”时，插件应：

1. 从新 Query Turn 冻结的上一轮 `WebApplication` 结果集解析 ordinal=1；
2. 补入具体 `WebApplication.argument`；
3. 构造并验证 `WebApplication(argument) > PageFamilies > PageFamily`；
4. 继承上一轮权威时间范围；
5. 引用不存在、过期、越界或跨 scope 时澄清，且零南向调用。

### 6.6 排行结果归一化与叙述校验

对于“最高/TopN”查询：

- 数值字段必须按数值而非字符串解释；
- 若服务契约要求客户端排序，按 `sortOrder=desc` 排序后再生成 rank；
- 若上游返回权威 rank，必须验证 rank 与数值方向一致；
- 无法确认顺序时不得展示“排名 1/2/3”，应明确返回原始顺序及警告；
- 表头使用结构化目标对象标签，第一轮必须显示业务/WebApplication，不能显示 PageFamily。

## 7. 零南向调用边界

以下情况必须在 Query Skill、`NapmClient` 和南向接口之前终止：

| 场景 | 预期结果 |
| --- | --- |
| 普通业务排行却以 `PageFamily` 为终端 group | `SEMANTIC_TARGET_PATH_MISMATCH` |
| 只有静态路径证明，没有结构化 drilldown 操作 | `SEMANTIC_TARGET_PATH_MISMATCH` |
| 第二轮序号引用缺失或过期 | 澄清或 `VALIDATION_FAILURE` |
| WebApplication 引用跨 conversation scope | `RESULT_REFERENCE_SCOPE_MISMATCH` |
| 排名序号越界 | `RESULT_REFERENCE_ORDINAL_OUT_OF_RANGE` |
| resultSet 对象类型不是 WebApplication | `RESULT_REFERENCE_OBJECT_TYPE_MISMATCH` |

所有上述场景都要求：

```text
Query Skill calls = 0
NapmClient calls = 0
southbound calls = 0
```

## 8. 回归测试计划

### 8.1 统一意图分类

1. “今天哪些业务页面访问量最高？”得到 `metric_topn + WebApplication + PGNPGE`。
2. “今天哪些页面访问量最高？”得到 `metric_topn + PageFamily + PGNPGE`。
3. “排名第一的业务都访问了什么？”得到明确 `drilldown + WebApplication -> PageFamily`。
4. 不在 Query Decision、插件或 Planner 中另加平行的业务页面同义正则。

### 8.2 路径规划

1. 正确单 group `WebApplication` 即使开启一次结构修复，也不得因“页面访问量”扩展路径。
2. 路径规划不得覆盖 `semanticConstraints.targetObjectType`。
3. 带可信业务引用的明确下钻可生成 `WebApplication(argument) > PageFamilies > PageFamily`。
4. 只有页面概念、没有 drilldown 操作的多级路径不得执行。

### 8.3 Query Decision 和直接 Tool 执行

1. 原句配错误 PageFamily 多级 Draft 返回 `SEMANTIC_TARGET_PATH_MISMATCH`。
2. Query Skill、`NapmClient.get/getJson/post` 和南向执行次数均为 0。
3. direct execute 与 Hook 路径执行相同策略。
4. 正确单 group `WebApplication + PGNPGE` 保持可执行。
5. 合法、明确并带可信来源的第二轮下钻保持可执行。

### 8.4 真实多轮生命周期

测试不得手工预先构造第二轮业务名或第三轮 `pageFamilyId`：

1. 第一轮返回多个 `WebApplication`，结果集形成可信行引用；
2. 第二轮仅回复“排名第一的都访问了什么”，从第一轮解析业务名并查询该业务页面族；
3. 第三轮仅回复“详细查看排名第一的前 20 个”，从第二轮解析 `pageFamilyId` 并执行 `pageViews`；
4. 重叠 run 不串用结果集；过期、跨 scope 和越界引用均零南向调用；
5. 三轮权威 finalContent 均 exactly-once，后续失败不得覆盖前序成功结果。

### 8.5 排行与叙述

1. 第一轮表头和对象名称必须是业务/WebApplication。
2. “最高”结果按数值降序，rank 与值一致。
3. 第二轮表头才允许使用 PageFamily。
4. 0 行生成 `NO_DATA`，不能复用上一轮排行。

## 9. 实施顺序

### 阶段一：锁定失败测试

先用现场原句建立分类器、Planner、Query Decision、direct execute 和完整 Hook 生命周期失败测试，并断言零南向调用。

### 阶段二：修复语义与规划边界

保持 requested target 不可变；收紧 Planner 授权；增加 Query Decision 目标/路径一致性门禁。

### 阶段三：补齐 WebApplication 权威引用

扩展 Query Turn 结果引用类型，完成第一轮业务排行到第二轮页面族排行的补名流程。

### 阶段四：统一排行与叙述

确认 TopN 排序责任，修复数值排序或错误 rank 展示，并保证对象标签来自权威结构化目标。

### 阶段五：完整门禁

执行：

```text
npm test -- --runInBand
npm run lint
npm run verify:runtime-contract
git diff --check
```

不得连接服务器、部署、制作发布包或修改版本号。实现完成并提交后，先交整合任务复审，再进入发布流程。

## 10. 验收标准

- 原句只查询 `WebApplication`，不出现 `PageFamilies/PageFamily`；
- 第一轮回答列出业务名称及 `PGNPGE`，不直接列 URL；
- 错误 PageFamily Draft 在任何南向调用前被阻断；
- 执行期路径修复不覆盖用户请求目标；
- 第二轮必须从权威业务结果引用补入具体业务名；
- 第三轮继续使用已实现的权威 PageFamily 引用执行 `pageViews`；
- 排行数值与 rank 顺序一致；
- direct execute、Hook、重叠 run、引用过期和 exactly-once 测试全部通过；
- 文档、运行时实现和 Tool 契约描述一致。
