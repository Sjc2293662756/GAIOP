# 故障分析 Skill 未触发问题 — 排查与修复复盘

> 日期：2026-06-29
> 问题：企微端用户要求"分析业务238web的故障情况，给出故障报告"，OpenClaw 未调用 `openclaw-napm-fault-diagnosis`，而是用 `openclaw-napm-alert-query` + `napm-skill-query` 零散查询自拼报告
> 状态：已修复，待用户验证

---

## 一、问题表现

用户三次在企微端发送故障分析请求：

```
石嘉成 15:28 — "分析一下回溯238web的故障情况，给出故障报告！"
石嘉成 15:50 — "分析一下回溯238web的故障情况，给出故障报告！"  
石嘉成 16:08 — "分析一下 业务 回溯238web 的故障情况，给出故障报告！"
```

三次 OpenClaw 的响应均为：
- 调用 `openclaw-napm-alert-query` 查告警
- 调用 `napm-skill-query` 零散查询流量/性能数据
- 自己用 LLM 拼叙述
- 调 `napm-report-export` 出 docx

**始终没有调用 `napm-fault-diagnosis`。**

---

## 二、排查过程

### 第一轮排查：Skill 未被插件注册

**发现**：`napm-openclaw-plugin.remote.js` 的 `SAFE_NAPM_TOOL_NAMES` 中只有 6 个 tool：

```javascript
const SAFE_NAPM_TOOL_NAMES = new Set([
  'napm-skill-query', 'napm-report-export', 'napm-packet-analysis',
  'napm-alert-query', 'napm-inspection-snapshot', 'napm-summary'
]);
```

没有 `napm-fault-diagnosis`。OpenClaw 根本不知道这个 tool 存在。

**修复**：
1. 新增 `NAPM_FAULT_DIAGNOSIS_EXECUTOR` 常量
2. 加入 `SAFE_NAPM_TOOL_NAMES`
3. 新增 `createFaultDiagnosisToolDefinition()` — tool 参数定义
4. 新增 `runFaultDiagnosisExecutor()` — CLI 调用封装
5. 新增 `buildFaultDiagnosisReply()` — 结果回复模板
6. `api.registerTool(faultDiagnosisTool)` — 注册 tool
7. 新增 `isFaultDiagnosisPrompt()` — prompt 路由检测
8. 新增 guard：拦截 fault diagnosis prompt 对 `napm-skill-query` / `napm-alert-query` 的调用
9. 系统提示词加入 FAULT DIAGNOSIS ROUTING 规则
10. 新建 `skills/openclaw-napm-fault-diagnosis/scripts/run_fault_diagnosis.js` — CLI 入口

### 第二轮排查：部署到远端

**发现**：本地修改未部署。远端服务器仍加载旧版插件。

**部署文件**：
- `napm-openclaw-plugin.remote.js` (230KB)
- `skills/openclaw-napm-fault-diagnosis/` 完整目录 (8 文件)
- `skills/openclaw-napm-report/services/` 4 个修改文件
- `skills/openclaw-napm-summary/services/` 2 个修改文件
- `skills/openclaw-napm-report/templates/diagnostic/` 3 个模板文件

### 第三轮排查：意图被 query skill 抢占

**发现**：部署后用户再次测试仍失败。排查发现 `openclaw-napm-query` 的 SKILL.md 中有以下规则：

```markdown
第202行: `报错` / `错误` / `异常` / `失败` → On `WebApplication` / `业务` → PGHTTP400 + PGHTTP500
第240行: `现在哪个业务报错最多？` → Service: ranking, Object: WebApplication, Metric: PGHTTP400+PGHTTP500
```

OpenClaw 在意图识别阶段读到这些规则，将"业务 + 故障/报错"直接匹配到 query skill，**根本不考虑其他 skill**。插件层的 guard 拦截发生在 OpenClaw 已经决定调用 `napm-skill-query` 之后——太晚了。

**修复**：在 `openclaw-napm-query/SKILL.md` 的 Skill Boundary 中加入**精确排除条款**：

```markdown
- **给指定业务/应用出故障诊断报告（如"分析XXweb的故障情况，给出故障报告"）
   → use `openclaw-napm-fault-diagnosis`.**
  注意：单个报错查询（如"哪个业务报错最多""XX业务的400数量"）仍然用本 skill
  ——只有"分析故障+出报告"这个组合意图才需要 fault-diagnosis。
```

同时在语义映射规则中加了例外说明：

```markdown
- `报错` / `错误` / `异常` / `失败` (without explicit HTTP/connection context):
  - On `WebApplication` / `业务` → default to `PGHTTP400` + `PGHTTP500`
  - **例外：如果用户意图是"出故障分析报告"，不要把意图拆成多次单指标查询来拼报告
    ——应使用 `openclaw-napm-fault-diagnosis` 一次性完成。单个报错查询不受影响。**
```

## 三、根因总结

```
用户: "分析业务238web的故障情况，给出故障报告"
  ↓
OpenClaw 意图识别:
  ├── 读到 openclaw-napm-query/SKILL.md:
  │   "业务" → WebApplication
  │   "报错/故障" → PGHTTP400 + PGHTTP500  ← 精准匹配，抢占
  │   → 决定调 napm-skill-query
  │
  ├── openclaw-napm-fault-diagnosis:
  │   插件根本没注册这个 tool  ← 根因1
  │   → OpenClaw 不知道它的存在
  │
  └── napm-openclaw-plugin guard:
      部署的是旧版 ← 根因2
      → isFaultDiagnosisPrompt() 不存在
```

**三个层次的问题叠加**：
1. **注册层**：插件没注册 `napm-fault-diagnosis` tool
2. **部署层**：修复后未推送到远端
3. **意图层**：query skill 的 SKILL.md 关键词匹配优先级高于 fault-diagnosis

```
5. 调 napm-report-export → .docx
```

- "哪个业务报错最多" → 仍走 `napm-skill-query` 查 PGHTTP400/500 ✅
