# NAPM 巡检报告误路由根因与修复方案

## 1. 问题现象

用户在企业微信执行 `/new` 后发送：

```text
给我最近七天的系统巡检报告！
```

系统返回的却是 `napm_全局综述报告_20260819_142044.docx`。用户要求的是巡检报告，实际执行和交付的是综述报告。

## 2. 远端证据

2026-08-19 14:20 的测试服务器审计日志形成了完整证据链：

1. 14:20:21，`/new` 清理当前企业微信会话状态成功，排除历史上下文污染。
2. 14:20:41，当前轮绑定的工具是 `napm-summary`。
3. 同一时刻产生 `napm_automatic_summary_started`，其中原始 prompt 是“给我最近七天的系统巡检报告！”，时间范围为 `last7days`。
4. 14:20:44 保存的报告源为 `sourceTool=napm-summary`、`reportType=summary_report`。
5. 14:20:46 生成并发送 `napm_全局综述报告_20260819_142044.docx`。

因此错误发生在报告类型路由阶段，不是巡检数据采集、模板渲染、文件命名或企业微信媒体发送阶段。

## 3. 根因

当前 `isSummaryPrompt()` 包含“报告 + 时间上下文”的宽泛兜底：

```js
if (/报告/.test(text) && /(?:最近|今天|昨天|本周|本月|过去)/i.test(text)) {
  return true;
}
```

“给我最近七天的系统巡检报告！”同时包含“最近”和“报告”，因此被判定为 summary。当前插件没有独立的 `isInspectionPrompt()` 或统一互斥的报告类型分类器。

`reply_dispatch` 和发送兜底又在 `isSummaryPrompt()` 为真时直接调用 `runAutomaticSummaryReportDelivery()`。该流程固定执行 `napm-summary`，所以一旦入口误判，后续 `reportType=summary_report`、综述模板和综述文件名都是错误路由的必然结果。

项目已有的《2026-07-30-巡检报告路由与企业微信阻断回包修复》声明巡检分类优先于综述，但 rc.12 当前源码没有对应实现，说明历史文档与统一仓库实际运行代码不一致。

## 4. 修复原则

1. 巡检、综述、已有结果导出必须是互斥报告类型，不能由多个独立布尔函数重叠命中。
2. 高置信巡检请求固定走 `napm-inspection-snapshot → napm-report-export`。
3. 高置信综述请求继续走 `napm-summary → napm-report-export`。
4. 报告导出器只消费上游确定的 `reportData`，不得根据标题或文件名猜测报告类型。
5. 复杂混合请求不由前置自动报告路径抢占，保留给模型按完整工作流处理。
6. 不修改巡检、综述固定模板，不影响普通查询、告警、数据包和故障诊断流程。

## 5. 统一报告分类

新增纯函数模块 `plugin/ReportIntentClassifier.js`，统一返回：

```text
inspection | summary | export | mixed | none
```

分类优先处理显式报告类型：

- 巡检：巡检、巡检报告、健康检查、健康检查报告、健康巡检、inspection、health check。
- 综述：综述报告、全局综述、业务综述、应用综述、业务组综述、网络综述、告警综述、summary report、overview report。
- 周期综述：日报、周报、月报。
- 已有结果导出：将以上/刚才/这个结果导出为 Word、docx 或 PDF。

同时出现巡检和综述，或者同时要求巡检与故障诊断报告时，返回 `mixed`，不自动执行任何一种报告。故障诊断报告和数据包分析报告不进入通用 summary 兜底。仅有“报告 + 最近/今天/昨天/本周/本月/过去”且没有明确报告类型时，为兼容现有行为返回 `summary`。

原有 `isSummaryPrompt()` 和新增 `isInspectionPrompt()` 都委托该分类器，避免再次出现交叉命中。

## 6. 巡检自动交付

新增 `buildAutomaticInspectionToolArgs()` 和 `runAutomaticInspectionReportDelivery()`，复用现有 Tool 定义和可信上下文：

```text
reply_dispatch
→ classifyReportPrompt(prompt)=inspection
→ inspectionSnapshotTool.execute()
→ 获得 reportType=inspection_report 的 reportSourceId
→ reportExportTool.execute()
→ dispatcher.sendFinalReply()
→ handled=true
```

巡检自动交付必须校验：

- snapshot 结果 `ok=true`；
- `reportData.reportType=inspection_report`；
- `reportData.templateId=napm_traffic_health_inspection_v1`；
- report source 来自 `napm-inspection-snapshot`；
- 导出结果成功并具有媒体文件路径。

任一校验失败时记录确定性错误，不允许降级调用 `napm-summary`。

## 7. Tool 边界

`before_tool_call` 增加当前轮报告类型判断：

- inspection 请求允许 `napm-inspection-snapshot` 和对应 `napm-report-export`；
- inspection 请求阻止 `napm-summary` 和 `napm-skill-query`；
- summary 请求维持现有 `napm-summary` 边界；
- mixed 请求不进入自动报告分支，由模型处理或澄清；
- 已有结果导出继续优先使用当前会话中明确的 `reportSourceId`。

## 8. 幂等与审计

以 `conversationKey + turnId + reportKind` 作为自动工作流键，同一轮只执行一次快照、一次导出和一次发送。

新增审计事件：

```text
napm_automatic_inspection_started
napm_automatic_inspection_completed
napm_automatic_inspection_failed
napm_inspection_report_dispatched
```

审计字段至少包含 `conversationKey`、`turnId`、`sourceTool`、`reportType`、`templateId`、`reportId` 和媒体路径摘要。

## 9. 回归测试

测试必须覆盖真实 `reply_dispatch` 生命周期，不能预置最终报告后直接调用 Hook：

1. “给我最近七天的系统巡检报告！”只调用 inspection snapshot 和 report export。
2. 结果为 `inspection_report`，模板为 `napm_traffic_health_inspection_v1`，文件名包含“巡检报告”。
3. 当前轮不调用 `napm-summary`。
4. “给我最近七天的系统综述报告！”仍只调用 summary 和 report export。
5. “生成最近七天的报告”保留现有 summary 兼容行为。
6. “先巡检再生成综述报告”返回 mixed，不被前置路径抢占。
7. 同一轮重复 dispatch 不重复查询、导出或发送。
8. `/new` 后首轮巡检正确路由。
9. 巡检失败不回退 summary。
10. 普通 NAPM 查询、告警、数据包和故障诊断回归不变。

## 10. 发布验收

本地通过定向测试、全量 Jest、lint、生产 Tool 运行时契约、Node 语法和 `git diff --check` 后，才能升级新的 rc 版本并执行统一发布流程。

测试服务器必须按 `verify-staged-release.sh → install-release.sh --dry-run → install-release.sh` 部署。真实企业微信验收必须同时满足：

- 日志出现 `napm_automatic_inspection_started` 和 `napm_automatic_inspection_completed`；
- 报告源为 `sourceTool=napm-inspection-snapshot`；
- 报告类型为 `inspection_report`；
- 模板为 `napm_traffic_health_inspection_v1`；
- 最终文件名和文档标题均为巡检报告；
- 当前轮没有 `napm_automatic_summary_started`，也没有第二个报告媒体回复。

## 11. 实施结果

2026-08-20 已按本方案完成本地实现，尚未构建或部署：

1. 新增 `plugin/ReportIntentClassifier.js`，统一巡检、综述、已有结果导出、混合和非报告分类。
2. `isSummaryPrompt()` 改为委托统一分类器；新增巡检和报告工作流判断，巡检不再命中 summary。
3. 新增前置巡检自动交付，固定执行 `napm-inspection-snapshot → napm-report-export`，并校验 `inspection_report` 和 `napm_traffic_health_inspection_v1`。
4. `reply_dispatch` 和兼容发送入口按同一个报告分类分流；巡检失败返回确定性错误，不回退 summary。
5. `before_tool_call` 阻止巡检请求调用 `napm-summary`、`napm-skill-query` 或其他错误 NAPM Tool。
6. 自动报告操作和最终发送按当前会话与 `turnId` 去重；`/new` 同时清理自动报告操作状态。
7. 发布构建的必需文件清单已加入 `plugin/ReportIntentClassifier.js`，避免制品遗漏运行时模块。
