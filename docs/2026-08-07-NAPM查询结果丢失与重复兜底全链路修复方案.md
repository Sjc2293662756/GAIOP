# NAPM 查询结果丢失与重复兜底全链路修复方案

日期：2026-08-07  
适用范围：`napm-skill-query`、`napm-summary`、`napm-report-export`、`napm-alert-query`、`napm-fault-diagnosis`、`napm-inspection-snapshot`、`napm-packet-analysis`，以及 OpenClaw 到企业微信的回复投递链路。

## 1. 问题结论

本次故障不是“现在系统情况怎么样”一句话未命中路由，而是 NAPM 全链路同时存在三类缺陷：

1. 查询规划缺陷：模型可以构造规范外的 `service` 或缺失必填字段，导致查询在 NAPM 执行前失败。
2. 结果关联缺陷：工具结果以可变的 prompt 文本作为身份键，元数据前缀改写 prompt 后，成功结果无法被当前轮次取回。
3. 消息生命周期缺陷：输出守卫把携带 `toolCall` 的中间 assistant 消息当成最终答案，并在每个工具阶段生成一次兜底。

因此必须按“轮次身份 + 工具执行结果 + 最终投递”整体修复，不能为某个问句增加特判。

## 2. 生产证据

已对 13 个工具型会话按以下顺序重建：

```text
user -> assistant/toolCall -> toolResult -> assistant -> WeCom delivery
```

统计结果：

- 8 个用户轮次出现兜底。
- 至少 6 个轮次是 NAPM 结果成功后仍出现兜底。
- 会话中共出现 44 条重复兜底 assistant 消息。
- 影响路径覆盖普通查询、综述、报告导出、告警、故障诊断、巡检和数据包分析。

典型证据：

- “现在系统情况怎么样？”的 `napm-summary` 成功返回 `overallStatus=critical`、55 条告警，模型也已生成完整最终答复，但落盘会话中被替换为兜底。
- 业务七天综述的 `napm-summary` 和 `napm-report-export` 都成功，DOCX 也已发送，但两次工具调用阶段和最终回复共被改写三次。
- 告警查询成功返回 `ok=true, service=alertsSummary`，但结果被输出守卫二次改写。
- 故障诊断返回 `Required diagnostic queries failed for step1_4xx_5xx_overview`，具体错误被通用兜底隐藏。
- “过去 24 小时的吞吐量趋势如何？”共调用 `napm-skill-query` 8 次，先后构造 `timeseries`、`trend`、`q_trend`、`q_timeseries`、`series` 等无效 service，最后又错误地使用 `topValues + groups:[{type:"time"}]`。

远端 `openclaw-gateway.service` 处于 `active` 状态；远端插件 SHA-256 与本地当前插件完全一致，因此本结论针对当前生产实现。

## 3. 根因分析

### 3.1 prompt 被当成结果身份

`rememberSkillResult()` 使用：

```text
conversation scope + normalize(prompt)
```

作为结果键。`before_prompt_build` 和 `before_agent_start` 的同一处 handler 会用元数据前缀 prompt 再次覆盖会话状态。工具执行时保存的通常是干净用户问题，输出钩子查找的却是以下文本：

```text
Conversation info (untrusted metadata):
...
原始用户问题
```

同一 conversation scope 下 prompt key 不同，导致假性“未拿到 skill 结果”。已排除 conversation scope 不一致假设。

### 3.2 中间 toolCall 被当成最终消息

`before_message_write` 会处理每一条 assistant 消息，包括携带 `toolCall` 的中间消息。`buildAssistantTextMessage()` 将整个 `content` 数组替换为一个 text block，直接删除了 `toolCall`。

这同时导致：

- 会话 JSONL 中出现没有前置 toolCall 的孤立 toolResult。
- 后续模型看到损坏的工具历史。
- 每多一个工具阶段，就多生成一次兜底。
- 报告、告警数据包等多工具流程受影响最明显。

### 3.3 中间预览处理顺序错误

`message_sending` 先执行“内部推理/绕过 skill 检测并改写”，后执行“取消 streaming preview”。因此本应静默取消的中间过程，先被改成用户可见兜底。

### 3.4 查询 Schema 与解析规范不一致

`napm-resolution-spec.v1.json` 声明的合法主要映射是：

| 用户意图 | service | queryModeKey |
| --- | --- | --- |
| TopN/排行 | `topValues` | `topn` |
| 平均/均值 | `averageValues` | `average` |
| 趋势/曲线 | `timeValues` | `timeseries` |
| 概览/状态 | `overview` | `overview` |
| 对象清单 | `groups` | `metadata` |
| 指标清单 | `metrics` | `metadata` |
| 下钻目录 | `drilldownCatalog` | `metadata` |

但当前工具 Schema 中 `service` 只是普通 string，且缺少以下必填属性：

- `timeValues.granularity`
- `overview.overviewScene`
- `topValues_multi_protocol.protocolQueries`

路由上下文也没有完整展开 service 映射，并引用了实际不存在的 `query-workflow-contract.md`。

### 3.5 失败结果的工具语义不准确

`makeToolResult()` 没有根据 `result.ok` 和 `result.error` 设置错误标志。解析规范拒绝的调用在会话中仍记录为 `isError=false`，导致模型在缺少确定修复提示时反复猜测 service，甚至尝试 `exec`、`read`、`memory_search`。

### 3.6 测试与生产代码脱节

14 个插件守卫测试仍加载 `.codex-temp/napm-openclaw-plugin.remote.js`，只有少数运行时和报告交接测试加载根目录当前插件。旧副本与当前/生产插件 SHA-256 不同。

当前全量测试虽然为 43 个套件、254 个用例通过，但没有覆盖：

- 元数据前缀 prompt。
- `before_message_write` 缺少 runId/messageId 的精简上下文。
- 携带 `toolCall` 的 assistant 消息。
- 多工具报告链。
- 单轮兜底次数。
- 当前根目录插件的输出钩子。

## 4. 修复设计

### 4.1 稳定轮次身份

1. `message_received` 为新轮次创建稳定 `turnId`。
2. 原始消息保存为只读 `canonicalPrompt`。
3. `before_prompt_build`/`before_agent_start` 只派生路由标记，不再覆盖 `canonicalPrompt` 和 `turnId`。
4. `before_tool_call` 绑定 `traceId -> conversation scope + turnId + toolName`。
5. 工具成功、无数据、参数错误和 NAPM API 错误都记录到当前 turn。
6. 输出钩子优先按 `turnId` 取结果，prompt 只用于旧记录兼容和审计。

### 4.2 正确的消息生命周期

1. `before_message_write` 发现 assistant 消息包含 `toolCall` 时必须原样保留。
2. `message_sending` 必须在任何文本改写前先取消 streaming/preview 输出。
3. 只有已完成的最终消息才能进入结果校验。
4. 每轮兜底最多发送一次；重复投递必须取消。
5. 已有当前轮次结果时，不能使用“未拿到 skill 结果”。
6. 结构化工具错误必须保留具体错误码、失败步骤和可采取的下一步。

### 4.3 查询契约单一真相源

1. 从 `napm-resolution-spec.v1.json` 生成 `service` 枚举和详细字段描述。
2. 补齐 `granularity`、`overviewScene`、`protocolQueries`、`filters`、`executionOptions` 等字段。
3. 将意图到 service/queryModeKey 的完整映射注入路由上下文。
4. 删除或修正不存在的文档引用。
5. 解析失败返回 `allowedServices`、`expectedQueryModeKey` 和 `requiredFields`，限制重构重试次数。
6. 严格校验“趋势语义却使用 topValues”等语义不一致，不能只校验 JSON 字段完整性。

### 4.4 测试策略

所有插件测试必须加载根目录当前插件。新增生产形态回归覆盖：

| 类型 | 必须验证 |
| --- | --- |
| TopN/平均/趋势/概览 | service 和 queryModeKey 正确，成功结果到达用户 |
| 对象/指标/下钻清单 | metadata 路径正确，无手工推测 |
| 综述 -> 报告 | 两次 toolCall 保留，文本只投递一次，文件只投递一次 |
| 告警 -> 数据包 | 交接结果与最终答案都属于同一 turn |
| 故障诊断/巡检/数据包 | 成功、无数据和结构化失败分流 |
| 企业微信 | 元数据 prompt、精简 write ctx、streaming preview、单轮一次兜底 |
| 会话完整性 | 每个 toolResult 都有对应 toolCall，不得产生孤立 toolResult |

## 5. 实施顺序

1. 先新增加载当前插件的失败回归测试，确认可稳定复现。
2. 实现 turn-aware 操作状态和 trusted trace 绑定。
3. 修复 `message_received`、`before_prompt_build`、`before_tool_call`、`message_sending`、`before_message_write` 的生命周期。
4. 补齐工具 Schema、路由映射和失败语义。
5. 将所有旧 `.codex-temp` 插件测试切换到当前插件。
6. 运行专项测试、全量测试、运行时契约预检和语法检查。
7. 备份测试服务器当前插件、辅助模块和配置。
8. 部署本地已验证文件，重启网关，执行生产形态的无外部投递冒烟测试。

## 6. 验收标准

1. NAPM 成功结果不再被“未拿到 skill 结果”替换。
2. 携带 `toolCall` 的 assistant 消息不被改写，会话中无孤立 toolResult。
3. 单个用户轮次最多一条最终文本兜底。
4. 趋势查询稳定使用 `service=timeValues, queryModeKey=timeseries`。
5. 平均、TopN、概览、清单和下钻均使用规范声明的 service。
6. 报告多工具链文本不重复，DOCX 不重复发送。
7. 结构化工具错误对用户可见，不被通用兜底隐藏。
8. 根目录当前插件的专项回归和全量测试全部通过。
9. 测试服务器网关保持 `active`，新增日志不出现连续改写和无效 service 重试。

## 7. 不采用的局部方案

以下方案不能单独作为正式修复：

- 只为“现在系统情况怎么样”增加关键词或硬编码路由。
- 只删除兜底文案，但仍保留 prompt 关联和 toolCall 改写。
- 只关闭企业微信 `sendThinkingMessage`。这可作为防御性配置，但无法修复会话落盘损坏和最终结果被覆盖。
- 只为 `timeseries` 增加别名。这无法解决其他无效 service、缺失必填字段和语义不一致。

本方案的目标是一次解决同一类的“真失败、假失败、结果被覆盖、兜底重复”问题，而不是修补某一条问句。

## 8. 实际实施结果

### 8.1 轮次身份与结果关联

已实现以下状态约束：

- `message_received` 为每个用户轮次创建稳定 `turnId`，并保存不可被路由元数据覆盖的 `canonicalPrompt`。
- `before_prompt_build` 和 `before_agent_start` 只更新派生路由状态，不再用带元数据前缀的 prompt 覆盖原始问句。
- `before_tool_call` 将 `traceId` 与 conversation scope、`turnId`、工具名绑定，并将可信上下文写入持久化存储。
- 工具完成后按 `scope + turnId` 记录成功、无数据、执行失败和边界校验失败结果。
- 输出阶段优先按当前 `turnId` 读取结果；prompt 关联仅保留为旧记录兼容手段。

### 8.2 消息生命周期

已完成以下修复：

- `before_message_write` 检测到 assistant 消息包含 `toolCall` 时原样保留，避免产生孤立 `toolResult`。
- `message_sending` 在任何绕过检测或兜底改写之前先取消 streaming/preview 消息。
- 通用兜底增加单轮投递标记，同一轮第二次及后续兜底直接取消。
- 当前轮已存在 skill 成功、无数据或结构化错误记录时，不再改写成“本轮未拿到有效 skill 结果”。
- 构造阶段在 `before_tool_call` 被阻断、工具 `execute()` 根本未运行时，也会先把结构化校验失败写入当前轮次。

最后一项是在首次远端冒烟中发现的遗漏分支。若只在 `execute()` 中记录失败，`before_tool_call` 的硬阻断仍会被输出层误认为没有 skill 结果。

### 8.3 查询契约

已完成以下修复：

- `napm-skill-query` 的 `service` 枚举由 `napm-resolution-spec.v1.json` 派生。
- 补齐 `granularity`、`overviewScene`、`protocolQueries`、`filters`、`executionOptions` 等字段。
- 路由上下文完整声明 `topValues/topn`、`averageValues/average`、`timeValues/timeseries`、`overview/overview` 及 metadata service 映射。
- 删除不存在的规范引用，改为仓库内真实文档路径。
- 边界校验失败返回 `isError=true`、`allowedServices`、`expectedQueryModeKey`、`requiredFields` 和具体错误信息。
- 对对象清单、复合应用清单及通用 resolvedQuery 语义不一致统一记录当前轮结构化失败。

### 8.4 丢包指标与数据包操作的语义隔离

第二次远端 E2E 暴露了另一个同类路由问题：英文 `packet loss` 中的普通单词 `packet` 被旧正则直接判定为抓包请求。结果是合法的 `PLI + IPAddress + topValues` 排行被强制导向 `napm-packet-analysis`，模型随后连续尝试 query、read、exec、memory 和 session 工具，均收到相同 packet 守卫提示。

现已将 `isPacketCapturePrompt()` 改为操作意图判定：

- `packet loss`、`loss rate`、`PLI`、`丢包`、`丢包率`属于性能指标语义，继续进入 `napm-skill-query`。
- `抓包`、`下载数据包`、`原始报文`、`PCAP/CAP`、packet capture/download/analysis/details 属于数据包工件或操作语义，进入 `napm-packet-analysis`。
- 同时保留真正抓包请求禁止使用 shell/curl 绕过专用 skill 的安全限制。

该修复不是为某一句话增加特例，而是把“性能指标”和“数据包工件”拆成两个可测试的意图类别。

## 11. 最终结论

本次修复覆盖的是一组共享机制，不是单一问句：轮次身份、工具结果关联、构造阶段错误、消息写入、preview、兜底去重、查询 schema 和相邻 skill 意图隔离均已纳入回归测试。

对于未来新增的 service 或新工具，仍必须同时更新 resolution spec、schema 派生、意图分类正反样例和远端无投递冒烟；不能再通过扩大关键词正则或增加单句硬编码来修复路由问题。
