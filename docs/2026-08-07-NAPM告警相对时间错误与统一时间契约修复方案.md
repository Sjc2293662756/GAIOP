# NAPM 告警相对时间错误与统一时间契约修复方案

日期：2026-08-07  
适用范围：`napm-alert-query`、`napm-skill-query`、公共时间解析器、OpenClaw NAPM 插件及告警 API 查询链路

## 1. 问题现象

同一时刻连续执行以下查询：

```text
最近一小时的告警情况 -> 57 条
/new
最近三小时的告警情况 -> 0 条
```

第二次查询展示的 Debug API 为：

```text
type=alertsSummary&start=1754542560&end=1754552160
```

实际含义是：

| 字段 | 实际时间 |
| --- | --- |
| `start=1754542560` | 2025-08-07 12:56 CST |
| `end=1754552160` | 2025-08-07 15:36 CST |
| 实际跨度 | 160 分钟 |
| 用户要求 | 2026-08-07 最近 3 小时，即 180 分钟 |

因此“0 条告警”不是可信业务结果，而是错误时间窗口产生的无效查询结果。

## 2. 复现证据

故障会话中，模型调用 `napm-alert-query` 时已经生成错误参数：

```json
{
  "prompt": "最近三小时的告警情况",
  "mode": "summary",
  "criteria": {
    "start": 1754542560,
    "end": 1754552160
  }
}
```

使用相同 payload 和固定服务器时间分别在本地、远端直接调用 alert skill，均稳定复现：

```text
最近一小时 + start/end=0
-> start=1786089360, end=1786092960, key=last1hour

最近三小时 + 错误非零 start/end
-> 原样保留 2025 时间, key=custom
```

这排除了以下假设：

- `/new` 与下一条消息并发导致状态串线；
- NAPM 后端在三小时内确实没有告警；
- 远端加载了另一份旧的 workspace skill；
- 身份问题门禁增量直接改坏告警时间代码。

## 3. 当前时间架构

项目不是完全没有公共时间规则，当前已有：

```text
ResolvedQueryTimeRangeService
  -> 解析标准 timeRange.key
  -> 生成分钟对齐的 start/end

timeResolver
  -> 为 query/fault 等执行入口提供统一执行时间对象

各 skill
  -> 部分复用公共解析器
  -> 部分仍自行解析用户自然语言时间
```

当前公共解析器支持：

```text
today
yesterday
lastNminutes
lastNhours
lastNdays
```

但插件 schema 又声明支持 `lastNseconds`，告警 skill 也把所有自然语言相对时间转换为：

```text
last${durationSeconds}seconds
```

这形成了“声明支持、调用方生成、执行器不识别”的契约断裂。

## 4. 根因分析

### 4.1 模型被要求生成绝对时间戳

`napm-alert-query` 工具 schema 当前写明：

```text
Executable modes require start/end Unix-second timestamps.
```

这使模型承担了本应由服务器负责的年份、时区、当前时间和时间跨度计算。模型输出不是可信系统时钟，不能作为最终执行参数。

### 4.2 告警相对时间生成了公共解析器不支持的 key

告警 skill 能识别“最近三小时”，但随后生成：

```text
last10800seconds
```

公共 `ResolvedQueryTimeRangeService` 没有 seconds 分支，返回不支持。告警函数把“不支持”折叠成 `null`，没有暴露错误。

### 4.3 解析失败后静默信任模型时间

相对时间解析返回 `null` 后，执行入口继续使用 `criteria.start/end`。只要模型给出的两个数字满足 `end > start`，就会被当成合法 `custom` 时间范围，即使年份和跨度与用户要求完全不一致。

### 4.4 一小时查询正确只是偶然

第一次“最近一小时”调用中，模型传入 `start=0,end=0`。相对时间解析同样失败，但公共执行器在没有有效显式时间时使用默认 `last1hour`，所以碰巧得到正确窗口。

这不是“一小时支持、三小时不支持”，而是同一缺陷在不同模型参数下产生了不同结果。

### 4.5 插件门禁没有规范化当前用户 prompt

`before_tool_call` 当前主要绑定 `traceId`，告警分支直接放行模型参数。故障调用虽然保留了 prompt，因此这不是本次首要根因，但如果模型遗漏或改写 prompt，skill 将彻底失去从原始问题重建时间的依据。

## 5. 统一时间契约

### 5.1 单一所有权

统一规则如下：

1. 模型只声明用户时间意图，不生成可信执行时间。
2. 相对时间统一由服务器当前时钟生成 `start/end`。
3. 所有执行时间在公共解析器中完成分钟对齐。
4. skill 和 API client 只能消费公共解析器返回的执行时间对象。
5. 用户明确给出固定日期/时刻时，才允许进入固定时间模式。
6. 相对时间与模型绝对时间冲突时，以用户原始 prompt 和服务器时钟为准。
7. 相对时间无法解析时必须结构化失败，禁止静默退化成 `custom`。

### 5.2 标准时间 key

标准 key 统一为：

```text
today
yesterday
last<number>minutes
last<number>hours
last<number>days
```

公共层同时兼容已有 `last<number>seconds` 声明，但只接受能够按分钟执行的范围，并最终规范化为统一执行时间。新代码不再主动生成 seconds key。

### 5.3 告警默认时间

| 用户表达 | 执行规则 |
| --- | --- |
| 最近/当前告警，未给范围 | 默认最近 1 小时 |
| 最近三小时 | 服务器当前分钟向前 3 小时 |
| 最近 90 分钟 | 服务器当前分钟向前 90 分钟 |
| 最近半小时 | 服务器当前分钟向前 30 分钟 |
| 最近七天 | 服务器当前分钟向前 7 天 |
| 今天/昨天 | 使用服务器本地时区自然日 |
| 明确固定起止时间 | 固定时间模式，校验两端和时区 |

## 6. 修复设计

### 6.1 公共时间解析器

1. 补齐标准 key 与既有 seconds key 的契约一致性。
2. 提供从时长生成规范 key 的公共函数，禁止各 skill 自行拼接字符串。
3. 保持分钟对齐和不可变执行时间对象约束。

### 6.2 告警 skill

1. 中文数字、阿拉伯数字、半小时等表达转换成受支持的规范 key。
2. 用户 prompt 含明确相对时间时，无条件覆盖模型 `start/end`。
3. 相对时间识别成功但公共解析失败时返回明确错误码。
4. 在结果 warnings 中记录被覆盖的原始时间和最终执行窗口，便于审计。
5. 没有时间表达且没有固定时间时，继续使用默认最近 1 小时。

### 6.3 JavaScript 插件边界

1. `before_tool_call` 为 `napm-alert-query` 注入当前轮 canonical prompt。
2. schema 改为优先声明 `criteria.timeRange.key`，相对时间不得要求模型生成 `start/end`。
3. `start/end` 仅用于用户明确指定的固定时间，并要求固定时间模式。
4. 插件不得覆盖 skill 最终基于服务器时钟生成的执行时间。

### 6.4 失败策略

以下情况必须停止查询并返回结构化错误，不能展示“0 条”：

- 用户明确要求相对时间，但无法解析；
- 时间 key 不受支持；
- 固定时间缺少一端；
- `end <= start`；
- 时间单位或跨度超过执行上限；
- 相对时间被错误降级为 `custom`。

## 11. 最终结论

本次故障不是三小时问句特例，而是时间所有权分散和契约不一致造成的系统性问题。修复后，模型不再拥有相对查询的绝对时间戳；普通查询和告警查询共享同一个自然语言时间解析器，summary/fault 等执行入口继续消费公共不可变执行时间对象。

以后新增查询 skill 时，必须复用 `ResolvedQueryTimeRangeService` 和 `timeResolver`，不得再次自行解析中文时间、拼接未经公共解析器声明的 key，或信任模型生成的相对时间 `start/end`。

## 12. 时间正确性保证与边界

### 12.1 已建立的保证

对于 NAPM 用户查询执行窗口，系统现在提供以下确定性保证：

1. “最近 N 分钟/小时/天”由测试服务器当前时钟生成，不采用模型计算的绝对时间戳。
2. 中文数字、阿拉伯数字、半小时和小数时长先规范化为公共时间 key，再生成 `start/end`。
3. `start/end` 统一向下对齐到分钟，执行前保证 `end > start`。
4. 用户 prompt 中存在相对时间时，该时间意图覆盖模型提供的错误年份、错误跨度和错误 `custom` 范围。
5. 模型遗漏 prompt 时，插件从当前轮会话状态注入 canonical prompt。
6. `/new` 只重建会话，不参与时间计算；新会话仍使用服务器当前时钟。
7. 相对时间无法解析或超出支持范围时，查询失败关闭，不访问 NAPM API，也不返回伪造的“0 条”。
8. Debug API、结构化 `criteria`、展示的时间范围使用同一个最终执行窗口。

因此，本次出现的以下故障模式已经被阻断：

```text
用户要求最近三小时
-> 模型生成 2025 年时间
-> skill 静默按 custom 查询
-> 返回 0 条并当成真实结果
```

### 12.2 支持的相对时间示例

以下表达使用同一公共规则：

```text
最近一小时
最近三小时
最近3小时
过去七小时
最近90分钟
最近半小时
最近七天
今天
昨天
```

未明确范围的“最近告警”“当前告警”继续采用告警查询默认值：最近 1 小时。

### 12.3 明确固定时间的边界

用户明确指定固定日期或起止时刻时，例如：

```text
查询 2026-08-07 12:00 到 15:00 的告警
```

系统允许使用固定 `start/end`，但必须满足：

- 起止时间都存在；
- `end > start`；
- 时间戳可以规范化到分钟；
- 使用服务器约定时区；
- 不能与用户 prompt 中的相对时间语义冲突。

固定日期查询不会被强制改成“最近一小时”，这是有意保留的业务能力。

### 12.4 不属于查询窗口的时间

以下时间虽然也使用系统时钟，但不属于 NAPM 查询 `start/end`：

| 时间类型 | 用途 | 是否使用查询时间范围对象 |
| --- | --- | --- |
| 报告创建时间 | 标记文档生成时刻 | 否 |
| 日志时间 | 运行审计和排障 | 否 |
| 缓存 TTL | 控制缓存失效 | 否 |
| 请求耗时 | 性能测量 | 否 |
| 巡检固定采样周期 | 巡检内部采集计划 | 按巡检契约 |

这些时间不能与用户查询窗口强行合并，否则会把业务时间、运行时间和性能计时混为一谈。

### 12.5 新增或修改 skill 的强制规则

以后任何需要 NAPM 查询时间的插件或 skill 必须遵守：

1. 自然语言时间解析使用 `ResolvedQueryTimeRangeService`。
2. 执行时间生成使用 `timeResolver`。
3. 下游 service 消费不可变的 `ExecutionTimeRange` 或其已验证 `start/end`。
4. 工具 schema 对相对时间优先声明 `timeRange.key`，不得要求模型计算当前 Unix 时间戳。
5. 固定时间与相对时间必须使用不同语义分支。
6. 解析失败必须返回结构化错误，禁止静默默认、静默改成 `custom` 或继续访问 API。
7. 新增时间表达必须同时增加公共解析器测试、skill 集成测试和插件边界测试。
8. 发布前必须执行固定时钟回放、真实只读 API 验证和无外部投递 OpenClaw E2E。

### 12.6 当前验收结论

截至 2026-08-07 本次部署完成后：

- NAPM 相对查询时间已经由服务器统一生成；
- 错误年份和错误跨度不能再覆盖用户相对时间意图；
- 普通查询和告警查询已经共享时间解释规则；
- summary 和 fault 继续使用公共不可变执行时间；
- 测试服务器部署版本已通过自动化、固定回放、真实 API 和 OpenClaw E2E；
- 当前服务保持 `active/running`，企业微信连接正常。

该保证针对“NAPM 用户查询执行窗口”。若未来新增代码绕过公共时间服务，则必须视为违反架构契约并由测试和发布检查阻止。
