# 2026-05-08 Skill 执行链路专业化收口说明

## 一、这次调整的目标

基于当前项目现状，这次调整的核心目标不是“再加一层判断”，而是把 `openclaw-napm-query` skill 收口成一个更稳定、更专业的执行器：

- OpenClaw 主链负责理解、边界判断、追问理解、澄清判定、`resolvedQuery` 构造
- Skill 负责消费结构化查询、执行 NAPM 请求、输出叙述契约

这样做的目的是：

1. 减少职责打架
2. 降低同一句话在不同入口下行为不一致的概率
3. 让 skill 的可测试性和可维护性更强

## 二、本次实际调整内容

### 1. 去掉 skill 内部残留的 prompt 直解析捷径

文件：

- `skills/openclaw-napm-query/scripts/run_napm_query.js`

本次移除了两类本地 prompt 分支：

- prompt-only overview 兜底入口
- 本地“解释型追问”文本分流

也就是说，当前执行器不再在缺少 `resolvedQuery` 时：

- 自己把“整体情况怎么样”猜成 overview
- 自己把“为什么会这样”猜成 explanation

现在统一要求：

- 正常执行必须有结构化 `resolvedQuery`
- 如果没有，就返回中文决策型 fallback，明确提示应先由 OpenClaw 主链完成理解

### 2. 保留但收紧会话续接能力

仍然保留：

- `applySessionContinuationToResolvedQuery()`

但它现在的定位更清晰：

- 不是从裸 prompt 重新理解意图
- 而是在已有结构化 `resolvedQuery` 的前提下，结合 session 做执行期补全

本次额外补强了结构化续接指令支持：

- 支持从 `resolvedQuery.pathPlanning.plannedGroups` 直接承接下钻路径
- 支持读取 `followUpAction / inheritGroups / inheritMetric / inheritTimeRange`

这意味着后续如果 OpenClaw 已经产出了更明确的 follow-up 结构，skill 可以直接按结构执行，而不是再靠本地猜短语。

### 3. 补齐 `sessionState` 兼容入口

文档里之前写的是：

- `sessionState`

但执行器原本只实际读取：

- `payload.session`

这次已经统一兼容：

- `payload.session`
- `payload.sessionState`
- `--session`

这样可以减少不同调用方因字段名不一致导致续问失效的问题。

### 4. 保留本地安全防护

虽然 skill 不再承担主语义判断，但有一类执行侧防护仍然保留，而且应该保留：

- 敏感凭证请求拦截

例如：

- 让它直接输出账号密码
- 让它暴露 `.env` 中的敏感字段

这类请求即便误进了 skill，也仍然会被本地拦住。

这属于执行层安全护栏，不属于“重新抢语义判断权”。

## 四、调整后的执行链路

现在推荐的稳定链路是：

```text
用户问题
  -> OpenClaw 主链
  -> 边界判断 / 追问理解 / 澄清判定
  -> 产出 resolvedQuery
  -> openclaw-napm-query
  -> 结构化续接与执行期校验
  -> NAPM API 查询
  -> narration contract
  -> OpenClaw 最终组织中文回复
```

Skill 当前不再承担：

- 边界内外主判
- out-of-scope 引导
- 没有 `resolvedQuery` 时的本地 prompt 兜底解析

## 五、这次调整带来的直接收益

### 1. 行为更稳定

同一类问题不再因为：

- 是不是新对话
- 是不是企微入口
- 有没有某些短语命中

而在 skill 里走出不同的隐藏分支。

### 2. 调试边界更清楚

以后如果出现：

- 边界外问题被错误回答
- “需要 / 继续 / 好的” 这类追问没接上
- 宽泛问题没有形成正确 `resolvedQuery`

优先排查点应该放在：

- OpenClaw 主链
- 调用方是否正确透传了 `resolvedQuery / session`

而不是再怀疑 skill 自己还有没有偷偷做 prompt 理解。

### 3. 更利于后续专业化升级

后续如果要继续提升专业性，正确方向应该是：

1. 让 OpenClaw 输出更稳定的结构化 `resolvedQuery`
2. 让 follow-up / clarification 也尽量结构化
3. 让 skill 继续专注在执行校验、查询稳定性、结果契约和叙述支持

## 六、当前结论

这次调整后，`openclaw-napm-query` 更接近一个真正可控的专业执行器，而不是“半个执行器 + 半个临时语义判断器”。

这对整个项目是正向收口：

- 责任更单一
- 行为更可预测
- 测试更贴近真实契约
- 后续继续打磨 skill 可用性时，发力点也更明确
