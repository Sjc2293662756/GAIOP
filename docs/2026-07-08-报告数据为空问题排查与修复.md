## 二、排查过程

### 2.1 第一层：API 调用日志（combined.log）

拉取 11:35-11:40 时间段的 combined.log，发现两类问题：

#### 证据 A：topValues 子查询缺少时间参数

```json
{
  "errors": ["Start and end timestamps are required"],
  "gatewayRequest": {
    "service": "topValues",
    "groups": [{"type": "BusinessGroup"}],
    "metric": "RFCI",
    "metrics": ["RFCI"],
    "topCount": 10,
    "topMetric": "RFCI",
    "userRequirement": ""
  },
  "message": "Gateway request validation failed"
}
```

> `gatewayRequest` 中 **没有 `start` 和 `end` 字段**。NPM API Gateway 校验拒绝了这个请求。

#### 证据 B：同一报告流程中的对比

| 子查询 | start/end | 结果 |
|--------|:---:|:---:|
| `alertsSummary` | `start=1778565600, end=1778652000` | ✅ 成功 |
| `topValues` (BusinessGroup) | **缺失** | ❌ 校验失败 |

**同一个 `napm-summary` 调用中**，告警子查询有时间参数，业务指标子查询没有——说明时间没有被统一透传。

#### 证据 C：成功调用的时间戳异常

成功 API 调用的 `start=1778565600, end=1778652000` 经换算约为 **2026 年 5 月 13 日**，而非实际日期 2026 年 7 月 8 日。差值约 56 天，与 NAPM API 服务器的时钟偏移一致。

> 这意味着即使 API 调用成功，查询的时间窗口也是错误的（5 月而非 7 月），数据库中该时间段可能无数据。

### 2.2 第二层：主日志（频道层）

在 11:34-11:39 时间窗口搜索 `before_tool_call tool=napm-summary`，**零结果**。而正常的数据查询（`before_tool_call tool=napm-skill-query`）有日志输出。

> 注意：`api.logger.info` 的日志可能写入 OpenClaw 内部日志而非 `/tmp/openclaw/` 主日志，因此不能仅凭主日志无输出来断定 Hook 未执行。

### 2.3 第三层：代码追溯

追踪 `before_tool_call` Hook 中的时间覆盖代码（`napm-openclaw-plugin.remote.js`，2026-07-07 添加）：

```javascript
// napm-summary / napm-fault-diagnosis: 覆盖 timeRange.start/end
if ((toolName === 'napm-summary' || toolName === 'napm-fault-diagnosis')
    && isPlainObject(event.params.timeRange)
    && event.params.timeRange.key) {       // ← 关键条件
  // ... 计算 start/end ...
  event.params.timeRange.start = start;
  event.params.timeRange.end = end;
}
```

对比 `napm-skill-query` 的覆盖：

```javascript
// napm-skill-query: 覆盖 resolvedQuery.start/end
if (toolName === 'napm-skill-query' && isPlainObject(event.params.resolvedQuery)) {
  applyTimeOverride(event.params.resolvedQuery);  // 无条件覆盖
}
```

两个关键差异：
1. `napm-skill-query` 对 `resolvedQuery` **无条件覆盖**
2. `napm-summary`/`napm-fault-diagnosis` 要求 `&& event.params.timeRange.key` 才覆盖

### 2.4 第四层：SummaryService 时间消费

`SummaryService._resolveTimeRange()`（`SummaryService.js` line 1330-1368）：

```javascript
_resolveTimeRange(input = {}, scope = {}) {
  const now = Math.floor(Date.now() / 1000);
  let start = Number(input.start) || 0;
  let end = Number(input.end) || 0;

  // Sanity check: 1 year past / 1 day future
  if (!start || start < now - MAX_PAST_SEC || start > now + 86400) {
    start = now - 86400;  // fallback
  }
  if (!end || end < now - MAX_PAST_SEC || end > now + 86400) {
    end = now;
  }
  return { start, end, displayText };
}
```

关键发现：
- `_resolveTimeRange` 从 `input.start/end` 读取时间（`input` 即 `timeRange` 对象）
- 如果 Hook 设置了 `event.params.timeRange.start/end`，这里能正确读取
- 但如果 Hook 因为 `key` 缺失而跳过覆盖，`input.start/end` 就是 LLM 传入的原始值
- Sanity check 窗口是 **365 天**，55-61 天的偏差不会触发 fallback

## 三、根因分析

### 3.1 完整因果链

```
1. LLM 调用 napm-summary
   参数: { timeRange: { start: 1778565600, end: 1778652000 } }
   ↑ LLM 直接传了绝对时间戳，没传 timeRange.key
   ↑ 时间戳值来源于 NAPM API 服务器的上下文（时钟偏差 ~56 天）

2. before_tool_call Hook 触发
   检测: toolName === 'napm-summary' ✓
         isPlainObject(timeRange)  ✓
         timeRange.key            ✗ ← 为空！
   → 条件不满足，时间覆盖被跳过

3. execute() 回调 → handleSkillCall → executeSummaryQuery
   → SummaryService.run(input)
   → _resolveTimeRange(input.timeRange)
     input.start = 1778565600  (LLM 传入的 5月13日)
     input.end   = 1778652000
     now         = 1783220000  (Date.now(), 7月8日)
     sanity check:
       1778565600 < 1783220000 - 31536000 ?
       = 1778565600 < 1751664000 ?  → NO ✓
       1778565600 > 1783220000 + 86400 ?
       = 1778565600 > 1783306400 ?   → NO ✓
     → start/end 通过 sanity check！不会 fallback。

4. plan(scope, timeRange) → _planGlobal(start, end, ...)
   → SummaryClient.getTopValues(start, end, ...)
   → NAPM API 查询 5月13日的数据
   → 数据为空（该时间段可能无数据存储）

5. reportData 为空 → 报告模板渲染 → 全是 "暂无数据" / "-"
```

### 3.2 为什么数据查询（napm-skill-query）没问题

```javascript
// napm-skill-query 的时间覆盖是无条件的：
if (toolName === 'napm-skill-query' && isPlainObject(event.params.resolvedQuery)) {
  applyTimeOverride(event.params.resolvedQuery);  // ← 无额外条件
}
```

`applyTimeOverride` 内部从 `resolvedQuery.timeRange.key` 读取 key，但如果 key 为空，默认 `'last1hour'`。所以 LLM 传什么时间戳都会被无条件覆盖。

### 3.3 为什么告警查询（napm-alert-query）没问题

告警查询的 `executeAlertQuery` 有独立的 `applyPromptRelativeTimeRange` 函数，从 prompt 文本中提取相对时间并覆盖 criteria 的 start/end。不依赖 `before_tool_call` Hook。

## 四、修复方案

### 4.1 修改位置

`napm-openclaw-plugin.remote.js` — `before_tool_call` Hook 中的时间覆盖代码块

### 4.2 修改内容

**改前**（line 4665-4691）：

```javascript
// napm-summary / napm-fault-diagnosis: 覆盖 timeRange.start/end
if ((toolName === 'napm-summary' || toolName === 'napm-fault-diagnosis')
    && isPlainObject(event.params.timeRange)
    && event.params.timeRange.key) {              // ← BUG: key 为空时跳过
  const now = Math.floor(Date.now() / 1000);
  const floor = (v) => Math.floor(v / 60) * 60;
  const timeKey = String(event.params.timeRange.key || '').trim();
  const DURATION_MAP = { ... };

  let start, end;
  // ... 计算 ...
  event.params.timeRange.start = start;           // 只设置了 timeRange.start/end
  event.params.timeRange.end = end;
}
```

**改后**：

```javascript
// napm-summary / napm-fault-diagnosis: 无条件覆盖时间（2026-07-08 修复）
// 即使 LLM 直接传了 start/end 而没有传 timeRange.key，也必须用 Date.now() 覆盖。
// 否则 SummaryService._resolveTimeRange 可能使用 LLM 提供的错误时间戳。
if (toolName === 'napm-summary' || toolName === 'napm-fault-diagnosis') {
  if (!isPlainObject(event.params.timeRange)) {
    event.params.timeRange = {};                  // ← FIX 1: 自动创建 timeRange
  }
  const now = Math.floor(Date.now() / 1000);
  const floor = (v) => Math.floor(v / 60) * 60;
  const timeKey = String(event.params.timeRange.key || '').trim() || 'last24hours';  // ← FIX 2: 默认 24h
  const DURATION_MAP = { ... };

  let start, end;
  // ... 计算（不变）...
  event.params.timeRange.start = start;
  event.params.timeRange.end = end;
  event.params.timeRange.key = timeKey;           // ← FIX 3: 回填 key
  // 同时设置根级别 start/end，兼容直接从 params 读取时间的服务
  event.params.start = start;                     // ← FIX 4: 根级别双保险
  event.params.end = end;
}
```

### 4.3 改动总结

| # | 改动 | 类型 | 效果 |
|---|------|------|------|
| 1 | 移除 `&& event.params.timeRange.key` 条件 | Bug 修复 | **无条件覆盖**，不依赖 LLM 是否传 key |
| 2 | `timeKey` 默认值 `'last1hour'` → `'last24hours'` | 改进 | 报告类查询默认 24 小时更合理 |
| 3 | 即使 `timeRange` 不存在也自动创建 | 防御 | LLM 完全不传 timeRange 时也能工作 |
| 4 | 同时设置根级别 `event.params.start/end` | 防御 | 兼容从 params 根级别读取时间的代码路径 |
| 5 | 回填 `event.params.timeRange.key` | 改进 | 下游代码可以知道实际使用的时间范围 |
