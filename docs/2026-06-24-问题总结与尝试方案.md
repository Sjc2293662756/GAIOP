# NAPM 查询耗时问题：完整总结

日期：2026-06-24

---

## 一、问题

企业微信用户问 "最近丢包最严重的IP是谁？"、"现在哪个业务报错最多？" 等 NAPM 查询，耗时 10-68 秒，且呈恶化趋势。

## 二、架构

```
企业微信 → OpenClaw Gateway(18789) → wecom频道 → napm-openclaw-plugin
  → LLM Agent(main, openai.yaml) → DeepSeek API(api.deepseek.com)
  → LLM思考 → 调napm-skill-query → NAPM API(101.254.114.238) → 返回结果
  → LLM叙述 → 回复用户
```

### 关键配置

- 模型：deepseek-chat（API: api.deepseek.com）
- 频道：wecom，`thinking: true`，`sendThinkingMessage: true`（必须保留）
- 服务器：101.254.114.237（Ubuntu, Node.js v22.14.0, CPU 2核 8GB）
- 插件：napm-openclaw-plugin.remote.js（~5800行）
- Agent prompt：openai.yaml（35行精简版）

## 三、耗时构成

通过 trajectory（`/home/netinside/.openclaw/agents/main/sessions/*.trajectory.jsonl`）的精确数据：

| 指标 | 简单查询（丢包） | 复杂查询（报错） |
|------|---------|---------|
| LLM 内部思考 token | ~70K | **553,984（55万）** |
| 思考消息条数 | 1-2 条 | **11 条** |
| 单次 API 调用总 token | ~70K | **575K** |
| NAPM API 执行 | ~0.7s | ~0.7s |
| 插件处理 | ~10ms | ~10ms |
| **总耗时** | **10-20s** | **60-68s** |

**结论：68 秒 = 一次 DeepSeek HTTP 调用，模型在服务端做了 55 万 token 的 chain-of-thought 推理。代码执行时间（插件+NAP API）不到 1 秒，占比 <2%。**

## 四、已尝试方案（全部失败）

### 1. 修复 Memory 子系统故障 ✅ 有效但不解决根本问题

**问题**：SQLite FTS5 + Embedding API 故障，每次浪费 7s。
**修复**：`config.yaml` 禁用 `memory.embeddings` + `memory.fts`。
**效果**：Memory 错误消失，但总耗时未明显下降。

### 2. 时间戳年份自动修正 ✅ 有效但不解决速度

**问题**：LLM 把 2026 年算成 2025 年，导致空数据。
**修复**：`ResolvedQueryTimeRangeService.js` 新增 `autoCorrectTimestampIfStale()`。
**效果**：年份 100% 正确，但不能加速。

### 3. 精简 prompt — 无效果

**改动**：`openai.yaml` 78行 → 35行。
**效果**：15s → 15.8s，无变化。prompt 大小不是瓶颈。

### 4. before_tool_call 规则引擎拦截 — 无效

**思路**：LLM 的 resolvedQuery 不合法时，用本地规则引擎（9ms）替代。
**效果**：LLM 产出的 query 格式越来越完整，永远不触发拦截。

### 5. before_agent_start 预解析注入 — 无效

**思路**：LLM 推理前，把规则引擎预解析的 resolvedQuery 注入系统上下文。
**效果**：LLM 完全无视注入内容，照自己的 chain-of-thought 走。

### 6. thinking: false — 无效

**思路**：关掉 OpenClaw 的 thinking 模式，阻止 LLM 的 chain-of-thought。
**效果**：20.7s，和开 thinking 没区别。`sendThinkingMessage: true` 可能内部又把它打开了。

### 7. API 速查表内嵌 prompt — 无效

**思路**：把 queryModeKey、必填字段、指标映射表直接写在 openai.yaml 里。
**效果**：68s，LLM 读了但还是按自己的节奏来（"我看到 PGHTTP400...但之前返回空..."）。

### 8. 语义标签方案 — 无效

**思路**：LLM 填 5 个中文标签 → 规则引擎映射 → 执行，替代完整 resolvedQuery。
**改动**：
- openai.yaml 指令从"构造JSON"改为"填5个标签"
- 新建 TagNormalizer.js（标签归一化+映射）
- prepareSkillExecutionArgs 新增 semanticTags 处理
- 工具定义新增 semanticTags 参数
- 工具定义删除 resolvedQuery 的详细 Schema
**效果**：LLM 完全不用 semanticTags，继续自己构造 resolvedQuery。

## 五、根因

**DeepSeek `thinking: true` 模式下，模型产生大量内部 chain-of-thought token，不受 prompt、工具定义、系统上下文控制。** 所有试图在 LLM 外部（prompt层、插件层、配置层）改变其行为的尝试全部失败。模型按照自己的推理习惯走——获取时间 → 构造 query → 试错 → 修正 → 再试 → 生成回答。

Trajectory 数据证明：55 万 token 的内部推理是一次 HTTP 调用内完成的，OpenClaw 插件没有机会介入。

## 六、当前代码状态

保留的有效改动：
- `ResolvedQueryTimeRangeService.autoCorrectTimestampIfStale()` — 年份自动修正
- `openai.yaml` 精简版（35行）
- 远端 `config.yaml` Memory 禁用
- `maybeAutoRepairResolvedQuery()` 插件兜底修正（原有功能）

已回退的无效改动：
- before_agent_start 预解析注入
- before_tool_call 规则引擎拦截
- prepareSkillExecutionArgs 语义标签映射
- TagNormalizer.js（文件仍存在但不被加载）
- 工具定义的 semanticTags / 精简 Schema
