# 2026-05-08 企业微信插件本地边界判断下线说明

## 一、本次调整背景

在 2026-05-07 到 2026-05-08 的联调过程中，企业微信入口为了止血，曾临时承担了一部分“本地语义判断”职责，例如：

- 判断当前问题是不是 NAPM 问题
- 判断当前是不是上一轮的追问
- 判断 `需要 / 好的 / 可以` 这类短句是否应继续放行
- 判断是否命中天气、节日、百科等泛问答边界

这些补丁在短期内能压住部分错误回复，但很快暴露出一个根本问题：

**问法千变万化，企业微信插件层不适合继续承担语义判断。**

也就是说，问题不在于词表补得够不够多，而在于“判断权”本身放错了层。

---

## 二、为什么不能继续在企业微信插件里补短语

### 1. 追问不是靠几个词能穷举的

例如：

- `那前三个呢`
- `继续`
- `需要`
- `就看这个`
- `把刚才那个展开`
- `按你说的继续查`

这些形式都可能表示“沿用上一轮上下文继续执行”，但它们并不共享一套稳定短语模板。

如果继续在企业微信插件里维护：

- `需要`
- `可以`
- `好的`
- `行`

这样的短语白名单，本质上只是不断补洞。

### 2. 企业微信插件拿不到真正完整的语义状态

企业微信插件当前能拿到的是：

- 原始文本
- 会话标识
- 少量本地 follow-up / clarification 状态

但真正更完整的判断上下文应来自：

- OpenClaw 的上游理解
- `resolvedQuery`
- 当前是否是 clarification / confirmation / continue / drilldown
- 当前是否应继续调用 Skill

这类能力本来就应该由 OpenClaw 主链统一掌握。

### 3. 本地语义判断会反复制造职责冲突

如果企业微信插件继续做这些判断，就会反复出现下面的问题：

1. 插件先按自己的词表判断一轮
2. OpenClaw 主链再按自己的语义理解判断一轮
3. 两边口径不一致时，就会出现：
   - 该放行的被拦掉
   - 该拦掉的被放行
   - 追问被误识别成新问题
   - 新问题被误识别成追问

这会让系统重新退回到“双重语义判断”的混乱状态。

---

## 三、本次调整目标

本次调整明确收口为：

```text
企业微信插件：
  只负责消息接收、会话透传、消息回传、安全硬拦截

OpenClaw 主链：
  统一负责领域边界判断、追问判断、clarification 判断、Skill 调度判断
```

也就是说：

- 企微插件不再在主流程里判断“是不是 NAPM”
- 企微插件不再在主流程里判断“是不是上一轮追问”
- 企微插件不再在主流程里判断“需要/可以/好的”是否表示继续
- 这些判断统一交回 OpenClaw 主链

---

## 四、本次实际修改

### 1. 从企业微信主流程中移除本地语义边界判断

本次从 `processWeComMessage()` 主流程中移除了以下本地语义分流逻辑：

- `looksLikeNapmQuery(boundaryText)`
- `isNapmFollowUpContext(frame)`
- `isLikelyNapmFollowUpText(boundaryText)`
- `detectWeComHardBoundary(boundaryText)`

此前这套逻辑会在企微入口提前决定：

- 放不放行
- 当不当追问
- 是否直接返回泛问答边界提示

现在这些都不再由插件主流程决定。

### 2. 保留安全类硬拦截

虽然本地语义边界判断已经从主流程撤掉，但以下安全类拦截仍保留在企业微信插件层：

- `isCredentialDisclosureRequest(text)`

也就是：

- 查密码
- 查 token
- 查账号凭证

这类高风险请求仍可在插件层直接拦截。

这类拦截保留的原因是：

- 它不属于“语义领域判断”
- 它属于明确的安全防护
- 放在入口层拦截更直接、更稳妥

### 3. 仍保留状态透传与消息回传

企微插件当前仍继续负责：

- 接收用户消息
- 构造消息上下文
- 透传会话标识
- 调用 OpenClaw 主链
- 将主链结果回发给企业微信

但不再抢先决定语义走向。

---

## 五、调整后的职责边界

调整前，链路大致是：

```text
企业微信消息
  -> 企微插件本地判断是不是 NAPM / 是不是追问 / 要不要拦
  -> 再决定是否进入主链
```

调整后，链路收口为：

```text
企业微信消息
  -> 企微插件仅接收与透传
  -> OpenClaw 主链统一判断
       - 是否属于 NAPM 领域
       - 是否属于上一轮追问
       - 是否需要 clarification
       - 是否需要调用 Skill
  -> 企业微信插件回消息
```

这意味着当前真正的判断权已经回收到 OpenClaw 主链。

## 七、当前结论

本次调整的本质不是“删掉几个 if 判断”，而是进一步收清职责边界：

**企业微信插件不再承担本地语义判断职责，是否属于 NAPM、是否是追问、是否继续执行，统一交由 OpenClaw 主链判断。**

这也意味着后续若再出现：

- 某类追问没接住
- 某类非 NAPM 问题误放行
- 某类确认型问法判断跑偏

正确的修复方向不再是继续给企业微信插件补词表，而应优先回到 OpenClaw 主链中修正语义判断与会话续接能力。
