# 指标语义归一化层设计与落地说明

## 问题

`400错误` 和 `400报错` 对人和大模型来说是同一个意思，但当前生产主链不能只依赖模型自由理解。

生产链路要求 OpenClaw 构造确定性的 `resolvedQuery`：

```text
prompt
  -> workflow classification
  -> metric semantic resolution
  -> object/path resolution
  -> resolvedQuery
  -> napm-skill-query execution
```

如果指标语义只散落在别名表或局部正则里，就会出现：

```text
400错误 能匹配
400报错 可能匹配不到
HTTP400异常 可能匹配不到
4xx错误 可能匹配不到
```

这不是模型不会理解，而是确定性解析器没有统一的同义表达归一化层。

## 解决原则

不在各处写：

```js
if (text.includes('400报错')) ...
```

而是建立统一服务：

```text
MetricSemanticNormalizerService
```

所有 workflow 分类、metric 解析、resolvedQuery 构造都调用这一层。

## 新增服务

文件：

```text
skills/openclaw-napm-query/services/MetricSemanticNormalizerService.js
```

职责：

- 读取 spec alias。
- 归一化常见自然语言指标语义。
- 返回标准 metric id。
- 返回语义域和匹配来源，便于审计。

核心 API：

```js
resolveMetricSemantic(prompt, options)
hasMetricSemantic(prompt, options)
inferDomain(metric)
```

返回示例：

```json
{
  "metric": "PGHTTP400",
  "metrics": ["PGHTTP400"],
  "domain": "http_status",
  "canonicalIntent": "http_400_count",
  "matchedAlias": "http_400_count",
  "source": "metric_semantic_normalizer",
  "confidence": 0.95
}
```

## 当前支持的归一化

### HTTP 400

```text
400
HTTP400
400错误
400报错
400异常
400失败
400状态码
400响应码
4xx
```

归一为：

```text
PGHTTP400
```

### HTTP 500

```text
500
HTTP500
500错误
500报错
500异常
500失败
500状态码
500响应码
5xx
```

归一为：

```text
PGHTTP500
```

### 其他常用指标

```text
丢包 / 丢包率 -> PLI
吞吐 / 吞吐量 -> TPIO
流量 -> BYTIO
```

## 接入点

### WorkflowClassifierService

之前：

```text
有哪些 -> object_inventory
```

现在：

```text
hasMetricSemantic(prompt) && hasQuestionListIntent(prompt)
  -> metric_topn
```

因此：

```text
在其他web应用中，有哪些页面出现400错误？
```

不会再被 `object_inventory` 截胡。

### NapmResolvedQueryResolverService

之前：

```text
inferMetric()
  -> 只查 spec aliases
  -> 可能 missing_metric
```

现在：

```text
inferMetric()
  -> MetricSemanticNormalizerService.resolveMetricSemantic()
  -> PGHTTP400 / PGHTTP500 / ...
```

## 修复后的例子

输入：

```text
在其他web应用中，有哪些页面出现400报错？
```

归一化：

```text
400报错 -> PGHTTP400
```

resolvedQuery：

```json
{
  "service": "topValues",

  "topMetric": "PGHTTP400",

  "semanticConstraints": {
    "workflowType": "metric_topn",
    "targetObjectType": "PageFamily"
  }
}
```

## 后续扩展

以后新增同义表达，不应改 resolver 或 classifier，而应扩展：

```text
MetricSemanticNormalizerService.js
```

例如：

```text
页面慢 / 响应慢 / 耗时高 -> PGTME 或 PGNSLPGE
连接失败 / 失败连接 -> RFCI/RFCO
访问量 / 页面访问数 -> PGNPGE
```

这样语义扩展是集中、可测、可审计的。
