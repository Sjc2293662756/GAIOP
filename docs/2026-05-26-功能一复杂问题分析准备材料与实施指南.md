## 1. 文档目的

本文档基于当前项目 `NAPM_Semantic_Gateway` 的真实代码结构，说明“功能一：复杂问题分析与复合查询分析”落地前，需要准备哪些文档、哪些业务材料、哪些数据样例，以及每类材料应该怎么做。

功能一不是简单增加一个新 API，也不是让模型直接把多个 API 串起来。按照当前项目架构，功能一应该沿着现有主链演进：

```text
OpenClaw 自然语言理解
  -> 构造 structured resolvedQuery / analysisPipeline
  -> openclaw-napm-query skill 执行
  -> overview / metadata / metric 执行内核
  -> 结构化结果归并
  -> narration contract
  -> 中文分析结论
```

因此，准备工作的核心不是“写一份大而空的功能说明”，而是把自然语言问题稳定落成当前项目可执行的结构化查询与分析计划。

### 2.2 已经存在的复合分析雏形

当前项目已经支持如下链路：

```text
用户：找到连接失败数最多的地址，然后对这个地址进行综合分析

OpenClaw 构造：
service = overview
overviewScene = network
analysisPipeline.discoveryQuery = topValues(IPAddress, RFCI, topCount=1)

skill 执行：
1. 先执行 discoveryQuery
2. 从 TopN 结果中提取目标对象
3. 把目标对象写入 focused overview 的 groups
4. 执行 overview
5. 返回 discovery + overview 结果
```

对应的测试已经存在于：

```text
test/run-napm-query-input-contract.test.js
```

这说明功能一不是从 0 开始，而是要把这条雏形链路产品化、契约化、测试化。

### 2.3 当前主要缺口

| 缺口 | 影响 |
|---|---|
| 没有正式的 `analysisPlan` 契约 | 当前只有 `analysisPipeline.discoveryQuery`，还不能表达完整多步根因分析 |
| 没有明确的复杂问题样例库 | OpenClaw 不容易稳定判断哪些问题该走复合分析 |
| 没有“分析目标 -> 指标组合 -> 查询步骤”的标准映射 | “慢”“异常”“错误”“不稳定”容易落成不同查询 |
| 没有多对象对比分析 executor | 方案里的 `comparative_analysis` 当前还不能完整落地 |
| 没有根因归纳规则 | 当前 overview 更偏“概览摘要”，还不是严格根因分析 |
| 没有阈值、基线、异常判定材料 | 系统很难判断“是否异常”“严重程度如何” |
| 没有固定验收对象与样例数据 | 功能验收容易变成只看链路是否跑通，不能判断分析是否正确 |

## 3. 功能一落地目标拆解

功能一建议拆成 5 类能力逐步落地。

| 能力 | 当前状态 | 建议优先级 |
|---|---|---|
| 单对象聚焦综合分析 | 已有 focused overview 基础 | P0 |
| 先发现异常对象，再自动分析 | 已有 `analysisPipeline.discoveryQuery` 雏形 | P0 |
| 慢/错误/流量/连接等专项分析 | 有 candidate 基础，但缺标准步骤 | P1 |
| 多对象横向对比分析 | 缺正式 executor 和输出契约 | P1/P2 |
| 根因结论归纳与建议动作 | 缺 InsightSynthesizer 规则 | P1/P2 |

第一阶段不要一口气做所有根因推理。建议先把当前项目已有的“overview + discovery”稳定成产品级能力。

## 5. M01：复杂分析场景清单怎么准备

### 5.1 目的

明确哪些问题属于“复杂问题分析与复合查询分析”，哪些仍然是普通单步查询。

### 5.2 准备方法

整理真实用户会问的问题，每个问题标注：

- 是否需要多步查询
- 是否有明确对象
- 是否需要先找对象
- 是否需要跨指标分析
- 是否需要横向对比
- 最终希望得到数值还是分析结论

### 5.3 推荐模板

| 场景编号 | 用户问题 | 场景类型 | 是否明确对象 | 是否需要 discovery | 是否需要多指标 | 期望输出 |
|---|---|---|---|---|---|---|
| S001 | 可观测239web 为什么慢？ | 单对象慢分析 | 是 | 否 | 是 | 慢的可能原因、证据、建议 |
| S002 | 找到连接失败最多的地址，然后分析它 | 先发现再分析 | 否 | 是 | 是 | Top 对象、连接失败情况、趋势、关联对象 |
| S003 | 最近哪些业务系统异常？ | 异常发现 | 否 | 是 | 是 | 异常对象列表、异常依据、优先级 |
| S004 | 比较 A、B、C 三个业务系统稳定性 | 多对象对比 | 是 | 否 | 是 | 对比结论、排序、差异原因 |
| S005 | 某工作组整体情况怎么样？ | 单对象综合诊断 | 是 | 否 | 是 | 访问、错误、性能、趋势 |

### 5.4 判断规则

普通单步查询：

```text
访问量最高的业务是谁？
某 IP 的平均响应时间是多少？
某业务最近一小时流量趋势是什么？
```

复杂分析：

```text
某业务为什么慢？
某系统异常的原因是什么？
先找连接失败最多的地址，再分析它。
比较这几个业务系统谁风险更高。
```

## 6. M02：用户自然语言问法样例怎么准备

### 6.1 目的

当前 skill 要求 OpenClaw 提供 `resolvedQuery`。因此必须给 OpenClaw 足够多的问法样例，让它稳定构造正确结构。

### 6.2 问法分类

| 类别 | 问法样例 | 推荐落点 |
|---|---|---|
| 明确对象综合分析 | `可观测239web 整体情况怎么样？` | focused overview |
| 明确对象慢分析 | `可观测239web 为什么慢？` | focused overview + slow questionType |
| 明确对象错误分析 | `可观测239web 最近报错严重吗？` | focused overview + error questionType |
| 先发现再分析 | `找到连接失败最多的地址，然后分析它` | overview + `analysisPipeline.discoveryQuery` |
| 异常对象发现 | `最近哪个业务系统最异常？` | discovery topValues |
| 多对象对比 | `比较 A、B、C 的访问、错误、性能差异` | comparative analysis |
| 后续追问 | `继续分析它`、`看下趋势` | session continuation |

### 6.3 每个问法样例要包含什么

每条样例至少包含：

```text
用户原话：
归属场景：
目标对象：
时间范围：
期望 workflow：
期望 resolvedQuery / analysisPipeline：
是否需要澄清：
期望回答结构：
```

### 6.4 示例

```text
用户原话：
找到连接失败最多的地址，然后对这个地址进行综合分析。

归属场景：
先发现再分析。

目标对象：
IPAddress。

时间范围：
默认最近 1 小时或用户指定时间。

期望 workflow：
overview with discovery。

期望结构：
outer service = overview
overviewScene = network
analysisPipeline.discoveryQuery = topValues(IPAddress, RFCI, topCount=1)

期望输出：
先说明发现的 IP，再说明该 IP 的连接失败、连接请求、连接趋势、关联应用或会话。
```

## 7. M03：对象清单样本怎么准备

### 7.1 目的

复杂分析必须有明确对象。当前项目对象口径已经有本体配置，但实际分析需要真实可查询对象。

### 7.2 需要准备哪些对象

| 对象类型 | 当前项目口径 | 用途 | 最少准备数量 |
|---|---|---|---|
| 业务系统 | `WebApplication` | 业务慢、业务异常、业务对比 | 5-10 个 |
| 工作组/业务组 | `BusinessGroup` | 工作组综合分析、横向评估 | 3-5 个 |
| 已定义应用 | `DefinedApp` | 应用流量、应用错误、应用体验 | 5-10 个 |
| IP 地址 | `IPAddress` | 网络慢、连接失败、丢包、会话分析 | 10 个 |
| 页面族 | `PageFamily` | 慢页面、页面访问分析 | 可选 |
| 用户 | `User` | 用户体验分析 | 可选 |
| 会话 | `IPConversation` | 对端会话分析 | 可选 |

### 7.3 对象清单模板

```csv
objectType,displayName,argument,description,owner,businessImportance,canUseInTest
WebApplication,可观测239web,可观测239web,核心业务系统,业务团队A,high,true
BusinessGroup,Default-Internet,Default-Internet,默认互联网工作组,网络团队,medium,true
IPAddress,101.254.114.237,101.254.114.237,测试服务器IP,运维团队,medium,true
DefinedApp,HTTP,HTTP,HTTP协议应用,网络团队,medium,true
```

### 7.4 注意事项

- `displayName` 是给人看的名字。
- `argument` 必须是 NAPM API 可执行的对象参数。
- 测试对象要选近期确实有数据的对象。
- 不要把“业务系统”和“业务组”混用。当前项目里普通“业务”通常是 `WebApplication`，不是 `BusinessGroup`。

## 8. M04：对象关系材料怎么准备

### 8.1 目的

复杂分析不仅看单个对象，还要看上下文。例如：

- 一个业务系统属于哪个工作组
- 一个 IP 关联哪些应用
- 一个应用关联哪些会话
- 一个业务系统有哪些慢页面

### 8.2 需要准备的关系

| 关系 | 示例 | 用途 |
|---|---|---|
| BusinessGroup -> WebApplication | 工作组包含哪些业务系统 | 业务组分析下钻 |
| WebApplication -> PageFamily | 业务系统有哪些页面族 | 慢页面分析 |
| IPAddress -> DefinedApp | IP 上有哪些应用 | IP 关联应用分析 |
| IPAddress -> IPConversation | IP 关联哪些会话 | 会话定位 |
| WebApplication -> ClientIPs | 业务系统的客户端来源 | 错误客户端分析 |
| WebApplication -> User | 业务系统用户访问 | 用户影响面分析 |

### 8.3 关系材料模板

```csv
sourceType,sourceArgument,targetType,targetArgument,relationType,confidence
BusinessGroup,核心业务组,WebApplication,可观测239web,contains,high
IPAddress,101.254.114.237,DefinedApp,HTTP,runs_or_observed_as,medium
WebApplication,可观测239web,PageFamily,/login,has_page_family,high
```

### 8.4 和当前项目的关系

当前项目已有 `config/groups-tree.static.json` 和下钻路径相关能力，但那是结构层面的“支持哪些路径”。功能一还需要真实对象之间的样例关系，用于测试和验收。

## 9. M05：分析意图到指标组合映射表怎么准备

### 9.1 目的

“慢”“异常”“错误”“不稳定”都是自然语言，不是 NAPM 可执行指标。必须把分析意图落成指标组合。

### 9.2 推荐映射

| 分析意图 | 适用对象 | 推荐指标 | 查询类型 | 用途 |
|---|---|---|---|---|
| 业务访问 | `WebApplication` | `PGNPGE`、`PGHTTP200` | topValues / timeValues | 判断访问规模和趋势 |
| 慢页面 | `WebApplication` | `PGNSLPGE`、`PGSLRT` | topValues / averageValues | 判断慢页面数量和比例 |
| 页面耗时 | `WebApplication` | `PGTME`、`PGTMC`、`PGTMS` | averageValues / timeValues | 判断页面响应慢 |
| HTTP 错误 | `WebApplication` | `PGHTTP500`、`PGHTTP500PCT`、`PGHTTP400`、`PGHTTP400PCT` | topValues / timeValues | 判断业务错误 |
| 应用吞吐 | `DefinedApp` | `TPIO`、`BYTIO` | topValues / timeValues | 判断应用流量 |
| 连接失败 | `IPAddress`、`BusinessGroup`、`IPConversation` | `RFCI`、`RFCO`、`RFRI`、`RFRO` | topValues / timeValues | 判断连接异常 |
| 连接请求 | `IPAddress`、`BusinessGroup` | `CONI`、`CONO`、`CCNI`、`CCNO` | averageValues / timeValues | 判断连接压力 |
| 网络时延 | `IPAddress`、`Prefix24` | `RTTI`、`RTTO`、`TRTT` | averageValues / timeValues | 判断网络延迟 |
| 服务器响应 | `IPAddress`、`DefinedApp` | `TRTI`、`TRTO` | averageValues / timeValues | 判断服务端响应 |
| 丢包 | `TotalTraffic`、`IPAddress`、`Prefix24` | `PLI`、`PLO` | topValues / timeValues | 判断网络丢包 |
| 重传 | `IPAddress`、`IPConversation` | `RTXI`、`RTXO`、`RDTI`、`RDTO` | topValues / timeValues | 判断传输质量 |

### 9.3 每个分析意图要补充的内容

```text
意图名称：
用户常见说法：
适用对象：
主指标：
辅助指标：
默认查询模式：
是否需要趋势：
是否需要 TopN：
是否需要同类对比：
异常判定规则：
建议动作模板：
```

### 9.4 示例

```text
意图名称：
连接失败分析

用户常见说法：
连接失败最多、连接异常、TCP 失败、哪个地址失败最多

适用对象：
IPAddress、BusinessGroup、IPConversation

主指标：
RFCI

辅助指标：
CONI、CCNI、RFRI、CSTI

默认查询模式：
如果没有明确对象，先 topValues 找对象；
如果有明确对象，直接 focused overview。

异常判定规则：
连接失败数明显高于同类对象，或失败率高于阈值。

建议动作：
检查该 IP 关联应用、对端会话、连接建立时间和近期趋势。
```

## 10. M06：Discovery 选择规则怎么准备

### 10.1 目的

当前项目已经支持 `analysisPipeline.discoveryQuery`，但需要明确“先找对象”时到底按什么对象、什么指标找。

### 10.2 触发 discovery 的典型表达

```text
找到……最多的……
哪个……最慢？
谁的……最高？
先找出异常对象，再分析。
失败最多的是哪个？
最近最差的是哪个？
```

### 10.3 Discovery 规则表

| 用户目标 | targetObjectType | discovery service | groups | metrics | topMetric | topCount |
|---|---|---|---|---|---|---|
| 找连接失败最多的地址 | `IPAddress` | `topValues` | `IPAddress` | `RFCI` | `RFCI` | 1 |
| 找最慢的 Web 应用 | `WebApplication` | `topValues` | `WebApplication` | `PGTME` | `PGTME` | 1 |
| 找慢页面最多的业务 | `WebApplication` | `topValues` | `WebApplication` | `PGNSLPGE` | `PGNSLPGE` | 1 |
| 找 HTTP 500 最多的业务 | `WebApplication` | `topValues` | `WebApplication` | `PGHTTP500` | `PGHTTP500` | 1 |
| 找吞吐最高的应用 | `DefinedApp` | `topValues` | `DefinedApp` | `TPIO` | `TPIO` | 1 |
| 找丢包最严重的对象 | `IPAddress` 或 `TotalTraffic` | `topValues` | 视场景决定 | `PLI` / `PLO` | `PLI` / `PLO` | 1 |

### 10.4 当前已支持的结构

```json
{
  "service": "overview",
  "queryModeKey": "overview",
```

## 12. M08：阈值与基线材料怎么准备

### 12.1 目的

如果没有阈值和基线，系统只能说“查到了什么”，很难说“是否异常”“是否严重”“可能原因是什么”。

### 12.2 需要准备的阈值

| 指标类别 | 指标示例 | 需要的判定规则 |
|---|---|---|
| 页面响应 | `PGTME` | 超过多少算慢 |
| 慢页面 | `PGNSLPGE`、`PGSLRT` | 慢页面数或慢页面率阈值 |
| HTTP 错误 | `PGHTTP500`、`PGHTTP500PCT` | 错误数或错误率阈值 |
| 连接失败 | `RFCI`、`RFRI` | 失败数或失败率阈值 |
| 连接建立时间 | `CSTI` | 连接建立时间阈值 |
| 网络时延 | `RTTI`、`RTTO` | RTT 阈值 |
| 丢包 | `PLI`、`PLO` | 丢包率阈值 |
| 重传 | `RTXI`、`RTXO` | 重传率阈值 |
| 流量突增 | `TPIO`、`BYTIO` | 环比/同比变化阈值 |

### 12.3 阈值模板

```csv
objectType,metric,level,condition,description,actionHint
WebApplication,PGTME,warning,>3000ms,页面平均耗时偏高,检查慢页面与后端响应
WebApplication,PGHTTP500PCT,critical,>5%,HTTP 500 比例过高,优先排查服务端错误
IPAddress,RFCI,warning,>1000,连接失败数偏高,检查连接建立与对端会话
IPAddress,PLI,critical,>3%,入向丢包严重,检查链路质量
```

### 12.4 如果暂时没有阈值怎么办

可以先准备弱规则：

- 与同类对象相比 Top 1 / Top 3 明显偏高
- 最近一小时高于过去 24 小时均值
- 错误指标和流量指标同时升高
- 慢指标升高但流量无明显升高，优先怀疑性能问题
- 慢指标升高且连接失败升高，优先怀疑网络或连接层问题

## 22. 功能一最终验收标准

功能一第一阶段完成时，至少应满足：

- 明确对象的问题可以稳定走 focused overview。
- “先找对象再分析”的问题可以稳定走 `analysisPipeline.discoveryQuery`。
- discovery 和 focused overview 使用同一时间范围。
- 输出能说明数据时间、锁定对象、关键发现、建议动作。
- discovery 失败时不编造对象。
- 元数据失败或指标不兼容时能给出可解释失败。
- 至少覆盖 IP、WebApplication、DefinedApp 三类对象。
- 至少有 5 条自动化测试覆盖复合分析链路。

功能一完整阶段完成时，进一步满足：

- 支持正式 `analysisPlan`。
- 支持多对象 `comparative_analysis`。
- 输出统一包含 `summary`、`structuredFindings`、`supportingEvidence`、`nextActions`。
- 具备基于阈值、趋势、同类对比的洞察归纳。
- 具备历史故障案例校准。

## 23. 当前最重要的结论

当前项目底座已经具备：

- 结构化查询执行能力
- overview 多模块编排能力
- discovery -> focused overview 雏形
- narration contract 输出能力

当前最缺的是：

- 复杂分析问题样例
- 对象与指标材料
- discovery 选择规则
- 分析步骤与输出契约
- 验收测试矩阵

因此，下一步不应优先新写大量代码，而应先把以上材料准备齐。材料一旦稳定，功能一可以沿当前项目已有链路自然扩展，而不是另起一套平行系统。
