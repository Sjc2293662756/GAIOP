# 应用语义歧义与已定义应用口径修复

## 背景

测试中出现如下错误解释：

- 把“已定义应用”解释成系统中注册名称为 `Application` 的列表。
- 去 `groups-tree.static.json` 查 `Application` 节点，并把维度树节点当成应用清单来源。
- 对“系统中有哪些已定义应用”进行不必要澄清，而不是稳定构造 `DefinedApp` 清单查询。

这些行为和 `napm-应用与业务对象说明-2026-05-23.md` 的领域口径不一致。

## 本次收口规则

- `applications` API 加 `Type` 过滤是应用类对象清单的真相源。
- `groups-tree.static.json` 只描述层级/下钻结构，不是应用清单真相源。
- “系统中有哪些已定义应用”稳定构造为 `groups:[{type:"DefinedApp"}]`，执行时过滤 `applications Type=2`。
- “系统中有哪些自动识别应用 / 自动识别的应用 / 自动识别出来的应用 / 系统自动识别的应用 / 复合协议 / 复合应用”稳定构造为 `groups:[{type:"CompositeApplication"}]`，执行时过滤 `applications Type=4`。
- “系统中有哪些业务 / Web 应用 / 业务系统”稳定构造为 `groups:[{type:"WebApplication"}]`，执行时过滤 `applications Type=3`。
- Plain “系统中有哪些应用” 是歧义问法，不默认等同 `DefinedApp`，也不返回 `applications` 全量目录。

## 修改点

- `NapmResolvedQueryResolverService`
  - 增加 plain 应用清单歧义识别。
  - “自动识别应用/自动识别的应用/自动识别出来的应用/特征识别应用”改归 `CompositeApplication`。
  - “已定义应用/服务器应用/协议应用”保持归 `DefinedApp`。
- `PromptRoutingService`
  - 旧快速路由同步 plain 应用清单歧义。
  - 避免复合/自动识别应用落入 `DefinedApp`。
- `ApplicationCatalogSemanticRules`
  - 新增共享应用清单语义规则，resolver 与旧路由统一消费，避免入口间规则漂移。
- `SKILL.md`、`agents/openai.yaml`、`openclaw-integration.md`
  - 增加禁止从 `groups-tree.static.json Application` 节点回答应用清单的说明。
  - 增加 plain “应用”必须澄清的说明。
- `napm-resolution-spec.v1.json`、`objectDimensions.js`
  - 给 `CompositeApplication` 增加“自动识别应用”“特征识别应用”别名。

## 验证

- `系统中有哪些自动识别的应用` -> `groups:[{type:"CompositeApplication"}]`
