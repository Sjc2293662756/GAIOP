# 语义标签方案：实施设计

日期：2026-06-24

## 一、改动范围

**只改 3 个地方：**

| 文件 | 改动 | 行数 |
|------|------|------|
| `agents/openai.yaml` | LLM prompt: 从"构造resolvedQuery"改为"提取标签+调用工具" | ~25行 |
| `napm-openclaw-plugin.remote.js` | `prepareSkillExecutionArgs` 新增标签→resolvedQuery映射 | ~60行 |
| **新建** `services/TagNormalizer.js` | 标签模糊归一化（"掉包"→"丢包"等） | ~80行 |

**不动**：NapmClient、MetricExecutionKernel、QueryValidator 等全部现有代码。

## 二、openai.yaml 改为什么

```
interface:
  default_prompt: |-
    你是 NAPM 查询助手。对每个用户查询，提取语义标签后立即调用 napm-skill-query。

    第一步：提取标签。只需填写以下字段，用中文描述即可：
    {
      "metricIntent": "丢包|报错|流量|延迟|连接数|数据包|页面访问|重传|...",
      "objectScope": "IP|业务|业务组|已定义应用|网段|...",
      "queryShape": "排行|均值|趋势|清单|综合分析",
      "timeAnchor": "最近1小时|最近24小时|今天|最近7天",
      "resultSize": "1个|5个|10个|20个"
    }

    第二步：立即调用 napm-skill-query，参数: { prompt: "用户原话", semanticTags: <上面的JSON> }
    
    不要获取当前时间。不要构造 resolvedQuery。不要查 queryModeKey。
    标签用中文填，不需要翻译成 NAPM 内部 code。插件自动映射。
    
    如果工具返回了 needsConstruction，说明需要你构造复杂查询，再照做。
    
    叙述要求：包含时间范围，不暴露英文推理，不输出 JSON 原文。
```

## 三、插件改动：标签 → resolvedQuery

### 3.1 prepareSkillExecutionArgs 新增逻辑

```
function prepareSkillExecutionArgs(args) {
  // 新增：如果有 semanticTags，直接映射为 resolvedQuery
  if (args.semanticTags) {
    const mapped = mapTagsToResolvedQuery(args.semanticTags, args.prompt);
    if (mapped.ok) {
      args.resolvedQuery = mapped.resolvedQuery;
      return applyPathPreflightToSkillArgs(args);
    }
    // 映射失败 → 需要 LLM 构造复杂查询
    return { needsConstruction: true, reason: mapped.reason };
  }
  
  // 原有逻辑不变
  maybeAutoRepairResolvedQuery(args);
  return applyPathPreflightToSkillArgs(args);
}
```

### 3.2 TagNormalizer.js（新增）

```javascript
// 把 LLM 千变万化的中文标签归一化到标准 key
const METRIC_NORMALIZE = {
  '丢包': 'packet_loss', '掉包': 'packet_loss', 'packet loss': 'packet_loss',
  '报错': 'http_error', '错误': 'http_error', '异常': 'http_error',
  'HTTP错误': 'http_error', '4xx': 'http_error', '5xx': 'http_error',
  '流量': 'traffic', '带宽': 'traffic', '吞吐': 'traffic',
  '延迟': 'latency', '响应时间': 'latency', '慢': 'latency', '卡': 'latency',
  '连接数': 'connection', '连接': 'connection',
  '数据包': 'packet_count', '包数量': 'packet_count',
  '页面访问': 'page_visits', '访问量': 'page_visits',
  '重传': 'retransmission',
  '慢页面': 'slow_page',
  // ... 覆盖所有常见中文说法
};

function normalizeMetricIntent(raw) {
  const text = String(raw || '').trim().toLowerCase();
  for (const [key, value] of Object.entries(METRIC_NORMALIZE)) {
    if (text.includes(key)) return value;
  }
  return null; // 无法归一化 → 规则引擎放弃 → 回退 LLM
}
```

### 3.3 标签 → resolvedQuery 映射表

```
metricIntent + objectScope → metric code:

  packet_loss    + IP/网段 → PLI
  http_error     + 业务    → PGHTTP400, PGHTTP500
  http_error     + 业务组  → RFCI, RFCO
  http_error     + IP/网段 → RFCI, RFCO
  traffic        + ANY     → TPIO
  latency        + 业务    → PGTME
  latency        + IP/网段 → RTTI, TRTI
  connection     + IP/网段 → CONI, CCNI
  packet_count   + ANY     → PKIO
  page_visits    + 业务    → PGNPGE
  retransmission + ANY     → RTXI

objectScope → groups:
  IP        → [{type:"IPAddress"}]
  业务      → [{type:"WebApplication"}]
  业务组    → [{type:"BusinessGroup"}]
  网段      → [{type:"Prefix24"}]
  已定义应用 → [{type:"DefinedApp"}]

queryShape → service + queryModeKey:
  排行 → topValues, topn
  均值 → averageValues, average
  趋势 → timeValues, timeseries
  清单 → groups/metrics, metadata

timeAnchor → timestamps (复用 ResolvedQueryTimeRangeService):
  最近1小时  → start: now-3600, end: now
  最近24小时 → start: now-86400, end: now
  今天      → today 00:00 ~ 23:59
  最近7天   → start: now-604800, end: now

resultSize → topCount:
  1个 → 1, 5个 → 5, 10个 → 10, 20个 → 20
```

## 四、完整流程

```
用户: "有没有哪个IP一直在掉包"
    │
    ▼
LLM (openai.yaml 新 prompt):
  提取标签 → {metricIntent:"丢包", objectScope:"IP", queryShape:"排行", 
              timeAnchor:"最近1小时", resultSize:"1个"}
  调 napm-skill-query({ prompt:"...", semanticTags: {...} })
    │ 耗时: ~2s (1轮推理，填5个选择题)
    ▼
插件 prepareSkillExecutionArgs:
  TagNormalizer: "丢包" → packet_loss, "IP" → IPAddress
  Mapper: packet_loss+IPAddress → PLI, topValues/topn, topCount=1
  TimeService: "最近1小时" → start/end Unix timestamps
  → resolvedQuery 完整构造
    │ 耗时: ~9ms
    ▼
NAP API 执行 → 0.7s
    │
    ▼
LLM 叙述结果 → 2s

总耗时: ~5s (vs 当前 60s)
```

## 五、LLM 只做填标签的好处

| | 构造 resolvedQuery | 填语义标签 |
|------|------|------|
| 输出 token | ~500 | ~50 |
| 思考内容 | 字段名、格式、时间戳计算、code | 用户问了什么 |
| 错误类型 | 漏字段、错年份、错 code | 标签描述不准 |
| 错误率 | 40% | <5% |
| 规则引擎角色 | 修 LLM 的错 | 从标签精确映射（零错误） |
| "掉包"→PLI | LLM 不一定知道 | TagNormalizer 100%知道 |

## 六、异常处理

```
标签映射成功 → 直接执行 → 返回结果 → LLM 叙述

标签映射失败（metricIntent 无法归一化、drilldown 需要多层路径等）:
  → 返回 { needsConstruction: true, reason: "..." }
  → LLM 收到后，走原来的复杂查询构造路径
  → 只影响复杂查询，不影响 80% 的简单查询
```
