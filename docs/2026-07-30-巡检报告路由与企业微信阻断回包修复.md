# 巡检报告路由与企业微信阻断回包修复

> 后续状态（2026-08-20）：统一仓库 rc.12 中没有保留本文所述的独立巡检分类，`isSummaryPrompt()` 再次把“报告 + 时间范围”识别为综述报告。2026-08-19 的真实企业微信测试已复现误路由。当前实现和后续验收以《2026-08-19-NAPM巡检报告误路由根因与修复方案》为准。

## 现象

企业微信输入“给我最近一天系统的巡检报告！”后，出现重复的插件阻断 JSON 和报告导出兜底文本，未获得巡检报告。

## 根因

1. `isSummaryPrompt()` 将“报告 + 时间范围”一律识别为综述报告，覆盖了“巡检报告”应走的专用链路。
2. 巡检快照、报告导出和后续错误工具调用没有统一的单次工作流状态，模型可继续重复调用工具。
3. 内部 `plugin-before-tool-call` 阻断 payload 未被企业微信出站守卫过滤，因而被直接发送或被后续兜底改写。

## 修复

- 新增巡检报告分类，优先于综述报告分类；巡检请求固定为 `napm-inspection-snapshot -> napm-report-export`。
- 巡检工作流限制为一次快照、一次报告导出；导出完成后不再允许重复导出。
- 成功的报告导出结果按会话范围回放；导出失败时仅回放一次真实失败结果。
- 在 `before_message_write` 和 `message_sending` 两层拦截内部阻断 JSON，禁止其出现在企业微信。

## 验证

- 回归输入：`给我最近一天系统的巡检报告！`
- 断言：不再被分类为 summary；禁止 `napm-skill-query` / `napm-summary`；允许巡检快照后导出；阻断 JSON 不写入也不发送。
- 本地验证：`node --check napm-openclaw-plugin.remote.js`；Jest 73 suites / 506 tests 通过。

## 二次根因与修复

真实企业微信复测证明巡检快照和报告导出 Tool 都被调度，但没有进入报告渲染器：`before_tool_call` 仅原地修改了 `event.params.traceId`，专用 Tool 分支返回 `undefined`。生产 Typed Hook 不保证该对象修改会传入 `execute()`，使快照结果按空会话 scope 保存，导出器找不到 `reportData` 后直接返回 `REPORT_DATA_NOT_FOUND`。

现已改为巡检快照、巡检报告导出、告警、综述、故障诊断显式返回带 `traceId` 的 `{ params }`；数据包和普通报告导出在通用分支同样显式回传。普通 Query 与开发诊断 Tool 保持原返回契约。新增回归直接把 Hook 返回参数交给巡检 Tool 执行，并断言报告数据保存在原企业微信会话范围。
