# PgPerf 页面性能分析集成 — 方案与实施记录

> 日期：2026-07-14
> 作者：Peter
> 关联：NAPM 故障诊断 Skill — `openclaw-napm-fault-diagnosis`

---

## 一、背景

### 1.1 现状

NAPM 故障诊断 Skill 内置两条标准化分析流程：

| 流程 | flowType | 覆盖场景 |
|---|---|---|
| B/S 业务慢 | `bs_app_slow` | Web 页面 HTTP 4xx/5xx 报错 → 页面错误分布 → 状态码详情 |
| C/S 应用慢 | `cs_app_slow` | 客户端软件慢 → 用户体验时间波峰 → 慢客户端定位 |

`bs_app_slow` 走的是 NAPM 中 **PgAna（页面错误分析）** 路径——关注 HTTP 状态码错误，分析锚点是"哪个页面报错最多"。

### 1.2 缺失的能力

NAPM 中还有一个平行的分析模块 **PgPerf（页面性能分析 / 性能问题根本原因定位）**，位于 `business/PagePerformance.jsp`，关注的是：

> **"页面慢的根因是应用服务器问题还是网络问题？"**

核心指标和判断逻辑：

```
PageTime（页面总耗时）≈ ServBusyTime（服务器处理耗时）+ NetBusyTime（网络传输耗时）

ServBusyTime 占比 > 60% → 根因是应用服务器处理慢
NetBusyTime  占比 > 60% → 根因是网络传输慢
```

PgPerf 与 PgAna 的对比：

| | PgAna（已有） | PgPerf（新增） |
|---|---|---|
| **分析目标** | HTTP 状态码错误 | 延时根因（服务器 vs 网络） |
| **topValues 指标** | PGHTTP200/300/400/500 | PGTME, PGNSLPGE, PGSLPCT |
| **pageViews 核心列** | HttpStatus, Http200S, Http400S, Http500S | PageTime, ServBusyTime, NetBusyTime |
| **默认排序** | PGHTTP500 | PGNSLPGE |
| **三层钻取** | topValues → pageViews → pageDetailViews | **完全相同** |

**痛点**：用户反馈"页面慢/卡/转圈但不报错"的场景，现有 `bs_app_slow` 无法覆盖——它只能分析有 HTTP 错误码的请求，无法回答"页面没报错但就是慢"这类性能问题。

### 1.3 目标

将 PgPerf 的分析能力集成为第三条标准化流程 `bs_page_perf`，与现有的 `bs_app_slow` / `cs_app_slow` 平行。

## 二、设计决策

### 2.1 架构选择：新增独立 flow

**选择：新增 `bs_page_perf` 作为独立 flow 类型，不融入现有 `bs_app_slow`。**

理由：

1. **NAPM 自身分离**：PgAna（页面错误分析）和 PgPerf（页面性能分析）在 NAPM 中是两个独立的 JSP 页面，各自有独立的分析目标和展示列
2. **关键词可区分**："报错/400/500/错误" → 错误分析，"慢/延时/加载/卡顿" → 性能分析
3. **零风险**：现有 `bs_app_slow` 完全不变，新增流程不会影响已有调用
4. **架构一致**：与 `bs_app_slow` / `cs_app_slow` / `network_slow` 的平行结构完全一致
5. **报告模板独立**：PgPerf 报告的表格列（PageTime/ServBusyTime/NetBusyTime）与错误分析报告完全不同

### 2.2 路由策略：两层判定

```
第一层：NAPM 目录解析（catalog 查询）
  └─ Type=3 → bs_app_slow
  └─ Type≠3 → cs_app_slow

第二层：用户意图覆盖（isPerfDescription）
  └─ bs_app_slow + 性能关键词 → 切换为 bs_page_perf
  └─ target 不变（仍是 WebApplication）
```

目录解析的权威性保留（判断是否为 WebApplication），但用户意图可以覆盖分析类型（判断走错误分析还是性能分析）。

### 2.3 关键词设计

使用**正则 + 关键词**双重匹配，解决中文分词歧义（如"加载很慢"≠"加载慢"）：

```javascript
// 正则：匹配"页面/加载/响应 + {0-2字} + 慢/延时/卡顿"
/(?:页面|加载|访问|响应|打开|载入|渲染|首屏).{0,2}(?:慢|延时|延迟|卡顿|卡|转圈)/

// 精确关键词
'页面性能', '性能分析', '白屏', '页面加载', '加载慢', '响应慢', ...
```

## 三、新增流程：B/S 页面性能慢（bs_page_perf）

### 3.1 三步标准化流程

```
Step 1 — 页面性能总览（averageValues，1 次 API 调用）
  接口: getAverageValues
  指标: PGNPGE, PGTME, PGNSLPGE, PGSLPCT
  分组: WebApplication
  判断: highAvgDelay(>3s) / highSlowPageRate(>10%) / highSlowPageCount(>100)

Step 2 — 页面延时 Top 20（topValues 三层钻取，1 次 API 调用）
  接口: getTopValues
  指标: PGNPGE, PGTME, PGNSLPGE, PGSLPCT
  排序: PGNSLPGE（慢页面数），Top 20
  分组: WebApplication → PageFamilies → PageFamily
  判断: slowPageConcentrated / slowPagesScattered / highDelayPageFound

Step 3 — 延时成分拆分（pageViews，对 Step2 每个慢页面 1 次 API 调用）
  接口: pageViews
  参数: pageFamilyId（从 Step2 groupPath 正则 /page\s+(\d+)/ 提取）
  分析: ServBusyTime vs NetBusyTime 占比
  判断: serverDominant(>60%) / networkDominant(>60%) / mixedDelay
        timeConcentrated / clientConcentrated / scatteredSlow
```

### 3.2 判断提示（15 条 hints + 3 条 packetTriggers）

完整定义在 `templates/judgment-hints.v1.json` → `bs_page_perf` 节点：

- **Step 1 (4 条)**：highAvgDelay → 建议进入延时成分分析；highSlowPageRate → 普遍性性能问题；highSlowPageCount → 多接口或公共依赖问题；perfNormal → 检查客户端环境
- **Step 2 (4 条 + 1 packetTrigger)**：slowPageConcentrated → 优先排查集中页面后端；slowPagesScattered → 公共组件问题；topVisitPageSlow → 高影响面；highDelayPageFound → 进入延时成分拆分 + 建议下载数据包
- **Step 3 (7 条 + 2 packetTriggers)**：serverDominant → 排查后端/数据库/中间件；networkDominant → 排查带宽/链路/重传；mixedDelay → 分别优化；singlePageSlow → 单页面专项；multiPageSlow → 公共基础设施；clientConcentrated → 客户端侧；timeConcentrated → 时段性负载；scatteredSlow → 扩大排查范围

### 3.3 报告结构

模板 ID：`napm_bs_page_perf_v1`（新建）

```
封面 → 目录
1 基本信息（故障名称/分析类型/分析对象/故障级别）
2 分析过程
   2.1 页面性能总览（指标表 + 分析提示）
   2.2 页面延时分析 Top 20（页面列表 + 分析提示）
   2.3 延时成分分析（逐次访问明细 + 服务器占比/网络占比 + 分析提示）
3 证据项（步骤/查询指标/数据量汇总）
4 根因判断（条件叙事规则：慢页面率 + 延时成分组合判断）
5 处置建议（服务器导向/网络导向 分路径）
6 验证方式
```

叙事规则见 `bs-perf-narrative-rules.v1.json`，支持条件组合：

```
慢页面率 ≥ 30% + step3Hints 存在 → 综合判断（含百分比数据）
10% ≤ 慢页面率 < 30% → 中度问题，关注集中 URL
慢页面率 < 10% → 正常范围，建议检查客户端
avgDelay > 3s → 延时超标，结合成分拆分判断
default → 综述
```

### 4.2 核心实现细节

#### 4.2.1 路由覆盖逻辑（`FaultDiagnosisService.start()`）

```javascript
// 目录解析（第一层）
const match = matchAppByName(candidateName, catalog);
if (match) {
  const resolved = resolveFlowTypeFromCatalog(match);
  flowType = resolved.flowType;  // Type=3 → bs_app_slow
}

// 关键词覆盖（第二层）
if (flowType === 'bs_app_slow' && isPerfDescription(description)) {
  flowType = 'bs_page_perf';  // target 不变，仍是 WebApplication
}
```

#### 4.2.2 模板数据构建（`_buildBsPerfTemplateData`）

报告数据结构与 `_buildBsTemplateData` 完全平行，差异仅在于：

- `templateId`: `'napm_bs_page_perf_v1'`
- `title`: `'XX_页面性能分析报告'`（而非 `_业务故障分析报告`）
- `step1` 提取 `PGTME/PGNSLPGE/PGSLPCT`（而非 HTTP 状态码）
- `step2` 按 `PGNSLPGE` 降序排列
- `step3` 提取 `PageTime/ServBusyTime/NetBusyTime` 并计算 `servRatio/netRatio`（而非过滤 HTTP 200）

#### 4.2.3 模板服务继承（`BsPerfTemplateService`）

```javascript
class BsPerfTemplateService extends BsFaultTemplateService {
  // 仅覆写差异部分：
  // - defaultTemplateId → 'napm_bs_page_perf_v1'
  // - buildRowsForSection() → 4 个 PgPerf row builder
  // - loadNarrativeRules() → bs-perf-narrative-rules.v1.json
}
```

继承 `BsFaultTemplateService` 可以复用完整的 Docx 渲染管线（封面、目录、TOC 样式后处理、图表、段落等），仅需替换表格行构建器和叙事规则。

#### 4.2.4 Step 3 延时成分分析（核心分析逻辑）

```javascript
_analyzePerfStep3(raw) {
  // 对每个页面的 pageViews 数据：
  for (const row of rows) {
    const servBusy = Number(row.servBusyTime || row.ServBusyTime || 0);
    const netBusy = Number(row.netBusyTime || row.NetBusyTime || 0);
    totalServBusy += servBusy;
    totalNetBusy += netBusy;
  }
  // 分类：serverRatio > 0.6 → serverDominant
  //       serverRatio < 0.4 → networkDominant
  //       0.4-0.6 → balanced
  // 同时分析：客户端 IP 集中度 + 时间桶分布
}
```

#### 4.2.5 模板注册（`ReportTemplateService.js`）

```javascript
if (report.templateId === 'napm_bs_page_perf_v1') {
  return this.bsPerfTemplate.renderDocx(report);
}
```

## 六、测试中发现并修复的问题

测试过程中发现并修复了 3 个 Bug：

### Bug 1：中文分词歧义导致关键词不匹配

**现象**：`classify("XXweb 页面加载很慢")` 返回 `bs_app_slow` 而非 `bs_page_perf`

**根因**：关键词列表使用精确字符串匹配（`'加载慢'`），但中文文本中常有插入词——"页面加载**很**慢"中"加载"与"慢"之间隔了"很"字，导致精确匹配失败。随后 `bs_app_slow` 的关键词 `'web'` 匹配了 "XXweb"，导致错误路由。

**修复**：在 `classify()` 和 `isPerfDescription()` 中增加正则匹配层：
```javascript
// 正则：允许关键词之间有 0-2 个插入字符
/(?:页面|加载|访问|响应|打开|载入|渲染|首屏).{0,2}(?:慢|延时|延迟|卡顿|卡|转圈)/
```

**影响文件**：`FaultDiagnosisFlowRouter.js` — `classify()` 和 `isPerfDescription()`

### Bug 2：extractTargetName 不识别 PgPerf 关键词模式

**现象**：`extractTargetName({ prompt: "testweb 页面加载很慢" })` 返回 `null`

**根因**：`_extractFromDescription()` 中的 `kwPatterns` 只包含故障/错误分析相关的关键词（如"应用故障"、"业务慢"、"故障分析"），不包含 PgPerf 页面性能相关的关键词。

**修复**：在 `kwPatterns` 数组中新增 3 类 PgPerf 模式：
```javascript
// 模式1：灵活匹配（正则，允许插入词）
/(?:页面|加载|延时|延迟|性能).{0,3}(?:慢|高|长|分析|诊断|卡顿|问题|拆分)/,
// 模式2：单关键词匹配
/(?:首屏|白屏|卡顿|转圈)/,
// 模式3：组合精确匹配
/(?:页面加载|页面慢|页面延时|页面延迟|页面卡顿|加载慢|响应慢|打开慢|渲染慢|性能分析|性能诊断|延时分析)/,
```

**影响文件**：`FaultDiagnosisFlowRouter.js` — `_extractFromDescription()`

### Bug 3：泛化模式"分析一下"过早匹配

**现象**：`extractTargetName({ prompt: "请帮我分析一下 238web 首屏加载慢的问题" })` 返回 `null`（期望返回 `"238web"`）

**根因**：原有的 `kwPatterns` 中包含 `/分析(?:报告|诊断|一下)/` 模式，它会匹配"分析一下"这个填充短语。在 PgPerf 模式之前匹配到"分析一下"后，`kwMatch.index` 指向位置 3（"分"字），导致 `before` 提取到的是"请帮我"而非"请帮我分析一下 238web 首屏"。

**修复**：
1. 从 `/分析(?:报告|诊断|一下)/` 中移除 `|一下`——"分析一下"是填充短语，不应作为诊断意图关键词
2. 将 PgPerf 模式移到该模式之前，确保页面性能意图优先匹配

**修改前**：
```javascript
kwPatterns = [
  ...,
  /分析(?:报告|诊断|一下)/,    // ← 过早匹配"分析一下"
  // PgPerf 模式在后
]
```

**修改后**：
```javascript
kwPatterns = [
  ...,
  // PgPerf 模式在前，优先匹配
  /(?:页面|加载|延时|延迟|性能).{0,3}(?:慢|高|长|分析|诊断|卡顿|问题|拆分)/,
  /(?:首屏|白屏|卡顿|转圈)/,
  /(?:页面加载|页面慢|页面延时|...)/,
  ...,
  /分析(?:报告|诊断)/,          // 移除"一下"，移到后面
]
```

**影响文件**：`FaultDiagnosisFlowRouter.js` — `_extractFromDescription()` 中 `kwPatterns` 的顺序和内容
