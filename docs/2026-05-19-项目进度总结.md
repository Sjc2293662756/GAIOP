## 2. 当前项目最准确的一句话总结

截至当前代码状态，本项目已经基本收口为一个：

**“由 OpenClaw 主链负责理解与结构化判路，由 `napm-openclaw-plugin` 负责技能路由注入与守门，由 `openclaw-napm-query skill` 负责执行 NAPM 查询并输出 narration contract 的执行型网关。”**

更准确地说：

```text
用户提问
  -> OpenClaw 主链做自然语言理解与边界判断
  -> napm-openclaw-plugin 为简单固定问法尽早注入 structured resolvedQuery
  -> openclaw-napm-query skill 执行查询、做元数据访问、路径规划、overview 编排、contract 输出
  -> OpenClaw 再把 contract 组织成最终用户回答
  -> 企业微信插件只负责通道与结果承载
```

当前已经不是“本地脚本直接猜 query”的阶段，但也还没有完全进入“所有复杂问法都能一次性结构化编译”的终态。

## 3. 当前真实运行主链

当前最值得记住的真实主链是：

```text
用户

  -> napm-openclaw-plugin.remote.js

  -> RequirementParserService / overview-module

  -> 企业微信结果通道
```

如果按职责拆开看，当前主链已经明显分成三段：

2. **执行与编排段**
   - `skills/openclaw-napm-query/scripts/run_napm_query.js`
   - `skills/openclaw-napm-query/services/RequirementParserService.js`

   - `skills/openclaw-napm-query/services/NapmMetadataService.js`

## 4. 当前职责边界

## 4.1 企业微信插件

企业微信插件当前应继续理解为：

- 消息接入通道；
- 最终结果承载通道；
- 不参与新的语义判路改造。

也就是说，企业微信插件不是当前“为什么查得慢、为什么查不准”的主要修补点。

## 4.2 OpenClaw 主链 + napm-openclaw-plugin

这一层当前负责：

- 判断问题是否属于 NAPM 域；
- 决定是否必须走 `napm-skill-query`；
- 对简单固定问法尽早注入结构化 `resolvedQuery`；
- 在 skill 执行前做必要的路径预判补齐；
- 阻止模型绕开 skill 去乱走其它系统工具。

2026-05-19 之后，这一层最重要的变化是：

- `PromptRoutingService` 已经从零散判断函数，提升为共享路由入口；
- `prepareSkillExecutionArgs()` 和 `buildCanonicalSkillToolParams()` 已统一复用同一套路由注入逻辑；
- `before_message_write` 已回退为同步守门层，而不是继续承担半个执行层职责。

## 4.3 openclaw-napm-query skill

skill 当前负责：

- 消费 structured `resolvedQuery`；
- 执行普通查询；
- 执行 overview 编排查询；
- 做元数据访问、路径规划、drilldown catalog 输出；
- 输出 OpenClaw 可消费的 narration contract；
- 在必要时返回 clarification / decision contract。

需要强调的是：

- skill 现在已经不是主理解层；
- 但 skill 仍保留少量定向 prompt fallback，用于在上游未注入结构化参数时尽量快速收口固定问法。

## 4.4 NAPM 上游接口

NAPM 上游接口当前仍是纯数据源与元数据源：

- 提供 metrics、groups tree、arguments、granularities 等元数据；
- 提供 topValues / averageValues / timeValues / groups 等实际查询结果；
- 不负责业务语义理解。

## 5. 当前已经收口的核心语义与路由约定

这一部分是当前项目最容易被改乱、但又最必须稳定的口径。

### 5.1 对象语义

- 普通“业务 / 业务系统 / Web应用 / 网站 / 站点”默认应落到 `WebApplication`
- 只有明确出现“业务组 / 工作组 / 分组”时，才应落到 `BusinessGroup`
- “应用 / 已知应用 / 协议应用”默认落到 `DefinedApp`

### 5.2 路由语义

当前简单固定问法已经开始往共享路由层集中，典型包括：

- 指标清单问法
- 业务清单问法
- overview 问法
- 层级目录 / 下钻目录问法

### 5.3 路径语义

当前路径规划的职责边界应保持为：

- 顶层对象类型由上游 `resolvedQuery` 或共享路由决定；
- `GroupPathPlannerService` 负责在对象已经基本明确后补齐下钻路径；
- 路径规划器不能偷偷把 `WebApplication` 改成 `BusinessGroup`，也不能反向承担顶层对象纠偏职责。

### 5.4 当前必须继续坚持的口径

后续继续推进时，以下口径必须保持不被破坏：

- `业务 = WebApplication`
- `业务组 = BusinessGroup`
- 简单问法优先第一跳收口，不再依赖后置纠偏
- skill 优先执行结构化查询，而不是重新做一遍自然语言理解

## 6. 2026-05-19 之后的关键变化

相较于 2026-05-12，这个仓库在 2026-05-19 已经发生了几处非常关键的结构收口。

## 6.1 共享路由入口已经出现

当前已经新增并接入：

- `skills/openclaw-napm-query/services/PromptRoutingService.js`
- `resolvePromptRoute(prompt, options)`

它已经不再只是单点判断 `isOverviewPrompt()` 之类，而是开始承担统一判路入口职责。

## 6.2 插件两个入口已经统一路由注入

当前插件内两个关键入口：

- `prepareSkillExecutionArgs()`
- `buildCanonicalSkillToolParams()`

都已经统一走：

- `resolvePromptInjectedResolvedQuery()`

这意味着：

- 同一句 prompt 在两个入口下的结构化注入顺序已经收口；
- “一个入口识别对了、另一个入口识别错了”的概率明显下降。

## 6.3 `before_message_write` 已经回退为守门层

当前同步钩子的职责已经比之前更清楚：

- 保留同步保护；
- 不再继续常态化承担结果重写与查询补偿职责。

这是一次很重要的边界回收。

## 6.4 skill prompt fallback 已经覆盖业务清单

当前 `run_napm_query.js` 中的本地 prompt fallback，已经不再只覆盖 overview。

当前实际保留的定向 fallback 包括：

1. 指标清单 fallback
2. 业务清单 fallback
3. 未知端口流量 fallback
4. 双协议未知端口流量 fallback
5. overview fallback
6. hierarchy catalog prompt fallback（单独在后置分支）

这说明当前 skill 的本地 fallback 已经更像“兼容型固定入口”，而不是早期那种通用 prompt 解析主链。

## 8. 当前仍然存在的结构性问题

这一部分是当前项目最需要诚实写清楚的地方。

## 8.1 还没有完全做到 pure resolvedQuery-only

当前代码已经移除了“通用自然语言本地猜测主链”，但仍然保留少量 **定向 prompt fallback**。

因此，当前最准确的表述不是：

```text
Skill 已经完全不看 prompt
```

而是：

```text
Skill 已经不再承担通用自然语言理解
但仍保留少量固定问法兼容入口
```

## 8.2 简单问法判路已改善，但复杂复合问法还没有统一规划器

当前已经完成的是：

- 简单固定问法的共享路由收口

但还没有完成的是：

- 复杂复合问法的一次性统一编译

例如这类问法：

- `连接失败数最多的业务的成员IP都有谁`
- `报错最多的业务是哪个，继续分析它`

当前仍缺少一个真正统一的：

- 对象判定
- 指标归属判定
- 子路径角色判定
- discovery -> focus -> drilldown 统一执行计划

也就是说，当前还没有专门的 `QueryPlanningService` 或同等级统一规划层。

## 8.3 对象 / 指标 / 路径的联合规划还没完全收口

当前这三个判断仍然分散在多层中：

- `PromptRoutingService`
- `napm-openclaw-plugin.remote.js`
- `RequirementParserService`
- `GroupPathPlannerService`
- `ClarificationGateService`

所以当前项目的真实状态是：

```text
简单问题已经能更早命中固定路径
复杂问题还没有完全做到“一次编译、直接执行”
```

## 8.4 “业务 = WebApplication” 这条口径必须继续守住

这是当前项目里非常关键的稳定语义。

后续改造时，不能因为某个指标更像 `BusinessGroup`，就把普通“业务”偷偷改写成 `BusinessGroup`。

如果后续出现：

- 对象已锁定为 `WebApplication`
- 指标或子路径与之不兼容

那么正确做法应当是：

- 显式桥接
或
- 一次澄清

而不是：

- 偷偷换对象

## 12. 当前最值得记住的几个结论

## 12.1 结论一：Skill 现在是执行中枢，不是主理解层

当前 skill 最核心的价值是：

- 执行结构化查询；
- 编排 overview；
- 输出 contract；
- 在执行前做守卫与兼容收口。

它已经不应该再回到“主解析 prompt”的角色。

## 12.2 结论二：简单问题变慢的主要根因，已经从“不会理解”转向“判路不够早”

截至 2026-05-19，这个问题已经部分被修复：

- 简单固定问法不再完全依赖临场自由探索；
- `PromptRoutingService` 和插件统一注入已经降低了多入口不一致问题。

## 12.3 结论三：当前最大的剩余问题不是再补单题，而是缺统一查询规划器

当前真正没完成的是：

- 对象、指标、路径、复合执行计划的一次性联合规划。

这也是为什么复杂复合问法仍然可能慢、仍然可能绕。

## 12.4 结论四：企业微信插件不是当前主改造点

当前最应该继续改的是：

- OpenClaw 主链与插件的判路层
- skill 的统一查询规划与执行层

而不是企业微信传输层。

## 13. 后续建议

按照当前仓库状态，后续最建议继续推进的事情有 5 件：

1. 新增统一查询规划层  
   建议新增 `QueryPlanningService`，把对象、指标、路径、复合执行计划统一编译。

2. 新增对象-指标兼容层  
   建议新增 `ObjectMetricCompatibilityService`，在执行前就识别 `对象已锁定但指标不兼容` 的场景。

3. 继续把简单 prompt 路由往共享服务集中  
   逐步减少 `run_napm_query.js` 内部散落 fallback 对路由优先级的独立维护。

4. 把复杂复合查询统一为 discovery -> focus -> drilldown 计划  
   避免继续出现“边试 API 边猜用户语义”的执行模式。

5. 用新增测试守住关键语义  
   尤其是：
   - `业务 = WebApplication`
   - `业务组 = BusinessGroup`
   - 简单清单问法第一跳收口
   - 复杂复合问法不偷偷换对象

当前最准确的总体判断是：

```text
主链已经成形
```
