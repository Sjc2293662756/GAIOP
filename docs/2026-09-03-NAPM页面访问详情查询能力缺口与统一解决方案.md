# NAPM 页面访问详情查询能力缺口与统一解决方案

> 2026-09-08 复核补充：本文保留首次实现时的历史记录，不代表当前所有页面追问和跨 Skill 事实链路均已完成。现已确认第三轮引用类型误拦截、标准字段缺失、异常响应误归一化及多客户端等缺口。后续实施以 [pageViews 事实链路补齐与统一实施方案](2026-09-08-NAPM-pageViews事实链路补齐与统一实施方案.md) 为准；共享辅助契约不等于三个 Skill 已统一数据访问。新方案当前仅为设计，尚未实施。

> 文档状态：本地功能分支已实施，待审查与整合，尚未部署
> 编写日期：2026-09-03
> 适用范围：`openclaw-napm-query`、NAPM OpenClaw 插件、Query Turn、多轮下钻，以及与故障诊断和数据包分析的能力边界
> 本文不代表已完成部署，不包含任何生产环境变更。

## 1. 结论

Query Skill 现已在本地功能分支支持业务访问量排行、页面族排行、页面聚合指标以及某个页面族下面的逐次访问详情。该实现尚未合并或部署，不能据此声明生产环境已经具备此能力。

原问题中，第三轮追问“详细查看排名第一的前 20 个”被错误构造成 `PageFamilyDetail` 分组下钻。现有实现会阻断该形状，并使用独立的 NAPM `pageViews` 服务；插件从上一轮权威页面排行投影解析 `pageFamilyId`，继承来源时间范围，再附加受校验的 `maxLimit`。

正确链路应为：

```text
WebApplication 业务访问量 TopN
  -> WebApplication > PageFamilies > PageFamily 页面族 TopN
  -> 从选中页面行的权威 groupPath 提取 pageFamilyId
  -> pageViews(start, end, pageFamilyId, maxLimit)
  -> 访问详情行及其 pageFamilyDetailId
  -> 可选：故障原因分析或数据包下载
```

该能力原先只在 `openclaw-napm-packet-analysis` 和 `openclaw-napm-fault-diagnosis` 局部存在。当前分支新增共享 `NapmPageViewsContract`，并让 Query、Fault Diagnosis 和 Packet Analysis 统一使用相同的 ID、limit、请求和结果字段语义。

## 2. 用户场景与复现

### 2.1 第一轮：业务访问量排行

用户问题：

```text
今天哪些业务页面访问量最高？
```

当前可使用：

- `service=topValues`
- `groups=[{type:"WebApplication"}]`
- `metric/topMetric=PGNPGE`
- `topCount=N`

这一步得到业务对象排行，属于 Query Skill 已支持能力。

### 2.2 第二轮：指定业务下的页面排行

用户追问：

```text
排名第一的都访问了什么？
```

当前可使用已验证的多级路径：

```text
WebApplication(argument=选中的业务)
  -> PageFamilies
  -> PageFamily
```

配合 `topValues + PGNPGE` 可得到页面族排行。返回行的 `groupPath` 中通常包含页面族 ID，例如：

```text
...>pages>page <pageFamilyId>/<page-label>
```

这一步仍属于聚合排行，不是逐次访问明细。

### 2.3 第三轮：页面访问实例详情

用户追问：

```text
详细查看一下排名第一的前 20 个
```

当前错误行为：

```text
把 PageFamilyDetail 当成新的 groupType 继续下钻
  -> 返回 0 行
  -> 误判为页面没有更细数据
```

预期行为：

```text
从上一轮第 1 行解析 pageFamilyId
  -> 调用 pageViews
  -> maxLimit=20
  -> 返回最多 20 条页面访问实例
```

复现原问题不需要连接生产服务器：基线提交 `12d81e2d204a3d04fe6df73e2bf9f866c3fff697` 之前的 resolution spec 和 Query Validator 不接受 `pageViews`，而数据包和故障诊断又各自维护局部调用。当前分支通过本地测试夹具验证新契约，没有连接生产服务器。

## 3. 领域模型必须先统一

### 3.1 PageFamily

`PageFamily` 表示页面族或归并后的页面对象，是 `topValues` 等聚合查询可以使用的终端分组维度。它可以承载：

- 页面访问量 `PGNPGE`；
- 页面流量；
- 页面响应时间；
- 慢页面数量；
- HTTP 400/500 数量或比例等聚合指标。

### 3.2 pageFamilyId

`pageFamilyId` 是页面族的服务端标识。当前代码可从页面排行记录的 `groupPath` 中提取该值，它是调用 `pageViews` 的输入。

它不应由模型根据 URL、页面名称或排行序号自行编造。

### 3.3 PageFamilyDetail

当前项目没有把 `PageFamilyDetail` 定义为 Query Skill 的分组对象，也没有证据表明它是可追加到 `groups` 的层级节点。因此不得构造：

```json
{
  "groups": [
    { "type": "WebApplication" },
    { "type": "PageFamilies" },
    { "type": "PageFamily" },
    { "type": "PageFamilyDetail" }
  ]
}
```

这种形状必须在 Query Decision 和 Skill 校验阶段失败，并保证 Query Skill、`NapmClient` 和南向接口调用次数均为 0。

### 3.4 pageFamilyDetailId

`pageFamilyDetailId` 是 `pageViews` 返回的某次访问实例标识。数据包分析可把它归一化为 `PATH1/<pageFamilyDetailId>`，继续构造 DownServlet 请求。

因此两个 ID 的方向不能颠倒：

| 标识 | 来源 | 用途 |
| --- | --- | --- |
| `pageFamilyId` | 页面族排行结果 | 调用 `pageViews` |
| `pageFamilyDetailId` | `pageViews` 访问详情结果 | 定位单次访问、数据包下载或进一步分析 |

- `skills/openclaw-napm-packet-analysis/scripts/run_packet_analysis.js` 使用共享构造器，缺省发送数值 `maxLimit=20`。

## 5. 原问题台账与落地状态

### P0-1：Query Skill 缺少 pageViews 服务契约

**状态**：已在当前功能分支解决。

**影响**：模型即使正确理解“查看前 20 条访问详情”，也无法构造一个能通过 Query Decision、resolution spec 和 Query Validator 的查询。

**根因**：现有 Query Skill 服务模型围绕聚合指标、时序、元数据和概览设计，没有把访问实例列表建模为一等查询类型。

**解决方向**：新增 `service=pageViews`、`queryModeKey=detail` 的专用契约和执行内核。

### P0-2：把访问详情错误建模为 PageFamilyDetail 分组

**状态**：已在 Query Decision、Validator 和执行策略中阻断。

**影响**：错误请求可能返回空数据，并被用户侧解释成“没有详情”，掩盖真实的契约错误。

**根因**：当前语义层没有明确区分“对象层级下钻”和“由对象 ID 打开独立详情服务”。

**解决方向**：禁止 `PageFamilyDetail` 出现在普通 `groups`；将“详情、访问明细、前 N 个访问”等语义映射为 `pageViews`。

### P0-3：跨轮次“排名第一”没有权威 ID 引用

**状态**：已为 `PageFamily` 排行结果实现 scope 隔离、30 分钟 TTL 和 Query Turn 冻结引用。

**影响**：模型可能只继承页面显示文本，丢失 `pageFamilyId`；也可能把上一轮业务第一名和页面第一名混淆。

**根因**：当前轻量查询上下文主要保存 `resolvedQuery`，没有为结果行建立可验证的 `resultRef`。Query Turn 虽保存结果，但还没有面向后续选择的稳定引用投影和有效期契约。

**解决方向**：由 `QueryTurnCoordinator` 保存当前会话最近一次可下钻结果的最小权威投影，使用 `turnId + resultSetId + rowIndex` 解析“第一名”，再从服务端保存的行中取得 `pageFamilyId`。模型只表达选择，不传递或猜测内部 ID。

### P0-4：maxLimit 行为不一致且存在字符串 undefined

**状态**：已统一为缺省 20 和本地保护上限 200；上游正式范围仍是开放问题。

**影响**：不同 Skill 对同一 API 形成不同请求；上游可能忽略、拒绝或错误解释 `maxLimit=undefined`。

**根因**：`pageViews` 没有共享参数契约。数据包分析自行构造 URL，故障诊断通过 Client 直接调用，两条路径没有统一校验。

**解决方向**：建立单一 `pageViews` 参数规范；`maxLimit` 必须是受范围约束的正整数，缺省值和最大值在核对真实 API 文档或脱敏请求证据后写入配置。代码不得发送字符串 `undefined`。

### P1-1：页面详情结果没有统一归一化

**状态**：已由共享契约统一。

**影响**：字段命名差异、空值和嵌套响应可能导致 Query、故障诊断和数据包分析展示不一致。

**解决方向**：统一归一化为稳定字段，包括：

```text
index
startTime
page
clientIp
serverIp
originatingIp
httpStatus
http200S/http400S/http500S
httpResponses
pageTime
pageTraffic/requestTraffic
userAgent
pageFamilyDetailId（仅内部引用）
```

对外结果使用稳定 `rowRef`；除维护诊断外，不要求模型或用户直接处理长 `pageFamilyDetailId`。

### P1-2：NO_DATA、无效引用和执行失败可能混淆

**状态**：已区分校验失败、`NO_DATA`、400/403 详情错误和一般执行失败。

**影响**：过期的“第一名”、缺失 `pageFamilyId`、非法 `maxLimit` 或错误服务形状可能被回答成“未查到数据”。

**解决方向**：执行前错误一律不得进入南向；只有完整且成功执行的 `pageViews` 返回 0 行才是 `NO_DATA`。

建议错误分类：

| 场景 | 结果 | 南向调用 |
| --- | --- | --- |
| 找不到上一轮排行 | `CLARIFICATION` 或 `CONTEXT_EXPIRED` | 0 |
| 排名超出结果范围 | `VALIDATION_FAILURE` | 0 |
| 选中行没有 `pageFamilyId` | `VALIDATION_FAILURE` | 0 |
| `PageFamilyDetail` 被当作 group | `VALIDATION_FAILURE` | 0 |
| `maxLimit` 非正整数或超上限 | `VALIDATION_FAILURE` | 0 |
| 完整请求成功但 0 行 | `NO_DATA` | 1 |
| 上游超时、拒绝或解析失败 | `EXECUTION_FAILURE` | 1 |

### P1-3：查询、诊断和数据包路由边界不清

**状态**：详情列表已进入结构化 `page_view_detail/detail_list`；Query 结果到 Fault/Packet 的跨 Skill 权威访问行引用仍未实现。

**影响**：普通“列出访问详情”可能误走完整故障诊断；“为什么 500”又可能被拆成多次普通查询；“下载第一条数据包”可能缺少可信访问实例引用。

**解决方向**：统一结构化意图后按目标动作路由：

| 用户意图 | Tool / Skill |
| --- | --- |
| 查看页面排行、列出前 N 条访问详情 | `napm-skill-query` |
| 分析具体业务/页面的 HTTP 错误、状态码或故障原因 | `napm-fault-diagnosis` |
| 下载、预览或分析某条访问实例的数据包 | `napm-packet-analysis` |

不得在多个路由器中分别增加同义正则。应让统一分类器输出 `operation=detail_list/fault_diagnosis/packet_analysis`、目标对象和引用类型，各策略只消费结构化结果。

### P1-4：重复实现导致契约漂移

**状态**：生产入口均已改用共享契约；故障诊断目录中的旧根级副本仍作为待清理遗留项。

**影响**：数据包与故障诊断已各自实现一部分 `pageViews` 逻辑；若 Query Skill 再复制第三份，很容易继续产生参数和字段差异。

**解决方向**：建立共享的 `NapmPageViewsService` 及契约测试，集中负责请求参数、字段归一化、ID 提取和限制策略。由于 Query Skill 当前声明 skill-local 资源为独立部署权威，提取共享模块时必须同步调整发布打包和 runtime contract，不能只修改 import 路径。

### P2-1：接口约束仍有待确认项

**状态**：仍然存在，当前实现只采用可由本地证据验证的保守规则。

当前本地代码能证明 `pageViews` 使用 `start`、`end`、`pageFamilyId` 和可选/预期的 `maxLimit`，但不能仅凭本地实现断言：

- `maxLimit` 是否为上游必填参数；
- 上游默认值；
- 合法最小值和最大值；
- 结果排序顺序；
- 是否支持分页或游标；
- 超限时是截断还是报错。

这些内容必须通过正式接口文档、脱敏的既有请求证据或独立测试环境确认。确认前不得把猜测固化为生产常量。

## 6. 目标调用链

### 6.1 首轮和页面排行

```text
用户问题
  -> WorkflowClassifierService 产生结构化操作、对象、指标语义
  -> napm-skill-query / QueryDecisionPolicy
  -> QueryTurnCoordinator
  -> topValues
  -> Query Turn 保存权威排行结果及可下钻行引用
  -> exactly-once 交付排行
```

### 6.2 详情追问

```text
用户：“详细查看排名第一的前 20 个”
  -> 分类为 operation=detail_list、target=PageView、ordinal=1、limit=20
  -> 当前 run/message 创建不可变 turnId
  -> Tool 携带可信 traceId 调用 napm-skill-query
  -> QueryTurnCoordinator 在相同 conversation scope 中解析 resultRef
  -> 取得上一轮第 1 个 PageFamily 行及 pageFamilyId
  -> QueryDecisionPolicy 校验引用、时间和 limit
  -> 形成完整 resolvedQuery(service=pageViews)
  -> PageViews 执行内核调用一次南向接口
  -> 统一归一化
  -> Coordinator 生成 RESULT/NO_DATA/FAILURE 权威 finalContent
  -> exactly-once 交付
```

### 6.3 禁止的行为

- 读取会话“最新 turnId”代替当前 run 绑定的 turnId；
- 由模型从页面 URL 猜测 `pageFamilyId`；
- 把排行序号直接当作 `pageFamilyId`；
- 把 `PageFamilyDetail` 加入 `groups`；
- 在引用过期或歧义时默认选择第一行；
- 发送 `maxLimit=undefined`；
- `pageViews` 执行失败后使用上一轮排行伪装本轮详情结果；
- 普通详情列表依赖旧 `ConversationOperationState` 作为结果交付源。

## 7. 建议查询契约

### 7.1 Query Draft：追问引用形态

模型提交选择语义，不提交内部页面 ID：

```json
{
  "service": "pageViews",
  "queryModeKey": "detail",
  "resultReference": {
    "objectType": "PageFamily",
    "ordinal": 1
  },
  "maxLimit": 20,
  "start": 1787702400,
  "end": 1787753100,
  "format": "json",
  "semanticConstraints": {
    "operation": "detail_list",
    "targetObjectType": "PageView"
  }
}
```

`start/end` 应优先继承被引用页面排行的可信时间范围。用户明确修改时间时，重新物化并校验时间。

### 7.2 Query Decision 后的 Resolved Query

插件从权威结果引用解析 ID 后，才能形成可执行请求：

```json
{
  "service": "pageViews",
  "queryModeKey": "detail",
  "pageFamilyId": "<opaque-page-family-id>",
  "maxLimit": 20,
  "start": 1787702400,
  "end": 1787753100,
  "format": "json",
  "sourceReference": {
    "sourceTurnId": "<trusted-turn-id>",
    "resultSetId": "<trusted-result-set-id>",
    "rowIndex": 0
  }
}
```

`sourceReference` 用于审计和防止跨会话串用，不发送到南向接口。

### 7.3 Resolution Spec

建议新增：

```json
{
  "pageViews": {
    "category": "detail_query",
    "required": [
      "service",
      "queryModeKey",
      "pageFamilyId",
      "maxLimit",
      "start",
      "end"
    ],
    "optional": [
      "format",
      "sourceReference",
      "semanticConstraints",
      "resolutionHints"
    ],
    "queryModes": ["detail"]
  }
}
```

是否允许直接提供 `pageFamilyId`，应限定在可信 Tool trace 和完整 Query Decision 内；普通自然语言追问优先使用 `resultReference`。

## 8. 参数与安全策略

### 8.1 pageFamilyId

- 必填且不得为空；
- 来自同一 conversation scope 内未过期的权威 `PageFamily` 结果，或来自经验证的显式对象解析；
- 不从显示 URL、页面名称或模型自由文本猜测；
- 解析失败时澄清或要求重新执行页面排行；
- 未完成验证前不调用 Query Skill 或南向接口。

### 8.2 maxLimit

- 输入必须是整数；
- “前 20 个”确定性映射为 `20`；
- “详细看一下”未给数量时使用配置定义的默认值；
- 小于 1、非数字或超过确认上限时在本地失败；
- 默认值、最大值和是否支持分页必须先完成接口确认；
- URL 构造器仅在有合法数值时设置 `maxLimit`，绝不发送字符串 `undefined`。

### 8.3 时间

- 使用根级 Unix 秒 `start/end`；
- 保持 60 秒边界对齐；
- 默认继承来源页面排行的时间范围；
- 不允许从另一个过期或不同 scope 的结果继承时间；
- 用户说“今天/最近 N 天”时仍由统一时间服务物化，模型不自行计算。

### 8.4 结果隐私和展示

页面访问详情可能包含客户端 IP、服务器 IP、URL、User-Agent 和内部实例 ID。最终回答应：

- 只展示用户请求数量；
- 遵循现有敏感字段和 URL 脱敏策略；
- 将 `pageFamilyDetailId` 保存为内部 `rowRef`，除维护诊断外不直接展示；
- 不在审计日志记录完整页面详情、凭证或未脱敏请求 URL；
- 下载数据包前仍执行 Packet Skill 自身权限和风险控制。

## 12. 回归测试计划

### 12.1 契约和校验

1. resolution spec 能返回 `pageViews` 服务定义。
2. `pageFamilyId` 缺失时 `VALIDATION_FAILURE`，Query Skill、`NapmClient`、南向调用均为 0。
3. `maxLimit=20` 通过；0、负数、浮点、字符串垃圾和超限值失败且零南向调用。
4. `PageFamilyDetail` 作为 group 时失败且零南向调用。
5. `pageViews` 不要求 metrics、topMetric、granularity 或 groups。
6. direct Tool execute 和 Hook 路径使用相同校验。

### 12.2 单轮执行

1. 有效 `pageFamilyId + maxLimit=20` 只调用一次南向接口。
2. 上游多种合法返回形状归一化为相同 rows。
3. 0 行生成 `NO_DATA` 权威 finalContent。
4. 上游超时、HTTP 错误和坏 JSON 生成 `EXECUTION_FAILURE`。
5. 缺少 `pageFamilyDetailId` 的行可以展示，但不可继续数据包动作，并返回结构化 warning。

### 12.3 真实多轮生命周期

不得通过测试代码预先构造第三轮完整查询，必须模拟真实插件生命周期：

1. 第一轮业务 TopN 返回多个 `WebApplication`。
2. 第二轮“排名第一的都访问了什么”从第一轮权威引用构造页面族 TopN。
3. 第三轮“详细查看排名第一的前 20 个”从第二轮权威引用取得 `pageFamilyId`，调用一次 `pageViews`，参数包含 `maxLimit=20`。
4. 排名超范围、来源 turn 过期、跨 scope 引用和对象类型错误全部零南向调用。
5. 同一会话重叠 run 不能串用另一轮的 resultRef。
6. `EXECUTING` 重放不产生第二次请求；终态重放只返回原权威结果。
7. 最终内容 exactly-once，后续失败不能覆盖成功或 NO_DATA。

### 12.4 路由测试

| 输入 | 预期 |
| --- | --- |
| 今天哪些业务访问量最高？ | Query / `topValues + WebApplication + PGNPGE` |
| 第一名都访问了什么？ | Query / 页面族 TopN |
| 详细查看第一名的前 20 个 | Query / `pageViews + maxLimit=20` |
| 分析第一名页面为什么有 500 | `napm-fault-diagnosis`，使用可信页面引用 |
| 下载详情第一条的数据包 | `napm-packet-analysis`，使用可信访问实例引用 |

2. 经完整 `pathPlanning` 验证的页面族多级 TopN 保持可执行。

## 14. 遗留风险与开放问题

1. `pageViews.maxLimit` 的正式范围和分页行为尚未由本地证据确认。
