# NAPM 巡检报告概览与附件交付修复方案

## 1. 问题现象

`1.1.0-rc.13` 已能把巡检请求稳定路由到 `napm-inspection-snapshot → napm-report-export`，并正确发送巡检报告 Word 附件。但企业微信同时收到以下技术文本：

```text
报告已生成：NAPM 系统巡检报告
格式：docx
下载链接：/reports/...
文件路径：/home/.../output/....docx
```

报告类型和附件均正确，用户可见文案仍暴露了内部下载 URL 和服务器文件路径，也没有展示报告已有的巡检结论。

## 2. 远端证据

2026-08-20 10:01 和 10:19 两次真实企业微信测试均确认：

1. 审计链为 `napm_automatic_inspection_started → report_generated → napm_automatic_inspection_completed → napm_inspection_report_dispatched`。
2. `sourceTool=napm-inspection-snapshot`、`reportType=inspection_report`、`templateId=napm_traffic_health_inspection_v1` 均正确。
3. Gateway 发送的 final payload 已经包含下载 URL 和服务器文件路径；企业微信通道只根据 `mediaUrls` 上传附件，没有追加这些文本。
4. 同一 payload 的 Word 文件上传和发送成功，因此问题位于插件的用户文案构造层，而不是媒体上传层。

## 3. 根因

通用 `buildReportExportReply()` 把 `downloadUrl` 和 `filePath` 直接拼入回复文本。巡检自动交付在导出完成后调用该通用函数，同时丢弃了 `napm-inspection-snapshot` 已返回的 `summary.status` 和 `summary.highlights`。

内部文件定位信息同时承担了两个不同职责：

- `filePath/mediaUrls` 用于企业微信附件上传；
- 用户文本用于说明巡检结论。

两者没有在交付层分离，导致内部路径进入用户可见文本。

## 4. 修复设计

1. 新增巡检专用 `buildInspectionReportDeliveryReply()`，直接消费结构化巡检 `summary`，不经过模型改写。
2. 总体状态统一映射为中文用户语义：`ok → 正常`、`warning → 需关注`、错误态 → `异常`；`unknown` 不直接展示。
3. 最多展示 5 条 `summary.highlights`；没有 highlights 时使用 `inspection.summary.conclusion`。
4. 通用 `buildReportExportReply()` 不再输出 `downloadUrl` 或 `filePath`，只保留报告标题、格式和附件提示。
5. `mediaUrl/mediaUrls` 继续保留真实文件路径供企业微信上传；审计事件继续记录内部路径，运行行为不变。
6. 本次只修改报告交付文案，不修改普通查询、告警、趋势、数据包、故障诊断和报告模板。

## 5. 用户侧目标格式

```text
系统巡检报告已生成：NAPM 系统巡检报告
总体状态：需关注
重点发现：
- 近一日流量存在明显波动。
- 检测到 5 次慢访问。
- HTTP 400 错误共 714 次。

完整巡检报告已作为附件发送。
```

用户文本不得包含 `/reports/`、`/home/`、`下载链接` 或 `文件路径`，但当前轮仍须只发送一个 Word 附件。

## 6. 回归测试

- 真实 `reply_dispatch → inspection snapshot → report export → sendFinalReply` 接缝必须展示状态和重点发现。
- final 文本不得包含导出 URL 或服务器文件路径。
- `mediaUrl/mediaUrls` 必须继续携带同一个 Word 文件路径。
- 重点发现最多 5 条；未知状态不得显示原始英文枚举。
- 无重点发现时使用结构化巡检结论。
- 综述等其他报告的通用交付文本不得再暴露路径。

## 7. 独立后续问题

当前 `buildAutomaticInspectionToolArgs()` 尚未把“最近7天/30天”转换为巡检查询时间参数。该问题涉及巡检数据口径，不属于本次用户文案修复；需要另行确认巡检模板支持的时间范围后再设计，不能在本次改动中猜测或静默扩展。

## 8. 实施状态

2026-08-20 已完成本地实现：先在真实交付接缝复现 2 个失败断言，再修复为通过。定向报告测试 4/4 套件、45/45 测试通过；全量 Jest 94/94 套件、721/721 测试、官方 lint、8 个生产 Tool 运行时契约、变更文件语法和 ESLint 均通过。尚未升级版本、构建发布包或部署测试服务器。
