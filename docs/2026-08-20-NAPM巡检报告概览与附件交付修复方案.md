# NAPM 巡检报告概览与附件交付修复方案

## 1. 问题现象

`1.1.0-rc.13` 已能把巡检请求稳定路由到 `napm-inspection-snapshot → napm-report-export`，并正确发送巡检报告 Word 附件。但企业微信同时收到以下技术文本：

```text
报告已生成：NAPM 系统巡检报告
格式：docx
下载链接：/reports/...
文件路径：/home/.../output/....docx
```

报告类型和附件均正确，用户可见文案仍暴露了内部下载 URL 和服务器文件路径，也没有展示报告已有的巡检结论。

## 2. 远端证据

2026-08-20 10:01 和 10:19 两次真实企业微信测试均确认：

1. 审计链为 `napm_automatic_inspection_started → report_generated → napm_automatic_inspection_completed → napm_inspection_report_dispatched`。
2. `sourceTool=napm-inspection-snapshot`、`reportType=inspection_report`、`templateId=napm_traffic_health_inspection_v1` 均正确。
3. Gateway 发送的 final payload 已经包含下载 URL 和服务器文件路径；企业微信通道只根据 `mediaUrls` 上传附件，没有追加这些文本。
4. 同一 payload 的 Word 文件上传和发送成功，因此问题位于插件的用户文案构造层，而不是媒体上传层。

## 3. 根因

通用 `buildReportExportReply()` 把 `downloadUrl` 和 `filePath` 直接拼入回复文本。巡检自动交付在导出完成后调用该通用函数，同时丢弃了 `napm-inspection-snapshot` 已返回的 `summary.status` 和 `summary.highlights`。

内部文件定位信息同时承担了两个不同职责：

- `filePath/mediaUrls` 用于企业微信附件上传；
- 用户文本用于说明巡检结论。

两者没有在交付层分离，导致内部路径进入用户可见文本。

## 4. 修复设计

1. 新增巡检专用 `buildInspectionReportDeliveryReply()`，直接消费结构化巡检 `summary`，不经过模型改写。
2. 总体状态统一映射为中文用户语义：`ok → 正常`、`warning → 需关注`、错误态 → `异常`；`unknown` 不直接展示。
3. 最多展示 5 条 `summary.highlights`；没有 highlights 时使用 `inspection.summary.conclusion`。
4. 通用 `buildReportExportReply()` 不再输出 `downloadUrl` 或 `filePath`，只保留报告标题、格式和附件提示。
5. `mediaUrl/mediaUrls` 继续保留真实文件路径供企业微信上传；审计事件继续记录内部路径，运行行为不变。
6. 本次只修改报告交付文案，不修改普通查询、告警、趋势、数据包、故障诊断和报告模板。

## 5. 用户侧目标格式

```text
系统巡检报告已生成：NAPM 系统巡检报告
总体状态：需关注
重点发现：
- 近一日流量存在明显波动。
- 检测到 5 次慢访问。
- HTTP 400 错误共 714 次。

完整巡检报告已作为附件发送。
```

用户文本不得包含 `/reports/`、`/home/`、`下载链接` 或 `文件路径`，但当前轮仍须只发送一个 Word 附件。

## 6. 回归测试

- 真实 `reply_dispatch → inspection snapshot → report export → sendFinalReply` 接缝必须展示状态和重点发现。
- final 文本不得包含导出 URL 或服务器文件路径。
- `mediaUrl/mediaUrls` 必须继续携带同一个 Word 文件路径。
- 重点发现最多 5 条；未知状态不得显示原始英文枚举。
- 无重点发现时使用结构化巡检结论。
- 综述等其他报告的通用交付文本不得再暴露路径。

## 7. 独立后续问题

当前 `buildAutomaticInspectionToolArgs()` 尚未把“最近7天/30天”转换为巡检查询时间参数。该问题涉及巡检数据口径，不属于本次用户文案修复；需要另行确认巡检模板支持的时间范围后再设计，不能在本次改动中猜测或静默扩展。

## 9. rc.14 真实发送链路补充

2026-08-20 16:30 的企业微信验收发现，rc.14 最终显示为：

```text
报告已生成：NAPM 系统巡检报告
格式：docx
完整报告将以附件形式发送。
```

附件、报告类型和内部路径隐藏均正确，但“总体状态”和“重点发现”没有进入用户最终正文，因此 rc.14 的巡检概览验收不通过。

远端日志确认：

1. `napm_automatic_inspection_started → report_generated → napm_automatic_inspection_completed → napm_inspection_report_dispatched` 全部成功。
2. 报告源仍为 `napm-inspection-snapshot`，类型为 `inspection_report`，固定模板为 `napm_traffic_health_inspection_v1`。
3. 保存的巡检数据包含 `overallStatus=warning` 和巡检结论，排除快照缺少总结字段。
4. 企业微信通道收到的 final payload 已是通用三行文案，排除通道侧改写。

真实根因是发送生命周期仍有第二个文案所有者：

```text
reply_dispatch
→ buildInspectionReportDeliveryReply（专用概览正确）
→ sendFinalReply 入队
→ message_sending 读取 fresh report export
→ buildFreshReportExportReply
→ buildReportExportReply（通用三行文案覆盖专用概览）
```

`before_message_write` 也使用同一个通用 fresh-report 分支，存在把会话历史改写为通用文案的相同风险。rc.14 的测试只断言了 `sendFinalReply()` 入队内容，没有把该 payload 继续送入 `message_sending` 和 `before_message_write`，因此形成测试假阳性。

## 10. 补充修复设计

1. `runAutomaticInspectionReportDelivery()` 生成专用正文后，将正文作为当前报告的确定性交付内容保存。
2. 状态键继续使用可信 `conversationKey + turnId`；不允许跨会话或跨轮次附着交付正文。
3. 报告状态新增 `deliveryContent` 和 `reportKind`，与 `result/filePath` 同生命周期、同清理策略。
4. `buildFreshReportExportReply()` 优先返回 `deliveryContent`，只有没有专用正文时才回退 `buildReportExportReply()`。
5. `message_sending` 与 `before_message_write` 继续复用同一个 fresh-report 入口，由状态记录保证两处得到相同正文。
6. `buildRecentReportExportReply()` 保持通用附件重放文案，不在后续“报告呢”追问中重复整段巡检概览。
7. `mediaUrl/mediaUrls`、报告生成、附件幂等和综述/普通导出文案均不改变。

回归测试必须覆盖完整生命周期：

```text
reply_dispatch
→ inspection snapshot
→ report export
→ sendFinalReply
→ message_sending
→ before_message_write
```

最终用户正文和会话历史必须逐字等于巡检专用概览，且巡检采集、报告导出和 Word 附件交付各执行一次。
