# NAPM 查询整体架构设计

日期：2026-06-24

## 设计原则

**一个入口，内部路由。LLM 只做语义理解 + 叙述，不做结构化构造。**

## 关键规则

### 规则引擎的能力边界

| 能处理 | 不能处理 |
|--------|---------|
| 单层对象 TopN 排行 | 多层 group 路径 (WebApplication→ClientIPs→IPAddress) |
| 单指标均值/趋势查询 | 综合分析 (overview, discover-then-analyze) |
| 对象/指标清单 | 多指标组合查询 |
| 时间范围解析 (最近1h/24h/7d) | 对比查询 (同比/环比) |
| topCount 推断 (谁→1, Top10→10) | 上下文继承 (继续/接着查) |

### 规则引擎失败时的返回

```json
{
  "ok": false,
  "needsConstruction": true,
  "reason": "multi_step_analysis|drilldown_path|context_inherit|ambiguous_metric",
  "hint": "需要解析多层下钻路径",
  "userPrompt": "业务组A下哪个应用连接失败最多"
}
```

LLM 收到后知道：不是系统错误，是需要我介入。然后构造 resolvedQuery 再调一次。

## 和之前方案的本质区别

| | 之前的尝试 | 本方案 |
|------|-----------|--------|
| LLM 角色 | 构造者（主要工作） | 路由判断者 + 兜底构造者 + 叙述者 |
| 规则引擎角色 | LLM失败后修补 | LLM之前先跑，做主路径 |
| 入口 | 多个拦截点 | 一个入口 |
| LLM prompt | 建议它"可以传raw prompt" | 指令它"第一步就调工具传prompt" |
| 复杂查询 | 相同流程 | LLM收到needsConstruction信号后介入 |

## openai.yaml 设计

```
你是 NAPM 查询助手。对任何用户查询，严格按以下流程:

第一步: 调 napm-skill-query
  参数: { "prompt": "<用户原话原文>" }
  不要修改用户措辞。不要先获取时间。不要构造 resolvedQuery。
  
第二步: 根据返回结果处理
  - 返回了数据结果 → 直接生成中文叙述。不做额外查询。
  - 返回了 needsConstruction=true → 你才需要构造完整的 resolvedQuery
    再调一次 napm-skill-query，这次带上 resolvedQuery。
    
叙述要求:
  - 必须包含数据时间范围
  - 不暴露英文推理过程
  - 不输出 JSON 原文
```

## 预期耗时

```
简单查询 (丢包最严重的IP):
  LLM调工具 → 规则引擎(9ms) → NAPM API(0.7s) → LLM叙述(2s) = ~3s
  
复杂查询 (综合分析):
  LLM调工具 → 规则引擎失败 → LLM收到needsConstruction → 构造resolvedQuery → 
  再调工具 → 执行 → 叙述 = ~15s (和现在一样，但没有简单查询拖后腿)

加权: 60%×3s + 40%×15s ≈ 7.8s (vs 当前 25s 平均)
```
