# 2026-05-19 业务清单入口路由修复说明

## 1. 问题现象

用户提问：

- `系统中都有哪些业务？`

OpenClaw 的思考过程能明显看出它已经理解“要查业务对象清单”，但没有第一时间进入固定的业务清单查询链路，而是先反复试探：

- 多次尝试 `groupArguments`
- 被 skill 校验层拦截为 `Invalid service type: groupArguments`
- 随后又去试 `topValues(IPAddress)` 等旁路
- 最后才晚一步触达 `businessGroups` / `applications`

这会造成两个问题：

- 用户看到的 reasoning preview 呈现出“明明是个简单问题，却一直在试错”
- 虽然最终可能答出来，但收敛速度和稳定性都不够

## 2. 根因判断

这次问题不属于“路径预判器没有生效”。

路径预判器解决的是：

- 在已经确定对象链路后，如何更快选到正确的下钻路径

而这次问题发生在更前一层：

- 业务清单问法没有在第一跳就被稳定收口到 `metadata_list -> WebApplication`

现状拆开看：

- 插件侧已经具备业务清单识别与结构化注入能力
  - `napm-openclaw-plugin.remote.js`
  - `isBusinessObjectInventoryPrompt()`
  - `buildBusinessObjectInventoryResolvedQuery()`
- 但 skill 侧的 prompt-only fallback 之前没有覆盖这类问法
  - `skills/openclaw-napm-query/scripts/run_napm_query.js`
  - `buildPromptFallbackResolvedQuery()`
  - 之前只兜底：
    - 指标清单
    - 未知端口流量
    - overview
  - 未兜底：
    - 业务清单

这意味着：

- 只要主链这次没有显式带上业务清单的 `resolvedQuery`
- skill 就不会立刻收口到固定查询
- 而会退化成“模型先自行探路”

## 3. 本次修复

本次只补“业务清单入口兜底”，不修改企业微信插件，不关闭 reasoning preview。

### 3.1 skill 侧新增业务清单 prompt fallback

修改文件：

- `skills/openclaw-napm-query/scripts/run_napm_query.js`

新增能力：

- `isPromptFallbackBusinessObjectInventoryPrompt(prompt)`
- `buildPromptFallbackBusinessObjectInventoryResolvedQuery(prompt)`

规则说明：

- 命中类似：
  - `系统中有哪些业务？`
  - `系统中都有哪些业务？`
  - `当前系统有哪些业务系统？`
  - `列出系统里的业务`
- 直接构造：
  - `service=groups`
  - `queryModeKey=metadata`
  - `semanticConstraints.operation=metadata_list`
  - `semanticConstraints.targetObjectType=WebApplication`
  - `groups=[{ type: 'WebApplication' }]`

排除项：

- 明确说的是：
  - `业务组`
  - `工作组`
  - `BusinessGroup`
- 则不走这个 fallback，避免把“业务组清单”误改写成“业务系统清单”

### 3.2 接入总 fallback 链路

`buildPromptFallbackResolvedQuery(prompt)` 的顺序调整为：

1. 指标清单 fallback
2. 业务清单 fallback
3. 未知端口流量 fallback
4. overview fallback

这样做的目的，是在 prompt-only 场景下优先收口“清单型问法”。

## 4. 为什么这次修复有效

修复后，即使主链没有先稳定生成结构化 `resolvedQuery`，skill 也能在入口阶段直接把：

- `系统中都有哪些业务？`

规范成：

- `groups + metadata_list + WebApplication`

这样至少能避免继续退化成：

- 反复试 `groupArguments`
- 再试旁路元数据
- 最后才碰对

也就是说，这次修复补的是：

- “主链没带结构化参数时，skill 自己仍然能第一时间查对”

而不是：

- 只在主链已经判断正确时才工作

## 5. 本地验证

已通过：

本次补充的关键回归点：

- `系统中都有哪些业务？` 应直接生成 `WebApplication metadata_list`
- `系统中都有哪些业务组？` 不应误命中该 fallback
- 插件侧对“系统中都有哪些业务？”保持业务清单识别能力

## 6. 影响范围

本次改动仅收敛在：

- `skills/openclaw-napm-query/scripts/run_napm_query.js`
- 测试文件
- 修复说明文档

未修改：

- 企业微信插件
- reasoning preview 开关
- 业务路径预判器逻辑

## 7. 预期测试结果

远端同步后，再问：

- `系统中都有哪些业务？`

预期表现：

- 不再出现多轮 `groupArguments` 试探
- 会更早进入 `WebApplication` 的 metadata 查询链路
- 思考过程仍然可见，但中间探路应显著减少

如果后续仍能看到明显的自由探索，则说明还需要继续往更前一层做“主链强制路由”，但这次至少已经把 skill fallback 这一层补齐了。
