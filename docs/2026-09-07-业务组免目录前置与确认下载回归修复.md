# 业务组免目录前置与确认下载回归修复

## 1. 现场复现

2026-09-07 出现以下会话：

```text
/new
看一下最近一分钟服务器网段的数据包情况！
  -> 当前问题必须通过 napm-packet-analysis 执行后才能回答

看一下最近五分钟服务器网段的数据包情况！
  -> 当前问题必须通过 napm-packet-analysis 执行后才能回答

现在系统有哪些工作组？
  -> 返回工作组清单

看一下最近一分钟服务器网段的数据包情况！
  -> 预览成功

进行下载分析！
  -> 当前问题必须经 NAPM skill 执行后才能回答
```

用户预期是：工作组清单不是前置步骤；首次指定一个已存在的工作组名称就应直接预览，预览要求确认时，下一轮确认应下载并完成协议分析。

## 2. 本地最小复现证据

对请求“看一下最近一分钟服务器网段的数据包情况！”调用 packet runtime：

| 模型传参形状 | 原修复前结果 |
| --- | --- |
| `criteria={}` | `PACKET_QUERY_REQUIRED` |
| `criteria.ipRanges=["服务器网段"]` | `PACKET_TARGET_INVALID` |

原实现只有在提示词出现“业务组/工作组/业务分组”时，才会把非 IP 值提升为 `BusinessGroup`。用户直接说“服务器网段”时，runtime 既没有目标字段，也不会查询 `businessGroups`，因此没有进入预览流程。

远端本次 SSH 访问返回 `Permission denied (publickey,password)`，未能读取 2026-09-07 的远端审计日志。因此不能仅凭这段聊天记录断言活动服务器运行的是哪个提交；是否仍存在旧确认路由，必须在部署验收时核对活动版本和审计事件。

## 3. 领域边界

单 IP 与业务组是两个独立目标：

- 单 IP：直接使用 `criteria.ips`，不需要属于某个业务组，也不需要先查询业务组清单。
- 业务组：名称解析为 `businessGroups.Name`，读取 `IpMembers`，将单 IP 放入 `ips`，将 IP 范围放入 `ipRanges`，再调用 `packetsPreview/packetsDown`。

两者只在目标解析阶段不同，从预览、确认、下载到 tshark 分析共用同一 packet 工作流。不得用业务组成员替换用户明确给出的单 IP。

## 4. 修复内容

### 4.1 未标注类型的工作组名称自动解析

packet runtime 新增了对带时间和数据包词的未标注名称的保守提取：

```text
看一下最近一分钟服务器网段的数据包情况！
  -> 提取“服务器网段”
  -> BusinessGroup
  -> businessGroups → IpMembers
  -> packetsPreview
```

支持“最近一分钟/最近五分钟/最近 N 小时”等常见相对时间表达，以及“分析/查看/看一下/查询”等请求动词。业务组目录仍是最终事实源；名称不存在时返回 `BUSINESS_GROUP_NOT_FOUND`，不会调用 packet endpoint。

为了避免把明显的错误 IP 当作工作组，类似 `999.999.999.999` 的数字点号目标仍返回 `PACKET_TARGET_INVALID`。

### 4.2 业务组确认下载固定使用预览成员

首次预览成功后，确认轮必须满足：

- 最近结果来自 `napm-packet-analysis`；
- `preview.ok=true`、`preview.empty=false`；
- `decision.next_action=CONFIRM_DOWNLOAD`；
- 预览结果包含有效目标和 Unix 秒级 `start/end`。

确认轮恢复预览已经展开的 `ips/ipRanges` 和固定时间，不接受模型重新填入的 IP、工作组或 `last5minutes`。业务组成员恢复时使用插件内部可信标记，runtime 会保留已解析成员，不重新清空或改写成员条件。

确认轮 route 为 `OTHER_SKILL`，由插件注入可信 `previewRiskAccepted=true`；没有有效待确认预览时，用户单独说“下载并分析”仍然不能直接下载。

### 4.3 路由和输出要求

- 业务组首次请求必须调用 `napm-packet-analysis`，不能先强制调用工作组清单查询。
- 确认下载不能落入普通 `NAPM_QUERY`，也不能被 `napm-skill-query` 守卫拦截。
- 同一 `scope + turnId` 的重复调用只允许一次实际下载和 tshark 执行。
- 下载完成答复读取实际 `analysis`，输出包数、协议分布、端点、会话、DNS、HTTP、TLS 等结构化摘要。
- 不输出 tshark 原始 `====` 分隔线、`Filter:` 或英文表头；`malformed` 只提示协议解析异常，不等同丢包。

## 5. 支持和拒绝的用户表达

确认意图不是固定几个短句白名单，而是“同会话待确认上下文 + 动作语义”联合判断。有效预览存在时，以下表达属于同一类确认：

```text
进行下载分析！
确认下载并分析；
确认下载，进行分析！
请把刚才预览的数据包下载下来并做协议解析
上一轮预览没有问题，直接执行下载分析
好的，继续
```

以下表达不能继承上一轮：

```text
不要下载，先只看预览
下载了吗？
帮我分析一下为什么下载失败
重新分析另一个 IP 的数据包
换成新的时间范围继续下载
```

## 6. 回归验证

本次新增和调整的验证包括：

- 未先查询工作组清单时，`criteria={}` 能从用户请求推断 `服务器网段` 并规划 `businessGroups` 解析；
- 模型把未标注名称误放进 `ipRanges` 时能自动修复；
- 明显错误 IPv4 不会被误判为工作组；
- 未标注业务组预览后，确认轮保持 `BusinessGroup`、已展开成员和原始 `start/end`，route 为 `OTHER_SKILL`；
- 单 IP 的确认下载、风险门控、幂等执行和 tshark 结果清洗不回归。

当前开发分支验证结果：

- `napm-packet-workgroup-time` 与 `napm-openclaw-plugin-packet-final`：41 个测试通过；
- packet 相关测试：12 个套件、109 个测试通过；
- 全量 Jest：108 个套件、1026 个测试通过；
- 插件/测试 ESLint、两个 packet runtime Node 语法检查、`git diff --check` 通过。
