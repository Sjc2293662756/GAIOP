## 2. 一句话结论

本次并没有修改 `wecom-openclaw-plugin` 的业务逻辑，而是：

- 在 `napm-openclaw-plugin` 中增加了一个临时开关 `NAPM_ALLOW_REASONING_PREVIEW`
- 打开了远端 `OpenClaw` 的 `channels.wecom.thinking / stream / streaming`
- 将新的 NAPM 插件文件同步到真实运行目录
- 通过 `systemd user service` 重启 `openclaw-gateway.service`

这样做之后，企业微信中的 NAPM 问题会重新显示中间思考流，而不再被插件层取消或替换成最终答案。

## 3. 背景与问题现象

前面项目为了防止 reasoning 泄露，已经做过两层保护：

1. 企业微信通道配置层关闭 thinking / streaming
2. `napm-openclaw-plugin` 对 NAPM 场景的 reasoning preview 做取消和改写

因此，即便上游模型会产生中间思考文本，用户在企业微信里通常也只能看到：

- 一个安全的“处理中”占位
- 或者直接看到最终答案

而看不到中间推理过程。

这次需求不是“恢复安全占位”，而是明确要把思考过程临时放出来，所以必须同时处理：

- OpenClaw 通道配置
- NAPM 插件层的 preview guard

仅改其中一层都不够。

---

## 4. 根因拆解

### 4.1 远端真实配置层

在远端 `~/.openclaw/openclaw.json` 中，企业微信原本处于如下状态：

```json
{
  "sendThinkingMessage": true,
  "thinking": false,
  "stream": false,
  "streaming": false
}
```

这意味着：

- 可以发一个“处理中”提示
- 但不会把真实的 thinking / stream 内容往外发

### 4.2 NAPM 插件层

`napm-openclaw-plugin` 中原本存在专门的 reasoning 泄露保护：

- `looksLikeInternalReasoningPreview(...)`
- `shouldCancelNapmPreviewMessage(...)`
- `message_sending` hook 中的 `cancel`
- `message_sending` hook 中的“刷新成最终答案”
- `before_message_write` hook 中的“把 reasoning 替换成 remembered 最终答复”

也就是说，即便把 `thinking=true` 打开，如果 NAPM 插件仍按原逻辑工作，思考流依然会被：

- 直接取消
- 或被中途替换成最终答案

所以这次不能只改配置，必须同步调整插件层保护逻辑。

## 5. 本次本地代码改动

## 5.1 改动文件

本次本地实际改动的关键文件有：

- `napm-openclaw-plugin.remote.js`
- `.codex-temp/napm-openclaw-plugin.remote.js`
- `.codex-temp/openclaw.remote.json`
- `test/napm-openclaw-plugin-streaming-guard.test.js`

### 5.2 插件层新增临时开关

在 `napm-openclaw-plugin.remote.js` 中新增：

```js
function shouldAllowNapmReasoningPreview() {
  const raw = String(process.env.NAPM_ALLOW_REASONING_PREVIEW || '').trim().toLowerCase();
  return ['1', 'true', 'yes', 'on'].includes(raw);
}
```

设计目标：

- 默认仍然沿用原有安全逻辑
- 只有显式配置 `NAPM_ALLOW_REASONING_PREVIEW=true` 时才放开 reasoning preview

这保证了它是“临时开关”，不是永久删除保护逻辑。

### 5.3 放开 preview cancel

原先 `shouldCancelNapmPreviewMessage(...)` 会在 NAPM 场景下直接取消 preview 消息。

本次改为：

- 如果 `NAPM_ALLOW_REASONING_PREVIEW=true`，则直接返回 `false`
- 不再取消中间 preview 消息

### 5.4 放开 reasoning fallback 改写

原先在两个位置会把 reasoning 文本改写成 remembered skill reply：

1. `message_sending`
2. `before_message_write`

本次改为：

- 只有在未打开 `NAPM_ALLOW_REASONING_PREVIEW` 时，才继续做这类 fallback 改写
- 一旦开关打开，就允许 reasoning 文本继续向下游发送

### 5.5 放开“中途刷新成最终答案”的保护

仅取消 `cancel` 还不够，因为 `message_sending` 后续还存在：

- `buildAsyncRefreshedReplyText(...)`
- `buildGenericNapmSkillRefreshText(...)`

这些逻辑会在 preview 期间提前把消息替换成最终答案。

因此本次又补了一层：

- 当 `NAPM_ALLOW_REASONING_PREVIEW=true`
- 且当前消息本身就是 streaming preview

则在 `message_sending` 中直接 `return undefined`，让 preview 原样继续向下游发送。

## 11. 风险说明

本次改动虽然满足了“临时打开思考过程”，但必须明确当前风险：

### 11.1 reasoning 泄露会重新出现

之前专门拦截过的中文/英文中间推理文本，现在会重新暴露给用户。

### 11.2 最终答复体验可能变差

用户可能会先看到一大段中间推理，再看到最终答案，观感上不如“处理中占位 + 最终一次性输出”稳定。

### 11.3 群聊环境下更容易显得冗长

如果后续群聊也走同一链路，则中间思考流可能明显拉长消息长度。

### 11.4 这不是长期推荐方案

从项目长期方向看，更合理的是：

- 保留可见的“处理中状态”
- 保留必要的进度反馈
- 但不要直接把原始 reasoning 文本暴露给用户

本次只是为了满足“现在先全部打开”的临时目标。

## 14. 总结

这次改动的本质，不是简单把某个配置从 `false` 改成 `true`，而是同时打通了两层：

1. OpenClaw 通道配置层允许 thinking / stream

只有两层同时放开，企业微信侧才会真正看到中间思考过程。

同时，本次改动仍然保留了“显式开关”的设计，没有直接删掉原有防泄露逻辑，因此后续如果需要收回，也可以比较平滑地回退到之前的安全模式。
