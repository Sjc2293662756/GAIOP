日期：2026-08-05  
范围：OpenClaw NAPM Skill 的意图识别、工具路由、查询规划、执行完成判定、结果汇总与用户可见输出。  
结论状态：仅检查与诊断；未修改代码、未修改服务器配置、未发起在线 NAPM 数据查询。

## 结论摘要

**已证实**：当前实现存在“至少一个相关查询成功，就把综合状态查询视为成功”的缺陷。`overview` 执行完成后以 `successCount > 0` 判定成功，并显式允许部分结果渲染；它没有检查宽泛问题所需的事实是否齐全，也没有把结论逐项关联到证据。因此，一条告警、丢包或 TopN 查询成功时，系统可能输出“整体概览”或被上游归纳为“整体正常”，即使流量、时延、TCP、接口、应用影响等未查询或已失败。

这支持背景案例的核心判断：问题不主要是模型不知道网络状态应该看哪些方向，而是“回答所需证据”没有被表达为可执行、可验证的查询计划。

**前端现场证据已取得，但服务端链路仍待补齐**：用户提供的 2026-08-05 前端会话转录，已包含“当前网络情况”“现在网络怎么样”“当前网络正常吗”三个独立会话的时间、流式中间文本和最终回复。它直接证明这三种宽泛问法会被模型路由到 `overview/network`，且模型会在部分概览结果后自行声称“已有足够数据”。但转录不含 tool-call ID、`resolvedQuery` 原文、每个 service 的原始输入输出和网关事件，故不能仅凭它精确核定实际调用次数、参数和失败原因；这部分仍需服务器日志关联。

## 三个层次的诊断

### 1. 意图识别：用户想知道什么

当前能力：

- OpenClaw 负责自然语言理解、对象范围和时间范围的上游构造；`resolvedQuery.service` 可选择 `topValues`、`averageValues`、`timeValues`、`overview` 等，见 [napm-openclaw-plugin.remote.js](../napm-openclaw-plugin.remote.js:2454)。
- overview 可从 payload、intent、resolvedQuery、提示词和 group 类型推断场景，见 [overview-module.js](../skills/openclaw-napm-query/scripts/overview-module.js:378)。
- overview 可根据“快速/详细/全面”等词推断查询深度；没有显式深度时默认 `standard`，见 [OverviewBudget.js](../skills/openclaw-napm-query/scripts/OverviewBudget.js:72)。

缺口：

- **已证实**：模型工具输入的核心结构只有一个 `resolvedQuery.service`，其 schema 未定义 `requiredFacts`、多步骤 `queryPlan`、事实到结论的证据绑定，或完成阈值，见 [napm-openclaw-plugin.remote.js](../napm-openclaw-plugin.remote.js:2464)。因此“识别到网络综合状态”不能结构化传达为“必须检查告警、流量、丢包、时延、TCP、接口、应用影响等事实集合”。
- **已证实**：严格 standalone 模式不以原句生成计划，而是完全依赖 OpenClaw 上游；上游若把宽泛问题构造成单个 `topValues`，Skill 无法凭原问题纠正它，见 [run_napm_query.js](../skills/openclaw-napm-query/scripts/run_napm_query.js:1591)。
- **待验证**：实际生产系统提示词如何要求模型把“当前网络情况”识别为 `overview`，尚未导出完整系统提示词和模型调用记录。纯部署 helper 测试中，`buildOverviewResolvedQuery("当前的网络情况！")`、`"现在网络怎么样"`、`"网络正常吗"` 都返回 `null`；这证明没有硬编码的 Skill 层兜底转换，但不能单独说明上游模型的最终行为。

### 2. 查询规划：回答需要哪些事实

当前能力：

- **已证实**：overview 已经有多候选模块、场景、深度、对象槽位、元数据健康度和预算选择机制，而不是简单的“关键词 -> 单一 service”。候选评分考虑场景、问题类型、指标、指标域、对象类型、焦点对象、元数据和查询成本，见 [OverviewPlanner.js](../skills/openclaw-napm-query/scripts/OverviewPlanner.js:233)。
- **已证实**：网络场景有预定义候选集合。快速档为告警、入向丢包、出向丢包；标准档再增加流量趋势、Top IP 吞吐、连接失败和焦点 IP 快照/趋势；深度档再增加应用、会话、网段、业务节点等，见 [OverviewCandidateRegistry.js](../skills/openclaw-napm-query/scripts/OverviewCandidateRegistry.js:1164)。
- **已证实**：候选会受查询数、子查询数、超时、重试预算限制；超出预算会记录为 `budget_limited`，见 [OverviewPlanner.js](../skills/openclaw-napm-query/scripts/OverviewPlanner.js:440)；预算值见 [OverviewBudget.js](../skills/openclaw-napm-query/scripts/OverviewBudget.js:11)。

缺口：

- **已证实**：当前是“静态 scene/depth 候选模板 + 排序/预算裁剪”，不是“从用户目标动态列出必须获得的事实，再将事实映射到 service”。网络标准档最多 5 个根查询，深度档最多 8 个；超出的维度会被裁剪，见 [OverviewBudget.js](../skills/openclaw-napm-query/scripts/OverviewBudget.js:19)。
- **已证实**：候选的选择语义是“可选、得分、预算”，未表达“必需/可选”“缺失是否阻断结论”“适用时间口径”“该模块不能证明什么”。`buildOverviewPlan` 仅输出 selected/skipped candidates，见 [OverviewPlanner.js](../skills/openclaw-napm-query/scripts/OverviewPlanner.js:555)。
- **已证实**：宽泛查询即便进入 overview，也不是对全部网络健康维度的保证。快速档只会选三类，标准档受 5 条根查询限制，且快速/标准默认不涵盖时延、接口状态等至少部分用户期望维度。这会使 `overview` 名称比实际覆盖范围更宽泛。
- **推测**：如果上游没有构造 `service=overview`，它可能采用“问题类型/关键词 -> 单个 service”的简单路由。当前 schema 允许单个 service，且 Skill 严格信任上游；但需要实际上游 prompt 和 trace 才能确认其具体路由规则。

### 3. 完成校验：现有数据是否足以支持结论

当前能力：

- **已证实**：执行器记录成功数、失败数、跳过候选、告警、超时、剩余子查询预算，见 [OverviewExecution.js](../skills/openclaw-napm-query/scripts/OverviewExecution.js:242)。
- **已证实**：结果归约器将这些执行元数据保留到 overview 输出中，见 [OverviewResultReducer.js](../skills/openclaw-napm-query/scripts/OverviewResultReducer.js:156)。
- **已证实**：时间戳会要求根级 `start/end`，并要求分钟对齐，见 [napm-openclaw-plugin.remote.js](../napm-openclaw-plugin.remote.js:2485)。

缺口和直接原因：

- **严重，已证实**：`overview-module.js` 只要 `successCount > 0` 即 `ok=true`，见 [overview-module.js](../skills/openclaw-napm-query/scripts/overview-module.js:729)。它不检查已选候选是否全部成功、不检查被预算跳过的维度、不检查用户目标覆盖率。
- **严重，已证实**：模块和 reducer 都显式设置 `allowPartialResult: true`，见 [overview-module.js](../skills/openclaw-napm-query/scripts/overview-module.js:749) 与 [OverviewResultReducer.js](../skills/openclaw-napm-query/scripts/OverviewResultReducer.js:165)。部分结果允许展示本身合理，但缺少“降级叙述/禁止整体结论”的配套控制。
- **严重，已证实**：没有找到“结论中的每个重要判断必须有对应 service 结果”“未覆盖维度不得声称整体正常”“执行失败必须继续补查或返回部分结论”的证据模型或校验器。现有汇总可产生 `summary`，但不含请求事实、事实状态、证据来源与结论置信度的显式结构，见 [OverviewResultReducer.js](../skills/openclaw-napm-query/scripts/OverviewResultReducer.js:143)。
- **已证实**：已有测试明确将 partial render policy 视为预期，见 [overview-module.test.js](../test/overview-module.test.js:327) 和 [overview-module.test.js](../test/overview-module.test.js:393)。这解释了为什么现有 231 个测试都通过仍未防住该问题。

## 背景案例提前结束的直接原因

下面的因果链由代码直接支持：

```text
宽泛网络问题被上游构造成 overview 或某个单查询 service
  -> 若为 overview，则静态候选受 depth/budget/metadata 限制而只执行部分维度
  -> 任一子查询成功
  -> successCount > 0，overview.ok = true
  -> allowPartialResult = true
  -> 生成 summary/displayText 并交给上游叙述
  -> 缺少证据覆盖检查，最终回复可能被表述为“整体情况”
```

若请求未被构造成 `overview` 而是一个单独 service，问题更早发生：模型工具 schema 天然只承载一个 `service`，而严格 Skill 不会以原问题补建多维计划。该分支是**架构上已具备的风险**，具体是否发生在本次线上案例仍为**待验证**。

对 2026-08-05 三次实际会话，服务器审计还发现模型反复生成非声明 service 或无效 `queryModeKey`，插件拒绝执行，而前端仍继续显示结果。这是需要单独处理的失败边界和消息泄露问题；它不证明、也不替代“综合问题在部分证据下提前完成”的主因。

## 按严重程度排序的发现

### P0：部分成功被当成整体成功

**证据**：`successCount > 0` 即成功、允许部分渲染，见 [overview-module.js](../skills/openclaw-napm-query/scripts/overview-module.js:729)。  
**影响**：单一成功维度可支撑“概览成功”状态，后续模型很容易将局部事实扩大为整体健康结论。  
**建议方向**：将“技术执行有结果”与“综合问题已满足”拆分为不同状态。

### P0：缺少事实覆盖和主张证据校验

**证据**：工具输入与 overview 输出都没有 `requiredFacts`、coverage 或 claim-evidence 字段，见 [napm-openclaw-plugin.remote.js](../napm-openclaw-plugin.remote.js:2464)、[OverviewResultReducer.js](../skills/openclaw-napm-query/scripts/OverviewResultReducer.js:143)。  
**影响**：没有程序化边界阻止“整体正常/整体异常”的过度结论。  
**建议方向**：对综合问题定义最低证据标准和结论许可条件。

### P1：overview 的名称和描述超过其实际保证

**证据**：文档将 `overview` 用于 broad/composite analysis，见 [SKILL.md](../skills/openclaw-napm-query/SKILL.md:192)；网络快速档只有三类候选，见 [OverviewCandidateRegistry.js](../skills/openclaw-napm-query/scripts/OverviewCandidateRegistry.js:1164)。  
**影响**：模型或用户可将“overview”误解为“已覆盖全部网络状态”。  
**建议方向**：将输出改为“已查询维度概览”，并在 metadata 声明覆盖范围、排除范围和质量等级。

### P1：上游单 service 接口不能表达多步骤计划

**证据**：`resolvedQuery` 只要求一个 `service`，见 [napm-openclaw-plugin.remote.js](../napm-openclaw-plugin.remote.js:2464)。  
**影响**：即使模型知道多个方向，也没有稳定、可审计的计划承载结构；多工具是否执行受模型临场行为影响。  
**建议方向**：增加结构化 `queryPlan`，由执行器而非自由文本决定查询轮次。

### P1：预算、超时与元数据可悄然减少覆盖

**证据**：标准档最多 5 个根查询、15 秒、0 次重试；执行器在超时和失败后跳过后续工作，见 [OverviewBudget.js](../skills/openclaw-napm-query/scripts/OverviewBudget.js:19)、[OverviewExecution.js](../skills/openclaw-napm-query/scripts/OverviewExecution.js:82)。  
**影响**：系统会偏向少量快速结果，却无强制的结论降级。  
**建议方向**：预算应首先保障必需事实，不能完成时返回 `partial/insufficient`，而非 `ok`。

### P2：时间口径对“当前”不透明

**证据**：overview 未收到有效 `start/end` 时回退到当前时间前的默认窗口，见 [overview-module.js](../skills/openclaw-napm-query/scripts/overview-module.js:360)。上游解析器的部分路径以 `last1hour` 为默认，见 [RequirementParserService.js](../skills/openclaw-napm-query/services/RequirementParserService.js:2761)。  
**影响**：用户的“当前/最近/今天”可能被隐式解释为不同窗口；即使最终带有 timeRange，仍可能不是用户理解的“当前”。  
**建议方向**：将时间解释作为计划的显式字段，在回答开头展示，并将“当前”与“最近一小时/最近 N 分钟”分开定义。

### P2：部署版本和工具面不一致

**证据**：生产扩展加载远端 fallback 文件，且 manifest 有 9 个工具；本地 Skill 文档称历史插件可选，见 [SKILL.md](../skills/openclaw-napm-query/SKILL.md:14)。  
**影响**：单独修改仓库内某一条链路，可能无法改变实际模型工具选择。  
**建议方向**：建立发布清单、版本标识和启动时工具/提示词快照。

### P1：推理、工具选择和参数修正已泄露到用户界面

**证据**：2026-08-05 用户提供的三段前端转录均直接展示 service 修正、参数构造、读取 Skill/spec 的计划和英文中间推理。插件具备 stream/delta/preview 事件过滤逻辑，见 [napm-openclaw-plugin.remote.js](../napm-openclaw-plugin.remote.js:207)；同时优先转发 `displayText`，见 [napm-openclaw-plugin.remote.js](../napm-openclaw-plugin.remote.js:2393)。overview 强制转发 display text，见 [run_napm_query.js](../skills/openclaw-napm-query/scripts/run_napm_query.js:2042)。生产环境启用了 WeCom 流式与 thinking 消息，已检查的 `NAPM_ALLOW_REASONING_PREVIEW` 为 false。  
**结论**：泄露现象已证实；NAPM 显式 reasoning-preview 开关不是已知直接原因。具体是上游流式、事件过滤还是 `displayText` 转发的哪一段造成，仍需服务端事件日志定位。  
**建议方向**：只允许结构化 final/narration 消息出站，记录每条消息的 channel、event phase 和来源，禁止把工具参数、配置读取和 reasoning delta 送入用户通道。

### P3：配置中发现明文敏感信息

**证据**：服务器配置检查中发现了明文凭据（本文不记录其内容）。  
**影响**：不影响本缺陷根因，但属于独立安全风险。  
**建议方向**：立即轮换、收紧文件权限、迁移到受控密钥注入，并从历史日志中清除敏感回显。

## 当前缺失或不完整的能力

1. 领域“最低证据标准”：每个综合问题需要哪些事实、哪些为必需、哪些可选、缺失时可得出什么级别的结论。
2. 由模型输出、程序接管的多步骤 `queryPlan`：计划步骤、依赖、服务、参数、预期事实、失败策略。
3. 完成校验：计划步骤状态、事实覆盖率、关键缺失项、结论许可等级。
4. 结论与证据映射：任何“整体正常/异常”“主要风险”等主张必须指向一个或多个工具结果。
5. 预算降级策略：必要步骤未执行、超时、服务失败或指标不可用时，不能保留“整体完成”语义。
6. 宽泛问题的统一时间解释，及用户可见的具体时间范围。
7. 可审计的生产 trace：原始问题、上游 intent、resolvedQuery/plan、每一步 service 输入输出摘要、最终回复和流式事件。

## 建议的目标机制（本轮不实施）

```text
用户问题
  -> 识别目标、对象范围、时间范围、结论粒度
  -> 根据领域最低证据标准生成 requiredFacts
  -> 模型生成结构化 queryPlan（事实 -> service/参数/依赖）
  -> 执行器按计划查询，记录每项事实状态与证据
  -> 覆盖校验：必需事实、时间一致性、失败/不可用情况、预算裁剪
  -> 仅对已满足证据门槛的主张授权
  -> 继续补查，或以“部分结果/无法判断整体”汇总
```

建议最小数据结构（概念示例，不是本轮代码设计）：

```json
{
  "intent": { "domain": "network", "goal": "current_health", "scope": "global" },
  "timeRange": { "semantic": "current", "start": 0, "end": 0, "displayText": "最近15分钟" },
  "requiredFacts": [
    { "id": "alerts", "required": true, "canSupport": ["active_incident"] },
    { "id": "loss", "required": true, "canSupport": ["network_quality"] },
    { "id": "latency", "required": true, "canSupport": ["network_quality"] },
    { "id": "traffic_baseline", "required": true, "canSupport": ["capacity_or_anomaly"] },
    { "id": "tcp_failures", "required": false, "canSupport": ["connection_health"] }
  ],
  "queryPlan": [
    { "factId": "alerts", "service": "alertsSummary", "required": true },
    { "factId": "loss", "service": "topValues", "required": true }
  ],
  "evidenceStatus": { "complete": false, "missingRequiredFacts": ["latency"] },
  "claimPolicy": { "overallHealthyAllowed": false }
}
```

“最低证据标准”应按领域和结论粒度配置，而非为每句自然语言编写规则。例如，“是否存在活跃网络告警”只需告警事实；“当前网络整体是否正常”需跨质量、可用性、负载/异常等多个事实，并允许按数据源能力调整，但必须显式说明缺失项。

## 后续应该怎么做

建议按以下顺序推进：

1. **补齐一次成功执行的完整 trace，再改代码。** 现有前端会话已证明模型选择了 `overview/network` 并声称数据足够，但服务器审计目前只记录了部分被拒绝的调用。需在模型/gateway 层补出同一会话的成功 tool-call 序列、`resolvedQuery`、overview 内部 selected/skipped candidates、每项结果与最终文案，才能量化“实际只调用一个 service”还是“overview 内部多查询但证据仍不全”。
2. **定义跨领域最低证据标准。** 先覆盖 network、application、security；为“整体健康”“当前状态”“异常排行”“单指标查询”定义 required/optional facts 与结论许可等级。服务器、数据库在确认有对应服务后再纳入。
3. **设计并引入结构化查询计划。** 上游模型只能负责生成候选计划；程序需要验证服务、参数、时间、依赖、预算和 required facts，不能将自由文本作为完成信号。
4. **替换 `successCount > 0` 的完成语义。** 保留 `executionSucceeded`（至少一条查询成功）与 `answerComplete`（必需事实满足）的区分。后者为 false 时，应继续补查或明确标注“仅得到部分结果，无法判断整体”。
5. **收紧叙述契约。** 聚合器输出 coverage、missingFacts、unsupportedClaims 和 allowedConclusionLevel；最终回复只能使用允许的结论。将 `overview` 展示为“已查询维度概览”，除非满足整体健康证据阈值。
6. **处理时间与预算。** 为“当前/最近/今天”定义产品级窗口与时区规则；预算先分配给必需事实，预算不够时宁可降级，不可静默裁剪关键维度。对慢服务可做并发、缓存或异步补查，但必须保留缺失状态。
7. **对齐部署。** 将服务器上实际加载的 extension、manifest、Skill 和本仓库建立版本校验；确认 9 个工具各自的提示、范围与实际入口，避免只改本地单入口链路。
8. **增加回归测试并以 trace 回放验收。** 在单元测试外，增加“上游计划 -> Skill 执行 -> narration contract”的集成测试；生产发布后核验真实 trace。
9. **并行处理独立安全问题。** 轮换服务器配置中的明文凭据，修订权限和密钥加载方式；不要把凭据、请求 URL 或工具参数放入用户可见流。

## 建议新增的回归测试

| 场景 | 断言 |
| --- | --- |
| `当前网络情况` | 生成 network/current_health 计划；required facts 至少跨多个维度；任一关键维度未执行时 `answerComplete=false`，不能出现“网络整体正常”。 |
| `现在网络怎么样` | 与上例等价；应展示明确时间窗口，不能静默默认 24 小时或 1 小时。 |
| `网络正常吗` | 若告警、丢包、时延/可用性或负载事实不全，结果必须是“无法完整判断”或受限结论，而非肯定正常。 |
| 指定窄查询 | 如“10.0.0.1 最近 1 小时入向丢包”：只规划该指标，单 service 成功可 `answerComplete=true`，并验证对象、指标、时间精确回显。 |
| 部分工具失败 | 一条成功、两条 required 失败：保留成功事实和错误明细，但 `overallHealthyAllowed=false`；测试补查策略或明确部分结果文案。 |
| 指标不可用 | metadata 指出时延/TCP 不可查询：计划标记 unavailable，最终输出缺失维度和影响；不得将不可用当成正常。 |
| 预算不足 | 关键事实被 `budget_limited` 或 `timeout_budget_exceeded`：结果为 insufficient，而不是 overview 成功。 |
| 结论证据 | 每句“正常/异常/主要风险/无告警”都能引用 `factId` 和 service result；没有证据的主张被 narration validator 拒绝。 |
| 流式与泄露 | reasoning/preview/tool parameter/config-read 事件不得进入 final 用户消息；只允许 final narration contract。 |
| 应用与安全综合状态 | 使用同一覆盖校验框架，防止共享 `allowPartialResult` 再次产生“整体”过度结论。 |

## 建议验收标准

修复完成的最低验收不是“模型多调了几个工具”，而是以下条件同时成立：

1. 宽泛综合问题会产生可审计的 required facts 和多步骤计划。
2. 单个相关查询成功不会让综合问题自动完成。
3. 所有必需事实已获得可用数据，才可使用“整体正常/整体异常”等整体结论。
4. 不可查、失败、超时、预算裁剪和时间不确定性必须显式影响结论等级。
5. 窄查询不会因为引入综合框架而被不必要地扩展或变慢。
6. 用户可见回复只包含最终事实与受控叙述，不包含推理、工具参数或配置过程。
