## 一、项目概述

NAPM（Network Application Performance Monitoring）语义网关是一个**企业级智能运维助手**，基于 OpenClaw 平台运行，通过**企业微信**作为交互入口，将用户的自然语言运维问题翻译为结构化的 NAPM 查询，调用 NetInside NAPM WebService 获取实时数据，最终以中文自然语言回答或 Word/PDF 报告的形式返回给用户。

### 1.1 核心价值

- **自然语言 → 结构化查询**：用户用中文描述需求（如"最近一天哪个业务报错最多"），系统自动转换为精确的 NAPM API 调用
- **多技能协作**：9 个专业 Skill 覆盖查询、报告、数据包、告警、巡检、综述、故障诊断等全场景
- **智能路由**：插件层规则引擎预解析用户意图，将请求路由到正确的 Skill，避免 LLM 做所有决策
- **报告自动化**：支持巡检报告、故障诊断报告、综述报告（日报/周报/月报）一键生成 Word 文档

### 1.2 技术栈

| 层级 | 技术 |
|------|------|
| 运行平台 | OpenClaw Gateway（Node.js，端口 18789） |
| AI 模型 | DeepSeek Chat（LLM 推理） |
| 插件框架 | OpenClaw Plugin（napm-openclaw-plugin.remote.js，242KB） |
| 后端 API | NetInside NAPM WebService（REST/HTTP） |
| 报告生成 | docx 库（Word）、ECharts（图表）、sharp（图片处理） |
| 数据包分析 | tshark / capinfos |
| 日志采集 | rsyslog → Syslog Watcher → 企业微信推送 |
| 部署方式 | pscp（PuTTY SCP）逐文件推送到远端 Linux 服务器 |
| 测试框架 | Jest（57 个测试文件） |

### 4.1 openclaw-napm-query（核心查询引擎）

**入口**: `skills/openclaw-napm-query/scripts/run_napm_query.js`

最核心的 Skill，负责将结构化 `resolvedQuery` 翻译为 NAPM API 调用并返回结果。

**支持能力**:
- 指标查询：吞吐、流量、丢包、重传、响应时间、连接数、HTTP 错误等
- TopN 排行、均值、时间序列趋势、综合分析
- 对象清单：系统中有哪些业务/业务组/应用/已定义应用/自动识别应用
- 指标清单：某对象支持哪些指标
- 下钻目录：某对象支持哪些下钻路径
- 复合分析链：先发现目标对象 → 锁定 → 聚焦综合分析

**关键对象语义契约**:
| 中文 | 对象类型 | 说明 |
|------|---------|------|
| 业务 / 业务系统 / Web应用 | `WebApplication` | Type=3 |
| 业务组 / 工作组 | `BusinessGroup` | - |
| 已定义应用 | `DefinedApp` | Type=2 |
| 自动识别应用 | `CompositeApplication` | Type=4 |

**关键指标语义防歧义**:
| 中文 | 正确指标 | ❌ 错误映射 |
|------|---------|-----------|
| 报错（Web应用） | PGHTTP400 + PGHTTP500 | PLI/PLO |
| 丢包 | PLI / PLO | - |
| 连接失败 | RFCI / RFCO | - |
| 服务器响应时间 | TRTI | RTTI |
| 数据包数量 | PKIO | TPIO |
| 吞吐/带宽 | TPIO / BYTIO | - |

**服务层（18+ 个 Service 文件）**:
- `RequirementParserService.js` — 核心查询执行引擎
- `WorkflowClassifierService.js` — 意图分类
- `ResolutionSpecService.js` — 查询契约验证
- `PromptRoutingService.js` — Prompt 路由
- `MetricSemanticNormalizerService.js` — 中文语义归一化
- `NapmMetadataService.js` — 元数据查询
- `GroupPathPlannerService.js` — 下钻路径规划
- `ExecutionKernelPolicy.js` — 执行内核路由
- `OpenClawNarrationContractService.js` — 中文叙述契约

### 4.3 openclaw-napm-packet-analysis（数据包分析）

**入口**: `skills/openclaw-napm-packet-analysis/scripts/run_packet_analysis.js`

处理数据包预览、下载、分析的全链路。

**支持模式**:
- `build_url_only` — 仅构造下载链接
- `preview_only` — 预览可用数据包
- `preview_download` — 预览后下载
- `preview_download_analyze` — 预览 → 下载 → tshark 分析
- `analyze_file` — 分析本地 pcap 文件

**业务数据包分析**: 支持通过业务名称自动解析 `businessName → pageFamilyId → pageFamilyDetailId → instanceId`，使用 DownServlet 下载业务页面数据包。

**安全策略**:
- 下载前必须预览（`packetsPreview`），空预览不下载
- 风险等级：`low` / `medium` / `high` / `unknown`
- 存储治理：磁盘使用率 ≥80% 清理旧文件，≥90% 阻止下载
- 默认保留 24 小时

### 4.4 openclaw-napm-alert-query（告警查询）

**入口**: `skills/openclaw-napm-alert-query/scripts/run_alert_query.js`

独立于 query Skill 的告警专用查询，拥有自己的事件模型。

**支持模式**:
- `summary` — 告警摘要（alertsSummary）
- `timeline` — 告警时间线（alertsSummaryTimeLine）
- `detail` — 告警详情（alertsDetail）
- `detail_with_timeseries` — 告警详情 + 触发指标时间序列
- `explain_notification` — 通知字段解释
- `explain_event_fields` — 事件字段解释

**间接数据包发现（核心特性）**:
当告警的 `categoryType` 为业务/应用/业务组类型时，告警的 `group` 是对象名而非 IP。系统自动：
1. 根据 categoryType 选择下钻路径（8 种映射）
2. 用告警触发指标查询嫌疑 IP 会话 Top5
3. 返回每个嫌疑 IP 的数据包下载候选

**告警 → 数据包跨 Skill 编排**:
```
Step 1: alert-query（先执行） → 获取告警详情 + packetHandoff
Step 2: packet-analysis（后执行） → 使用 packetHandoff.candidates 下载分析
```

### 4.7 openclaw-napm-fault-diagnosis（故障诊断）

**入口**: `skills/openclaw-napm-fault-diagnosis/scripts/run_fault_diagnosis.js`

**🚨 路由优先 Skill**：当用户要求"分析XXweb的故障情况，给出故障报告"时，必须路由到此 Skill，不应拆成多次单指标查询。

**3 种故障分析流程**:

| 流程 | flowType | 步骤 | 适用场景 |
|------|---------|:--:|---------|
| B/S 业务慢 | `bs_app_slow` | 3 步 | Web 页面 4xx/5xx |
| C/S 应用慢 | `cs_app_slow` | 2 步 | 客户端软件/数据库慢 |
| 网络慢 | `network_slow` | 4 步（交互式） | 全网慢/带宽占满 |

**B/S 标准化 3 步流程**（最常用）:
```
Step 1 — 业务基本情况（averageValues，8 项指标）
Step 2 — 页面错误分析 Top 20（topValues 三层钻取）
Step 3 — 页面状态码详情（pageViews，逐页面查询）
```

**报告结构**: 封面 → 目录 → §1 基本信息 → §2 分析过程（含表格+判断提示）→ §3 证据项 → §4 根因判断 → §5 处置建议 → §6 验证方式

**内置报告生成**，一次调用直接返回 .docx 文件路径，不需额外调 report Skill。

## 六、核心插件详解

### 6.1 napm-openclaw-plugin.remote.js

这是整个系统的**主运行时**（242KB，6000+ 行），运行在 OpenClaw 插件沙箱中。

**核心职责**:
1. **NAPM 边界检测** — 判断用户消息是否属于 NAPM 领域（30+ 个正则模式）
2. **意图分类** — 识别 overview / alert / fault-diagnosis / summary / packet / query 等意图类型
3. **规则引擎快速通道** — 在 LLM 调用前用规则引擎预解析查询（节省 7-16 秒）
4. **resolvedQuery 自动修复** — 检测并修复常见错误（如 TPIO→BYTIO 修正）
5. **时间契约执行** — 验证时间范围合法性，检测年份偏移
6. **边界守卫** — 阻止绕过 Skill 的裸 API 调用、过程叙述泄露
7. **审计日志** — 记录每次 Skill 调用（`audit.log`），自动脱敏
8. **结果缓存** — 90 秒内相同 prompt 返回缓存结果
9. **媒体去重** — 2 分钟内阻止重复发送同一文件
10. **报告导出仲裁** — 确保报告请求走正确的 report-export 通道

## 九、关键设计决策

### 9.1 混合查询架构

针对"LLM 推理是唯一瓶颈"（DeepSeek Chat 占 96% 耗时，16.8s）的问题，设计了混合架构：

- **规则引擎快速通道**：LLM 提取语义标签（中文描述，~2s）→ 规则引擎进行标签→resolvedQuery 精确映射（9ms）
- **复杂查询回退**：`needsConstruction` 标记时，LLM 完整构造 resolvedQuery

### 9.2 resolvedQuery 严格收口

所有 NAPM 查询必须通过 `resolvedQuery` 结构化对象，包含：
- `service`：服务名（topValues / averageValues / timeValues / overview / groups / metrics / drilldownCatalog）
- `start` / `end`：Unix 秒级时间戳（分钟对齐）
- `groups`：对象类型和参数
- `metrics` / `metric`：指标代码
- `queryModeKey`：查询模式

插件层执行契约校验，不合法则触发自动修复或返回错误。

### 9.3 对象本体收敛

- "业务" → `WebApplication`（不与 BusinessGroup 混淆）
- "已定义应用" → `DefinedApp`（不与 WebApplication 合并）
- Application 清单 = `applications` API + Type 过滤（不用 groups-tree）

### 9.4 时间处理策略

- 时区：`Asia/Shanghai`（UTC+8）
- 时间戳格式：Unix 秒（非毫秒）
- 分钟边界对齐（60 秒整除）
- 年份自动修正（2025 → 2026）
- 相对时间（"最近5分钟"）实时计算，不使用缓存时间戳

### 9.5 Skill 编排 vs 插件编排

2026-06 完成了从"插件编排"到"Skill 编排"的演进：
- query / packet / report / alert / inspection / summary / fault-diagnosis 各自独立为 Skill
- 插件层仅负责边界检测、路由、缓存、审计
- Skill 内部自治查询、执行、输出

## 十三、关键约束与设计原则

1. **Skill 归位原则**: 每个 Skill 拥有明确定义的边界，跨边界调用通过 OpenClaw 编排
2. **不绕过 Skill**: 禁止 LLM 直接调用 NAPM API，必须通过 Skill 执行器
3. **数据时间透明**: 每个回答必须包含数据时间范围
4. **空结果诚实**: 不编造结果，说明查询了什么、时间范围、为什么为空
5. **认证脱敏**: 所有面向用户的输出中 Password 必须显示为 `***`
6. **报告只消费数据**: report Skill 不自行查询 NAPM，只消费已有结构化数据
7. **PDF 不静默降级**: PDF 不可用时返回明确错误，不偷偷生成 Word
