# 应用清单仅返回“对象列表”全链路故障修复方案

日期：2026-08-07

## 1. 问题现象

生产环境连续出现以下对话：

```text
用户：现在系统有哪些应用？
助手：对象列表

用户：现在系统有哪些应用？
助手：对象列表

用户：为什么没有返回？
助手：当前问题属于 NAPM 下钻/层级目录查询……
```

该问题不是南向接口无数据，而是对象语义、结果渲染、历史结果复用和输出门禁之间的契约不一致。

## 2. 远端证据

2026-08-07 14:38 首次查询的真实执行记录如下：

- 调用了 `napm-skill-query`。
- 上游传入 `service=groups`、`groups=[{type:"Application"}]`。
- 执行层查询南向 `applications` 接口。
- `Application` 在执行层映射为 `DefinedApp`，按 `applications Type=2` 过滤。
- 返回 `ok=true`、`rowCount=6`。
- 返回对象为：回溯238、Esxi-local、HIS系统1、可观测239、Zabbix、应用故障测试1。
- 结果中的 `displayText` 和 `replyText` 均为空，`summary.title` 只有“对象列表”。
- 模型最终只输出了“对象列表”，输出门禁未检查 6 条对象是否真正展示。

2026-08-07 14:39 第二次相同查询没有调用 skill，而是复用上一轮同提示词记录，继续输出残缺标题。

2026-08-07 14:40 追问“为什么没有返回？”时，模型原始答案已经正确列出 6 个应用；但答案末尾包含“下钻分析”，`before_message_write` 把助手答案当作用户问题重新路由，最终覆盖为层级目录兜底。

## 3. 领域口径确认

本项目的规范语言由本次业务确认更新为：

| 用户表达 | 规范对象类型 | 实例来源 |
| --- | --- | --- |
| 应用、系统有哪些应用 | `DefinedApp` | `applications Type=2` |
| 业务、系统有哪些业务、业务系统、Web 应用 | `WebApplication` | `applications Type=3` |
| 内置应用 | `BuiltinApplication` | `applications Type=1` |
| 自动识别应用、复合应用、复合协议 | `CompositeApplication` | `applications Type=4` |
| 未知应用、其他应用 | `OtherApp` | `groupArguments` |

因此 `Application -> DefinedApp` 的业务映射是正确的。错误在于项目中仍有规则把普通“应用”当成歧义问法，且执行结果没有稳定转成用户可见清单。

本口径取代以下旧结论：

```text
Plain “系统中有哪些应用” 是歧义问法，必须先澄清。
```

旧文档保留为历史记录，但后续代码、测试和提示规则必须以本文为准。

## 4. 根因

### 4.1 同一领域词在不同入口含义不一致

- `ObjectMetadataRegistry` 已将 `Application` 映射到 `DefinedApp`。
- `ObjectOntologyService`、`ApplicationCatalogSemanticRules` 和 resolver 却把普通“应用”标记为歧义。
- 插件生产入口没有调用歧义 resolver，最终偶然执行了正确的 Type=2 查询，但没有形成统一、可验证的构造契约。

### 4.2 `group_list` 缺少通用展示文本

- `WebApplication` 清单已有专用 `displayText`。
- `DefinedApp` 等其他对象清单只有 `summary.title="对象列表"`。
- 插件兜底函数在没有 `displayText` 时只读取标题，不读取 `narrationStructure.items` 或 `rows`。

### 4.3 门禁只验证“有 skill 结果”，不验证“结果已展示”

`rowCount>0` 时，最终答案仍可只有标题。当前没有对象清单完整性约束。

### 4.4 历史记录被当成本轮证据

相同提示词可以命中上一轮记录，从而跳过当前轮 skill 调用。残缺文案会被持续复用。

### 4.5 助手输出反向污染用户意图

`message_sending` 和 `before_message_write` 把助手输出作为 `selectActivePromptText()` 的候选。助手答案中出现“下钻”后，会改变本轮路由并覆盖正确结果。

### 4.6 结果交付追问没有专用语义

“为什么没有返回”“怎么只有标题”“再发一次”等问法没有绑定最近一次成功结果，无法稳定重放完整清单。

## 5. 修复方案

### 5.1 统一普通应用语义

- 普通“应用”直接解析为 `DefinedApp`。
- “业务/业务系统/Web 应用”保持解析为 `WebApplication`。
- resolver 为“系统有哪些应用”生成 `service=groups`、`groups=[{type:"DefinedApp"}]`。
- 插件边界把遗留上游类型 `Application` 显式规范化为 `DefinedApp`，并保留审计信息。
- 对象清单校验必须使用 workflow 的目标对象类型，禁止任意组类型漂移。

### 5.2 为所有对象清单生成确定性 `displayText`

`group_list` 必须根据对象类型、metadata 和 rows 生成完整文本。`DefinedApp` 示例：

```text
系统中目前有 6 个已定义应用（DefinedApp，applications Type=2）：

1. 回溯238
2. Esxi-local
3. HIS系统1
4. 可观测239
5. Zabbix
6. 应用故障测试1
```

空列表必须明确写“当前没有返回已定义应用”，不能只写“对象列表”。

### 5.3 插件稳定渲染结构化结果

插件用户文案选择顺序调整为：

```text
displayText
-> summary.displayText
-> narrationStructure.displayText
-> narrationStructure.items/rows 的确定性渲染
-> summary.title（仅限无结构化结果）
```

对于成功且 `rowCount>0` 的 `group_list`，最终答案必须包含总数和至少一个返回对象；否则由插件使用 skill 结果重建完整清单。

### 5.4 对象清单要求当前轮执行记录

- 所有 `object_inventory` 纳入强制 skill 记录范围。
- 历史记录可用于结果交付追问，不得作为新的普通查询轮次的执行证据。
- 南向 metadata 缓存仍可复用，但对话层必须生成当前轮结果记录。

### 5.5 用户问题与助手输出彻底分离

- 路由只使用 `message_received` 保存的 `canonicalPrompt`。
- `before_tool_call` 可在没有会话状态时使用工具参数中的 prompt。
- `message_sending` 和 `before_message_write` 不得使用助手输出推断用户意图。
- 助手输出仅用于检查泄漏、旁路、残缺结果等内容问题。

### 5.6 增加结果交付追问

识别以下问法：

```text
为什么没有返回
为什么没显示
怎么只有标题
结果呢
重新发一下
再发一遍
```

命中后读取最近一次成功 skill 结果并重新渲染，不重新查询，不进入 `drilldownCatalog`。

## 6. 回归测试

至少覆盖：

1. “系统有哪些应用”解析为 `DefinedApp`。
2. “系统有哪些业务”解析为 `WebApplication`。
3. `Application` 在插件边界规范化为 `DefinedApp`。
4. `groups + DefinedApp + 非空 rows` 生成包含总数和对象名的 `displayText`。
5. 非空对象清单不能退化为“对象列表”。
6. 第二次相同普通查询没有当前轮记录时必须要求执行 skill。
7. “为什么没有返回”重放最近成功清单。
8. 助手正确答案中包含“下钻”时不能改变用户问题路由。
9. `BuiltinApplication`、`CompositeApplication`、`OtherApp` 原有口径不回归。
