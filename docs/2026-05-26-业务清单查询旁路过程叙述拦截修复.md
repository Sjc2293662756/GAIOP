# 业务清单查询旁路过程叙述拦截修复

## 背景

用户询问“系统中有哪些业务？”时，标准链路应为：

```text
OpenClaw 语义判断
  -> 构造 resolvedQuery
  -> napm-skill-query
  -> MetadataExecutionKernel
  -> NapmMetadataService.listObjectInstances("WebApplication")
  -> applications Type=3
  -> narration contract 输出
```

本轮线上回答虽然最终列出了业务对象，但追问“怎么查询的 / python过滤输出是什么”时，模型描述成了：

```text
直接调用 applications 原始 API
通过 exec 执行 python
本地 python 过滤 type=3
没有经过 napm-skill-query 中间管道
```

这类描述违反当前职责边界：模型不能把临时脚本、curl、python、exec 或直接南向 API 探查包装成生产查询流程。

## 问题判断

数据口径本身是正确的：

- `WebApplication` / “业务系统” 的对象清单来自 `applications Type=3`。
- `DefinedApp` / “已定义应用” 来自 `applications Type=2`。
- `CompositeApplication` / “自动识别应用” 来自 `applications Type=4`。

错误在输出过程叙述：

- 标准链路允许 `MetadataExecutionKernel` 内部通过 `NapmMetadataService` 调用南向 `applications`。
- 不允许 assistant 对用户说“我直接调 API / 我用 python 过滤 / 没走 napm-skill-query”。
- 如果用户追问查询过程，必须基于已记录的 skill result / resolvedQuery / metadata 审计字段回答。

## 修复内容

### 1. 扩展 NAPM 元追问识别

文件：

```text
napm-openclaw-plugin.remote.js
```

`isNapmMetaFollowUpPrompt()` 增加以下意图识别：

- `谁在做`
- `工具`
- `python过滤`
- `过滤输出`
- `exec`
- `有没有走 skill`
- `napm-skill-query`
- `中间管道`
- `中间层`

这样在上一轮是 NAPM 查询上下文时，“python过滤输出是什么？谁在做？”会被识别为 NAPM 查询过程追问，而不是普通越界闲聊。

### 2. 扩展旁路过程叙述拦截

`looksLikeNapmBypassProcessText()` 增加识别：

- 小写 `python` 过滤/筛选/处理/解析/输出
- `exec 工具`
- `直接查`
- `直接去后端`
- `直接从API`
- `后端探查`
- `本地 python`
- `没走/没有走 napm-skill-query`
- `未经过/没有经过 napm-skill-query`
- `没有经过中间层/中间管道`

命中后，`message_sending` / `before_message_write` 不再放行该过程描述，而是改写为已记录的 skill 查询链路。

### 3. 增加回归测试

文件：

```text
test/napm-openclaw-plugin-meta-followup-guard.test.js
```

新增用例覆盖：

```text
python过滤输出是什么？谁在做？
```

期望行为：

- 在 NAPM 上下文中被识别为 meta follow-up。
- 如果 assistant 尝试输出 `exec/python/没有经过 napm-skill-query`，插件必须改写。
- 改写后的回答包含 `napm-skill-query`、`providerType=applications`、`applicationTypeFilter=[3]`。
- 不允许原文中的 `exec 工具`、`python 命令`、`没有经过 napm-skill-query` 透出。

## 修复后的正确解释

对于“系统中有哪些业务？”，正确查询过程应表述为：

```text
1. OpenClaw 将问题识别为 object_inventory。
2. 对象本体将“业务”绑定为 WebApplication。
3. 构造 resolvedQuery：service=groups，queryModeKey=metadata，groups=[{type:"WebApplication"}]。
4. napm-skill-query 执行该 resolvedQuery。
5. MetadataExecutionKernel 按对象本体调用 NapmMetadataService。
6. NapmMetadataService 使用 applications provider，并按 applicationTypeFilter=[3] 获取业务系统。
7. narration contract 基于 skill 结构化结果组织最终回答。
```

注意：

- 不是模型自己执行 python。
- 不是 assistant 直接 curl 南向 API。
- 不是按中文名称过滤。
- 不是按近期流量活跃度过滤。
- `applications Type=3` 是 WebApplication 对象实例的元数据口径。
