# NAPM API 时间参数构成与错误定位

## 结论

真实流程中的错误时间不是服务器时区造成的。远端运行版本与当前工作区的插件、查询时间解析器和时间范围服务校验一致，服务器时区为 `Asia/Shanghai`。

根因是执行时间的构造分散在多个模块：查询、告警、综述和故障诊断使用不同的默认值、支持范围和覆盖时机。部分生产路径依赖 `before_tool_call` Hook 才能补齐根级 `start/end`；一旦 Hook 未执行或其参数改写未传递，严格校验会先于 Skill 内的对齐逻辑失败。

## API 执行时间契约

NetInside API 的执行时间统一应为：

- 字段：根级 `start`、`end`
- 单位：Unix 秒
- 对齐：向下对齐到 60 秒边界
- 语义：`timeRange.key` 仅表达用户选择的窗口，不能作为 API 执行字段
- 时区：日历窗口（`today`、`yesterday`）按 `Asia/Shanghai` 解释

正确的目标链路应是：

```text
用户时间表达
  -> timeRange.key / 绝对时间
  -> resolveExecutionTime()
  -> root start/end（秒、分钟对齐）
  -> 工具契约校验
  -> Skill 组装 NetInside API 参数
```

审查时的异常链路为：

```text
用户时间表达
  -> 上游 timeRange.key
  -> before_tool_call Hook（部分路径才执行）
  -> 工具 execute 严格校验
  -> Skill
  -> NetInside API
```

## 已确认问题

### P0：任意相对时间窗被错误回退为最近 1 小时

文件：`skills/openclaw-napm-query/src/shared/timeResolver.js`

`applyTimeOverride()` 使用的 `DURATION_MAP` 仅覆盖：

```text
last5minutes, last1hour, last24hours, last1day, last7days, last30days
```

未知 key 使用 `3600` 秒回退。因此：

```text
last2hours  -> 最近 1 小时（错误）
last8hours  -> 最近 1 小时（错误）
last14days  -> 最近 1 小时（错误）
```

同仓库的 `ResolvedQueryTimeRangeService.resolveTimeRange()` 已能正确解析 `lastNhours`、`lastNdays`，但 Hook 没有复用它，导致同一个 key 在不同阶段得到不同窗口。

影响：`topValues`、`averageValues`、`timeValues`、`overview`、`topValues_multi_protocol` 的真实 API 请求可能与用户要求的时间范围不一致。

### P0：查询工具直调时缺少根级执行时间

文件：`napm-openclaw-plugin.remote.js`

`createSkillToolDefinition().execute()` 直接调用 `validateResolvedQueryAgainstSpec()`，要求查询对象已有根级 `start/end`。时间覆盖只在 `before_tool_call` Hook 中执行，`execute()` 自身没有调用时间解析器。

可复现输入：

```json
{
  "resolvedQuery": {
    "service": "topValues",
    "queryModeKey": "topn",
    "groups": [{ "type": "IPAddress" }],
    "metrics": ["TPIO"],
    "topMetric": "TPIO",
    "topCount": 10,
    "timeRange": { "key": "last2hours" }
  }
}
```

直调结果：`UPSTREAM_RESOLVED_QUERY_INVALID`，原因 `incomplete_resolved_query`，缺少 `start/end`。

远端审计日志还记录过多次 `invalid_time_boundary_alignment`，说明至少有部分实际调用未获得 Hook 写入的分钟对齐时间。

### P1：工具提示、schema 和严格校验相互矛盾

`napm-skill-query` 的系统提示要求调用方只传 `timeRange.key`，不要自行传时间戳；但配置 `config/napm-resolution-spec.v1.json` 又要求可执行查询必须携带根级 `start/end`。

这使调用正确性依赖隐式 Hook。重试、工具直调、Hook 注册失败、参数复制或运行时改造都可能让查询在校验阶段失败。

### P1：综述和故障诊断使用另一套时间语义

相关文件：

- `skills/openclaw-napm-summary/services/SummaryService.js`
- `skills/openclaw-napm-fault-diagnosis/services/FaultDiagnosisService.js`
- `napm-openclaw-plugin.remote.js`

两项 Skill 的内部 `_resolveTimeRange()` 只读取 `start/end` 或 `faultWindow`，没有读取 `timeRange.key`；缺省时直接回退最近 24 小时。插件 Hook 又使用独立且有限的 key 映射，未知 key 也回退最近 24 小时。

此外，这两个工具的 schema 不允许 `timeRange.key`，但全局时间提示要求调用方使用它。这会造成相同的“最近 2 小时”在 query、summary、fault-diagnosis 间产生不同结果。

### P2：告警的“今天/昨天”未被相对时间解析器识别

文件：`skills/openclaw-napm-alert-query/scripts/run_alert_query.js`

告警脚本能解析“最近两小时”等表达，但 `resolveRelativeTimeRangeFromPrompt()` 不处理“今天”或“昨天”。当调用未提供 `criteria.start/end` 时，插件默认补最近 1 小时，因此“今天有哪些告警”存在查询最近 1 小时的风险。

### P2：测试不能保护当前真实入口

- 专项时间测试只覆盖固定枚举 key，未覆盖任意 `lastN*`。
- `test/napm-openclaw-plugin-time-contract.test.js` 使用 `.codex-temp/` 中的旧插件副本，不是当前插件入口。
- 全量 Jest 在审查时为 48 个套件通过、12 个失败；多项失败表明测试期待的工具契约已经落后于当前实现。
- `SummaryClient.js` 有重复的 `formatTimestamp` 函数声明。Node CommonJS 当前可以加载，但 Jest 转换器拒绝解析，导致综述时间相关测试无法执行。

## 审查时模块分布

| 场景 | 当前时间构造者 | 默认值 / 风险 |
|---|---|---|
| 普通查询 | `before_tool_call` -> `timeResolver.applyTimeOverride()` | 未知相对 key 错回退 1 小时；直调无时间 |
| 查询 Skill | `run_napm_query.normalizeResolvedQueryTimeRange()` | 仅对已有时间向下对齐，不能补缺失时间 |
| 告警 | 插件默认 + `run_alert_query` 提示词重算 | “今天/昨天”可能落成最近 1 小时 |
| 综述 | 插件 Hook + `SummaryService._resolveTimeRange()` | 内部不识别 key，默认最近 24 小时 |
| 故障诊断 | 插件 Hook + `FaultDiagnosisService._resolveTimeRange()` | 内部不识别 key，默认最近 24 小时 |
| 巡检 | 各巡检服务自行以 `Date.now()` 计算 | 固定窗口，未统一复用时间服务 |
| 数据包 | 调用方提供 `criteria.start/end` | 无统一窗口补齐，依赖上游/告警交接 |

## 修复前方案

1. 新建唯一的 `resolveExecutionTime()`，作为所有工具的唯一时间真源。
2. 支持 `lastNminutes`、`lastNhours`、`lastNdays`、`today`、`yesterday` 和显式 `start/end`。
3. 该函数使用显式 `Asia/Shanghai` 日历边界，返回根级秒级、分钟向下对齐的 `start/end`。
4. 在每个工具的 `execute()` 开头调用该函数，再做契约校验。`before_tool_call` 只调用同一函数作提前归一，不能成为唯一补齐点。
5. 统一 query、alert、summary、fault-diagnosis 的 schema：要么均接受 `timeRange.key`，要么均只接受根级时间；推荐接受 key 并在执行入口解析。
6. 保留原始用户时间表达和解析后的窗口到审计字段，便于按请求追溯。

## 已实施修复

1. `ResolvedQueryTimeRangeService` 明确使用 `Asia/Shanghai` 计算日历窗口；`today` 截止当前服务器分钟，`yesterday` 截止前一日 23:59，并支持 `lastNseconds`。
2. 新增统一入口 `resolveExecutionTime()`，支持任意正数的 `lastNseconds`、`lastNminutes`、`lastNhours`、`lastNdays`、`today`、`yesterday` 及显式秒/毫秒级 `start/end`。所有 API 执行时间均输出为分钟对齐的 Unix 秒。
3. `napm-skill-query` 在 `execute()` 校验前调用统一入口。Hook 仍可提前归一，但直调不再依赖 Hook；携带 `timeRange.key` 的请求会重算并覆盖陈旧根级时间戳。
4. `napm-alert-query`、`napm-summary`、`napm-fault-diagnosis` 的执行入口均接入统一入口；三个工具的 schema 均接受 `timeRange.key`。告警支持“今天”“昨天”和中文数字的相对时间表达。
5. 工具提示与查询契约改为声明动态 `lastN*` 窗口，避免把未枚举窗口误导为固定 1 小时。注释版插件同步了“今天截至当前分钟”的规则。
6. 删除 `SummaryClient.js` 重复的 `formatTimestamp` 声明，使 Jest 可以加载综述时间相关模块。

未修改巡检和数据包分析的既有业务窗口：它们不消费本次四个工具的 `timeRange.key` 契约，仍维持原有固定窗口或上游交接的显式时间。

## 验收矩阵

| 用例 | 期望 API 窗口 |
|---|---|
| 最近 5 分钟 | `end - 300` 至 `end` |
| 最近 2 小时 | `end - 7200` 至 `end` |
| 最近 8 小时 | `end - 28800` 至 `end` |
| 最近 14 天 | `end - 1209600` 至 `end` |
| 今天 | 上海时区当日 00:00 至当前分钟 |
| 昨天 | 上海时区前一日 00:00 至 23:59 |
| 只传 `timeRange.key` 的 query 直调 | 自动补齐后通过校验 |
| Hook 路径与直调路径 | 产生完全相同的 `start/end` |
| 告警“今天/昨天” | 不得回退最近 1 小时 |
| summary / fault-diagnosis 任意相对窗口 | 与 query 产生相同时间范围 |
