## 二、组件详解

### 2.1 FaultDiagnosisFlowRouter — 流程路由

**场景识别**：基于关键词匹配，将用户自然语言描述映射到 3 个流程之一。

```javascript
classify("全网都慢，昨天下午")       → "network_slow"
classify("web-app登录页面打开很慢")  → "bs_app_slow"
classify("客户端软件访问数据库慢")   → "cs_app_slow"
classify("")                        → "network_slow"  // 默认
```

识别规则：
- 含 `web/页面/url/http/登录慢/接口慢/400/500` → `bs_app_slow`
- 含 `客户端软件/数据库访问/非web/固定端口/能连上但/操作慢` → `cs_app_slow`
- 含 `全网/网络慢/带宽/拥塞/全局/整体` 或为空 → `network_slow`

**流程跳转**：将用户决策文本映射到目标流程+步骤。

```javascript
resolveJump("network_slow", "step1", "转应用分析")  → { flowType: "bs_app_slow", stepId: "step1_business_overview" }
resolveJump("network_slow", "step1", "继续下一步")  → { flowType: "network_slow", stepId: "step2_top_objects" }
resolveJump("network_slow", "step4", "继续下一步")  → null  // 最后一步，无下一步
```

### 2.2 FaultDiagnosisSteps — 步骤实现

每个步骤提供两个方法：

| 方法 | 输入 | 输出 | 职责 |
|------|------|------|------|
| `buildQueries(flowType, stepId, context)` | 流程类型 + 步骤ID + 时间上下文 | `{ label, description, queries[] }` | 构建 NAPM 查询计划 |
| `analyzeStepData(flowType, stepId, rawData)` | 流程类型 + 步骤ID + 原始数据 | `{ flag1: true, flag2: false }` | 生成数据标记，供提示匹配 |

**示例 — 网络慢 Step 1**：

```javascript
// buildQueries
_networkStep1(ctx) {
  return {
    queries: [
      { label: 'faultTrend',
        fn: () => this.client.getTimeValues(faultStart, faultEnd,
                'TPIO,TPI,TPO', [{type:'TotalTraffic'}], granularity) },
      { label: 'baselineTrend',  // 基线窗存在时
        fn: () => this.client.getTimeValues(baselineStart, baselineEnd,
                'TPIO,TPI,TPO', [{type:'TotalTraffic'}], granularity) }
    ]
  };
}
```

**示例 — B/S 应用慢 Step 2**：

```javascript
// buildQueries — 3 个并发查询
_bsStep2(ctx) {
  return {
    queries: [
      { label: 'slowUrls',    // WebApplication → PageFamily(慢URL排行)
        fn: () => this.client.getTopValues(..., 'PGSLPCT,PGNSLPGE,PGTME', ...,
                [...webAppGroup, {type:'PageFamily'}]) },
      { label: 'errorUrls',   // WebApplication → PageFamily(HTTP错误URL)
        fn: () => this.client.getTopValues(..., 'PGHTTP400,PGHTTP500', ...,
                [...webAppGroup, {type:'PageFamily'}]) },
      { label: 'slowClients', // WebApplication → ClientIPs → IPAddress(慢客户端)
        fn: () => this.client.getTopValues(..., 'PGSLPCT,PGTME', ...,
                [...webAppGroup, {type:'ClientIPs'}, {type:'IPAddress'}]) }
    ]
  };
}
```

### 2.3 FaultDiagnosisService — 流程编排

核心 API：

| 方法 | 用途 |
|------|------|
| `start(input)` | 启动新诊断：分类→创建 session→执行第一步 |
| `executeStep(session, stepId)` | 执行单步：查询 NAPM→分析数据→匹配提示→返回选项 |
| `nextAction(session, decision)` | 处理用户决策：继续/跳转/生成报告 |
| `buildReportData(session)` | 将 session 转为标准 reportData |

会话状态（session）结构：

```json
{
  "flowType": "network_slow",
  "flowLabel": "网络慢/网络运行异常",
  "description": "核心交换机端口流量中断",
  "context": {
    "faultStart": 1780000000, "faultEnd": 1780007200,
    "baselineStart": 1779913600, "baselineEnd": 1780000000,
    "target": null, "granularity": 60
  },
  "completedSteps": [
    {
      "stepId": "step1_traffic_trend",
      "flowType": "network_slow",
      "description": "第一步：查看总流量趋势",
      "rawData": { "faultTrend": {...} },
      "analysisFlags": { "hasFaultData": true },
      "hints": [
        {"type": "judgment", "text": "总吞吐量明显升高后骤降..."},
        {"type": "packet_trigger", "text": "重传率异常高，建议下载包..."}
      ],
      "userJudgment": "确认流量在14:05开始下降"
    }
  ],
  "currentStepId": "step3_network_quality"
}
```

### 2.4 FaultDiagnosisReportBuilder — 报告构建

将 session 中的 `completedSteps` 转换为动态 `sections[]`。

构建规则：

| 来源 | 生成的 section |
|------|------|
| session.metadata | 1 基本信息（summary） |
| 步骤数 | 2 分析过程概览（summary） |
| 每个 step | 2.N 步骤描述（summary） |
| step.hints(judgment) | 判断提示（items） |
| step.hints(packet_trigger) | 数据包触发条件（items） |
| step.userJudgment | 用户判断（summary） |
| step.rawData | NAPM 查询结果（table） |
| 全部步骤汇总 | 3 证据项（summary + table） |
| hints 文本 + fault.severity | 4 根因判断（summary） |
| fault.recommendations | 5 处置建议（items） |
| fault.prevention | 6 验证方式（items） |

**3 步诊断 → 18 个动态 section 的完整报告。**

### 2.5 judgment-hints.v1.json — 判断提示文本库

按公司流程文档中的判断规则表结构化存储。

```json
{
  "network_slow": {
    "step1_traffic_trend": {
      "hints": [
        {"when": "totalBytesIncreased AND faultTimeMatch",
         "text": "总吞吐量和总字节数明显升高，可能存在带宽占用、大流量业务或异常流量"},
        {"when": "trafficNormal",
         "text": "总流量正常但用户仍反馈慢，不应判断为带宽问题..."}
      ]
    },
    "step3_network_quality": {
      "hints": [...],
      "packetTriggers": [
        {"when": "retransRateHigh",
         "text": "重传率异常高，建议下载数据包确认TCP重传、ACK、丢包方向"}
      ]
    }
  }
}
```

数据包触发条件统一标注为 `type: "packet_trigger"`，与系统指标提示（`type: "judgment"`）区分。

## 三、路由与集成

### 3.1 渲染路由

```javascript
// ReportTemplateService.renderDocx()

// v1 — 固定模板（§6章）
if (report.templateId === 'napm_fault_diagnosis_v1') {
  return this.renderDiagnosticDocx(report);  // → DiagnosticFixedTemplateService
}

// v2 — 动态 sections（§8结构）
// 不匹配任何固定模板 → 走通用渲染管线
// 这里的 sections[] 由 FaultDiagnosisReportBuilder 动态生成
```

### 3.2 完整调用链

```
用户输入 (企微)
  ↓
OpenClaw → openclaw-napm-fault-diagnosis
  ↓
FaultDiagnosisService.start()
  ├─ FlowRouter.classify()         → "network_slow"
  ├─ Steps.buildQueries()         → NAPM 查询计划
  ├─ SummaryClient                 → NAPM API
  ├─ Steps.analyzeStepData()      → 数据标记
  ├─ matchHints()                  → 判断提示
  └─ return { data, hints, nextOptions }
  ↓
用户决策 → Service.nextAction()
  ├─ "继续下一步" → executeStep(nextStepId)
  ├─ "转应用分析" → executeStep(bs_app_slow, step1)
  └─ "生成报告"   → ReportBuilder.build(session)
  ↓
ReportBuilder → reportData { templateId: "napm_fault_diagnosis_v2", sections: [...] }
  ↓
ReportTemplateService.renderDocx() → 通用渲染 → .docx
```

## 五、v1 vs v2 对照

| 维度 | v1（保留） | v2（新增） |
|------|------|------|
| Skill | `openclaw-napm-summary` (fault scope) | `openclaw-napm-fault-diagnosis` |
| 模式 | 一次性查询→聚合→填模板 | 分步诊断→人工判断→累积报告 |
| 流程 | 单一 fault scope | 3 类独立流程 + 流程间跳转 |
| 分层 | 无（查全部指标） | 系统指标层 + 数据包触发层 |
| 判断 | 系统自动推断根因 | 系统给判断提示，人做决策 |
| 步骤数 | 1 次查询计划（6-10 API） | 4+3+2 = 9 步骤，每步 1-3 个 API |
| 报告结构 | 6 章固定模板 | §8 动态结构（基本信息→分析过程→证据→根因→建议→验证） |
| 报告渲染 | DiagnosticFixedTemplateService (固定) | 通用渲染（动态 sections） |
| templateId | `napm_fault_diagnosis_v1` | `napm_fault_diagnosis_v2` |
| 适用场景 | 已知参数的快速一键报告 | 逐步排查、不确定方向的交互式诊断 |
| 依赖 | SummaryService + SummaryClient | SummaryClient (直接) + FlowRouter + Steps |

## 六、后续扩展

### 6.1 待落地的流程（第 2/4/5/6 类）

| 流程 | 优先级 | 状态 |
|------|:--:|:--:|
| 用户/部门/客户端投诉 | P1 | 未实现（FlowRouter 可识别，Steps 未定义） |
| 连接失败/RST/超时 | P1 | 未实现 |
| 丢包/延时/重传网络质量专项 | P2 | 未实现（但网络慢 Step3 已覆盖部分） |
| 安全异常/攻击/病毒/蠕虫/非法外连 | P2 | 未实现 |

扩展方式：在 `FaultDiagnosisFlowRouter.FLOW_TYPES` 中新增流程定义，在 `FaultDiagnosisSteps` 中新增步骤实现，在 `judgment-hints.v1.json` 中新增判断提示。

### 6.2 判断提示的智能化

当前判断提示基于预定义条件标记匹配（`when: "trafficNormal"` → flag 检查）。后续可升级为：
- 基于阈值的自动标记（如 `TPIO_drop > 50%` → 自动设置 `trafficDropSignificant`）
- 基于时序关联的自动标记（如告警时间 vs 流量异常时间差 < 5min → 自动设置 `alertTrafficCorrelated`）

### 6.3 与 openclaw-napm-packet-analysis 的联动

当前系统仅在提示中"建议下载数据包"。后续可实现：
- 用户确认后，系统自动调用 `openclaw-napm-packet-analysis` 抓取对应五元组的数据包
- 数据包分析结果自动合并到报告的证据项中
