# LLM 推理深度优化方案：如何做到简单问题 4-5s

日期：2026-07-08
状态：方案设计（不修改代码）

---

## 一、重新审视：P0+P1+P2 为什么不够

### 1.1 关键认知：输入侧优化解决的是 prefill 时间，不是 generation 时间

上篇方案 P0+P1+P2 全部聚焦于**减少 LLM 输入 token**。这确实能减少 prefill 时间，但**无法减少 generation 时间**——而 generation 恰恰是耗时大头。

### 1.2 实测数据验证

从 09:40 查询的 answer，实际 LLM 生成了 **539 个字符**：

```
以下是最近一小时（08:40~09:40）吞吐量前10的IP：

| 排名 | IP | 吞吐量 |
|:---:|---|---|
| 1 | 101.254.114.237 | 9.62 KB/s |
| 2 | 171.111.194.192 | 12.06 KB/s |
... (10 rows)
| 10 | 101.254.114.242 | 24.10 KB/s |

整体流量水平较低，最大吞吐 IP 为 101.254.114.242（24.10 KB/s），
其次是 171.111.194.192（12.06 KB/s）。
如需进一步查看某个 IP 的流量趋势或组成，可以告诉我。
```

这 539 个字符 ≈ **200-250 token**。DeepSeek Chat 中文 generation 速度约 **30-50 tok/s**，仅生成这段文本就需要 **4-7 秒**——无论你把输入 token 减到多少，这个时间都不会变。

### 1.3 P0+P1+P2 的真实效果

```
                    改前            改后(P0+P1+P2)
                    ─────           ──────────────
LLM 调用 #1（Tool决策）:
  Prefill           2,700ms  →      1,100ms  (-59%)
  Generation         2,500ms →       2,500ms  (不变！)
  
LLM 调用 #2（格式化回答）:
  Prefill             200ms  →         80ms   (-60%)
  Generation         5,000ms →       5,000ms  (不变！！！)
  
其他（网络/Tool）      900ms  →        700ms
─────────────────────────────────────────────────
合计                11,300ms →       9,380ms

仅节省 ~1.9 秒，距离 4-5s 目标还差 4-5 秒。
```

### 1.4 端到端时间分布（改前实测）

```
10.3 秒拆解

Pre-fill                    ██████████████  2,700ms  26%
LLM Generation #1           █████████████   2,500ms  24%
Hook+Skill+API             ██               300ms    3%
LLM Generation #2           ██████████████████████████  5,000ms  48%  ← 主瓶颈
Network/Other              ████             700ms    7%
─────────────────────────────────────────────────────────
                                    10,300ms
```

**结论**：P0+P1+P2 触达的是 **26% 的 prefill 时间**，无法触达 **72% 的 generation 时间**。要实现 4-5s 目标，必须从 **输出侧** 下手。

## 二、核心策略：让 LLM 少生成、不生成

### 2.1 关键洞察

对于"吞吐量前 10 IP"这种简单查询，LLM 的"智能"只用在一个地方：

> **理解用户意图 → 决定调用哪个 Tool → 构造参数**

一旦 Tool 返回数据，后续的"格式化 Markdown 表格 + 写分析文字"是**纯机械劳动**——代码在微秒级就能完成，不该让 LLM 花 5 秒生成。

```
当前流程（2 次 LLM 调用）：

LLM 调用 #1                 LLM 调用 #2
┌──────────────┐   数据    ┌──────────────────┐
│ 理解意图     │ ──────→  │ 格式化表格        │
│ 选择Tool     │          │ 写分析文字        │
│ 构造参数     │          │ 添加建议          │
│              │          │ (耗时 5s！！)     │
└──────────────┘          └──────────────────┘
   ~2.5s generation          ~5.0s generation

优化后流程（1.5 次 LLM 调用）：

LLM 调用 #1                代码格式化
┌──────────────┐   数据    ┌──────────────────┐
│ 理解意图     │ ──────→  │ Skill 预格式化    │
│ 选择Tool     │          │ displayText       │
│ 构造参数     │          │ (耗时 <1ms)       │
└──────────────┘          └──────────────────┘
   ~2.5s generation              │
                           LLM 调用 #2（轻量）
                           ┌──────────────────┐
                           │ 输出 displayText  │
                           │ 一字不改          │
                           │ (耗时 ~0.5s)      │
                           └──────────────────┘
```

### 2.2 可行性依据：Alert 已经这样做了

当前告警查询的完整链路就是一个**成功先例**：

```
告警查询流程（已实现，已验证）：
1. LLM 决定调用 napm-alert-query
2. handleSkillCall → executeAlertQuery → 返回预格式化的 displayText
3. 路由上下文告诉 LLM："Output it VERBATIM — character-for-character"
4. LLM 输出 displayText，几乎不生成任何新 token
5. 端到端耗时远低于数据查询
```

**问题**：为什么同样的模式不能用于 `napm-skill-query`？

答案：可以。`buildOpenClawReplyContract` 已经生成了 `displayText`，只是：
- 当前的 `displayText` 较简短，LLM 倾向于自己格式化
- 路由上下文中对数据查询没有"verbatim"级别的强制要求
- 没有像 alert 那样的 `message_sending` 兜底拦截

## 三、方案四：Skill 预格式化 + 强制 Verbatim 输出（P4）

### 3.1 改造内容

#### 3.1.1 Skill 侧：增强 `displayText` 为完整最终答案

当前 `buildOpenClawReplyContract` 已经生成 `displayText`，但格式较简。改为生成**完整的、用户可直接阅读的最终答案**。

**改前** displayText（简短，LLM 会自己扩写）：
```
"最近一小时吞吐量前10 IP: 101.254.114.237(9.62 KB/s), 171.111.194.192(12.06 KB/s)..."
```

**改后** displayText（完整，LLM 一字不改即用）：
```markdown
以下是最近一小时（08:40~09:40）吞吐量前10的IP：

| 排名 | IP | 吞吐量 |
|:---:|---|---|
| 1 | 101.254.114.237 | 9.62 KB/s |
| 2 | 171.111.194.192 | 12.06 KB/s |
| 3 | 101.254.114.235 | 8.79 KB/s |
| 4 | 101.254.114.239 | 10.89 KB/s |
| 5 | 101.254.114.238 | 5.14 KB/s |
| 6 | 60.204.130.174 | 5.11 KB/s |
| 7 | 204.76.203.77 | 4.38 KB/s |
| 8 | 101.254.114.240 | 5.69 KB/s |
| 9 | 36.112.176.209 | 7.50 KB/s |
| 10 | 101.254.114.242 | 24.10 KB/s |

整体流量水平较低，最大吞吐 IP 为 **101.254.114.242**（24.10 KB/s），
其次是 **171.111.194.192**（12.06 KB/s）。
如需进一步查看某个 IP 的流量趋势或组成，可以告诉我。
```

**关键**：这个 `displayText` 完全由 `buildOpenClawReplyContract` 在 Skill 中生成，**不需要 LLM 参与格式化**。

#### 3.1.2 路由上下文：添加强制 Verbatim 规则

在 `buildNapmRoutingSystemContext()` 中添加一条规则，类似告警的 verbatim 合约：

```javascript
// 新增规则
'🔴 DATA QUERY FINAL ANSWER CONTRACT: `napm-skill-query` returns pre-formatted `displayText` containing the COMPLETE answer with markdown table and analysis. Output `result.displayText` VERBATIM — character-for-character. Do NOT re-format the table, do NOT add commentary, do NOT change the wording. If displayText is present and non-empty, it IS the final answer.'
```

这条规则长约 400 字符（~160 token），远小于 LLM 自己生成回答的 ~5,000ms generation 时间。

#### 3.1.3 `message_sending` Hook：安全兜底

在 `message_sending` Hook（`napm-before-message-write-guard`，line 5800+）中添加拦截逻辑：

```javascript
// 伪代码
// 如果最近的 napm-skill-query 结果有完整的 displayText，
// 且 LLM 生成的回答与 displayText 差异较大，
// 直接用 displayText 替换
if (hasRecentSkillResult && skillResult.displayText) {
  return {
    message: buildAssistantTextMessage(skillResult.displayText, message)
  };
}
```

**这不是首选路径**——首选是 LLM 自觉输出 verbatim。Hook 只是兜底，确保即使 LLM 没有遵守 verbatim 合约，用户也能得到快速回答。

### 3.2 改造范围

| 文件 | 改动 | 类型 |
|------|------|------|
| `skills/openclaw-napm-query/scripts/run_napm_query.js` | `buildOpenClawReplyContract` 中 `displayText` 从简洁版 → 完整版 | 文本改动 |
| `napm-openclaw-plugin.remote.js` | `buildNapmRoutingSystemContext` 新增 1 条 verbatim 规则 | 新增 ~400 字符 |
| `napm-openclaw-plugin.remote.js` | `message_sending` Hook 新增 displayText 兜底逻辑 | ~20 行代码 |

## 四、方案五：消除第二轮 LLM 调用的完全体方案（P5）

### 4.1 思路

P4 将第二轮 LLM generation 从 5,000ms 降至 500ms。但仍有 500ms 的 verbatim echo 开销。能否**完全消除**第二轮 LLM 调用？

### 4.2 实现路径

当前 `createSkillToolDefinition.execute` 的返回方式：

```javascript
// 改前：结果发给 LLM，LLM 再格式化
execute: async (_toolCallId, args) => {
  const result = await napmQuerySkill().handleSkillCall(preparedArgs);
  rememberDebugApi(...);
  return makeToolResult(result);  // ← 结果回到 LLM
}
```

对比 `createAlertQueryToolDefinition.execute`：

```javascript
// Alert 工具：返回 content 块，可能直接作为输出
execute: async (_toolCallId, args = {}) => {
  const result = await napmAlertSkill().handleSkillCall(args || {});
  const dt = result?.narrationInput?.displayText;
  if (dt) {
    return { content: [{ type: 'text', text: dt }] };  // ← 直接输出
  }
  // ...
}
```

**关键区别**：Alert 工具在 `execute()` 中返回 `{ content: [...] }`，数据查询工具返回 `makeToolResult(result)`。

如果 OpenClaw 框架允许 Tool 返回 content 作为最终输出（跳过 LLM 第二轮调用），那么可以实现：

```javascript
// 改后：content 块直接作为最终输出（跳过 LLM）
execute: async (_toolCallId, args) => {
  const result = await napmQuerySkill().handleSkillCall(preparedArgs);
  const displayText = result?.displayText || result?.summary?.displayText;
  
  if (displayText && result?.responseType === 'direct_query') {
    // 简单查询：直接输出，不经过 LLM 第二轮
    return {
      content: [{ type: 'text', text: displayText }],
      details: result
    };
  }
  
  // 复杂查询：仍然经过 LLM（需要 LLM 的深度解读）
  rememberDebugApi(...);
  return makeToolResult(result);
}
```

### 4.3 是否可行

需要验证 OpenClaw 框架行为：

| 返回格式 | OpenClaw 行为（推测） | 验证方法 |
|---------|---------------------|---------|
| `makeToolResult(result)` | 结果发回 LLM，LLM 再回复 | 当前行为 |
| `{ content: [...], details: result }` | 可能作为 tool 最终输出，跳过 LLM | 观察 alert 查询是否有第二轮 LLM generation |
| `{ content: [...], details: result, isFinal: true }` | 未知 | 需查阅 OpenClaw 文档 |

**验证计划**（不修改代码、只观察）：
1. 在企业微信发送一条告警查询
2. 从主日志分析 alert 查询是否有两次 LLM generation（两个 streamId）
3. 如果 alert 只有一次 LLM generation → 证明 `{ content }` 模式可以跳过第二轮 LLM 调用
4. 将此模式扩展到数据查询

### 4.4 效果预估（如果可行）

```
简单查询：

                    当前          P4(vervatim)   P5(skip 2nd LLM)
                    ─────         ─────         ──────────────
LLM #1 prefill      2,700ms       1,100ms        1,100ms
LLM #1 generation   2,500ms       2,500ms        2,500ms
LLM #2 prefill        200ms          80ms            0ms   ← 消除
```

## 六、实施方案：聚焦 P4（预格式化 + Verbatim）

P4 是**性价比最高**的方案——改动量中等、风险低、效果显著（简单查询从 10.3s → ~5s）。

### 6.1 三件要做的事

#### ① 增强 Skill 的 `displayText`（`run_napm_query.js`）

在 `buildOpenClawReplyContract` 中，为常见的查询模式生成完整的、用户就绪的 Markdown 答案：

```
查询模式          displayText 格式
─────────────────────────────────────────
topValues        Markdown 排序表格 + 排名 + Top 1 高亮
averageValues    数值卡片 + 时间范围
timeValues       趋势描述 + 峰值/谷值标注
overview         结构化摘要（不含解读，数据事实）
groups           列表/清单
```

**原则**：displayText **只包含数据和事实**，不添加 LLM 才应该做的解读。解读留给 LLM——但通过 verbatim 合约，LLM 只需 echo displayText，不用重新格式化数据。

#### ② 路由上下文添加 Verbatim 合约

```javascript
// buildNapmRoutingSystemContext() 中新增（~400 字符）
'🔴 DATA QUERY ANSWER CONTRACT: `napm-skill-query` result.displayText contains the COMPLETE pre-formatted answer (markdown table, ranking, data facts). If displayText is present and non-empty, output it EXACTLY as-is. Do NOT create your own table, do NOT rephrase the data, do NOT add redundant analysis. The displayText IS the answer. Only add interpretation when the user explicitly asks for analysis or the data shows anomalies worth explaining.',
```

#### ③ `message_sending` Hook 兜底

在现有的 `napm-before-message-write-guard` Hook 中（line 5800+），添加：

```javascript
// 伪代码
// 如果：最近有 napm-skill-query 结果，且 LLM 生成的回答与 displayText 不一致
// 则：用 displayText 替换
const rememberedRecord = getRememberedRecordForPrompt(activePrompt);
if (rememberedRecord?.result?.displayText) {
  const llmText = extractTextContent(message);
  const displayText = rememberedRecord.result.displayText;
  // 如果 LLM 做了大量改写（文本相似度 < 70%），直接替换
  if (textSimilarity(llmText, displayText) < 0.7) {
    return {
      message: buildAssistantTextMessage(displayText, message)
    };
  }
}
```

> **注意**：此拦截**不是**首选路径。首选是 LLM 遵守 verbatim 合约自觉输出 displayText。Hook 只是安全网——在 LLM 没遵守合约时兜底。

### 6.2 不改的部分

- **LLM 的工具选择能力**：完全不变，LLM 仍然自主决定调用哪个 Tool
- **LLM 的参数构造能力**：完全不变，LLM 仍然构造 `resolvedQuery`
- **复杂查询的 LLM 分析能力**：如果 `displayText` 为空（复杂查询），LLM 正常格式化
- **其他 6 个 Tool**：Alert 已有 verbatim，Summary/Fault/Inspection 各自独立

## 八、关键风险与缓解

| 风险 | 概率 | 缓解 |
|------|:---:|------|
| **LLM 不遵守 verbatim 合约** | 中 | `message_sending` Hook 兜底拦截，强制替换为 displayText |
| **displayText 质量不够好** | 中 | 先在小范围验证（topValues 简单查询），确认格式满意后再扩展到全模式 |
| **复杂查询被误判为简单查询** | 低 | 通过 `responseType` 区分：`direct_query` → verbatim，`overview`/`drilldown` → 正常 LLM 格式化 |
| **displayText 缺失或为空** | 低 | 降级逻辑：如果 displayText 为空，LLM 正常格式化（与改前行为一致） |
| **用户不满意预格式化答案** | 低 | displayText 格式与 LLM 当前生成的格式一致（都是 Markdown 表格），用户无感知差异 |

```
└────────────────────────────────────────────────────────┘
```

**结论**：不换模型的前提下，**简单问题 ~5s、复杂问题 ~8s** 是切实可达的目标。极限优化（P5 消除第二轮 LLM）可达 **~4s / ~7.5s**。
