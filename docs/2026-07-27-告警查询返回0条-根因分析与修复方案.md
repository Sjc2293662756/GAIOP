## 三、根因分析

### 核心问题：校验失败时生成误导性"0条告警"显示

代码执行链路（涉及 3 个文件）：

```
napm-openclaw-plugin.remote.js        run_alert_query.js           AlertNarrationContractService.js
─────────────────────────────────     ─────────────────────        ──────────────────────────────
                                                                  
[AI] → napm-alert-query({            handleSkillCall(params)      
        mode: "summary",                ↓                         
        prompt: "...",            ① validateAlertQuery()          
        criteria: {}                  ↓ FAIL — 缺少 start/end     
      })                         ② buildFailureResult()           
                                      ↓                         
                                 ③ buildNarrationInput(result) ──→ buildDisplayText(result)
                                      ↓                              ↓
                                 ④ result.narrationInput         events = [] (空数组)
                                    .displayText                  summary = null
                                    = "告警总数：0 条..."         返回 380 字符模板
                                                                  
[plugin] buildAlertQueryReply():                                  
  ⑤ skillText = result.narrationInput.displayText  ← 存在！       
  ⑥ return skillText  ← 直接返回"0条告警"，错误被吞噬             
  ⑦ if (!result?.ok) ← 永远不会执行到这里                        
```

### 缺陷一：校验时机错误

[`run_alert_query.js:60-67`](skills/openclaw-napm-alert-query/scripts/run_alert_query.js#L60-L67):

```javascript
async function executeAlertQuery(payload = {}, options = {}) {
  const validation = validateAlertQuery(payload.alertQuery || payload);  // ← ① 先校验
  if (!validation.ok) {
    return buildFailureResult(...);  // ← ② 失败直接返回！
  }
  const { query } = validation;
  const prompt = payload.prompt || payload.userQuery || query.prompt || '';
  const timeRangeAdjustment = applyPromptRelativeTimeRange(query, prompt, options);  // ← ③ 来不及执行
  // ...
}
```

`validateAlertQuery` 在 `applyPromptRelativeTimeRange` **之前**执行。当 AI 传入 `criteria: {}`（无 start/end）时，即使 prompt 中包含"最近三小时"的明确时间表达，代码也来不及从 prompt 中解析时间覆盖 criteria 就校验失败了。

### 缺陷二：错误消息被静默吞噬

[`napm-openclaw-plugin.remote.js:2755-2770`](napm-openclaw-plugin.remote.js#L2755-L2770):

```javascript
function buildAlertQueryReply(result = {}) {
  // skill 已生成 displayText → 直接透传
  const skillText = result?.narrationInput?.displayText;
  if (skillText) {                     // ← 失败情况下 displayText 也存在！
    const requestUrl = maskDebugApiUrl(result.requestUrl || ...);
    return requestUrl && !skillText.includes(requestUrl)
      ? `${skillText}\n\nDebug API:\n${requestUrl}`
      : skillText;                      // ← 直接返回"告警总数：0 条"文本
  }

  if (!result?.ok) {                    // ← 被上面拦截，永远不会执行
    return String(
      result?.message
      || result?.error?.message         // ← "ALERT_TIME_RANGE_REQUIRED" 被丢弃
      || '告警查询失败。'
    ).trim();
  }
  // ...
}
```

**问题**：`buildFailureResult()` 在生成失败 result 时，仍然通过 `buildNarrationInput()` → `buildDisplayText()` 创建了完整的"0条告警"模板。`buildAlertQueryReply()` 看到 displayText 存在就直接透传，真正的错误码 `ALERT_TIME_RANGE_REQUIRED` 被丢弃。

### 缺陷三：生产环境钩子日志缺失

`before_tool_call` 钩子应在 [line 5233](napm-openclaw-plugin.remote.js#L5233) 输出：
```
[napm-openclaw-plugin] before_tool_call tool=napm-alert-query ...
```

但在 OpenClaw 网关日志 (`/tmp/openclaw/openclaw-2026-07-27.log`) 和 systemd journal 中**完全没有找到**该日志条目。这表明以下可能之一：

1. 钩子未被实际触发（OpenClaw 框架对插件 `before_tool_call` 的支持可能有限，line 4464 注释暗示了这一点）
2. 钩子内部 `require(timeResolver)` 抛出异常被 `catch` 静默吞掉（line 5301-5302）
3. `api.logger.info()` 的输出目标与预期不同

## 四、为什么是"偶尔"出现？（偶发性分析）

### 4.1 统计数据全景

从审计日志中提取了全部 94 次 `napm_alert_displaytext_set` 事件：

| 2026-07-08 | 8 | 0 | **0%** |
| 2026-07-09 | 3 | 0 | **0%** |
| **2026-07-14** | 39 | 2 | **5%** ← 代码重构后开始出现 |

| 2026-07-22 | 4 | 1 | 25% |

- **7月14日代码重构后：失败开始出现，整体失败率约 15%（14/94）**

### 4.3 为什么"大部分时候有数据，偶尔没有"？

综合证据指向 **三层因素的叠加效应**：

#### 第一层（必要条件）：校验在时间解析之前

`executeAlertQuery()` 中 `validateAlertQuery()` 在第 60 行，`applyPromptRelativeTimeRange()` 在第 67 行。当 `criteria` 中缺少 `start/end` 时，校验必定失败。这是**每次都会触发**的结构性问题。

#### 第二层（保护机制）：`before_tool_call` 钩子兜底

钩子在 [line 5283-5299](napm-openclaw-plugin.remote.js#L5283-L5299) 为 `napm-alert-query` 设置了 `criteria.start/end` 的 1 小时默认值。**大部分时候钩子正常工作** → 校验通过 → API 调用成功 → 返回真实数据。

#### 第三层（触发条件）：钩子偶尔失效

钩子的整个时间覆盖逻辑包裹在一个 `try-catch` 中（line 5240-5301）：

```javascript
try {
  const { applyTimeOverride } = require(
    path.resolve(__dirname, 'skills/openclaw-napm-query/src/shared/timeResolver')
  );
  // ... 所有工具的默认时间逻辑，包括 napm-alert-query
} catch (_timeOverrideError) {
  api.logger.warn(`time override failed for ${toolName}: ${_timeOverrideError.message}`);
}
```

**如果 `require()` 调用抛异常，所有工具的默认时间设置都被跳过**，包括告警查询的 1 小时兜底。之后校验因缺少 `start/end` 而失败，返回误导性的"0条告警"。

可能触发 `require()` 失败的情况：

| 触发条件 | 可能性 | 说明 |
|----------|--------|------|
| 插件热加载机制 (`delete require.cache`) 正在刷新模块缓存 | ⭐⭐⭐ | 技能文件推送后 `loadSkill()` 清除缓存，与并发请求中的 `require()` 产生瞬时竞争 |
| 磁盘 I/O 瞬时阻塞（高负载、备份任务等） | ⭐⭐ | `require()` 从磁盘读取模块文件时偶发 I/O 错误 |
| 文件系统 inode 变更（vim/rsync 写文件方式） | ⭐ | 推送代码时文件短暂不可用 |

#### 为什么重试几乎总是成功？

- 重试间隔只有几秒 → 竞争条件已自动解除（模块缓存已稳定，I/O 已完成）
- 统计数据：14 次失败后，已知的重试中约 80% 在第二次或第三次就成功了

#### 为什么 7/16 失败率高达 67%？

7月14-16日是代码重构的密集期（插件从旧版 `index.js` 迁移到新版 `napm-openclaw-plugin.remote.js`，参见远端 `.bak` 文件）。频繁的代码推送导致 `require()` 缓存被持续刷新，`before_tool_call` 钩子中的 `require(timeResolver)` 在并发请求下命中竞争窗口的概率大幅增加。

### 4.4 失败长度的微妙差异（380 vs 420）

| 长度 | 原因 |
|------|------|
| **380** | `buildFailureResult` 的 `timeRange: null` → `buildDisplayText` 中无时间头 → 恰好 380 字符 |
| **420** | `buildFailureResult` 有 `timeRange`（从 query 传入）→ 多了 `"最近三小时 告警查询结果\n\n"` → 约 420 字符 |
| **386** | 同上，时间显示文本略有不同 |

三种长度都对应同一个根因：校验失败后 `buildDisplayText` 用空 `events` 数组生成了"0条告警"模板。

### 5.2 修复二：`executeAlertQuery` — prompt 时间解析提前到校验之前（核心修复）

**文件**：[`skills/openclaw-napm-alert-query/scripts/run_alert_query.js:59`](skills/openclaw-napm-alert-query/scripts/run_alert_query.js#L59)

**修改前**：
```javascript
async function executeAlertQuery(payload = {}, options = {}) {
  const validation = validateAlertQuery(payload.alertQuery || payload);  // ← ① 先校验
  if (!validation.ok) {
    return buildFailureResult(...);  // ← ② 失败直接返回！
  }
  const { query } = validation;
```

**修改后**：
```javascript
async function executeAlertQuery(payload = {}, options = {}) {
  // 🔴 2026-07-27 修复: prompt 时间解析必须在校验之前
  const prompt = payload.prompt || payload.userQuery || (payload.alertQuery && payload.alertQuery.prompt) || '';
  const promptTimeRange = resolveRelativeTimeRangeFromPrompt(prompt, options.nowMs);
  if (promptTimeRange) {
    const criteria = (payload.alertQuery && payload.alertQuery.criteria)
      || payload.criteria
      || (payload.alertQuery || payload);
    if (criteria && typeof criteria === 'object' && !Array.isArray(criteria)) {
      if (!criteria.start) criteria.start = promptTimeRange.start;
      if (!criteria.end) criteria.end = promptTimeRange.end;
      if (!criteria.timeRange || typeof criteria.timeRange !== 'object') {
        criteria.timeRange = {};
      }
      if (!criteria.timeRange.key) criteria.timeRange.key = promptTimeRange.key;
      if (!criteria.timeRange.displayText) criteria.timeRange.displayText = promptTimeRange.displayText;
    }
  }

  const validation = validateAlertQuery(payload.alertQuery || payload);  // ← 现在校验
  if (!validation.ok) {
    return buildFailureResult(...);
  }
  const { query } = validation;
  const timeRangeAdjustment = applyPromptRelativeTimeRange(query, prompt, options);
```

> **效果**：从根源解决问题。即使 AI 传入 `criteria: {}`（无 start/end），代码也会先解析 prompt 中的"最近三小时"→ 计算出正确的 Unix 时间戳 → 预填到 criteria → 校验通过 → 正常调用 NAPM API。

### 5.3 修复三：`before_tool_call` 钩子 — 告警默认时间独立于 `require(timeResolver)`

**文件**：[`napm-openclaw-plugin.remote.js:4702`](napm-openclaw-plugin.remote.js#L4702)

**修改前**：告警的默认时间逻辑与其他工具的 `require(timeResolver)` 共用同一个 try-catch。一旦 require 抛异常，所有默认时间设置（包括告警）全部静默跳过。

```javascript
}
```

**修改后**：告警的时间默认逻辑**独立提取到 try-catch 之外**，不依赖 `require(timeResolver)` 是否成功：

```javascript
// 🔴 2026-07-27 修复: 独立于 try-catch，不依赖 timeResolver require
if (toolName === 'napm-alert-query') {

// 下面才是 try-catch 包裹的 require(timeResolver) 及 napm-skill-query/napm-summary 逻辑
if (isSafeNapmToolName(toolName) && isPlainObject(event.params)) {

    // ... 其他工具的时间覆盖 ...

}
```

> **效果**：消除了 `require()` 偶发失败导致告警默认时间全部被跳过的风险。

## 九、防御层级总结

```
用户查询 "最近三小时告警"
        │
        ▼
┌─ 第一层 (hook): before_tool_call 独立设置 criteria.start/end ──────┐
│  不再依赖 require(timeResolver)，始终生效                            │
├─ 第二层 (skill): executeAlertQuery 从 prompt 解析时间 → 预填 criteria │
│  在 validateAlertQuery 之前执行                                      │
├─ 第三层 (结构): buildNarrationInput 失败时 displayText = null         │
│  ok:false 的结果永远不会产生误导性文本                                 │
├─ 第四层 (消费): buildAlertQueryReply 优先检查 result.ok               │
│  即使前3层全失效，用户也能看到真实错误而非"0条告警"                     │
└────────────────────────────────────────────────────────────────────┘
```
