# NAPM 查询最终架构设计：语义标签映射

日期：2026-06-24

---

## 一、核心问题定义

| 组件 | 擅长 | 不擅长 |
|------|------|--------|
| LLM | 理解千变万化的问法（"掉包"→丢包，"卡死了"→延迟，"哪台机器网络质量最差"→IP丢包排行） | 精确构造 JSON（漏字段、错queryModeKey、年份算错）|
| 规则引擎 | 精确映射（丢包→PLI，IP→IPAddress，最严重→topValues/topn/topCount=1，最近→last1hour时间戳）| 处理非标准措辞（正则匹配不上就失败）|

**核心矛盾**：LLM 要做它不擅长的精确构造（14-30s，错误率40%），规则引擎只能做"标准句式→精确映射"（9ms，100%准确）。

**解决**：LLM 只做语义描述（自由文本→结构化意图），规则引擎做精确映射（意图→resolvedQuery）。各司其职。

---

## 二、整体架构

```
用户输入任意问法
      │
      ▼
┌──────────────────────────────────────┐
│ Phase 1: LLM 语义标签提取 (~2s)       │
│                                      │
│ 输入: 用户的自然语言问句               │
│ 输出: 语义标签 JSON (不是resolvedQuery!) │
│                                      │
│ 任务: 理解意图，填标签；               │
│       不需要知道 PLI/PGHTTP400 等 code；│
│       不需要计算 Unix 时间戳           │
└──────────────────┬───────────────────┘
                   │ 语义标签 JSON
                   ▼
┌──────────────────────────────────────┐
│ Phase 2: 规则引擎标签映射 (9ms)        │
│                                      │
│ 输入: 语义标签 JSON                    │
│ 输出: 完整 resolvedQuery              │
│                                      │
│ 确定性的映射表:                        │
│   "丢包" → PLI                        │
│   "IP地址" → IPAddress                │
│   "找最严重的" → topValues/topn        │
│   "最近" → last1hour → Unix timestamps│
│   "1个" → topCount=1                  │
│                                      │
│ 100% 准确，零幻觉。失败则安全回退。      │
└──────────────────┬───────────────────┘
                   │ resolvedQuery
                   ▼
┌──────────────────────────────────────┐
│ Phase 3: NAPM 执行 (~0.7s)            │
│ NapmClient → NetInside API            │
└──────────────────┬───────────────────┘
                   │ 查询结果
                   ▼
┌──────────────────────────────────────┐
│ Phase 4: LLM 中文叙述 (~2s)           │
│ 输入: 查询结果 + narrationContract    │
│ 输出: 用户可读的中文回答               │
└──────────────────────────────────────┘

总耗时 (简单查询): 2s + 0.009s + 0.7s + 2s ≈ 5s
总耗时 (复杂查询): 2s + 0.009s(失败) + LLM构造(10s) + 0.7s + 2s ≈ 15s
```

## 三、语义标签 Schema

### 3.1 标签定义

LLM 提取的是**意图描述**，不是 NAPM 内部 code。字段值用中文自然表达，规则引擎负责归一化。

```json
{
  "metricIntent": {
    "description": "用户想查询什么指标？用中文描述即可",
    "examples": ["丢包", "报错", "流量", "响应时间", "连接数", "页面访问量", "重传", "HTTP500错误", "慢页面"]
  },
  "objectScope": {
    "description": "用户想查询什么类型的对象？",
    "examples": ["IP地址", "业务系统", "业务组", "已定义应用", "网段", "自动识别应用", "页面"]
  },
  "objectName": {
    "description": "如果用户指定了具体名称，填在这里；否则为空",
    "examples": ["239web", "服务器网段", "其他Web应用", ""]
  },
  "queryShape": {
    "description": "用户想怎么查？",
    "enum": ["找最X的", "看平均", "看趋势变化", "列出所有", "综合分析"]
  },
  "timeAnchor": {
    "description": "时间范围，用中文描述",
    "examples": ["最近1小时", "最近24小时", "今天", "最近7天", "最近30天"]
  },
  "resultSize": {
    "description": "用户想看几个结果？没有明确说就填'默认'",
    "examples": ["1个(谁/哪个)", "5个", "10个", "20个", "默认"]
  },
  "drilldown": {
    "description": "用户是否要下钻？如需要，描述下钻方向；不需要则填null",

  },
  "compositeIntent": {
    "description": "是否需要多步分析？不需要则填null",
    "examples": [null, "先找最X的再分析", "概览分析", "对比分析"]
  }
}
```

### 3.2 LLM 提取 Prompt

极简，~15 行。不教规则——规则引擎负责规则。

```
分析用户的 NAPM 查询意图，输出以下 JSON。用中文描述，不要翻译成英文 code。

{
  "metricIntent": "用户问什么指标?",
  "objectScope": "查什么对象?",
  "objectName": "具体名称或空",
  "queryShape": "找最X的|看平均|看趋势变化|列出所有|综合分析",
  "timeAnchor": "最近1小时|最近24小时|今天|最近7天|最近30天",
  "resultSize": "1个(谁/哪个)|5个|10个|20个|默认",
  "drilldown": null 或 "下钻方向",
  "compositeIntent": null 或 "先找最X的再分析|概览分析"
}

用户问: "{{user_prompt}}"

只输出 JSON。不要解释。
```

## 四、规则引擎：标签 → resolvedQuery 映射

### 4.1 核心映射表

```javascript
const METRIC_INTENT_MAP = {
  '丢包':          { metric: 'PLI',   metrics: ['PLI'],       topMetric: 'PLI' },
  '掉包':          { metric: 'PLI',   metrics: ['PLI'],       topMetric: 'PLI' },
  'packet loss':   { metric: 'PLI',   metrics: ['PLI'],       topMetric: 'PLI' },
  '报错':          { metric: 'PGHTTP400', metrics: ['PGHTTP400','PGHTTP500'], topMetric: 'PGHTTP400' },
  'HTTP错误':      { metric: 'PGHTTP400', metrics: ['PGHTTP400','PGHTTP500'], topMetric: 'PGHTTP400' },
  'HTTP400':       { metric: 'PGHTTP400', metrics: ['PGHTTP400'], topMetric: 'PGHTTP400' },
  'HTTP500':       { metric: 'PGHTTP500', metrics: ['PGHTTP500'], topMetric: 'PGHTTP500' },
  '连接失败':      { metric: 'RFCI',  metrics: ['RFCI','RFCO'], topMetric: 'RFCI' },
  '流量':          { metric: 'TPIO',  metrics: ['TPIO'],       topMetric: 'TPIO' },
  '带宽':          { metric: 'TPIO',  metrics: ['TPIO'],       topMetric: 'TPIO' },
  '吞吐':          { metric: 'TPIO',  metrics: ['TPIO'],       topMetric: 'TPIO' },
  '数据包':        { metric: 'PKIO',  metrics: ['PKIO'],       topMetric: 'PKIO' },
  '响应时间':      { metric: 'TRTI',  metrics: ['TRTI'],       topMetric: 'TRTI' },
  '延迟':          { metric: 'RTTI',  metrics: ['RTTI'],       topMetric: 'RTTI' },
  '页面延时':      { metric: 'PGTME', metrics: ['PGTME'],      topMetric: 'PGTME' },
  '连接数':        { metric: 'CONI',  metrics: ['CONI','CCNI'],topMetric: 'CONI' },
  '页面访问':      { metric: 'PGNPGE',metrics: ['PGNPGE'],     topMetric: 'PGNPGE' },
  '重传':          { metric: 'RTXI',  metrics: ['RTXI','RTXO'],topMetric: 'RTXI' },
  '用户体验':      { metric: 'UEII',  metrics: ['UEII'],       topMetric: 'UEII' },
};
```

### 4.2 归一化层：模糊匹配

LLM 填的 `metricIntent` 可能是 "掉的包"、"高丢包"、"packet drop" 等变体。规则引擎在精确匹配之前加一层**模糊归一化**：

```
输入: "网络延迟很大"
  → 分词: ["网络", "延迟", "很大"]
  → 查关键词表: "延迟" → metricIntent归一化为 "延迟"
  → 查映射表: "延迟" → RTTI
```

关键词表覆盖每个映射入口的所有常见说法。

### 4.3 上下文敏感映射

部分映射需要结合 `objectScope`：

```javascript
function resolveMetric(metricIntent, objectScope) {
  const resolved = METRIC_INTENT_MAP[fuzzyMatch(metricIntent)];
  if (!resolved) return null;
  
  // 上下文修正
  if (metricIntent === '报错' && objectScope === '业务组') {
    return { metric: 'RFCI', metrics: ['RFCI','RFCO'], topMetric: 'RFCI' };
  }
  if (metricIntent === '响应时间' && objectScope === '业务系统') {
    return { metric: 'PGTME', metrics: ['PGTME'], topMetric: 'PGTME' };
  }
  
  return resolved;
}
```

### 4.4 时间归一化

```javascript
const TIME_ANCHOR_MAP = {
  '最近1小时':  { key: 'last1hour',  seconds: 3600 },
  '最近24小时': { key: 'last24hours', seconds: 86400 },
  '今天':       { key: 'today',      dayOffset: 0 },
  '昨天':       { key: 'yesterday',  dayOffset: -1 },
  '最近7天':    { key: 'last7days',  seconds: 604800 },
  '最近30天':   { key: 'last30days', seconds: 2592000 },
};

function resolveTime(timeAnchor) {
  const key = fuzzyMatch(timeAnchor, Object.keys(TIME_ANCHOR_MAP));
  return ResolvedQueryTimeRangeService.resolveTimeRange(key);
}
```

## 五、复杂查询处理

### 5.1 规则引擎的边界

规则引擎只处理**单步查询**。当遇到以下情况时返回 `needsConstruction: true`：

- `drilldown` 不为 null → 需要多层 group 路径规划
- `compositeIntent` 不为 null → 需要 discover-then-analyze 或 overview
- 映射后的 metric/object 组合不兼容 → 需要 LLM 澄清

### 5.2 返回给 LLM 的信号

```json
{
  "needsConstruction": true,
  "reason": "drilldown_required|composite_analysis|ambiguous",
  "context": {
    "prompt": "原始用户问句",
    "extractedTags": "{LLM提取的语义标签}",
    "resolvedBasics": "{规则引擎已解析的基础部分}"
  },
  "guidance": "需要下钻路径: 从WebApplication到ClientIPs再到IPAddress"
}
```

### 5.3 LLM 介入构造

LLM 收到 `needsConstruction` 后，基于已有的基础解析结果，只补充缺失部分：

- 构造 `groups` 数组（多层路径各节点的 type 和 argument）
- 构造 `analysisPipeline.discoveryQuery`（如果是 discover-then-analyze）
- 补齐 `semanticConstraints` 等元数据

然后带着完整 `resolvedQuery` 再调一次 `napm-skill-query`。

## 七、和之前方案的对比

| | 之前 | 本方案 |
|------|------|--------|
| LLM 输出 | 完整 resolvedQuery JSON (500 token) | 语义标签 JSON (50 token) |
| LLM 任务 | 写代码（想字段名、算时间戳） | 做选择题（丢包/流量/报错/延迟...） |
| LLM 耗时 | 14-30s，3-5轮推理 | 1-2s，1轮推理 |
| LLM 错误率 | 40%（漏字段、错年份） | <5%（标签填错） |
| 精确映射 | LLM 负责 → 常错 | 规则引擎负责 → 永不 |
| 千变万化问法 | 用 openai.yaml 教 LLM 映射规则 | LLM 天然理解 → 标签提取 |
| 复杂查询 | 相同 LLM 路径 | LLM 收到 needsConstruction → 介入 |
| 入口 | LLM 判断路径 | 统一入口 `napm-skill-query({prompt})` |

## 八、预期效果

```
简单查询 (丢包最严重的IP):
  标签提取(1-2s) → 规则映射(9ms) → 执行(0.7s) → 叙述(2s) = ~4s

复杂查询 (综合分析):
  标签提取(1-2s) → 规则映射失败(9ms) → needsConstruction →
  LLM构造resolvedQuery(8s) → 执行(0.7s) → 叙述(2s) = ~12s

加权 (60%简单 + 40%复杂): 0.6×4 + 0.4×12 ≈ 7s (vs 当前 25s)
```
