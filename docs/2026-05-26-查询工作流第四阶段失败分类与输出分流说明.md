# 查询工作流第四阶段失败分类与输出分流说明

## 背景

前三阶段已经完成：

- 第一阶段：先识别 workflow。
- 第二阶段：对象本体和 provider 绑定统一到 `object-ontology.v1.json`。
- 第三阶段：metadata / metric 执行内核物理分层。

第四阶段解决的是失败语义和输出边界问题。

过去系统容易把以下情况混在一起：

- workflow/service 构造错误
- 对象类型未解析
- provider 绑定错误
- metadata API 400 / 403
- metric API 400 / 403
- 真实空数据
- 代码依赖或运行时错误

更严重的是，正式回答里可能出现调试过程、失败尝试、端口探测、旧假设等内容，导致用户看到的结论和真实 skill 结果不一致。

## 本阶段目标

本阶段新增两个统一服务：

- `ExecutionFailureClassifier`
- `AnswerModeRouter`

目标：

- 所有失败进入标准错误分类。
- 正式回答只基于最终确认结果。
- debug trace 与 final answer 物理分流。
- 失败时输出标准失败语义，不再把原始错误 message 当最终数据结论。

## 新增 ExecutionFailureClassifier

新增：

```text
skills/openclaw-napm-query/services/ExecutionFailureClassifier.js
```

职责：

- 根据 `error.code`、HTTP status、service、workflowType 判断失败类别。
- 区分 metadata 域和 metric 域。
- 生成 `userMessage`、`debugMessage`、`retryable` 等字段。

当前标准失败类别包括：

```text
WORKFLOW_SELECTION_INVALID
OBJECT_TYPE_UNRESOLVED
PROVIDER_BINDING_INVALID
METADATA_ARGUMENT_TYPE_UNRESOLVED
METADATA_EMPTY
METADATA_UPSTREAM_400
METADATA_UPSTREAM_403
METRIC_EMPTY
QUERY_SHAPE_INVALID
DEPENDENCY_CONTRACT_MISMATCH
NAPM_UPSTREAM_400
NAPM_UPSTREAM_403
NAPM_UPSTREAM_ERROR
```

示例：

```text
WORKFLOW_SERVICE_CONTRACT_MISMATCH
```

会被归类为：

```text
WORKFLOW_SELECTION_INVALID
```

含义是：不是没有数据，而是 workflow 与 service 不匹配。

## 新增 AnswerModeRouter

新增：

```text
skills/openclaw-napm-query/services/AnswerModeRouter.js
```

职责：

- 判断当前输出模式：
  - `final_answer_mode`
  - `debug_trace_mode`
- 生成对应 render policy。
- 决定是否允许透传 `displayText`。

默认模式：

```text
final_answer_mode
```

正式模式规则：

- 不输出中间尝试。
- 不输出失败假设。
- 不输出端口试探、fallback 过程。
- 失败时输出标准 `failureClassification.userMessage`。
- 不把原始 `error.message` 直接当最终回答。

debug 模式规则：

- 可以输出 workflow、objectType、provider、request 参数、失败类别。
- 可以展示中间失败尝试。
- 必须明确区分失败假设和最终执行状态。

## RequirementParserService 改造

`RequirementParserService.buildExecutionFailureError()` 已改为调用：

```js
ExecutionFailureClassifier.normalizeError(error, context)
```

返回结构增加：

```json
{
  "code": "WORKFLOW_SERVICE_CONTRACT_MISMATCH",
  "category": "WORKFLOW_SELECTION_INVALID",
  "userMessage": "查询工作流与执行服务不匹配...",
  "failureClassification": {
    "category": "WORKFLOW_SELECTION_INVALID",
    "domain": "metadata",
    "service": "topValues",
    "workflowType": "object_inventory"
  }
}
```

这样执行层失败不会再只暴露原始错误码，也不会被误解释成空数据。

## OpenClawNarrationContractService 改造

`buildOpenClawReplyContract()` 现在会：

- 解析 `answerMode`。
- 标准化 `error.failureClassification`。
- 把 `failureClassification` 写入：
  - 顶层返回
  - `narrationStructure`
  - `narrationInput`
  - `renderPolicy`
- 正式模式下如果存在失败分类，不再透传原始 `displayText`。

正式模式下：

```text
responseMode = machine_narration_input
```

让 OpenClaw 根据结构化失败语义叙述，而不是复述原始错误文本。

debug 模式下：

```text
answerMode = debug_trace_mode
```

允许透出调试信息。

## run_napm_query.js 改造

主 catch 中原先会把：

```text
error.message
```

作为 `displayText` 输出。

现在改为：

```js
ExecutionFailureClassifier.classify(error, {})
```

并输出标准 `failureClassification.userMessage`。

## 当前边界

本阶段没有让 plugin 重新承担答案拼接职责。

plugin 仍只做：

- 边界守卫
- 敏感信息保护
- skill 结果透传
- 必要的 debug/guard 信息拦截

正式答案的内容来源仍然是 skill 返回的结构化结果和 OpenClaw narration contract。

## 验收重点

以后再出现：

```text
系统都有哪些工作组
```

如果被错误构造成 `topValues`，应返回标准失败：

```text
WORKFLOW_SELECTION_INVALID
```

而不是：

```text
系统没有工作组
```

如果南向 metadata API 返回 400，应解释为：

```text
METADATA_UPSTREAM_400
```

而不是：

```text
没有数据
```

如果用户没有开启 debug 模式，正式回答不得包含：

- 我先试一下
- 端口不通
- 又换了个方式
- 上一次假设
- 被推翻的对象类型
