# 普通数据包确认续答与固定窗口修复

## 现场表现

用户先请求分析单 IP 最近 5 分钟的数据包，预览返回 `CONFIRM_DOWNLOAD`；下一轮回复“进行下载分析！”时，模型虽然继续调用 `napm-packet-analysis`，Query Turn 却被创建为 `NAPM_QUERY`，调用被 `NAPM_QUERY_TOOL_REQUIRED` 拦截。结果没有执行 `packetsDown` 和 tshark，只返回通用 Skill 缺失提示。

## 根因

- 短确认文本本身不含“数据包”等关键词，普通 packet 工作流没有像告警数据包那样恢复上一轮待确认状态。
- 确认轮默认落入 `NAPM_QUERY`，而该 route 只允许 `napm-skill-query`。
- 即使模型重复传入原请求，也会再次解析“最近 5 分钟”，导致下载窗口相对预览窗口向后漂移。
- packet Tool 没有同轮执行合并，模型重试可能重复下载。
- 最终答复只显示下载文件，没有消费结构化 `analysis`。

## 修复后的事务

```text
首次单 IP / 业务组分析请求
  -> napm-packet-analysis
  -> packetsPreview
  -> preview.ok=true + empty=false + CONFIRM_DOWNLOAD
  -> 保存当前 scope 的结构化结果和固定 start/end

用户短确认
  -> 验证最近结果确为普通 packet 待确认预览
  -> Query Turn route=OTHER_SKILL
  -> 覆盖模型目标和时间，删除相对 timeRange
  -> 插件注入 previewRiskAccepted=true
  -> packetsDown
  -> tshark/capinfos
  -> 确定性分析答复
```

单 IP 与业务组只在目标解析阶段不同：单 IP 直接使用 `criteria.ips`；业务组先查询 `businessGroups` 并展开 `IpMembers`。两者的预览、确认、固定窗口下载和协议分析流程相同，互不依赖。

## 安全与幂等边界

- 无待确认 packet 结果时，裸“下载分析”不获得授权。
- 初始请求中由模型传入的 `previewRiskAccepted` 会在插件边界删除。
- `SUGGEST_NARROW_TIME_RANGE` 必须缩小范围后重新预览，不能直接确认。
- 确认轮只信任上一轮 Skill 返回的目标与 Unix 秒级 `start/end`。
- 同一 `scope + turnId` 的重叠或重复 Tool execute 共享一个执行 Promise，只调用一次 packet runtime。
- 审计日志区分确认恢复、固定参数应用和执行重放。
- 短确认归一化会去除常见中英文尾部标点（包括 `；`），因此企业微信中的“确认下载并分析；”与无标点确认语义一致；正文词汇仍需完整匹配，不会放宽为任意自然语言。

## 最终答复

下载分析成功后，确定性答复包含下载文件、协议分析状态、可用的数据包数，以及结构化结果中存在的协议层级、主要端点、主要会话、DNS、HTTP 和 TLS SNI 摘要。未执行 tshark 时不得声称完成协议分析。

## 验证范围

- 普通 packet 确认续答定向测试：11 个测试通过，覆盖固定条件恢复、裸确认、伪确认、高风险范围和同轮并发单次执行。
- packet runtime、业务组、业务页面、认证、存储、会话隔离、生命周期和告警数据包回归：14 个测试套件、111 个测试通过。
- 全量 Jest：108 个测试套件、1006 个测试通过。
- 项目 lint、插件直接 ESLint、Node 语法检查、Skill runtime contract、临时安装形态的 OpenClaw extension runtime smoke 和 `git diff --check` 通过。
