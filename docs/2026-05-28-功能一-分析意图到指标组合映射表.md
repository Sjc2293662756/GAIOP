## 1. 文档目标

本文档把“慢、异常、错误、不稳定、风险、丢包、连接失败、流量异常”等自然语言分析意图，映射为当前 NAPM 可执行的指标组合与查询步骤。

它解决三个问题：

- 用户说某类分析意图时，应该看哪些主指标。
- 如果用户没有明确对象，应该用哪个 discovery 指标先找对象。
- 找到对象后，focused overview 应该补哪些辅助指标作为证据。

时间范围不在本文档中手算。所有 `start/end` 必须由 `napm-resolve-time-range` 生成。

---

## 2. 总体规则

### 2.1 模型与代码的职责

```text
OpenClaw / 模型：
识别用户分析意图、对象口径、是否需要 discovery、时间语义 key。

确定性服务：
napm-resolve-time-range 负责生成 start/end。
NapmMetadataService / metricsForGroup 负责校验对象和指标可执行性。

skill：
执行 resolvedQuery / analysisPipeline，归并结果并输出 narration contract。
```

### 2.2 查询选择规则

| 用户问题形态 | 推荐 workflow |
|---|---|
| 明确对象 + 问整体/为什么/异常/慢 | focused overview |
| 未明确对象 + 问哪个最异常/最慢/最多 | discovery topValues |
| 先找对象再分析 | overview + `analysisPipeline.discoveryQuery` |
| 多个明确对象比较 | comparative analysis，后续阶段实现 |
| 只问排行/数值/趋势 | 普通 topValues / averageValues / timeValues |

### 2.3 指标使用原则

- 主指标用于 discovery 或结论排序。
- 辅助指标用于 focused overview 解释原因。
- discovery 与 focused overview 默认复用同一时间范围。
- discovery 结果为空时，不得编造对象。
- 指标最终必须通过运行时 `metricsForGroup` 校验，本文档只定义优先候选。

## 4. 详细意图规则

### I001：慢分析

适用问法：

```text
可观测239web 为什么慢？
某业务最近是不是变慢了？
哪个业务响应最慢？
这个 IP 网络时延是不是高？
```

对象与指标：

| 对象 | discovery 主指标 | focused overview 辅助指标 |
|---|---|---|
| WebApplication | PGTME 或 PGNSLPGE | PGTMC、PGTMS、PGSLRT、PGNPGE、PGHTTP500 |
| PageFamily | PGTME | PGTMC、PGTMS、PGSLRT |
| IPAddress | RTTI 或 TRTI | RTTO、TRTT、CONI、RFCI、TPIO |

规则：

- 用户明确业务系统时，不需要 discovery，直接 `overviewScene=business`。
- 用户问“哪个业务最慢”时，使用 `WebApplication + PGTME` 或 `PGNSLPGE` discovery。
- 用户问“网络慢/链路慢/IP 慢”时，使用 `IPAddress + RTTI` discovery。

discovery 示例：

```json
{
  "service": "topValues",
  "queryModeKey": "topn",
  "groups": [
    { "type": "WebApplication" }
  ],
  "metrics": ["PGTME"],
  "topMetric": "PGTME",
  "topCount": 1
}
```

结论证据：

```text
是否慢：
页面平均耗时/慢页面数量/慢页面比例是否高。

慢在哪里：
页面端、服务端、网络侧、访问压力、错误导致体验差。

建议动作：
优先检查慢页面、服务端响应、关联接口、异常时间段。
```

### I002：HTTP 错误分析

适用问法：

```text
哪个业务 HTTP 500 最严重？
可观测239web 最近报错严重吗？
哪些业务 4xx/5xx 比较多？
```

对象与指标：

| 对象 | discovery 主指标 | focused overview 辅助指标 |
|---|---|---|
| WebApplication | PGHTTP500 | PGHTTP500PCT、PGHTTP400、PGHTTP400PCT、PGNPGE、PGTME |

规则：

- 用户明确业务时，focused overview 看 4xx/5xx、访问量、耗时。
- 用户未明确业务时，先按 `PGHTTP500` 找最严重业务。
- 如果用户明确问 4xx，则主指标换成 `PGHTTP400`。

discovery 示例：

```json
{
  "service": "topValues",
  "queryModeKey": "topn",
  "groups": [
    { "type": "WebApplication" }
  ],
  "metrics": ["PGHTTP500"],
  "topMetric": "PGHTTP500",
  "topCount": 1
}
```

结论证据：

```text
错误规模：HTTP 500 数量。
错误占比：PGHTTP500PCT。
背景流量：PGNPGE / PGHTTP200。
用户体验影响：PGTME / 慢页面指标。
```

### I003：连接失败分析

适用问法：

```text
找到连接失败最多的地址，然后分析它。
哪个 IP 连接失败最严重？
某工作组连接异常吗？
```

对象与指标：

| 对象 | discovery 主指标 | focused overview 辅助指标 |
|---|---|---|
| IPAddress | RFCI | RFCO、RFRI、RFRO、CONI、CCNI、CSTI |
| BusinessGroup | RFCI | RFCO、CONI、CONO、CCNI、CCNO |
| IPConversation | RFCI | RFCO、RFRI、RFRO、RTTI、TPIO |

规则：

- “地址/IP/主机连接失败”默认 `IPAddress`。
- “工作组/业务组连接失败”默认 `BusinessGroup`。
- “会话/对端连接失败”默认 `IPConversation`。

discovery 示例：

```json
{
  "service": "topValues",
  "queryModeKey": "topn",
  "groups": [
    { "type": "IPAddress" }
  ],
  "metrics": ["RFCI"],
  "topMetric": "RFCI",
  "topCount": 1
}
```

结论证据：

```text
失败最多对象是谁。
失败方向是入向还是出向。
是否伴随连接请求增多、并发连接压力或建连耗时异常。
是否需要继续看关联应用、对端会话或业务组。
```

---

### I004：丢包分析

适用问法：

```text
丢包最严重的 IP 是谁，为什么？
最近网络质量最差的是哪个地址？
哪个网段丢包最高？
```

对象与指标：

| 对象 | discovery 主指标 | focused overview 辅助指标 |
|---|---|---|
| IPAddress | PLI | PLO、RTXI、RTXO、RTTI、RTTO、TPIO |
| Prefix24 | PLI | PLO、RTXI、RTXO、TPIO |
| TotalTraffic | PLI | PLO、RTTI、RTTO、BYTIO |

规则：

- “IP/地址/主机丢包”默认 `IPAddress`。
- “网段/区域网络质量”默认 `Prefix24`。
- “整体丢包/全局丢包”默认 `TotalTraffic`。
- 如果用户没有指定方向，首版以 `PLI` 做主排序，同时查询 `PLO` 辅助判断方向。

discovery 示例：

```json
{
  "service": "topValues",
  "queryModeKey": "topn",
  "groups": [
    { "type": "IPAddress" }
  ],
  "metrics": ["PLI", "PLO"],
  "topMetric": "PLI",
  "topCount": 1
}
```

结论证据：

```text
丢包最高对象。
入向/出向方向。
是否伴随重传、时延、吞吐异常。
是否像链路质量问题还是业务侧流量压力。
```

---

### I005：流量/吞吐分析

适用问法：

```text
最近一小时流量较大的前 10 个 IP。
哪个应用吞吐最高，看看是否异常。
哪些业务访问流量最大？
```

对象与指标：

| 对象 | discovery / TopN 主指标 | 辅助指标 |
|---|---|---|
| IPAddress | TPIO | BYTIO、BYTI、BYTO、CONI、CONO |
| DefinedApp | TPIO | BYTIO、FILI、FILO、RFCI |
| WebApplication | PGNPGE 或 PGBYTI | PGBYTO、PGHTTP200、PGHTTP500 |
| Prefix24 | TPIO | BYTIO、BYTI、BYTO |

规则：

- 单纯问“前 10 个”是普通 TopN，不必进入复杂分析。
- 问“吞吐最高，看看是否异常”才进入 discovery + focused overview。
- “应用”如果明确是已定义应用，使用 `DefinedApp`；“业务/业务系统”使用 `WebApplication`。

---

### I006：系统整体风险分析

适用问法：

```text
现在系统整体有没有风险？
最近系统哪里不正常？
整体情况怎么样，哪些方向需要关注？
```

对象与指标：

| 分析方向 | 候选指标 |
|---|---|
| 全局流量 | TPIO、BYTIO |
| 连接失败 | RFCI、RFCO |
| 丢包 | PLI、PLO |
| 重传 | RTXI、RTXO |
| 业务错误 | PGHTTP500、PGHTTP400 |
| 业务慢 | PGTME、PGNSLPGE |

推荐 workflow：

```json
{
  "service": "overview",
  "queryModeKey": "overview",
  "overviewScene": "system",
  "start": "<from napm-resolve-time-range>",
  "end": "<from napm-resolve-time-range>",
  "timeRange": {
    "key": "last1hour",
    "displayText": "最近一小时"
  },
  "semanticConstraints": {
    "workflowType": "system_overview",
    "questionType": "risk"
  },
  "format": "json"
}
```

结论证据：

```text
先给整体风险等级。
按业务、应用、网络、连接、安全等方向列出 Top findings。
每个 finding 给对象、指标、数值、时间范围。
最后给建议动作。
```

## 5. Discovery 选择规则

### 5.1 触发表达

出现以下表达时，通常需要 discovery：

```text
找到……最多的……
哪个……最慢？
谁的……最高？
最严重的是谁？
先找出异常对象，再分析。
失败最多的是哪个？
最近最差的是哪个？
```

### 5.2 Discovery 规则表

| 用户目标 | targetObjectType | discovery service | groups | metrics | topMetric | topCount |
|---|---|---|---|---|---|---|
| 找连接失败最多的地址 | IPAddress | topValues | IPAddress | RFCI | RFCI | 1 |
| 找最慢的 Web 应用 | WebApplication | topValues | WebApplication | PGTME | PGTME | 1 |
| 找慢页面最多的业务 | WebApplication | topValues | WebApplication | PGNSLPGE | PGNSLPGE | 1 |
| 找 HTTP 500 最多的业务 | WebApplication | topValues | WebApplication | PGHTTP500 | PGHTTP500 | 1 |
| 找吞吐最高的应用 | DefinedApp | topValues | DefinedApp | TPIO | TPIO | 1 |
| 找丢包最严重的 IP | IPAddress | topValues | IPAddress | PLI、PLO | PLI | 1 |
| 找重传最严重的 IP | IPAddress | topValues | IPAddress | RTXI、RTXO | RTXI | 1 |
| 找网络质量最差的网段 | Prefix24 | topValues | Prefix24 | PLI、RTTI、RTXI | PLI | 1 |

### 5.3 Discovery 输出绑定规则

discovery 查询成功后，必须把 Top1 对象绑定为 focused overview 的目标对象：

```json
{
  "analysisPipeline": {
    "targetObjectType": "IPAddress",
    "selection": {
      "rank": 1
    },
    "discoveryQuery": {}
  }
}
```

执行层要求：

- discovery 和 focused overview 使用同一 `start/end`。
- discovery 的 Top1 对象必须写入 focused overview 的 `groups[0].argument`。
- 如果 discovery 返回空，最终回答必须说明“未锁定明确对象”，不能编造对象。
- 如果 discovery 的对象类型和 focused overview 的对象类型不一致，必须阻断或澄清。

## 6. overviewScene 选择规则

| 对象/表达 | overviewScene |
|---|---|
| 系统、整体、全局、总览 | system |
| 业务、业务系统、Web 应用、站点、网站 | business |
| 工作组、业务组、业务分组 | business_group |
| 应用、已定义应用、协议应用 | application |
| IP、地址、主机、网段、链路、丢包、时延 | network |
| 未知端口、未知应用、外联、安全、攻击、风险 | security |

注意：

- 普通“业务”是 `WebApplication`，不是 `BusinessGroup`。
- “工作组/业务组”才是 `BusinessGroup`。
- “已定义应用/协议应用/应用”默认 `DefinedApp`。
- “自动识别的应用”是 `CompositeApplication`，通常属于元数据清单，不直接等同复杂分析对象。

## 7. 首版验收建议

首版实现可以先验收以下 P0 问题：

```text
1. 可观测239web 为什么慢？
2. 找到连接失败最多的地址，然后分析它。
3. 最近哪些业务系统异常？
4. Default-Internet 工作组整体情况怎么样？
5. 丢包最严重的 IP 是谁，为什么？
6. 哪个业务 HTTP 500 最严重，并分析原因。
```

每个问题验收点：

- 是否正确选择对象类型。
- 是否正确选择 overviewScene。
- 是否正确选择主指标和辅助指标。
- 是否正确使用 `napm-resolve-time-range` 生成时间。
- 是否在需要 discovery 时构造 `analysisPipeline.discoveryQuery`。
- discovery 结果是否能绑定到 focused overview。
- 输出是否包含结论、证据、时间范围、建议动作。
