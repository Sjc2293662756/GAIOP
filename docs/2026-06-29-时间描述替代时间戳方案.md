# 时间描述替代时间戳方案

日期：2026-06-29

## 一、核心原则

**LLM 只传时间描述（字符串），插件计算时间戳（Date.now()）。LLM 永远不碰 Unix 数字。**

## 二、LLM 传什么

```json
{
  "timeRange": {
    "key": "last1hour | last24hours | today | yesterday | last7days | last30days | custom",
    "displayText": "最近1小时"   // 可选，给用户看的
  }
}
```

`resolvedQuery` 里不再需要 `start`/`end` 字段。LLM 的工具定义里，这两个字段从 schema 中移除。

## 三、插件做什么

```
runSkillExecutor 中，payload 构建后:

1. 取 timeRange.key
2. 映射为时长:
     last1hour    → 3600s
     last24hours  → 86400s
     last7days    → 604800s
     last30days   → 2592000s
     today        → now - 今日00:00
     yesterday    → 昨日00:00 ~ 昨日23:59:00
     custom       → 尝试解析 displayText
     无/空        → 默认 last1hour
3. 计算: start = floorToMinute(Date.now()/1000 - duration)
         end   = floorToMinute(Date.now()/1000)
4. 注入 resolvedQuery.start / resolvedQuery.end
```

## 五、已有能力复用

| 能力 | 位置 | 状态 |
|------|------|------|
| key→时长映射 | 内联常量表 | 需写 ~10 行映射 |
| today/yesterday 动态计算 | 内联 Date 计算 | 需写 ~10 行 |
| 60s 边界对齐 | `roundToNearestMinute`（已有） | 复用 |

不需要新建文件，不需要加载新的依赖。所有逻辑内联在 `runSkillExecutor` 中。

## 六、边界场景处理

| 场景 | LLM 传 | 插件处理 |
|------|--------|---------|
| "最近1小时" | key="last1hour" | now-3600 → now |
| "今天" | key="today" | 今日00:00 → now |
| "昨天" | key="yesterday" | 昨日00:00 → 昨日23:59 |
| LLM 没传 timeRange | 无 | 默认 last1hour |
| LLM 传了 start/end | 仍保留 | 忽略，用 key 重新计算 |
| 综合分析/overview | key="last24hours" | 同样逻辑，overview 也用 start/end |

## 七、风险 = 零

| 之前的方案 | 本方案 |
|-----------|--------|
| LLM 算时间戳 → 可能错 | LLM 不碰时间戳 |
| 插件判断"是否覆盖" → 可能误判 | 插件总是计算，不需要判断 |
| custom 时间有容差风险 | LLM 传描述，插件解析，明确意图 |
| 覆盖后 displayText 不一致 | 直接从 key 生成 displayText，始终一致 |

## 八、现状确认

`ResolvedQueryTimeRangeService` 已有以下函数，本次实现内联等价逻辑：

```
resolveKnownTimeRangeKey(key):
  today       → 今日00:00 ~ 23:59
  yesterday   → 昨日00:00 ~ 23:59
  last1hour   → now-3600 ~ now
  last24hours → now-86400 ~ now
  last7days   → now-604800 ~ now
  last30days  → now-2592000 ~ now
```

内联实现的理由：插件和 skill 是独立进程，直接内联避免跨进程依赖。

## 九、验证方式

1. 部署后，用户问"最近1小时流量前20的IP"
2. 查审计日志，确认 `start`/`end` 在正确年份（2026）且差距 = 3600s
3. 重复 5 次不同时间范围的查询，确认时间戳始终正确
