# NAPM 业务指标查询误覆盖与重复提问修复方案

## 1. 问题范围

企业微信连续查询以下问题时，业务指标查询表现异常：

- `业务有哪些指标可以用？` 首次只返回“指标列表”。
- 相同问题再次提问时，返回“本轮未拿到有效 skill 结果”。
- 应用、网络、工作组指标查询在同一轮测试中可以正常返回。

本问题涉及 NAPM `metrics/metadata` 查询的结果输出和会话证据门禁，不是南向指标接口本身的查询失败。

## 2. 远端证据

### 首次业务指标查询

- 路由为 `napm_candidate`。
- `napm-skill-query` 实际收到 `service=metrics`、`groups=[WebApplication]`。
- Skill 返回 `ok=true`，共 26 条指标行。
- 模型轨迹中生成了完整的业务指标回答，但持久化的 assistant 消息被改写为“指标列表”。

### 第二次相同查询

- 路由仍为 `napm_candidate`。
- 本轮没有 `before_tool_call`，也没有新的 Skill 调用。
- 模型根据会话历史生成了回答，但当前轮没有可核验的 Skill 记录。
- 第一轮结果已经超过会话结果有效期，因此输出门禁返回“本轮未拿到有效 skill 结果”。

### 对比结论

应用、网络、工作组问题均在当前轮调用了 Skill，因此没有触发无结果门禁。业务问题的差异来自输出门禁和模型工具调用行为，不来自指标源数据。

## 3. 根因

### 3.1 业务对象清单规则误用于业务指标

`looksLikeInvalidBusinessInventoryAnswer()` 通过模型正文判断业务清单是否混入 `DefinedApp`。业务指标回答为了提示用户还可以查询应用指标，正文中出现了“DefinedApp”。

原规则同时命中“业务/WebApplication”和“DefinedApp”，在 `message_sending` 和 `before_message_write` 中将合法的 `metric_list` 正文误判为错误业务对象清单。

### 3.2 指标清单缺少确定性回退文本

指标叙述结构虽然包含 `rows` 和 `items`，但 `metric_list` 没有生成 `displayText`。输出门禁调用 `buildRememberedSkillReplyText()` 时，只能退化到 `summary.title`，所以最终只显示“指标列表”。

### 3.3 相同问题可以看到历史结果，但模型没有重新调用 Tool

模型提示要求使用当前轮 Tool 结果，但模型仍可能根据上一轮会话内容直接回答。旧实现按 prompt key 保存结果，在有效期内存在复用旧结果的路径；有效期过后则直接进入无结果门禁。

### 3.4 自由改写会造成指标代码错误

现场模型回答把“页面访问率”写成了 `PGNPGE`，而 Skill 源行实际返回代码是 `PGRT`。这说明指标清单不能完全依赖模型重新编排，代码、名称和单位必须以 Skill rows 为准。

## 4. 解决方案

### 4.1 门禁按结构化结果分域

业务对象清单保护规则只适用于：

- `service=groups`
- 对象类型为 `WebApplication`
- `responseType=group_list` 或等价的对象目录结果

`service=metrics`、`responseType=metric_list` 永远跳过业务对象清单正文校验。模型正文中出现 `DefinedApp`、`BusinessGroup` 等比较性说明，不再作为拒绝依据。

### 4.2 指标清单由 Skill rows 生成确定性文本

新增指标清单展示构造器，使用每一行的：

- `label`
- `id`
- `unit`

生成完整的对象范围、指标数量和逐项列表，并写入 `narrationStructure.displayText` 与 `summary.displayText`。在当前轮成功返回 `metric_list` 时，`message_sending` 和 `before_message_write` 直接采用这份确定性文本，模型不再拥有改写指标代码、名称和单位的权限；只有明确的指标详情追问才继续走上下文追问路径。

### 4.3 普通指标查询只信任当前 turn

相同的指标清单问题进入新 turn 后，不读取旧 prompt key 的结果。只有明确的“详细点”“继续展开”“重新发送上一结果”等上下文追问，才沿用上一轮指标结果。

如果当前轮没有新的 `napm-skill-query` 成功结果，输出门禁继续拒绝数据结论，不自动使用历史答案。

- `skills/openclaw-napm-query/services/OpenClawNarrationContractService.js`

  - 为 `metric_list` 补齐 `narrationStructure.displayText` 和 `summary.displayText`。
- `napm-openclaw-plugin.remote.js`
  - 新增结构化业务对象清单门禁范围判断。
  - `metrics` 结果不再触发业务对象清单误判。
  - 插件侧增加指标清单确定性回退，并在两个最终输出 Hook 中对当前轮成功的 `metric_list` 直接直出。

- `test/openclaw-narration-contract.test.js`
  - 验证指标代码、名称、单位来自真实 rows。
- `test/napm-openclaw-plugin-metric-inventory-guard.test.js`
  - 验证业务指标正文提到 `DefinedApp` 不会被覆盖。
  - 验证新 turn 没有 Skill 结果时不复用上一轮结果。

## 6. 验收标准

1. `业务有哪些指标可以用？` 返回完整的 WebApplication 指标清单，不再只显示“指标列表”。
2. 返回的指标代码和单位与 Skill rows 一致，不能出现 `PGRT` 被写成 `PGNPGE` 的情况。
3. 业务指标答案提到其他对象类型时，不触发业务对象清单门禁。
4. 业务对象清单仍能拦截 DefinedApp/Type=2 等错误对象解释。
5. 相同问题新 turn 未调用 Skill 时，不得复用上一轮查询结果。
6. 应用、网络、工作组指标查询保持原有行为。
7. 当前轮 `metric_list` 在流式发送和消息持久化两个出口均使用同一份 Skill rows 确定性文本。
