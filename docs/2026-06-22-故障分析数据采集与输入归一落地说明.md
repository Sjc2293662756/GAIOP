> 日期：2026-06-22
> 变更范围：`openclaw-napm-summary` + `openclaw-napm-report`

## 一、变更摘要

本次变更为故障分析报告补齐了**数据采集层**，使其能像综述报告一样端到端生成——从 NAPM API 查询到 `.docx` 文件全链路打通。

核心思路：**复用 `openclaw-napm-summary` 的流水线，新增 `fault` scope**。不新建 Skill，改动集中在 4 个文件约 250 行代码。

### 修改文件

| 文件 | 改动行数 | 说明 |
|------|---------|------|
| `skills/openclaw-napm-summary/services/SummaryService.js` | +200 | 新增 `fault` scope：`_planFault()` + `_aggregateFault()` + 辅助方法 |
| `skills/openclaw-napm-summary/services/SummaryReportDataService.js` | +75 | 新增 `buildFaultDiagnosisReportData()` — 输出 `diagnostic_report` 类型 |
| `skills/openclaw-napm-report/services/ReportInputContractService.js` | +85 | 新增 `isFaultDiagnosisSourceResult()` + `buildFaultDiagnosisReportData()` 归一化入口 |

### 不变文件

- `SummaryClient.js` — 无需改动，复用全部 NAPM API 方法
- `SummaryService.plan()` (其他 scope) — 逻辑完全不变
- `SummaryService.aggregate()` — 不受影响，fault 走独立聚合路径
- `ReportTemplateService.js` — 无需改动（上一轮已集成路由）
- `DiagnosticFixedTemplateService.js` — 无需改动

## 二、新增 `fault` scope

### 2.1 查询计划：`_planFault()`

放在 `SummaryService.plan()` 调度表中，和 `global` / `webApplication` 等 scope 并列：

```javascript
const plans = {
  // ... existing scopes ...
  fault: () => this._planFault(scope, timeRange, granularity)
};
```

查询层级：

| 层级 | 标签 | NAPM API | 指标 | 始终查询？ |
|------|------|---------|------|:--:|
| 1-告警 | `alertsSummary` | `getAlertsSummary` | — | ✅ |
| 1-告警 | `alertsTimeline` | `getAlertsTimeline` | — | ✅ |
| 2-流量 | `faultTrend` | `getTimeValues` | TPIO,TPI,TPO,PLI,PLO | ✅ |
| 2-流量 | `topIPs` | `getTopValues` | TPIO,TPI,TPO | ✅ |
| 2-流量 | `baselineTrend` | `getTimeValues` | TPIO,TPI,TPO | 基线窗存在时 |
| 3-业务 | `slowAccess` | `getTopValues` | PGSLPCT,PGNSLPGE,PGTME | focus=all/business 时 |
| 3-业务 | `httpErrors` | `getTopValues` | PGHTTP400,PGHTTP500 | focus=all/business 时 |
| 3-应用 | `appConnections` | `getTopValues` | CONI,CONO | DefinedApp/Application 目标时 |
| 3-应用 | `appFailures` | `getTopValues` | RFCO,RFCI | DefinedApp/Application 目标时 |
| 3-应用 | `appQuality` | `getTopValues` | PLI,PLO,RTTI,RTTO | DefinedApp/Application 目标时 |
| 4-设备 | `applianceInfo` | `getApplianceInfo` | — | ✅ |

最少 6 个查询，最多 10 个（含基线 + 应用质量 + 业务）。

### 2.2 时间范围特殊处理

故障分析的时间范围和综述不同——它支持**双窗口**：

```javascript
// 综述 — 单一窗口
timeRange = { start, end, displayText }

// 故障分析 — 故障窗 + 可选基线窗
timeRange = {
  faultWindow: { start, end },
  baselineWindow: { start, end },  // 可选
  displayText
}
```

`_resolveTimeRange()` 按 scope.type 分发：
```javascript
if (scope.type === 'fault' && input.faultWindow) {
  // 提取双窗口结构
  return { faultWindow, baselineWindow };
}
// 原有逻辑不变
return { start, end };
```

### 2.3 聚合逻辑：`_aggregateFault()`

两个关键增强：

**A. 降幅计算**（流量类故障的核心）

```
baselineAvg = avg(基线窗 TPIO)
faultMin = min(故障窗 TPIO)
dropPercent = (baselineAvg - faultMin) / baselineAvg × 100%

IF dropPercent > 60% → severity: "critical"
IF dropPercent > 30% → severity: "major"
IF dropPercent ≤ 30% → 不生成异常
```

**B. 异常检测 + 关联**

```
1. 流量突降检测 → fault window min vs baseline avg
2. 缺失点检测 → stats.missingPointCount > 0
3. 零流量检测 → stats.zeroSegmentCount > 0
4. 尖峰检测   → stats.spikeCount > 0
5. 告警关联   → critical > 0 AND anomalies > 0 → 强关联
```

**C. 自动生成 fault 元信息**

如果调用方未提供 `timeline` / `recommendations` / `prevention`，聚合逻辑自动从检测结果中生成：
- timeline — 从 `trafficAnalysis.anomalies` 提取
- recommendations — 从告警/流量/业务异常数量推导
- prevention — 通用预防建议

### 2.4 输出 schema

```json
{
  "ok": true,
  "schema": "openclaw_napm_fault_diagnosis_result.v1",
  "scope": { "type": "fault", "label": "故障分析", "focus": "all|traffic|business" },
  "timeRange": { "faultWindow": {...}, "baselineWindow": {...} },
  "fault": { "description": "...", "severity": "critical", "timeline": [...], "recommendations": [...], "prevention": [...] },
  "alertAnalysis": { "overallStatus": "critical", "summary": {...}, "timeline": [...] },
  "trafficAnalysis": { "trend": {...}, "baselineTrend": {...}, "topIPs": [...], "anomalies": [...] },
  "businessAnalysis": { "slowAccess": [...], "httpErrors": [...] },
  "reportData": null  // built downstream by SummaryReportDataService
}
```

与综述的 `summary` 单一对象不同，故障输出拆分为 4 个独立域 — 直接对应 `diagnostic_report` 的数据契约。

## 三、SummaryReportDataService 扩展

### 路由分发

```javascript
buildReportData(result, options) {
  if (scope.type === 'fault') {
    return this.buildFaultDiagnosisReportData(result, options);
  }
  // ... existing summary logic ...
}
```

### buildFaultDiagnosisReportData()

- 从 `result.fault/alertAnalysis/trafficAnalysis/businessAnalysis` 组装
- 将 `timeRange.faultWindow` 展平为模板需要的 `timeRange.start/end`
- 输出 `reportType: "diagnostic_report"`, `templateId: "napm_fault_diagnosis_v1"`
- 可选合并 `packetAnalysis`（从上游传入）

## 四、ReportInputContractService 扩展

### 检测函数

```javascript
function isFaultDiagnosisSourceResult(result = {}) {
  // 匹配条件（任一满足）：
  // 1. reportData.reportType === 'diagnostic_report' && templateId === 'napm_fault_diagnosis_v1'
  // 2. result.schema === 'openclaw_napm_fault_diagnosis_result.v1'
  // 3. narrationInput.schema === 'openclaw_napm_fault_diagnosis.v1'
  // 4. 同时存在 alertAnalysis + trafficAnalysis（推断为故障诊断结果）
}
```

### 构建函数

`buildFaultDiagnosisReportData()` 将非标准输入归一化为标准 `reportData`：
- 从 `result.fault` / `narrationInput.fault` 提取
- 从 `result.alertAnalysis` / `narrationInput.alertAnalysis` 提取
- 展平双窗口时间范围
- 通过 `templateId: "napm_fault_diagnosis_v1"` 路由到固定模板

### 归一化链位置

在 `normalizeReportInput()` 中的匹配顺序不变：`summary` → `fault` → `packet` → 回退。故障结果在 summary 之后、packet 之前检测。

## 五、调用方式

### CLI

```bash
# 流量类故障（无目标，全流量分析）
node skills/openclaw-napm-summary/scripts/run_summary.js --queryJson '{
  "scope": {"type":"fault","focus":"traffic","label":"故障分析",
    "fault":{"description":"核心交换机端口流量突降","severity":"critical"}},
  "timeRange":{
    "faultWindow":{"start":1780000000,"end":1780007200},
    "baselineWindow":{"start":1779913600,"end":1780000000}
  }
}'

# 业务类故障（指定目标应用）
node skills/openclaw-napm-summary/scripts/run_summary.js --queryJson '{
  "scope": {"type":"fault","focus":"business","label":"故障分析",
    "fault":{"description":"web-app-01慢访问率飙升","severity":"major"},
    "target":{"groupType":"WebApplication","groupArgument":"web-app-01"}},
  "timeRange":{
    "faultWindow":{"start":1780000000,"end":1780007200},
    "baselineWindow":{"start":1779913600,"end":1780000000}
  }
}'

# 全维度故障（默认 focus=all）
node skills/openclaw-napm-summary/scripts/run_summary.js --queryJson '{
  "scope":{"type":"fault","label":"故障分析"},
  "timeRange":{"start":1780000000,"end":1780007200}
}'
```

### OpenClaw 调用

OpenClaw 只需构造 scope + timeRange，调用 `openclaw-napm-summary`，然后用 `openclaw-napm-report` 生成 docx：

```json
// Step 1: 调用 openclaw-napm-summary
{
  "scope": { "type": "fault", "focus": "all", "label": "故障分析",
    "fault": { "description": "...", "severity": "critical" }
  },
  "timeRange": {
    "faultWindow": { "start": ..., "end": ... },
    "baselineWindow": { "start": ..., "end": ... }
  }
}
// → 返回 { alertAnalysis, trafficAnalysis, businessAnalysis, fault, ... }

// Step 2: 调用 openclaw-napm-report
// → 传入上一步的结果作为 sourceResult
// → ReportInputContractService 自动识别 schema 并归一化
// → DiagnosticFixedTemplateService 渲染 docx
```

## 六、兼容性

### 对现有功能的影响

| 功能 | 影响 |
|------|------|
| `global` / `webApplication` / `network` / `application` / `businessGroup` / `alert` scope | **零影响** — plan() 调度表仅新增，不改原有逻辑 |
| `SummaryService.aggregate()` | **零影响** — fault 走独立路径，不经过此方法 |
| `SummaryService._resolveTimeRange()` | **零影响** — 仅当 scope.type === 'fault' 且 input.faultWindow 存在时走新路径 |
| `ReportInputContractService.normalizeReportInput()` | **零影响** — fault 检测在现有匹配链之后，不影响已有优先级 |
| 已生成的 summary/docx 文件 | **零影响** — 不同 reportType / templateId |

### 新 scope 支持矩阵

```
summary scope: global webApplication application network businessGroup alert  → summary_report
fault scope:   fault                                                         → diagnostic_report
```

## 八、与模板层的完整链路

```
用户/OpenClaw
  │
  ├─ scope: { type: "fault", focus: "all", fault: {...} }
  ├─ timeRange: { faultWindow, baselineWindow }
  │
  ▼
SummaryService.run()
  ├─ _planFault()        → 7-10 次 NAPM API 查询
  ├─ execute()           → 并行执行
  └─ _aggregateFault()   → alertAnalysis + trafficAnalysis + businessAnalysis + fault
  │
  ▼
SummaryReportDataService.buildFaultDiagnosisReportData()
  → reportType: "diagnostic_report", templateId: "napm_fault_diagnosis_v1"
  │
  ▼
ReportInputContractService.normalizeReportInput()
  → 识别 schema → 归一化为标准 reportData
  │
  ▼
ReportTemplateService.renderDocx()
  → DiagnosticFixedTemplateService.renderDocx()
  → 6 章固定模板 .docx
```
