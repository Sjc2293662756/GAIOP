## 1. 验收目标

本文档把功能一首版能力转成可执行验收矩阵。

验收重点不是“能不能回答一句中文”，而是检查整条主链路是否稳定：

- OpenClaw 是否正确理解语义。
- 是否调用 `napm-resolve-time-range` 生成时间。
- 是否构造正确的 `resolvedQuery`。
- 是否正确区分普通查询、元数据查询、focused overview、discovery + overview。
- skill 是否按结构化查询执行。
- 最终输出是否符合 narration 契约，不泄露内部 fallback 或临时脚本。

## 2. 通用验收规则

### 2.1 时间规则

凡是执行类查询必须满足：

- `start/end` 位于 resolvedQuery 根层级。
- `start/end` 来自 `napm-resolve-time-range`。
- `resolutionHints.time.source === "time_range_resolver"`。
- `timeRange` 只保留 `key/displayText`，不携带 `start/end`。
- `discoveryQuery` 内不携带 `start/end/timeRange`。

元数据清单和下钻目录通常不需要时间。

### 2.2 对象规则

- 普通“业务”必须是 `WebApplication`。
- “业务组/工作组”必须是 `BusinessGroup`。
- “已定义应用”必须是 `DefinedApp`。
- “自动识别应用”必须是 `CompositeApplication`。
- “应用”单独出现时必须澄清口径，不能返回混合列表。

### 2.3 service 规则

| 问题类型 | 期望 service |
|---|---|
| 对象清单 | `groups` + `metadata` |
| 指标清单 | `metrics` |
| 下钻路径 | `drilldownCatalog` |
| TopN 排行 | `topValues` |
| 单对象综合分析 | `overview` |
| 先发现再分析 | `overview + analysisPipeline.discoveryQuery` |

### 2.4 输出规则

最终回答必须：

- 给出结论或明确说明无数据。
- 给出对象、指标、证据、时间范围。
- 元数据清单说明 provider 和 Type 过滤口径。
- 不暴露 curl、Python、8083、fallback、内部尝试过程。
- 不出现“当前问题必须经 NAPM skill 执行后才能回答”这类保护提示。
- 不编造原因，不把空结果直接解释为系统正常。

## 4. 详细用例

### P0-001：业务清单

用户：

```text
系统中有哪些业务？
```

期望 resolvedQuery：

```json
{
  "service": "groups",
  "queryModeKey": "metadata",
  "semanticConstraints": {
    "operation": "metadata_list",
    "targetObjectType": "WebApplication"
  },
  "groups": [
    { "type": "WebApplication" }
  ],
  "format": "json"
}
```

断言：

- 不使用 `overview`。
- 不使用 `drilldownCatalog`。
- 不使用 `BusinessGroup`。
- 不合并 `applications Type=2`。
- 输出说明 `applications Type=3`。

### P0-005：丢包 TopN

用户：

```text
最近一小时丢包最高的前 10 个 IP
```

期望调用顺序：

```text
napm-resolve-time-range(key=last1hour)
-> napm-skill-query(resolvedQuery)
```

期望 resolvedQuery：

```json
{
  "service": "topValues",
  "queryModeKey": "topn",
  "groups": [
    { "type": "IPAddress" }
  ],
  "metrics": ["PLI", "PLO"],
  "topMetric": "PLI",
  "topCount": 10,
  "start": "<from napm-resolve-time-range>",
  "end": "<from napm-resolve-time-range>",
  "timeRange": {
    "key": "last1hour",
    "displayText": "最近一小时"
  },
  "resolutionHints": {
    "time": {
      "source": "time_range_resolver"
    }
  },
  "format": "json"
}
```

断言：

- 不进入 `overview`。
- 不输出保护提示。
- 不暴露 Debug API，除非调试模式显式开启。

### P0-006：时间追问

上下文：

```text
用户：最近一小时丢包最高的前 10 个 IP
用户：最近一天的呢？
```

期望行为：

- 继承上一轮对象、指标、排行数量。
- 只把时间语义改成 `last24hours`。
- 重新调用 `napm-resolve-time-range(key=last24hours)`。
- 不复用上一轮 `start/end`。

期望 resolvedQuery 差异：

```json
{
  "service": "topValues",
  "groups": [
    { "type": "IPAddress" }
  ],
  "metrics": ["PLI", "PLO"],
  "topMetric": "PLI",
  "topCount": 10,
  "timeRange": {
    "key": "last24hours",
    "displayText": "最近一天"
  }
}
```

断言：

- 不能把追问判成非 NAPM 问题。
- 不能丢失上轮 `groups/metrics/topCount`。
- 不能由模型手算时间戳。

### P0-009：连接失败最多地址并分析

用户：

```text
找到连接失败最多的地址，然后分析它。
```

期望 resolvedQuery：

```json

  "service": "overview",
  "queryModeKey": "overview",
  "overviewScene": "network",
  "analysisPipeline": {
    "targetObjectType": "IPAddress",
    "selection": {
      "rank": 1
    },
    "discoveryQuery": {
      "service": "topValues",
      "queryModeKey": "topn",
      "groups": [
        { "type": "IPAddress" }
      ],
      "metrics": ["RFCI"],
      "topMetric": "RFCI",
      "topCount": 1
    }
  },
  "start": "<from napm-resolve-time-range>",
  "end": "<from napm-resolve-time-range>",
  "timeRange": {
    "key": "last1hour",
    "displayText": "最近一小时"
  },
  "format": "json"
```

断言：

- `analysisPipeline.targetObjectType === discoveryQuery.groups[0].type`。
- `discoveryQuery` 内没有 `start/end`。
- discovery 空结果时不继续 overview。
- 输出包含发现对象、发现依据、聚焦证据、建议动作。

## 6. 回归失败判定

出现以下任意情况，即视为验收失败：

- 返回“当前问题必须经 NAPM skill 执行后才能回答”。
- 用 curl、Python、临时脚本说明查询过程。
- 访问或提到旧网关端口 `8083`。
- `系统中有哪些业务` 返回 `Type=2 + Type=3` 混合结果。
- `自动识别应用` 返回吞吐排行，而不是 `CompositeApplication` 清单。
- `最近一天的呢` 丢失上一轮查询对象和指标。
- 执行查询中 `start/end` 是模型手算或明显漂移到错误年份。
- `discoveryQuery` 携带自己的 `start/end`。
- 最终输出没有时间范围。
- 空数据时编造原因或直接判断系统正常。
