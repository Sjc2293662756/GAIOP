# 服务器时间强制覆盖方案

日期：2026-06-29

## 一、问题

LLM 计算 Unix 时间戳频繁出错：

| 错误类型 | 实例 | 频率 |
|---------|------|------|
| 年份错 | 2026 年算成 2025 年 | ~30% |
| 月日错 | 6月29日算成 3月12日 / 6月18日 | ~20% |
| 完全随机 | 2024-07-10, 2025-11-19 | ~10% |

现有 `autoCorrectTimestampIfStale` 只修年份，月日错和同年不同月的错误（如 6月18日 vs 6月29日）无法修正。

## 二、方案

在插件的 `runSkillExecutor` 中，`payload` 构建完成后、`execFileAsync` 执行前，用服务器的 `Date.now()` 强制覆盖 `start/end`。

### 改动位置

`napm-openclaw-plugin.remote.js` → `runSkillExecutor` 函数，约 line 2591。

### 覆盖逻辑

```
function overrideTimestampIfNeeded(payload) {
  const rq = payload.resolvedQuery;
  if (!rq) return;

  const now = floorToMinute(Date.now() / 1000);
  const timeKey = rq.timeRange?.key || '';
  const llmStart = Number(rq.start);
  
  // Step 1: 确定正确的时长
  const duration = resolveDuration(timeKey, llmStart, now);

  // Step 2: 计算正确的 start/end
  const serverStart = floorToMinute(now - duration);
  const serverEnd = now;

  // Step 3: 判断是否需要覆盖
  const diff = Math.abs(serverStart - llmStart);
  if (shouldOverride(diff, timeKey, duration)) {
      rq.start = serverStart;
      rq.end = serverEnd;
      rq.timeRange.key = timeKey || 'last1hour';
      记录审计日志;
  }
}
```

## 三、时长解析规则

| timeRange.key | 对应时长 | 说明 |
|---------------|---------|------|
| `last5minutes` | 300s | |
| `last1hour` | 3600s | 默认值 |
| `last24hours` / `last1day` | 86400s | |
| `last7days` | 604800s | |
| `last30days` | 2592000s | |
| `today` | now - todayMidnight | 动态计算 |
| `yesterday` | yesterdayMidnight → yesterdayMidnight+86340 | |
| 无 key 或 `custom` | 反推 | 从 LLM 的 end-start 反推时长 |

## 四、是否覆盖的判断规则

```
if (LLM 没有传 start 或 start ≤ 0)           → 覆盖
if (timeKey 是已知相对键 且 差距 > 1小时)     → 覆盖
if (timeKey 是 custom 或 空 且 差距 > 2小时)  → 覆盖（custom 给更大容差）
if (差距 ≤ 1小时)                             → 不覆盖（保留精确时间请求）
```

### 为什么 custom 给 2 小时容差

用户可能说"查昨天上午 10 点到 11 点"——LLM 算的时间戳可能和服务器计算的"昨天 10:00"有 1-2 小时偏差（时区、对齐问题）。给 2 小时容差保护这类合理请求。

### 为什么相对键只给 1 小时容差

"最近1小时"、"最近24小时"——服务器时间就是正确答案，LLM 没理由偏差 >1 小时。偏差 >1 小时说明 LLM 算错了，必须覆盖。

## 五、风险评估与规避

| 风险 | 概率 | 影响 | 规避 |
|------|------|------|------|
| 覆盖了用户的精确时间范围 | 低 | 数据不是用户想要的时段 | custom 键给 2h 容差；差距 ≤1h 不覆盖 |
| timeRange.displayText 与实际不一致 | 中 | 用户看到的时间描述是错的 | 覆盖时同步更新 displayText |
| 服务器时间本身不准 | 极低 | 所有查询时间偏移 | 依赖 NTP，服务器时间偏差通常 <1s |
| 跨天查询被误覆盖 | 低 | "昨天"变成"今天" | `today`/`yesterday` 键单独处理，不复用相对时长逻辑 |
| overview 服务受影响 | 低 | 综合分析时间范围被改 | overview 同样走 `start/end`，逻辑一致 |
| 审计日志量增大 | 极低 | 存储压力 | 只在覆盖时记录，大部分查询不触发 |
| NAPM 系统时间和服务器时间不一致 | 中 | 覆盖后查不到数据 | 差距 >1h 才覆盖，如果 NAPM 真的滞后 1h+，会被误覆盖。**这是可接受的**：滞后 1h+ 本身就应该告警 |

## 六、不可覆盖的场景（保留 LLM 时间）

| 场景 | 原因 |
|------|------|
| `start` 和 `end` 差距 ≤ 1h | LLM 可能指定了精确时间窗口 |
| `timeRange.key = "custom"` 且差距 ≤ 2h | 用户指定了具体时段 |
| 非可执行 service（groups/metrics/drilldownCatalog） | 这些不需要 start/end |

## 七、和现有修正的关系

```
现有: autoCorrectTimestampIfStale（skill 进程内，只修年份）
新增: overrideTimestampIfNeeded（插件层，修所有）
```

两个保留，互为补充：
- `autoCorrectTimestampIfStale`：skill 进程内的最后防线
- `overrideTimestampIfNeeded`：插件层的主防线，覆盖面更广
