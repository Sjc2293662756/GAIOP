# 2026-05-07 企业微信 NAPM 直连逻辑下线与主链回收说明

## 一、本次调整目标

本次调整采用方案 B：

**直接下线企业微信插件中的 NAPM 直连逻辑，回到 OpenClaw 主链统一调度。**

也就是：

- 不再由企业微信插件抢先识别并直连 NAPM Skill
- 不再让企业微信插件直接把裸 `userQuery` 丢给 Skill
- 恢复为由 OpenClaw 主链负责理解自然语言、产出 `resolvedQuery`、再决定是否调用 Skill

## 二、为什么要这样改

### 1. 当前正式职责边界已经明确

当前项目正式职责边界是：

- OpenClaw：负责自然语言理解
- OpenClaw：负责产出结构化 `resolvedQuery`
- Skill：只负责消费 `resolvedQuery` 执行 NAPM 查询
- Skill：不再承担本地 prompt 解析责任

### 2. 企业微信插件中的 NAPM 直连逻辑已与当前职责边界冲突

原来的企业微信插件中有一段特殊逻辑：

- 在 `processWeComMessage()` 中
- 发送 thinking 消息后
- 先调用 `tryHandleNapmQuery(...)`
- 由该逻辑判断是否像 NAPM 问题
- 如果像，则直接 `requestNapmSkillQuery(...)`

问题在于：

当前 `requestNapmSkillQuery(...)` 传递的只有：

- `userQuery`
- `clarificationContext`
- `chatId`
- `sessionKey`
- `conversationId`

并没有传：

- `resolvedQuery`

于是链路变成：

1. 企业微信插件识别到像 NAPM 问题
2. 直接把原始自然语言扔给 Skill
3. 跳过 OpenClaw 应该负责的 `resolvedQuery` 生成步骤
4. Skill 因缺少 `resolvedQuery` 按契约失败

### 3. 这会引发“思考过程外露”

当 NAPM 直连失败时，旧链路会回退到通用 agent 或文本桥，最终把下面这类中间过程暴露给用户：

- 我先试试
- 让我看看
- 根据 skill 文档
- 密码需要 URL 编码
- 返回 400 / 403

这些都不是正式的最终答复，而是异常回退副作用。

## 三、为什么选择“下线直连逻辑”，而不是继续补这条链

从当前远端代码可见，企业微信插件现有能力中：

- 有 `runOpenClawPrompt(prompt)`  
  这个桥拿到的是自然语言文本回复

但是没有现成的：

- 结构化 `resolvedQuery` 获取桥
- 结构化 `decision / intent / session` 获取桥

因此如果继续保留企业微信插件中的 NAPM 直连逻辑，就必须额外补一套：

1. 调 OpenClaw 产出结构化 NAPM 结果
2. 读取 `resolvedQuery`
3. 再转调 Skill

这会继续把 NAPM 专用调度逻辑滞留在企业微信插件层。

相比之下，直接回到 OpenClaw 主链统一调度更干净：

- 责任边界清晰
- 插件不再承担 NAPM 特殊逻辑
- 避免两套调度路径并存

## 四、本次实际改动

### 1. 下线企业微信插件中的 NAPM 直连入口

原主流程位于企业微信插件的 `processWeComMessage()` 中：

```js
const napmHandled = await tryHandleNapmQuery({...});
if (napmHandled) {
  cleanupState();
  return;
}
```

本次已将其从主流程中摘除。

现在消息流程改为：

1. 企业微信收到消息
2. 解析文本 / 图片 / 文件 / 引用
3. 群策略 / 私聊策略检查
4. 下载媒体
5. 初始化消息状态
6. 发送 thinking 消息
7. **直接进入 `buildMessageContext(...)`**
8. **直接走 `routeAndDispatchMessage(...)`**
9. 由 OpenClaw 主链统一处理

### 2. 保留“过程性内容外露保护”

虽然本次已下线 NAPM 直连主入口，但此前做的保护仍有价值，已保留：

- 若结果润色返回明显过程文本，则拒绝采用
- 避免“我先试试 / 让我看看 / URL 编码 / 返回 400”等过程语句直接暴露给用户

## 五、当前链路变化

### 调整前

```text
企业微信消息
  -> processWeComMessage
  -> tryHandleNapmQuery
  -> requestNapmSkillQuery(userQuery)
  -> Skill
  -> 失败后回退 / 暴露过程
```

### 调整后

```text
企业微信消息
  -> processWeComMessage
  -> buildMessageContext
  -> routeAndDispatchMessage
  -> OpenClaw 主链
  -> OpenClaw 负责理解并生成 resolvedQuery
  -> Skill（如需）
```

## 六、本次调整带来的直接好处

### 1. 责任边界重新一致

- 企业微信插件不再决定 NAPM 如何特判执行
- OpenClaw 重新成为统一语义理解和 Skill 调度入口

### 2. 消除“裸 userQuery 直塞 Skill”的违约调用

Skill 不再被错误调用为：

- `requestNapmSkillQuery({ userQuery })`

从而避免继续和“Skill 只吃 resolvedQuery”的正式契约冲突。

### 3. 降低过程性内容外露概率

由于不再先走那条半截的 NAPM 直连链路，原来那种“先直连失败，再自由发挥”的问题会明显减少。

## 七、需要注意的现实影响

### 1. 企业微信中的 NAPM 查询不再走旧直连快车道

也就是说：

- 响应路径回到主链
- NAPM 问题将和其他问题一样先经过 OpenClaw 主链统一判断

### 2. 后续 NAPM 表现是否正确，取决于 OpenClaw 主链是否稳定产出 `resolvedQuery`

本次只是把错误的企业微信侧“特判直连”收掉，
并不代表所有 NAPM 问答立刻全部变好。

真正后续需要观察的是：

- OpenClaw 主链是否能稳定识别 NAPM 问题
- 是否能稳定产出正确的 `resolvedQuery`
- 是否能再正确调用 Skill

## 九、最终结论

本次改动的本质不是“修一个小 bug”，而是：

**把原先前置在企业微信插件里的 NAPM 特殊调度逻辑收回，恢复到 OpenClaw 主链统一负责语义理解与 Skill 调度。**

这一步的意义在于：

1. 重新对齐职责边界
2. 消除企业微信插件对 Skill 的违约调用
3. 避免 Skill 缺少 `resolvedQuery` 时异常回退
4. 减少过程性思考内容向用户侧泄漏
