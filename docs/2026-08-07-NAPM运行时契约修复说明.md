# NAPM 运行时契约修复说明

日期：2026-08-07  
适用范围：`napm-skill-query`、`napm-packet-analysis`，以及全部七个生产 NAPM 工具的加载、发布和回归校验。

## 1. 现象与根因

用户查询“最近丢包较大的前 10 个 IP 都有哪些？”时，工具调用失败：

```text
napmQuerySkill(...).handleSkillCall is not a function
```

NAPM OpenClaw 插件已使用进程内 `require()` 加载每个 Skill，并以 `runtime.handleSkillCall(params)` 执行。查询脚本仅导出了 `__test__`，抓包脚本既没有导出 `handleSkillCall`，又会在被 `require()` 时立即启动 CLI `main()`。因此这不是 NAPM 数据、模型理解或查询参数问题，而是插件调用端与 Skill 运行时入口之间的接口契约不一致。

该问题不只影响当前查询：任何进入 `napm-skill-query` 的有效请求都会在执行阶段失败；任何进入 `napm-packet-analysis` 的请求也会出现同类加载风险。

## 2. 修复策略

1. 将查询和抓包脚本拆为“可复用业务执行函数 + CLI 外壳”。业务函数返回结果对象；仅 CLI 外壳负责 JSON 标准输出和退出码。
2. 两个脚本均导出异步 `handleSkillCall(params)`，接收插件提供的普通 JavaScript 对象，不要求调用方重新序列化为 CLI JSON。
3. 查询入口兼容对象形式的 `resolvedQuery`、`decision`、`intent`、`sessionState`，并将异常转换为既有的受控 OpenClaw 回复结构。
4. 抓包入口仅在 `require.main === module` 时执行 CLI；插件入口合并 `packetQuery`、顶层 `mode`/`downloadType`、`criteria`、`analysis`、`filePolicy`，并复用既有校验与安全 URL 构造。
5. 增加七个生产 NAPM 工具的统一运行时清单。清单与 `openclaw.plugin.json` 中的生产工具必须一一对应，每个脚本都必须能被加载并导出 `handleSkillCall`。
6. 新增部署前命令 `npm run verify:runtime-contract`。该命令可通过 `OPENCLAW_SKILLS_ROOT` 指向实际测试服务器 Skill 根目录；任何入口文件、共享模块、依赖或导出缺失都会阻止重启。

## 3. 本地发布包完整性

统一检查还发现本地工作区缺少两个远端已使用的共享模块和报告依赖：

- `skills/openclaw-napm-query/src/shared/timeResolver.js`
- `skills/shared/ExecutionOutcome.js`
- `docx@9.7.1`

这说明此前本地工作区不能代表可发布运行时。已以测试服务器运行版本为基线补齐共享模块，并在根 `package.json` 声明 `docx`。这不是把检查放宽，而是把发布输入补完整，使本地、测试服务器执行同一份运行时契约。

## 4. 回归覆盖

- `test/napm-skill-runtime-contract.test.js`：查询对象参数执行、抓包 URL 构造、无网络依赖。
- `test/napm-openclaw-plugin-runtime-contract.test.js`：从插件注册工具到进程内查询 Skill 的完整调用路径。
- `test/napm-skill-runtime-contract-registry.test.js`：manifest 与七工具运行时清单一致，并验证全部模块可加载且导出入口。
- `scripts/verify-napm-skill-runtime-contract.js`：发布前或重启前针对实际 Skill 根目录执行的独立烟测。

## 5. 部署与验收

部署前必须备份测试服务器当前的查询、抓包脚本和相关共享模块。随后部署本地已验证的运行时文件，在重启 `openclaw-gateway.service` 前执行：

```powershell
$env:OPENCLAW_SKILLS_ROOT = '/home/netinside/.openclaw/workspace/skills'
node scripts/verify-napm-skill-runtime-contract.js
```

验收要求：

1. 七个生产工具全部显示 `ok: true`。
2. 网关重启后保持 `active`。
3. 真实普通查询“最近丢包较大的前 10 个 IP 都有哪些？”完成工具调用，不再出现 `handleSkillCall is not a function`。
4. 抓包工具可通过进程内入口生成受控 URL，且 `require()` 本身不触发下载、预览或分析。

## 6. 影响边界

本方案解决的是所有遵循 NAPM OpenClaw 进程内 Skill 调用模型的“运行时入口/依赖/发布包不一致”问题，而非只对当前丢包查询打补丁。它不会替代独立的数据口径、NAPI 可用性、模型路由或报告内容质量测试；这些问题会以各自的业务错误返回，但不再因脚本接口缺失而在执行边界直接崩溃。
