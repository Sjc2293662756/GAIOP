# NAPM 意图与轮次决策模块阶段一设计方案

日期：2026-08-28
状态：架构设计完成，代码尚未实施；本文档产生于 `rc.37` 部署后，仅作为后续 `rc.38` 整合输入
基线：`main` / `v1.1.0-rc.37`，远端测试服务器当前运行 `1.1.0-rc.37`
范围：NAPM 用户问题意图识别、轮次决策、OpenClaw Hook/Tool/Skill 生命周期协作及相关测试

## 1. 背景

当前 NAPM 链路已经具备参数、时间、对象和南向执行边界校验，但“用户这一轮到底要做什么”仍由多个位置分别推断：

- `PromptRoutingService` 判断是否属于概览或 NAPM 问题；
- `WorkflowClassifierService` 判断趋势、排行等工作流；
- 插件自身通过正则判断应用趋势、概览和语义错配；
- `NapmResolvedQueryResolverService` 根据部分证据构造 `resolvedQuery`；
- `ClarificationGateService` 在 Skill 已收到 `resolvedQuery` 后判断参数是否需要澄清；
- `before_message_write` 根据“是否调用过 Skill”猜测最终消息是否可信。

这些判断没有共享的本轮状态，因此可能出现以下问题：

1. 用户问“最近 7 天应用流量趋势如何”，但没有提供应用名称；模型原本已经正确追问，消息守卫却因为本轮没有 Skill 结果而覆盖追问。
2. “应用流量趋势”被错误构造成 `TotalTraffic`，只能在 Tool 或 Skill 边界被事后拦截，无法在模型调用前形成明确澄清。
3. 同一 session 的多个 run 只依赖 latest cache 或 prompt 重新匹配，结果和失败状态存在串线风险。
4. “没有工具结果”同时可能表示尚未调用、模型已澄清、工具失败或合法空结果，现有状态无法区分。

## 2. 设计目标

阶段一的目标是建立两个相互衔接、职责清晰的单一事实源：

```text
Monitoring Question
        |
        v
Intent Decision Module
        |
        v
Turn Decision Module
        |
        v
Hook / Tool / Resolver / Skill adapters
```

具体目标：

1. 将自然语言问题归一为稳定的意图事实，不再继续增加并行 regex 特例。
2. 在 `message_received` 首轮创建本轮决策，必要时在 Tool 调用前就决定“执行”或“澄清”。
3. 将“决策状态”和“执行生命周期”分离，避免把澄清、失败、成功空结果混为“无结果”。
4. 让 Hook、Tool、Skill 只转换事件、执行校验和推进状态，不重复推断本轮意图。
5. 保留现有 `ResolutionSpecService.evaluateQueryArgumentPolicy` 作为最终执行契约。
6. 先补齐真实插件生命周期测试，再考虑发布和部署；阶段一不改变当前远端 `rc.37`。

## 3. 非目标与约束

阶段一暂不做以下事情：

- 不删除现有 `ClarificationGateService`，也不改变现有 Skill 参数和时间校验契约。
- 不允许模型或插件通过默认值猜测缺失的应用名称。
- 不把多对象趋势自动套用单对象趋势规则。
- 不直接把所有 Hook 改造成只读消息发送层；这属于后续显式 resultId/reportId 阶段。
- 不在本阶段部署远端、重启 Gateway 或替换线上 `rc.37`。

## 4. 统一意图模型

### 4.1 Intent Decision 输入

`Intent Decision Module` 是纯决策模块，输入应包含：

```text
Monitoring Question
当前 sessionKey / runId
可用的对象、指标、时间范围和查询模式证据
可选的 resolvedQuery
必要的上游结构化字段
```

模块可以消费现有分类器产生的事实，但不能再复制一套独立 regex。现有 `PromptRoutingService` 和 `WorkflowClassifierService` 的判断应逐步收口到该接口。

### 4.2 意图优先级

所有分类必须采用固定 precedence，避免“通用怎么样”抢在更具体的查询语义之前：

1. 明确的全局、整体、总体或总流量查询；
2. 明确名称的对象查询；
3. 单对象查询与对象发现/枚举的区分；
4. 趋势或时间序列；
5. 平均值；
6. 通用“怎么样”或概览表达。

趋势和平均值必须先于通用“怎么样”判断。明确的对象范围优先于泛化的概览词。

### 4.3 意图闭合度与 query policy

意图决定不能只返回 `service`，还必须判断当前问题的信息是否足够执行。该判断由配置驱动的 query policy 表达：

```text
workflowType + objectType + operation
        -> scope requirement / argument policy / supported state
```

目标口径如下：

| 用户语义 | 意图结果 | 执行策略 |
| --- | --- | --- |
| 全局、整体、总流量趋势 | `TotalTraffic` + 时间序列 | `execute`，禁止附带对象参数 |
| 明确具体应用的趋势/平均值 | `DefinedApp` + `argument` | `execute` |
| 应用趋势/平均值但无应用名称 | 单对象应用意图未闭合 | `clarification`，不得调用 Tool |
| 应用排行、TopN、对象清单 | 发现/枚举意图 | `execute`，对象参数可选 |
| 多个应用各自趋势 | 多对象时间序列 | 当前契约未闭合，`clarification` 或 `reject/unsupported` |
| 域外问题 | 非 NAPM 意图 | `reject` 或 `model_owned`，不得强制 NAPM Skill |

`ResolutionSpecService.evaluateQueryArgumentPolicy` 仍是执行阶段的最终判断：即使上游意图判断错误、绕过 Hook 或直接调用 Skill，执行契约仍必须拒绝非法 `TotalTraffic` 参数和缺失的 `DefinedApp` 参数。

## 5. Turn Decision 状态模型

### 5.1 决策状态

`decision` 表示本轮应该采取的用户交互策略：

```text
model_owned       非 NAPM 或允许模型直接回答
execute           允许调用 NAPM Skill/Tool
clarification     需要向用户补充信息，可直接澄清
reject            请求不属于支持范围或违反边界
```

为兼容现有调用方，可以暂时保留 `decision.next_action`，但新增规范字段 `decisionState` 或 `turnOutcome`，所有 adapter 最终使用规范字段。

### 5.2 执行生命周期

`lifecycle` 表示本轮执行到了哪一步，与 `decision` 分开保存：

```text
pending       当前轮尚未完成
tool_called   已发起 Tool/Skill 调用
succeeded     已获得成功结果，包括合法空结果
failed        执行失败或契约拒绝
```

`pending` 不是用户可见结果。对于 `decision=execute` 且 `lifecycle=pending` 的本轮，`before_message_write` 不得把模型内容替换成通用失败文案。

### 5.3 状态与证据

决策记录至少应包含：

```text
sessionKey
runId
decisionState / turnOutcome
lifecycle
reason
evidence
nextAction
queryPolicy
resolvedQuery（可空）
toolCallId / resultId（可选）
failureCode（可选）
```

状态必须按 `sessionKey + runId` 绑定，不能只依赖“最近一次 prompt”或全局 latest record。

## 6. 模块职责

### 6.1 Intent Decision Module

职责：

- 消费统一的 Monitoring Question 和已有分类事实；
- 按固定 precedence 判断 workflow、object、operation 和 scope；
- 判断意图闭合度；
- 输出可执行策略和缺失证据；
- 不执行南向请求，不发送用户消息。

### 6.2 Turn Decision Module

职责：

- 在首轮创建 turn decision；
- 接收 prompt、resolvedQuery、tool lifecycle、model candidate 等事件；
- 按规则推进 `decision` 和 `lifecycle`；
- 为所有 Hook/Tool/Skill adapter 提供同一份本轮事实；
- 输出 reason、evidence、nextAction 和 queryPolicy。

### 6.3 ClarificationGateService

保留该模块，但深化其 interface：

- 只负责根据已构造的 query、解析证据和 policy 生成 gate evidence；
- 不决定 Hook 是否必须调用 Skill；
- 不负责覆盖模型消息；
- 由 Turn Decision Module 消费其 gate 结果，统一决定 `clarification`、`reject` 或 `execute`。

### 6.4 Hook adapters

Hook 只负责事件转换和交付：

| Hook | 阶段一职责 |
| --- | --- |
| `message_received` | 创建当前 `sessionKey + runId` 的 turn decision |
| `before_prompt_build` | 注入决策结果；澄清状态明确提示“本轮不得调用 Tool” |
| `before_tool_call` | 将模型工具调用转换为事件；执行边界校验；不重新推断意图 |
| `after_tool_call` | 写入 `tool_called/succeeded/failed` 生命周期事件 |
| `Skill.execute` | 执行最终契约校验并推进状态；不能绕过 policy |
| `before_message_write` | 根据决策和生命周期确定性地保留、交付或输出失败 |

### 6.5 `before_message_write` 交付规则

必须停止使用以下逻辑作为唯一依据：

```text
NAPM prompt + rememberedRecord == null -> generic guard
```

改为按显式状态处理：

| decision | lifecycle | 交付行为 |
| --- | --- | --- |
| `clarification` | `pending` | 保留并交付经过验证的澄清文本 |
| `execute` | `pending` / `tool_called` | 不将当前内容改写成 generic failure |
| `execute` | `succeeded` | 交付结果 |
| `execute` | `failed` | 交付确定性的失败文案 |
| `reject` | 任意终态 | 交付范围或参数拒绝说明 |
| `model_owned` | 任意 | 保留模型自主回答 |

澄清文本应通过 `isValidClarificationText` 或等价验证器确认其确实回答了缺失条件，不能只要出现问号就放行。

## 7. 典型流程

### 7.1 缺少应用名称的趋势问题

```text
用户：最近 7 天应用流量趋势如何？
  -> Intent Decision：单对象应用趋势，scope 未闭合
  -> Turn Decision：decision=clarification, lifecycle=pending
  -> before_prompt_build：明确不得调用 Tool，只询问应用名称
  -> 模型：请提供具体应用名称
  -> before_message_write：保留澄清，不触发 generic guard
```

### 7.2 明确总流量问题

```text
用户：最近 7 天总体流量趋势如何？
  -> Intent Decision：全局流量趋势
  -> Turn Decision：decision=execute, lifecycle=pending
  -> Tool/Skill：执行 TotalTraffic，禁止附带 argument
  -> after_tool_call：succeeded 或 failed
  -> before_message_write：交付结果或确定性失败
```

### 7.3 错误的 TotalTraffic 参数

```text
错误 resolvedQuery：TotalTraffic + argument=HTTP
  -> Intent/Turn Decision：拒绝或标记不一致
  -> before_tool_call：阻断
  -> Skill.execute：ResolutionSpec 再次阻断
  -> 南向调用次数：0
```

## 8. 实施阶段

### 阶段一：决策契约与状态仓库

1. 定义 `IntentDecision`、`TurnDecision`、事件和状态迁移契约。
2. 实现纯函数式 `Intent Decision Module`，优先复用现有分类事实。
3. 实现 `Turn Decision Module` 和按 `sessionKey + runId` 存取的状态仓库适配。
4. 将 `ClarificationGateService` 调整为 evidence builder，不改变现有执行校验。
5. 先接入测试用 adapter 或最小 Hook 读写路径。

### 阶段二：插件生命周期接入

1. 接入 `message_received`、`before_prompt_build`、`before_tool_call`、`after_tool_call`。
2. 将 `Skill.execute` 和 `before_message_write` 改为读取统一决策。
3. 删除或停用 `shouldRequireSkillBackedReply`、`shouldForceSkillRecordForPrompt`、`derivePromptGuardState` 等重复猜测路径。
4. 保留必要的兼容字段和观测日志，便于灰度验证。

### 阶段三：结果关联与长期演进

后续再考虑显式 `resultId/reportId`、去除 latest cache，以及让 Tool 返回最终可交付内容。该阶段不属于本次第一阶段范围。

## 9. 测试计划

### 9.1 纯决策契约测试

- 全局/整体/总流量优先于通用“怎么样”；
- 趋势和平均值优先于通用概览；
- 缺少单对象名称时返回 `clarification`；
- 明确应用名称时返回 `execute + DefinedApp + argument`；
- 排行/清单返回 `execute`，对象参数按 policy 可选；
- 多对象趋势在契约未闭合时不得套用单对象规则；
- 域外问题返回 `model_owned` 或 `reject`。

### 9.2 状态迁移测试

- `message_received -> clarification/pending`；
- `message_received -> execute/pending -> tool_called -> succeeded`；
- `execute/pending -> failed`；
- `reject` 不得进入 Tool 调用；
- `pending` 不得被当成用户结果；
- 同一 session 多个 run 的结果和失败不串线；
- 重叠 run 使用各自 `runId` 独立决策。

### 9.3 插件生命周期端到端测试

- 模型不调用 Tool 但产出正确澄清，`before_message_write` 原样保留；
- 模型不调用 Tool 且输出无依据数据断言，仍触发确定性保护；
- `api.on` 的 Typed Hook 真实注册并能接收 `after_tool_call`；
- Tool 调用被阻断时南向调用次数为 `0`；
- Skill 直达执行仍受 `ResolutionSpecService` 约束；
- 合法总流量和具体应用查询仍可执行；
- 合法空结果与执行失败使用不同生命周期和交付文案。

### 9.4 现有测试保持不变的范围

阶段一不得削弱现有覆盖：

- `test/query-argument-policy.test.js`；
- `test/napm-openclaw-plugin-trend-query-context.test.js`；
- `test/napm-resolved-query-resolver-service.test.js`；
- `test/run-napm-query-input-contract.test.js`；
- 现有全量测试、lint 和 runtime contract 检查。

## 10. 验收标准

阶段一只有同时满足以下条件，才可进入发布候选：

1. 无 Tool 调用但模型正确澄清时，澄清内容被原样交付，并记录 `decision=clarification`。
2. 无 Tool 调用且模型输出无依据数据断言时，不得被误认为合法澄清。
3. 错误 `TotalTraffic` 调用在 Tool/Skill 边界均被阻断，南向调用次数为 `0`。
4. 明确总流量仍能执行 `TotalTraffic`；明确应用仍能执行 `DefinedApp + argument`。
5. `pending` 不再触发 generic guard 覆盖模型内容。
6. 工具失败、成功空结果和模型澄清在状态与交付文案上可区分。
7. 同一 session 的不同 `runId` 不串状态。
8. 全量测试、lint、runtime contract 和新增生命周期测试全部通过。

## 11. 版本与部署边界

当前基线保持不变：

```text
main                  -> v1.1.0-rc.37
远端测试服务器          -> 1.1.0-rc.37
```

实施阶段应从 `main@rc.37` 创建独立分支，例如：

```text
codex/napm-turn-decision-phase1
```

阶段一完成后，必须经过新的整合分支、全量验证和唯一发布包流程，才能申请新的版本号（例如 `rc.38`）。在此之前：

- 不直接修改 `main`；
- 不从旧目录 `skill_project` 或 `project_3` 部署；
- 不逐文件上传服务器；
- 不覆盖当前远端 `rc.37`；
- 不因本地测试通过而跳过远端 staged、dry-run 和部署后验收。

本文档及其后续实现不得重新标记、打包或部署为 `rc.37`。代码实施完成后，由唯一整合部署任务统一纳入 `rc.38` 或更高版本。

## 12. 当前结论

本文件记录的是阶段一实施规格，不代表功能已经实现。当前已完成的是架构走查、问题定位、状态模型和测试计划；代码修改、新版本构建及远端部署均尚未开始。本设计文档是在 `rc.37` 部署后新增的仓库变更，后续只能由整合任务纳入 `rc.38` 或更高版本。
