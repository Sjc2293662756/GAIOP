# 业务清单首答旁路强制拦截说明

## 现象

用户清理会话后再次询问：

```text
系统中有哪些业务？
```

线上仍回答：

```text
系统中"业务"相关共 14个
Web业务应用（9个）
自定义业务应用（5个）
查询方式：直接调用后端 type=applications API -> python按type字段过滤 -> 未经过中间管道
```

## 判断

这不是单纯的会话缓存问题。

根因是首答阶段仍可能出现两种漂移：

1. 模型绕过标准链路，选择 `curl/API/exec/python` 等临时方式查数据。
2. 模型没有真实执行旁路工具，但在最终回答里编造了“直接 API + python 过滤”的查询过程。

无论是哪一种，最终用户看到的内容都违反生产链路：

```text
OpenClaw 构造 resolvedQuery
  -> napm-skill-query
  -> MetadataExecutionKernel
  -> NapmMetadataService
  -> applications Type=3
  -> narration contract
```

## 正确语义

“系统中有哪些业务？”只表示：

```text
WebApplication / 业务系统 / applications Type=3
```

不能合并：

```text
DefinedApp / 已定义应用 / applications Type=2
```

因此以下回答口径是错误的：

```text
Web业务应用 Type=3 + 自定义业务应用 Type=2 = 业务相关 14 个
```

## 修改内容

### 1. 输出层识别错误业务清单首答

新增 `looksLikeInvalidBusinessInventoryAnswer()`，拦截以下内容：

- `自定义业务应用`
- `type=2` / `Type=2`
- `DefinedApp` / `已定义应用`
- `Web业务应用 ... 自定义业务应用`
- `业务相关 14 个`
- `python 按 type 字段过滤`
- `exec 工具`
- `直接调用后端`
- `直接从API`
- `未经过中间管道`
- `没有经过 napm-skill-query`

命中后：

- 如果有可核验的当前 skill 记录，替换为 skill 结果。
- 如果没有 skill 记录，替换为“必须先通过 NAPM skill 执行”的边界回复。

### 2. 对对象清单类问题强制要求 skill 记录

新增 `shouldForceSkillRecordForPrompt()`。

以下问题类型必须存在当前 skill 记录才允许最终回答：

- 业务清单
- 工作组/业务组清单
- 自动识别应用清单
- 指标清单
- 指标明细
- 下钻目录
- NAPM 查询过程追问

这可以防止首答阶段在未执行主链路时直接给出“看起来像答案”的内容。

### 3. 强化系统提示约束

在 NAPM routing system context 中增加：

```text
Never answer "系统中有哪些业务" by merging applications Type=2 and Type=3.
Type=2 is DefinedApp/已定义应用, not WebApplication/业务系统.

Never claim that business inventory was queried by direct curl/API, exec,
python filtering, raw backend probing, or by bypassing napm-skill-query.
```
