## 1. 文档目的

本文集中记录“最近 7 天应用流量趋势如何？”这一问题在多轮实测、代码审查和复审中暴露的全部查询链路问题，以及最终采用的整体修复方案。

本文不是部署记录，也不是临时补丁说明。它用于：

1. 固化每个问题的复现路径、影响、根因和最终处理；
2. 说明各模块当前唯一职责，避免再次产生多套状态和语义判断；
3. 给整合、回归和正式部署提供可检查的验收基线；
4. 记录仍然存在的边界和后续风险。

## 2. 总体结论

初始故障看起来是“应用”关键词没有识别，实际由四类系统性缺陷叠加造成：

- Query Draft 没有统一的执行前决策，缺参数、范围错配和结构错误可能直接进入 Query Skill；
- 同一查询的轮次、修复、结果和最终交付由多个状态源共同决定；
- Hook 和 direct execute 的校验边界不一致，可通过不同入口绕过；
- 应用流量语义在多个模块中用独立正则重复识别，规则会漂移。

最终方案不是继续增加关键词补丁，而是建立以下单一主链：

```text
Monitoring Question
  -> immutable run/message binding
  -> Query Draft or clarificationAnswer
  -> QueryDecisionPolicy
       -> CLARIFICATION / REJECTION: local terminal, zero southbound
       -> EXECUTE_QUERY: complete Resolved Query only
  -> QueryTurnCoordinator
       -> Attempts / repair budget / terminal finalContent / delivery claim
  -> Query Skill -> NapmClient -> NAPM, only when execution is authorized
  -> run-bound exactly-once final delivery
```

## 4. 对象与意图语义问题

### SEM-01 未命名应用趋势被当成可执行查询

复现：

```text
用户：最近 7 天应用流量趋势如何？
错误 Draft：timeValues + DefinedApp（无 argument）+ TPIO
旧行为：执行查询并返回空数据，或者由后续兜底生成失败答复
```

影响：

- `DefinedApp` 单对象趋势缺少具体对象名称，查询本身没有完整语义；
- 空结果被误解释为真实 `NO_DATA`；
- 用户得不到“请提供应用名称”的正常追问。

根因：缺少一个在 Query Skill 前区分“用户缺参数”和“技术校验失败”的统一决策层。

最终修复：

- `ResolutionSpecService.evaluateQueryArgumentPolicy()` 统一声明参数 required/optional/forbidden；
- `DefinedApp`、`WebApplication` 的单对象 `timeValues/averageValues` 缺 argument 时返回 `ASK_CLARIFYING_QUESTION`；
- 澄清为 `ok=true`、`isError=false` 的正常终态；
- Query Skill、NapmClient 和南向调用均为 0。

回归：`query-decision-policy.test.js`、`napm-openclaw-plugin-query-turn-integration.test.js`。

### SEM-02 应用流量趋势错误落到 TotalTraffic

复现：

```text
用户：最近 7 天应用流量趋势如何？
错误 Draft：timeValues + TotalTraffic + TPIO
旧行为：查询到真实全局流量，并以“应用流量”口径回答
```

影响：返回的数据真实但对象范围错误，比空结果更危险；用户会把全局流量误认为应用流量。

根因：构造层把“应用流量”当成“总流量”，执行层没有核对 Monitoring Question 与 Query Draft 的对象范围一致性。

最终修复：

- Query Decision 在 Hook 和 direct execute 中统一检查对象范围；
- 趋势/平均值错配返回正常澄清，并把 pending Draft 规范化为无 argument 的 `DefinedApp`；
- 只有明确的总流量/全局流量意图才允许 `TotalTraffic`；
- `TotalTraffic` 禁止携带 argument。

回归：应用趋势错配、无 prompt 但 `semanticConstraints.targetObjectType=DefinedApp` 的 direct execute 均验证零南向调用。

### SEM-03 应用流量排行错误使用 TotalTraffic

复现：

```text
用户：应用流量最高的是哪些？
错误 Draft：topValues + TotalTraffic
```

影响：`TotalTraffic` 是单一全局范围，不能回答“哪些应用”的对象排行。

根因：早期范围错配规则只覆盖趋势/平均值，没有覆盖 `topValues`。

最终修复：

- 应用排行必须使用 `topValues + DefinedApp`；
- 排行是集合发现，不要求先追问单个应用名称；
- `topValues + TotalTraffic` 返回 `APPLICATION_SCOPE_MISMATCH / VALIDATION_FAILURE`；
- 修复提示明确要求把 Draft 改为 `DefinedApp`，不得引导成单对象澄清。

### SEM-04 对象清单形状错配

复现包括：

- “系统中有哪些应用？”被构造成 `WebApplication`；
- “系统中有哪些业务？”被构造成 `DefinedApp` 或 `topValues`；
- 自动识别应用清单使用 `overview/auto_apps`；
- 清单携带 `argument:"all"` 或多个 groups；
- 无 prompt 的 `overview/auto_apps` 绕过文本校验。

影响：对象目录口径混乱，并可能以分析结果替代元数据清单。

根因：对象清单契约只在部分 Prompt Hook 中校验，direct execute 和无 prompt 输入可绕过。

最终修复：

- 一般对象清单统一为 `service=groups + queryModeKey=metadata`；
- 顶层对象清单只允许一个无 argument group；
- `Application -> DefinedApp`、业务 -> `WebApplication`、自动识别应用 -> `CompositeApplication`；
- prompt、`semanticConstraints` 和 `overviewScene=auto_apps` 都进入同一 Policy；
- 所有不合规清单在 Query Skill 前终止。

### SEM-05 普通查询多个 groups 未验证

复现：

```json
{
  "service": "timeValues",
  "queryModeKey": "timeseries",
  "groups": [
    { "type": "DefinedApp", "argument": "HTTP" },
    { "type": "DefinedApp", "argument": "HTTPS" }
  ],
  "metrics": ["TPIO"],
  "granularity": 3600,
  "timeRange": { "key": "last7days" }
}
```

旧行为：结构必填字段齐全时直接返回 `EXECUTE_QUERY`。

影响：无意义或伪造的 group path 可进入 Query Skill 和南向接口；不能把 `groups.length > 1` 当成路径已经合法。

根因：Resolution Spec 声明服务支持多级 groups，但没有验证具体路径是否来自明确、合法的下钻规划。

最终修复：

- 普通查询多 group 默认返回 `MULTI_GROUP_PATH_UNVERIFIED / VALIDATION_FAILURE`；
- 仅当 `pathPlanning` 同时满足以下条件时允许执行：
  - `applied=true`、`shouldApply=true`；
  - `strategy=static_groups_tree`；
  - anchor 与首 group 一致；
  - `plannedGroups` 与实际 groups 类型和参数一致；
  - `selectedPath` 与 group 类型序列一致；
  - 路径存在于静态 groups tree，且 terminal 可查询；
- 只有 `pathPlanning` 空壳或只有多个 groups 不能获得执行许可；
- direct execute 错误输入的 Query Skill、NapmClient、执行服务和南向调用均为 0。

合法回归：`BusinessGroup -> Applications -> DefinedApp` 显式下钻保持可执行；单 group 查询不需要 pathPlanning。

### SEM-06 应用流量语义重复判断

现象：`PromptRoutingService`、`WorkflowClassifierService`、插件和 `QueryDecisionPolicy` 分别用正则判断“应用 + 流量 + 趋势/排行”，导致同一语义在不同入口得到不同结论。

影响：规则补丁会继续分叉；修复趋势后仍可能漏掉排行、英文表达或 direct execute。

根因：Policy 消费原始 prompt，而不是统一的结构化意图。

最终修复：

- `WorkflowClassifierService` 统一输出：
  - `workflowType`；
  - `targetObjectType`；
  - `metricSemantic`；
- 对象类型来自 `ObjectOntologyService`，指标语义来自 `MetricSemanticNormalizerService`；
- `TotalTraffic` 纳入 Object Ontology；
- Query Decision 只消费结构化操作、对象和指标语义；
- 删除 Query Decision 和插件中的独立应用流量正则。

## 5. Query Turn 身份问题

### ID-01 重叠 run 串用最新 turn

复现：同一 conversation 中 run A 尚未完成时 run B 到达；旧 Tool/输出路径读取 `conversationState.turnId`，run A 可能拿到 run B 的状态或结果。

影响：串轮、错答、重复交付，且难以从日志重建真实执行归属。

根因：`conversationKey` 同时被当作 scope 和“当前轮指针”。

最终修复：

- `message_received` 为每个 run/message 创建独立 `turnId`；
- 建立不可变 run/message binding；
- Tool 和输出 Hook 只通过当前 run/message 的可信绑定定位 Query Turn；
- 缺少身份、绑定不存在或 runtime 改变 runId 时 fail-closed；
- 禁止回退到 conversation latest turn；message binding 可在 Hook 间稳定定位原 turn。

### ID-02 direct execute 缺少可信身份仍可执行

复现：直接调用 `napm-skill-query.execute()`，不携带插件签发的 trace 或 trace 无法解析 scope/turn。

影响：绕过 OpenClaw 生命周期约束，pending Draft 和会话结果可能落入错误轮次。

最终修复：在 pending 恢复、时间物化、Query Decision 和 Skill 调用前验证可信 `traceId + scope + turnId`；任一缺失返回绑定失败，南向调用为 0。

### ID-03 direct execute 未校验 toolName 和 route

复现：可信 trace 绑定的是其他 Tool，或现有 Query Turn route 为 `OTHER_SKILL`，但仍调用 query adapter。

影响：错误 Tool 可冒充查询 Tool，普通查询 route 也可能被其他工作流覆盖。

最终修复：

- trace 中的可信 `toolName` 必须精确为 `napm-skill-query`；
- 已存在 Query Turn 的 route 必须为 `NAPM_QUERY`；
- route 创建后不可变；
- 错误分别返回 `QUERY_TOOL_IDENTITY_MISMATCH` 或 `QUERY_TURN_ROUTE_MISMATCH`；
- 校验发生在 pending 恢复和时间物化前。

## 6. 状态机与执行所有权问题

### STATE-01 EXECUTING 可回退并重复执行

复现：同一轮两个 Tool 调用重叠；后来的 `recordDecision()` 把 `EXECUTING` 改回 `DECIDED`，adapter 又忽略 `beginExecution()` 是否真正取得执行权。

影响：同一 Query Turn 可产生多次 Query Skill 和南向调用。

最终修复：

- `recordDecision()`、`recordValidationFailure()` 和 `beginExecution()` 禁止 `EXECUTING` 回退；
- execution attempt 是唯一执行 claim；
- adapter 只有在自己创建了 `EXECUTION/STARTED` attempt 时才拥有执行权；
- `EXECUTING` 重放在处理 Draft、时间和校验前返回 `QUERY_EXECUTION_IN_PROGRESS`；
- 即使重放携带损坏 Draft，也不会触发第二次调用。

### STATE-02 终态可被覆盖

复现：成功后记录 late failure，或 validation/execution failure 后再写 Decision/Result。

影响：最终内容不稳定，先成功后失败或先失败后成功都可能改变用户看到的结果。

最终修复：所有 `TERMINAL` write-once；Decision、Result、Failure 和执行重放均不能覆盖终态，只有 delivery claim 可单调推进一次。

### STATE-03 Result/Failure 可从非法 phase 写入

复现：从 `RECEIVED`、`REPAIR_PENDING` 或 `DECIDED` 直接调用 `recordResult()`/`recordFailure()`。

影响：绕过执行 claim，状态图失去可审计性。

最终修复：

- `recordResult()` 和 `recordFailure()` 仅允许从 `EXECUTING` 迁移；
- 放弃修复使用 `recordRepairAbandoned()`；
- Skill 执行期正常澄清使用 `recordExecutionClarification()`；
- 非法迁移保持原记录不变。

### STATE-04 Query Attempt 和修复预算不统一

旧行为：技术校验错误由不同 Hook 临时处理，重放可能重复扣预算，失败历史也可能丢失。

最终修复：

- 每次构造/执行都有 `attemptId`、kind 和 status；
- 同 attempt 重放幂等；
- 第一次技术构造失败进入 `REPAIR_PENDING`，只允许一次结构修复；
- 第二个构造失败进入 terminal `VALIDATION_FAILURE`；
- 修复成功保留第一次失败 attempt；
- 执行失败立即终止，不消耗构造修复预算。

## 7. 澄清续答问题

### CLAR-01 正常澄清被通用失败覆盖

复现：模型正确回答“请提供应用名称”，但没有 Query Skill 结果；输出 guard 把“没有 Skill 结果”统一改写为“本轮未拿到有效 skill 结果”。

影响：用户看不到可操作的追问，且正确澄清被误报为系统失败。

根因：澄清由模型文本临时拥有，Query Turn 没有权威 Decision 和 finalContent。

最终修复：

- 普通查询即使需要澄清也必须调用 `napm-skill-query` adapter；
- adapter 在本地运行 Query Decision，不调用 Query Skill；
- `CLARIFICATION` 由 Coordinator 生成权威 `finalContent`；
- generic guard 不再是普通查询的交付权威。

### CLAR-02 用户只回复 HTTP 无法恢复原查询

复现：第一轮询问应用趋势并澄清；第二轮用户只回复“HTTP”。旧测试必须手工预构造完整查询才能继续。

影响：真实对话丢失时间、指标、service 和对象类型，用户需要重复问题。

最终修复：

- Coordinator 在 conversation scope 保存 Policy 规范化后的 pending Query Draft；
- 下一轮模型只传 `clarificationAnswer=HTTP`；
- 插件创建新的 run-bound Query Turn，记录 `parentTurnId`；
- 恢复 pending Draft，并把答案补入声明的 `groups[n].argument`；
- 消费 pending 后重新运行完整 Policy；
- direct execute 同样支持该流程，不依赖 Hook 预构造完整查询。

### CLAR-03 Skill 正常澄清被记录为执行失败

复现：Query Skill 返回旧形状正常澄清：

```text
ok=false, error=null, responseType=decision_result,
summary.mode=ASK_CLARIFYING_QUESTION
```

旧行为：adapter 只看 `ok=false`，记录 `EXECUTION_FAILURE`。

最终修复：识别旧形状澄清并规范化为 `ok=true + clarification_required`；通过执行期澄清专用迁移把 execution attempt 标记成功，终态为 `CLARIFICATION`，不是失败。

## 8. 结果与最终交付问题

### DEL-01 成功和 NO_DATA 不由 Query Turn 权威交付

旧行为：澄清/失败逐步进入 Query Turn，但成功和空数据仍依赖旧 `ConversationOperationState` 或“最近结果”。

影响：双权威源导致交付内容与执行记录不一致；同会话重叠查询尤其容易串结果。

最终修复：

- `RESULT` 和 `NO_DATA` 与所有失败终态一样生成非空权威 `finalContent`；
- `before_message_write` 从当前 run-bound Query Turn 读取；
- `message_sending` 对同一 turn 只声明一次交付；
- late failure 不能覆盖成功或空数据；
- 旧 `ConversationOperationState` 不再是普通查询结果和交付源。

### DEL-02 未完成查询没有确定性终态

覆盖场景：

- `RECEIVED`：模型没有调用必需 Tool；
- `DECIDED`：Policy 已允许执行，但 Tool adapter 没有开始；
- `REPAIR_PENDING`：模型放弃唯一一次结构修复；
- `EXECUTING`：最终输出到达但没有执行结果。

旧影响：轮次可能停在非终态，输出 guard 只能猜测是否应显示错误。

最终修复：非流式最终输出统一收口：

| phase | terminal outcome | reason code |
| --- | --- | --- |
| `RECEIVED` 无 Decision/Attempt | `CONTRACT_VIOLATION` | `MODEL_OMITTED_REQUIRED_TOOL` |
| `DECIDED` 未开始 adapter 执行 | `CONTRACT_VIOLATION` | `QUERY_TOOL_EXECUTION_NOT_STARTED` |
| `REPAIR_PENDING` | `VALIDATION_FAILURE` | 放弃修复的校验原因 |
| `EXECUTING` 无结果 | `EXECUTION_FAILURE` | `QUERY_EXECUTION_RESULT_MISSING` |

迟到的 Tool 结果不能替换上述终态。

### DEL-03 流式、重复发送和终态重放

问题包括：流式“正在查询”被误当最终回答；`before_message_write` 与 `message_sending` 重复交付；终态后 Tool 重放再次调用 Skill。

最终修复：

- streaming partial/preview 只表示进度，不终结 Query Turn；
- terminal `finalContent` write-once；
- delivery claim exactly-once；
- 终态 Tool 重放返回已有权威结果，不再次调用 Query Skill 或南向接口；
- `OTHER_SKILL` 和 `MODEL_OWNED` 不由普通查询 Coordinator 抢交付。

## 9. 输入与运行时契约问题

### CON-01 Query Draft 与 Resolved Query 契约混用

现象：运行时错误提示仍要求旧 `resolvedQuery`；Tool schema、提示词和实现对“可缺参数的草稿”与“完整可执行查询”命名不一致。

影响：模型可能把不完整 Draft 当作 Resolved Query，或者在澄清续答时重建整个查询。

最终修复：

- Tool 主输入为 `queryDraft`；
- 只有 `EXECUTE_QUERY` 后才形成完整 `resolvedQuery`；
- `resolvedQuery` 仅作为迁移期兼容别名和 Query Skill 的执行输入；
- 澄清续答使用独立的 `clarificationAnswer`；
- 生产提示、错误文案、Skill 契约和工作区文档同步为 Query Draft-first。

## 10. 最终模块职责

### WorkflowClassifierService

- 输出结构化 `workflowType + targetObjectType + metricSemantic`；
- 组合 Object Ontology 和 Metric Semantic Normalizer；
- 不读写 Query Turn，不决定是否执行。

### QueryDecisionPolicy

- 校验 service、mode、必填字段、对象参数和高风险语义；
- 校验普通查询多 group 的显式静态路径；
- 只输出澄清、执行或拒绝；
- 不调用 Query Skill、NapmClient 或南向接口。

### QueryTurnCoordinator

- 拥有普通查询的 route、Draft、Decision、Attempts、修复预算和 pending clarification；
- 管理不可变 run/message binding；
- 管理 execution claim、terminal `finalContent` 和 delivery claim；
- 不执行 NAPM 查询。

### napm-skill-query adapter

- 校验可信 trace、toolName 和 route；
- 恢复 clarificationAnswer 对应的 pending Draft；
- 在 Hook 和 direct execute 中运行同一个 Policy；
- 只有取得 execution claim 后调用 Query Skill；
- 把 Skill 结果写入当前 Query Turn。

### Query Skill

- 只执行完整 Resolved Query；
- 不拥有 Query Turn、pending clarification 或最终交付状态；
- 不从原始 prompt 猜测并修复生产查询。

## 13. 仍保留的风险与边界

1. Query Turn Repository 当前为进程内状态；Gateway 重启后不会恢复 pending clarification 或未完成 turn。正式需要跨重启恢复时，应单独设计持久化 Repository，不应继续扩展 conversation Map。
2. 多级路径以本地静态 groups tree 为事实来源。南向新增合法路径但静态树未同步时会 fail-closed 拒绝，需先更新静态树和回归测试。
3. `resolvedQuery` 兼容别名仍保留。删除它需要确认所有生产提示、调用方和测试均已迁移到 `queryDraft`。
4. QueryTurnCoordinator 只接管普通 `NAPM_QUERY`；告警、报告、巡检、综述、故障诊断和数据包分析继续使用各自工作流。
5. 本文记录的是本地实现状态，不代表 rc.38 已正式发布或生产验证完成。
