## 一、背景与动机

### 1.1 问题陈述

NAPM 系统使用一个约 6131 行的单体 Plugin 文件（`napm-openclaw-plugin.remote.js`），通过 `execFileAsync` spawn 7 个 Node.js 子进程来执行 7 个 Skill。这种架构存在以下 5 个核心问题：

| # | 问题 | 影响范围 | 严重程度 |
|---|------|---------|---------|
| 1 | **时间覆盖仅在 `runSkillExecutor` 中执行**（line 2618-2648），其他 6 个 Executor 没有 | napm-summary、napm-fault-diagnosis、napm-alert-query 等如果 LLM 传了错误时间戳，不会被 Plugin 覆盖 | **高** |
| 2 | **跨进程 JSON 序列化导致信任断裂** | Plugin 用 `Date.now()` 算好了时间，但 Skill 进程收到的只是 JSON 数字，不知道来源是 Plugin 还是 LLM，被迫再做防御性校验（`validateTimeRangeFreshness` + `autoCorrectTimestampIfStale`） | 中 |
| 3 | **3 种不同的 CLI 参数传递方式** | `--payload`（inline JSON）、`--input`（temp file）、`--queryFile`（temp file），增加维护负担 | 中 |
| 4 | **7 个 Executor 各自为政** | 错误处理不一致（`runSkillExecutor` throw，其他 6 个 return `{ok:false}`）、maxBuffer 不一致、env var 不一致、TLS 配置不一致 | 中 |
| 5 | **`run_fault_diagnosis.js` 有严重 bug** | 无 `require.main === module` 守卫，无 `module.exports`——`require()` 会立即触发 `main()` 执行 | **高** |

### 1.2 目标

1. **消除子进程边界** — `require()` 替代 `execFileAsync`，Plugin 和 Skill 在同一 Node.js 进程中运行
2. **统一时间覆盖** — 在 `before_tool_call` Hook 中一处覆盖，7 个 Tool 全部受益
3. **删除冗余校验** — Skill 脚本不再需要 `validateTimeRangeFreshness` + `autoCorrectTimestampIfStale`
4. **缩减 Plugin** — 删除约 800 行冗余代码（7 个 Executor、6 个 payload builder、`extractSkillJson`、`registerCommand`）

## 二、改前架构分析

### 2.1 整体架构

```
┌─ Plugin 进程 ──────────────────────────────────────┐
│                                                     │
│  1. 注册 Tool（api.registerTool × 7）               │
│  2. Hook 拦截（message_received / before_prompt /   │
│     before_tool_call / message_sending）            │
│  3. 手动 spawn 子进程执行（execFileAsync × 7）      │
│                                                     │
│  runSkillExecutor          → spawn run_napm_query.js         │
│  runSummaryExecutor        → spawn run_summary.js            │
│  runFaultDiagnosisExecutor → spawn run_fault_diagnosis.js    │
│  runInspectionExecutor     → spawn run_inspection_snapshot.js│
│  runAlertExecutor          → spawn run_alert_query.js        │
│  runPacketExecutor         → spawn run_packet_analysis.js    │
│  runReportExecutor         → spawn generate_napm_report.js   │
│                                                     │
└─────────────────────────────────────────────────────┘
         │  JSON 序列化（跨进程边界）
         ▼
┌─ Skill 子进程 ──────────────────────────────────────┐
│  JSON.parse(payload)                                │
│  → 不知道 time 是 Plugin 算的还是 LLM 填的          │
│  → 必须"防御性"地 validateTimeRangeFreshness       │
│  → 必须 autoCorrectTimestampIfStale                 │
│  → 必须再次 floorToMinute                           │
└─────────────────────────────────────────────────────┘
```

### 2.3 时间覆盖的唯一入口

时间覆盖只在 `runSkillExecutor` 中执行（Plugin line 2618-2648），核心逻辑：

```javascript
// 2026-06-29: "时间描述替代时间戳" 策略
// LLM 只传 timeRange.key，插件用 Date.now() 无条件计算 start/end
if (needsTime.includes(String(rq.service || '').trim())) {
  const now = Math.floor(Date.now() / 1000);
  const timeKey = String(rq.timeRange?.key || '').trim() || 'last1hour';
  // ... today/yesterday/relative 三种分支计算 start/end ...
  rq.start = start;
  rq.end = end;
}
```

**问题**：此逻辑只在 `runSkillExecutor`（即 `napm-skill-query`）中生效。当用户使用 `napm-summary` 或 `napm-fault-diagnosis` 时，LLM 传入的时间戳不会被覆盖。

### 2.4 时间校验的冗余层

Skill 进程收到 JSON 解析后的时间戳后，无法判断来源，被迫再次校验：

```javascript
// run_napm_query.js normalizeResolvedQueryTimeRange() line 476-493
// 时间戳年份校验：防止 LLM 自行计算时间戳时出现年份错误（如 2025 vs 2026）
const freshness = validateTimeRangeFreshness(query.start, query.end);
if (!freshness.ok) {
  const correctedStart = autoCorrectTimestampIfStale(query.start);
  const correctedEnd = autoCorrectTimestampIfStale(query.end);
  query.start = correctedStart;
  query.end = correctedEnd;
}
```

这次校验本质上是**对 Plugin 已经做过的计算不信任**——因为跨了进程边界。

### 2.5 `run_fault_diagnosis.js` 的严重 bug

```javascript
// 第 49 行：无条件调用 main()，无 require.main === module 守卫
main().catch((err) => {
  process.stderr.write(`[fault-diagnosis] Fatal: ${err.message}\n`);
  process.exit(1);
});
// 文件末尾：无 module.exports
```

如果任何代码执行 `require('./run_fault_diagnosis.js')`，会立即触发 `main()` 执行，写入 stdout 并可能修改进程状态。这是本重构首先必须修复的问题。

## 三、改后架构设计

### 3.1 核心设计决策

**保留 `api.registerTool()` 注册机制**，只改 `execute()` 内部实现：

```
改前：execute() → execFileAsync('node', [script, '--flag', JSON]) → stdout → extractSkillJson()
改后：execute() → require(script).handleSkillCall(params) → 直接返回结果
```

不改的部分：Hook 拦截逻辑、契约校验、审计日志、结果缓存、所有 `services/` 目录。

### 3.2 新增统一时间覆盖

时间覆盖从 `runSkillExecutor` 内部移至 `before_tool_call` Hook 开头，在所有路由逻辑之前执行：

```
改前：时间覆盖仅在 runSkillExecutor 中 → 仅 napm-skill-query 受益
改后：时间覆盖在 before_tool_call 中 → 所有 7 个 Tool 受益
```

覆盖范围：

| Tool | 时间参数路径 | 覆盖方式 |
|------|------------|---------|
| `napm-skill-query` | `event.params.resolvedQuery` | `applyTimeOverride(resolvedQuery)` |
| `napm-summary` | `event.params.timeRange` | 内联计算 start/end |
| `napm-fault-diagnosis` | `event.params.timeRange` | 内联计算 start/end |
| `napm-alert-query` | `event.params.alertQuery.criteria` | 默认 1 小时 |
| `napm-inspection-snapshot` | — | 无需时间覆盖 |
| `napm-packet-analysis` | — | 无需时间覆盖 |
| `napm-report-export` | — | 无需时间覆盖 |

### 3.3 同进程调用机制

Plugin 顶层新增 `loadSkill()` 工厂函数：

```javascript
function loadSkill(skillDir, scriptName) {
  const skillPath = path.join(OPENCLAW_SKILLS_ROOT, skillDir, 'scripts', scriptName);
  try {
    delete require.cache[require.resolve(skillPath)];
  } catch (_e) {
    // 首次加载，缓存中可能没有
  }
  return require(skillPath);
}

const napmQuerySkill = () => loadSkill('openclaw-napm-query', 'run_napm_query.js');
const napmReportSkill = () => loadSkill('openclaw-napm-report', 'generate_napm_report.js');
// ... 其余 5 个同理
```

**为什么用工厂函数而不是顶层 `require`**：每次 `execute()` 调用前 `delete require.cache` 确保远端推送新代码后能热加载，无需重启。

### 3.4 统一 Skill 接口

每个 Skill 脚本新增 `handleSkillCall(params)` 导出，统一接口规范：

```javascript
/**
 * Plugin 通过 require() 同进程调用的入口。
 * params 已经是 JavaScript 对象，无需 JSON 解析。
 * 时间覆盖已由 before_tool_call Hook 完成。
 */
async function handleSkillCall(params = {}) {
  try {
    // ... 参数转换 + 调用核心 service ...
    return result;
  } catch (error) {
    return {
      ok: false,
      error: {
        code: error.code || 'SKILL_ERROR',
        message: error.message || String(error)
      }
    };
  }
}
```

**统一错误处理**：所有 `handleSkillCall` 都 catch 异常、返回 `{ok: false}`，不再 throw（解决了改前 `runSkillExecutor` throw 而其他 6 个 return 的不一致问题）。

## 五、时间链路对比

### 5.1 改前（8 Stage，3 道防线）

```
Stage 1: LLM 构造 Tool Call
    │   传入 timeRange.key（如 "last1hour"）或错误的绝对时间戳
    ▼
Stage 2: before_tool_call Hook
    │   validateResolvedQueryAgainstSpec（只校验，不覆盖时间）
    ▼
Stage 3: Tool execute() 回调
    │   validateResolvedQueryAgainstSpec（再次校验，仍不覆盖）
    ▼
Stage 4: runSkillExecutor（仅 napm-skill-query 执行此步）
    │   Date.now() 计算 start/end → 无条件覆盖 ← ★ 主防线（仅 1/7 Tool）
    │   JSON.stringify(payload) → spawn 子进程
    │   ★ 其他 6 个 Executor 跳过此步，直接 spawn
    ▼
Stage 5: Skill 进程 JSON.parse
    │   恢复为 JavaScript 对象，但丢失了时间来源信息
    ▼
Stage 6: normalizeResolvedQueryTimeRange
    │   floorToMinute（再次对齐） ← 冗余（Plugin 已对齐）
    │   validateTimeRangeFreshness（年份校验） ← 冗余（不知 Plugin 已算好）
    │   autoCorrectTimestampIfStale（年份修正） ← 冗余
    │   删除 timeRange.start/end
    ▼
Stage 7: RequirementParserService.executeGatewayRequest
    │   start/end → NAPM API URL 参数
    ▼
Stage 8: NAPM API 返回数据
```

**问题总结**：
- 时间覆盖只在 Stage 4 执行，且仅 1/7 Tool 受益
- Stage 6 的校验本质是"不信任 Stage 4 的结果"——因为 JSON 序列化丢失了来源信息
- 如果 LLM 传入错误年份的时间戳给 napm-summary，Stage 4 被跳过，Stage 6 也不执行，错误时间戳直接到达 NAPM API

### 5.2 改后（3 Stage，1 道防线）

```
Stage 1: LLM 构造 Tool Call
    │   传入 timeRange.key（如 "last1hour"）
    ▼
Stage 2: before_tool_call Hook
    │   Date.now() 计算 start/end → 无条件覆盖 ← ★ 唯一防线（对所有 7 个 Tool）
    │   validateResolvedQueryAgainstSpec（校验）
    ▼
Stage 3: Tool execute() 回调
    │   require(skill).handleSkillCall(params) ← 同进程函数调用，无 JSON
    │   normalizeResolvedQueryShape（只 floor + 删除 timeRange.start/end）
    │   RequirementParserService.executeGatewayRequest
    │   → NAPM API 返回数据
```

**改进效果**：
- 时间覆盖只发生一次（Stage 2），对所有 7 个 Tool 统一生效
- 消除了 JSON 序列化边界，Skill 代码可以信任传入的时间戳
- 不再需要 `validateTimeRangeFreshness` / `autoCorrectTimestampIfStale`
- Stage 3 的 `floorToMinute` 保留为防御性二次对齐（同进程调用，零成本）

### 6.2 遇到的问题与修复

#### 问题 1：Plugin 从错误的目录加载

**现象**：推送到 workspace 后，Gateway 仍使用旧代码。

**根因**：`index.mjs` 中的 Plugin 加载路径是 `./napm-openclaw-plugin.remote.js`（相对于 extensions 目录），而非 workspace 目录。

```
Gateway 加载链：
  /home/netinside/.openclaw/extensions/napm-openclaw-plugin/index.mjs
    → require('./index.js')  ← 编译版，优先加载
    → require('./napm-openclaw-plugin.remote.js')  ← 回退，但也在 extensions 目录
```

**修复**：
1. 将 `napm-openclaw-plugin.remote.js` 推送到 `/home/netinside/.openclaw/extensions/napm-openclaw-plugin/`
2. 将 `openclaw.plugin.json` 推送到 `/home/netinside/.openclaw/extensions/napm-openclaw-plugin/`
3. 将 `src/shared/timeResolver.js` 推送到 `/home/netinside/.openclaw/extensions/napm-openclaw-plugin/src/shared/`

#### 问题 2：`openclaw.plugin.json` 缺少 `napm-fault-diagnosis`

**现象**：Gateway 日志输出 `[plugins] plugin must declare contracts.tools for: napm-fault-diagnosis`

**根因**：Plugin 代码中注册了 `napm-fault-diagnosis` 工具，但 manifest 的 `contracts.tools` 数组中未声明。

**修复**：在 `openclaw.plugin.json` 的 `contracts.tools` 中添加 `"napm-fault-diagnosis"`。

#### 问题 3：旧编译版 `index.js` 覆盖了新 `remote.js`

**现象**：Gateway 仍加载旧代码（含 `execFile` 和 `runSkillExecutor`）。

**根因**：`index.mjs` 优先 `require('./index.js')`（242KB 编译版），我们的 `napm-openclaw-plugin.remote.js` 不会被加载。

**修复**：删除 `/home/netinside/.openclaw/extensions/napm-openclaw-plugin/index.js`（先备份），让 `index.mjs` 回退到 `require('./napm-openclaw-plugin.remote.js')`。

#### 问题 4：`NAPM_SKILL_EXECUTOR is not defined`

**现象**：删除 `index.js` 后，Gateway 报 `ReferenceError: NAPM_SKILL_EXECUTOR is not defined`。

**根因**：Plugin 中有 2 处代码引用了已删除的 `NAPM_SKILL_EXECUTOR` 常量：
- Line 679：`getSkillWorkspaceRootFromExecutor()` — 用 executor 路径推导 workspace 根目录
- Line 1464：`getWorkflowClassifierService()` — 用 executor 路径推导 services 目录

这些引用在删除 executor 常量时被遗漏。

**修复**：
1. `getSkillWorkspaceRootFromExecutor()` → 改为 `path.join(OPENCLAW_SKILLS_ROOT, 'openclaw-napm-query/scripts/run_napm_query.js')`
2. `getWorkflowClassifierService()` → 改为 `path.join(OPENCLAW_SKILLS_ROOT, 'openclaw-napm-query/services/WorkflowClassifierService')`

## 八、关键发现与经验

### 8.1 架构发现

1. **Plugin 实际加载路径与预期不符**：Deploy 配置记录的 workspace 路径并非 Plugin 的实际加载位置。Gateway 通过 `extensions/napm-openclaw-plugin/index.mjs` 加载 Plugin，该 ESM wrapper 优先加载编译版 `index.js`，回退到 `napm-openclaw-plugin.remote.js`。

2. **编译版 `index.js` 的优先级高于源文件**：`index.js`（242KB）是旧代码的编译/打包版本，存在于 extensions 目录时，源文件 `napm-openclaw-plugin.remote.js` 不会被加载。需要删除或更新 `index.js`。

3. **`openclaw.plugin.json` 的 contracts 声明是必需的**：Gateway 对每个注册的 Tool 检查 contracts 声明，缺失会输出 warning（不影响功能但影响日志质量）。

### 8.2 代码发现

4. **`run_fault_diagnosis.js` 有两个严重 bug**：无 `require.main === module` 守卫导致 `require()` 会立即执行 `main()`；无 `module.exports` 导致无法导出任何接口。

5. **`floorToMinute` 在 3 个位置重复实现**：Plugin 内联、`run_napm_query.js` 本地函数、`ResolvedQueryTimeRangeService.js` 的 `alignToMinute`。`TimeUtils.js` 中也有但未被使用。

6. **`NAPM_SKILL_EXECUTOR` 有 2 处非 Executor 引用**：在 `getSkillWorkspaceRootFromExecutor()` 和 `getWorkflowClassifierService()` 中用作目录路径推导，不在 Executor 代码块内，初次删除时被遗漏。

### 8.3 部署经验

7. **推送 Plugin 必须同步到两个位置**：`extensions/napm-openclaw-plugin/`（实际加载位置）和 `workspace/`（备份/一致性）。

8. **删除 `index.js` 是让新代码生效的关键步骤**：只要编译版存在，源文件修改不会生效。

9. **Gateway 重启后可能出现短暂的"已杀死"消息**：这是因为 `plink` 执行 `bash -c "nohup ... &"` 后 bash 退出时的副产品，不影响实际运行的 nohup 后台进程。
