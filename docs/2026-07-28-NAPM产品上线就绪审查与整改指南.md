## 2. 审查结论摘要

当前系统能够启动，远端 Gateway 健康检查正常，关键运行文件与本地工作区哈希一致，服务器资源也没有明显压力。但产品上线需要同时满足安全、数据隔离、结果真实性、核心功能、自动化质量门禁和可回滚发布等条件；当前这些维度均存在阻断项。

|---|---|---|
| 凭据与通信安全 | 有效凭据进入仓库，生产链路关闭 TLS 校验 | 阻断 |

## 3. 审查数据快照

### 3.1 本地代码与质量门禁

- Git 分支：`main`，审查时与 `origin/main` 指向同一提交。
- 审查时工作区：144 个已跟踪文档处于删除状态、17 个已跟踪文件有修改、17 个路径未跟踪。
- 全量 Jest：61 个测试套件中 12 个失败；414 个测试中 39 个失败、375 个通过。
- ESLint：`npm run lint` 无法执行，仓库缺少 ESLint 配置。
- CI/CD：未发现 GitHub Actions、GitLab CI、Jenkins、Azure Pipeline 等配置。
- 依赖审计：使用 npm 官方审计端点得到 4 个 high、2 个 moderate 生产依赖漏洞。
- 安装可重复性：根 `.gitignore` 忽略 `package-lock.json`，Git 未跟踪锁文件。
- 测试可信度：至少 19 个插件测试引用被忽略的 `.codex-temp/napm-openclaw-plugin.remote.js`，其哈希与生产插件不同。

### 3.2 远端测试环境

- Gateway 由用户级 systemd 服务管理，本机健康检查返回 HTTP 200。
- Gateway 配置了 Token 认证；外部网络未能直接访问 Gateway 端口。
- 服务器磁盘使用约 48%，可用内存约 6 GiB，当前不存在明显资源容量阻断。
- 本地关键插件、7 个工具入口和远端 workspace 文件哈希一致。
- workspace 与 extension 中的插件、manifest、时间解析器副本哈希一致。
- 远端实际加载 extension 中的 `remote.js` 回退入口，未发现优先级更高的 `index.js`。
- 远端 OpenClaw 版本落后于审查时可见的新版本，应在上线前完成兼容性和安全升级评估。
- 同一个 Syslog 日志被两个 watcher 和一个 receiver 同时跟随；其中一个 watcher 是 systemd 服务，另一个是遗留手工进程。
- 未发现 OpenClaw/NAPM 专用日志轮转配置。
- 远端 NAPM TLS 校验关闭，workspace 还开启了上游 API 调试输出开关。

### ISO-001：报告结果存在跨会话串单风险

**证据**

- `napm-openclaw-plugin.remote.js:33-34` 使用进程级 `latestNapmResult`。
- `napm-openclaw-plugin.remote.js:2173-2175` 返回全局最新结果。
- `napm-openclaw-plugin.remote.js:3260-3271` 导出报告时不按会话过滤。
- 工具执行读取 `args.conversationKey`，但工具 schema 没有声明该字段且设置了 `additionalProperties: false`。
- 只读复现：先保存会话 A 结果，再保存会话 B 结果，会话 A 的“导出以上内容”会解析到 B 的结果。

**风险**

- 企业微信多用户并发时导出其他用户、其他群或其他故障的报告。
- 产生数据越权、隐私泄漏和错误工单证据。

**整改指导**

1. 移除 `latestNapmResult` 作为业务回退源。
2. 所有结果必须以服务端可信的 `conversationKey + userId/channelId` 组合键存储和读取。
3. 不要让模型自行传递会话键；从 OpenClaw hook/tool 上下文注入可信会话身份。
4. 报告导出必须显式携带本轮 `reportData`，或只从当前会话的状态仓库读取。
5. 状态仓库必须设置 TTL、最大容量、逐会话清理和进程退出策略。
6. 任何会话键缺失、过期或不匹配都应硬失败为 `REPORT_DATA_NOT_FOUND`，不得回退到全局结果。

**验收条件**

- A/B 两个会话并发、交错执行 100 轮，报告标题、对象、时间和文件均不串单。
- 缺少会话身份时报告导出硬失败。
- 单元测试和 OpenClaw 集成测试覆盖跨用户、跨群、超时和重启场景。
- 插件状态 Map 有容量上限和可验证的淘汰逻辑。

### ISO-002：告警文本存在跨会话覆盖风险

**证据**

- `napm-openclaw-plugin.remote.js:50` 定义全局 `pendingAlertDisplayText`。
- `napm-openclaw-plugin.remote.js:4074-4077` 在告警执行后写入全局值。
- `napm-openclaw-plugin.remote.js:5067-5073` 任意下一条 `message_sending` 消费该值并替换整条消息。
- 相同全局逻辑还存在另一处发送 hook。

**风险**

- 用户 A 的告警内容替换用户 B 的普通回复。
- 告警对象、严重度和处置建议发送到错误群聊。

**整改指导**

1. 删除全局 `pendingAlertDisplayText`。
2. 将最终告警文本直接作为当前 tool call 的结构化返回值交付。
3. 如必须经过 `message_sending`，使用 `conversationKey + requestId/toolCallId` 精确关联。
4. 消费状态必须执行 compare-and-delete，且只允许匹配的消息使用。
5. 超时状态必须自动清理，禁止任何 global fallback。

**验收条件**

- 两个会话并发执行“告警查询”和“普通查询”，回复始终落到原始会话。
- 乱序、重试、流式消息和重复 hook 场景均不串消息。
- 代码中不再存在无会话归属的 pending 告警单例。

### COR-001：综述失败会被伪装为健康

**证据**

- `skills/openclaw-napm-summary/services/SummaryClient.js:133-151` 对 HTTP 错误状态缺少严格失败判断。
- `skills/openclaw-napm-summary/services/SummaryService.js:727-740` 使用 `Promise.allSettled` 后把 rejection 置为 `null`。
- `skills/openclaw-napm-summary/services/SummaryService.js:446-453` 仍返回 `ok: true` 并计算健康状态。
- 只读复现中，所有告警查询都抛错时仍得到 `ok: true`、总数 0、`overallStatus: "ok"`。

**风险**

- NAPM 服务中断被解释为“无告警、系统健康”。
- 日报、周报和管理层综述产生错误结论。

**整改指导**

1. HTTP 非 2xx、解析失败、超时和鉴权失败必须进入明确失败分支。
2. 为每个计划查询记录 `success/empty/failed/skipped` 四态，禁止只用 `null`。
3. 定义最低数据完整度：关键查询全部失败时 `ok: false`；部分失败时 `partial: true`。
4. `overallStatus` 只能在必需数据成功时计算，否则返回 `unknown`。
5. 报告显式列出失败的数据源和缺失章节，禁止用 0 代替失败。
6. narration 必须区分“查询成功但无数据”和“查询失败”。

**验收条件**

- 所有南向请求失败时，综述返回 `ok: false`，不出现“健康”结论。
- 部分请求失败时返回 `partial: true` 和机器可读的 `failures[]`。
- 真实空数据返回 `ok: true`、`empty: true`，且与失败路径测试完全分离。

### COR-002：故障诊断失败会被伪装为报告就绪

**证据**

- `skills/openclaw-napm-fault-diagnosis/services/FaultDiagnosisService.js:321-334` 把查询失败转换为 `null`。
- `FaultDiagnosisService.js:218-224` 步骤仍返回 `ok: true`。
- `FaultDiagnosisService.js:101-104` 最终仍可返回 `reportReady: true`。

**风险**

- 在没有数据证据时生成看似完成的故障诊断报告。
- 运维人员依据空数据报告采取错误处置动作。

**整改指导**

1. 每个诊断步骤定义必需查询和可选查询。
2. 必需查询失败时步骤必须失败，不允许继续生成正式结论。
3. 可选查询失败时标记 partial，并在报告证据章节展示失败原因。
4. `reportReady` 只能在所有必需步骤成功且证据非空时为 true。
5. 报告构建器禁止把缺失数据解释为正常值。

**验收条件**

- 必需 API 全失败时 `ok: false`、`reportReady: false`。
- 单步骤失败、超时、返回空和格式错误均有独立测试。
- 报告中的每条结论可以追溯到成功查询的证据。

### REP-001：普通查询和数据包报告不可生成

**证据**

- `skills/openclaw-napm-report/services/ReportGenerationService.js:5-12` 声明支持 `quick_report`、`comparative_report`、`operation_report` 等类型。
- `skills/openclaw-napm-query/services/ReportDataContractService.js:35-43` 为普通查询生成 `quick_report` 或无固定模板的诊断报告。
- `skills/openclaw-napm-report/services/ReportTemplateService.js:466-490` 只接受巡检、综述和 3 个固定诊断模板，其他类型全部抛出 `REPORT_TEMPLATE_NOT_FOUND`。
- 数据包报告同样可能生成没有受支持 `templateId` 的 `diagnostic_report`。

**风险**

- TopN、综合分析、对比、普通运维和数据包分析的 Word 导出失败。
- 产品文档承诺与实际用户体验不一致。

**整改指导**

选择并固定一种契约，不要继续同时维护“声明支持”和“渲染拒绝”两套口径：

1. 为 `quick_report`、`comparative_report`、`operation_report` 和数据包诊断建立正式模板；或
2. 从生成服务、工具说明、SOUL/PROJECT 和用户文案中删除未支持类型；或
3. 设计受控的通用报告模板，但必须限定 section schema，不能恢复任意文本拼接。

同时建立 `reportType + templateId + schemaVersion` 的注册表，让 producer 和 renderer 使用同一真源。

**验收条件**

- 每个公开声明的报告类型至少有一个端到端生成测试。
- producer 生成的每个 `reportType/templateId` 都能被 renderer 接受。
- 未注册组合在进入生成阶段前被契约校验拦截。
- TopN、综合分析和数据包分析均能生成可打开的 Word 文件。

### REP-002：报告文件没有可靠的 MEDIA 交付闭环

**证据**

- `napm-openclaw-plugin.remote.js:3997-4007` 报告工具只返回文本和 details，没有返回 `mediaUrl/mediaUrls`。
- `skills/openclaw-napm-report/services/ReportStorageService.js:61-73` 默认写入源码树并生成相对 `/reports` URL。
- 当前测试只覆盖已有媒体链接的去重，没有验证“生成报告后企业微信收到附件”。

**风险**

- 用户只看到服务器文件路径或不可访问链接，实际收不到 Word。
- 报告文件堆积在源码目录，发布与运行数据相互污染。

**整改指导**

1. 将报告输出目录迁移到独立运行数据目录，例如受控的 reports volume。
2. 生成结果返回 OpenClaw/企业微信通道认可的媒体结构，而不是仅返回文本路径。
3. 下载地址必须由真实受控静态服务或对象存储生成，并设置鉴权和有效期。
4. 文件发送成功后记录会话、报告 ID、媒体 ID、发送状态和追踪 ID。
5. 配置保留期、容量水位、定时清理和失败重试。

**验收条件**

- 企业微信端到端测试确认用户收到可打开的 Word 附件。
- URL 不可被未授权用户长期访问。
- 源码目录不再产生运行报告文件。
- 失败发送可以重试，重复发送受当前会话范围约束。

### TLS-001：南向 API 关闭 TLS 证书校验

**证据**

- `skills/openclaw-napm-syslog-watcher/config/watcher.config.json:10`
- `skills/openclaw-napm-alert-query/services/AlertApiService.js:72-81`
- 远端 `.env` 的 TLS insecure 标志为 true，数据包链路的 reject-unauthorized 标志为 false。

**风险**

- 携带认证信息的请求可能受到中间人攻击。
- 无法确认返回数据确实来自目标 NAPM 服务。

**整改指导**

1. 为 NAPM 服务配置有效证书，或在运行环境安装并信任内部 CA。
2. 生产配置禁止 `rejectUnauthorized: false` 和等价 insecure 开关。
3. 将 insecure 仅保留为显式的本地开发能力，并在生产启动时硬校验。
4. 对证书过期、主机名不匹配和未知 CA 建立启动/健康告警。

**验收条件**

- 生产配置中所有 TLS insecure 标志均为 false。
- 使用错误证书时请求必须失败。
- 使用正确证书时查询、告警、巡检、综述和数据包链路均通过。

## 5. P1：上线前必须补齐

### FEA-001：`network_slow` 仅存在于文档，没有完整实现

**证据**

- `PROJECT.md:35`、`SOUL.md:35`、`IDENTITY.md:29` 对外声明 4 种故障诊断流程。
- `skills/openclaw-napm-fault-diagnosis/services/FaultDiagnosisFlowRouter.js:14-27` 只定义 3 种流程。
- 分类器无法识别网络慢，最终默认回退 `bs_app_slow`。
- 查询步骤和报告模板都没有完整的 network flow。

**整改指导**

- 产品决定必须二选一：完整实现 `network_slow`，或从所有产品说明、工具契约和路由提示中移除该能力。
- 如果实现，需要同时补齐 flow 定义、分类、目标识别、查询步骤、判断规则、报告模板、叙述规则和端到端测试。

**验收条件**

- “全网慢”“指定链路慢”“带宽占满”“高丢包/高时延”等场景不会进入 HTTP 4xx/5xx 流程。
- network flow 的数据、结论和报告模板均有固定契约和回归测试。

### SPEC-001：Word/PDF 和故障报告调用方式的规格互相矛盾

**证据**

- `PROJECT.md` 和 `SOUL.md` 对外承诺 Word/PDF。
- `ReportGenerationService.js:55-58` 明确返回 `REPORT_PDF_EXPORT_UNAVAILABLE`。
- `SOUL.md` 一处要求故障报告调用 `napm-report-export`，另一处又称故障诊断内置文件生成、无需 export。
- fault skill 文档承诺单次返回文件，实际 runner 只返回 `reportData`。

**整改指导**

1. 建立一份公开能力矩阵，明确每个报告类型支持 Word、PDF、MEDIA 的真实状态。
2. 故障诊断固定为一种调用链：推荐“诊断生成 reportData -> report-export 生成并发送文件”。
3. PDF 要么在上线前实现并验收，要么从所有用户可见文案和参数枚举中删除。

**验收条件**

- SOUL、PROJECT、工具描述、Skill 文档、实现和测试只保留一套一致口径。
- 不支持的格式无法被模型选择，也不会对用户承诺。

### QA-001：当前测试门禁不可信且为红色

**证据**

- 全量 Jest：12/61 suites 失败，39/414 tests 失败。
- `npm run lint` 因没有 ESLint 配置直接失败。
- 至少 19 个测试导入 `.codex-temp` 下未跟踪旧插件，例如 `test/napm-openclaw-plugin-report-export.test.js:58`。
- `.codex-temp` 插件哈希与生产插件不同。

**整改指导**

1. 所有测试只导入真实生产入口，删除对临时副本的依赖。
2. 先按“失效测试”和“真实回归”分类 39 个失败，不得直接批量改期望值。
3. 增加 ESLint 配置，并覆盖插件及全部 9 个 Skill，而不只 query skill。
4. 建立 CI，至少执行安装、lint、单元测试、集成测试、秘密扫描和依赖审计。
5. 新增跨会话、失败注入、报告 MEDIA、network flow 和 Syslog 并发测试。

**验收条件**

- 干净克隆无需本机临时文件即可运行测试。
- lint、单元测试和集成测试全部通过。
- CI 为必需检查，失败时禁止合并和部署。

### SUP-001：依赖漏洞、缺少锁文件和 Node 版本口径错误

**证据**

- npm 官方审计：4 high、2 moderate。
- 涉及 Axios、JS-YAML、Sharp、ECharts 及传递依赖。
- `.gitignore:3` 忽略所有 `package-lock.json`。
- 根 `package.json` 宣称 Node >=16，但当前依赖和部分 Skill 文档要求 Node >=18。
- Syslog watcher 直接 `require('iconv-lite')`，但根和 watcher 都未声明该直接依赖。

**整改指导**

1. 统一支持的 Node LTS 版本，建议与 OpenClaw 生产运行时一致并固定最小版本。
2. 跟踪根锁文件；如各 Skill 独立发布，则每个独立包也必须有受控 manifest/lock。
3. 升级并回归所有 high/moderate 漏洞依赖。
4. 为每个直接 `require/import` 声明直接依赖，不能依赖偶然的传递安装。
5. CI 使用 `npm ci` 验证干净安装。

**验收条件**

- 干净容器内 `npm ci` 成功。
- `npm audit --omit=dev` 不存在 high/critical；moderate 必须有书面风险接受。
- Node engine、文档、CI 和远端运行版本一致。

### OPS-001：Syslog 存在重复消费者和无界并发风险

**证据**

- 远端同一日志存在两个 watcher 和一个 receiver。
- 第二个 watcher 不属于 systemd 服务，是遗留手工进程。
- `watcher.config.json:24` 将去重窗口设置为 0。
- `SyslogWatcherService.js:140` 对每一行触发 async `_handleLine()`，没有 await、队列、并发上限或局部 catch。
- 远端日志出现同一富化请求重复执行。

**整改指导**

1. 明确唯一生产链路：watcher 与 receiver 不能在职责不清时同时消费同一来源。
2. 所有守护进程必须由 systemd/容器编排管理，禁止 nohup/手工常驻进程。
3. 恢复合理去重窗口，并使用稳定事件键而非仅内存时间窗口。
4. 增加有界队列、并发限制、退避重试、死信记录和背压。
5. 单条消息异常必须被局部捕获，不能演变为未处理 Promise。
6. 增加启动时单实例锁或 leader election。

**验收条件**

- 远端进程清单中每个职责只有一个受管实例。
- 同一告警重复输入只推送一次。
- 告警突发压测下并发、内存和 API QPS 保持在配置上限内。
- 服务重启后去重策略符合产品定义。

### REL-001：发布不可复现、非原子，热加载说明不准确

**证据**

- 当前部署依赖 `pscp` 逐文件覆盖 workspace 和 extension。
- 远端无 Git 工作副本，本地关键运行代码包含未提交修改。
- 插件只删除入口脚本的 require cache；入口引用的 services/shared 模块仍可能保留旧缓存。
- `napm-openclaw-plugin.package.json` 指向不存在的 `index.js` 和 `index.mjs`，实际 wrapper 文件名不同。
- `openclaw.plugin.json` 没有可追踪的发布版本。

**整改指导**

1. 产出单一、版本化、带哈希的发布包，不再逐文件手工推送。
2. 发布包包含插件、manifest、全部 Skill、配置 schema 和依赖锁定信息。
3. 上传到新版本目录，完成校验后通过原子 symlink/目录切换启用。
4. 明确每次发布都需要受控 Gateway reload/restart；不要依赖不完整的热加载。
5. 保留上一版本发布包和一键回滚命令。
6. 发布记录包含 Git SHA、构建号、文件哈希、迁移步骤和验收结果。

**验收条件**

- 任意干净机器可以从 Git SHA 构建相同哈希的发布物。
- 部署中断不会形成混合版本。
- 5 分钟内可以回滚到上一版本，并通过健康检查。
- 远端运行版本可以反查 Git SHA 和构建号。

### LOG-001：日志存在隐私、阻塞和容量风险

**证据**

- 插件审计事件记录 prompt、resolvedQuery 和请求参数。
- 部分执行日志记录原始响应片段。
- 字段名脱敏不能处理嵌入字符串中的 IP、对象名和完整 URL。
- 插件在请求路径使用同步追加日志。
- 文件日志未配置 max size、max files 或保留期；远端未发现专用 logrotate。

**整改指导**

1. 建立结构化审计 schema，只记录必要字段、哈希化身份和 trace ID。
2. URL 仅记录 service/mode 等白名单摘要，不记录完整 query string。
3. 删除同步文件 I/O，统一使用异步日志设施。
4. 设置单文件大小、轮转数量、保留天数、磁盘水位和清理告警。
5. 明确普通日志、审计日志和安全日志的访问控制及保留策略。

**验收条件**

- 日志抽样不包含密码、Token、Webhook、完整认证 URL 或不必要的用户内容。
- 压测下日志不阻塞 Gateway 事件循环。
- 自动轮转和过期清理可验证，磁盘接近阈值时有告警。

### DOC-001：文档基线和运行真源断裂

**证据**

- AGENTS 要求的 `运行环境文档.md` 不存在。
- 审查时 144 个历史 docs 文件处于删除状态。
- Syslog runbook、skills overview 等关键文档也在删除集合中。
- README 仍引用已经迁移或不存在的路径，并保留过期 Node 版本口径。
- 报告 output 目录跟踪了历史 DOCX 和审计 JSON。

**整改指导**

1. 确认 144 个删除是否为有意归档；不要在来源不明时直接提交。
2. 重建最小生产文档集：架构、运行环境、配置 schema、发布、回滚、监控、备份恢复、故障处理和安全响应。
3. 文档中的能力矩阵必须由测试或 manifest 验证。
4. 运行输出和历史业务样例移出源码，并加入 `.gitignore`。
5. 所有示例必须脱敏。

**验收条件**

- 新成员只依赖仓库文档即可完成构建、部署、回滚和常见故障处理。
- 文档路径、版本、工具数量、Skill 数量和实现一致。
- 源码仓库不再包含运行生成的报告和真实业务数据。

## 10. 审查边界

- 本次审查为只读审查，没有修改运行代码、远端配置或服务状态。
- 未执行真实 NAPM 业务查询，避免把审查操作混入生产数据链路。

## 11. 结论

当前项目不是“补少量测试即可上线”的状态，而是存在安全、会话隔离、结果真实性、核心报告链路和发布治理等系统性阻断。整改时应先解决会造成数据泄漏或错误运维结论的 P0 项，再补齐产品能力和发布工程。任何单点修复都不能替代第 8 节的完整上线验收。
