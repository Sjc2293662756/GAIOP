# 查询工作流第三阶段执行内核分层说明

## 背景

第一阶段已经把用户问题先收口为 workflow，第二阶段已经把对象语义和 provider 绑定收口到 `object-ontology.v1.json`。

第三阶段解决的是执行层串线问题：过去 `RequirementParserService.executeDirectGatewayRequest()` 同时承担 metadata 查询和 metric 查询执行，导致同一句话即使上游已经识别成对象清单，也可能在执行层被改走 `topValues`、`overview` 等指标查询路径。

典型风险：

- `系统都有哪些工作组` 属于 `object_inventory`，只能走 metadata 查询，却可能漂移到 `topValues + BusinessGroup`。
- `系统中有哪些自动识别的应用` 属于 `object_inventory`，只能走 `applications Type=4`，不能走 overview 应用概览。
- 指标类问题如果误走 `groups`，也会把指标查询错误解释成对象清单或空结果。

## 本阶段目标

本阶段把执行入口物理拆成两个内核：

- `MetadataExecutionKernel`
- `MetricExecutionKernel`

并增加 `ExecutionKernelPolicy` 作为 workflow/service 契约边界。

原则：

- metadata workflow 只能进入 metadata kernel。
- metric workflow 只能进入 metric kernel。
- workflow 和 service 不匹配时直接拒绝，返回结构化错误，不做兜底换路。
- `RequirementParserService` 只负责请求归一、kernel 分派、错误收口，不再在一个大函数里同时执行两类查询。

## 新增模块

### ExecutionKernelPolicy

新增：

```text
skills/openclaw-napm-query/services/ExecutionKernelPolicy.js
```

职责：

- 定义 metadata workflow：
  - `object_inventory`
  - `metric_inventory`
  - `drilldown_catalog`
- 定义 metric workflow：
  - `metric_topn`
  - `metric_average`
  - `metric_timeseries`
  - `overview`
  - `composite_analysis`
- 定义 metadata service：
  - `groups`
  - `metrics`
  - `metricsForGroup`
  - `drilldownCatalog`
  - `applications`
  - `businessGroups`
  - `groupArguments`
- 定义 metric service：
  - `topValues`
  - `averageValues`
  - `timeValues`
  - `overview`
  - `alertsSummary`

当发现 workflow/service 不匹配时返回：

```text
WORKFLOW_SERVICE_CONTRACT_MISMATCH
```

### MetadataExecutionKernel

新增：

```text
skills/openclaw-napm-query/services/MetadataExecutionKernel.js
```

职责：

- 执行对象清单查询。
- 执行指标清单查询。
- 执行 metadata 类型的 `groups` 查询。
- 保留已有 `NapmMetadataService` 的 truth source 和 provider 逻辑。

当前承接的核心能力：

- `groups + 单对象` -> `NapmMetadataService.listObjectInstances()`
- `metrics + group path` -> `NapmMetadataService.getMetricsForGroupPath()`
- metadata raw groups 查询 -> metadata kernel 内完成

### MetricExecutionKernel

新增：

```text
skills/openclaw-napm-query/services/MetricExecutionKernel.js
```

职责：

- 执行 `topValues`
- 执行 `averageValues`
- 执行 `timeValues`
- 后续承接 overview / composite analysis 的指标执行侧能力

本阶段保持原南向参数构造语义不变，只改变执行归属。

## RequirementParserService 改造

`RequirementParserService.executeDirectGatewayRequest()` 现在只做：

1. 复制并归一化执行态请求。
2. 保留 `semanticConstraints`、`workflowType`、`queryModeKey` 等语义字段。
3. 调用 `ExecutionKernelPolicy.assertWorkflowServiceContract()`。
4. 根据 `ExecutionKernelPolicy.resolveExecutionKernel()` 分派到 metadata 或 metric kernel。
5. 统一 catch 并返回结构化错误。

特别修复：

执行态 `queryRequest` 之前没有保留 `semanticConstraints`，导致执行层看不到 workflow，无法阻止漂移。本阶段已明确保留：

```js
semanticConstraints: passthroughGatewayRequest.semanticConstraints,
workflowType: passthroughGatewayRequest.workflowType,
queryModeKey: passthroughGatewayRequest.queryModeKey
```

这是第三阶段生效的关键前提。

## 契约拒绝示例

对象清单问题不能走 `topValues`：

```json
{
  "service": "topValues",
  "semanticConstraints": {
    "workflowType": "object_inventory",
    "operation": "metadata_list",
    "targetObjectType": "BusinessGroup"
  }
}
```

会被拒绝为：

```json
{
  "code": "WORKFLOW_SERVICE_CONTRACT_MISMATCH",
  "details": {
    "workflowType": "object_inventory",
    "service": "topValues",
    "expectedKernel": "metadata",
    "actualKernel": "metric"
  }
}
```

指标 TopN 问题不能走 `groups`：

```json
{
  "service": "groups",
  "semanticConstraints": {
    "workflowType": "metric_topn",
    "operation": "metric_query",
    "targetObjectType": "IPAddress"
  }
}
```

会被拒绝为：

```text
WORKFLOW_SERVICE_CONTRACT_MISMATCH
```

## 已删除旧逻辑

`RequirementParserService.executeDirectGatewayRequest()` 中原先 metadata 和 metric 混在一起的旧执行段已经物理删除。

现在旧链路不会再在同一个方法中：

- 先尝试 metadata 特例；
- 不命中再落到通用 metric 参数构造；
- 再自行请求南向 API。

执行必须先过 kernel policy，然后进入指定 kernel。
