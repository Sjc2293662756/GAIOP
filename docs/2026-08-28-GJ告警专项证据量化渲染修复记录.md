# GJ 告警专项证据量化渲染修复记录

## 生产现象

`GJ-9YYDSJP9` 的数据包分析状态为 `COMPLETED`，5 个候选会话均显示“已捕获”，但回复只有 HTTP 时序、TCP RTT、TCP 重传的数量，没有实际耗时，也没有把候选实测值与告警触发值 `2216 毫秒` 对照。

这不是候选 IP 未取到，也不是数据包下载失败。生产审计已确认告警数据包组合工具被调用并完成确定性最终回复，问题位于证据保存和最终渲染层。

## 根因

1. 最终回复只输出专项证据行数，没有解析 `http.time` 和 `tcp.analysis.ack_rtt` 的秒值，也没有逐候选与触发值比较。
2. 数据包执行器使用“所有专项行数合计大于 0”的旧判断。某一必需证据类别为空时，仍可能被标记为 `SUPPORTED`，造成“整体已捕获、局部未捕获”的矛盾。
3. 告警引用档案的安全克隆器用一个跨兄弟节点持续存在的 `WeakSet` 判断循环引用。同一个 IP 数组同时挂在候选和 `criteria.ips` 时，被错误写成 `"[Circular]"`，影响跨会话候选恢复。

## 修复内容

- `AlertPacketFinalReplyService`：
  - 展示 HTTP 响应耗时、TCP RTT 的平均值和最大值，秒值统一换算为毫秒。
  - 展示重传数量；达到 100 行展示上限时显示“至少 N 条，已达到展示上限”。
  - 增加“告警指标对照”，逐候选说明高于或低于告警触发值。
  - 对历史状态重新按必需证据类别校验，缺一类时降级为“部分捕获”。
  - 专项结论改为“重点排查对象/证据不足”，禁止仅凭单一字段直接认定根因。
- `run_packet_analysis.js`：
  - 保存各类证据的截断标记。
  - 按 `evidenceChecks` 逐项判定 `SUPPORTED/PARTIAL/NOT_CAPTURED`，移除总行数大于 0 的粗略判断。
- `AlertReferenceStore`：
  - 安全克隆只追踪当前递归路径，保留合法共享对象，仍能识别真正的循环引用。
  - 读取历史档案时，将已写入的 `"[Circular]"` 候选 IP/画像数组从同一档案中的可信字段恢复，并原子回写，避免旧引用无法续传。

## 验收标准

对新的 `server_user_experience_time` 告警，最终回复必须同时满足：

- 显示告警触发值、单位、阈值命中和超阈值差值。
- 每个候选显示 HTTP 时延、RTT 的实际统计值，而不是只有“已捕获 N 条”。
- 明确候选实测值相对告警触发值的高低及排查意义。
- 缺少某类证据时显示“未捕获/部分捕获”，不得继续显示完整捕获。
- 不输出 `eventId`、Unix `start/end`、原始抓包行、URL 或认证信息。

## rc.37 部署后增量修复

提交 `4634b0fb9076079f6d46878728b8cbfeaff92352` 进一步收紧完成态结论：

- 只使用告警窗口内可量化的 HTTP、RTT 和重传证据。
- 从成功候选中选择 HTTP 最大响应耗时最高者，并明确其是否达到告警触发值。
- 结论直接给出优先排查候选，不再以“已完成专项证据核对”的泛化模板收尾。
- 重传只有数量、缺少总包数或重传率时，明确禁止单独认定为根因。
- 没有窗口内 HTTP 量化证据时保守降级，说明当前抓包证据不能解释告警触发值。
