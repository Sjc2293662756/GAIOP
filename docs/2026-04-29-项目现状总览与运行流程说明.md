# 项目现状总览与运行流程说明

日期：2026-04-29

## 1. 项目当前定位

当前项目已经从“网关转发/网关裁决”模式，收敛为“OpenClaw 直接调用 Skill，OpenClaw 输出结构化 `resolvedQuery`，Skill 负责执行、结果收口与叙述契约输出”的模式。

当前真实主链路是：

```text
用户问题
  -> OpenClaw / 企业微信插件
  -> skills/openclaw-napm-query/scripts/run_napm_query.js
  -> RequirementParserService 执行结构化查询
  -> NapmClient 调用 NAPM WebService
  -> OpenClawNarrationContractService 组装叙述契约
  -> OpenClaw / 插件输出中文回答
```

几个需要明确的现状：

- 旧 `src/routes`、`src/services` 网关链路已经不再参与当前查询主流程。
- 代码里仍保留不少 `gatewayRequest`、`executeGatewayRequest` 之类的命名，但这里的 `gateway` 已经只是历史命名，不代表旧网关仍在运行。
- 当前运行核心集中在 `skills/openclaw-napm-query/`，`src/` 只保留被 Skill 复用的基础常量和工具。
- 当前结果输出已经要求带数据时间范围，叙述层会尽量把 `数据时间：开始 至 结束` 放到回答前部。

## 3. 项目整体流程

### 3.1 启动与入口阶段

1. OpenClaw 或插件把问题传给 `skills/openclaw-napm-query/scripts/run_napm_query.js`。
2. `run_napm_query.js` 加载 `.env`，解析 `--payload`、`--resolvedQuery`、`--intent` 等参数。
3. 当前正式口径要求调用方必须给出 `resolvedQuery`。
4. `run_napm_query.js` 会对传入的 `resolvedQuery` 做规范化、补意图摘要与语义摘要，然后进入执行链路。

### 3.2 语义理解与查询构造阶段

1. OpenClaw / 上游先完成自然语言理解，输出结构化 `resolvedQuery`。
2. `run_napm_query.js` 调用 `normalizeResolvedQueryShape()`，把查询对象规范成当前执行链需要的稳定结构。
3. `RequirementParserService.buildIntentResult()` 生成意图摘要，供上游和结果层使用。
4. `RequirementParserService.buildSemanticResolutionResult()` 生成语义摘要，补对象、指标、时间、路径等结构化说明。

### 3.3 执行阶段

1. `run_napm_query.js` 判断本次是不是概览类查询。
2. 如果是概览类问题，走 `overview-module.js`：
   - 先判定场景
   - 再按场景展开多条父子查询
   - 最后聚合成概览结果
3. 如果不是概览类问题，直接走 `RequirementParserService.executeGatewayRequest()`。
4. `executeGatewayRequest()` 内部调用 `NapmClient`，向 NetInside / NAPM WebService 发起 HTTP 请求。
5. 返回结果后，如果是 CSV 字符串，会用 `CsvParser` 做解析；如果是 JSON，则直接处理。

### 3.4 结果收口与叙述阶段

1. `run_napm_query.js` 根据执行结果补 summary、displayText、followUp 等基础信息。
2. `OpenClawNarrationContractService.buildOpenClawReplyContract()` 将结果整理成统一叙述契约。
3. 叙述契约中会尽量带上：
   - 结果类型
   - 结构化行数据
   - 数据时间范围
   - 推荐叙述策略
   - 可继续追问的 follow-up
4. 最终由 OpenClaw / 插件输出用户可读的中文回答。

## 5. 主要核心函数

下面列的是当前最值得记住的一批核心函数。

### 5.1 入口与流程控制

- `run_napm_query.js`
  - `parseArgs(argv)`：解析命令行参数。
  - `resolveInput(args, payload)`：统一整理 payload、resolvedQuery 等输入，并强制要求存在结构化 `resolvedQuery`。
  - `executeResolvedQuery(prompt, resolvedQuery, payload, intentResult)`：判断走概览模块还是直接执行。
  - `main()`：总入口，完成输入解析、执行、结果收口、异常兜底。

### 5.2 查询编排中枢

- `RequirementParserService.js`
  - `executeGatewayRequest(gatewayRequest, requestContext)`：执行单条 NAPM 查询。
  - `buildIntentResult(partialQuery, userRequirement)`：为上游和叙述层补一份结构化意图结果。
  - `buildSemanticResolutionResult(partialQuery)`：把结构化查询再整理成对象、指标、时间等摘要结果。

说明：这里的 `gatewayRequest` 其实就是当前 Skill 内部执行对象，不应再把它理解成旧 HTTP 网关请求。

### 5.3 结构化查询规范化

- `run_napm_query.js`
  - `normalizeResolvedQueryShape(resolvedQuery, prompt)`：把上游传入的结构化查询补齐为当前执行链需要的稳定字段。
  - `RequirementParserService.buildIntentResult(...)`：生成给 OpenClaw 使用的意图摘要。
  - `RequirementParserService.buildSemanticResolutionResult(...)`：生成给 OpenClaw 使用的语义摘要。

### 5.4 概览分支

- `overview-module.js`
  - `resolveOverviewScene(...)`：判断当前概览属于 system、business、application、network、security 哪类场景。
  - `buildOverviewQueries(scene, start, end)`：按场景展开多条子查询。
  - `executeOverviewModule(options)`：执行父子查询并聚合结果。
  - `buildOverviewSummary(...)` / `buildOverviewDisplayText(...)`：概览结果摘要与展示文案生成。

### 5.5 NAPM 请求发送

- `NapmClient.js`
  - `get(params)`：发 GET 请求。
  - `post(data)`：发 POST 请求。
  - `getJson(params)`：强制追加 `json=true` 并返回 JSON 结构。

### 5.6 结果叙述收口

- `OpenClawNarrationContractService.js`
  - `normalizeTimeRange(payload, summary)`：从结果里统一提取数据时间范围。
  - `ensureSummaryTimeRange(summary, timeRange)`：把时间范围注入 summary highlights。
  - `buildNarrationStructure(...)`：按列表、TopN、趋势、概览等类型生成叙述结构。
  - `buildOpenClawReplyContract(data, options)`：最终生成 OpenClaw 叙述契约。

### 5.7 时间工具

- `TimeUtils.js`
  - `normalizeDynamicTimeRange(input)`：把“近1小时/最近一天/近7天”等文本转成动态范围。
  - `parseTimeRange(timeRange)`：把时间 key 或时间文本转换成 `start/end`。
  - `getTodayStart()` / `getTodayEnd()` / `getYesterdayStart()` / `getYesterdayEnd()`：生成固定时间边界。

## 6. 当前项目的几个关键认识

### 6.1 主运行路径已经非常明确

当前真正运行的主链只有两条：

- 普通查询：`run_napm_query.js -> RequirementParserService -> NapmClient -> NarrationContract`
- 概览查询：`run_napm_query.js -> overview-module.js -> RequirementParserService.executeGatewayRequest() -> NarrationContract`

### 6.2 `skills/` 是主战场，`src/` 是基础库

- `skills/openclaw-napm-query/` 才是当前项目真正的业务核心。
- `src/` 目前不再承载旧网关业务，只保留 Skill 仍然依赖的常量和工具函数。

### 6.3 仍有一些历史命名残留

当前代码里仍能看到：

- `gatewayRequest`
- `executeGatewayRequest`
- `stableQueryTemplates`

这些命名来自旧阶段，但现在语义上都已经变成 Skill 内部的执行对象、执行函数和模板机制，不应再按“独立网关服务”理解。

### 6.4 当前模型与 Skill 的分工

- OpenClaw / 插件负责接收问题、调用 Skill、最终组织用户回答。
- Skill 负责真正的 NAPM 语义解析和数据查询。
- `OpenClawNarrationContractService` 负责给上游一个足够稳定的叙述输入结构。

## 7. 一句话总结

截至 2026-04-29，这个项目的本质已经不是“NAPM 网关服务”，而是“一个以 `run_napm_query.js` 为入口、以 `RequirementParserService` 为核心编排器、以 `NapmClient` 为执行器、以 `OpenClawNarrationContractService` 为结果收口层的 OpenClaw 直连 NAPM 查询 Skill”。
