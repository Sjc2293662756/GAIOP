# GJ 告警批量候选续传修复记录

## 问题

多候选告警首轮返回 `CANDIDATE_SELECTION_REQUIRED` 后，用户发送“按顺序分析！”或同义指令，系统没有恢复上一轮 GJ 引用。生产表现为：

- `GJ-RX8QWSWF` 被模型汇总成“5 个候选均失败”，但没有真实数据包分析调用；
- `GJ-37LD8VAW` 因续传参数为空而回复“需要 eventId”；
- 引用档案中的候选仍为 `DISCOVERED`。

根因是续传识别只覆盖下载确认词，未覆盖批量候选分析词；同时工作流没有“分析全部候选”分支，多候选默认始终要求人工选择。

## 修复

1. 插件识别“按顺序分析、按顺序都进行分析、依次分析、逐一分析、逐个分析、全部分析、分析所有候选”等指令。
2. 从当前会话的上一轮告警状态恢复 GJ 引用，生成内部 prompt：`分析告警 GJ-XXXXXX 按顺序分析全部候选`。
3. 增加插件自有参数 `analyzeAllCandidates`，不向用户暴露 `eventId/start/end`。
4. 批量续传只恢复告警指标和数据包窗口，不自动设置 `previewRiskAccepted`，仍遵守下载确认策略。
5. 工作流在 `analyzeAllCandidates=true` 时按候选 `rank` 顺序逐一调用现有数据包 Skill，保留告警指标专项画像。
6. 分析结束后同步更新引用档案的工作流状态和每个候选的 `ANALYZED`、`ANALYSIS_FAILED` 或 `AWAITING_DOWNLOAD_CONFIRMATION` 状态。

## 验证

- 旧代码新增回归先稳定失败，确认复现了“按顺序分析”未续传和多候选仍停留在选择状态。
- 修复后定向告警数据包测试：19/19 通过。
- 全量 Jest：100 个测试套件、807 个测试通过。
- `npm run lint`：通过。
- `node --check`：插件、工作流和结果契约通过。
- `npm run verify:runtime-contract`：8 个生产工具入口全部 `ok: true`。
- 最小运行时回放确认：恢复 GJ 引用、事件号、固定时间窗口、告警指标画像和 `analyzeAllCandidates=true`；`previewRiskAccepted=false`。
