# 故障分析 Skill 全面重构记录

## 概述

本次重构将 NAPM 故障诊断 skill 从"三流程 + 交互式 + 死代码"精简为"两流程 + 全自动"。

核心变化：删除 `network_slow` 及所有交互式逻辑，只保留 `bs_app_slow`（业务故障分析）和 `cs_app_slow`（应用故障分析），两者均为标准化单次调用，全自动执行。

---

## 一、业务 vs 应用

NAPM 系统严格区分两类对象：

| | 业务 | 应用 |
|------|------|------|
| NAPM 对象 | WebApplication (Type=3) | DefinedApp (Type=2) / CompositeApplication (Type=4) / BuiltinApplication (Type=1) / OtherApp |
| 协议层 | HTTP/HTTPS | TCP/UDP |
| 流程 | `bs_app_slow` — B/S 架构业务慢 | `cs_app_slow` — C/S 架构应用慢 |
| 锚点 | 页面 URL → HTTP 状态码 | 时间波峰 → 用户体验时间成分 |
| 报告模板 | `napm_bs_fault_diagnosis_v2` | `napm_cs_fault_diagnosis_v1` |

分析对象由 NAPM catalog 的 `applications` 接口确定，工具在 `start()` 中自动查询并匹配。

---

## 二、CS 应用故障分析流程（3 步）

参考 NAPM AppPro（单个应用剖析）接口文档设计：

| 步骤 | 接口 | 指标 | 分组 |
|------|------|------|------|
| Step1 应用概览 | `averageValues` | UEII, CSTI, TRTI, PTTO, RDTO | DefinedApp(应用名) |
| | `timeValues` | TPI, TPO | DefinedApp(应用名) |
| Step2 用户体验趋势 | `timeValues` | UEII, CSTI, TRTI, PTTO, RDTO | DefinedApp(应用名) |
| Step3 波峰客户端 | `topValues` × N | UEII, CSTI, TRTI, PTTO, RDTO | DefinedApp → ExternalIPs → IPAddress |

Step2 的 `_analyzeCsStep2` 自动标记 UET 时间序列中的波峰。Step3 对每个波峰 ±30s 窗口查询慢客户端 IP。

应用类型识别通过 `_resolveCsAppMeta(target)` 统一处理：`CompositeApplication`/`BuiltinApplication` 映射为 `DefinedApp`；`OtherApp` 使用 `ConnectedIP` 替代 `IPAddress`。

## 三、流程类型自动解析

### 核心模型

```
用户描述 → extractTargetName → 候选名称
  → _getAppCatalog() → NAPM applications API（5min 缓存）
  → matchAppByName() → 计分匹配（精确100 > 前缀80 > 包含50）
  → resolveFlowTypeFromCatalog() → Type → flowType + groupType + target
```

### 名称提取（extractTargetName）

从用户原话（`prompt` 字段）中提取对象名：

1. 定位"应用故障"/"业务故障"/"故障分析"等关键词
2. 取关键词前文本 → 去"的" → 剥离动作词前缀 → 取第一段 CJK/字母数字

### 名称匹配（matchAppByName）

全量匹配 NAPM catalog，计分排序。不做后缀剥离，不做 contained 匹配。同分优先 Type=2（DefinedApp 名称更精确）。

### flowType 判定

```
catalog 命中 → Type=3 → bs_app_slow + WebApplication
             → Type≠3 → cs_app_slow + DefinedApp

catalog 未命中 → classify() 关键词 fallback
```

### classify() 关键词（fallback）

```
"业务故障"/"web"/"页面"/"http"/"400"/"500" → bs_app_slow
"应用故障"/"数据库访问"/"客户端软件"/"cs" → cs_app_slow
其余 → bs_app_slow（默认）
```

## 六、AI 路由修复

AI（观枢）反复将应用故障分析误判为业务。排查发现在多个层面存在引导 AI 走错方向的问题：

### 修复清单

| 层面 | 问题 | 修复 |
|------|------|------|
| 工具参数定义 | `flowType` 和 `target` 暴露给 AI，AI 会填写 | 从 parameters 中移除，只保留 `description` + `timeRange` |
| 参数传递 | `description \|\| prompt` → AI 改写的内容优先 | `prompt \|\| description` → 用户原话优先 |
| 工具定义 | `flowType` 未标记 required | `required: ['prompt', 'description']`，提示必须复制用户原话 |
| 路由表 | 两行（business / application），迫使 AI 先判断再选行 | 合并为一行，AI 无需区分 |
| SKILL.md | "先查 XX 在 NAPM 中是什么类型" → 教 AI 自己查 | 删除，改为"不要自己判断，直接传 description" |
| 拦截消息 | "call napm-fault-diagnosis with flowType='bs_app_slow'" → 强制 BS | 改为 "call with description + timeRange only" |
| 系统提示 | "fault/error analysis → flowType='bs_app_slow', target=WebApplication" → 强制 BS | 移除 flowType/target 部分 |
| 名称提取 | `_extractFromDescription` 取最后一个词 → "可观测239web 页面HTTP错误" 取到 "HTTP错误" | 改为取第一个名称段 |
| 关键词 | "回溯238应用" → "应用"后无关键词 → 匹配失败 | 新增 `/(?:应用\|业务)$/` 模式 |
| start() | flowType 非空时跳过 catalog → AI 传 BS 就永远 BS | catalog 无条件运行，结果覆盖外部输入 |

## 八、最终架构

```
用户说 "给我可观测239的应用故障分析报告"
  │
  ▼
handleSkillCall(params)
  → payload.prompt = params.prompt || params.description  (用户原话优先)
  → service.run(payload)
  │
  ▼
start(input)
  ├─ extractTargetName(input)  →  "可观测239"
  ├─ _getAppCatalog()  →  NAPM applications API (5min TTL)
  ├─ matchAppByName("可观测239", catalog)  →  {name:"可观测239", type:2, score:100}
  ├─ resolveFlowTypeFromCatalog({type:2})  →  cs_app_slow + DefinedApp
  │   (catalog 失败 → classify(description) fallback)
  │
  ├─ executeStep × 3
  │    step1: averageValues(UEII,CSTI,TRTI,PTTO,RDTO) + timeValues(TPI,TPO)
  │    step2: timeValues(UEII,CSTI,TRTI,PTTO,RDTO) → 波峰标记
  │    step3: topValues(UEII,CSTI,TRTI,PTTO,RDTO) × N → 波峰客户端
  │
  ▼
run()
  → _buildBsTemplateData 或 _buildCsTemplateData  →  reportData
  │
  ▼
napm-report-export
  → buildReportInputForExport  →  从 latestNapmResult 注入 reportData
  → CsFaultTemplateService.renderDocx 或 BsFaultTemplateService.renderDocx
  → .docx
```

**NAPM catalog 是唯一真相源。Type 决定 flowType + groupType。**
