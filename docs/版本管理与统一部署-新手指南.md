# NAPM 版本管理与统一部署：新手指南

## 先记住一个结论

以后只修改这个目录：

```text
G:\my_file\项目测试\观枢·智维平台-GAIOP\NAPM_skill_unified
```

下面两个旧目录只作为历史备份，不再继续开发，也不要删除：

```text
G:\my_file\项目测试\观枢·智维平台-GAIOP\skill_project\NAPM_skill
G:\my_file\项目测试\观枢·智维平台-GAIOP\project_3\NAPM_skill
```

完整备份在：

```text
G:\my_file\项目测试\观枢·智维平台-GAIOP\version_backups\20260814_before_unification
```

## 三个词，用最简单的话理解

1. **Git 提交**：一次有编号的存档。改好并验证后做一次提交，就能知道某段代码属于哪个版本。
2. **版本号**：给人看的版本名称，例如 `1.1.0-rc.1`。`rc` 表示测试候选版，还不是正式生产版。
3. **部署包**：从某个 Git 提交自动生成的完整 ZIP。它包含这一版本需要的所有代码，不需要人工挑文件。

“唯一部署包”不是只剩一个源代码文件，而是一次部署只上传一个完整 ZIP。ZIP 内每个文件都来自同一个 Git 提交，因此不会再出现“插件是新版、某个 Skill 还是旧版”的混合状态。

## 每天修改代码的固定步骤

### 第 1 步：进入唯一仓库

```powershell
Set-Location 'G:\my_file\项目测试\观枢·智维平台-GAIOP\NAPM_skill_unified'
git status --short --branch
```

正常情况下应看到分支 `integration/unified-v1`。开始新工作前，最好没有 `M`、`A`、`??` 等未提交标记。

### 第 2 步：修改代码

只在 `NAPM_skill_unified` 中修改。不要在两个旧目录中同时修改同一个功能。

### 第 3 步：运行三道检查

```powershell
npm test -- --runInBand --silent
npm run lint
npm run verify:runtime-contract
```

三条命令都成功后才能提交。当前完整标准是：

- 90 个测试文件通过
- 628 条测试通过
- lint 0 错误、0 警告
- 8 个生产工具入口全部 `ok: true`

### 第 4 步：做 Git 存档

```powershell
git status --short
git add --all
git commit -m "fix: 简短说明本次修改"
```

不要提交 `.env`、密码、Webhook、日志、报告、数据包或临时查询 JSON。

### 第 5 步：查看刚才的版本

```powershell
git log -1 --oneline
git status --short --branch
```

记下提交号，例如 `4a9c184`。工作区应重新变干净。

## 什么时候修改版本号

- 继续测试同一个候选版：`1.1.0-rc.1` → `1.1.0-rc.2`
- 修复正式版的小问题：`1.1.0` → `1.1.1`
- 增加向后兼容的新功能：`1.1.0` → `1.2.0`
- 有不兼容的大改动：`1.x.x` → `2.0.0`

测试候选版升级示例：

```powershell
npm version prerelease --preid=rc --no-git-tag-version
git add package.json package-lock.json
git commit -m "chore: bump release candidate version"
```

不确定该升哪一位时不要猜，先让维护者或 Codex检查本次改动范围。

## 构建唯一部署包

工作区干净后执行：

```powershell
npm run release:build
```

构建命令会再次自动运行全部测试、lint 和生产入口检查，然后从当前 Git 提交生成：

```text
dist\NAPM_skill-<版本号>-<提交号>.zip
```

例如：

```text
dist\NAPM_skill-1.1.0-rc.1-1234abcd.zip
```

命令还会显示 SHA-256。ZIP 内含 `RELEASE-MANIFEST.json`，记录完整提交号、版本号和构建时间。

发布包不会包含：

- `.env` 或真实凭据
- `node_modules`
- 日志、报告和数据包
- `query_*.json` 等运行数据
- 历史 `archive`、测试和旧 `.bak`
- Syslog watcher 的真实运行配置
- `logs/`、`output/`、`data/` 和历史报告文件

## 上传和部署测试服务器

部署前先得到明确批准。普通发布只上传 ZIP，不再逐个上传源文件。

```powershell
pscp 'dist\NAPM_skill-<版本号>-<提交号>.zip' 'netinside@101.254.114.237:/home/netinside/releases/'
```

登录服务器后：

```bash
mkdir -p /home/netinside/releases/<版本号>-<提交号>
unzip -q /home/netinside/releases/NAPM_skill-<版本号>-<提交号>.zip \
  -d /home/netinside/releases/<版本号>-<提交号>
cd /home/netinside/releases/<版本号>-<提交号>/NAPM_skill-<版本号>-<提交号>
bash scripts/verify-staged-release.sh
bash scripts/install-release.sh --dry-run
bash scripts/install-release.sh
```

`verify-staged-release.sh` 只在候选版本自己的解压目录中安装依赖并检查代码，不修改正在运行的 OpenClaw。`install-release.sh --dry-run` 只预览部署目标，也不修改服务器。最后一条命令才会：

1. 备份现有插件、将更新的 Skills、workspace 依赖和顶层配置。
2. 保留服务器上的 `.env`、日志、输出、运行数据和 watcher 配置。
3. 同步整个版本的插件与 Skills。
4. 按 `package-lock.json` 安装 Linux 依赖。
5. 验证插件语法和 8 个工具入口。
6. 恢复原先处于活动状态的 Gateway 和 watcher 服务并检查状态。
7. 任一步骤失败时，自动恢复部署前版本。

安装脚本会打印备份文件位置。部署失败时不要继续手工覆盖文件，也不要直接删除目录；先确认自动回退结果和服务状态。

## Git 标签和远端仓库

候选版本验证完成后，可建立本地标签。已经建立的标签不要移动；发布修复应增加候选版本号，例如：

```powershell
git tag -a v1.1.0-rc.2 -m "NAPM unified release candidate 2"
git show --no-patch v1.1.0-rc.2
```

标签表示“这个版本号固定对应这个提交”。推送 GitHub 和部署服务器是两件不同的事，都应在明确确认后执行：

```powershell
git push origin integration/unified-v1
git push origin v1.1.0-rc.2
```

## 出问题时先看哪里

```powershell
git status --short --branch
git log -5 --oneline --decorate
```

- 不知道自己改了什么：`git diff`
- 不知道暂存了什么：`git diff --cached`
- 构建提示工作区不干净：先提交或明确处理未提交文件，不要强行跳过
- ZIP 名字和预期不同：检查 `package.json` 的 `version` 和 `git log -1`
- 服务器部署失败：停止继续覆盖，保存输出和安装脚本打印的备份路径

## 禁止事项

- 不再从 `skill_project` 或 `project_3` 直接部署。
- 不再把“这次改过的几个文件”手工拼成一个线上版本。
- 不把密码写进 Git、命令模板或文档。
- 不在工作区有未提交修改时构建发布包。
- 不删除两个旧目录或 `version_backups`，直到统一版本经过测试服务器验收。
