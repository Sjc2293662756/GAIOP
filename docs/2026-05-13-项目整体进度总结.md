## 2. 当前最准确的一句话总结

截至 2026-05-13，`NAPM_Semantic_Gateway` 已经基本收口到这样一条主链：

```text
企业微信 / OpenClaw 接入
  -> OpenClaw 主链负责语义理解、澄清判断、生成受约束的 resolvedQuery
  -> napm-openclaw-plugin 负责守卫、转发和结果保护
  -> openclaw-napm-query skill 负责执行 NAPM 查询并输出 narration contract
  -> OpenClaw / WeCom 返回最终中文答案
```

项目方向已经明确，当前处于“继续收掉历史 fallback 和插件特例”的执行阶段，而不是重新推翻主架构的阶段。

## 3. 当前真实主链

当前最应该统一的理解是：

```text
企业微信用户
  -> wecom-openclaw-plugin
  -> OpenClaw 主链 + LLM
  -> napm-openclaw-plugin
  -> openclaw-napm-query skill
  -> NAPM / NetInside API
  -> narration contract
  -> OpenClaw / WeCom 最终回包
```

对应职责边界如下：

- `wecom-openclaw-plugin`：负责通道接入、消息收发、处理中占位、最终回包承载。
- `OpenClaw 主链 + LLM`：负责是不是 NAPM 问题、是否要追问、如何理解语义、如何生成 `resolvedQuery`。
- `napm-openclaw-plugin`：负责 NAPM 范围守卫、工具限制、预览消息保护、结果回写保护。
- `openclaw-napm-query skill`：负责消费 `resolvedQuery`、执行查询、整理结果、输出 contract。
- `NAPM / NetInside API`：只负责提供数据，不负责理解用户问题。

## 4. 截至今天已经完成的关键收口

## 4.1 架构认知已经基本收口

当前已经明确三件事：

- 企业微信插件不应该再长期承载业务语义理解。
- Skill 不应该继续承担“从裸 prompt 猜用户真实查询意图”的主职责。
- LLM 可以参与 `resolvedQuery` 生成，但必须被规则约束，而不是自由生成任意查询。

这意味着后续改造的方向不是“继续往插件里堆规则”，而是：

```text
让 OpenClaw LLM 负责语义理解
让代码规则负责约束、校验和执行保护
让 Skill 负责稳定执行
```

## 4.2 “丢包率最高的 IP 是谁”链路第一阶段已收口

本轮已经完成的关键修复包括：

- 去掉插件和 Skill 中把 `packet loss` 排行默认偷偷改成按 `TPIO` 排序的隐式规则。
- 去掉插件对这类问法“发送前再强制查一遍”的重复刷新逻辑。
- 在 `OpenClaw` 提示词中补上约束，明确这类问法不能再被改写成吞吐排序。

这部分已经补了针对性回归测试，已通过的测试包括：

- `test/packet-loss-default-sort-metric.test.js`
- `test/napm-openclaw-plugin-packet-loss-guard.test.js`
- `test/openclaw-narration-contract.test.js`

这说明第一阶段最明显的“语义跑偏 + 重复执行 + 响应变慢”问题已经被收掉一部分。

## 4.3 企业微信“处理中完全没反应”问题已定位并修复

这个问题今天已经明确根因：

- 不是消息链路断了。
- 不是 Skill 没返回。
- 也不是必须重新打开 reasoning streaming 才能有反馈。

真正原因是远端真实配置里把企业微信的安全处理中占位关掉了：

```json
channels.wecom.sendThinkingMessage=false
```

而此前为防止 reasoning 泄露，远端又已经保持：

```json
channels.wecom.stream=false
channels.wecom.streaming=false
channels.wecom.thinking=false
```

于是企业微信侧就变成“处理中完全静默，只能等最终答案一次性出来”。

今天已完成的修复是：

- 将远端 `sendThinkingMessage` 恢复为 `true`
- 继续保持 `stream=false`
- 继续保持 `streaming=false`
- 继续保持 `thinking=false`
- 重启真实生效服务 `openclaw-gateway.service`

这次修复的目标很明确：

- 恢复“正在处理”的安全占位
- 不恢复 raw reasoning / partial preview / thinking 文本泄露

修复后预期行为是：

- 用户发消息后 1 到 2 秒内出现处理态反馈
- 最终结果准备好后再完整返回
- 不再出现之前那种循环输出中间推理内容的问题

## 6. 当前项目与目标架构之间仍然存在的差距

虽然主方向已经明确，但现在还没有完全收干净，主要差距有四类：

### 1. Skill 内仍保留少量 prompt fallback

当前 `run_napm_query.js` 里仍然存在少量兼容型 fallback，主要用于：

- overview prompt 兜底
- hierarchy catalog 类问法兜底

这些能力现在更适合理解成“兼容入口”，而不是最终主路径。

### 2. 插件层仍然保留一些历史兼容逻辑

当前 `napm-openclaw-plugin` 仍承担：

- 预览消息取消
- 结果刷新保护
- 结果回写保护
- 工具调用守卫

这些保护逻辑短期内必要，但后续仍要继续避免插件层重新长出新的业务语义特例。

### 3. LLM 规则约束还需要继续补强

方向已经对了，但后续还需要继续增强：

- 对象映射约束
- 指标归属约束
- service 与 metric 的兼容约束
- overview scene 白名单
- continuation / follow-up 的结构化约束

目标不是让 LLM 更自由，而是让它在更明确的规则边界内更稳定。

### 4. 可观测性还不够强

后续仍建议继续补齐以下链路日志：

- 原始 prompt
- LLM 产出的 `resolvedQuery`
- Skill 归一化后的 `resolvedQuery`
- 最终发往上游 API 的参数
- 最终 contract 与回包结果

这样后续才能快速判断问题到底出在：

- 语义理解
- 规则校验
- 上游执行
- 最终渲染

## 7. 当前阶段判断

截至 2026-05-13，可以把当前项目状态判断为：

### 1. 主架构方向已经稳定

现在已经不适合再把项目理解成“企业微信插件 + 本地规则主导的 NAPM 网关”，而应该理解成：

```text
OpenClaw 主链负责理解
Skill 负责执行
插件负责接入、守卫和回包保护
```

### 2. 项目已经进入“收口和产品化执行阶段”

当前最重要的事情不再是继续发散新逻辑，而是：

- 收掉历史特例
- 降低插件复杂度
- 稳定 `resolvedQuery` 主链
- 提升线上可定位性

### 3. 今天的修复说明问题已经从“方向不清”进入“细节收口”

今天处理的两个问题很典型：

- `packet loss` 问法跑偏，本质是隐式规则和重复执行问题
- 企业微信无反馈，本质是远端安全占位配置被关掉

这说明现在的大问题已经不再是“整个链路怎么设计”，而是“哪些历史 stopgap 需要继续收掉、哪些真实运行配置要与目标架构保持一致”。

## 10. 最终结论

截至 2026-05-13，项目最值得坚持的方向已经很明确：

- 让 `OpenClaw LLM` 负责语义理解，但必须接受规则限制。
- 让代码负责约束、校验和执行保护，而不是继续在插件里堆业务特例。
- 让企业微信恢复“有处理态反馈但不泄露推理”的体验，而不是在“完全静默”和“推理裸流出”之间二选一。

换句话说，当前项目并不是思路错了，而是已经走到“把正确的主架构继续收干净”的阶段了。
