# 查询工作流第一阶段收口说明

## 背景

线上出现过“系统都有哪些工作组”这类对象清单问题被模型改走 `overview`、`topValues`、直接 API 试错路径的情况，最终把“查询方式错了”误解释成“系统没有工作组”。

根因不是单个对象别名没写全，而是缺少一个统一的工作流分类入口。模型在构造或执行前没有被明确约束：这个问题到底是对象清单、指标清单、下钻目录，还是指标数据查询。

## 本阶段目标

第一阶段只解决工作流分类收口：

- 先判断用户问题属于哪个 workflow。
- 对 `object_inventory` 问题建立硬契约。
- 禁止对象清单问题漂移到 `overview`、`topValues` 等 metric 执行链路。

本阶段不做完整对象本体拆分，也不重写执行内核。后续阶段再推进 `ObjectOntologyService`、`ResolvedQueryBuilder`、`MetadataExecutionKernel` 与 `MetricExecutionKernel`。

## 新增模块

新增：

```text
skills/openclaw-napm-query/services/WorkflowClassifierService.js
```

当前支持的 workflow：

- `object_inventory`
- `metric_inventory`
- `drilldown_catalog`
- `metric_topn`
- `metric_average`
- `metric_timeseries`
- `overview`

典型分类：

```text
系统都有哪些工作组 -> object_inventory + BusinessGroup
系统中有哪些业务 -> object_inventory + WebApplication
系统中有哪些自动识别的应用 -> object_inventory + CompositeApplication
工作组都可以查哪些指标 -> metric_inventory + BusinessGroup
BusinessGroup 可以往下钻到哪里 -> drilldown_catalog + BusinessGroup
```

## Resolver 改造

`NapmResolvedQueryResolverService` 已接入 `WorkflowClassifierService`。

metadata resolvedQuery 现在会补充：

```json
{
  "semanticConstraints": {
    "operation": "metadata_list",
    "workflowType": "object_inventory",
    "targetObjectType": "BusinessGroup"
  }
}
```

这样执行层、审计层和输出层都能看到“这是对象清单查询”，而不是只看到 `service=groups`。

## Plugin 边界改造

plugin 在 `before_tool_call` 阶段新增 `object_inventory` 契约校验。

对于：

```text
系统都有哪些工作组
```

只允许：

```json
{
  "service": "groups",
  "queryModeKey": "metadata",
  "semanticConstraints": {
    "operation": "metadata_list"
  },
  "groups": [
    { "type": "BusinessGroup" }
  ]
}
```

不允许：

```json
{
  "service": "topValues",
  "groups": [
    { "type": "BusinessGroup", "argument": "all" }
  ]
}
```

如果发生漂移，plugin 返回：

```text
object_inventory_contract_mismatch
```

并要求 OpenClaw 重新构造 resolvedQuery。

## 回归测试

新增：

```text
test/workflow-classifier-service.test.js
```

补充：

```text
test/napm-openclaw-plugin-business-inventory-guard.test.js
test/napm-resolved-query-resolver-service.test.js
```

验证点：

- “系统都有哪些工作组”必须识别为 `object_inventory + BusinessGroup`。
- “系统中有哪些业务”必须识别为 `object_inventory + WebApplication`。
- “系统中有哪些自动识别的应用”必须识别为 `object_inventory + CompositeApplication`。
- “工作组都可以查哪些指标”必须优先识别为 `metric_inventory`，不能误判为 object inventory。
- “BusinessGroup 可以往下钻到哪里”必须优先识别为 `drilldown_catalog`。
- 工作组清单问题如果被构造成 `topValues + BusinessGroup + argument=all`，plugin 必须拦截。

## 当前边界

本阶段只是第一步，仍保留现有 `ObjectMetadataRegistry` 和 `NapmMetadataService` 的 provider 执行逻辑。

下一阶段建议继续做：

1. 建 `ObjectOntologyService`，把对象别名、provider、executionGroupType 统一收口。
2. 建 `ResolvedQueryBuilder`，让 workflow + objectType 统一生成 resolvedQuery。
3. 拆分 `MetadataExecutionKernel` 和 `MetricExecutionKernel`，从物理入口上阻断 metadata / metric 串线。
