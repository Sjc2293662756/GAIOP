# 2026-04-28 业务与业务组识别链路复盘

## 1. 背景与问题现象

说明：本文是 2026-04-28 的历史复盘，下面提到的文件路径已按当前仓库结构或“已移除”状态重新标注。

在 2026-04-28 的联调中，围绕以下问句出现了多次不一致行为：

- `系统中有哪些业务？`
- `系统中有哪些业务组？`
- `哪个 Web 应用 HTTP 500 最多？`
- `101.254.114.238 昨天连接失败数是多少？`

主要现象：

- 同类问句有时被识别为 `WebApplication`，有时被识别为 `BusinessGroup`。
- 部分请求虽然查询成功，但 OpenClaw 侧回复“未查到数据”或叙述不自然。
- 指标别名偶发透传到上游 API（如 `connectionFailureCount`、`http500Count`），导致 400 或执行偏差。

---

## 2. 当前架构事实（本轮确认）

- 网关当前运行模式：`GATEWAY_QUERY_ONLY_MODE=true`。
- 网关职责：执行上游结构化 `resolvedQuerySeed`，不做完整本地判定打分。
- 决策来源：上游 OpenClaw `assistantDecision/resolvedQuerySeed`。
- 叙述职责：以 OpenClaw 为主（网关返回 `narrationInput` 机器载荷）。

关键含义：

- 当上游把对象类型传成 `BusinessGroup` 时，网关会按契约执行，不会“主动改语义”。
- 所谓“通过”，是通过执行契约校验，不是网关内部语义打分通过。

---

## 3. 时间线与定位结论

## 3.1 业务被查成业务组

用户在 `17:05:38` 提问 `系统中有哪些业务？`，返回为 `type=businessGroups`。

日志确认：

- `napm_metadata_named_groups_completed` 记录的 `gatewayRequest.groups[0].type=BusinessGroup`
- 执行参数为 `type=businessGroups&json=true`

结论：

- 本次不是网关“误改”，而是上游传入的结构化对象就是 `BusinessGroup`。

## 3.2 “未查到数据”与叙述异常

网关回放显示有真实数据，但 OpenClaw 偶发输出“未查到”。

定位结果：

- 技术上属于“机器载荷字段消费不一致”风险：调用侧可能读取了旧字段或单字段判空。
- 已在 skill 输出中加强 `rows/structuredRows/summary.rowCount/summary.empty` 的兼容信号，降低误判概率。

## 3.3 指标别名透传问题

出现过：

- `connectionFailureCount`
- `http500Count`

定位结果：

- 别名未充分归一时会进入执行层，引发错误或查询偏差。
- 已补齐别名归一与执行前约束，避免无效指标字符串直透上游。

## 6. 根因总结

本轮问题不是单点故障，而是三类问题叠加：

- 上游对象判定漂移：`业务` 与 `业务组` 在部分轮次识别不稳定。
- 别名归一缺口：个别指标别名未及时映射到标准码。
- 叙述消费不一致：上游叙述侧对机器载荷字段存在历史兼容差异。
