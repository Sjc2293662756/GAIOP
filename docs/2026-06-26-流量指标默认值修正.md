# 流量指标默认值修正：TPIO → BYTIO

日期：2026-06-26

## 问题

用户问"流量最大的IP"或"流量最大的应用"时，系统错误地使用 TPIO（吞吐速率）查询，而非用户期望的 BYTIO（累计传输量/总字节数）。

```
TPIO = 吞吐速率 (Kbps) → 适合 "带宽" "速率"
BYTIO = 总传输量 (data) → 适合 "流量最大" "总共传了多少" "累计流量"
```

## 修改

| 文件 | 改动 |
|------|------|
| `agents/openai.yaml` | Critical anti-patterns 新增：流量默认 → BYTIO，吞吐/带宽 → TPIO |
| `references/chinese-semantic-metric-mapping.md` | 3.3节表格：流量列默认值换为 BYTIO；对象速查矩阵全量修正；line 205 错误说明修正 |
| `services/TagNormalizer.js` | METRIC_CODE_MAP: traffic → BYTIO（备用） |

## 插件层兜底修正

日期：2026-06-28（追加）

### 问题

`openai.yaml` 的 prompt 层修正被 LLM thinking 模式无视。17:43 查询仍然返回 TPIO（kb/s）而非 BYTIO（MiB）。

### 修复

`napm-openclaw-plugin.remote.js` 的 `prepareSkillExecutionArgs`：在 `maybeAutoRepairResolvedQuery` 之后增加硬修正逻辑：

- 若 `resolvedQuery` 使用 TPIO
- 且 `prompt` 含"流量"但不含"吞吐/带宽/速率/throughput"
- → 强制替换 `metric`、`topMetric`、`metrics` 中的 TPIO → BYTIO

```javascript
const usesTPIO = metric === 'TPIO' || topMetric === 'TPIO' || metrics.includes('TPIO');
const isTrafficIntent = /流量/.test(prompt) && !/吞吐|带宽|速率|throughput/i.test(prompt);
if (usesTPIO && isTrafficIntent) { /* 强制替换 TPIO → BYTIO */ }
```

### 层级说明

```
prompt 层 (openai.yaml)     → LLM 经常无视  ← 不可靠
插件层 (prepareSkillExecutionArgs) → 强制执行     ← 可靠
```

## 映射规则

```
用户说 "流量最大" / "流量最多" / "流量排行" → BYTIO
用户说 "带宽" / "吞吐" / "速率" / "吞吐量" → TPIO
```

## 附带修复：TopN 结果截断 bug

日期：2026-06-28

### 问题

用户请求 `topCount=20`，NAPM API 返回了 20 条数据，但 LLM 只展示了 10 条。LLM 误判为"系统只采集到 10 个IP"。

### 根因

`OpenClawNarrationContractService.js` 的 `buildTopnStructure` 函数第 443 行硬编码 `rows.slice(0, 10)`，无论实际返回多少条，narration 结构最多只包含 10 条。LLM 基于 narration 结构生成回答，看不到 10 条之后的数据。

### 修复

```javascript
// 修复前
const items = rows.slice(0, 10).map(...)

// 修复后
const displayLimit = Math.max(
  Number(payload?.resolvedQuery?.topCount) || 10,
  rows.length > 0 ? Math.min(rows.length, 50) : 10
);
const items = rows.slice(0, displayLimit).map(...)
```

取 `resolvedQuery.topCount` 作为展示上限（上界 50），跟随用户的实际请求。

## 附带修复：时间戳年份检查增强

日期：2026-06-28

### 问题

LLM 查询时首次使用了 2025-07-05 的时间戳（距当前 2026-06-28 约 358 天），自动修正未触发，导致 NAPM API 返回空数据。LLM 自行发现后重试才拿到正确结果。

### 根因

`ResolvedQueryTimeRangeService.isTimestampFresh` 使用 400 天阈值判断。2025-07-05 距当前 358 天 < 400 天 → 判定"新鲜" → 不修正。但年份错了（2025 vs 2026），应该无条件修正。

### 修复

`ResolvedQueryTimeRangeService.js`:

1. `isTimestampFresh` — 新增年份检查：年份不匹配直接返回 false
2. `autoCorrectTimestampIfStale` — 年份不匹配优先修正，不再依赖距离阈值

```javascript
// isTimestampFresh 新增:
const tsYear = new Date(value * 1000).getFullYear();
const nowYear = new Date(nowSeconds * 1000).getFullYear();
if (tsYear !== nowYear) return false;  // 年份不对 → 直接判过期

// autoCorrectTimestampIfStale 新增:
if (tsDate.getFullYear() !== nowDate.getFullYear()) {
  tsDate.setFullYear(nowDate.getFullYear());  // 保留月日时分，只改年份
  return alignToMinute(Math.floor(tsDate.getTime() / 1000));
}
```
