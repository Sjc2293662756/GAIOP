# NAPM 查询轮次统一决策与澄清机制重构方案

日期：2026-08-30
状态：rc.38 阻断项本地整改完成，未部署
范围：`napm-skill-query` 插件契约、查询轮次状态、Resolution Spec、查询 Skill、OpenClaw Hook 和相关测试

## 1. 问题结论

“最近 7 天应用流量趋势如何？”暴露的不是一条应用关键词规则缺失，而是查询轮次没有统一的权威状态：

1. 模型可以直接生成正确澄清，但没有产生 Tool 记录；
2. `before_message_write` 把“没有 Skill 结果”统一解释成查询失败；
3. 正确澄清因此被 generic guard 覆盖；
4. 另一条路径又可能把 Application 错误构造成 `TotalTraffic` 并获得真实但口径错误的数据；
5. `before_prompt_build`、`before_tool_call`、Tool execute、Skill 和输出 Hook 分别维护自己的判断，规则不断增加但决策所有权没有集中。
6. 同一会话的重叠 run 通过 conversation latest turn 取状态，早先 run 的 Tool 或输出 Hook 可能读到后续 turn；
7. 查询修复预算和结果交付仍依赖旧 `ConversationOperationState`，与 Query Turn 形成双权威源；
8. `VALIDATION_FAILURE` 和 `EXECUTION_FAILURE` 等失败终态仍可能被后续写入覆盖；
9. 澄清后的“HTTP”续答没有由插件恢复 pending Query Draft，测试只能依赖上游预构造完整查询；
10. 直接 Tool execute、模型漏调 Tool、流式 partial 和其他 Skill 路由缺少同一套确定性边界。

本次重构不继续增加 Hook 特判。目标是建立一个查询轮次协调 module，使查询动作、执行结果和最终交付都依赖同一份 Query Decision。

## 2. 领域模型

### 2.1 Monitoring Question

用户的自然语言 NAPM 查询问题。它是 Query Draft 的来源；Query Draft 形成后，原文只用于审计和高风险语义一致性检查。

### 2.2 Query Draft

OpenClaw 对 Monitoring Question 的结构化解释。Query Draft 可以缺少必须由用户选择的参数，因此不可直接调用 Query Skill 或南向接口。

### 2.3 Query Decision

Query Decision Policy 对 Query Draft 的权威评估，只允许三种动作：

| action | 含义 | 是否调用 Query Skill | 是否调用南向接口 |
| --- | --- | ---: | ---: |
| `ASK_CLARIFYING_QUESTION` | 缺少必须由用户补充的信息 | 否 | 否 |
| `EXECUTE_QUERY` | 已生成完整 Resolved Query | 是 | 是 |
| `REJECT_QUERY` | 操作、对象或指标不受支持 | 否 | 否 |

模型传入的 `decision`、`policyAction` 或自然语言回答不得覆盖 Query Decision Policy 的结果。

### 2.4 Resolved Query

通过 Query Decision Policy 全部校验后的完整、可执行查询。只有 `EXECUTE_QUERY` 可以携带 Resolved Query 进入 Query Skill。

### 2.5 Query Turn

一个 Monitoring Question 的完整生命周期记录，以 `conversationKey + turnId` 为身份。`conversationKey` 只表示 scope，不指向当前或最新轮次。Query Turn 保存路由、Draft、Decision、Attempts、修复预算、终态内容和交付声明，但不让 Query Skill 保存会话状态。

### 2.6 Run Binding

`message_received` 为当前 OpenClaw run/message 创建 `turnId` 并建立不可变绑定。Tool 和输出 Hook 只能通过当前 run/message 的可信绑定读取 Query Turn；缺少 run/message identity 或找不到绑定时 fail-closed，任何情况下都禁止回退到 conversation 中的 latest `turnId`。

### 2.7 Query Attempt

一次有身份的结构构造或执行尝试。`attemptId` 用于处理同一 Tool 生命周期回调的幂等重放。首次技术校验失败记录一个 `CONSTRUCTION/FAILED` attempt、进入 `REPAIR_PENDING` 并消耗唯一一次修复预算；第二个构造失败终止。执行 attempt 失败立即终止。

### 2.8 Pending Clarification

`CLARIFICATION` 后由 Coordinator 在 conversation scope 保存缺少参数的权威 Query Decision Draft。应用语义被错构为 `TotalTraffic` 时，Policy 先把 pending Draft 规范化为无参数 `DefinedApp`。下一轮用户只回复对象名时，模型调用 `napm-skill-query` 并传 `clarificationAnswer`；插件创建新 Query Turn、恢复 pending Draft、补入声明的 `groups[n].argument`，随后消费 pending 记录。

## 3. 目标调用链

```text
Monitoring Question
  -> message_received creates turnId and immutable run/message binding
  -> OpenClaw constructs Query Draft, or sends clarificationAnswer for a pending Draft
  -> napm-skill-query Tool adapter
  -> Query Decision Policy
       -> ASK_CLARIFYING_QUESTION: local clarification, no Skill, no southbound
       -> EXECUTE_QUERY: validated Resolved Query -> Query Skill -> NAPM
       -> REJECT_QUERY: local rejection, no Skill, no southbound
  -> Query Turn Coordinator records Attempts and terminal finalContent
  -> before_message_write/message_sending resolve the same run-bound Query Turn
  -> exactly one final delivery for every terminal outcome
```

## 4. 状态模型

路由、动作、阶段和结果不得再混成一个枚举。

| 维度 | 值 |
| --- | --- |
| route | `MODEL_OWNED` / `NAPM_QUERY` / `OTHER_SKILL` |
| phase | `RECEIVED` / `REPAIR_PENDING` / `DECIDED` / `EXECUTING` / `TERMINAL` |
| action | `ASK_CLARIFYING_QUESTION` / `EXECUTE_QUERY` / `REJECT_QUERY` |
| outcome | `CLARIFICATION` / `RESULT` / `NO_DATA` / `REJECTION` / `VALIDATION_FAILURE` / `EXECUTION_FAILURE` / `CONTRACT_VIOLATION` |
| attempt kind | `CONSTRUCTION` / `EXECUTION` |
| attempt status | `STARTED` / `SUCCEEDED` / `FAILED` |

状态不变量：

1. `conversationKey` 只作 scope；同一 conversation 内重叠 run 各自绑定不同且不可变的 `turnId`；
2. `ASK_CLARIFYING_QUESTION` 不得携带 `error`，Tool Result 的 `isError` 必须为 `false`；
3. 只有 `EXECUTE_QUERY` 可以进入 `EXECUTING`；
4. 首次技术校验失败进入 `REPAIR_PENDING` 并消耗一次修复预算；同一 `attemptId` 重放不重复计数；第二个失败终止；
5. 执行失败立即进入 `EXECUTION_FAILURE`，不使用结构修复预算；
6. 所有 `TERMINAL` 都 write-once，不允许被 Decision、Result 或 Failure 覆盖；只有 delivery claim 可从未声明单调变为已声明；
7. `RESULT` 和 `NO_DATA` 与澄清、拒绝、失败、契约违规一样必须生成非空权威 `finalContent`；
8. 同一 Query Turn 最多声明一次最终交付，重复发送必须取消；
9. Tool 和输出 Hook 不得以 conversation 范围的“最新结果”或最新 `turnId` 代替当前 run 的绑定；
10. 流式 partial 和进度文本不产生终态；
11. `OTHER_SKILL` 和 `MODEL_OWNED` 轮次不由普通查询 Coordinator 抢占最终交付。
12. route 在 Query Turn 创建后不可变；Tool 名称、Tool Decision 或 Tool Result 都不得重分类本轮 route。
13. 非流式最终输出到达时，`RECEIVED` 且没有 Decision/Attempt 终结为 `CONTRACT_VIOLATION`；`REPAIR_PENDING` 终结为 `VALIDATION_FAILURE`；`DECIDED` 且 Tool adapter 未开始执行终结为 `CONTRACT_VIOLATION`；`EXECUTING` 且没有结果终结为 `EXECUTION_FAILURE`。普通查询不得以非终态完成输出，迟到结果不得覆盖已写入终态。

## 5. Module 设计

### 5.1 QueryDecisionPolicy

位置：`skills/openclaw-napm-query/services/QueryDecisionPolicy.js`

职责：

- 读取 `ResolutionSpecService`；
- 校验 service、queryModeKey、对象、指标、时间和参数策略；
- 统一执行 Monitoring Question 与 Query Draft 的高风险语义一致性检查；
- 输出 `ASK_CLARIFYING_QUESTION / EXECUTE_QUERY / REJECT_QUERY`；
- 不读写会话 Map，不调用 Query Skill，不调用南向接口。

`ResolutionSpecService.evaluateQueryArgumentPolicy()` 继续作为参数策略事实来源，不在 Plugin Hook 中复制相同规则。

### 5.2 QueryTurnCoordinator

位置：`plugin/QueryTurnCoordinator.js`

职责：

- 创建和读取 Query Turn；
- 建立并解析不可变 run/message 到 turnId 的绑定；
- 接收 Query Decision；
- 记录 construction/execution Query Attempt 和一次修复预算；
- 保存、恢复并消费 pending clarification Query Draft；
- 记录 Query Result、无数据、校验失败、执行失败或契约违规；
- 保护所有 terminal 状态不被后续写入覆盖；
- 为每一种 terminal outcome 生成当前轮权威 `finalContent`；
- 提供交付幂等声明；
- 隐藏 Map、TTL、fingerprint 和状态转换实现。

Query Turn 使用 `conversationKey + turnId` 作为键，run/message binding 使用 `conversationKey + runId/messageId` 定位该键；pending clarification 只在 conversation scope 暂存。Query Skill 不直接读取或推进这些状态。

### 5.3 napm-skill-query Tool adapter

Tool adapter 是 OpenClaw 与查询领域之间的 seam：

1. 校验插件签发的可信 `traceId`，解析 conversation scope 和当前 `turnId`；缺少绑定时在时间物化与策略校验前 fail-closed；
2. 接收 Query Draft；
3. 澄清续答时接收 `clarificationAnswer`，从 Coordinator 恢复 Query Decision Policy 规范化后的 pending Query Draft；
4. 已处于 `EXECUTING` 时在处理重放 Draft 前返回 `QUERY_EXECUTION_IN_PROGRESS`；
5. 在 Hook 和 direct execute 两条入口调用同一 QueryDecisionPolicy；
6. 对追问和拒绝直接返回结构化正常结果；
7. 对执行动作把 Resolved Query 交给现有 Query Skill；
8. 把 Attempt、Decision、Result 或 Failure 写入 QueryTurnCoordinator；
9. 返回确定性 Tool Result。

高风险语义检查不得只存在于 `before_tool_call`：direct execute 也必须覆盖 Application 趋势/平均值/排行与 `TotalTraffic` 范围错配、`CompositeApplication` 和一般对象清单契约、无 prompt 的 `overview/auto_apps`，包括对象清单只允许单 group。任何未获得 `EXECUTE_QUERY` 的输入都不得调用南向接口。

过渡阶段允许旧 `resolvedQuery` 输入作为 Query Draft 兼容别名。所有生产提示、测试和调用方迁移后再删除兼容入口。

## 6. Resolution Spec 职责

Resolution Spec 只负责静态领域策略：

- service 和 queryModeKey；
- 对象与指标兼容性；
- 参数 `required / optional / forbidden`；
- 哪类缺失需要用户澄清；
- 澄清字段和稳定提示模板；
- 可执行时间、粒度和服务必填字段。

以下内容不得写入 Resolution Spec：

- Hook 调用顺序；
- Query Turn 生命周期；
- 交付幂等状态；
- 会话 Map 或 TTL；
- 是否覆盖模型最终文本。

## 7. Hook 职责

| Hook | 重构后职责 |
| --- | --- |
| `message_received` | 创建 turnId，绑定当前 run/message；识别名称型澄清续答并恢复 pending Draft |
| `before_prompt_build` | 注入稳定路由契约；NAPM 查询即使需要澄清也必须调用 `napm-skill-query` |
| `before_tool_call` | 按当前 run binding 注入可信 conversationKey/turnId，执行统一策略并记录 construction attempt；缺少绑定时 fail-closed，禁止读 latest turn；普通查询的错误生产 Tool 直接阻断 |
| Tool execute | 再次执行统一策略以防直接调用绕过；必要时执行 Query Skill，记录 execution attempt 和终态 |
| `before_message_write` | 非流式 final 从 run-bound Query Turn 读取权威内容；`RECEIVED` 无 Decision/Attempt 或 `DECIDED` 且 adapter 未开始执行，记录 `CONTRACT_VIOLATION`；`REPAIR_PENDING` 记录 `VALIDATION_FAILURE`；`EXECUTING` 无结果记录 `EXECUTION_FAILURE` |
| `message_sending` | 从同一 run-bound Query Turn 声明 exactly-once 最终交付；流式 partial 不终结轮次 |

普通查询不再依赖 `shouldRequireSkillBackedReply()` 或 `shouldForceSkillRecordForPrompt()` 的猜测来决定是否执行/交付。`NAPM_QUERY` 在最终输出前仍未调用 Tool，或 Tool Decision 已接受执行但 adapter 未启动时，Coordinator 记录确定性的 `CONTRACT_VIOLATION`；等待结构修复却直接进入最终输出时记录 `VALIDATION_FAILURE`；adapter 已进入执行却没有产生结果时记录 `EXECUTION_FAILURE`。旧 guard 只服务尚未迁移的其他工作流，不能成为普通查询权威源。

## 8. 澄清与错误契约

### 8.1 正常澄清

```json
{
  "ok": true,
  "responseType": "clarification_required",
  "decision": {
    "action": "ASK_CLARIFYING_QUESTION",
    "reasonCode": "GROUP_ARGUMENT_REQUIRED",
    "missingFields": ["groups[0].argument"],
    "clarifyingQuestion": "应用流量趋势需要指定具体应用名称，请告诉我要查询哪个应用。",
    "southboundAllowed": false
  }
}
```

### 8.2 合法空结果

完整 Resolved Query 已执行但无数据时返回 `NO_DATA`，Coordinator 同时生成非空权威 `finalContent`。只有该终态允许使用“当前对象、指标和时间范围未返回数据点”。

### 8.3 校验失败

模型输出无法形成 Query Draft、服务不存在或结构损坏属于技术校验失败，它不是用户缺少参数。首次失败记录 attempt、进入 `REPAIR_PENDING` 并消耗一次修复预算；同一 `attemptId` 重放幂等。修复后的第二个失败，或 `REPAIR_PENDING` 时非流式最终输出先到而放弃修复，均进入 terminal `VALIDATION_FAILURE`，生成确定性 `finalContent` 并停止重试。

### 8.4 执行失败

Query Skill、元数据或南向调用失败属于 `EXECUTION_FAILURE`，立即终止并生成失败 `finalContent`。Query Turn 已进入 `EXECUTING`，但非流式最终输出先到且仍没有执行结果时，也以 `QUERY_EXECUTION_RESULT_MISSING` 终结为 `EXECUTION_FAILURE`。不得改写成澄清、无数据或健康结论，也不得被迟到的成功或失败覆盖。

### 8.5 契约违规

`NAPM_QUERY` 轮次到达非流式最终输出时仍没有 Tool Decision 或 Attempt，说明模型漏调了必需的 `napm-skill-query`，以 `MODEL_OMITTED_REQUIRED_TOOL` 记录 terminal `CONTRACT_VIOLATION`。若已有 `EXECUTE_QUERY` Decision、状态停在 `DECIDED`，说明 Tool adapter 未开始执行，以 `QUERY_TOOL_EXECUTION_NOT_STARTED` 记录同类终态。两者都输出确定性安全文案且不调用新的南向接口；判断不依赖旧 prompt 猜测 guard。

### 8.6 最终内容与流式输出

`CLARIFICATION`、`RESULT`、`NO_DATA`、`REJECTION`、`VALIDATION_FAILURE`、`EXECUTION_FAILURE` 和 `CONTRACT_VIOLATION` 都必须持有非空、write-once 的 `finalContent`。`before_message_write` 只负责替换为当前 run-bound 内容，`message_sending` 只负责一次性交付声明；流式 partial/preview 不记录终态。

## 9. 关键示例

### 9.1 未命名 Application 趋势

```text
最近 7 天应用流量趋势如何？
-> Query Draft: timeValues + DefinedApp + TPIO + last7days
-> argumentPolicy: DefinedApp single-object trend requires argument
-> Query Decision: ASK_CLARIFYING_QUESTION
-> Query Skill calls: 0
-> southbound calls: 0
-> final: ask for the concrete Application name
```

### 9.2 用户补充名称

```text
HTTP
-> model calls napm-skill-query with clarificationAnswer=HTTP
-> create a new run-bound Query Turn linked to the clarification turn
-> restore and consume the pending Query Draft from the same conversation scope
-> set DefinedApp.argument=HTTP
-> Query Decision: EXECUTE_QUERY
-> Resolved Query -> Query Skill -> NAPM
```

### 9.3 全局流量趋势

```text
最近 7 天总流量趋势如何？
-> TotalTraffic without argument
-> Query Decision: EXECUTE_QUERY
```

### 9.4 错误范围

```text
Monitoring Question says Application trend
Query Draft says TotalTraffic
-> Query Decision: ASK_CLARIFYING_QUESTION
-> never execute the global query
```

该检查在 `before_tool_call` 和 direct Tool execute 两条入口都执行；通过任何入口都不能用真实总流量数据回答应用问题。

### 9.5 对象清单的单 group 契约

```text
CompositeApplication inventory mapped to overview/auto_apps, with argument="all", or with an extra group
-> Query Decision: VALIDATION_FAILURE
-> Query Skill calls: 0
-> southbound calls: 0
```

一般对象清单也必须满足 `service=groups + queryModeKey=metadata + groups=[{type: targetObjectType}]`，因此对象清单只允许一个 group；其他查询仍可按 Resolution Spec 使用合法的多级 group path。

## 10. 分阶段实施

1. 文档和领域术语：增加 Query Draft、Query Decision 和 Query Turn；
2. 特征测试：固定当前合法执行、空结果、追问和失败行为；
3. 决策策略：实现 QueryDecisionPolicy 及参数矩阵；
4. 状态协调：实现 QueryTurnCoordinator、run binding、Attempts、修复预算、pending clarification 和非法转换测试；
5. Tool 接入：澄清改为正常 Tool Result，增加 `clarificationAnswer`，direct execute 复用统一策略；
6. Hook 接入：输出只读取当前 run-bound Query Turn 终态；
7. 旧状态降权：普通查询不再以 ConversationOperationState 或 prompt 猜测 guard 作为修复和交付权威源；
8. 契约同步：更新工作区规则、Skill/工作流契约、Tool Schema、项目和设计文档；
9. 质量门禁：完整测试、lint、runtime contract 和差异审查。

## 11. 测试矩阵

### 决策策略

- `DefinedApp + timeValues` 缺 argument -> CLARIFICATION；
- `WebApplication + averageValues` 缺 argument -> CLARIFICATION；
- `DefinedApp + topValues` 无 argument -> EXECUTE；
- `groups + DefinedApp` 无 argument -> EXECUTE；
- `TotalTraffic + timeValues` 无 argument -> EXECUTE；
- `TotalTraffic` 携带 argument -> REJECT；
- Application 问句与 `TotalTraffic` Draft 冲突 -> CLARIFICATION；
- Application 排行问句与 `topValues + TotalTraffic` Draft 冲突 -> VALIDATION_FAILURE；
- `CompositeApplication`/一般对象清单形状错配 -> VALIDATION_FAILURE；
- 无 prompt 的 `overview/auto_apps` -> VALIDATION_FAILURE；
- 任意普通查询包含多个 group -> VALIDATION_FAILURE；
- 上述高风险检查在 direct execute 中同样生效。

### Tool 与南向调用

- 澄清结果 `ok=true`、`isError=false`；
- 澄清不调用 Query Skill、NapmClient 或元数据目录；
- 完整 Resolved Query 恰好执行一次；
- 缺少可信 `traceId`/scope/turn 的 direct execute 在校验前失败，南向调用为 0；
- `EXECUTING` 中的重叠 Tool 即使携带损坏 Draft 也在校验前返回执行中状态，南向调用总数仍为 1；
- 合法空结果为 `NO_DATA`；
- 技术错误为 `EXECUTION_FAILURE`；
- 首次技术校验失败进入 `REPAIR_PENDING`，同 attempt 幂等，第二个失败 terminal；
- 澄清、拒绝、校验失败均无错误南向调用；
- 用户只回复 `HTTP` 时，Tool 输入只有 `clarificationAnswer`，插件恢复 Draft 后恰好执行一次。

### Hook 和 Query Turn

- Query Decision 在 `before_message_write` 和 `message_sending` 中一致；
- 正确澄清不被 generic guard 覆盖；
- 每种 terminal 都有权威 `finalContent`，同一 turn 只发送一次；
- 同一会话两个重叠 run 的 Tool 和输出 Hook 始终读取各自 turn；
- runtime 在 Hook 间改变 runId 时仍使用 message binding；
- 缺少 runId/messageId 时输出 Hook fail-closed，不读取或 claim 同会话其他 turn；
- 不同 conversation 不共享 Query Draft 或 Query Result；
- 所有 terminal 不被同轮后续 Decision/Result/Failure 覆盖；
- 模型绕过 Tool 时记录 `CONTRACT_VIOLATION` 并确定性交付；
- 非流式最终输出收口覆盖全部非终态：`RECEIVED`/`DECIDED` 为契约违规、`REPAIR_PENDING` 为校验失败、`EXECUTING` 为执行失败；
- 非流式 reasoning 样式文本不能绕过 `CONTRACT_VIOLATION`；错误的其他生产 NAPM Tool 不能改变 route，且无南向调用；
- 流式 partial 不终结 Query Turn；
- `OTHER_SKILL` 轮次不被普通查询 Coordinator 抢交付。

## 12. 验收标准

企业微信新会话必须满足：

| 输入 | 预期 |
| --- | --- |
| 最近 7 天应用流量趋势如何？ | 追问具体应用名称；无南向调用 |
| HTTP | 查询 `DefinedApp + argument=HTTP` |
| 最近 7 天总流量趋势如何？ | 查询 `TotalTraffic` |
| 应用流量最高的是哪些？ | `topValues + DefinedApp`，不要求单对象名称 |
| 系统中有哪些应用？ | `groups + DefinedApp` |

审计必须能从 run/message binding 定位同一个 `turnId`，并看到 Query Draft、Attempts、修复预算、Query Decision、是否允许南向、Query Result、terminal `finalContent` 和最终交付状态。澄清续答还应记录 `parentTurnId` 和 `clarificationAnswer`。

## 14. 本地实施记录

本次已经完成以下代码落地：

1. `QueryDecisionPolicy` 集中分类追问、执行、拒绝和技术校验失败，并统一覆盖应用/总流量、对象清单、`CompositeApplication` 和对象清单单 group 高风险检查；
2. `QueryTurnCoordinator` 保存 Query Turn、不可变 route 与 run/message binding、Attempts、一次修复预算、pending clarification、所有 terminal `finalContent` 和 delivery claim；
3. `napm-skill-query` Tool schema 以 `queryDraft` 为主入口、兼容同形 `resolvedQuery`，并增加 `clarificationAnswer` 续答入口；
4. `message_received` 为每个 run/message 建立独立 turn，名称型续答恢复 pending Draft 并创建带 `parentTurnId` 的新 turn；
5. `before_tool_call` 和 direct Tool execute 复用统一 Query Decision Policy，未获 `EXECUTE_QUERY` 时 Query Skill/南向调用均为 0；
6. 首次技术校验失败进入 `REPAIR_PENDING`，同 attempt 幂等，修复后的第二个失败终止；执行失败立即终止；所有 terminal write-once；`EXECUTING` 重放在 Draft 处理前返回执行中结果，终态 Tool 重放返回已有权威结果，两者均不再调用 Query Skill/南向接口；
7. `before_message_write` 和 `message_sending` 从当前 run-bound Query Turn 读取同一权威 `finalContent`，所有 outcome exactly-once；流式 partial 不终结；
8. 非流式最终输出到达时，模型未调用必需 Tool（包括 reasoning final）或 Tool 已决策但 adapter 未执行，记录 `CONTRACT_VIOLATION`；等待结构修复时记录 `VALIDATION_FAILURE`；执行已开始但仍无结果时记录 `EXECUTION_FAILURE`。普通查询调用错误的其他生产 NAPM Tool 会被阻断且不改 route，其他 Skill 不由普通查询 Coordinator 抢交付；
9. 旧 `ConversationOperationState` 不再是普通查询修复、结果和交付权威源；Query Skill CLI 仍保持无状态，只执行完整 Resolved Query；
10. 已同步工作区规则、查询契约和本设计文档。

已验证场景：

- 未命名 `DefinedApp` 趋势返回 `ok=true`、`isError=false` 的 `CLARIFICATION`；
- “应用流量趋势”错误映射到 `TotalTraffic` 时返回同样的正常澄清；
- 两种澄清路径的 Query Skill / 南向调用次数均为 0；
- 用户下一轮只回复 `HTTP`，模型只传 `clarificationAnswer`，插件恢复 Policy 规范化后的 pending Draft、补 `DefinedApp.argument=HTTP` 并执行一次；
- 明确的 `TotalTraffic` 全局趋势、命名应用趋势、应用排行和应用清单保持可执行；
- 未知 service 等技术性错误按一次修复预算进入 `REPAIR_PENDING` 或 terminal `VALIDATION_FAILURE`；
- Coordinator 参数化单测覆盖全部 terminal write-once；真实插件生命周期测试覆盖重叠 run、稳定 message binding、成功/空数据权威交付、late failure、重复发送、澄清、技术校验和契约违规等重点路径；
- 缺少 run/message identity 的重叠输出 fail-closed；错误 Tool 和非流式 reasoning final 均不能绕过查询契约；
- Tool 已决策但 adapter 未执行时以 `QUERY_TOOL_EXECUTION_NOT_STARTED` 终结；执行已开始但没有结果时以 `QUERY_EXECUTION_RESULT_MISSING` 终结，迟到成功不能覆盖且重复发送被取消；
- direct execute 的范围错配、对象清单和对象清单多 group 校验均确认无错误南向调用；
- direct execute 缺少可信轮次绑定时在校验前失败；`EXECUTING` 重放使用损坏 Draft 仍不会再次校验、改写状态或产生第二次南向调用；
- 应用排行错映射到 `TotalTraffic`、无 prompt 的 `overview/auto_apps` 均被统一策略阻断且南向调用为 0；
- 流式 partial 与 `OTHER_SKILL` 路由不会被普通查询终态逻辑误拦截。
