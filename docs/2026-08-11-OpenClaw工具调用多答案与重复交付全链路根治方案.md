# OpenClaw 工具调用多答案与重复交付根治方案

日期：2026-08-11  
实施范围：NAPM OpenClaw 插件  
当前状态：NAPM-only 修复已部署到 `101.254.114.237`，Gateway 已重启；等待一次真实企业微信入站消息完成最终验收。

## 1. 最终决策

本次故障只修改 NAPM 插件，不修改 OpenClaw 核心，不修改企业微信插件。

原因不是企业微信重试，也不是同一用户问题被处理了两次。真实链路中：

1. 用户消息只入站一次。
2. `napm-alert-query` 只调用一次。
3. 模型正常产生一条带 ToolCall 的过程 Assistant 消息和一条 terminal Assistant 消息。
4. OpenClaw 将两条非空 Assistant 文本构造成两个待投递 payload。
5. NAPM 插件原来在每个 payload 上重建同一份确定性告警正文。
6. 企业微信收到两次发送并分别 ACK，因而展示了两份相同正文。

修复原则：只取消由 NAPM 插件在当前会话、当前轮次明确登记为 ToolCall progress 的 payload。terminal、多段合法回复、相同正文的独立业务消息均不得因内容相同被拦截。

## 2. 明确不采用的方案

以下方案都没有解决身份和生命周期问题，不采用：

- 通用正文去重或正文 SHA 去重。
- 30 秒、90 秒等时间窗口去重。
- “第一条 final 获胜”。
- 全局限制一个用户轮次只能投递一个 payload。
- 根据 `I'll query`、`我来查询` 等固定句式拦截。
- 关闭企业微信 thinking 或 streaming。
- 修改企业微信累加器来掩盖上游重复正文。
- 长期 patch OpenClaw `dist/*.js`。

这些做法会误伤合法多段文本、附件和媒体，也无法区分业务多消息与传输重试。

## 3. 真实故障证据

### 3.1 原始故障

```text
用户问题：现在系统都有哪些告警？
```

已确认事实：

- 企业微信只有一次用户入站。
- Session 协议序列为 `user -> assistant(text + toolCall) -> toolResult -> assistant(stop)`。
- 第一条 Assistant 为过程输出，第二条为正式告警答案。
- Gateway 对两个 payload 各发送一次，两个发送均收到 ACK。
- 企业微信最终可见长度为 `2182 = 1091 * 2`。
- `/new` 已在本轮问题之前完成，不是触发源。

因此企业微信不是重复生产者，也没有发生通道重试。

## 4. 根因

### 4.1 第一层：业务改写粒度错误

OpenClaw 允许一个工具调用轮次产生多个 Assistant 协议消息和多个 payload，这是合法能力。NAPM 插件原来在逐 payload 的 `message_sending` 中重建完整业务答案，导致 progress payload 和 terminal payload 都被改成同一份正文。

正确职责是：

- `before_message_write`：在完整 Assistant message 仍可见时识别 `text + toolCall`。
- `message_sending`：在任何业务正文改写之前，只取消对应的已登记 progress。
- terminal payload：继续进入原有 NAPM 确定性业务改写。

### 4.2 第二层：OpenClaw 两个 hook 的 scope 身份不同

远端 OpenClaw 2026.5.4 的真实上下文为：

```text
before_message_write:
  sessionKey = agent:main:wecom:direct:shijc

message_sending:
  channelId = wecom
  accountId = default
  conversationId = shijc
```

原 `ConversationScopeResolver` 优先使用 `sessionKey`：

```text
session:agent:main:wecom:direct:shijc
```

投递阶段没有 `sessionKey`，只能得到：

```text
conversation:wecom:default:shijc
```

同一个真实会话被解析成两个 scope。账本记录正确，但投递阶段无法按 `scope + turnId` 找回，因此 progress 没有被取消。

原测试在所有 hook 中复用了同一个完整 ctx，掩盖了真实 SDK 上下文差异。

## 5. NAPM-only 设计

### 5.1 AssistantOutputLedger

文件：`plugin/AssistantOutputLedger.js`

账本只登记结构上明确包含 ToolCall 的 Assistant 文本：

```text
scope
turnId
outputId
phase = progress
stopReason
hasToolCall = true
textLength
fingerprint
state = PENDING_DELIVERY
```

消费必须同时满足：

```text
canonical scope 相同
turnId 相同
phase = progress
state = PENDING_DELIVERY
正文长度和指纹与登记记录相同
```

消费后状态变为 `PROGRESS_DELIVERY_SUPPRESSED`，同一记录不能再次消费。

这里的正文指纹是已登记 progress 的完整性校验，不是全局正文去重。没有对应 lifecycle 记录的相同正文不会被拦截。

### 5.2 ConversationScopeRegistry

文件：`plugin/ConversationScopeResolver.js`

`message_received` 同时拿到 session 身份和通道身份时，注册别名关系：

```text
session:agent:main:wecom:direct:shijc
  <- alias ->
conversation:wecom:default:shijc
```

canonical scope 采用可信 `sessionKey`。后续 `before_message_write` 只携带 session 身份、`message_sending` 只携带通道身份时，都会解析为同一个 canonical scope。

注册表约束：

- 只根据 hook 上下文身份字段建立关系，不解析正文。
- 别名有效期 5 分钟。
- 最多 2000 条记录。
- `/new`、`/reset` 清理业务状态时同时清理 scope 别名。
- 多账号通过 `channelId + accountId + conversationId` 隔离。

### 5.3 生命周期

```text
message_received(session + channel identity)
  -> 注册 canonical scope 与 delivery scope 别名
  -> 创建 turnId

before_message_write(session identity)
  -> assistant(text + toolCall)
  -> 登记 canonical scope + turnId + progress
  -> 保留原 ToolCall session 历史

message_sending(channel identity)
  -> 归一到 canonical scope
  -> 在所有业务改写前消费已登记 progress
  -> 命中：cancel=true
  -> 未命中：继续原有 terminal、多 part、媒体和业务改写流程
```

该机制适用于当前八个 NAPM 工具，不依赖具体前导语句式：

```text
napm-skill-query
napm-report-export
napm-packet-analysis
napm-alert-query
napm-alert-packet-analysis
napm-inspection-snapshot
napm-summary
napm-fault-diagnosis
```

## 6. 告警统计口径修复

重复交付之外，原答案还存在独立的数据正确性问题：标题总数使用完整 1741 条，分类却从截断后的 200 条明细重新计算，导致分类合计只有 200。

修复后：

- 总数、分类和严重级别统一读取完整 `summary.byCategory` 与 `summary.byCategoryDetail`。
- `result.events` 只作为明细展示窗口。
- 当总数大于展示窗口时，正文明确区分完整统计口径与明细保留数量。
- 回归夹具断言 `1638 + 80 + 8 + 3 + 8 + 4 = 1741`，不受 200 条展示窗口影响。

## 9. 验收标准

真实企业微信入站必须满足：

```text
inbound user message = 1
napm-alert-query toolCall = 1
tool failure = 0
assistant(text + toolCall) 被登记为 progress
tool_progress_delivery_suppressed = 1（当 progress 含文本时）
terminal 用户答案 = 1
企业微信 terminal 发送 = 1
企业微信 terminal ACK = 1
告警分类合计 = 告警总数
```

纯 ToolCall 没有可见 progress 文本时，不要求出现 suppression 事件，但 terminal 仍只能投递一次。

CLI `openclaw agent --deliver` 不触发真实 `message_received`，不能替代最终入站验收。它可以验证投递，但不能在 Gateway 重启后建立 session scope 与 delivery scope 的别名关系。

## 10. 回滚

若新版本出现模块加载失败、hook handler error 或正常 terminal 被取消：

1. 停止继续验收。
2. 从第二阶段备份恢复 extension/workspace 的主插件和 `ConversationScopeResolver.js`。
3. 重启 `openclaw-gateway.service`。
4. 核对备份 SHA、`gateway ready` 和企业微信认证。

第一阶段备份独立保留，可按需整体回滚 Assistant ledger 和告警统计修复。

## 11. OpenClaw 与企业微信的后续定位

本次不需要修改 OpenClaw 或企业微信源码。

OpenClaw 未来若在 `message_sending` 传播 `sessionKey/turnId/assistantMessageIndex/phase`，NAPM 可以删除当前 scope 兼容映射并直接使用平台身份。这是可选的平台能力增强，不是本次修复的依赖。

企业微信未来只有在真实证据表明同一个发送身份因 ACK 丢失被重投时，才需要引入 `deliveryId` 幂等。本次两个发送各有独立 reqId 且都收到 ACK，不属于该问题。
