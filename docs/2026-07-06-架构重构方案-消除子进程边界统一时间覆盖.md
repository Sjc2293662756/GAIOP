## 一、背景与问题

### 1.1 当前架构

NAPM 系统使用一个约 6000 行的单体 Plugin 文件（`napm-openclaw-plugin.remote.js`），同时承担三种职责：

```
┌─ Plugin 进程 ──────────────────────────────────────┐
│                                                     │
│  1. 注册 Tool（api.registerTool × 7）               │
│  2. Hook 拦截（message_received / before_prompt /   │
│     before_tool_call / message_sending × 5）        │
│  3. 手动 spawn 子进程执行（execFileAsync × 7）      │
│                                                     │
│  runSkillExecutor → spawn run_napm_query.js         │
│  runSummaryExecutor → spawn run_summary.js          │
│  runFaultDiagnosisExecutor → spawn run_fault_dx.js  │
│  runInspectionExecutor → spawn run_inspection.js    │
│  runAlertExecutor → spawn run_alert_query.js        │
│  runPacketExecutor → spawn run_packet_analysis.js   │
│  runReportExecutor → spawn generate_report.js       │
│                                                     │
└─────────────────────────────────────────────────────┘
         │  JSON 序列化（跨进程）
         ▼
┌─ Skill 子进程 ──────────────────────────────────────┐
│  JSON.parse(payload)                                │
│  → 不知道 time 是 Plugin 算的还是 LLM 填的          │
│  → 必须"防御性"地 validateTimeRangeFreshness       │
│  → 必须 autoCorrectTimestampIfStale                 │
└─────────────────────────────────────────────────────┘
```

### 1.2 核心问题

| # | 问题 | 影响 |
|---|------|------|
| 1 | **时间覆盖只在 `runSkillExecutor` 里有**（line 2618-2648），其他 6 个 Executor 没有 | napm-summary、napm-fault-dx 等如果 LLM 传了错误时间戳，不会被 Plugin 覆盖 |
| 2 | **跨进程 JSON 序列化导致信任断裂** | Plugin 用 `Date.now()` 算好了时间，但 Skill 进程收到的只是 JSON 数字，不知道来源，被迫再做防御性校验 |
| 3 | **3 种不同的参数传递方式** | `--payload`（inline JSON）、`--input`（temp file）、`--queryFile`（temp file），增加维护负担 |
| 4 | **7 个 Executor 各自为政** | 错误处理不一致（有的 throw、有的 return）、env var 不一致、maxBuffer 不一致 |
| 5 | **单体文件 6000 行** | 维护困难，改动一个 Executor 可能影响整条链路 |

---

## 二、目标

1. **消除子进程边界** — `require()` 替代 `execFileAsync`，Plugin 和 Skill 在同一 Node.js 进程中运行
2. **统一时间覆盖** — 在 `before_tool_call` Hook 中一处覆盖，7 个 Tool 全部受益
3. **删除冗余校验** — Skill 脚本不再需要 `validateTimeRangeFreshness` + `autoCorrectTimestampIfStale`
4. **Plugin 缩减** — 删除约 1500 行冗余代码

---

## 三、核心设计决策

### 保留 `api.registerTool`，改 `execute()` 内部实现

经过对 OpenClaw 框架接口的探索，确认：
- OpenClaw 的 Skill 系统通过扫描 `skills/*/SKILL.md` 自动发现
- Skill 可配 `agents/openai.yaml`（含 `policy.allow_implicit_invocation`）
- **但 SKILL.md 不会自动变成可执行的 Tool** — 仍然需要 `api.registerTool()` 注册

因此方案是：**保留 Tool 注册机制，但 execute() 内部从 spawn 改为 require()**。

```
改前：execute() → execFileAsync('node', [script, '--payload', JSON]) → stdout → JSON.parse
改后：execute() → require(script).handleSkillCall(params) → 直接返回结果
```

### 不改的部分

| 模块 | 说明 |
|------|------|
| `before_tool_call` Hook 路由逻辑 | LLM Tool 调用拦截（必须保留） |
| `message_sending` Hook | LLM 回复内容拦截（必须保留） |
| `before_prompt_build` Hook | 注入 NAPM 路由 System Context（必须保留） |
| `message_received` Hook | 消息域检测（必须保留） |
| 审计日志 | `appendPluginAuditEvent`（保留） |
| 结果缓存 | `napmResultByPrompt`、`napmDebugApiByPrompt`（保留） |
| 契约校验 | `validateResolvedQueryAgainstSpec`、`normalizeResolvedQueryForPlugin`（保留） |
| 所有 `services/` 目录文件 | NAPM API 调用层完全不变 |

## 四、实施步骤

### 第一步：新建 `src/shared/timeResolver.js`

从两处合并提取时间覆盖逻辑：

- 来源 1：`napm-openclaw-plugin.remote.js` line 2618-2648（时间覆盖核心逻辑）
- 来源 2：`skills/openclaw-napm-query/services/ResolvedQueryTimeRangeService.js`（`isTimestampFresh`、`autoCorrectTimestampIfStale` 等，保留作为参考但不在此模块中重复）

```javascript
// src/shared/timeResolver.js

const DURATION_MAP = {
  last5minutes: 300,
  last1hour: 3600,
  last24hours: 86400,
  last1day: 86400,
  last7days: 604800,
  last30days: 2592000
};

function floorToMinute(v) {
  return Math.floor(v / 60) * 60;
}

/**
 * 根据 timeKey 计算时间范围的 start/end。
 * 与 Plugin line 2628-2641 完全相同的逻辑。
 */
function resolveTimeFromKey(timeKey, nowSeconds) {
  const now = Number.isFinite(nowSeconds) && nowSeconds > 0
    ? nowSeconds
    : Math.floor(Date.now() / 1000);

  if (timeKey === 'today') {
    const d = new Date(now * 1000);
    d.setHours(0, 0, 0, 0);
    const start = floorToMinute(d.getTime() / 1000);
    return { start, end: floorToMinute(now), key: 'today' };
  }

  if (timeKey === 'yesterday') {
    const d = new Date(now * 1000);
    d.setDate(d.getDate() - 1);
    d.setHours(0, 0, 0, 0);
    const start = floorToMinute(d.getTime() / 1000);
    return { start, end: floorToMinute(start + 86340), key: 'yesterday' };
  }

  const duration = DURATION_MAP[timeKey] || 3600; // 默认 1 小时
  const start = floorToMinute(now - duration);
  const end = floorToMinute(now);
  return { start, end, key: timeKey || 'last1hour' };
}

/**
 * 对 resolvedQuery 无条件覆盖 start/end。
 * 只在 service 需要时间参数时执行。
 */
function applyTimeOverride(resolvedQuery, nowSeconds) {
  if (!resolvedQuery || typeof resolvedQuery !== 'object') return;

  const NEEDS_TIME = new Set([
    'topValues', 'averageValues', 'timeValues', 'overview', 'topValues_multi_protocol'
  ]);

  const service = String(resolvedQuery.service || '').trim();
  if (!NEEDS_TIME.has(service)) return;

  const now = Number.isFinite(nowSeconds) && nowSeconds > 0
    ? nowSeconds
    : Math.floor(Date.now() / 1000);

  const timeKey = String(resolvedQuery.timeRange?.key || '').trim() || 'last1hour';
  const range = resolveTimeFromKey(timeKey, now);

  resolvedQuery.start = range.start;
  resolvedQuery.end = range.end;

  if (!resolvedQuery.timeRange || typeof resolvedQuery.timeRange !== 'object') {
    resolvedQuery.timeRange = {};
  }
  resolvedQuery.timeRange.key = timeKey;
}

module.exports = {
  DURATION_MAP,
  floorToMinute,
  resolveTimeFromKey,
  applyTimeOverride
};
```

### 第二步：每个 Skill 脚本新增 `handleSkillCall` 导出

每个 `skills/openclaw-napm-*/scripts/run_*.js` 新增统一的导出接口：

```javascript
/**
 * Plugin 通过 require() 同进程调用的入口。
 * params 已经是 JavaScript 对象，无需 JSON 解析。
 * params.resolvedQuery.start/end 已经由 Plugin 在 before_tool_call Hook 中用 Date.now() 覆盖。
 * 不再需要 validateTimeRangeFreshness / autoCorrectTimestampIfStale。
 */
async function handleSkillCall(params) {
  try {
    // 只做：normalizeResolvedQueryShape → 删除 timeRange.start/end → 执行
    return await executeResolvedQuery(
      params.prompt,
      params.resolvedQuery,
      params,
      null
    );
  } catch (error) {
    return {
      ok: false,
      error: {
        code: error.code || 'SKILL_EXECUTION_ERROR',
        message: error.message || String(error)
      }
    };
  }
}

// 保留 CLI 入口（本地测试用）
if (require.main === module) {
  main().catch((error) => {
    console.error(error);
    process.exit(1);
  });
}

module.exports = { handleSkillCall };
```

```javascript
  const preparedArgs = prepareSkillExecutionArgs(args || {});
  const validation = validateResolvedQueryAgainstSpec(
    preparedArgs?.resolvedQuery,
    getResolvedQueryValidationOptions(preparedArgs)
```

## 六、时间链路变化对比

### 改前（8 个 Stage，3 道防线）

```
Stage 1: LLM 构造 Tool Call
    │   传入 timeRange.key（如 "last1hour"）
    ▼
Stage 2: before_tool_call Hook
    │   validateResolvedQueryAgainstSpec（只校验）
    ▼
Stage 3: Tool execute() 回调
    │   validateResolvedQueryAgainstSpec（再次校验）
    ▼
Stage 4: runSkillExecutor
    │   Date.now() 计算 start/end → 无条件覆盖 ← ★ 主防线
    │   JSON.stringify(payload) → spawn 子进程
    ▼
Stage 5: Skill 进程 JSON.parse
    │   恢复为 JavaScript 对象
    ▼
Stage 6: normalizeResolvedQueryTimeRange
    │   floorToMinute（再次对齐）
    │   validateTimeRangeFreshness（年份校验） ← ★ 冗余
    │   autoCorrectTimestampIfStale（年份修正） ← ★ 冗余
    │   删除 timeRange.start/end
    ▼
Stage 7: RequirementParserService.executeGatewayRequest
    │   start/end → NAPM API URL 参数
    ▼
Stage 8: NAPM API 返回数据
```

### 改后（3 个 Stage，1 道防线）

```
Stage 1: LLM 构造 Tool Call
    │   传入 timeRange.key（如 "last1hour"）
    ▼
Stage 2: before_tool_call Hook
    │   Date.now() 计算 start/end → 无条件覆盖 ← ★ 唯一防线（对所有 7 个 Tool 生效）
    │   validateResolvedQueryAgainstSpec（校验）
    ▼
Stage 3: Tool execute() 回调
    │   require(skill).handleSkillCall(params) ← 同进程函数调用
    │   normalizeResolvedQueryShape（只 floor + 删除 timeRange.start/end）
    │   RequirementParserService.executeGatewayRequest
    │   → NAPM API 返回数据
```

时间覆盖只发生一次，在 `before_tool_call` Hook 中，**对所有 7 个 Tool 统一生效**。

```javascript
  'napm-fault-diagnosis':   { type: 'timeRange',     timeKeyPath: 'timeRange.key',              defaultKey: 'last1hour' },
  'napm-alert-query':       { type: 'alertQuery',    timeKeyPath: 'alertQuery.criteria.timeRange.key', defaultKey: 'last1hour' },
  'napm-inspection-snapshot': { type: 'none' }, // 固定 1 小时，无需覆盖
  'napm-packet-analysis':   { type: 'criteria',      timeKeyPath: 'criteria.timeRange.key',     defaultKey: 'last1hour' },
  'napm-report-export':     { type: 'none' }, // 不需要时间参数
};

const timeConfig = NAPM_TOOL_TIME_PARAM_MAP[toolName];
if (timeConfig && timeConfig.type !== 'none' && isPlainObject(event.params)) {
  const targetObj = timeConfig.type === 'resolvedQuery'
    ? event.params.resolvedQuery
    : timeConfig.type === 'timeRange'
      ? event.params.timeRange
      : timeConfig.type === 'alertQuery'
        ? (event.params.alertQuery?.criteria || event.params)
        : event.params;

  if (isPlainObject(targetObj)) {
    const timeKey = getNestedValue(targetObj, timeConfig.timeKeyPath) || timeConfig.defaultKey;
    const range = resolveTimeFromKey(timeKey, Math.floor(Date.now() / 1000));
    if (timeConfig.type === 'resolvedQuery') {
      targetObj.start = range.start;
      targetObj.end = range.end;
    } else {
      targetObj.start = range.start;
      targetObj.end = range.end;
    }
  }
}
```

### 8b. 7 个 Tool 的 execute() 回调

从各自的 `runXxxExecutor(args)` 改为 `require(skillPath).handleSkillCall(args)`。

统一模式：

```javascript
execute: async (_toolCallId, args) => {
  const preparedArgs = prepareSkillExecutionArgs(args || {});
  // ... 各自的校验逻辑（不变）...

  const skillPath = path.join(OPENCLAW_SKILLS_ROOT, '<skill-dir>/scripts/<script>.js');
  delete require.cache[require.resolve(skillPath)];
  const skillModule = require(skillPath);
  const result = await skillModule.handleSkillCall(preparedArgs);

  // ... 各自的后续处理（rememberXxx、audit 等）...
  return makeToolResult(result);
}
```

## 十、风险与缓解

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| `require()` 缓存导致 Skill 代码更新后不生效 | 中 | 更新不生效，用旧代码 | 每次 execute 前 `delete require.cache[require.resolve(skillPath)]` |
| Skill 脚本的 `require.main === module` 误触发 main() | 极低 | CLI 入口在 require() 时也执行 | 已确认：`require()` 不改变 `require.main`，只有在 `node script.js` 时才触发 |
| 同进程调用后 Skill 内部状态泄漏（全局变量污染） | 低 | 多次调用间数据串扰 | 每个 Skill 的 Service 是无状态的 Class，每次 new 实例 |
| 同进程调用后异常 crash 整个 Plugin 进程 | 中 | 所有 NAPM 功能不可用 | `handleSkillCall()` 内部 catch 所有异常，返回 `{ok:false}` 而非 throw |
| `napm-skill-query` 是唯一用 inline `--payload` 的，与其他 Skill 不统一 | — | — | 统一改为同进程函数调用后，此差异自然消除 |
| 7 个 Tool 的 execute() 错误处理不一致（有的 throw，有的 return） | — | — | 统一为 `handleSkillCall()` 内部 catch + return `{ok:false}` |
| 远端 Node.js 版本不兼容 | 极低 | require() 行为差异 | 确认远端 Node.js 版本 ≥ 14（与本地一致） |
