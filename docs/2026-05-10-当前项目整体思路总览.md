# 2026-05-10 当前项目整体思路总览

最后更新：2026-05-10

## 一句话理解

当前这个项目，已经不应该再理解成“一个自己做自然语言理解的 NAPM 网关”，而应该理解成：

**一个由 OpenClaw 主链负责理解和决策、由 NAPM Skill 负责执行、由 WeCom 通道负责接入和结果承载的 NAPM 查询系统。**

换句话说：

- OpenClaw 决定“这句话属于什么问题、该查什么、该不该追问、该不该拦截”
- NAPM Skill 负责“怎么查、查哪些模块、怎么把结果整理成结构化 narration contract”
- WeCom 负责“消息进出、结果承接、最终回复回写”，但当前实现里它不是完全无逻辑的纯传输层

---

## 当前真实运行链路

现在最准确的主链路应理解为：

```text
企业微信用户
  -> wecom-openclaw-plugin
  -> OpenClaw 主链
  -> napm-openclaw-plugin
  -> openclaw-napm-query skill
  -> NAPM / NetInside WebService
  -> skill 输出 narration contract
  -> OpenClaw / WeCom 渲染最终中文回复
```

这个链路里，真正的“主理解层”不在 skill 内，而在 `OpenClaw 主链 + napm-openclaw-plugin`。

---

## 各层职责边界

### 1. WeCom plugin 的职责

企业微信插件当前不是单纯的“字节转发器”，但它也不是主判断层。

它当前实际承担的职责包括：

- 企业微信消息接入与回复发送
- 接收 NAPM 结构化结果并交给 OpenClaw 渲染
- 对部分 NAPM 回复做结果呈现保护
- 对 overview 类型结果避免被错误的 `displayText` 直接短路
- 在最终回写前，保证概览类回复仍然按“总览/概览”口径输出

它**不应该**承担的职责：

- 作为主语义理解层决定对象语义
- 自己把“应用 / 业务 / 业务组”长期固化成一套独立判断逻辑
- 替代 OpenClaw 主链完成完整的边界判断、追问判断和 `resolvedQuery` 构造

一句话概括：

**WeCom 现在是“接入层 + 结果承载层 + 少量结果保护逻辑”，不是“主判断层”。**

### 2. OpenClaw 主链 + napm-openclaw-plugin 的职责

这一层是当前系统真正的主决策层。

它当前应该负责：

- 判断这是不是 NAPM 范围内问题
- 判断是不是边界外问题
- 判断是不是 follow-up
- 判断是不是需要澄清
- 继承上下文
- 形成结构化 `resolvedQuery`
- 强制 NAPM 相关问题优先走 `napm-skill-query`
- 拦截危险工具调用
- 对 overview 问句做 scene 注入与强制纠偏
- 在最终回消息前，如果发现缓存结果的 scene 与当前问句不一致，强制刷新

这层也是这次排查后最需要记住的一点：

**很多“明明 skill 改对了，线上还是不对”的问题，实际发生在这一层。**

### 3. Skill 的职责

`openclaw-napm-query` skill 现在应该被理解成“结构化查询执行器”，不是“主理解器”。

它当前应该负责：

- 接收可执行的 `resolvedQuery`
- 做结构规范化与执行前校验
- 做元数据解析、路径规划、参数构造
- 执行 `topValues / averageValues / timeValues / overview`
- 对 overview 做多模块展开与聚合
- 把结果输出成统一 narration contract

它当前**不应该**再负责：

- 从裸 prompt 重新做完整自然语言理解
- 自己判断边界内外
- 自己决定是否拒答和引导
- 在缺失 `resolvedQuery` 时，偷偷恢复成旧时代的本地主理解链路

补充说明：

- 出于兼容性考虑，skill 内部仍保留了少量 prompt fallback / continuation 能力
- 但这些能力现在应该视为“兜底能力”，而不是“主路径”

### 4. NAPM 上游接口的职责

这一层只负责提供数据，不负责理解问题。

这里的错误需要和上层问题区分开：

- `400` 可能是对象类型、指标、时间窗、参数构造不对
- `ok=true 但 rows=[]` 可能是当前时间窗没有数据
- 元数据接口 `403` 不等于业务查询接口不可用

所以以后排查时要分清：

- 是“上游没数据”
- 还是“上游参数被喂错了”
- 还是“上层对象语义就错了”

## 当前已经收口的核心语义约定

以下是当前项目里最重要、最应该稳定坚持的对象语义：

| 用户表述 | 当前运行对象 | 说明 |
| --- | --- | --- |
| 应用 | `DefinedApp` | 指协议应用、已知应用、应用协议对象 |
| 业务 | `WebApplication` | 普通“业务/业务系统/Web应用/网站/站点”默认落到这里 |
| 业务组 | `BusinessGroup` | 只有明确出现“组/分组/工作组”才应落到这里 |
| IP网段 | `Prefix24` | 典型网段维度 |
| 会话 | `IPConversation` | 指 IP 会话对象 |
| 监控口 / 接口 | 当前代码中同时存在 `MonitoredPort` / `Interface` 术语 | 这一维度已有接口/元数据能力，但命名和支持完整度还没有前五类收得这么稳 |

尤其要记住下面这三条：

- `应用 != 业务`
- `业务 != 业务组`
- `Plain 业务` 默认应理解为 `WebApplication`，而不是 `BusinessGroup`

这也是这次“为什么问应用整体，却回答成业务组流量概况”的根因之一。

## 当前 overview / 整体情况 问题的设计

“整体情况 / 总览 / 概览”类问题，不能再理解成单点 TopN 问题，而应该理解成 `overview` 服务。

当前项目里的 overview scene 应收口为：

| 问句类型 | overview scene |
| --- | --- |
| 系统整体 | `system` |
| 网络整体 | `network` |
| 应用整体 | `application` |
| 业务整体 | `business` |
| 业务组整体 | `business_group` |
| 安全整体 | `security` |

### 当前 scene 与对象域的对应关系

- `application` 场景：以 `DefinedApp` 相关模块为主
- `business` 场景：以 `WebApplication` 相关模块为主
- `business_group` 场景：以 `BusinessGroup` 相关模块为主

### 当前已确认的概览模块方向

`应用整体` 应优先落到：

- 应用告警概况
- 应用分布排行
- 应用吞吐排行
- 应用访问 / 体验 / 失败相关模块

`业务整体` 应优先落到：

- 业务访问排行
- 业务实时访问排行
- 业务告警概况
- WebApplication 相关访问与体验模块

`业务组整体` 应优先落到：

- 业务组吞吐排行
- 业务组连接请求排行
- 业务组告警概况

关键原则：

**应用整体不能再被错误折叠成“业务组流量概况”。**

## 为什么之前会越改越乱

之前混乱的根因，不是某一个函数单独写错了，而是**职责同时散落在多层**。

历史上同时存在过这些现象：

1. WeCom plugin 自己做一部分结果判断
2. OpenClaw 主链做一部分判断
3. `napm-openclaw-plugin` 自己再做一层问句改写和兜底
4. Skill 又保留了一部分本地 prompt fallback
5. 远端同时存在多份 skill / plugin 副本，导致“改了但没生效”

于是同一句话在不同入口、不同缓存状态、不同部署副本下，可能走出不同分支。

这次排查后可以明确记住：

### 1. WeCom 不是完全无逻辑

它会参与结果承接与渲染保护，所以“企业微信只是知识传输层”这个说法现在不完全准确。

更准确的说法是：

**企业微信插件不是主判断层，但它确实参与结果呈现。**

### 2. napm-openclaw-plugin 不只是转工具

它当前会参与：

- NAPM 范围路由
- 工具重写
- overview prompt 注入
- direct tool 改写回 skill
- before_message_write 时的概览强制刷新

所以 overview 问题的稳定性，不能只看 skill。

### 3. Skill 不是唯一修补点

如果出现：

- 应用整体走成业务组
- overview 被单维度结论覆盖
- 线上和本地自测不一致

就必须同时检查：

- WeCom 渲染层
- `napm-openclaw-plugin`
- skill overview scene
- 远端真实生效路径

## 当前已经确认的线上生效路径

现在远端真正生效的核心路径如下：

- `~/.openclaw/extensions/napm-openclaw-plugin/index.js`
- `~/.openclaw/extensions/wecom-openclaw-plugin/dist/index.cjs.js`
- `~/.openclaw/extensions/wecom-openclaw-plugin/dist/index.esm.js`
- `~/.openclaw/skills/openclaw-napm-query/scripts/run_napm_query.js`

当前服务重启目标是：

- `systemctl --user openclaw-gateway.service`

当前已经确认并清理过的问题：

- 远端曾同时存在 `~/.openclaw/openclaw-napm-query` 与 `~/.openclaw/skills/openclaw-napm-query`
- 真正生效的是 `~/.openclaw/skills/openclaw-napm-query`
- 重复副本会直接导致“本地明明改了，线上却没效果”的错觉

因此后续部署默认原则应是：

**以本地仓库为准，覆盖远端真实生效路径，不再让远端长期保留多套并行副本。**

## 这次排查后最值得记住的几个收口点

### 1. overview scene 必须前后一致

现在已经明确：

- `现在应用整体情况怎么样？` -> `application`
- `现在业务整体情况怎么样？` -> `business`
- `现在业务组整体情况怎么样？` -> `business_group`

而且这个一致性要同时在两层成立：

- skill 内部成立
- `napm-openclaw-plugin` 的 prompt 注入和最终回写前刷新逻辑也成立

### 2. 上游错误缓存不能继续污染当前问句

当前 `napm-openclaw-plugin` 已补上 scene 强校验。

也就是说：

- 如果当前问句是“应用整体”
- 但缓存里记住的是一个错误的 `BusinessGroup` 结果

那么在最终回消息前，应该强制按当前问句重建 `application overview`，而不是继续沿用旧缓存。

### 3. WeCom 不能把 overview 又渲染歪

现在 WeCom 渲染层的收口原则是：

- 普通 query / topn / trend 可以按已有 `displayText` 或结构化结果处理
- 但 `overview` 不能被旧的 `displayText` 直接短路
- `overview` 必须按“总览/概览”口径总结，而不是私自改成“按业务组看一下”之类的单维度回复

## 关键代码文件应该怎么理解

### 1. `skills/openclaw-napm-query/scripts/run_napm_query.js`

这是 skill 的统一执行入口。

当前应把它理解成：

**执行入口收口层**

它当前的重点职责是：

- 读取 `payload / resolvedQuery / session`
- 规范化结构
- 分流到普通查询或 overview
- 输出统一 contract

它不应该再被当成“主自然语言理解入口”。

### 2. `skills/openclaw-napm-query/scripts/overview-module.js`

这是 overview 专用执行层。

它当前负责：

- 识别 overview scene
- 编排 overview 候选模块
- 聚合多个查询结果
- 生成 overview 结构化结果

这一层决定“应用整体 / 业务整体 / 业务组整体”到底走哪些模块。

### 3. `skills/openclaw-napm-query/services/OpenClawNarrationContractService.js`

这是 narration contract 生成层。

它负责把执行结果整理成 OpenClaw 可以稳定消费的结构，包括：

- time range
- summary
- structured rows / series
- overview modules
- narrationStructure
- follow-up hints

### 4. `.codex-temp/napm-openclaw-plugin.remote.js`

这是当前最容易被低估的一层。

它实际上承接了：

- NAPM 范围路由
- tool guard
- direct tool reroute
- overview prompt fallback resolvedQuery
- before_message_write 时的最终概览纠偏

所以线上问题如果只看 skill，很容易漏掉这一层。

### 5. `.codex-temp/wecom-openclaw-plugin/index.cjs.js` / `index.esm.js`

这是企业微信结果承载层。

它现在主要负责：

- 识别结构化结果类型
- 调用 OpenClaw 做最终渲染
- 对 overview 类型避免错误短路
- 在 OpenClaw 叙述失败时提供更安全的 deterministic fallback

## 后续继续推进时的正确顺序

如果接下来还要继续优化，不要再走“哪层看着不对就顺手再补一层规则”的路线。

更稳的推进顺序应该是：

1. 先看问题属于哪一层
2. 再在正确层修复
3. 最后做跨层联调验证

更具体地说：

### 第一优先级：主链职责是否收口

检查：

- 边界判断是否还分散
- follow-up 是否还在多层重复猜
- `resolvedQuery` 是否仍被多层独立改写

### 第二优先级：overview 设计是否一致

检查：

- 当前问句命中的 scene 对不对
- 当前 scene 下选的模块对不对
- 最终渲染时有没有被改成单维度结论

### 第三优先级：远端部署是否真的生效

检查：

- 改的是不是远端真实生效文件
- 服务是不是已经重启
- 是否仍存在重复副本或历史垃圾备份干扰排查

## 当前最推荐保留在脑子里的模型

如果现在再看这个项目，建议只保留下面这套理解：

```text
WeCom = 接入层 + 结果承载层
OpenClaw 主链 = 大脑
napm-openclaw-plugin = NAPM 路由与守卫层
Skill = 执行层
NAPM API = 数据来源
Narration Contract = 把数据整理好再交回上层说话
```

再换一句话说：

- OpenClaw 决定“这是不是 NAPM 问题、要查什么、该怎么问”
- `napm-openclaw-plugin` 决定“这条 NAPM 请求怎么被安全、稳定地送进 skill”
- Skill 决定“怎么查、怎么聚合、怎么整理结果”
- WeCom 决定“这段结果怎么被稳定送回用户”

这就是当前项目最该坚持的整体思路。
