## 1. 故障摘要

用户提交告警数据包分析请求后，界面只显示：

```text
I'll analyze this alert packet using the composite tool for alert+packet analysis.
```

没有显示真正的告警数据包分析报告。

经远端真实日志确认，本次不是告警查询失败、数据包分析失败、时间范围错误、告警类别误过滤或认证失败。复合工具已经成功完成，模型也已经生成完整中文报告；故障发生在 OpenClaw 最终消息选择与企业微信发送阶段。

问题本质：

```text
工具调用前导语被 OpenClaw 标记为 kind=final
  -> NAPM 插件把它认领为本轮唯一最终交付
  -> 真正分析报告留在 session 中，没有发送给用户
```

## 6. 已证实根因

### 6.1 工具调用消息同时携带可见文本

第一条 assistant 消息结构为：

```json
{
  "role": "assistant",
  "content": [
    {
      "type": "text",
      "text": "I'll analyze this alert packet using the composite tool for alert+packet analysis."
    },
    {
      "type": "toolCall",
      "name": "napm-alert-packet-analysis"
    }
  ],
  "stopReason": "toolUse"
}
```

该文本只是模型在调用工具前的过程说明，不是业务答案。

### 6.2 `before_message_write` 对 toolCall 消息直接跳过

文件：

```text
napm-openclaw-plugin.remote.js:6327
```

当前逻辑：

```js
if (messageContainsToolCall(message)) {
  return undefined;
}
```

这会保留 toolCall 消息中的英文前导语。它虽然不应对外发送，但仍存在于 OpenClaw 的消息生命周期中。

### 6.3 预览识别依赖不完整的文本启发式

文件：

```text
napm-openclaw-plugin.remote.js:275
napm-openclaw-plugin.remote.js:338
napm-openclaw-plugin.remote.js:4476
```

当前逻辑先判断事件是否为 streaming/preview，再用若干英文或中文正则识别内部过程文本。

本次英文前导语长度为 `82` 个字符，已超过内部过程文本检测的 80 字符最低长度。它漏过检测的真正原因不是长度，而是规则只覆盖 `let me...`、`now I see...` 等句式，没有覆盖：

```text
I'll analyze...
I'll use...
I will call...
```

同时，OpenClaw 已把该事件标成 `kind=final`，`isStreamingPreviewMessageEvent()` 因而返回 `false`。

### 6.4 最终交付权在内容校验前被认领

文件：

```text
napm-openclaw-plugin.remote.js:6147-6159
```

当前顺序：

```text
确认存在复合 Skill 结果
  -> 立即 claimFinalDelivery()
  -> 之后才继续处理输出内容
```

该逻辑只保证“第一条 final 可以发送”，没有保证“第一条 final 是真正最终答案”。

本次第一条被标成 final 的内容恰好是工具前导语，因此它抢先获得交付权。审计日志随后记录：

```text
event=napm_plugin_duplicate_alert_packet_delivery_suppressed
turnId=napm-turn-425c35b7-b9d9-4d48-8ba7-724fc22376b0
workflowState=COMPLETED
```

### 6.5 复合结果没有专用的最终文本替换分支

普通告警结果可通过 `isAlertSkillResultRecord()` 进入 `buildAlertQueryReply()`，把错误的待发文本替换为 Skill 结果。

复合结果使用独立的 `isAlertPacketSkillResultRecord()`，当前只参与最终交付认领和重复抑制，没有对应的确定性最终文本构造/替换分支。因此插件知道复合工作流成功了，却没有用复合结果纠正错误的英文待发内容。

## 9. 影响范围

该故障不是 `eventId=745506` 特例，也不是告警数据内容导致。

确定受影响：

```text
告警数据包复合工作流
模型在 toolCall 前输出短前导语
OpenClaw/渠道把该前导语作为 kind=final 交给 message_sending
```

潜在受影响：

1. 其他会输出 `text + toolCall` 的复合 Skill。
2. 其他未提供结果专用输出替换器的 NAPM 工具。
3. 使用不同模型时产生的新前导语句式。

普通告警查询已有 `buildAlertQueryReply()` 结果替换路径，风险相对较低；但仍应使用统一消息阶段契约解决，不能继续依赖逐句增加正则。

## 10. 修复原则

本问题不应通过只增加一条 `I'll analyze` 正则解决。合理修复需要同时满足：

1. 含 `toolCall` 的 assistant 文本默认是过程消息，不得直接成为对外 final。
2. `claimFinalDelivery()` 必须在确认或构造合法最终内容之后执行。
3. 复合 Skill 结果需要专用的结果判定和最终文本构造/替换路径。
4. 最终交付判断应基于消息阶段、结果来源、turnId 和 workflowState，而不是语言、长度或固定句式。
5. 即使 OpenClaw 把前导语错误标成 `kind=final`，插件也必须取消或替换它。
6. 真正最终报告到达时，必须仍然拥有交付资格。

建议状态顺序：

```text
TOOL_PENDING
  -> TOOL_COMPLETED
  -> FINAL_CONTENT_READY
  -> FINAL_DELIVERY_CLAIMED
  -> FINAL_DELIVERED
```

不允许从 `TOOL_COMPLETED` 直接因为任意 `kind=final` 进入 `FINAL_DELIVERY_CLAIMED`。

### 14.2 最终交付状态机

`plugin/ConversationOperationState.js` 新增：

```text
prepareFinalContent({ scope, turnId, content, source, workflowState })
getPreparedFinalContent(scope, turnId)
claimPreparedFinalDelivery(scope, turnId)
```

每份最终内容按 `scope + turnId` 保存，并记录 SHA-256 内容指纹、来源、工作流状态和更新时间。未准备最终内容时，`claimPreparedFinalDelivery()` 固定返回 `false`；只有 `FINAL_CONTENT_READY` 内容才能进入 `FINAL_DELIVERY_CLAIMED`。`/new` 调用 `clearScope()` 时会同时清除准备和认领状态。

### 14.3 两阶段 Hook 行为

`before_message_write`：

1. `assistant(text + toolCall)` 仍被识别为工具调用阶段，不作为最终内容候选。
2. 复合 Skill 结果到达后，仅捕获同一 `turnId` 的无 toolCall assistant 消息。
3. 合格文本经凭据清洗后写入 `FINAL_CONTENT_READY`，不改写 session 原消息。

`message_sending`：

1. 告警数据包工作流优先于通用 preview/兜底逻辑处理。
2. 如已捕获模型最终报告，则用该报告替换任何待外发前导语。
3. 如模型最终报告未捕获，则从当前复合结果生成确定性用户报告。
4. 准备完成后才认领一次交付；同轮后续消息全部取消。
5. 不依赖 OpenClaw 是否传递 `kind=final`，因此规避核心阶段元数据丢失。
