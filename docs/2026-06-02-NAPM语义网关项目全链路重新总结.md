# NAPM 语义网关项目全链路重新总结

日期：2026-06-02  
范围：当前仓库 `NAPM_Semantic_Gateway` 的插件层、查询 Skill、报告 Skill、配置、公共工具与测试守卫。  
结论：当前项目不是传统 HTTP 网关项目，而是“OpenClaw 插件 + NAPM 查询 Skill + NAPM 报告 Skill + NetInside/NAPM WebService”的直接执行链路。生产查询入口必须以 `napm-skill-query` 为中心，报告导出入口为 `napm-report-export`；自然语言理解与 `resolvedQuery` 构造属于 OpenClaw 主链，Skill 只消费已经结构化的查询并执行。

## 1. 项目定位

本仓库承担三类职责：

1. 给 OpenClaw 注册 NAPM 工具、命令和 hook。
2. 将 OpenClaw 构造好的 `resolvedQuery` 转换成 NAPM WebService 请求并执行。
3. 将查询结果整理为 OpenClaw 可消费的中文叙述契约，并可进一步导出 Word 报告。

需要特别注意历史命名：代码中仍保留 `GatewayRequest`、`executeGatewayRequest` 等名称，但当前含义已经偏向“结构化执行请求”，不是旧的项目级 HTTP gateway。当前主链路明确绕开旧 `src/routes`、旧项目级 `src/services`，以 `skills/openclaw-napm-query` 为真实运行核心。

## 2. 总链路鸟瞰

```text
用户问题
  -> OpenClaw 主链理解意图、对象、指标、时间、上下文
  -> OpenClaw 构造 structured resolvedQuery
  -> napm-openclaw-plugin.remote.js
     -> 注入路由策略
     -> 校验边界与时间契约
     -> 只允许生产入口 napm-skill-query
  -> node skills/openclaw-napm-query/scripts/run_napm_query.js --payload <json>
  -> run_napm_query.js 解析 payload / resolvedQuery / session
  -> RequirementParserService 准备执行请求
  -> ExecutionKernelPolicy 分流 metadata 或 metric
  -> MetadataExecutionKernel / MetricExecutionKernel / overview-module
  -> NapmClient
  -> NetInside / NAPM WebService
  -> CSV/JSON 解析与结果归一
  -> OpenClawNarrationContractService 生成 narrationInput / summary / reportData
  -> OpenClaw 输出中文答案
  -> 可选：napm-report-export 使用 reportData 生成 docx
```

核心边界：

| 层级 | 职责 | 不负责 |
| --- | --- | --- |
| OpenClaw 主链 | 自然语言理解、范围判断、澄清、多轮继承、`resolvedQuery` 构造 | 直接拼 NAPM API 绕过 Skill |
| OpenClaw 插件 | 注册工具、注入系统策略、拦截绕路工具、校验 `resolvedQuery` 边界、调用 executor | 生产环境中临时从 prompt 猜查询 |
| 查询 Skill | 规范化结构化查询、执行守卫、元数据/指标/overview 查询、输出叙述契约 | 决定是否越界、替代 OpenClaw 做主链语义理解 |
| 报告 Skill | 消费 `reportData` 并生成报告文件 | 自行查 NAPM、自行理解自然语言查询 |
| NapmClient | 补齐账号密码、构造 HTTP 请求、访问 NAPM WebService | 语义决策、指标归属判断 |

## 4. OpenClaw 插件链路

### 4.1 入口加载

```text
napm-openclaw-plugin.index.mjs
  -> try require('./index.js')
  -> fallback require('./napm-openclaw-plugin.remote.js')
  -> export id/name/description/register
```

本地仓库通常没有 `index.js`，因此开发态实际加载 `napm-openclaw-plugin.remote.js`。远端部署时，`napm-openclaw-plugin.remote.js` 通常会成为 `~/.openclaw/extensions/napm-openclaw-plugin/index.js`。

### 4.2 生产工具

插件默认注册两个生产工具：

| 工具 | 用途 | 右侧调用 |
| --- | --- | --- |
| `napm-skill-query` | 执行已经构造好的 NAPM `resolvedQuery` | `runSkillExecutor` -> `run_napm_query.js` |
| `napm-report-export` | 将最新或显式传入的 `reportData` 导出报告 | `runReportExecutor` -> `generate_napm_report.js` |

诊断工具 `napm-resolve-query`、`napm-mainflow-query` 只有在 `NAPM_ENABLE_DEV_RESOLVER_TOOLS=true` 时注册，不属于生产查询路径。

### 4.3 Hook 链路

| Hook | 左侧触发 | 本层处理 | 右侧影响 |
| --- | --- | --- | --- |
| `message_received` | 用户消息进入 OpenClaw | 记录会话级 guard state，判断是否 NAPM/监控相关 | 后续 hook 可知道本轮范围 |
| `before_prompt_build` / `before_agent_start` | OpenClaw 准备 prompt | 注入 NAPM 路由策略，要求 `resolvedQuery-first` | 影响模型工具选择和回答边界 |
| `before_tool_call` | OpenClaw 准备调用工具 | 阻断旧 NAPM 直连工具、shell/exec 绕路、非法 `resolvedQuery` | 允许或拒绝 `napm-skill-query` |
| `message_sending` / 写出前 guard | 助手消息准备发给用户 | 拦截手工推理、绕过 Skill、陈旧结果等话术 | 改写为必须走 Skill 或使用真实结果 |

旧直连工具已经被移除或阻断：

```text
napm-topn
napm-average
napm-timeseries
```

### 4.4 插件到 Skill 的调用

```text
napm-skill-query.execute(args)
  -> prepareSkillExecutionArgs(args)
  -> validateResolvedQueryAgainstSpec(args.resolvedQuery)
  -> runSkillExecutor(preparedArgs)
  -> execFile("node", [
       NAPM_SKILL_EXECUTOR,
       "--payload",
       JSON.stringify(preparedArgs)
     ])
  -> extractSkillJson(stdout)
  -> rememberDebugApi / rememberSkillResult
  -> makeToolResult(result)
```

可执行数据服务必须具备根级 `start/end`：

```text
topValues
averageValues
timeValues
overview
topValues_multi_protocol
```

`timeRange` 只作为声明性字段，不能承载执行时间。

## 5. 查询 Skill 主链路

入口文件：

```text
skills/openclaw-napm-query/scripts/run_napm_query.js
```

### 5.1 入口阶段

```text
main()
  -> parseArgs()
  -> parseJsonArg("--payload")
  -> buildTraceIdFromPayload()
  -> resolveInput(args, payload)
  -> logSkillAudit("napm_skill_resolved_query_received")
```

`resolveInput` 接受：

| 输入 | 说明 |
| --- | --- |
| `--payload` | 插件调用 Skill 的主要方式。 |
| `--resolvedQuery` | 手工 CLI/测试方式。 |
| `--queryJson` | 兼容输入方式。 |
| `--decision` / `--intent` / `--session` | 上游 trace 与多轮上下文。 |

如果没有 `resolvedQuery`，不会自行猜查询，而是返回 `UPSTREAM_RESOLVED_QUERY_REQUIRED` 对应的中文决策契约。

### 5.2 执行前分支

`main()` 在真正访问 NAPM 前会处理：

| 分支 | 条件 | 输出 |
| --- | --- | --- |
| 敏感凭据保护 | prompt 命中账号、密码、token 等请求 | `security_refusal` |
| 澄清门 | `clarificationGate.required=true` | `ASK_CLARIFYING_QUESTION` 风格契约 |
| executionGuard | `resolvedQuery.executionGuard.blockExecution=true` 且非 overview | 澄清/阻断契约 |
| 下钻目录 | `service=drilldownCatalog` | 静态/本地层级目录结果 |
| 普通执行 | 其他有效 `resolvedQuery` | `executeResolvedQuery()` |

### 5.3 核心执行分流

```text
executeResolvedQuery(prompt, resolvedQuery, payload, intentResult)
  -> normalizeResolvedQueryShape()
  -> normalizeResolvedQueryTimeRange()
  -> if service=topValues_multi_protocol:
       executeUnknownPortDualProtocolQuery()
  -> else if overview + analysisPipeline.discoveryQuery:
       discoveryQuery first
       deriveDiscoveryFocusSelection()
       buildFocusedOverviewResolvedQuery()
       executeOverviewModule()
  -> else if overview:
       executeOverviewModule()
  -> else:
       RequirementParserService.executeGatewayRequest()
```

## 6. RequirementParserService 执行链路

核心文件：

```text
skills/openclaw-napm-query/services/RequirementParserService.js
```

虽然名字叫 parser，但当前它的真实职责是“结构化请求准备与执行编排”。主要链路：

```text
executeGatewayRequest(gatewayRequest, requestContext)
  -> normalizeTopLevelQueryShape()
  -> applyStaticGroupPathPlanning()
  -> matchStableQueryTemplate()
  -> prepareGatewayExecution()
  -> ExecutionKernelPolicy.assertWorkflowServiceContract()
  -> resolveExecutionKernel(query)
  -> MetadataExecutionKernel.execute()
     或 MetricExecutionKernel.execute()
  -> parseNapmPayload()
  -> buildExecutionDataSummary()
```

它左侧通常被调用于：

| 左侧调用者 | 场景 |
| --- | --- |
| `run_napm_query.js` | 普通 topValues/averageValues/timeValues/groups/metrics 执行。 |
| `overview-module.js` | overview 子查询执行。 |
| `executeUnknownPortDualProtocolQuery` | TCP/UDP 双协议拆分查询。 |
| tests | 直接验证执行内核、fallback、路径修复。 |

它右侧主要调用：

| 右侧依赖 | 用途 |
| --- | --- |
| `MetricMappingService` | 指标名/指标码映射、指标校验。 |
| `NapmClient` | 最终访问 NAPM WebService。 |
| `GroupBuilder` | group 参数构造，如 `groupType1`、`groupArgument1`。 |
| `QueryValidator` | service、metrics、时间、granularity 等校验。 |
| `NapmMetadataService` | group、metricsForGroup、应用目录、下钻等元数据。 |
| `GroupPathPlannerService` | 基于静态 tree 规划多层 group path。 |
| `QueryMetadataConstraintService` | 动态元数据约束审查与修复建议。 |
| `MetadataExecutionKernel` | 元数据 service 执行。 |
| `MetricExecutionKernel` | 指标数据 service 执行。 |
| `ExecutionFailureClassifier` | 失败归类与用户可读信息。 |
| `CsvParser` / `TimeUtils` / `auditLogger` | 解析、时间、审计与脱敏。 |

## 7. 执行内核链路

### 7.1 内核选择

文件：


分流规则：

| 类型 | workflow/service |

### 7.2 MetadataExecutionKernel

文件：

```text
skills/openclaw-napm-query/services/MetadataExecutionKernel.js
```

链路：

```text
MetadataExecutionKernel.execute(queryRequest)
  -> normalize metadata groups
  -> service=metrics + groups:
       NapmMetadataService.getMetricsForGroupPath()
       filterMetricInventoryForOwnership()
  -> service=groups + one group:
       NapmMetadataService.resolveObjectInstanceProviderMetadata()
       NapmMetadataService.listObjectInstances()
  -> fallback metadata API:
       NapmClient.get({ type: service, json: true, ...groupParams })
  -> parseNapmPayload()
  -> response.data
```

典型对象清单口径：

| 对象 | 来源 |
| --- | --- |
| `WebApplication` | `applications` API，过滤 `Type=3`。 |
| `DefinedApp` | `applications` API，过滤 `Type=2`。 |
| `CompositeApplication` | `applications` API，过滤 `Type=4`。 |
| `BuiltinApplication` | `applications` API，过滤 `Type=1`。 |
| `BusinessGroup` | `businessGroups` API。 |
| `PageFamily` / `User` 等 | `groupArguments` API 或本体定义的 provider。 |

## 8. NapmClient 与上游 API

文件：

```text
skills/openclaw-napm-query/services/NapmClient.js
```

职责：

```text
constructor()
  -> read NETINSIDE_HOST / NETINSIDE_USERNAME / NETINSIDE_PASSWORD
  -> build axios client
  -> optional NETINSIDE_TLS_INSECURE

get(params)
  -> buildOrderedParams({ UserName, Password, ...params })
  -> audit/log masked params and safe URL
  -> axios.get("")
  -> return response.data

post(data)
  -> 同 GET，但发送 POST

getJson(params)
  -> get({ ...params, json:"true" })
  -> JSON.parse when needed
```

真实 API URL、账号、密码必须只在 `.env` 中配置，日志通过 `auditLogger` 脱敏。

```text
skills/openclaw-napm-query/scripts/overview-module.js
```

```text
executeOverviewModule({ prompt, payload, intent, resolvedQuery, executeGatewayRequest })
  -> resolveOverviewScene()
  -> resolveOverviewDepth()
  -> getOverviewBudget()
  -> listOverviewCandidates()
  -> loadOverviewMetadataReviewSafely()
  -> extractOverviewSlots()
  -> buildOverviewPlan()
  -> compileOverviewPlan()

```

相关文件：

| 文件 | 职责 |
| --- | --- |
| `OverviewCandidateRegistry.js` | 注册可用于不同 scene 的候选模块。 |

综合分析中“先发现再分析”的链路：

```text
resolvedQuery.service=overview

  -> validateAnalysisPipelineContract()
  -> buildDiscoveryQuery()
  -> RequirementParserService.executeGatewayRequest(discoveryQuery)
  -> deriveDiscoveryFocusSelection()
  -> buildFocusedOverviewResolvedQuery()
  -> executeOverviewModule(focusedOverviewResolvedQuery)
  -> result.responseType = comprehensive_analysis_with_discovery
```

典型问题：

```text
先找失败最多的 IP，再综合分析它
找到丢包最高的业务，然后分析原因
```

## 11. 多协议 TopN 链路

`service=topValues_multi_protocol` 用于未知端口流量等需要 TCP/UDP 分开查再合并的场景。

```text
executeUnknownPortDualProtocolQuery(prompt, resolvedQuery)
  -> read resolvedQuery.protocolQueries
  -> for each protocolQuery:
       RequirementParserService.executeGatewayRequest(protocolQuery)
  -> merge rows
  -> each row add protocol
  -> return topValues_multi_protocol result
```

失败码：

| 失败码 | 含义 |
| --- | --- |
| `UNKNOWN_PORT_PROTOCOL_QUERIES_MISSING` | 缺少 `protocolQueries`。 |
| `UNKNOWN_PORT_PROTOCOL_QUERIES_FAILED` | TCP/UDP 等子查询全部失败。 |

## 13. 报告导出链路


```text
napm-report-export.execute(args)
  -> runReportExecutor(args)
  -> buildReportDataForExport(args)
     -> prefer args.reportData
     -> else latest remembered NAPM skill result reportData
  -> write temp input JSON

       "--input",
       tempInputPath,
       "--downloadBaseUrl",
       baseUrl
     ])
  -> extractSkillJson(stdout)
  -> buildReportExportReply(result)
```

报告 Skill 链路：

```text
skills/openclaw-napm-report/scripts/generate_napm_report.js
  -> parseArgs()
  -> readInput(args)
  -> JSON.parse()
  -> new ReportGenerationService()
  -> service.generate(payload)
```

`ReportGenerationService`：

```text
validate(report)
  -> check reportType
  -> check format
  -> reject pdf
  -> require sections

generate(report)
  -> storage.createReportId()
  -> storage.buildPaths()
  -> template.renderDocx()
  -> storage.writeBuffer()
  -> storage.writeAuditJson()
  -> return reportId/filePath/downloadUrl/generatedAt
```

支持：

| 格式 | 状态 |
| --- | --- |
| `docx` / `word` | 支持，`word` 在插件侧归一为 `docx`。 |
| `pdf` | 明确拒绝，返回 `REPORT_PDF_EXPORT_UNAVAILABLE`，不静默降级。 |

## 15. 常见问题到代码路径

### 15.1 “系统中有哪些业务？”

```text
OpenClaw -> resolvedQuery:
service=groups
groups=[{ type:"WebApplication" }]
semanticConstraints.workflowType=object_inventory
```

执行：

```text
napm-skill-query
  -> run_napm_query.js
  -> RequirementParserService.executeGatewayRequest
  -> MetadataExecutionKernel
  -> NapmMetadataService.listObjectInstances("WebApplication")
  -> applications API filter Type=3
  -> OpenClawNarrationContractService group_list
```

### 15.2 “业务都可以查哪些指标？”

```text
service=metrics
groups=[{ type:"WebApplication" }]
workflowType=metric_inventory
```

执行：

```text
MetadataExecutionKernel
  -> NapmMetadataService.getMetricsForGroupPath(WebApplication)
  -> filterMetricInventoryForOwnership()
  -> 返回 WebApplication 业务指标口径
```

### 15.3 “最近一天丢包最高的 10 个 IP”

```text
service=topValues
metric/topMetric=PLI 或 PLO
groups=[{ type:"IPAddress" }]
topCount=10
start/end=root-level minute aligned
```

执行：

```text
MetricExecutionKernel
  -> type=topValues
  -> metrics=PLI/PLO
  -> groupType1=IPAddress
  -> NapmClient.get()
  -> CSV/JSON parse
  -> responseType=topn
```

### 15.4 “今天网络整体情况怎么样？”

```text
service=overview
overviewScene=network
start/end=root-level
```

执行：

```text
executeOverviewModule
  -> scene=network
  -> budget=standard by default
  -> candidate registry
  -> compile multiple child queries
  -> execute through RequirementParserService
  -> reduceOverviewResults
  -> responseType=comprehensive_analysis
```

### 15.5 “先找失败最多的 IP，再分析它”

```text
service=overview
analysisType=comprehensive_analysis
analysisMode=discover_then_analyze
analysisPipeline.discoveryQuery={ service:"topValues", ... }
```

执行：

```text
discoveryQuery topValues
  -> select top object
  -> build focused overview groups with selected object
  -> executeOverviewModule
  -> responseType=comprehensive_analysis_with_discovery
```

### 15.6 “BusinessGroup 支持哪些下钻？”

```text
service=drilldownCatalog
groups=[{ type:"BusinessGroup" }]
```

执行：

```text
buildHierarchyCatalogPayloadFromResolvedQuery
  -> NapmMetadataService.getDrilldownPathsForGroupType("BusinessGroup")
  -> config/groups-tree.static.json
  -> drilldown catalog contract
```

### 15.7 “将以上结果导出 Word”

执行：

```text
napm-report-export
  -> use latest remembered skill result reportData
  -> generate_napm_report.js
  -> ReportGenerationService
  -> ReportTemplateService.renderDocx
  -> ReportStorageService.writeBuffer/writeAuditJson
```

## 16. 配置 truth source

| 配置/常量 | 是什么的 truth source | 不是 |
| --- | --- | --- |
| `config/napm-resolution-spec.v1.json` | `resolvedQuery` 合约、service 字段、时间规则、模板、边界策略 | 真实对象实例清单 |
| `config/object-ontology.v1.json` | 对象本体、应用 Type 口径、实例 provider | 指标运行时兼容最终判定 |
| `config/groups-tree.static.json` | group hierarchy、下钻结构、路径规划 | WebApplication/DefinedApp/CompositeApplication 清单 |
| `config/metrics-config.yml` | 指标映射补充来源 | 指标与对象兼容性的唯一判定 |
| `src/constants/objectMetricOwnership.js` | 指标归属、业务/非业务口径过滤 | NAPM 实时支持度最终判定 |
| `src/constants/metricDomains.js` | 指标域、默认候选、兼容辅助判断 | 替代 `metricsForGroup` |
| NAPM `metricsForGroup` API | 某 group path 指标运行时兼容最终信号 | 中文语义归属解释 |
| NAPM `applications` API | 应用类对象实例清单 | 下钻层级结构 |

## 17. 审计与排障链路

主要日志工具：

```text
src/utils/logger.js
src/utils/auditLogger.js
```

一次完整查询应能看到类似事件：

```text
napm_plugin_skill_call_received
  -> napm_plugin_resolved_query_forwarded
  -> napm_plugin_skill_executor_invoked
  -> napm_skill_resolved_query_received
  -> napm_skill_execution_started
  -> napm_metric_api_request_built / napm_metadata_api_request_built
  -> napm_metric_execution_completed / napm_metadata_execution_completed
  -> napm_skill_execution_completed
  -> napm_plugin_skill_executor_completed
```

排查建议：

| 现象 | 优先检查 |
| --- | --- |
| 用户问了 NAPM 但没查数据 | 是否有 `napm_plugin_resolved_query_blocked`、`napm_skill_missing_resolved_query`。 |
| 时间异常 | 根级 `start/end` 是否存在、是否秒级、是否 60 秒对齐。 |
| 业务清单错成协议应用 | `groups[0].type` 是否是 `WebApplication`，是否走 `applications Type=3`。 |
| 自动识别应用异常 | `groups[0].type` 是否是 `CompositeApplication`，是否过滤 `Type=4`。 |
| 指标清单口径异常 | 是否 plain “业务” 被误映射到 `BusinessGroup`，是否经过 ownership 过滤。 |
| 下钻路径异常 | 是否走 `service=drilldownCatalog`，是否从 static groups tree 取结构。 |
| overview 结果少 | 看 `overview.executionMeta.queryCount/successCount/failedCount/skippedCandidates`。 |
| 报告无法生成 | 是否存在 `reportData.sections`，PDF 是否被明确拒绝。 |

## 20. 一句话总图

```text
OpenClaw 负责把人话变成 resolvedQuery
  -> 插件负责只放行合法 napm-skill-query / napm-report-export
  -> 查询 Skill 负责把 resolvedQuery 变成 NAPM WebService 请求
  -> 执行内核负责分 metadata / metric / overview
  -> NapmClient 负责访问南向 NAPM
  -> NarrationContract 负责把结果变成 OpenClaw 可讲述结构和 reportData
  -> 报告 Skill 只负责把 reportData 落成 docx
```
