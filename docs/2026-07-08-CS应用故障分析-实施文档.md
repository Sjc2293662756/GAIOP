# C/S 应用故障分析 — 实施文档

## 概述

为 NAPM 故障诊断系统新增 **C/S 应用故障分析**（`cs_app_slow`）完整流程，使其与已有的 B/S 业务故障分析（`bs_app_slow`）达到同等可用水平。

### 系统中的"业务"与"应用"

NAPM 系统严格区分两个对象类型（参见 `src/constants/objectDimensions.js`）：

| 系统概念 | NAPM 对象类型 | 协议层 | 故障分析流程 | 典型指标 |
|------|------|------|------|------|
| **业务** | `WebApplication`（Type=3） | HTTP/HTTPS（7 层） | `bs_app_slow` — B/S 架构业务慢 | PGNPGE、PGHTTP400/500、PGTME |
| **应用** | `DefinedApp`（Type=2） | TCP/UDP（4 层） | `cs_app_slow` — C/S 架构应用慢 | UEII、CSTI、TRTI、PTTO、RDTO、TPIO |

**业务**是 Web 业务系统（通过浏览器访问），分析锚点是页面 URL 和 HTTP 状态码。**应用**是已定义的网络应用（通过 TCP/UDP 端口/协议识别），分析锚点是时间波峰和用户体验时间成分。

### 核心思路

- **B/S 业务分析**：以"页面 URL"为锚点下钻（哪个页面报错最多？）
- **C/S 应用分析**：以"时间波峰"为锚点下钻（哪个时刻最慢？那时谁在访问？）

### 参考来源

CS 查询设计参考 NAPM AppPro（单个应用剖析）接口文档 `单个应用剖析-接口文档.md`，使用标准用户体验指标体系：UEII（体感指数）、CSTI（建连时间）、TRTI（响应时间）、PTTO（传输时间）、RDTO（重传时延）。

## 分析流程

### Step 1 — 应用整体概览

| 查询 | 接口类型 | 指标 | 分组 |
|------|---------|------|------|
| appPerformanceSummary | `averageValues` | UEII, CSTI, TRTI, PTTO, RDTO | DefinedApp(应用名) |
| appTrafficTrend | `timeValues` | TPI, TPO | DefinedApp(应用名) |

**目的**：获取应用性能基线（五项用户体验指标均值）和流量趋势（判断断崖/突发）。

### Step 2 — 用户体验趋势（找波峰）

| 查询 | 接口类型 | 指标 | 分组 |
|------|---------|------|------|
| userExpTrend | `timeValues` | UEII, CSTI, TRTI, PTTO, RDTO | DefinedApp(应用名) |

**波峰标记策略**（`_analyzeCsStep2`）：
1. 提取 UEII 时序数据
2. 计算阈值 = 均值 + 2×标准差
3. 标记超过阈值的连续区间，区间内取最大值作为波峰
4. **离散尖峰 > 5 个** → 按 UEII 值降序取 Top 5
5. **持续高原**（区间跨度 > 50% 总时长 + ≥3 个区间）→ 取 5 个等间距采样点
6. 存储波峰列表到 `analysisFlags._selectedPeaks`

### Step 3 — 波峰窗口慢客户端定位

对每个波峰 ±30s 窗口：

| 查询 | 接口类型 | 指标 | 分组 | 排序 |
|------|---------|------|------|------|
| peak_N_clients | `topValues` | CSTI, TRTI, PTTO, RDTO | DefinedApp → ExternalIPs → IPAddress | UEII, Top 10 |

同时查询全窗口的 `overallSlowClients` 作为对照。

**无波峰时**：仅查全窗口慢客户端（优雅降级）。

## 关键设计决策

| 决策 | 选择 | 原因 |
|------|------|------|
| 分析对象 | **应用**（`DefinedApp`，Type=2） | 与 AppPro 接口文档一致；CS 流程对标 NAPM 的"应用"（DefinedApp），BS 流程对标"业务"（WebApplication） |
| Step3 分组 | `DefinedApp → ExternalIPs → IPAddress` | 与 AppPro slowClientApp 查询一致 |
| 指标体系 | UEII/CSTI/TRTI/PTTO/RDTO | NAPM AppPro 标准用户体验指标 |
| 波峰检测 | 均值+2σ 阈值 + 代码选取策略 | 简单有效，不需外部依赖 |
| 无波峰降级 | 仅查全窗口慢客户端 | 保证分析不中断 |
| 模板 ID | `napm_cs_fault_diagnosis_v1` | 与 BS 业务模板 `napm_bs_fault_diagnosis_v2` 命名对齐 |
| run() 分流 | 简单条件判断 | 仅 2 种标准化流程，不需要复杂路由 |

## 与 B/S 业务故障分析的对比

| 维度 | B/S 业务故障分析 | C/S 应用故障分析 |
|------|------|------|
| 分析对象（NAPM） | **业务** — `WebApplication` | **应用** — `DefinedApp` |
| 协议层 | HTTP/HTTPS（7 层） | TCP/UDP（4 层） |
| 下钻锚点 | 页面 URL | 时间波峰 |
| Step1 | 4xx/5xx 错误概览 | 性能概要 + 流量趋势 |
| Step2 | 页面错误 Top20（PGHTTP400/500） | 用户体验时序（UEII/CSTI/TRTI/PTTO/RDTO） |
| Step3 | pageViews 逐页状态码 | 波峰窗口慢客户端 IP |
| 核心问题 | 哪个页面报错最多？ | 哪个时刻最慢？那时谁在访问？ |
| 报告模板 | `napm_bs_fault_diagnosis_v2` | `napm_cs_fault_diagnosis_v1` |
| 报告标题 | `_业务故障分析报告` | `_应用故障分析报告` |

## 调用方式

```json
{
  "description": "某C/S架构桌面应用访问慢",
  "flowType": "cs_app_slow",
  "target": {
    "groupType": "DefinedApp",
    "groupArgument": "应用名-tcp",
    "groupLabel": "应用名"
  },
  "timeRange": {
    "faultWindow": { "start": 1782805440, "end": 1782891840 }
  }
}
```

**分类器触发**：描述中含 `客户端软件`、`数据库访问`、`非web`、`cs`、`c/s`、`固定端口`、`操作慢`、`桌面应用` 等关键词时自动路由到 `cs_app_slow`。
