# 功能一：复杂分析场景与问法样例

版本：v0.1
日期：2026-05-28
来源：基于 `2026-05-26-功能一复杂问题分析准备材料与实施指南.md` 生成的首版案例库

---

## 1. 使用目标

本文档用于收敛“功能一：复杂问题分析与复合查询分析”的首批用户场景，帮助 OpenClaw 稳定判断：

- 哪些问题属于复杂分析，而不是普通单步查询。
- 是否需要先 discovery 找对象。
- 应该落到哪个 `overviewScene`。
- 应该使用哪些主指标和辅助指标。
- 应该构造普通 `resolvedQuery`，还是 `overview + analysisPipeline.discoveryQuery`。

本文档中的时间戳均为示例占位。实际执行时必须先通过 `napm-resolve-time-range` 生成 `start/end`，再写入 `resolvedQuery` 根层级。

## 3. P0 详细案例

### S001：明确对象慢分析

用户原话：

```text
可观测239web 为什么慢？
```

可扩展问法：

```text
可观测239web 最近访问是不是变慢了？
看一下可观测239web 的性能问题。
可观测239web 页面响应慢是什么原因？
```

结构化标注：

| 字段 | 值 |
|---|---|
| 场景类型 | 单对象慢分析 |
| 目标对象 | WebApplication |
| 对象参数 | 可观测239web |
| 时间范围 | 默认 last1hour，用户指定则覆盖 |
| 是否需要 discovery | 否 |
| 是否需要多指标 | 是 |
| overviewScene | business |
| questionType | slow / performance |

推荐指标组合：

| 用途 | 指标 |
|---|---|
| 页面耗时 | PGTME、PGTMC、PGTMS |
| 慢页面 | PGNSLPGE、PGSLRT |
| 访问规模 | PGNPGE、PGHTTP200 |
| HTTP 错误 | PGHTTP500、PGHTTP500PCT、PGHTTP400 |

推荐 resolvedQuery 形态：

```json
{
  "service": "overview",
  "queryModeKey": "overview",
  "overviewScene": "business",
  "groups": [
    { "type": "WebApplication", "argument": "可观测239web" }
  ],
  "start": "<from napm-resolve-time-range>",
  "end": "<from napm-resolve-time-range>",
  "timeRange": {
    "key": "last1hour",
    "displayText": "最近一小时"
  },
  "semanticConstraints": {
    "workflowType": "focused_overview",
    "questionType": "slow",
    "targetObjectType": "WebApplication"
  },
  "format": "json"
}
```

期望输出：

```text
先给结论：是否慢、慢在哪里。
给证据：页面耗时、慢页面数量/比例、访问量、HTTP 错误。
给判断：更像服务端慢、页面慢、访问压力大，还是错误导致体验差。
给建议：优先检查慢页面、服务端处理、对应接口或时间段。
```

### S002：先发现连接失败最多的地址，再分析

用户原话：

```text
找到连接失败最多的地址，然后分析它。
```

可扩展问法：

```text
最近哪个 IP 连接失败最多？分析一下原因。
先找连接最异常的地址，再做综合分析。
失败连接最多的是谁，它为什么失败？
```

结构化标注：

| 字段 | 值 |
|---|---|
| 场景类型 | 先发现再分析 |
| 目标对象 | IPAddress |
| 时间范围 | 默认 last1hour |
| 是否需要 discovery | 是 |
| discovery 指标 | RFCI |
| 是否需要多指标 | 是 |
| overviewScene | network |

discovery 规则：

| 字段 | 值 |
|---|---|
| service | topValues |
| groups | IPAddress |
| metrics | RFCI |
| topMetric | RFCI |
| topCount | 1 |

推荐 resolvedQuery / analysisPipeline：

```json
{
  "service": "overview",
  "queryModeKey": "overview",
  "overviewScene": "network",
  "analysisPipeline": {
    "targetObjectType": "IPAddress",
    "selection": {
      "rank": 1
    },
    "discoveryQuery": {
      "service": "topValues",
      "queryModeKey": "topn",
      "groups": [
        { "type": "IPAddress" }
      ],
      "metrics": ["RFCI"],
      "topMetric": "RFCI",
      "topCount": 1
    }
  },
  "start": "<from napm-resolve-time-range>",
  "end": "<from napm-resolve-time-range>",
  "timeRange": {
    "key": "last1hour",
    "displayText": "最近一小时"
  },
  "format": "json"
}
```

期望输出：

```text
先说明发现的 IP。
说明连接失败数、连接请求数、失败趋势。
如有数据，补充关联应用、会话、对端或业务组。
判断是否为单点异常、范围性异常或流量压力导致。
```

### S003：最近哪些业务系统异常

用户原话：

```text
最近哪些业务系统异常？
```

可扩展问法：

```text
现在有哪些业务不正常？
最近哪个业务系统风险最高？
哪些 Web 应用需要重点关注？
```

结构化标注：

| 字段 | 值 |
|---|---|
| 场景类型 | 异常对象发现 |
| 目标对象 | WebApplication |
| 时间范围 | 默认 last1hour |
| 是否需要 discovery | 是 |
| 是否需要多指标 | 是 |
| overviewScene | business |

推荐 discovery 指标候选：

| 异常方向 | discovery 指标 | 说明 |
|---|---|---|
| HTTP 500 异常 | PGHTTP500 | 找服务端错误最多的业务 |
| 慢页面异常 | PGNSLPGE | 找慢页面最多的业务 |
| 页面耗时异常 | PGTME | 找平均耗时最高的业务 |
| 访问异常 | PGNPGE | 找访问量突增/高访问业务 |

首版建议：

```text
如果用户只说“异常”，优先走 business overview，并让 overview candidate 同时覆盖错误、慢页面、访问量。
如果必须 discovery，首选 PGHTTP500 和 PGNSLPGE 两类候选，后续由结果归并排序。
```

推荐结构：

```json
{
  "service": "overview",
  "queryModeKey": "overview",
  "overviewScene": "business",
  "start": "<from napm-resolve-time-range>",
  "end": "<from napm-resolve-time-range>",
  "timeRange": {
    "key": "last1hour",
    "displayText": "最近一小时"
  },
  "semanticConstraints": {
    "workflowType": "anomaly_discovery",
    "targetObjectType": "WebApplication",
    "questionType": "anomaly"
  },
  "format": "json"
}
```

期望输出：

```text
列出异常业务系统 TopN。
每个业务给异常依据：HTTP 500、慢页面、访问量、耗时。
按严重程度排序。
说明是否需要继续分析某个业务。
```

## 4. 普通单步查询与复杂分析的边界

普通单步查询：

```text
访问量最高的业务是谁？
最近一小时丢包最高的前 10 个 IP。
某 IP 的平均响应时间是多少？
某业务最近一小时流量趋势是什么？
```

复杂分析：

```text
某业务为什么慢？
某系统异常的原因是什么？
先找连接失败最多的地址，再分析它。
比较这几个业务系统谁风险更高。
系统整体有没有风险，哪些方向最值得关注？
```

判断原则：

- 只要用户要“原因、为什么、是否异常、整体情况、综合分析、风险、建议”，通常是复杂分析。
- 如果问题只要一个数值、排行或趋势，通常是普通单步查询。
- 如果用户说“先找……再分析……”，必须走 discovery + focused overview。
- 如果用户没有明确对象但要分析具体对象，必须先 discovery，不能编造对象。

---

## 5. 时间构造约束

复杂分析仍然必须遵守当前主链时间契约：

- OpenClaw 只能判断时间语义，例如 `last1hour`、`last24hours`、`today`、`yesterday`。
- 时间戳必须由 `napm-resolve-time-range` 生成。
- `resolvedQuery.start/end` 必须在根层级。
- `timeRange` 只保留 `key/displayText`。
- discovery 和 focused overview 默认复用同一组 `start/end`。
