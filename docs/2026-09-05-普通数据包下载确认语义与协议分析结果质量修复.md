# 普通数据包下载确认语义与协议分析结果质量修复

## 1. 文档目的

本文沉淀普通数据包请求在单 IP、业务组场景中的完整处理规则，以及本轮现场问题的证据、根因和修复结果。适用工具为 `napm-packet-analysis`，不适用于告警数据包批量分析或其他 NAPM 查询。

关联文档：[普通数据包确认续答与固定窗口修复](2026-09-04-普通数据包确认续答与固定窗口修复.md)。

## 2. 正确业务流程

```text
用户请求
  -> 识别目标和时间
  -> packetsPreview
  -> 返回预览和下一步决策
  -> 若 next_action=CONFIRM_DOWNLOAD，等待用户确认
  -> 恢复预览时已经物化的目标、start、end
  -> packetsDown
  -> capinfos/tshark 协议分析
  -> 结构化中文结果
```

单 IP 和业务组不是同一种目标，也不存在“单 IP 必须属于业务组”这一前置条件：

| 场景 | 目标解析 | 请求参数 |
| --- | --- | --- |
| 单 IP | 直接校验用户给出的 IP | `criteria.ips=[目标 IP]` |
| 业务组 | 先按名称查询 `businessGroups`，读取 `IpMembers`，拆分单 IP 和 IP 范围 | 分别填入 `ips` 和 `ipRanges` |

两者从 `packetsPreview` 开始共用预览、确认、下载和协议分析流程。不得用业务组成员替换用户明确给出的单 IP；单 IP 无数据时必须依据该 IP 的实际预览响应和审计日志判断，不能凭业务组结果推断。

业务组展开规则仍为：名称 → `businessGroups.Name` → `IpMembers` → 单 IP 放 `ips`、范围放 `ipRanges`。工作组名称不能直接作为 `packetsPreview/packetsDown` 的 IP 参数。

## 3. 现场问题与证据

### 3.1 预览成功，确认后却只返回 Skill 拦截提示

现场出现过以下模式：

1. 单 IP 最近 5 分钟预览成功，并返回“需要确认后才能继续”。
2. 用户随后说“进行下载分析！”、“确认下载并分析；”或“确认下载，进行分析！”。
3. 回复变成“当前问题必须经 NAPM skill 执行后才能回答”，没有下载文件，也没有协议分析。

远端审计记录显示，确认轮被创建成普通 `NAPM_QUERY`，随后出现 `napm_query_wrong_tool_blocked`，期望工具是 `napm-skill-query`，实际工具却是 `napm-packet-analysis`。对应确认轮没有 `packetsDown` 调用，也没有 tshark 进程。因此失败点是确认轮路由和状态恢复，不是单 IP 接口天然不支持。

### 3.2 下载成功，但答复泄漏原始 tshark 表格

后续现场已经出现下载完成和“数据包数：621 个”，说明下载及协议分析链路可以执行；但“协议层级”“主要端点”“主要会话”仍直接包含 `====`、`Protocol Hierarchy Statistics`、`Filter:`、英文表头和空表头。这是结果适配和答复格式问题，不是抓包文件本身的统计失败。

`_ws.malformed` 表示某些帧无法按当前协议解码，只能作为解析异常提示；它不等同于网络丢包，是否丢包要结合 TCP 指标或原始抓包进一步确认。

## 4. 根因

- 确认文本很短，单独看不含“数据包”或 IP，旧路径没有从同一会话的待确认预览恢复 packet 工作流。
- 确认轮默认落入 `NAPM_QUERY`，普通查询工具守卫因此阻断了 `napm-packet-analysis`。
- 续答若重新解析“最近 5 分钟”，会相对确认时刻重新计算，造成预览和下载窗口漂移。
- 模型自行传入确认标志或新目标时，若没有插件边界校验，会产生越权确认或查询条件变化。
- 重叠 Tool 调用没有统一合并时，模型重试可能触发重复下载。
- tshark 分析结果原先以行数组传递，最终答复只做了简单拼接，没有按协议、端点、会话等区段过滤表头和分隔线。

## 5. 修复方案

### 5.1 上下文优先的确认授权

确认语句本身只提供一个保守的动作意图信号，真正的授权来自同一 conversation scope 最近的一次有效 packet 预览。必须同时满足：

- `sourceTool=napm-packet-analysis`；
- `preview.ok=true`；
- `preview.empty=false`；
- `decision.next_action=CONFIRM_DOWNLOAD`；
- 预览保存了有效的 Unix 秒级 `start/end` 和目标条件。

不满足这些条件时，即使用户说“下载并分析”，也不能直接下载。

确认轮被规范化为明确的 packet continuation，route 为 `OTHER_SKILL`，不会再被普通 `NAPM_QUERY` 工具守卫拦截。

### 5.2 自然语言动作组合，而非固定短句白名单

实现按动作类别和上下文解析，不维护“只能匹配几个短句”的白名单。支持的类别包括：

- 承诺/继续动作：确认、同意、允许、批准、开始、继续、执行、进行、直接、请、帮我、可以、好的、按上一轮处理，以及常见英文表达；
- 数据包动作：下载、导出、获取、保存、抓取、拉取、提取、落盘；
- 分析动作：分析、解析、解码、检查、研判、协议分析，以及常见英文表达。

在存在有效待确认预览时，下列自然表达均可视为同一类续答（示例不是穷举列表）：

```text
确认下载并分析
确认下载，进行分析；
请把刚才预览的数据包下载下来并做协议解析
上一轮预览没有问题，直接执行下载分析
按之前的预览结果继续处理
可以开始下载这个 pcap 文件并分析吗
好的，继续
go ahead and download and analyze the preview
```

以下表达会被拒绝或要求重新发起查询：

```text
不要下载，先只看预览
下载了吗？
帮我分析一下为什么下载失败
重新分析 203.0.113.99 最近 5 分钟的数据包
换成另一个 IP，继续下载
```

拒绝原因分别是：否定动作、状态询问、故障诊断、重试/替换请求或显式新目标/新时间。裸“好的”“继续”等简短确认只有在同一会话存在有效 `CONFIRM_DOWNLOAD` 预览时才有效。

### 5.3 固定查询条件和幂等执行

- 初始预览把相对时间一次性物化为 Unix 秒级 `start/end`；确认轮删除 `timeRange`，复用原值，不重新计算“最近 5 分钟”。
- 确认轮忽略模型重新填写的 IP、业务组和时间，防止目标漂移。
- `previewRiskAccepted=true` 只能由插件根据可信待确认状态注入；初始请求或模型参数中的同名字段会被删除。
- 同一 `scope + turnId` 的并发或重复 execute 合并为一次实际 Skill、下载和 tshark 执行，后续调用复用权威结果。
- `SUGGEST_NARROW_TIME_RANGE`、空预览、缺少固定时间或非 packet 最近结果不能通过普通确认绕过。

### 5.4 结构化协议分析答复

下载成功后，插件消费 `result.analysis` 并按区段格式化：

- 协议层级 → 协议中文名、帧数、字节数；
- 端点 → IP、包数、总字节及发出/接收方向；
- 会话 → 有效的通信双方、帧数和字节数；
- DNS、HTTP、TLS SNI → 保留可用的查询、路径、状态和 SNI；
- `malformed` → 单独输出“协议解析异常帧”提示。

最终答复不得输出 tshark 原始分隔线、`Filter:`、英文表头或空会话表头。没有某一类数据时省略该行，不填充伪造的零值。

## 6. 期望输出契约

成功的下载分析至少应包含：

```text
时间范围：预览时固定的 start 至 end
目标：单 IP 或已展开的业务组成员
预览：命中记录、流量和主要通信（若有）
下载完成：文件名和字节数
协议分析：已完成
数据包数：N 个
协议分布：...
主要端点：...
主要会话：...
DNS/HTTP/TLS：按实际结果展示
解析提示：仅在存在 malformed 等解析异常时出现
```

如果下载未执行，必须明确写“仅预览，未下载”；如果 tshark 失败或没有有效分析结果，不得声称“协议分析已完成”。

开发分支已有验证记录：

- packet final 定向测试 26 项通过，覆盖自然语言确认正负例、固定条件恢复、裸确认、高风险时间范围、同轮并发单次执行和 tshark 表格清洗；
- packet 相关回归 14 个测试套件、111 个测试通过；
- 全量 Jest 108 个测试套件、1006 个测试通过；
- ESLint、Node 语法检查、Skill runtime contract、临时安装形态 extension runtime smoke 和 `git diff --check` 通过。

现场验收至少复测以下流程：

1. 单 IP 预览 → “下载并分析” → 下载和 tshark 均成功；
2. 业务组预览 → 自然语言确认 → 仍使用原业务组展开后的 `ips/ipRanges`；
3. 确认轮时间与首轮 `start/end` 完全一致；
4. 无待确认预览的“下载并分析”不会直接下载；
5. 输出中不存在 `====`、`Filter:` 和原始英文表头；
6. 重复确认不会产生第二次下载。

## 9. 结论

单 IP 查询本身与业务组查询相互独立；此前“只能预览不能下载”的主要故障是确认轮没有恢复 packet 上下文而被普通查询路由拦截。修复后，确认授权由“同会话有效预览上下文 + 动作意图”共同决定，下载沿用固定窗口并只执行一次；协议分析结果再经过结构化清洗，避免把 tshark 原始表格直接交给用户。
