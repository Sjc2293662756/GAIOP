# 故障分析流程类型自动解析方案 —— 基于 NAPM 目录的名称匹配

## 背景

当前 `FaultDiagnosisFlowRouter.classify()` 采用纯关键词匹配来判断走 BS（业务故障分析）还是 CS（应用故障分析）。在实际使用中发现两个问题：

1. **关键词覆盖不全**：用户说"可观测239的应用故障分析报告"，分类器匹配不到任何 CS 关键词，直接跌入默认（`network_slow`）
2. **名称歧义无法消解**：AI（观枢）看到"239"就联想到"239web"，自作主张走了 BS，但实际上"可观测239"在 NAPM 中是 `DefinedApp (Type=2)`——应该走 CS

根本原因：**关键词分类器没有 NAPM 对象类型的 ground truth 信息**。只有去 NAPM 实际查询该名称对应的 Type，才能做出正确判断。

---

## 核心思路

```
用户说 "可观测239的应用故障分析报告"
  │
  ├─ 提取候选名称: "可观测239"
  │
  ├─ 查 NAPM applications 目录
  │    { name: "可观测239",      type: 2 }  ← DefinedApp（应用）
  │    { name: "可观测239web",   type: 3 }  ← WebApplication（业务）
  │
  ├─ 名称匹配: "可观测239" 精确命中 type=2
  │
  └─ 判定: Type=2 → cs_app_slow → C/S 应用故障分析 ✓
```

**设计原则**：NAPM 自身数据目录作为 ground truth，关键词分类器作为 fallback。

## 详细设计

### 步骤 1：提取候选名称

从用户输入中提取要分析的目标名称。

#### 来源优先级

| 优先级 | 来源 | 说明 |
|:--:|------|------|
| 1 | `input.target.groupLabel` | 调用方已明确指定 |
| 2 | `input.target.groupArgument` | 同上 |
| 3 | `input.description` 正则提取 | 从自然语言中解析 |

#### 正则提取规则

**规则 A**：`XX的应用/业务故障分析`
```
(.+?)的(?:应用|业务)故障
```
匹配示例：
- `可观测239的应用故障分析报告` → 提取 `可观测239`
- `可观测239web的业务故障分析报告` → 提取 `可观测239web`

**规则 B**：`分析XX的应用/业务故障`
```
分析(.+?)(?:的)?(?:应用|业务)(?:故障|慢|异常)
```
匹配示例：
- `分析可观测239的应用故障` → 提取 `可观测239`
- `分析239web的业务慢` → 提取 `239web`

**规则 C**：`XX 应用/业务故障分析`
```
(\S+)\s*(?:应用|业务)故障
```
匹配示例：
- `可观测239 应用故障分析报告` → 提取 `可观测239`

**规则 D**：`给XX出故障报告`
```
给(.+?)(?:出|的).*(?:故障|分析|报告)
```
匹配示例：
- `给我可观测239的故障分析报告` → 提取 `可观测239`

**降级**：如果以上规则均不匹配，`extractTargetName()` 返回 `null`，跳过名称匹配，直接走关键词分类器。

### 步骤 2：查询 NAPM 应用目录

#### API

```
接口: applications
参数: csv=true
返回: [{ name, type, description, id, status }, ...]
```

Type 字段含义：

| Type | 含义 | 对应故障分析流程 |
|:--:|------|------|
| 1 | BuiltinApplication（内置端口应用） | `cs_app_slow`（映射为 DefinedApp） |
| 2 | DefinedApp（已定义应用） | `cs_app_slow` |
| 3 | WebApplication（业务） | `bs_app_slow` |
| 4 | CompositeApplication（自动识别复合应用） | `cs_app_slow`（映射为 DefinedApp） |

#### 缓存策略

`applications` 目录变化不频繁，在 `FaultDiagnosisService` 实例存活期间缓存一次即可：

```javascript
class FaultDiagnosisService {
  constructor(options = {}) {
    // ... existing code ...
    this._appCatalogCache = null;  // { list: [], fetchedAt: timestamp }
  }

  async _getAppCatalog() {
    const TTL_MS = 300_000; // 5 minutes
    if (this._appCatalogCache && (Date.now() - this._appCatalogCache.fetchedAt < TTL_MS)) {
      return this._appCatalogCache.list;
    }
    try {
      const raw = await this.client.request('applications', {});
      const list = Array.isArray(raw) ? raw : (Array.isArray(raw?.rows) ? raw.rows : []);
      this._appCatalogCache = { list, fetchedAt: Date.now() };
      return list;
    } catch (err) {
      // Query failed — return null, caller falls back to keyword classifier
      return null;
    }
  }
}
```

### 步骤 3：名称匹配

#### 匹配策略（按得分降序）

| 优先级 | 匹配方式 | 得分 | 条件 |
|:--:|------|:--:|------|
| 1 | **精确匹配** | 100 | `app.name === candidate` |
| 2 | **前缀匹配** | 80 | `app.name.startsWith(candidate)` |
| 3 | **包含匹配** | 50 | `app.name.includes(candidate)` |
| 4 | **候选名称被包含** | 40 | `candidate.includes(app.name)` 且 `app.name.length >= 3` |
| 5 | **模糊匹配** | 30 | 任意一方包含另一方，且 `app.name.length >= 2` |

匹配示例（候选名称 = `可观测239`）：

| applications 条目 | name | type | 匹配方式 | 得分 |
|------|------|:--:|------|:--:|
| 精确匹配 | `可观测239` | 2 | 精确匹配 | 100 |
| 前缀匹配 | `可观测239web` | 3 | 前缀匹配 | 80 |
| 包含匹配 | `交通可观测性分析平台` | 3 | 包含匹配 | 50 |
| 包含匹配 | `告警业务测试238、239` | 3 | 包含匹配 | 50 |

#### 得分相同时的处理

1. 优先取 **精确匹配** 的最高得分
2. 同得分时，优先取 **Type=2**（DefinedApp）——因为 DefinedApp 名称通常更短、更精确（如 `可观测239`），WebApplication 名称通常带后缀（如 `可观测239web`）
3. 仍相同 → 取第一个

### 步骤 4：类型判定

根据匹配到的 Type 决定 flowType 和 target.groupType：

```javascript
/**
 * 根据 NAPM application type 解析故障分析流程类型。
 * @param {object} match — matchAppByName 的返回值 { name, type }
 * @returns {object} — { flowType, groupType, groupArgument, groupLabel }
 */
function resolveFlowTypeFromCatalog(match) {
  // Type=3 → WebApplication → BS 业务故障分析
  // Type=1,2,4 → DefinedApp（或映射为 DefinedApp）→ CS 应用故障分析
  const isBusiness = match.type === 3;
  
  return {
    flowType: isBusiness ? 'bs_app_slow' : 'cs_app_slow',
    groupType: isBusiness ? 'WebApplication' : 'DefinedApp',
    groupArgument: match.name,
    groupLabel: match.name
  };
}
```

#### 关于 OtherApp

`OtherApp` 不在 `applications` 目录中（它来自 `groupArguments` 接口）。如果候选名称在 `applications` 中未命中但在 `groupArguments` 中能查到，说明是 `OtherApp`——此时应走 `cs_app_slow`，`groupType=OtherApp`。

作为第一版实现，可暂不处理 OtherApp 的自动发现（需要额外 API 调用），留到后续迭代。

### 步骤 5：集成到 FaultDiagnosisService.start()

```
start(input)
  │
  ├─ 如果调用方已传 input.flowType
  │    → 跳过解析，直接使用（保持现有行为）
  │
  ├─ 否则，调 extractTargetName(input)
  │    │
  │    ├─ 有名称 → _getAppCatalog() → matchAppByName() → resolveFlowTypeFromCatalog()
  │    │    │
  │    │    ├─ 命中 → 设置 input.flowType + 补全 input.target
  │    │    └─ 未命中 → 回退到 classify(input.description)
  │    │
  │    └─ 无名称 → 回退到 classify(input.description)
  │
  └─ 继续后续流程（保持现有逻辑不变）
```

#### 伪代码

```javascript
async start(input = {}) {
  // ── 1. 如果调用方已指定 flowType，直接使用 ──
  let flowType = input.flowType || null;

  // ── 2. 尝试名称 → NAPM 目录解析 ──
  if (!flowType) {
    const candidateName = extractTargetName(input);
    if (candidateName) {
      const catalog = await this._getAppCatalog();
      if (catalog) {
        const match = matchAppByName(candidateName, catalog);
        if (match) {
          const resolved = resolveFlowTypeFromCatalog(match);
          flowType = resolved.flowType;
          // 自动补全 target（如果调用方没传）
          if (!input.target || !input.target.groupType) {
            input = {
              ...input,
              target: {
                groupType: resolved.groupType,
                groupArgument: resolved.groupArgument,
                groupLabel: resolved.groupLabel
              }
            };
          }
        }
      }
    }
  }

  // ── 3. fallback: 关键词分类器 ──
  if (!flowType) {
    const description = String(input.description || input.fault?.description || '');
    flowType = classify(description);
  }

  // ── 4. 后续流程不变 ──
  const flow = getFlow(flowType);
  // ... existing code ...
}
```

## 容错策略

| 场景 | 处理 |
|------|------|
| `applications` API 调用失败（网络、超时） | `_getAppCatalog()` 返回 `null`，回退到关键词分类器 |
| 名称提取正则全部不匹配 | `extractTargetName()` 返回 `null`，回退到关键词分类器 |
| 名称在目录中匹配不到 | `matchAppByName()` 返回 `null`，回退到关键词分类器 |
| 多个应用同名（NAPM 中极罕见） | 取第一个精确匹配，打 warning 日志 |
| 调用方已传 `flowType` | 整个解析流程跳过，直接使用传入值 |

**关键保证**：这个方案**永远不会让现有功能变得更差**。最坏情况（目录查询失败/名称提取失败/匹配失败）下，行为完全等同于现在的关键词分类器。
