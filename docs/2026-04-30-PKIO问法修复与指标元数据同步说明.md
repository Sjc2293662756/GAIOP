# 2026-04-30 PKIO问法修复与指标元数据同步说明

## 今日修改概览

今天主要完成了两件事：

1. 修复 `数据包数量最多的前5个应用分别是谁` 这类问法被错误映射到 `PKTI`、`CONI` 的问题。

## 一、PKIO问法修复

### 1. 问题现象

用户提问：

- `数据包数量最多的前5个应用分别是谁`

实际返回中出现了以下异常情况：

- 将 `数据包数量` 误解释为 `PKTI`
- 继续兜底到 `CONI`
- 回复中夹带 `Let me query...` 这类内部推理文本

这说明当前链路里，`数据包数量` 这一类语义没有被前置钉死，后续消歧和兜底逻辑发生了漂移。

### 2. 根因分析

排查后确认主要原因有三点：

1. `config/nl-query-mapping.v1.json` 中原本没有把 `数据包数量 / 包数量 / 包个数 / 包流量` 这一组语义明确配置到 `PKIO`
2. `config/metric-semantic-disambiguation.v1.json` 中也缺少 `PKIO` 的显式消歧项
3. `NaturalLanguageQueryMapper` 与 `MetricSemanticDisambiguationService` 里还保留了偏泛化的“流量/吞吐/连接数”收敛逻辑，前置语义一旦不够硬，就会被后续逻辑带偏

### 3. 本次修改位置

1. `config/nl-query-mapping.v1.json`
2. `config/metric-semantic-disambiguation.v1.json`
3. `skills/openclaw-napm-query/services/NaturalLanguageQueryMapper.js`
4. `skills/openclaw-napm-query/services/MetricSemanticDisambiguationService.js`
5. 历史本地解析测试：`test/packet-metric-mapping.test.js`（现已移除）

### 4. 本次修复内容

统一将以下问法强制映射到包流量指标：

- `数据包数量`
- `包数量`
- `包个数`
- `数据包个数`
- `包流量`
- `总包流量`
- `packet count`
- `packet traffic`

收敛规则如下：

- 无方向词时：`PKIO`
- 有 `流入 / 入站 / 上行` 时：`PKI`
- 有 `流出 / 出站 / 下行` 时：`PKO`

同时增加保护逻辑：

- 这类问法不再允许被“泛流量归一化”改写成 `TPIO / TPI / TPO`
- 这类问法不再允许被消歧链路改写成 `PKTI`
- 这类问法不再落入连接数兜底 `CONI`

### 5. 验证结果

新增回归测试后，已确认：

- `数据包数量最多的前5个应用分别是谁`

本地映射结果稳定为：

- `service=topValues`
- `metric=PKIO`
- `groups[0].type=DefinedApp`

并且不会再被后续消歧改写为：

- `PKTI`
- `CONI`

## 二、指标元数据全量同步

### 1. 问题现象

对比远端接口：

- `https://101.254.114.238/webservice/NetInside?UserName=GAIOP&Password=GAIOP123&type=metrics&csv=true`

发现本地：

- `config/metrics-config.yml`

中的指标定义明显不全。

### 2. 对比结果

实际核对结果如下：

- 远端指标总数：`107`
- 本地原有指标总数：`52`
- 缺失指标数：`55`

缺失的关键指标包括但不限于：

- `PKIO`
- `PKI`
- `PKO`
- `PKTIO`
- `TRTO`
- `RTTO`
- `UEII`
- `UEIO`
- `PGNSLPGE`
- `PGTMC`
- `PGTMS`

此外，部分已有指标描述也已经落后于远端当前口径，例如：

- `PGNPGE`
- `PGTME`
- `RFCI`
- `RFCO`
- `CCNI`
- `CCNO`

### 3. 本次修改位置

1. `config/metrics-config.yml`

### 4. 本次同步内容

本次已将本地指标表直接按远端 `metrics` 接口全量重建，主要变化如下：

- 指标数量从 `52` 补齐到 `107`
- 所有 `code` 与远端保持一致
- `description` 统一按远端当前返回值更新
- 新增 `unit` 字段，保留远端单位信息

说明：

- 当前 `MetricMappingService` 读取该文件时只依赖 `code` 和 `description`
- 因此增加 `unit` 不会影响现有链路
- 后续如需在展示层或叙述层用到单位，可直接复用该字段

### 5. 验证结果

本地校验结果：

- `metrics-config.yml` 可正常被 YAML 解析
- `MetricMappingService` 启动后实际加载指标数为 `107`
- `PKIO` 已包含在配置中

截至今天，项目在这两个点上已经收口：

1. `数据包数量 / 包流量` 这一类问法，skill 侧已能稳定映射到 `PKIO` 体系，不再漂到 `PKTI` 或 `CONI`
