# 2026-05-21 NAPM 边界收口与远端部署说明

## 1. 本次目标

本轮修改的目标是把 `napm-openclaw-plugin` 进一步收口为“薄桥接层”，把 `resolvedQuery` 的语义构造职责尽量回收到 skill 侧，并为后续继续删除 plugin 内的语义遗留逻辑建立稳定可测试基线。

核心方向：

- plugin 主链路不再根据原始 prompt 注入、替换或改写 `resolvedQuery`
- plugin 保留：
  - tool 注册
  - skill-first 守卫
  - 危险工具拦截
  - 必要的回复守卫与异步刷新
- skill 保留：
  - `resolvedQuery` 归一化
  - session continuation 合并
  - metadata / ownership 校验
  - query execution
  - narration contract 输出
- rollout 默认仍使用 `compat`，保证现网问法不会因为边界切换立即失效

## 2. 背景结论

结合设计稿 `resolvedQuery-boundary-design.md` 与当前项目现状，本轮确认了三条边界原则：

1. OpenClaw 主链 / 上游应该是 `resolvedQuery` 的正式拥有者。
2. plugin 不应继续承担 prompt 到 `resolvedQuery` 的主链语义构造职责。
3. 在完全切到 strict 之前，skill 可以在 `compat` 模式下保留有限的 prompt fallback，用于过渡期兼容。

## 3. 本次修改清单

### 3.1 新增边界规格文件

新增文件：

- `config/napm-resolution-spec.v1.json`

作用：

- 集中描述 query contract、service spec、object alias、metric alias、routing rules、boundary rules
- 给 plugin 和 skill 提供统一边界约束来源
- 为后续 strict 模式切换提供单点规范文件

该文件重点声明：

- plugin 不应拥有：
  - `prompt_to_resolvedQuery_semantic_construction`
  - `path_preflight_query_rewrite`
  - `overview_scene_replacement`
  - `inventory_query_fabrication`
- plugin 应拥有：
  - `tool_registration`
  - `skill_first_tool_guard`
  - `dangerous_tool_block`
  - `thin_skill_bridge`
- skill 在 strict 模式下不应再做 prompt-only fallback

### 3.2 新增 ResolutionSpecService

新增文件：

- `skills/openclaw-napm-query/services/ResolutionSpecService.js`

职责：

- 加载 `config/napm-resolution-spec.v1.json`
- 提供 `loadResolutionSpec()`
- 提供 `getServiceSpec()`
- 提供 `getBoundaryMode()`
- 提供 `isStrictBoundaryMode()`

这样 plugin 和 skill 不再各自散落维护边界模式，而是统一从同一份配置读取。

### 3.3 plugin 主链不再注入 resolvedQuery

修改文件：

- `napm-openclaw-plugin.remote.js`

核心改动：

1. 新增 ResolutionSpecService 动态加载逻辑
2. 新增：
   - `getBoundaryMode()`
   - `isStrictBoundaryMode()`
3. `prepareSkillExecutionArgs()` 不再根据 prompt 自动塞入 `resolvedQuery`
4. `buildCanonicalSkillToolParams()` 不再根据 prompt 自动塞入 `resolvedQuery`
5. `buildForwardSkillArgsFromDirectTool()` 不再补 overview 型 `resolvedQuery`
6. `applyPathPreflightToSkillArgs()` 不再在主链路改写 `resolvedQuery`
7. overview / metric inventory / business inventory 的异步刷新逻辑，改为只把 `prompt` 和 `userQuery` 交给 skill，不再由 plugin 伪造 fallback query

这意味着：

- plugin 仍然保留 helper 能力
- 但 helper 不再自动参与主链 query 注入
- helper 现在主要用于：
  - 局部守卫
  - 独立测试
  - 过渡期验证

### 3.4 skill 新增 compat 模式的丢包 prompt fallback

修改文件：

- `skills/openclaw-napm-query/scripts/run_napm_query.js`

新增能力：

- `isPromptFallbackPacketLossClientTopPrompt(prompt)`
- `buildPromptFallbackPacketLossClientTopResolvedQuery(prompt)`

能力含义：

- 当处于 `compat` 模式且 prompt 类似“哪个客户端IP丢包最高”时
- skill 自己在本地完成 `topValues + IPAddress + PLI/PLO + topCount=1` 的 fallback 构造
- 不再要求 plugin 先帮忙构造

这一步是“职责回收”的关键：

- packet loss 兼容能力仍在
- 但主链 owner 从 plugin 迁到 skill

### 3.5 strict 模式下强制要求上游提供 resolvedQuery

修改文件：

- `skills/openclaw-napm-query/scripts/run_napm_query.js`

行为变化：

- `compat`：
  - 仍允许 metric inventory / business inventory / packet loss / unknown port / overview 等有限 prompt fallback
- `strict`：
  - 不再允许 prompt-only fallback
  - 缺少 `resolvedQuery` 时抛出 `UPSTREAM_RESOLVED_QUERY_REQUIRED`
  - error details 中显式返回 `boundaryMode: strict`

这为后续正式切 strict 提供了完整开关。

### 3.6 RequirementParserService 多层路径兼容修复

修改文件：

- `skills/openclaw-napm-query/services/RequirementParserService.js`

本轮保留并验证了此前已做的修复：

- `buildMetricCandidatesFromMetadataReview()` 在 multilevel path 场景下
- 即使静态 ownership 不完全匹配
- 只要 runtime metadata 明确支持，也允许保留候选 metric

收益：

- 避免多层路径 query 被过早错误过滤
- 让 runtime metadata 校验结果拥有更高优先级

### 3.7 环境变量示例补充

说明：

- `strict` 是下一阶段目标模式

## 4. napm-openclaw-plugin 当前职责说明

本轮之后，`napm-openclaw-plugin` 的职责更明确了。

### 4.1 现在仍由 plugin 负责

- 注册 `napm-skill-query`
- 注册直连查询工具：
  - `napm-topn`
  - `napm-average`
  - `napm-timeseries`
- 维护 skill-first 策略
- 阻断危险工具：
  - `exec`
  - shell / deploy / restart / systemctl / docker / kubectl 等
- 对明显旁路/越界回复做 rewrite 或 cancel
- 在必要时通过 `message_sending` 触发异步 skill refresh

### 4.2 不再由 plugin 主链负责

- 根据 prompt 构造 overview query
- 根据 prompt 构造 metric inventory query
- 根据 prompt 构造 business inventory query
- 根据 prompt 构造 packet-loss top query
- 根据 prompt 强制改写 path preflight 后的 groups
- 根据 prompt 替换已有 `resolvedQuery`

### 4.3 当前仍留在 plugin 内但已弱化为遗留 helper 的能力

- `buildOverviewResolvedQuery`
- `buildMetricInventoryResolvedQuery`
- `buildBusinessObjectInventoryResolvedQuery`
- `buildPacketLossClientTopResolvedQuery`
- `applyPathPreflightToResolvedQuery`

这些函数现在更多是：

- 单独 helper
- 测试支撑
- 迁移过渡遗留

后续如果继续收口，可以进一步评估删除或继续下沉。

## 12. 2026-05-21 追加修正：上游 resolvedQuery 产出稳定性收口

### 12.1 这次真正的问题，不是 skill 兜底不够

针对企业微信中的这类问法：

- `系统中有哪些工作组？`
- `业务都可以查哪些指标？`
- `BusinessGroup 可以往下钻到哪里？`

本次重新核查后确认，真正的问题不是 skill 缺少更多 prompt fallback，而是上游 OpenClaw 主链没有稳定地产出 `resolvedQuery`。

也就是说，问题根因是：

1. `napm-resolution-spec.v1.json` 已经定义了 query contract、对象别名和 service 模式
2. 但 plugin 注入给 OpenClaw 的系统上下文，之前仍在强调“直接把 raw prompt 丢给 napm-skill-query”
3. 这会让上游默认把 skill 当作“帮忙从自然语言继续猜 query 的地方”
4. 最终导致 metadata inventory / hierarchy / overview 这类结构化问题，不能稳定形成 `resolvedQuery`

所以这次修正的核心，不是继续增加 fallback，而是反过来约束上游：

- OpenClaw 必须先完成意图理解与结构化
- 再携带 `resolvedQuery` 调用 `napm-skill-query`

### 12.2 这次新增的上游约束

修改文件：

- `skills/openclaw-napm-query/services/ResolutionSpecService.js`
- `napm-openclaw-plugin.remote.js`

本次新增的关键能力：

1. `ResolutionSpecService` 新增：
   - `getQueryContract()`
   - `getObjectAliases()`
   - `getRoutingRules()`
   - `getMetadataRules()`
2. plugin 开始真正消费 `napm-resolution-spec.v1.json` 的以下内容：
   - query contract
   - object aliases
   - routing rules
   - metadata rules
3. `buildNapmRoutingSystemContext()` 改为明确告诉 OpenClaw：
   - `resolvedQuery` 应由上游主链构造
   - `napm-skill-query` 是 structured query executor，不是自然语言主解析器
   - `系统中有哪些工作组？` 应构造成：
     - `service=groups`
     - `queryModeKey=metadata`
     - `semanticConstraints.operation=metadata_list`
     - `groups=[{type:"BusinessGroup"}]`
4. `napm-skill-query` 的 tool description 也已改为 `resolvedQuery-first` 契约

### 12.3 新增 tool-call 硬拦截

本次最关键的运行时收口是：

- 对 metadata inventory / hierarchy / overview / packet loss 这类结构化 NAPM 请求
- 如果 OpenClaw 调 `napm-skill-query` 时没有带合格的 `resolvedQuery`
- plugin 现在会在 `before_tool_call` 直接阻断

阻断信息会明确提示：

- 缺少 `resolvedQuery`
- 或 `resolvedQuery` 缺少 service 对应的必填字段
- 并要求 `OpenClaw must construct resolvedQuery first`

这意味着：

- 以后不会再默认鼓励“raw prompt -> skill 内部继续猜 query”
- 上游如果没完成结构化，会直接暴露为链路问题
- 便于继续把主责稳定收回到 OpenClaw mainflow

### 12.4 针对“工作组”类问法的额外识别

为了让这条硬约束真正覆盖到 `系统中有哪些工作组？`，plugin 侧本次还新增了：

- `isBusinessGroupInventoryPrompt(prompt)`
- `shouldRefreshBusinessGroupInventory(prompt, rememberedRecord)`

作用不是继续 fabricating query，而是：

- 把 `工作组/业务组/BusinessGroup` 清单识别成“必须由上游先构造 resolvedQuery”的结构化 metadata 请求
- 防止它被错当成普通聊天或泛化描述

### 12.5 本次新增验证

新增/调整测试覆盖了以下行为：

1. `系统中有哪些工作组？`
   - 若未携带 `resolvedQuery`
   - `before_tool_call` 必须返回 `block=true`
2. `系统中有哪些工作组？`
   - 若携带：
     - `service=groups`
     - `queryModeKey=metadata`
     - `semanticConstraints.operation=metadata_list`
     - `groups=[{type:'BusinessGroup'}]`
   - 则允许通过
3. `业务都可以查哪些指标？`
   - prompt-only 调用 `napm-skill-query` 不再被视为合法主链输入
4. tool definition 必须显式体现：
   - `resolvedQuery-first`
   - `resolvedQuery` 是 NAPM 结构化请求的 required payload
