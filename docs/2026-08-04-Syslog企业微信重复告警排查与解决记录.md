# Syslog 企业微信重复告警排查记录

**日期**：2026-08-04  
**范围**：NAPM Syslog 接收、`openclaw-napm-syslog-watcher`、企业微信机器人推送  
**结论状态**：根因已定位并完成即时修复；未修改 rsyslog、NAPM 源端、企业微信 Webhook 或业务代码。

## 0. 处理结果

已停止脱离服务管理的旧 watcher 进程（排查时为 PID 6352）。该进程与系统级 watcher 使用相同脚本、相同配置并消费同一个 syslog 文件，是企业微信双推的直接原因。

修复后的远端状态：

- 系统级 `napm-syslog-watcher.service` 仍为 `active/running`；
- `run_syslog_watcher.js` 仅剩系统级 watcher 主进程；
- 系统级 watcher 仅保留一个对应的 `tail -F -n 0 /var/log/netinside/syslog.log` 子进程；
- 等待 8 秒后旧 watcher 没有被自动重启；
- 用户级 `gaiop-syslog-receiver.service` 保持 `active`，但它运行的是不同的 `openclaw-napm-syslog-receiver` 脚本，README 明确说明其不包含企业微信/Webhook 投递配置，因此不是本次企业微信双推来源。

本次停止的是精确确认的孤立旧进程，不是 `gaiop-syslog-receiver.service`，也没有停止系统级 watcher。

## 1. 问题现象

企业微信中出现两条内容完全相同的告警通知。截图中的两条消息具有相同的：

- 告警名称和严重级别；
- 监控对象和指标值；
- `Alert ID=124`；
- `Event ID=738756`；
- 告警开始时间和接收时间。

这不是“同一规则在不同监控对象上触发”的正常多告警场景，而是同一业务事件被企业微信推送两次。

## 2. 调查范围与约束

本次只执行了远端只读检查：服务状态、进程、rsyslog 配置、原始 syslog、watcher journal 和 watcher 输出日志。没有执行以下操作：

- 未重启、停止或禁用任何服务；
- 未修改 watcher 配置或源代码；
- 未调用企业微信 Webhook；
- 未保存密码、Webhook、token 或其他认证信息到本文件。

## 3. 实际链路

```text
NAPM 告警源
  -> UDP/514
  -> rsyslog (imudp + netinside_udp514 ruleset)
  -> /var/log/netinside/syslog.log
  -> 一个或多个 SyslogWatcherService 实例 (tail -F -n 0)
  -> SyslogParserService
  -> AlertEnrichmentService (NAPM alertsDetail 查询)
  -> WeComPushService (企业微信 Webhook HTTPS POST)
```

rsyslog 的远端配置显示：

- `rsyslog.service` 处于 `active`；
- UDP `514` 同时监听 IPv4 和 IPv6；
- `/etc/rsyslog.d/10-netinside.conf` 加载 `imudp`；
- 接收规则使用 `netinside_udp514` ruleset；
- ruleset 只有一个 `omfile` 写入动作，目标为 `/var/log/netinside/syslog.log`，模板为 `NetinsideSyslogRaw`。

因此，watcher 不接收 UDP 报文，也不会向该原始 syslog 文件回写；它只消费 rsyslog 已落盘的新增行。

## 4. 原始 Syslog 的重复性结论

远端快照时 `/var/log/netinside/syslog.log` 约 30 MB、47,254 行。全部告警行来自同一个 NAPM 告警源，最近 1,000 行均为 `appAlerts`。

### 4.1 完全重复与语义重复

| 口径 | 统计结果 | 解释 |
| --- | ---: | --- |
| 完整原始行完全相同 | 0 组 | 没有同一字节内容的重复行。 |
| 仅移除接收时间戳后完全相同 | 38 组、110 行 | 少量持续告警会重复上报相同状态和相同指标，仅接收时间不同。 |
| `elogid` 出现两次 | 20,416 个 | 通常是一条触发记录和一条恢复记录。 |
| `elogid` 出现超过两次 | 778 个 | NAPM 对持续中的同一事件周期性上报状态更新。 |

`elogid` 是事件标识；`alertid` 是告警规则标识，不能将 `alertid` 的重复视为单事件重复。

### 4.2 持续告警更新的例子

某个事件在告警持续期间出现 577 次：其 `elogid`、告警开始时间和监控对象相同，但每分钟上报的指标值不同。该模式说明 NAPM 会持续发送当前状态，而不是只在触发时发送一条消息。

另有少量事件在持续期间指标值也相同，导致“去除接收时间后内容一致”。这说明源端或 UDP 链路向 rsyslog 交付了等价状态报文；rsyslog 的单一写入规则和 watcher 都不是该原始文件重复行的生成者。

## 5. 截图事件 `elogid=738756` 的逐段证据

对企业微信截图中的事件，在原始 syslog 中只找到了两条记录：

| 时间 | `alertid` | `elogid` | `starttime` | `endtime` | 指标值 | 含义 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| 15:42:18 | 124 | 738756 | 1785829320 | 0 | 1033.3700 | 告警触发/持续中。 |
| 15:43:18 | 124 | 738756 | 1785829320 | 1785829380 | `N/D` | 告警恢复。 |

这证明企业微信的两条同内容消息不是由源端为该触发状态发送两份原始日志造成的。

在 15:42:10 至 15:42:30 的 systemd watcher journal 中，受 systemd 管理的 watcher 仅记录：

1. 一次“发现告警”；
2. 一次按 `elogid=738756` 的详情查询；
3. 一次“已推送企业微信”。

也就是说，systemd watcher 对该原始触发行只做了一次推送。

## 6. 企业微信重复通知的根因

服务器上同时存在两个运行中的 watcher 实例，均使用同一脚本、同一配置、同一 syslog 文件：

| 进程 | 管理边界 | 启动时间 | 标准输出 | tail 子进程 |
| --- | --- | --- | --- | --- |
| PID 6303 | `system.slice/napm-syslog-watcher.service` | 2026-07-14 15:29:41 | systemd journal | 一个 `tail -F -n 0 /var/log/netinside/syslog.log` |
| PID 6352 | `user.slice/.../session-13673.scope` | 2026-07-14 15:29:41 | `/home/netinside/.openclaw/logs/syslog-watcher.out.log` | 一个 `tail -F -n 0 /var/log/netinside/syslog.log` |

同一时刻还检测到用户级服务 `gaiop-syslog-receiver.service` 处于运行状态。后续核验表明，该服务运行的是不同的 `openclaw-napm-syslog-receiver` 脚本，负责兼容接收，不包含企业微信/Webhook 投递配置。它虽然也读取同一 syslog 文件，但不是本次双推来源，不应作为重复 watcher 停止。

两个实例会同时读到同一条触发日志，并各自执行一次企业微信 Webhook POST。于是对于 `elogid=738756`：

```text
一条原始触发 syslog
  -> systemd watcher 推送一次
  -> 用户会话 watcher 推送一次
  -> 企业微信显示两条相同通知
```

这就是截图中完全相同通知的直接根因。

## 7. Watcher 收到日志后的处理行为

实现位于：

- `skills/openclaw-napm-syslog-watcher/services/SyslogWatcherService.js`
- `skills/openclaw-napm-syslog-watcher/services/SyslogParserService.js`
- `skills/openclaw-napm-syslog-watcher/services/AlertEnrichmentService.js`
- `skills/openclaw-napm-syslog-watcher/services/WeComPushService.js`

处理顺序如下：

1. 通过 `tail -F -n 0` 监听新行；`-F` 支持日志轮转，`-n 0` 不重放启动前的存量日志。
2. 先按 UTF-8 解码；若出现替换字符则回退 GBK。
3. 解析 rsyslog 头部和 `xxxAlerts severity=... alertid=...` 告警体。
4. 提取 `alertid`、`elogid`、`starttime`、`endtime`、对象路径、触发条件及 `metricN/valueN/unitsN`。
5. 当所有指标值为 `N/D` 时，认定为恢复事件，只记录“跳过已恢复告警”，不推送企业微信。
6. 对非恢复事件，优先使用 `elogid` 查询 NAPM `alertsDetail` 补充详情。
7. 调用 `WeComPushService.pushAlert()`。

远端实际配置 `dedup.windowSeconds=0`，即当前关闭去重。因而每条持续告警更新都会继续处理和推送。

## 8. 企业微信推送行为

`WeComPushService` 会：

1. 根据业务告警等级选择对应路由 Webhook；无专用路由时使用默认 Webhook。
2. 若配置了签名密钥，则向 URL 追加 HMAC-SHA256 签名；否则直接使用 Webhook URL。
3. 构造 `markdown_v2` 消息，包含告警名称、等级、类别、时间、触发条件、监控对象、指标、`Alert ID`、`Event ID` 和告警时间窗。
4. 对 Webhook 发起 HTTPS POST，超时为 10 秒。
5. 只在接口返回成功码时计为成功；失败时记录错误和进程内计数。

当前实现没有持久化出站队列，也没有企业微信推送的可靠重试或补偿机制。进程重启后，去重缓存和推送失败状态均会丢失。

## 10. 风险与建议

### 10.1 已实施的即时处置

1. 已保留 systemd 系统服务 `napm-syslog-watcher.service`。
2. 已确认 PID 6352 的命令行为旧版 `run_syslog_watcher.js`，其父进程为 PID 1，且不属于系统级 watcher 的 cgroup。
3. 已向 PID 6352 发送 `SIGTERM`，由 watcher 的优雅退出逻辑停止其 `tail -F` 子进程。
4. 已在停止后验证：仅剩一个 `run_syslog_watcher.js` 实例和一个该 watcher 对应的 `tail -F` 子进程。
5. 已保留 `gaiop-syslog-receiver.service`，因为它是无企业微信投递能力的独立兼容接收器。

在后续维护中，如再次出现第二个 watcher，应先确认其所属服务和是否存在其它依赖：

   ```bash
   systemctl status napm-syslog-watcher.service --no-pager
   systemctl --user status gaiop-syslog-receiver.service --no-pager
   pgrep -af run_syslog_watcher
   ```

不要仅因其也读取 syslog 文件而停止 `gaiop-syslog-receiver.service`；应以是否运行 `run_syslog_watcher.js`、是否持有企业微信投递配置作为区分依据。

### 10.2 防复发建议

1. 在 systemd unit 的 `ExecStart` 前使用 `flock`，或使用 `RuntimeDirectory` 配合 pidfile，确保同一日志路径只能有一个 watcher 实例。
2. 为 watcher 增加启动自检：若已存在同配置、同日志路径的 watcher，则拒绝启动并写明已有 PID。
3. 保留 `elogid` 作为事件键。不要仅以 `alertid` 去重，因为同一规则可以同时作用于多个对象。
4. 对持续告警定义明确的通知策略：首次触发必推；后续更新仅在等级变化、指标变化超过阈值或达到提醒间隔时推送。
5. 为企业微信失败推送增加持久化队列和可观测的重试/补偿机制。

### 10.3 验收标准

完成清理和单实例保护后，针对一个新的 `elogid`：

1. 原始 syslog 只有一条触发记录时，企业微信只收到一条通知。
2. 同一事件的恢复记录仅在 watcher journal 中显示“跳过已恢复告警”，企业微信不新增通知。
3. `pgrep -af run_syslog_watcher` 只显示一个 watcher 主进程。
4. 独立的 `gaiop-syslog-receiver.service` 可继续存在，但不应运行 `run_syslog_watcher.js` 或拥有企业微信 Webhook 投递能力。
5. systemd watcher journal 和企业微信通知数在同一时间窗内一一对应。
