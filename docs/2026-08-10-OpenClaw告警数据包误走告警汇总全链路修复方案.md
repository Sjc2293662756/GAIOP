# OpenClaw 告警数据包误走告警汇总全链路修复方案

日期：2026-08-10  
适用范围：OpenClaw 企业微信通道、NAPM OpenClaw 插件、`openclaw-napm-alert-query`、`openclaw-napm-packet-analysis`  
当前状态：告警详情、数据包分析和复合工具路由已完成本地修复、测试服务器部署与真实事件回放；2026-08-10 14:13 新发现“工具前导语抢占最终交付”缺陷，数据执行成功但完整报告未投递，当前已诊断、尚待修复。详见本文第 19 节。

## 1. 文档目标

本文档解决一类明确的业务请求：

```text
根据指定告警事件，分析其触发时间附近的真实网络数据包，
定位告警指标异常的原因。
```

代表性输入：

```text
分析告警数据包 eventId=745278 start=1786327320 end=1786327560
用户体验时间（服务器）
触发指标值: 用户体验时间（服务器）=3055.3701毫秒
告警级别: 紧急
触发条件: 如果 用户体验时间（服务器） > 3000.0 则为 Critical ...
```

该请求的目标不是查询告警数量，也不是生成告警汇总，而是：

1. 用 `eventId` 查询告警明细。
2. 从告警明细中定位对象及关联 IP 会话。
3. 使用输入中的固定 `start/end` 分析数据包。
4. 把现有数据包 Skill 的分析证据与告警触发值关联。
5. 输出告警原因、证据和结论边界。

## 2. 范围界定

### 2.1 本次必须解决的问题

1. “告警数据包分析”被错误当成普通告警查询。
2. OpenClaw 模型可以把 `mode=detail` 改成 `analysis/summary`。
3. 固定 `start/end` 可以被模型增加的 `timeRange.key` 静默覆盖。
4. 告警推送先到达、`alertsDetail` 稍后可见时，当前链路不会重试。
5. 指定事件明细暂时为空时，被误渲染为七大类告警全部为 0。
6. 告警结果出现后，下一步数据包 Skill 仅靠文本指令要求模型继续调用。
7. `message_sending` 将中间事件和最终事件都改写成同一份告警结果，导致重复发送。

### 2.2 本次明确不处理的问题

1. 不修改 `openclaw-napm-packet-analysis` 当前的数据包下载和分析算法。
2. 不把“数据包分析能力不足”作为本次已证实根因。
3. 不修改 OpenClaw 核心源码。
4. 不改变普通告警汇总、告警时间线、单独数据包分析和普通故障诊断的业务口径。

原因：本次真实会话中 `napm-packet-analysis` 一次都没有被调用，因此不能根据本次故障得出“现有数据包 Skill 无法分析原因”的结论。必须先修通调用链路，再使用真实数据包结果评估分析能力。

## 4. 已证实根因

### 4.1 “告警数据包”没有独立的确定性工作流

当前插件已能识别 `activeAlertPacketPrompt`，系统上下文也明确写了：

```text
告警数据包 -> napm-alert-query FIRST -> napm-packet-analysis
```

但该顺序只是给模型的文本指令，不是 JavaScript 强制状态机。模型仍可以选择 `analysis/summary`，也可以在中间空结果后自行扩大查询范围。

### 4.2 `before_tool_call` 只校验工具大类，不校验工作流阶段

当前门禁会阻止数据包请求走 shell/curl 或普通 `napm-skill-query`，但对告警数据包请求，仍允许：

```text
napm-alert-query
napm-packet-analysis
```

门禁没有表达：

```text
当前是否必须查询 detail
当前 detail 是否已成功
当前是否已获得 packet candidates
当前是否已完成 packet analysis
```

因此门禁能防止跨域工具，但不能保证同一业务工作流内的正确顺序。

### 4.3 固定时间和相对时间可同时进入执行器

`run_alert_query.js` 会把 `timeRange.key/start/end` 同时交给公共时间解析器。当相对 key 存在时，当前 `resolveExecutionTime()` 优先使用 key，所以第一次调用中用户明确给出的 `10:02-10:06` 被 `last1hour` 覆盖。

对本工作流而言，推送中的 `start/end` 是权威的数据包分析窗口，不允许模型增加任何相对时间。

### 4.4 告警明细查询没有处理近实时可见性延迟

`alertsDetail` 在当前执行链路中只调用一次。空结果会立即被当成稳定业务结论，没有“推送已收到，但明细暂未可见”的中间状态。

### 4.5 详情空结果复用了汇总模板

详情模式在 `details=[]` 时，叙述层仍使用告警汇总模板，因而生成：

```text
告警总数：0 条
网络性能告警：0 条
...
智能分析告警：0 条
```

该文案只能用于汇总查询，不能表示“指定事件当前暂未可见”。

### 4.6 数据包交接仍依赖模型二次决策

告警 Skill 获得 `packetInstruction` 后，插件只是向模型输出“必须继续调用 `napm-packet-analysis`”。这是建议性控制，不是执行性控制。

真实日志已证明，模型可以忽略该指令，改为继续查询告警汇总。

### 4.7 发送钩子没有每轮唯一的最终交付认领

`message_sending` 中只要当前 prompt 属于告警上下文且存在最近告警结果，就会把当前待发事件替换为完整告警回答。

该分支没有同时校验：

```text
当前是否为最终 assistant 消息
当前 turn 是否已经交付过文本
当前内容指纹是否已发送
```

从而造成“3 个 toolResult + 1 个 assistant final -> 4 份相同最终文本”的发送结果。

## 5. 解决方案总览

本次不修改 OpenClaw 核心，而是使用 OpenClaw 现有插件机制实现一个确定性复合工具：

```text
napm-alert-packet-analysis
```

工作流划分：

```text
OpenClaw 插件层
  -> 识别 alert_packet_analysis
  -> 注册 napm-alert-packet-analysis
  -> 门禁禁止走其他工具
  -> 绑定 conversationKey / turnId / traceId

复合 Skill 编排层
  -> 解析和校验 eventId/start/end/触发指标
  -> 只调用 alertsDetail
  -> 处理明细可见性重试
  -> 消费 packetInstruction/suggestedPacketQuery
  -> 直接调用现有 napm-packet-analysis

OpenClaw 输出层
  -> 记忆本轮复合 Skill 结果
  -> 只允许基于数据包结果生成最终回答
  -> 每轮最多交付一次
```

不建议把自动数据包下载分析直接塞入普通 `napm-alert-query`。普通告警汇总和告警详情应继续保持只读查询语义；跨 Skill 编排由独立复合工具承担，避免影响普通告警场景。

## 6. OpenClaw 接入设计

### 6.1 意图名称和优先级

新增工作流意图：

```text
workflowType=alert_packet_analysis
```

优先级必须高于：

```text
alert_query
packet_analysis
fault_diagnosis
summary
ordinary_napm_query
```

最小识别条件：

```text
同时包含“告警”和“数据包/报文/抓包”
且包含可解析的 eventId
```

代表性正样例：

```text
分析告警数据包 eventId=745278 start=... end=...
分析告警 745278 的数据包
根据告警 eventId:745278 抓包定位原因
查看这条告警的报文并分析为什么触发
```

反样例：

```text
最近一小时告警情况
查询 eventId=745278 的告警详情
分析 101.254.114.237 的数据包
查看某业务的故障原因
```

### 6.2 输入解析契约

从 canonical prompt 中解析：

```json
{
  "eventId": "745278",
  "start": 1786327320,
  "end": 1786327560,
  "triggerMetrics": {
    "names": ["用户体验时间（服务器）"],
    "values": [3055.3701],
    "units": ["毫秒"],
    "severity": "紧急",
    "condition": "用户体验时间（服务器） > 3000.0"
  }
}
```

执行前必须校验：

1. `eventId` 是非空数字字符串。
2. `start/end` 是 Unix 秒级时间戳。
3. `end > start`。
4. 时间窗口不超过安全上限。
5. 该工作流不接受 `timeRange.key`。
6. 触发指标允许为空，但只要推送原文已提供，就必须完整保留。

校验失败时返回结构化错误，不允许回退到告警汇总。

### 6.3 新增 OpenClaw 复合工具

工具名：

```text
napm-alert-packet-analysis
```

工具输入 schema 建议：

```json
{
  "type": "object",
  "properties": {
    "prompt": { "type": "string" },
    "eventId": { "type": "string" },
    "start": { "type": "number" },
    "end": { "type": "number" },
    "triggerMetrics": { "type": "object" },
    "traceId": { "type": "string" }
  },
  "required": ["prompt", "eventId", "start", "end"],
  "additionalProperties": false
}
```

插件层保留 canonical prompt 作为权威上下文，不盲信模型在工具参数中重写的 `eventId/start/end`。插件应从 canonical prompt 重新解析并校验，如与工具参数不一致，以 canonical prompt 为准并写入审计日志。

### 6.4 插件注册点

`napm-openclaw-plugin.remote.js` 需要完成：

1. 在 `REQUIRED_NAPM_SKILL_RUNTIME_PATHS` 增加复合 Skill 运行文件。
2. 增加 `napmAlertPacketSkill()` loader。
3. 在 `SAFE_NAPM_TOOL_NAMES` 增加 `napm-alert-packet-analysis`。
4. 增加 `createAlertPacketAnalysisToolDefinition()`。
5. 在 `register(api)` 中注册新工具。
6. 将系统路由中的“告警查询后再调数据包工具”改为“直接调复合工具”。
7. 新增复合结果识别函数，不得将它当成普通 alert result。

### 6.5 `before_tool_call` 工作流门禁

对 `activeAlertPacketPrompt=true` 的轮次，只允许：

```text
napm-alert-packet-analysis
```

以下调用全部拦截：

```text
napm-alert-query
napm-summary
napm-skill-query
napm-fault-diagnosis
napm-packet-analysis（未通过复合工具的内部调用）
shell / exec / curl
```

注意：复合 Skill 在插件进程内直接调用现有 `handleSkillCall()`，不会再经过模型的 `before_tool_call`。因此门禁可以禁止模型直接调用普通告警和数据包工具，但不会阻断复合 Skill 内部编排。

建议拦截理由：

```text
ALERT_PACKET_WORKFLOW_REQUIRED:
该请求必须使用 napm-alert-packet-analysis。
禁止降级为告警汇总或跳过 eventId 明细定位。
```

## 7. 复合 Skill 设计

### 7.1 目录结构

```text
skills/openclaw-napm-alert-packet-analysis/
  SKILL.md
  package.json
  scripts/run_alert_packet_analysis.js
  services/AlertPacketWorkflowService.js
  services/AlertPacketResultContractService.js
```

`SKILL.md` 描述用途和输入输出契约；真正的顺序、重试、终止条件和错误分类必须由 JavaScript 实现，不能只写在描述文件里。

### 7.2 内部复用现有 Skill

复合 Skill 直接复用：

```text
openclaw-napm-alert-query/scripts/run_alert_query.js
  -> handleSkillCall()

openclaw-napm-packet-analysis/scripts/run_packet_analysis.js
  -> handleSkillCall()
```

不复制 NAPM API client，不手工拼接 curl，不重写数据包下载和分析逻辑。

### 7.3 告警详情调用契约

复合 Skill 内部只能构造：

```json
{
  "mode": "detail",
  "criteria": {
    "eventIds": ["745278"],
    "start": 1786327320,
    "end": 1786327560
  },
  "options": {
    "packetHandoff": true,
    "discoveryEnabled": true,
    "discoveryTopCount": 5,
    "packetBufferSeconds": 120,
    "alertTriggerMetrics": {
      "names": ["用户体验时间（服务器）"],
      "values": [3055.3701],
      "units": ["毫秒"],
      "condition": "用户体验时间（服务器） > 3000.0",
      "severity": "紧急"
    }
  }
}
```

禁止字段：

```text
criteria.timeRange
mode=analysis
mode=summary
mode=timeline
```

该约束保证固定推送窗口不会再被 `last1hour` 或其他相对时间覆盖。

### 7.4 明细可见性重试

只在以下条件同时满足时重试：

```text
查询调用本身成功
mode=detail
details=[]
eventId 非空
```

默认重试时序：

```text
attempt 1: 0 ms
attempt 2: 2000 ms
attempt 3: 4000 ms
attempt 4: 8000 ms
```

最长新增等待约 14 秒，不超过当前工具 HTTP 超时量级。延迟和尝试次数应可通过环境变量配置，但必须有严格上限。

不重试：

```text
参数校验失败
HTTP 400
认证失败
eventId 缺失
固定时间无效
```

对可重试的网络超时或 5xx，可使用独立、更小的上限，不得与“明细暂未可见”混为一类。

### 7.5 严禁空详情降级成告警汇总

重试后仍无明细时，返回：

```json
{
  "ok": false,
  "workflowState": "ALERT_DETAIL_NOT_VISIBLE",
  "error": {
    "code": "ALERT_DETAIL_NOT_VISIBLE",
    "message": "已收到告警推送，但指定事件明细在有界重试后仍未可见，未执行推测性数据包分析。"
  }
}
```

不允许：

```text
改用 alertsSummary
扩大查询窗口
将 eventId 改为类别查询
输出七大类告警全部为 0
根据推送文本猜测 IP
```

### 7.6 数据包交接和执行

告警详情成功后，复合 Skill 只消费现有告警 Skill 返回的：

```text
narrationInput.packetInstruction
packetHandoff.candidates
candidates[].suggestedPacketQuery
```

不允许模型手工猜测 IP、手工拼数据包 URL 或把告警 `eventId` 直接当成 packet skill 的 `criteria.id`。

对每个有效 candidate，调用：

```text
openclaw-napm-packet-analysis.handleSkillCall(suggestedPacketQuery)
```

窗口规则：

1. 以推送原文中的固定 `start/end` 为权威窗口。
2. `suggestedPacketQuery` 中的关联 IP、模式和分析上下文继续复用。
3. candidate 数量受现有 `discoveryTopCount` 和复合工具安全上限约束。
4. 单个 candidate 失败不得把其他已成功结果丢失；使用 `PARTIAL_PACKET_ANALYSIS` 表达部分成功。

### 7.7 复合工作流状态机

```text
RECEIVED
  -> DETAIL_QUERYING
  -> DETAIL_RETRYING
  -> DETAIL_READY
  -> PACKET_TARGETS_READY
  -> PACKET_ANALYZING
  -> COMPLETED
```

终止状态：

```text
INVALID_INPUT
ALERT_DETAIL_NOT_VISIBLE
NO_PACKET_CANDIDATE
PACKET_ANALYSIS_FAILED
PARTIAL_PACKET_ANALYSIS
COMPLETED
```

核心不变式：

1. 进入该工作流后，`alertsSummary` 调用数必须为 0。
2. 没有 `DETAIL_READY` 不能进入 `PACKET_ANALYZING`。
3. 没有 packet result 不能返回 `COMPLETED`。
4. 任何失败都保留已完成阶段和结构化错误，不伪造业务结论。

## 8. 输出和去重设计

### 8.1 复合结果契约

建议返回：

```json
{
  "schema": "openclaw_napm_alert_packet_analysis.v1",
  "ok": true,
  "workflowState": "COMPLETED",
  "alertContext": {},
  "alertResult": {},
  "packetCandidates": [],
  "packetResults": [],
  "narrationInput": {
    "renderPolicy": {
      "target": "final_user_reply",
      "forbidAlertSummaryFallback": true
    }
  },
  "error": null
}
```

最终回答只能使用该复合结果。不得使用中间 `alertResult.displayText` 作为最终回答，否则又会将用户带回告警汇总文案。

### 8.2 最终回答内容

成功时应包含：

1. `eventId`、告警对象、告警级别和触发值。
2. 实际分析的固定时间窗口。
3. 告警 Skill 发现的关联 IP 或 IP 会话。
4. 现有数据包 Skill 返回的分析结果。
5. 基于现有数据包证据对告警原因的解释。
6. 数据包为空、不完整或分析失败时的明确边界。

失败时不得输出：

```text
告警总数 0 条
七大告警类别全部为 0
告警查询完成
未经数据包证据支持的原因猜测
```

### 8.3 OpenClaw 最终交付认领

新增每轮交付状态：

```text
deliveryKey = conversationKey + turnId + resultSchema
```

规则：

1. 工具结果和中间 reasoning/preview 事件不可认领最终交付。
2. 只有最终 assistant 消息可以认领。
3. 首次认领后记录 `deliveredAt` 和内容指纹。
4. 同一 `deliveryKey` 的后续发送直接 `cancel=true`。
5. 内容指纹去重作为第二道保护，不代替 turn 认领。

### 8.4 两个输出钩子的责任

`before_message_write`：


```text

只使用现有数据包 Skill 的真实结果解释告警原因；
```
