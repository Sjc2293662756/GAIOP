# 告警间接数据包发现 — 问题排查复盘

> 日期：2026-06-30 | 轮次：10+ 轮测试，6 轮修复

---

## 问题时间线

### 第 1 轮：初始路由错误（6/29 15:59）

**现象：** 用户 `分析这个告警数据包 696902` → AI 直接调 packet-analysis → packetsPreview → 403。

**根因：** `agents/openai.yaml` 中 `数据包 → packet-analysis` 独占路由，AI 跳过 alert-query。

**修复：**
- `alert-query agents/openai.yaml`：新增"告警数据包"跨 skill sequencing 规则
- `packet-analysis agents/openai.yaml`：新增 Alert event ID routing guard
- `alert-query SKILL.md`：Boundary 新增 Cross-Skill Sequencing

**结果：** 路由部分生效，但仍有绕过问题。

---

### 第 2 轮：AI 绕过 null packetHandoff（6/29 16:13）

**现象：** 告警 696909（securityAlerts，linkType=0，非业务告警）→ packetHandoff=null → AI 绕过 null 直接调 packet-analysis。

**根因：** `agents/openai.yaml` 只规定了"先调 alert-query"，没有规定 null 时禁止回退。

**修复：**
- 两个 `agents/openai.yaml` 新增：`packetHandoff=null → STOP`，不准回退到 packet-analysis

**结果：** null 终止规则生效，但 AI 偶尔仍忽略。

---

### 第 3 轮：suggestedPacketQuery.mode 错误（6/29 16:40）

**现象：** 告警 696956（categoryType=14, group="NOP可观察性"）→ 间接发现执行了 → 但 `mode: 'build_url_only'` 只构造链接不下载。

**根因：** `AlertIndirectPacketDiscoveryService.js` 中硬编码 `mode: 'build_url_only'`。

**修复：**
- 改为 `mode: 'preview_download_analyze'`
- agents 新增：AI 必须原样使用 suggestedPacketQuery，不得修改 mode

**结果：** 修复后正常，但后续测试暴露新问题。

---

### 第 4 轮：categoryType=51 未覆盖 + OtherApp 不匹配（6/30 13:36）

**现象：** 告警 697812（SSH, categoryType=51）→ packetHandoff=null。

**根因：**
- `CATEGORY_TYPE_TO_GROUP_TYPE` 缺少 51
- `DISCOVERY_GROUP_CHAIN_MAP` 缺少 51
- `groupType1` 写死在代码里

**修复：**
- `AlertConstants.js`：新增 51→'OtherApp'（后改为 'DefinedApp'）、56→'OtherApp'
- `DISCOVERY_GROUP_CHAIN_MAP`：新增 51 配置
- `groupType1` 改为从 `CATEGORY_TYPE_TO_GROUP_TYPE` 动态获取

**结果：** categoryType=51 可识别。

---

### 第 5 轮：API 返回格式不匹配（6/30 14:26）

**现象：** 告警 697722（Esxi-local, DefinedApp）→ discovery 返回空。

**根因：** NAPM topValues API 返回的是 `[{group:{argument,key},groupPath}]` 树形格式，`parseTopValuesResult` 只支持两种格式。

**修复：**
- `parseTopValuesResult` 新增格式 3：树形 drill-down `[{group:{argument,key}}]`

**结果：** 能正确解析 IP 会话对。

---

### 第 6 轮：discovery 时间窗口过窄（6/30 14:20~14:52）

**现象：** 告警 697917（SSH）→ 3 层下钻返回 HTTP 400。

**根因：** discovery 使用告警自身 60s 窗口，NAPM API 要求更大的时间范围。

**排查过程：**
1. 告警窗口 1782803130~1782803430（2 分钟）→ 扩展到 300s → 仍 400
2. 用户手动验证：相同 URL 用 2 小时窗口 → 成功
3. 确认：API 不接受窄窗口的 3 层下钻

**修复：**
- discovery 改用用户提供的 criteria.start/end（宽窗口）
- packet download 仍用告警自身 ±120s（精确窗口）

**结果：** SSH 成功发现 5 条 IP 会话对。

---

### 第 7 轮：HTTP 400 fallback（6/30 15:09）

**现象：** 告警 697895（"可观测239"）→ 400→`ALERT_INDIRECT_DISCOVERY_FAILED`。

**根因：** "可观测239" 在 NAPM 中不存在，API 返回 400。但：
1. 400 fallback 的正则匹配失败（error.message 格式问题）
2. fallback 查询返回对象名列表，但走了 IP 解析器被过滤掉

**修复：**
- 400 检测改为"任何错误都尝试 fallback"
- fallback 直接提取树形格式中的对象名（不经过 IP 解析器）
- 生成 `ALERT_INDIRECT_DISCOVERY_OBJECT_NOT_FOUND` + hint 提示

**结果：** 能准确提示用户对象不存在，并列出 NAPM 中现有对象。

---

### 第 8 轮：Plugin 截断输出（6/30 14:15）

**现象：** 远端代码输出正确，但 AI 始终说"没看到 packetHandoff"。

**根因：** `napm-openclaw-plugin.remote.js` 的 `buildAlertQueryReply` 和 tool metadata 都没有传 `packetHandoff`/`packetInstruction`。

**修复：**
- `buildAlertQueryReply`：新增 `[packetHandoff]` + `[packetInstruction]` 文本段
- tool `metadata`：新增 `packetHandoff` + `packetInstruction`

**结果：** AI 能看到 packetInstruction，并遵循 USE_CANDIDATES / STOP 指令。

---

### 第 9 轮：Plugin 拦截告警数据包（6/30 17:50）

**现象：** 描述规则改了无数遍，AI 仍然先调 packet-analysis。

**根因：** `napm-openclaw-plugin.remote.js:5497` 有硬拦截：
```js
if (activePacketPrompt && toolName !== 'napm-packet-analysis') {
    return { block: true };
}
```
用户说"数据包"→ `activePacketPrompt=true` → AI 想调 alert-query → 被插件直接拦住。

**修复：**
- 系统提示新增 alert-packet sequencing 规则
- 新增 `activeAlertPacketPrompt` 检测（同时包含告警+数据包）
- 拦截条件增加例外：`!(activeAlertPacketPrompt && toolName === 'napm-alert-query')`

**结果：** 告警数据包场景 napm-alert-query 被放行。

## 关键教训

1. **AI 路由不可靠**：agents/openai.yaml 文字规则远不够强，必须配合 plugin 层拦截逻辑。
2. **Plugin 层是最后一道防线**：AI 看不到的输出等于不存在——`packetHandoff`/`packetInstruction` 必须通过 `buildAlertQueryReply` 文本化。
3. **NPM API 返回格式不统一**：同一个 topValues 端点返回 3 种不同格式，解析器必须全覆盖。
4. **时间窗口对 API 的影响**：NAPM 3 层下钻需要足够大的时间窗口，告警自身窄窗口不够用。
5. **categoryType 映射需要参照官方文档**：51→OtherApp 但 NAPM 实际用 DefinedApp，需以文档为准。
6. **测试告警与真实告警差异大**：测试告警（"告警推送应用测试1"）常引用不存在的对象名、metrics 为空、linkType=0——需要做好容错。
