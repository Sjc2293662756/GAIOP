# 综述报告整体综述追问问题修复说明

问题发现与修复：2026-07-01  
复盘整理与文档扩写：2026-07-02

## 1. 背景

`openclaw-napm-summary` 已经支持两种综述模式：

- 整体维度综述：只给 `scope.type`，不提供 `scope.target`
- 单对象综述：同时提供 `scope.type` 和 `scope.target`

其中，以下四类 scope 均已具备“整体综述”能力：

- `webApplication`
- `application`
- `network`
- `businessGroup`

但在实际对话中，观枢AI 遇到“业务整体综述”“应用整体综述”请求时，仍然追问目标对象名称，和系统真实能力不一致。

本次修复不是新增功能，而是**把文档契约修正到与现有实现一致**，避免上层 agent 被旧文档误导。

## 2. 事件结论

一句话结论：

- 代码已经支持“整体综述无需 target”
- 插件路由说明也已经支持“整体综述无需 target”
- 只有 `skills/openclaw-napm-summary/SKILL.md` 仍保留旧口径，写成“非 global scope 必须带 target”
- 观枢AI 在执行前优先参考了这份旧文档，因此错误地向用户追问具体对象

所以本次问题的根因是：**文档滞后于实现演进**。

## 3. 问题现象

用户真实表达为：

- “给我一个应用整体的综述报告”
- “给我一个业务整体的综述报告”

系统实际表现为：

- 将“应用整体综述”误判为必须指定某个应用对象
- 将“业务整体综述”误判为必须指定某个业务系统对象
- 在已经具备足够语义信息的情况下，仍继续追问对象名

这带来的直接问题有三类：

1. 交互变长：本可一轮生成的综述报告，被迫多一轮澄清。
2. 能力误导：用户会误以为系统不支持整体维度综述。
3. 维护混乱：排查时若只看运行效果，很难第一时间意识到是文档问题而不是代码问题。

## 4. 复现路径

### 4.1 复现条件

满足以下条件即可复现：

- 用户请求的是综述报告，不是查询
- 语义中明确包含“整体”
- 请求对象属于 `webApplication` 或 `application` 维度
- agent 主要依据 `skills/openclaw-napm-summary/SKILL.md` 解释输入契约

### 4.2 典型复现语句

- “给我一个业务整体的综述报告”
- “给我一个应用整体的综述报告”
- “来一份网络整体综述报告”
- “给我一个业务组整体综述”

### 4.3 错误行为

错误行为不是调用失败，而是**过早追问**：

- “请告诉我具体是哪个应用”
- “请告诉我具体是哪个业务系统”

这说明 agent 在“是否必须有 target”这个判定点上走偏了。

## 5. 预期行为与实际行为对照

| 场景 | 用户输入 | 预期行为 | 实际错误行为 |
|---|---|---|---|
| 业务整体综述 | 给我一个业务整体的综述报告 | 直接构造 `scope.type=webApplication` 且省略 `target` | 追问具体业务名称 |
| 应用整体综述 | 给我一个应用整体的综述报告 | 直接构造 `scope.type=application` 且省略 `target` | 追问具体应用名称 |
| 网络整体综述 | 给我一个网络整体的综述报告 | 直接构造 `scope.type=network` 且省略 `target` | 潜在同类风险 |
| 业务组整体综述 | 给我一个业务组整体的综述报告 | 直接构造 `scope.type=businessGroup` 且省略 `target` | 潜在同类风险 |
| 单对象业务综述 | 给我一个 239web 的业务综述报告 | 构造 `scope.type=webApplication` + `scope.target` | 正常 |

## 6. 根因链路

### 6.1 第一层根因：`SKILL.md` 输入契约过时

旧版 `skills/openclaw-napm-summary/SKILL.md` 将以下 scope 全部写成 target 必填：

- `webApplication`
- `application`
- `businessGroup`
- `network`

这个写法来自早期“分类综述必须聚焦单对象”的设计口径，但已经不再覆盖当前实现。

### 6.2 第二层根因：实现已经进化，但文档未回填

后续实现中，`SummaryService` 增加了“有 target / 无 target”双模式：

- 有 `scope.target`：走单对象综述
- 无 `scope.target`：走 overview 整体综述

也就是说，**代码早已支持整体综述**，只是 skill 文档没有同步。

### 6.3 第三层根因：多处文档口径分叉

这个问题之所以容易漏掉，是因为项目里同时存在三层“事实来源”：

1. 设计文档
2. 实现落地文档
3. skill 对外契约文档

其中：

- 2026-06-18 设计方案中，早期口径偏向“分类综述聚焦单对象”
- 2026-06-22 实现落地文档已经明确支持“无 target 的整体综述”
- 但 `SKILL.md` 仍保留旧描述

于是出现了“实现是新的，技能说明还是旧的”分叉状态。

## 7. 真实实现现状

以下是本次排查确认的真实实现情况。

### 7.1 插件层已经支持 overview 模式

插件路由系统上下文明确规定：

- 用户未指定目标对象时，应省略 `scope.target`
- 此时进入 overall / overview 的维度综述模式

这意味着从插件入口看，整体综述本来就是合法请求。

### 7.2 `SummaryService` 已按有无 target 自动分流

`SummaryService.plan()` 的真实行为是：

- `webApplication`：有 target 走 `_planWebApplicationTarget()`，无 target 走 `_planWebApplicationOverview()`
- `application`：有 target 走 `_planApplicationTarget()`，无 target 走 `_planApplicationOverview()`
- `network`：有 target 走 `_planNetworkTarget()`，无 target 走 `_planNetworkOverview()`
- `businessGroup`：有 target 走 `_planBusinessGroupTarget()`，无 target 走 `_planBusinessGroupOverview()`

这说明实现层并没有“强制 target”的限制。

### 7.3 overview 模式已具备独立查询计划

例如：

- 业务整体综述会查询 `slowAccess`、`httpErrors`、`pageTraffic`、`pageViews`
- 应用整体综述会查询 `topApps`、`appConnections`、`appFailures`、`appQuality`

因此这类模式不是“兜底行为”，而是已经设计完成的正式能力。

## 11. 修复前后行为对照

### 11.1 修复前

用户说：

```text
给我一个业务整体的综述报告
```

agent 可能会理解为：

```json
{
  "scope": {
    "type": "webApplication",
    "label": "业务"
  },
  "needTarget": true
}
```

于是继续追问：

- “请告诉我具体是哪个业务系统”

### 11.2 修复后

同样输入应直接解释为：

```json
{
  "scope": {
    "type": "webApplication",
    "label": "业务"
  }
}
```

并直接进入整体综述执行链路，不再追问对象。

应用整体综述同理：

```json
{
  "scope": {
    "type": "application",
    "label": "应用"
  }
}
```

## 13. 经验教训

这次问题有两个典型教训。

### 13.1 skill 文档本身就是运行时输入的一部分

对于 OpenClaw 这类依赖技能文档进行能力边界判断的系统来说，`SKILL.md` 不是“可有可无的说明书”，而是实际影响 agent 决策的输入。

因此：

- skill 文档过时，等价于行为配置过时
- 维护时不能只改代码不改 `SKILL.md`

### 13.2 设计文档、实现文档、skill 契约文档必须一起收口

一个能力经历“设计 → 落地 → 对外契约”三个阶段时，最容易出错的不是代码本身，而是三份文档的口径漂移。

后续如果出现类似“代码明明支持，agent 却不会用”的问题，优先检查：

1. `SKILL.md`
2. 插件系统上下文
3. 最近的实现说明文档

## 14. 后续建议

建议继续做三件事：

1. 对 `napm-summary` 相关提示词和路由说明做一次统一巡检，确保“整体综述 vs 单对象综述”口径完全一致。
2. 为“业务整体综述”“应用整体综述”补一组自动化或回归测试，避免将来再次回退到“强制追问 target”。
3. 后续凡是扩展 `scope` 能力时，同步更新：
   `SKILL.md`、`docs/` 实现说明、`memory/` 维护记录，避免再次出现单点更新。

## 15. 当前结论

当前维护结论应固定为：

- `webApplication` 支持整体综述和单对象综述
- `application` 支持整体综述和单对象综述
- `network` 支持整体综述和单对象综述
- `businessGroup` 支持整体综述和单对象综述
- 只有在用户明确聚焦某个对象时，才需要 `scope.target`
- 用户已经表达“整体综述”时，不应再额外追问对象名称
