# NAPM 元数据查询运行时依赖与边界失败泄露修复方案

## 1. 问题背景

测试环境运行 `1.1.0-rc.6` 时，企业微信出现两类元数据清单查询失败：

- `现在系统中有哪些业务？` 返回完整 `BOUNDARY_VALIDATION_ERROR` JSON，提示 `service=groups` 缺少 `groups`。
- `现在系统中有哪些应用？` 返回“当前问题必须经 NAPM skill 执行后才能回答”，没有返回对象目录。

本次排查以测试服务器 Gateway 日志和插件审计日志为准，没有通过代码行为推测后端结果。

## 2. 现场证据

### 2.1 业务清单

请求正确进入 `napm_candidate`。模型第一次调用缺少对象类型：

```json
{
  "service": "groups",
  "queryModeKey": "metadata"
}
```

边界校验按契约拒绝该参数。模型随后两次已正确修复为：

```json
{
  "service": "groups",
  "queryModeKey": "metadata",
  "groups": [{ "type": "WebApplication" }]
}
```

两次正确调用均在 Tool 执行入口加载时间解析模块时异常，没有进入 NAPM 元数据接口。

### 2.2 应用清单

模型第一次调用即正确构造为：

```json
{
  "service": "groups",
  "queryModeKey": "metadata",
  "groups": [{ "type": "DefinedApp" }]
}
```

参数通过插件审计，但同样在 Tool 执行入口加载时间解析模块时异常。

### 2.3 运行时异常

活动 extension 报错：

```text
Cannot find module '../../services/ResolvedQueryTimeRangeService'
Require stack:
- .../extensions/napm-openclaw-plugin/skills/openclaw-napm-query/src/shared/timeResolver.js
- .../extensions/napm-openclaw-plugin/index.js
```

因此该问题不是 NAPM 后端元数据错误，也不是 `WebApplication` / `DefinedApp` 的对象映射错误。

## 3. 根因

### 3.1 extension 携带了不完整的 Skill 私有依赖

插件 Tool 入口从 extension 自身目录加载：

```text
skills/openclaw-napm-query/src/shared/timeResolver.js
```

`timeResolver.js` 又相对加载：

```text
../../services/ResolvedQueryTimeRangeService
```

安装器只复制前者，没有复制后者，形成不完整的运行时依赖闭包。由于 `timeResolver` 在 `napm-skill-query.execute()` 中无条件加载，影响范围不只 `groups` 元数据查询，所有合法 `napm-skill-query` 调用都可能在到达 Skill 前失败。

### 3.2 构造失败记录与 Skill 结果混用

第一次缺少 `groups` 的失败被保存在当前轮 `queryFailureByTurn`。后续正确调用在写入成功 Skill 结果前异常，输出 Hook 又把这条构造失败当作 `rememberedRecord`。

失败对象没有用户展示文本，最终进入通用 `JSON.stringify(result, null, 2)` 兜底，导致内部边界 JSON 对外泄露。

### 3.3 发布验证没有覆盖真实安装布局

现有发布验证只检查发布目录中的完整 workspace Skill，以及对插件执行 `node --check`。它没有构造安装器实际生成的最小 extension 布局，也没有执行 extension 中的 `napm-skill-query` Tool，因此无法发现延迟 `require` 的缺失依赖。

## 4. 设计原则

1. Skill 代码只有一个运行时来源，不在 extension 中维护残缺副本。
2. 查询参数构造失败、Skill 执行结果、Skill 执行异常必须是三种独立状态。
3. 内部结构化错误不得通过通用 JSON 兜底直接发送给企业微信用户。
4. 对象语义继续由模型理解，不通过新增“业务/应用”关键词正则修补。
5. 发布验证必须复现正式安装后的目录结构和模块加载方式。

## 5. 修复方案

### 5.1 统一 Skill 运行时来源

插件已经通过 `resolveOpenClawSkillsRoot()` 选择完整的 Skill 根目录，并从该目录加载各 Skill 执行器。`timeResolver` 必须使用同一根目录：

```js
const timeResolverPath = path.join(
  OPENCLAW_SKILLS_ROOT,
  'openclaw-napm-query/src/shared/timeResolver'
);
const { applyTimeOverride } = require(timeResolverPath);
```

同时执行以下调整：

- 删除安装器向 extension 单独复制 `timeResolver.js` 的逻辑。
- extension 不再包含 `skills/openclaw-napm-query` 残缺副本。
- 将 `timeResolver.js` 和 `ResolvedQueryTimeRangeService.js` 加入完整 Skill 运行时路径校验。

不采用“再复制一个 Service 文件”的临时方案，避免以后新增依赖时再次漏包。

### 5.2 分离失败状态

`ConversationOperationState` 分别管理：

- `query_validation_failure`：上游构造错误，只服务于单轮修复预算。
- `skill_execution_result`：Skill 已执行并返回的结构化结果。
- `skill_execution_failure`：Tool 加载或执行异常，供安全失败提示和审计使用。

当同一轮 `resolvedQuery` 通过边界校验时，立即清除或标记之前的 `query_validation_failure` 为已修复。构造失败记录不得再作为 Skill 查询结果返回给输出 Hook。

### 5.3 安全错误输出

边界错误和执行异常不得进入通用 JSON 展示兜底。企业微信只返回稳定、脱敏的中文提示：

```text
NAPM 查询工具执行失败，本次没有取得有效数据。
请稍后重试；如持续失败，请联系维护人员检查查询工具运行状态。
```

详细异常、模块路径、`resolvedQuery` 摘要和 traceId 仅写入脱敏审计日志。

### 5.4 强化元数据 Tool 契约

继续由模型根据完整上下文判断对象类型：

| 用户语义 | NAPM 对象类型 | applications 类型 |
|---|---|---|
| 业务、业务系统 | `WebApplication` | Type=3 |
| 应用、已定义应用 | `DefinedApp` | Type=2 |
| 业务组 | `BusinessGroup` | 不适用 |

Tool 描述从 `napm-resolution-spec.v1.json` 展示各 service 的必填字段。`service=groups` 必须明确要求 `queryModeKey=metadata` 和非空 `groups`。边界校验保留一次修复机会，但不依赖模型永远一次构造正确。

### 5.5 发布门禁

新增以下验证：

1. 最小 extension 布局不包含 Query Skill 副本，仍能从 `OPENCLAW_SKILLS_ROOT` 加载完整依赖。
2. `WebApplication` 和 `DefinedApp` 两类 `groups` 元数据 Tool 调用能进入 Skill 执行器。
3. 第一次参数无效、第二次参数正确时，旧边界失败不得成为最终回答。
4. Skill 加载或执行异常时，不得输出边界 JSON、堆栈或本机路径。
5. staged 发布和正式安装后都执行模块加载检查，而不只执行 `node --check`。

## 6. 验收标准

本地测试必须覆盖：

- 最小 extension 布局运行时加载。
- `groups / metadata / WebApplication`。
- `groups / metadata / DefinedApp`。
- 构造失败后正确重试的状态替换。
- Tool 异常的用户安全输出。
- 完整 Jest、lint、运行时契约和发布 staged 验证。

测试服务器部署后，通过企业微信验证：

```text
现在系统中有哪些业务？
现在系统中有哪些应用？
```

分别应使用 `WebApplication / Type=3` 和 `DefinedApp / Type=2` 返回真实目录。企业微信中不得出现边界 JSON、模块路径、堆栈或内部执行过程。

## 7. 发布策略

本修复作为 `1.1.0-rc.7` 候选版本处理。必须从干净提交构建统一发布包，依次完成 staged 验证、dry-run、正式安装和部署后验收；不得逐文件覆盖活动 extension。

## 8. 实施结果

已在 `codex/fix-query-runtime-dependencies` 分支完成本地实现：

- 插件改为从 `OPENCLAW_SKILLS_ROOT` 加载 `timeResolver`，不再从 extension 私有目录加载残缺副本。
- 完整运行时检查新增 `timeResolver.js` 和 `ResolvedQueryTimeRangeService.js`。
- 安装器删除单文件嵌入逻辑，正式安装与 staged 验证共用 `stage-openclaw-extension.sh`。
- 新增 `verify-openclaw-extension-runtime.js`，通过无南向访问的 `security_refusal` 调用验证插件、时间解析器和 Query Skill 能够完整加载。
- 查询构造失败与 Skill 执行失败使用独立状态；合法重试会清除上一条构造失败。
- 两个输出 Hook 对类型化失败统一生成脱敏中文提示，不再序列化边界 JSON；显式开启的非企业微信诊断预览保持原行为。
- Tool 描述从 resolution spec 展示 service 必填字段，并明确 `groups` 元数据示例及 `WebApplication` / `DefinedApp` 语义。

修复前专项测试稳定复现 4 条失败：两种最小 extension 元数据调用缺模块、旧构造失败被输出、状态存储缺少清除能力。修复后验证结果：

- 聚焦回归：3 个套件、26 个测试全部通过。
- 完整 Jest：90 个套件、668 个测试全部通过。
- `npm run lint`：通过。
- `npm run verify:runtime-contract`：8 个生产 Tool 入口全部通过。
- 远程生命周期脚本：12 项无外发 Hook 冒烟全部通过。
- Node 语法、3 份 shell 脚本语法、新增脚本/状态模块/测试 ESLint 和 `git diff --check`：通过。

当前仅完成本地代码、测试和文档修改，尚未提交、构建发布包、创建标签或部署测试服务器。
