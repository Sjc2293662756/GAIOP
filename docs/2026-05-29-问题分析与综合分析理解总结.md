## 1. 核心结论

本文档所说的“问题分析 / 综合分析”，不是简单查询一个指标、一个排行或一个趋势。

它更接近运维工程师处理真实故障时的诊断链路：

```text
用户描述现象
  -> 识别问题类型
  -> 锁定分析对象
  -> 选择主指标和辅助指标
  -> 执行 discovery 或 focused overview
  -> 组织证据链
  -> 判断异常方向
  -> 给出建议动作
  -> 必要时做验证和前后对比
```

因此，我之前给出的回答只能算“基于文档和项目的综合理解分析”，还不是针对某个具体故障的完整复杂分析。

真正的复杂分析必须围绕一个具体问题或对象展开，并拿到可验证的指标证据。

## 2. 从案例文档看到的分析模式

`项目案例补充V1.2.docx` 中的案例有一套稳定结构：

```text
背景 / 运维挑战
  -> 部署架构
  -> 应用场景
  -> 异常现象
  -> 数据分析
  -> 分析结论
  -> 解决建议
  -> 问题验证
  -> 用户收益
```

其中真正有价值的部分不是“发现一个指标异常”，而是把现象、对象、数据包、指标、趋势和处置结果串成闭环。

典型例子包括：

| 场景 | 现象 | 分析动作 | 结论方向 |
|---|---|---|---|
| 定时任务失败 | 连接过程中被 RST | 抓包、看会话、对比 TTL、统计 RST 次数 | 某未知系统或节点发出异常 RST |
| 主机中毒 | 多台主机大量发送失败 | 按发送失败排行定位主机，下载数据包验证 | 异常主机感染病毒或产生垃圾流量 |
| ARP 攻击 | 网络卡顿、流量高峰 | 下载高峰数据包，发现大量 ARP 广播 | 单台终端异常广播导致网络异常 |
| 支付平台超时 | 支付响应慢、交易失败 | 分析支付业务链路、外联地址、丢包和响应时间 | 外网链路或中间设备存在问题 |
| 业务慢访问 | 页面访问超过 5 秒 | 看慢页面、URL、瀑布图、服务器响应时间 | 服务端响应时间长导致慢访问 |

这些案例说明，复杂分析最终要回答的不是“查到了什么”，而是：

```text
哪里异常？
异常证据是什么？
更像哪类原因？
下一步应该处理哪里？
处理后如何验证？
```

## 3. 本项目中的对应理解

当前项目 `NAPM Semantic Gateway` 的复杂分析不是另起一套系统，而是在现有主链上演进：

```text
OpenClaw 自然语言理解
  -> 构造 structured resolvedQuery
  -> 必要时构造 analysisPipeline.discoveryQuery
  -> napm-openclaw-plugin 做边界校验和工具守卫
  -> openclaw-napm-query skill 执行结构化查询
  -> overview / metadata / metric 执行内核
  -> 结果归并
  -> OpenClaw narration contract
  -> 中文分析结论
```

其中职责边界应保持清楚：

| 层级 | 职责 |
|---|---|
| OpenClaw | 理解自然语言、识别问题类型、构造 `resolvedQuery` |
| plugin | 注入规则、校验边界、阻断错误工具和错误查询结构 |
| skill | 执行结构化查询，不在生产链路中临时猜测 prompt |
| overview module | 编排多个候选查询，形成综合分析结果 |
| narration contract | 输出可被 OpenClaw 叙述的结构化结果 |

## 4. 复杂分析与普通查询的区别

普通查询只回答数值、排行或趋势。

复杂分析要回答原因方向、证据和建议。

| 用户问题 | 类型 | 推荐链路 |
|---|---|---|
| 最近一小时丢包最高的前 10 个 IP | 普通 TopN | `service=topValues` |
| 某 IP 的平均响应时间是多少 | 普通指标查询 | `service=averageValues` |
| 某业务最近一小时流量趋势 | 普通趋势查询 | `service=timeValues` |
| 可观测239web 为什么慢 | 聚焦综合分析 | `service=overview` + focused analysis |
| 丢包最严重的 IP 是谁，为什么 | 先发现再分析 | `overview + analysisPipeline.discoveryQuery` |
| 哪个业务 HTTP 500 最严重，并分析原因 | 先发现再分析 | `overview + discoveryQuery` |
| 系统整体有没有风险 | 系统综合分析 | `overviewScene=system` |

判断规则：

- 用户只问“多少、前几、趋势”，通常是普通查询。
- 用户问“为什么、原因、是否异常、整体情况、综合分析、风险、建议”，通常是复杂分析。
- 用户说“先找出谁，再分析它”，必须走 discovery + focused overview。
- 用户没有给对象但要求分析具体对象时，不能编造对象，必须先 discovery。

## 5. 复杂分析的三种基本形态

### 5.1 聚焦综合分析

适用于用户已经给出明确对象。

示例：

```text
可观测239web 为什么慢？
Default-Internet 工作组整体情况怎么样？
10.61.132.78 最近连接是否异常？
```

推荐结构：

```json
{
  "service": "overview",
  "queryModeKey": "overview",
  "analysisType": "comprehensive_analysis",
  "analysisMode": "focused_analysis",
  "analysisScene": "business",
  "overviewScene": "business",
  "groups": [
    {
      "type": "WebApplication",
      "argument": "可观测239web"
    }
  ],
  "start": "<from time resolver>",
  "end": "<from time resolver>"
}
```

重点是围绕该对象补充多个证据指标，而不是只查一个值。

### 5.2 先发现再分析

适用于用户没有给明确对象，但要求分析“最严重、最多、最慢、最高”的对象。

示例：

```text
找到连接失败最多的地址，然后分析它。
丢包最严重的 IP 是谁，为什么？
哪个业务 HTTP 500 最严重，并分析原因？
```

推荐结构：

```json
{
  "service": "overview",
  "queryModeKey": "overview",
  "analysisType": "comprehensive_analysis",
  "analysisMode": "discover_then_analyze",
  "analysisScene": "network",
  "overviewScene": "network",
  "analysisPipeline": {
    "targetObjectType": "IPAddress",
    "selection": {
      "rank": 1
    },
    "discoveryQuery": {
      "service": "topValues",
      "queryModeKey": "topn",
      "groups": [
        {
          "type": "IPAddress"
        }
      ],
      "metrics": ["RFCI"],
      "topMetric": "RFCI",
      "topCount": 1
    }
  },
  "start": "<from time resolver>",
  "end": "<from time resolver>"
}
```

注意：

- `discoveryQuery` 不应该携带自己的 `start/end`。
- 顶层 `start/end` 是唯一时间真相源。
- discovery 查出的对象必须绑定到后续 focused overview。
- discovery 没有结果时，不能编造对象。

### 5.3 系统整体综合分析

适用于用户问全局风险、整体情况、哪里不正常。

示例：

```text
现在系统整体有没有风险？
最近系统哪里不正常？
整体情况怎么样，哪些方向需要关注？
```

推荐结构：

```json
{
  "service": "overview",
  "queryModeKey": "overview",
  "analysisType": "comprehensive_analysis",
  "analysisMode": "system_analysis",
  "analysisScene": "system",
  "overviewScene": "system",
  "start": "<from time resolver>",
  "end": "<from time resolver>"
}
```

系统分析不是找一个对象，而是从业务、应用、网络、连接、安全等方向列出重点风险。

## 6. 分析意图到指标组合

复杂分析必须把自然语言意图映射到指标组合。

| 分析意图 | 常见说法 | 主指标 | 辅助指标 | 推荐场景 |
|---|---|---|---|---|
| 慢分析 | 慢、卡、响应慢、耗时高 | `PGTME`、`PGNSLPGE`、`RTTI` | `PGTMC`、`PGTMS`、`PGSLRT`、`TRTI`、`CONI` | business / network |
| HTTP 错误 | 报错、500、4xx、页面错误 | `PGHTTP500` | `PGHTTP500PCT`、`PGHTTP400`、`PGNPGE`、`PGTME` | business |
| 连接失败 | 连接失败、TCP 失败、建连失败 | `RFCI` | `RFCO`、`RFRI`、`RFRO`、`CONI`、`CCNI`、`CSTI` | network / business_group |
| 丢包分析 | 丢包、网络质量差、掉包 | `PLI` | `PLO`、`RTXI`、`RTXO`、`RTTI`、`TPIO` | network |
| 重传分析 | 重传高、传输质量差 | `RTXI` | `RTXO`、`RDTI`、`RDTO`、`PLI`、`RTTI` | network |
| 流量分析 | 流量大、吞吐高、带宽高 | `TPIO` | `BYTIO`、`BYTI`、`BYTO`、`CONI`、`CONO` | network / application |
| 业务异常 | 业务异常、不正常、风险高 | `PGHTTP500`、`PGNSLPGE`、`PGTME` | `PGHTTP500PCT`、`PGHTTP400`、`PGNPGE`、`PGSLRT` | business |
| 安全异常 | 未知应用、外联异常、病毒、攻击 | `CONO`、`RFCO`、`TPIO` | 未知 TCP/UDP、失败连接、异常流量 | security |

## 7. 标准输出形态

复杂分析的最终中文回答应尽量稳定，不要像工具日志，也不要像流水账。

推荐结构：

```text
结论：
本次最需要关注的是 <对象>，主要异常方向是 <异常方向>。

发现依据：
按 <discovery 指标> 排序，<对象> 排名第 1，指标值为 <value>。

关键证据：
- <指标1>：<值>，说明 <含义>
- <指标2>：<值>，说明 <含义>
- <指标3>：<值>，说明 <含义>

分析判断：
综合看更像 <原因方向>，暂不能证明 <不能确认的根因>。

建议动作：
建议优先检查 <对象关联方向>。

数据时间：
<displayText>，<startText> 至 <endText>。
```

如果是失败态，也要明确失败阶段：

```text
本次未能完成“先发现对象”的步骤，因此没有进入聚焦分析。

失败阶段：discoveryQuery
查询对象：IPAddress
排序指标：RFCI
失败原因：<error message>
```

## 8. 当前项目已经具备的能力

当前项目已经具备复杂分析的主要底座：

| 能力 | 当前状态 |
|---|---|
| 单步结构化查询 | 已支持 `topValues`、`averageValues`、`timeValues`、`groups`、`metrics` |
| overview 编排 | 已有 `overview-module.js` 和候选模块注册表 |
| discovery -> focused overview | 已支持 `analysisPipeline.discoveryQuery` |
| 时间契约 | 已收口到顶层 `start/end` |
| 对象本体 | 已有 `object-ontology.v1.json` |
| 指标口径 | 已有 `metrics-config.yml` 和 metric ownership |
| plugin 边界守卫 | 已能阻断复杂分析被构造成普通 TopN |
| narration contract | 已支持 `comprehensive_analysis` 和 `comprehensive_analysis_with_discovery` |
| 回归测试 | 已覆盖 discovery pipeline、overview、输出契约、guard 等 |

这说明项目不是从零开始做复杂分析，而是在把已有查询能力组织成更像专家诊断的分析链路。

## 9. 当前仍然存在的缺口

当前项目还没有完全达到案例文档中的人工专家分析深度。

主要缺口：

| 缺口 | 影响 |
|---|---|
| 阈值和基线不足 | 很难判断“是否严重”和“严重等级” |
| 根因归纳规则不足 | 容易停留在“查到指标”，而不是“判断原因方向” |
| 数据包证据未形成结构化输入 | 还不能自动复现 TTL、MAC、RST、ARP 等深层证据 |
| 前后对比能力不足 | 难以自动回答“处理后是否恢复” |
| 多对象对比分析未完全落地 | 不能稳定比较多个业务或多个 IP |
| 输出洞察结构还可增强 | `topFindings` 更偏摘要，不是完整 `evidence / conclusion / nextActions` |
| 真实验收样例不足 | 需要更多稳定对象、mock 响应和预期输出 |

因此，当前更准确的能力定位是：

```text
基于 NAPM 指标的自动化综合诊断雏形。
```

而不是完整替代人工抓包和根因复盘。

## 10. 我理解的下一步建设方向

### 10.1 第一阶段：把已有链路稳定成产品能力

重点：

- 固化 `focused_analysis`
- 固化 `discover_then_analyze`
- 补全 IP、WebApplication、DefinedApp、BusinessGroup 的 P0 用例
- 确保复杂分析问题不会被错误构造成普通 TopN
- discovery 失败时不编造对象

### 10.2 第二阶段：增强证据结构

建议输出结构中增加：

```json
{
  "conclusion": {},
  "target": {},
  "structuredFindings": [],
  "supportingEvidence": [],
  "nextActions": [],
  "confidence": "low|medium|high"
}
```

这样 OpenClaw 最终生成中文时，不会只拿到一段摘要，而是拿到可组织成诊断报告的结构化材料。

### 10.3 第三阶段：引入 InsightSynthesizer

目标是把查询结果从“摘要”升级为“判断”。

示例规则：

```text
慢页面数量高 + 页面平均耗时高 + HTTP 500 不高
  -> 更像服务端响应慢或页面性能问题

连接失败高 + 连接请求高 + 建连耗时高
  -> 更像连接层或服务端接入能力问题

丢包高 + 重传高 + 时延高
  -> 更像网络链路质量问题

未知 TCP/UDP 外联高 + 发送失败高
  -> 更像异常主机或安全风险
```

### 10.4 第四阶段：补数据包和前后验证

要贴近案例文档的专家分析，还需要支持：

- RST 特征识别
- TTL 差异识别
- MAC 地址异常识别
- ARP 广播异常识别
- 策略调整前后对比
- 异常消失验证

这部分可以作为后续“深度取证分析”能力，不建议和当前 P0 复杂分析混在一起一次做完。

## 11. 一句话定义

我对本项目“问题分析 / 综合分析”的最终理解是：

```text
把用户描述的运维现象，稳定转换成可执行的 NAPM 多步骤查询；
先锁定对象，再组织多指标证据；
最后输出有结论、有依据、有时间范围、有建议动作的诊断结果。
```

它的近期目标不是直接给出绝对根因，而是先做到：

```text
锁定异常对象
说明异常方向
列出证据指标
指出下一步排查路径
不编造无法证明的原因
```

等阈值、基线、数据包证据和前后验证能力补齐后，才能逐步接近案例文档中的完整专家级根因分析闭环。
