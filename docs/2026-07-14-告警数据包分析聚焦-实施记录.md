# 告警数据包分析聚焦修复 —— 实施记录

**日期**: 2026-07-14
**问题**: 从 syslog-watcher 推送的告警"深入分析"进入后，数据包分析结果为普通/泛化的协议分布统计，未聚焦于告警触发指标的根因分析。
**根因**: `packet-analysis` 的 `normalizeAnalysisOptions` 丢弃了 `alert-query` 通过 `suggestedPacketQuery.analysis` 传入的告警上下文字段（metrics、instruction 等）。
**修复**: 在 `run_packet_analysis.js` 中新增告警上下文保留与透传链路，共 3 处修改。

---

## 1. 背景

### 1.1 涉及的 Skill 及角色

| Skill | 角色 |
|---|---|
| `openclaw-napm-syslog-watcher` | 监听 NAPM Syslog → 补全告警详情 → 推送企业微信卡片（含"深入分析"指令） |
| `openclaw-napm-alert-query` | 告警查询 + 间接数据包发现（对业务/应用告警自动下钻找嫌疑 IP）→ 输出 `packetHandoff` + `suggestedPacketQuery` |
| `openclaw-napm-packet-analysis` | 数据包预览/下载/tshark 分析 → 输出分析报告 |

### 1.2 完整告警→数据包分析链路

```
NAPM Syslog 告警
  → syslog-watcher 推送企业微信卡片（含 "深入分析" 指令）
  → 用户复制指令发给 OpenClaw
  → alert-query 查询告警详情 + 间接 IP 发现
  → 输出 suggestedPacketQuery { mode, criteria: { ips, start, end }, analysis: { metrics, instruction, ... } }
  → packet-analysis 使用 suggestedPacketQuery 预览/下载/tshark 分析
  → AI 生成中文分析报告
```

### 1.3 问题表现

`alert-query` 在 `suggestedPacketQuery.analysis` 中注入了丰富的告警上下文：

```json
{
  "hasTriggerMetrics": true,
  "metrics": ["UXTIME_SRV"],
  "metricLabels": ["用户体验时间（服务器）"],
  "values": [7363.4702],
  "units": ["毫秒"],
  "condition": "如果 用户体验时间（服务器） > 3000.0 则为 紧急...",
  "severity": "紧急",
  "summary": "用户体验时间（服务器）(UXTIME_SRV)=7363.4702毫秒",
  "instruction": "数据包分析报告必须围绕 用户体验时间（服务器） 展开。解释为什么达到 7363.4702毫秒，结合数据包中的 TCP 重传、延迟、连接失败等证据，找出导致指标异常的具体 IP 会话和时间点。"
}
```

但 `packet-analysis` 的 `normalizeAnalysisOptions` 只提取了 5 个开关型字段：

```javascript
// 修复前
function normalizeAnalysisOptions(options = {}) {
  return {
    level: options.level || 'summary',
    includeDns: options.includeDns !== false,
    includeHttp: options.includeHttp !== false,
    includeTls: options.includeTls !== false,
    includePorts: options.includePorts !== false,
    timeoutMs: Number(options.timeoutMs || ...),
  };
  // ↑ hasTriggerMetrics、metrics、metricLabels、values、
  //   condition、severity、summary、instruction 全部被丢弃！
}
```

后果：tshark 分析结果是纯协议分布（TCP 80%、HTTP 20%...）+ 端点 + 会话 + DNS + HTTP + TLS，AI 层面没有任何告警上下文可以参照，只能输出"普通的数据包分析"。

## 2. 修复方案

### 2.1 设计原则

1. **不改变 tshark 行为**：告警上下文只透传、不干预 tshark 命令行
2. **向后兼容**：当 query.analysis 不带告警上下文时，行为与修改前完全一致
3. **失败路径也保留**：`analysisFailure()` 通过 spread 保留 alertContext

### 2.2 数据流（修复后）

```
suggestedPacketQuery.analysis (来自 alert-query)
  │
  ├─ normalizeAnalysisOptions()  ← 改动①
  │   └─ buildAlertAnalysisContext()  保留全部告警上下文到 options.alertContext
  │
  ├─ analyzePacketFile(filePath, analysisOptions)  ← 改动②
  │   └─ result.alertContext = analysisOptions.alertContext
  │
  └─ buildNarrationInput(result)  ← 改动③
      ├─ summarizeAnalysis()  透传 alertContext 到 narrationInput.analysis
      └─ buildAlertRenderHint()  生成 renderPolicy.alertRenderHint
           ↓
      AI 收到明确的告警聚焦叙述指令
```

## 3. 代码修改详情

### 3.1 改动①：`normalizeAnalysisOptions` — 保留告警上下文

**位置**: `skills/openclaw-napm-packet-analysis/scripts/run_packet_analysis.js`

**修改前**:

```javascript
function normalizeAnalysisOptions(options = {}) {
  return {
    level: options.level || 'summary',
    includeDns: options.includeDns !== false,
    includeHttp: options.includeHttp !== false,
    includeTls: options.includeTls !== false,
    includePorts: options.includePorts !== false,
    timeoutMs: Number(options.timeoutMs || process.env.PACKET_ANALYSIS_TIMEOUT_MS || 60000),
  };
}
```

**修改后**: 新增 `buildAlertAnalysisContext()` 从 options 提取告警上下文，`normalizeAnalysisOptions` 将其存入 `alertContext` 字段。

关键逻辑：
- `hasTriggerMetrics === false` 时返回 `{ hasTriggerMetrics: false, note: "..." }`，兼容普通数据包查询
- `hasTriggerMetrics === true` 时完整保留 metrics / metricLabels / values / units / condition / severity / summary / instruction

### 3.2 改动②：`analyzePacketFile` — 嵌入告警上下文

**位置**: 同上文件，`analyzePacketFile` 函数内的 result 初始化。

**修改**: 在 result 对象中新增 `alertContext` 字段：

```javascript
const alertContext = analysisOptions.alertContext || null;
const result = {
    ok: true,
    filePath: resolvedPath,
    fileName: path.basename(resolvedPath),
    // ... 原有字段 ...
    alertContext,  // ★ 新增
    error: null,
};
```

`analysisFailure()` 通过 `{ ...partial, ok: false, error: ... }` 自动保留 alertContext。

### 3.3 改动③：`summarizeAnalysis` + `buildNarrationInput` — 暴露给 AI 层

**3.3.1 `summarizeAnalysis`**: 新增透传 `alertContext`

```javascript
function summarizeAnalysis(analysis) {
  if (!analysis) return null;
  return {
    // ... 原有字段 ...
    alertContext: analysis.alertContext || null,  // ★ 新增
    error: analysis.error,
  };
}
```

**3.3.2 `buildNarrationInput`**: 新增 `renderPolicy.alertRenderHint`

```javascript
const alertContext = result.analysis && result.analysis.alertContext;
const alertRenderHint = alertContext && alertContext.hasTriggerMetrics
    ? buildAlertRenderHint(alertContext)
    : null;

return {
    // ... 原有字段 ...
    renderPolicy: {
        // ... 原有字段 ...
        alertRenderHint,  // ★ 新增
    },
};
```

**3.3.3 新增 `buildAlertRenderHint()`**: 生成 AI 层聚焦叙述指令，包含触发指标、条件、级别的格式化文本 + 4 条明确的叙述要求。

### 4.2 端到端数据流（手动追踪）

| 步骤 | 调用 | alertContext 状态 |
|---|---|---|
| 解析 query | `resolveQuery()` → `normalizeAnalysisOptions(query.analysis)` | ✅ 保留到 `task.analysis.alertContext` |
| 执行分析 | `analyzePacketFile(filePath, task.analysis)` | ✅ 存入 `result.alertContext` |
| 分析失败 | `analysisFailure(code, msg, result)` | ✅ `{ ...result }` spread 保留 |
| 汇总输出 | `summarizeAnalysis(result.analysis)` | ✅ 透传到 narrationInput |
| AI 叙述指令 | `buildAlertRenderHint(alertContext)` | ✅ 生成 renderPolicy.alertRenderHint |

### 4.3 向后兼容验证

| 场景 | 行为 |
|---|---|
| query.analysis 未传 | `normalizeAnalysisOptions({})` → `alertContext = { hasTriggerMetrics: false, note: "..." }` → `alertRenderHint = null` |
| query.analysis 只有开关字段 | 同上，原有 behavior 不变 |
| query.analysis 带完整告警上下文 | alertContext 完整保留，alertRenderHint 生成 |

## 6. 预期效果

修复前，对告警 Event ID 716973（监控对象 HTTP，触发指标"用户体验时间（服务器）=7363ms"）的"深入分析"结果：

```
> 数据包分析完成。
> 协议分布：TCP 85%、HTTP 10%、TLS 5%
> 主要端点：10.1.1.5 ↔ 10.2.2.100
> DNS 查询：example.com (5次)
> HTTP 请求：GET /api/data 200
> ...
```

修复后，AI 收到 `alertRenderHint` 后的预期输出：

```
> ⚠️ 本次分析由告警事件触发：用户体验时间（服务器）= 7363.47ms（紧急）
>
> 在 10.1.1.5 ↔ 10.2.2.100 的会话中，发现以下导致该指标异常的证据：
>
> 1. TCP 重传率 12.3%（告警时段内 45 次重传），正常基线 < 2%
>    → 每次重传增加约 200ms 服务器等待时间
> 2. 服务器响应延迟：HTTP 请求平均 RTT 850ms，P99 达 3200ms
>    → 单次页面加载累积 4-5 个 RTT，总耗时超过 3000ms 阈值
> 3. 连接失败：告警触发前 30s 内出现 3 次 SYN 重传超时
>
> 结论：10.1.1.5 → 10.2.2.100:443 链路的网络质量劣化（丢包→重传→延迟放大）
> 是导致"用户体验时间（服务器）"飙升至 7363ms 的直接原因。
```
