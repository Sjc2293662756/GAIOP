# 查询耗时根因分析：LLM 推理是唯一瓶颈（硬数据验证）

日期：2026-06-23

## 背景

经过前两轮修复（时间戳年份校验 + Memory embeddings 禁用），查询耗时从 19s 降至 17.5s，但仍然偏慢。本次分析通过远端审计日志的精确时间戳，定位了真正的瓶颈。

## 分析方法

### 数据源

| 日志 | 路径 | 时间精度 | 内容 |
|------|------|---------|------|
| 频道日志 | `/tmp/openclaw/openclaw-YYYY-MM-DD.log` | 毫秒 | 用户消息收发、WebSocket 事件 |
| 审计日志 | `/home/netinside/.openclaw/logs/audit.log` | 毫秒 | 插件工具调用、skill 执行、resolvedQuery 修复 |

两个日志的时间戳对齐方式：审计日志使用 UTC（`Z` 后缀），频道日志使用 `+08:00`，换算关系为 `UTC+8 = 本地时间`。

### 关键审计事件

| 事件名 | 含义 |
|--------|------|
| `napm_plugin_resolved_query_auto_repaired` | LLM 产出的 resolvedQuery 不完整，插件自动修复 |
| `napm_plugin_skill_executor_invoked` | skill 开始执行 |
| `napm_plugin_skill_executor_completed` | skill 执行完成（含 NAPM API 调用） |

## 关键发现

### 1. LLM 是唯一瓶颈（96%）

DeepSeek Chat 花了 14 秒构造 `resolvedQuery`，而插件的 `NapmResolvedQueryResolverService` 只需 9ms 就能完成同样的工作。LLM 比规则引擎慢了 **1500 倍**。

### 2. LLM 产出质量差

花了 14 秒推理，产出的 `resolvedQuery` 仍然：
- 缺少 3 个必填字段（`queryModeKey`, `metrics`, `topMetric`）
- 时间戳是 2025 年（差一整年）
- 时间范围用 24h 而非更合理的 1h

插件在 9ms 内修复了全部 5 个错误。

### 3. NAPM API 极快（4%）

从发起 HTTP 请求到拿到丢包排行数据，整个 NAPM API 调用仅 682ms。不是瓶颈。

### 4. prompt 大小不是主因

LLM 读了 78 行 guardrail 规则，仍然漏了必填字段、用错了年份。说明问题不在规则多少，而是 LLM 本身就不适合做精确的 query 构造。

## 对比：三次查询的 LLM 表现

| | 17:08 (修复前) | 17:50 (修复前) | 18:05 (修复后) |
|------|------------|------------|------------|
| LLM 推理时间 | ~10s | ~12s | **16.8s** |
| resolvedQuery 完整性 | 完整 | queryModeKey 错误 | **缺3个必填字段** |
| 时间戳年份 | 2026 ✅ | **2025 ❌** | **2025 ❌ (插件修复)** |
| 插件修复次数 | 0 | 1 | 1 |
| NAPM API 耗时 | ~500ms | ~500ms | **682ms** |
| 答案正确性 | ✅ | ❌ (空数据) | ✅ (插件修复后) |

LLM 推理时间不仅没有下降，反而从 10s 上升到了 16.8s（可能因为 OpenClaw 刚重启，缓存冷启动）。但插件修复机制确保了最终答案正确。

## 优化方向结论

| 方向 | 预期收益 | 依据 |
|------|---------|------|
| **简单查询绕过 LLM 构造** | **-14s (80%)** | 插件 9ms 就能构造 resolvedQuery |
| 换更快模型 | -5~8s (30-50%) | DeepSeek Chat 单轮 5-7s |
| 精简 prompt | -0~2s (0-10%) | prompt 只占 2000 token，不是瓶颈 |
| 减少 tool call 轮次 | -3~5s (20-30%) | 当前 2-3 轮 |

**结论：最优策略是用 `NapmResolvedQueryResolverService`（9ms）替代 LLM（14s）来构造 resolvedQuery，让 LLM 只做中文叙述生成。**
