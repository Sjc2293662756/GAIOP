# NAPM 趋势查询空结果与上下文追问门禁修复方案

日期：2026-08-18  
范围：`napm-openclaw-plugin`、`openclaw-napm-query` 查询契约、会话查询上下文、最终回复策略

## 1. 问题现象

测试会话先询问：

```text
最近一天的总流量的趋势怎么样？
```

系统执行 `timeValues` 后返回“未查到数据”。随后用户追问：

```text
那最近7天的呢？
```

OpenClaw 模型已经构造最近 7 天的 `timeValues` 查询，但插件把当前轮识别为 `model_owned`，在 `before_tool_call` 阶段阻止了 `napm-skill-query`，因此第二次查询没有执行。

## 2. 远端证据

### 2.1 首轮查询实际执行但缺少对象范围

会话轨迹中的首轮 `resolvedQuery` 为：

```json
{
  "service": "timeValues",
  "queryModeKey": "timeseries",
  "metrics": ["TPIO"],
  "topMetric": "TPIO",
  "timeRange": {
    "key": "last24hours",
    "displayText": "最近一天"
  },
  "granularity": 3600
}
```

实际南向参数没有 `groupType1` 和 `numGroups`。接口返回 HTTP 200，但 `rowCount=0`。

历史审计中存在同一时间窗口、粒度和指标集合的差分记录：

| 查询形态 | 结果 |
|---|---|
| 不带 `groups` | `rowCount=0` |
| `groups=[{type:"TotalTraffic"}]` | `rowCount=1` |

因此本次空结果不是“该时段没有采集数据”，而是全局趋势查询缺少 `TotalTraffic` 对象范围。

### 2.2 追问由模型正确理解，但被插件阻止

模型为“那最近7天的呢？”构造了：

```json
{
  "service": "timeValues",
  "queryModeKey": "timeseries",
  "metrics": ["TPIO"],
  "topMetric": "TPIO",
  "timeRange": {
    "key": "last7days",
    "displayText": "最近7天"
  },
  "granularity": 86400
}
```

插件日志随后记录：

```text
blocked tool for non-action turn: route=model_owned tool=napm-skill-query
```

说明 OpenClaw 对话上下文和模型语义理解均正常，失败发生在插件工具授权层。

## 3. 根因

### 3.1 `timeValues` 契约把 `groups` 错误定义为可选

`napm-resolution-spec.v1.json` 当前只要求：

```text
service, queryModeKey, metrics, start, end, granularity
```

`groups` 位于 `optional`。插件因此把缺少对象范围的查询判定为合法，并执行一个必然返回空数据的南向请求。

### 3.2 追问继承仍依赖有限文本列表

身份能力问题修复移除了“所有短句都是追问”的宽泛规则，这是正确的；但当前 `isContinuationPrompt()` 只识别“这个、继续、换成”等固定表达。“那最近7天的呢？”没有命中，因此不继承 NAPM 状态。

不能通过继续追加“那……呢”正则解决，因为“那你呢？”必须继续属于模型直接回答，不能继承 NAPM 工具权限。

### 3.3 `model_owned` 无条件禁止所有工具

模型能够根据完整会话构造正确的结构化查询，但 `before_tool_call` 只看预先确定的 `TurnPolicy`。一旦当前轮为 `model_owned`，即使模型提交的是同一查询的安全时间范围变更，也会被无条件阻止。

### 3.4 查询结果记录有效期不足以支持真实追问间隔

普通查询结果记录默认只保留 90 秒。本次两条消息间隔接近 7 分钟。结果记录不应为最终回答长期复用，但结构化查询上下文需要独立、较长的有效期，才能安全判断后续查询是否属于同一查询族。

### 3.5 流量指标口径不一致

当前配置和文档对 `TPIO`、`BYTIO` 的解释不完全一致：

- `TPIO`：吞吐速率，单位 Kbps；
- `BYTIO`：累计流量，单位 data；
- 部分配置把普通“流量”映射为 `TPIO`；
- 指标语义文档把普通“流量”映射为 `BYTIO`。

对象范围 `TotalTraffic` 与指标 `TPIO/BYTIO` 必须分开表达，不能继续把 `TPIO` 写成“总流量”。

## 4. 设计目标

1. 全局 `timeValues` 查询必须有明确对象范围。
2. 缺少对象范围时在插件边界失败，不得请求南向接口。
3. 不通过扩充短句正则判断上下文查询。
4. 模型提出的只读时间范围追问必须经过上一轮可信结构化查询校验。
5. “那你呢？”等身份追问不得获得查询权限。
6. 空结果可以作为查询上下文，但不能作为下一轮最终答案直接复用。
7. 普通最终回答不显示 Debug API。

## 5. 实现方案

### 5.1 收紧 `timeValues` 查询契约

将 `groups` 加入 `timeValues.required`，从 `optional` 删除。合法全局趋势查询示例：

```json
{
  "service": "timeValues",
  "queryModeKey": "timeseries",
  "groups": [{ "type": "TotalTraffic" }],
  "metrics": ["TPIO"],
  "granularity": 3600,
  "timeRange": { "key": "last24hours" }
}
```

插件继续坚持严格边界：不根据用户原文静默补 `groups`。上游模型必须重新构造完整 `resolvedQuery`。

### 5.2 明确工具契约和模型提示

`napm-skill-query` 工具描述及系统上下文增加：

- 全局、整体或总流量趋势使用 `groups=[{type:"TotalTraffic"}]`；
- `timeValues.groups` 必须非空；
- `TPIO` 表示吞吐速率，`BYTIO` 表示累计字节流量；
- 相对时间追问必须提交完整查询，不允许只提交新的时间字段。

### 5.3 增加独立查询上下文

在 `ConversationOperationState` 中增加轻量级查询上下文记录：

```text
conversationKey
turnId
sourceTool
resolvedQuery
updatedAt
```

约束：

- 只记录成功的 `napm-skill-query`；
- `rows=[]` 仍属于成功执行，可以记录；
- 不保存或复用数据行作为新一轮最终回答；
- 默认有效期 30 分钟；
- `/new`、`/reset` 和会话清理同时删除；
- 严格按 conversation scope 隔离。

### 5.4 增加结构化上下文追问授权

第一阶段只放行 `timeValues` 时间窗口变更。当前轮即使为 `model_owned`，模型调用 `napm-skill-query` 时仍可进入受控校验：

1. 同会话存在有效的上一轮查询上下文；
2. 上一轮与当前轮均为 `service=timeValues`、`queryModeKey=timeseries`；
3. 指标集合保持一致；
4. 对象范围保持一致；当前查询遗漏对象范围时，只允许进入正常契约错误和单次重构，不静默继承；
5. 时间范围或粒度必须发生变化；
6. 当前 `resolvedQuery` 继续经过全部既有边界校验；
7. 其他 Tool、其他服务或同查询原样重放继续阻止。

授权后，本轮内部提升为 `napm_candidate`，并记录父查询 `turnId`。身份问题没有结构化时间变更，不会满足授权条件。

后续如需扩展到 `topValues`、`averageValues`、`overview`，必须分别增加查询差异策略和回归证据，不在本次直接放开。

### 5.5 统一流量指标语义

采用以下规则：

| 用户语义 | 指标 |
|---|---|
| 流量趋势、流量速率、吞吐、带宽 | `TPIO` |
| 流量总量、累计流量、流量大小、字节数 | `BYTIO` |
| 全局/整体/总流量对象范围 | `TotalTraffic` |

指标别名使用最长语义优先，使“流量趋势”命中 `TPIO`，普通“流量/累计流量”命中 `BYTIO`。

### 5.6 收口空结果和 Debug API 输出

- 合法查询返回空数组时，只陈述对象、指标、时间范围和“未返回数据点”；
- 没有失败分类证据时，不推测采集异常、权限或数据延迟；
- `final_answer_mode` 不输出 `requestUrl`；
- 只有显式开启上游 API 调试配置时才追加脱敏 Debug API。

## 6. 测试范围

### 6.1 查询契约

- `timeValues` 缺少 `groups` 返回 `incomplete_resolved_query`；
- `TotalTraffic + TPIO + granularity + timeRange` 通过；
- 工具描述明确提示全局趋势对象范围。

### 6.2 上下文追问

- 上一轮成功但 `rows=[]`，7 分钟后“那最近7天的呢？”允许执行；
- 当前追问缺少 `groups` 时进入结构化重构错误，而不是 `model_owned` 通用阻止；
- “那你呢？”即使在 NAPM 查询后也不允许工具执行；
- 不同 conversation 不能共享查询上下文；
- 查询上下文超过有效期后不再授权。

### 6.3 指标和输出

- “流量趋势”映射 `TPIO`；
- “累计流量/流量最高”映射 `BYTIO`；
- 普通最终回复不包含 Debug API；
- 显式调试模式下 URL 仍保持凭据脱敏。

## 7. 验收标准

企业微信新会话执行：

```text
最近一天的总流量的趋势怎么样？
那最近7天的呢？
```

必须满足：

1. 两轮各调用一次 `napm-skill-query`；
2. 两轮均携带 `groups=[{type:"TotalTraffic"}]`；
3. 第二轮使用 `last7days`，不再要求用户重复确认；
4. 返回内容说明指标名称、单位、对象范围和时间范围；
5. 不出现无证据的采集异常推测；
6. 不出现 Debug API；
7. 随后询问“那你呢？”时正常回答身份且不调用 Tool。
