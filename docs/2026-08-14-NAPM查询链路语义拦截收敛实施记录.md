# 2026-08-14 NAPM 查询链路语义拦截收敛实施记录

## 1. 目标

本次修改处理以下线上问题：

> 最近一周有哪些业务出现较多 HTTP 500 错误？

上游已经构造出合法的 `topValues + PGHTTP500 + WebApplication` Resolved Query，但 plugin 再次读取原始问题，把“有哪些”分类为 `object_inventory`，随后强制要求 `groups + metadata_list`。一次用户请求因此产生 5 次 `object_inventory_contract_mismatch`，且没有任何 `PGHTTP500` 请求到达 NAPM。

本次目标不是增加新的关键词 guard，而是建立以下不变量：

1. 合法 Resolved Query 不因 trace prompt 不同而改变放行结果。
2. prompt 语义 mismatch 默认只观测，不参与执行裁决。
3. 结构化 query contract 继续严格执行。
4. 每轮只允许一次查询重构。
5. 成功 Query Result 不得被后续失败覆盖。
6. 失败尝试必须独立记录并可以终止。

## 2. 问题与根因复盘

### 2.1 正确的查询链路

自然语言只应在查询构造阶段参与语义判断。一旦生成并通过结构校验的 Resolved Query，后续组件应按结构执行，不应再次根据原始 prompt 改写查询类型。

```text
Monitoring Question
  -> 主流程解析/Resolver
  -> Resolved Query
  -> 结构与安全边界校验
  -> NAPM Skill 执行
  -> Query Result
  -> 回复交付
```

在本问题中，正确的 Resolved Query 是：

```json
{
  "service": "topValues",
  "queryModeKey": "topn",
  "metric": "PGHTTP500",
  "metrics": ["PGHTTP500"],
  "topMetric": "PGHTTP500",
  "groups": [{ "type": "WebApplication" }],
  "timeRange": { "key": "last7days" }
}
```

其中“业务”决定对象类型 `WebApplication`，“HTTP 500”决定指标 `PGHTTP500`，“较多”决定降序 TopN，“最近一周”决定 `last7days`。“有哪些”只是自然语言表达的一部分，不能单独覆盖更明确的指标排行语义。

### 2.2 实际故障链路

修改前存在两个并行的语义事实来源：上游已经构造 Resolved Query，plugin 的 `before_tool_call` 又通过原始 prompt 重新分类。旧分类逻辑优先命中“有哪些”，把整句判为 `object_inventory`，随后 `validateObjectInventoryResolvedQuery()` 要求查询必须改成：

```text
service=groups
queryModeKey=metadata
semanticConstraints.operation=metadata_list
groups=[{type:"WebApplication"}]
```

合法的 `topValues` 因而被判为 `object_inventory_contract_mismatch`。这不是 NAPM 不支持 WebApplication 排行，也不是必须先查询对象清单，而是 plugin 用低精度 prompt 规则否定了已经完成的结构化查询。

```text
原问题
  -> 上游正确构造 topValues
  -> plugin 再读原问题
  -> “有哪些”命中 object_inventory
  -> 强制要求 groups/metadata
  -> block topValues
  -> 模型按错误提示重构并重试
  -> 同一 prompt 再次触发相同 block
```

原审计日志证明，一轮会话中出现 5 次 `object_inventory_contract_mismatch`，没有任何 `PGHTTP500` 请求到达 NAPM。后续模型尝试单个业务、改变 group 大小写、改用 drilldown 等方式均无效，因为拦截依据始终是同一个原始 prompt，而不是新 Resolved Query 的结构合法性。

### 2.3 为什么会造成误判

误判由以下因素叠加产生：

1. **关键词粒度过粗**：旧 inventory 规则把“有哪些”视为强意图，没有要求句子中不存在指标、排行、平均或趋势语义。
2. **分类优先级错误**：旧流程先落入 metadata/inventory fallback，明确的 `较多 + HTTP 500` 没有优先成为 TopN。
3. **执行所有权重复**：Resolver 和 plugin 都在决定 service、object 和 operation，二者结论冲突时 plugin 以 block 覆盖上游结果。
4. **trace prompt 被当成执行输入**：工具接口中的 prompt 本应只用于审计和追踪，却被语义 guard 再次用于执行裁决。
5. **重试没有轮次预算**：每次失败都返回“重新构造”，没有 terminal 状态，模型会持续尝试不同形状。
6. **会话原问题持续继承**：后续“查单个业务”等尝试仍绑定最初问题，导致同一 inventory 判断反复生效。
7. **成功与失败状态未分离**：一次成功后出现的后续失败可能覆盖本轮成功记录，造成最终回复仍显示失败。

此外还发现两个独立但会放大链路崩坏的缺陷：周时间表达没有进入统一解析，可能退化为 `last1hour`；`normalizeExecutableQueryShape()` 无条件递归调用自身，命中时会触发栈溢出。

### 2.4 “系统中有哪些业务”为什么不应由 plugin 拦截

纯问题“系统中有哪些业务”确实是元数据清单查询，正确结构为 `groups + metadata + WebApplication`。但“它是元数据查询”不等于“plugin 必须根据 prompt 再做一次语义阻断”。正确的职责划分是：

1. 主流程或 Resolver 根据自然语言构造 `groups` 查询。
2. plugin 检查 `groups` 查询的结构是否完整、service 与 queryModeKey 是否匹配、group 是否合法。
3. Skill 执行元数据查询。

如果上游为纯清单问题构造了结构合法但语义错误的 `topValues`，plugin 默认只记录 prompt/query mismatch，由上游构造质量测试负责修复。这样可以保持“一个执行事实来源”。紧急情况下可临时使用 `enforce` 恢复旧行为，但会同时恢复本次误判风险。

### 2.5 为什么会不停拦截，而不是一次处理完成

旧链路没有“失败尝试属于同一轮”的状态模型。每次工具调用都被当作新的独立请求，执行以下相同步骤：重新读取 active prompt、重新分类、重新比较 prompt 与 Resolved Query、再次 block。错误响应又要求模型重构，因此形成反馈环：

```text
block
  -> RECONSTRUCT_RESOLVED_QUERY
  -> 新工具调用
  -> 使用同一 active prompt
  -> 再次 block
  -> 再次重构
```

对象清单预查询也没有解决问题，因为拿到 WebApplication 列表后，最终排行仍必须调用 `topValues`；只要 semantic guard 继续把原问题认作清单，最终数据查询就必然再次被拒绝。问题不在“清单没查到”，而在“清单查询被错误地当成排行查询的前置许可”。

### 2.6 受影响的查询范围

| 查询类型 | 示例 | 修改前风险 | 修改后行为 |
| --- | --- | --- | --- |
| 纯对象清单 | 系统中有哪些业务？ | 正常走 metadata，但依赖 plugin 二次语义判断 | Resolver 构造 `groups`，plugin 做结构校验 |
| 清单词 + 排行 | 哪些业务 HTTP 500 较多？ | 被误判为 object inventory | `topValues + PGHTTP500 + WebApplication` |
| 清单词 + HTTP 400 | 有哪些业务 400 错误最多？ | 同类误拦截或错误重构 | `topValues + PGHTTP400` |
| 清单词 + 平均值 | 哪些业务平均响应时间较高？ | inventory 抢占 average | 明确平均语义优先 |
| 清单词 + 趋势 | 哪些业务最近一周错误趋势上升？ | inventory 抢占 timeseries | 明确趋势语义优先 |
| 原问题后的单对象重试 | 查一下 Zabbix-web 的 HTTP 500 | 继承原 prompt 后继续被拦 | 以合法 Resolved Query 为准 |
| 周时间表达 | 最近一周、近两周 | 可能退化为 `last1hour` | 分别解析为 `last7days`、`last14days` |
| 多次无效重构 | 同轮连续提交非法 query | 无限返回重构提示 | 一次修复后 `STOP_RETRYING` |
| query shape 归一化 | 进入 executable normalization | 可能递归栈溢出 | 复用 top-level normalization |

原则上，任何同时包含“有哪些/哪些/列出”和更强数据操作词的混合问法都可能受到旧分类优先级影响。对象范围不只限于 WebApplication，也包括使用相同 prompt 分类和 boundary guard 的 DefinedApp、BusinessGroup 及其他目录对象。

### 2.7 哪些 guard 保留，哪些 guard 收敛

本次没有删除所有拦截。系统中的 guard 分属不同职责，处理策略如下：

| Guard 类型 | 处理策略 | 原因 |
| --- | --- | --- |
| Resolved Query 结构校验 | 强制保留 | 防止缺字段、非法 service、错误时间和不支持的执行形状进入 NAPM |
| 安全与越界校验 | 强制保留 | 防止非 NAPM 请求、危险参数或错误工具越权执行 |
| 明确工具路由约束 | 按场景保留 | 报告、告警数据包等有独立工具和交付契约 |
| prompt/query 语义一致性 | 默认改为 `shadow` | 只用于发现上游构造问题，不再否定合法结构化查询 |
| 回复去重与结果保护 | 保留并深化状态 | 防止重复发送以及失败覆盖成功 |

需要继续收敛的是“在多个 hook 中重复解释自然语言并改写同一查询”的实现，而不是结构、安全和工具权限边界本身。

## 4. 修改过程与实施决策

修改按以下顺序完成：先用失败测试固定线上问法和重复重试行为；再把 prompt 语义守卫降级为 shadow；随后调整分类优先级、Resolver 顺序、指标和时间别名；然后引入单轮修复预算与成功结果保护；最后修复 query shape 自递归，运行全量回归并发布到测试服务器。每一步都先验证当前反馈环，再进入下一步。

### 4.1 Resolved Query 是查询执行的唯一事实来源

`napm-skill-query` 的 interface 已声明 prompt 为 trace-only，因此 plugin 在收到合法 Resolved Query 后不得根据 prompt 再次决定 `groups`、`topValues`、`averageValues` 或 `timeValues`。

旧的 inventory 语义判断仍保留为短期观测 implementation：

- 默认：`NAPM_QUERY_SEMANTIC_GUARD_MODE=shadow`
- 旧行为：`NAPM_QUERY_SEMANTIC_GUARD_MODE=enforce`
- 关闭观测：`NAPM_QUERY_SEMANTIC_GUARD_MODE=off`

`shadow` mismatch 写入审计事件 `napm_plugin_prompt_query_semantic_mismatch_observed`，但不 block 查询。

### 4.2 结构校验继续强制执行

以下校验没有删除：

- service 是否注册
- queryModeKey 是否与 service 匹配
- 必填字段、metrics、topMetric
- 根级 start/end 与分钟对齐
- groups 形状
- 时间物化
- skill 执行 adapter 前的 QueryValidator 与 ExecutionKernelPolicy

合法 query 与 prompt 的关系不再由 plugin 裁决；非法 query 仍会被 `validateResolvedQueryAgainstSpec()` block。

### 4.3 单轮执行状态深化

`ConversationOperationState` Module 新增独立 query failure 状态：

- `rememberQueryFailure()` 记录失败指纹、attemptCount 和 terminal
- `getQueryFailureForTurn()` 给输出 adapter 读取本轮类型化失败
- 默认 queryRepairBudget 为 1
- 第二次失败，无论相同还是不同结构，进入 terminal
- 相同失败指纹设置 `duplicate=true`
- 已有明确成功时，后续明确失败不能覆盖成功记录

第一次结构失败返回 `RECONSTRUCT_RESOLVED_QUERY`；第二次失败改为 `STOP_RETRYING`，避免无限重构。

### 4.4 混合意图优先级

`WorkflowClassifierService` 现在按以下顺序处理高确定性数据操作：

```text
drilldown / metric inventory
→ trend
→ average
→ ranking
→ object inventory
→ overview
```

排行词表补充 `较多/更多/偏多/较少/更少/偏少`。纯“系统中有哪些业务”仍为 object inventory；“有哪些业务 HTTP 500 较多”变为 metric TopN。

`NapmResolvedQueryResolverService.resolvePrompt()` 先解析 TopN，再解析 metadata，避免 metadata fallback 抢占明确排行。

### 4.5 指标与时间别名

两份 resolution spec 同步补充：

- `HTTP500`、`HTTP 500`、`500错误`、`500 错误` → `PGHTTP500`
- `HTTP400`、`HTTP 400`、`400错误`、`400 错误` → `PGHTTP400`

`ResolvedQueryTimeRangeService` 统一支持：

- 最近一周 → `last7days`
- 近两周 → `last14days`
- 带数字或中文数字的“周/星期”表达

### 4.6 直接缺陷修复

`RequirementParserService.normalizeExecutableQueryShape()` 原先无条件调用自身。现改为先调用已有 `normalizeTopLevelQueryShape()`，再完成 metric 去重和大写归一化。该修改复用现有 seam，没有增加新的 shallow Module。

随后通过 Skill 执行同一结构化查询。NAPM 接口返回 HTTP 200，请求参数包含 `type=topValues`、`groupType1=WebApplication`、`metrics=PGHTTP500`、`topMetric=PGHTTP500`，返回 7 条业务记录，结果契约为 `ok=true`。

第一次从交互式 SSH 子进程执行数据冒烟时没有加载 OpenClaw 根级 `.env`，因此得到 `Missing required environment variable: NETINSIDE_HOST`。核对配置来源后，子进程显式加载与网关相同的根级和 workspace dotenv 文件，再次执行成功。该失败未经过网关、未改变服务状态，也不是本次发布代码的运行错误。

### 7.4 待完成验收

当前技术冒烟已完成，仍需从企业微信执行真实会话验收，并继续覆盖：纯业务清单、HTTP 400/500 排行、平均、趋势、overview、告警、报告和数据包问题集。验收时应确认：

1. 审计日志出现 `napm_plugin_resolved_query_forwarded`。
2. 如存在语义分歧，可出现 `napm_plugin_prompt_query_semantic_mismatch_observed`，但 `enforced` 必须为 false。
3. 目标问题不得出现 `napm_plugin_resolved_query_blocked` 或 `object_inventory_contract_mismatch`。
4. NAPM 请求必须使用 `topValues`、`PGHTTP500` 和 `WebApplication`。

如发现上游持续生成错误 Resolved Query，可临时设置：

```text
NAPM_QUERY_SEMANTIC_GUARD_MODE=enforce
```

该开关会恢复旧语义 guard，仅用于紧急回滚和问题定位；它也会恢复本次误判风险。

## 8. 未纳入本次修改

- 上游 OpenClaw 的完整 QueryPlan 编译仍不在本仓库的生产调用链内。本次保证 plugin 不破坏合法 Resolved Query，但不能证明所有自然语言都一定被上游构造正确。
- `message_sending` 与 `before_message_write` 仍有重复 delivery implementation。本次只让它们在没有成功时读取本轮 query failure；完整 ReplyDeliveryPolicy Module 收敛需要独立变更。
- `PromptRoutingService` 和旧 prompt validator 尚未删除。先通过 shadow 审计确认无必要拦截，再删除可降低发布风险。
- 企业微信真实会话和完整问题集尚待人工验收；本次已完成服务器发布、插件边界冒烟和 NAPM 只读数据冒烟。

## 9. 后续删除条件

满足以下条件后，可以删除 legacy prompt semantic guard implementation：

1. 测试服务器 shadow 问题集无必须依赖旧 guard 的案例。
2. 线上 shadow 审计窗口内，mismatch 均由合法结构化 query 正确处理。
3. 上游 Resolved Query 构造有独立回归问题集。
4. `enforce` 模式连续一个发布周期未被启用。

删除后，plugin hook 只保留结构契约、安全策略、trace 绑定和薄 adapter 职责，从而提高 query contract 的 locality 与 leverage。
