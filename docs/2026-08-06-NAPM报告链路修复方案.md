# NAPM 报告链路修复方案

日期：2026-08-06  
适用范围：`napm-summary`、`napm-inspection-snapshot`、`napm-fault-diagnosis`、`napm-alert-query`、`napm-skill-query`、`napm-packet-analysis` 与 `napm-report-export` 的跨工具报告流程。

## 1. 问题结论

生产插件的报告流程依赖插件进程内的 `ConversationOperationState` 保存上一个工具的 `reportData`。生产 WeCom/微信运行上下文通常只提供 `sessionKey`，但当前 `getConversationKey` 要求 `channelId`、`accountId`、`conversationId` 三项全部存在。

因此真实链路是：

```text
工具生成 reportData
  -> 会话键为空
  -> traceId 不注入
  -> reportData 不写入状态
  -> napm-report-export 取不到结果
```

这不是 `summary` 独有问题。六类报告源使用同一套状态写入逻辑，在 sessionKey-only 上下文中都会失败。

此外还存在三个共性风险：

1. 报告源只在内存中保存，网关重启、进程分流或 90 秒 TTL 到期后丢失。
2. 使用“同会话最新 NAPM 结果”作为报告源，中间任意一次查询都可能覆盖原报告，导致导出错误报告。
3. 工具结果中的 `details.reportData` 会被会话持久化层截断，不能要求模型复制完整 `reportData` 作为兜底。

旧版全局 `latestNapmResult` 虽然减少了“找不到结果”，但会造成跨会话数据泄漏，不能恢复该方案。

## 2. 目标

- 所有报告源在 WeCom、微信和其他入口都能使用稳定的会话范围。
- 报告导出不依赖模型搬运大对象。
- 网关重启后，未过期报告仍可导出。
- 不同会话不能读取彼此的报告源。
- 多个报告并行生成时，导出必须绑定正确的报告源。
- 本地源码、部署包、Skill 根目录和工具清单保持一致。

## 3. 方案

### 3.1 统一会话范围

新增 `ConversationScopeResolver`，优先使用可信运行时 `ctx.sessionKey`，回退到完整的 `channelId/accountId/conversationId` 组合：

```js
function resolveConversationScope(ctx = {}) {
  const sessionKey = String(ctx.sessionKey || '').trim();
  if (sessionKey) return `session:${sessionKey}`;

  const parts = [ctx.channelId, ctx.accountId, ctx.conversationId]
    .map(value => String(value || '').trim());
  return parts.every(Boolean) ? `conversation:${parts.join(':')}` : '';
}
```

该范围只能从可信 Hook 上下文获取，不能从模型传入的普通参数推断。不能再提供无范围的全局最新结果兜底。

### 3.2 引入报告源存储

新增 `ReportSourceStore`，在单机阶段使用本地短期文件存储：

```text
/home/netinside/.openclaw/state/napm-report-sources/
```

建议每个报告源使用随机 `reportSourceId`，记录如下：

```json
{
  "reportSourceId": "rps_<uuid>",
  "ownerScopeHash": "<sha256>",
  "sourceTool": "napm-summary",
  "reportType": "summary_report",
  "createdAt": 0,
  "expiresAt": 0,
  "reportData": {}
}
```

写入使用临时文件加原子重命名，目录权限为 `0700`，文件权限为 `0600`。建议报告源保留 30 分钟、每个会话最多 20 条、单条不超过 5MB，并清理密码、Token 和认证 URL。

### 3.3 在生产者边界标准化

每个报告源工具执行成功后，立即使用现有 `ReportInputContractService` 转换为 `openclaw_napm_report_data.v1`，再写入 `ReportSourceStore`。不要在导出阶段猜测 `result.reportData`、`details.reportData` 等多个结构。

工具返回短文本和 `reportSourceId`，完整数据留在插件内部：

```text
报告数据编号：rps_<uuid>
```

### 3.4 导出按 ID 取数

`napm-report-export` 增加 `reportSourceId` 参数，取数顺序为：

1. 显式 `reportSourceId`。
2. 同会话唯一且未过期的报告源。
3. 多个候选时返回 `REPORT_SOURCE_AMBIGUOUS`，禁止猜测。
4. 无结果时返回明确的范围、过期或不存在错误。

禁止使用通用 `getLatestSkillResult(scope)` 作为报告源。该状态仍可用于防止推理泄漏，但不能承担报告数据交接职责。

错误码至少包括：`REPORT_SCOPE_MISSING`、`REPORT_SOURCE_NOT_FOUND`、`REPORT_SOURCE_EXPIRED`、`REPORT_SOURCE_FORBIDDEN`、`REPORT_SOURCE_AMBIGUOUS`。

### 3.5 失败边界

报告请求失败时，只允许返回受控错误。报告意图下禁止调用 `exec`、`write` 或直接运行报告脚本，避免模型绕过插件链路手工拼装 Word。

### 3.6 部署一致性

生产端当前存在扩展内置 Skill 和工作区 Skill 两份副本。应将完整扩展和所有报告 Skill 纳入本仓库，生成唯一发布包；启动时校验九个工具的入口文件、manifest 和发布版本哈希。禁止因目录存在与否静默切换 Skill 根目录。

## 4. 实施顺序

### P0：恢复功能

1. 以生产当前版本为本地开发基线。
2. 接入 `sessionKey` 会话范围解析。
3. 增加会话缺失和 trace 绑定审计。
4. 禁止报告意图调用 `exec/write`。

P0 可以恢复同一进程、短时间内的全部报告导出，但不是最终方案。

### P1：消除跨工具内存依赖

1. 实现 `ReportSourceStore`。
2. 六类报告源统一生成 `reportSourceId`。
3. `napm-report-export` 按 ID 和会话范围读取。
4. 保留旧内存路径一个兼容周期，并记录迁移告警。

### P2：发布治理

1. 清理重复 Skill 副本，固定 `OPENCLAW_SKILLS_ROOT`。
2. 增加发布包版本和入口校验。
3. 使用原子目录发布和可回滚备份。
4. 多实例部署时将 `ReportSourceStore` 替换为 Redis/数据库实现，保持同一接口。

## 5. 回归测试与验收

- 六类报告在只有 `sessionKey` 的 WeCom/微信上下文中均可导出。
- 报告源之间插入其他 NAPM 查询，不会导出错误报告。
- 重启 Node 进程后，未过期 `reportSourceId` 仍可导出。
- 不同会话读取同一 ID 返回 `REPORT_SOURCE_FORBIDDEN`。
- 过期、损坏、缺失和多候选分别返回明确错误。
- 工具结果详情被截断时，仍可使用 `reportSourceId` 完成导出。
- 每个工具入口和实际加载 Skill 版本通过部署烟测。
- 审计链完整记录 `report_source_stored`、`report_export_source_resolved`、`report_generated`，不记录原始 `reportData`。

## 6. 结论

`sessionKey` 回退是当前故障的止血修复；`ReportSourceStore + reportSourceId + 会话权限校验` 才是覆盖所有报告类型、能抵抗重启和并发的项目级修复。报告模板和 NAPM 数据口径属于独立问题，应在本链路稳定后单独验收。

## 7. 实施与验收记录

### 7.1 实施内容

已在 2026-08-06 完成以下修改：

1. 新增 `plugin/ConversationScopeResolver.js`，优先从可信运行时上下文读取 `sessionKey`，并保留完整 `channelId/accountId/conversationId` 组合作为回退；不再相信模型参数中的会话标识。
2. 新增 `plugin/ReportSourceStore.js`。六类报告数据生产工具统一将标准化后的 `reportData` 保存为带会话权限的 `reportSourceId`，使用文件原子重命名、30 分钟 TTL、每会话容量限制和敏感字段脱敏。
3. `napm-report-export` 改为优先按 `reportSourceId` 读取并校验会话范围；没有 ID 时只接受同会话内唯一的未过期源，多候选明确返回 `REPORT_SOURCE_AMBIGUOUS`，禁止猜测“最新结果”。
4. 新增 `plugin/TrustedToolContextStore.js`。真实 OpenClaw 运行时的 Hook 和工具执行可能使用不同插件模块实例，因此可信 `traceId -> 会话范围` 映射同时写入 5 分钟短期持久化存储，工具侧在内存未命中时回退读取该存储。
5. Hook 注册调整为优先使用 OpenClaw 2026.5.4 的 `api.on(...)`。对冻结的工具参数创建副本后返回带 `traceId` 的新参数，避免直接修改失败；报告意图下继续阻止 `exec`、`write` 和脚本绕过。
6. 补齐报告审计：成功解析报告源时写入 `report_export_source_resolved`，成功生成文件时写入 `report_generated`。审计仅保存 ID、类型、格式和范围哈希，不保存原始 `reportData`、凭据或报告正文。

### 7.5 后续约束

- 当前实现适用于单网关实例。若部署为多实例，必须将 `ReportSourceStore` 和 `TrustedToolContextStore` 替换为 Redis 或数据库实现，接口与权限语义保持不变。
- 不应把工作区中的旧插件副本当作运行时入口。发布应继续以扩展实际加载目录为准，并在每次发布后检查哈希、语法和服务状态。
- 本轮保留本地既有未提交工作区改动，未执行 Git 提交或代码仓库推送；测试服务器已完成部署。
