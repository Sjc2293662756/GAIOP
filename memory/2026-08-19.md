## rc.11 告警正确转录但企业微信发送错误的根因与修复

- rc.11 真实测试发现企业微信仍收到包含 Top5、代表性事件和主要触发指标的模型自由摘要，不符合告警 Skill 的七分类确定性格式。
- 远端 11:40 会话证据确认：`napm-alert-query` 正确生成 1198 字符 canonical `displayText`，模型另生成 773 字符自由摘要；`before_message_write` 将 1198 字符文本写入会话 JSONL，但企业微信 final payload 仍发送 773 字符文本，且当前链路没有触发 `message_sending`。
- 根因是 rc.11 把 `before_message_write` 和 `message_sending` 当作生产最终发送入口；在 OpenClaw 2026.5.4 的当前 WeCom agent-final 链路中，前者只拥有转录写入，后者未参与该次发送。直接调用 Hook handler 的单元测试和远端 smoke 因此形成假阳性。
- 新增 `docs/2026-08-19-NAPM告警查询真实发送链路修复方案.md`，改用项目已经验证的原生 `reply_dispatch` 和 `dispatcher.sendFinalReply({ text })` 交付当前轮告警 canonical 文本，并返回 `handled=true` 阻止默认模型文本发送。
- 新交付路径继续严格校验当前会话、当前 `turnId`、`sourceTool=napm-alert-query` 和成功告警结果；综述/Word/PDF、告警数据包、无结果、跨轮和其他 Tool 均不接管。
- 使用 `prepareFinalContent()` 和 `claimPreparedFinalDelivery()` 做 `conversationKey + turnId` 单次认领，重复 dispatch 返回 handled 但不再次排队，并写入专用审计事件。
- 新增真实 `ReplyDispatcher` 形状的成功、重复、无结果、跨轮和报告隔离测试。定向组合回归 67/67 通过；全量 92/92 Jest 套件、700/700 测试、lint、8 个生产 Tool 运行时契约、Node 语法和 `git diff --check` 全部通过。
