# 2026-08-30

## NAPM 查询轮次统一决策与澄清机制

- 根因：`napm-skill-query` 适配器把缺少具体应用名的正常澄清记录为 `ok=false/error`，`before_tool_call` 又提前阻断 Tool；输出 Hook 因没有可验证 Skill 结果，把模型的正确追问覆盖成 generic guard。
- 新增 `QueryDecisionPolicy`：统一输出 `ASK_CLARIFYING_QUESTION`、`EXECUTE_QUERY`、`REJECT_QUERY`，复用 Resolution Spec 参数策略。
- `conversationKey` 仅表示 scope；`message_received` 为每个 run/message 创建不可变 `turnId` 绑定，Tool 和输出 Hook 禁止读取会话 latest turn；缺少 run/message 身份或绑定时 fail-closed。
- Query Turn route 在 begin 后不可变；普通查询调用错误的其他生产 NAPM Tool 会被阻断，不能通过 Tool 结果把 `NAPM_QUERY` 改成 `OTHER_SKILL`。
- `QueryTurnCoordinator` 统一保存 Query Draft、construction/execution Attempts、一次修复预算、pending clarification、所有 terminal `finalContent` 和 delivery claim；旧 `ConversationOperationState` 不再是普通查询修复、结果或交付权威源。
- 首次技术校验失败进入 `REPAIR_PENDING`，同 `attemptId` 重放幂等，修复后的第二个失败终止；执行失败立即终止；所有 terminal write-once，终态 Tool 重放不再调用 Query Skill 或南向接口。
- `napm-skill-query` Tool 现接受 `queryDraft`，迁移期兼容 `resolvedQuery`。澄清返回 `ok=true`、`isError=false`、无 `error`，且不调用 Query Skill 或南向接口。
- “应用流量趋势”不得降级为 `TotalTraffic`；缺应用名时追问具体应用。明确总流量问题仍使用 `TotalTraffic`。
- 澄清后用户下一轮只回复应用名（例如 `HTTP`）时，模型以 `clarificationAnswer` 调用 Tool；应用语义误构为 `TotalTraffic` 时先由 Policy 规范化为 `DefinedApp` pending Draft，插件再创建新 turn、恢复 pending Draft、补 `DefinedApp.argument=HTTP` 并执行，模型不重建完整 Query Draft。
- `before_message_write` 与 `message_sending` 读取同一 run-bound Query Turn。`RESULT`、`NO_DATA`、澄清、拒绝、失败和 `CONTRACT_VIOLATION` 都由 Coordinator 生成权威内容并 exactly-once 交付；流式 partial 不终结轮次。
- 非流式最终输出到达时，`RECEIVED` 无 Decision/Attempt 以 `MODEL_OMITTED_REQUIRED_TOOL` 终结为 `CONTRACT_VIOLATION`，`REPAIR_PENDING` 终结为 `VALIDATION_FAILURE`，`DECIDED` 且 adapter 未开始执行以 `QUERY_TOOL_EXECUTION_NOT_STARTED` 终结为 `CONTRACT_VIOLATION`，`EXECUTING` 无结果以 `QUERY_EXECUTION_RESULT_MISSING` 终结为 `EXECUTION_FAILURE`。所有路径都生成权威答复，迟到结果不能覆盖，重复发送会取消；`OTHER_SKILL` 轮次不由普通查询 Coordinator 抢交付。
- Hook 和 direct execute 统一执行高风险策略：应用/`TotalTraffic` 范围、`CompositeApplication`/一般对象清单和对象清单单 group 约束；失败路径不产生错误南向调用。
